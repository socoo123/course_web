# Project 2：把一棵树写成可检查的不变量

导航：[全部要求与固定接口](#/c/cmu-15-445-2025/lab/project2?v=zh) · [Project1资源生命周期](#/c/cmu-15-445-2025/lab/project1?v=guide) · [L10并发笔记](#/c/cmu-15-445-2025/lec/lec10?v=notes) · [公共资料](#/c/cmu-15-445-2025)。

本文不提供可直接提交的代码、完整插删伪代码或公开用例的最终树形。你需要自己决定拆分方法、页操作和锁协议；这里提供的是每一项决定必须回答的问题、错误反例和自测方向。

## 1. 开始前画三张账本

先确认 Project1 的 guard 移动、Drop、最后 unpin、dirty、替换和死锁问题已经解决。B+Tree 读错页不一定是比较器错，也可能是 frame 被提前复用；多加一把树锁无法修复错误的 BPM 生命周期。

### 1.1 页身份账本

建议每行记录：索引 page id、当前 frame id、页类型、物理 size、max/min、叶 next id、持有的 guard、当前允许的操作。业务 key 与 RID 另列。

例如订单号是业务排序依据，RID 定位表记录；叶槽号只定位当前叶数组中的一项。分裂后叶槽号可改变、索引 page id 可改变，而表记录 RID 可以完全不变。若你把槽号写回 RID，点查可能“返回了一个数字”，却已不再指向原记录。

### 1.2 可见性账本

对每个叶同时记三列：

1. **物理数组**：所有 key/RID，包含已 tombstoned 的项；
2. **待兑现删除**：按旧到新列出 tombstone 所指的 key，并保留当前物理下标；
3. **逻辑视图**：过滤 tombstone 后的有序活跃项。

这三列不能合并。只拿一个 `size` 同时当物理项数和活跃项数，会在容量判断、删除、迭代三个地方产生相互矛盾的“修复”。

### 1.3 锁与资源账本

每次操作标出：已经持有的 header／祖先／当前叶／兄弟 guard；等待什么；何时可以释放；释放后还有哪些指针或引用可能被使用。pin 与 latch 分两列，别把“页还在内存”写成“页不会被别人修改”。

## 2. 页内设计：先定义不变量，再决定辅助方法

### 2.1 建议逐项写在私有设计笔记中

| 层次 | 每个对外可观察的稳定状态应成立 |
|---|---|
| 字节布局 | 索引页结构和使用到的数组项不越过8192字节；动态容量不超过实际布局允许的上限 |
| 基础头 | type与实际解释一致；size、max/min遵守自己的占用约定，初始化不是碰巧依赖全零 |
| 内部页 | 第0个key不参与比较；每个有效child与自己的路由区间一致；有效分隔键数比child数少一 |
| 叶数组 | 物理key有序，每个RID与对应key一起移动，不能两个数组各自排一次序 |
| tombstone | 下标合法且唯一，指向正确key；数目不超过k，返回次序是旧到新 |
| 叶链 | 所有叶按范围连通，不漏叶、不成环，最终next为invalid |
| 整树 | 所有叶深度相同；父路由覆盖全部子树；根的身份与header一致 |
| 资源 | 页内指针／引用只在相应保留及访问权限有效时使用；每份guard责任释放一次 |

这是稳定状态清单，不是要求多字段更新的每一条机器指令都向其他线程公开。必须能说明“中间状态由哪些 latch 遮住”。

### 2.2 容量与取整不能靠猜

先在纸上分别推导 internal 与 leaf 的实际布局预算，再选择 runtime max/min 和结构调整时机。非零 k 会消耗叶内空间；大小不同的 `GenericKey` 会改变容量；内部 value 是页号，叶 value 是 RID。

骨架允许自行处理半满取整和分裂时机，但自由选择不是免除证明。至少考虑小的奇数／偶数容量、根叶、只有一个孩子的根、插入前／后的瞬间占用。若使用“先插入再分裂”，应能指出临时多出来的一项到底存在哪里，不能让一个越界写侥幸被后面的分裂掩盖。

### 2.3 比较器是一份接口，不是整数捷径

`GenericComparator` 的调用结果为 -1／0／1。检查所有分支是不是分别处理“小于、相等、大于”，尤其是等于内部边界时去哪个子树。`ToString()` 和 `SetFromInteger()` 是测试／调试辅助，不是通用索引键语义。

页内二分查找值得早做：一旦找位置的定义稳定，点查、重复键判断、插入位置才不会分别使用不同的边界规则。这里不指定二分实现；先用极小页对“空、首端、末端、精确相等、两键间”逐个解释位置的含义。

## 3. Tombstone：检查的是身份、次序与容量三个维度

### 3.1 首先问清“这次操作有没有物理删除”

k>0 的一次 Remove 可能仅增加逻辑删除，也可能因缓冲已满而兑现旧删除；k=0 则不能依赖任何缓冲槽。因而同样调用 Remove，物理 size 的变化和逻辑可见项数变化不必发生在同一个 key 上。

不要从“刚删的key不可见”推导“刚删的key所在槽已经移走”。这是 tombstone 最常见的混淆。`KeyAt` 看物理项，`GetValue` 和 iterator 看逻辑项，`GetTombstones` 看待兑现项的删除顺序。

### 3.2 一个不含解答的纸面练习

自行选几个不连续订单号，让删除先后顺序与 key 排序不同，固定 k=2。分别安排：

- 两次删除恰好填满缓冲；
- 再删除另一个活跃键，制造兑现最旧删除的压力；
- 在 tombstoned 槽之前插入新键；
- 用不同 RID 重新插入一个逻辑删除键；
- 再次删除已经逻辑删除的键。

每步只填写前述三列账本，自己推导结果；然后检查是否仍能从 tombstone 下标还原正确 key。不要拿本页的序列当公开测试答案，事实上这里没有规定具体数值或最终状态。

### 3.3 三个容易“看似正确”的错误

**按key大小排序 tombstones。** 点查可能都正确，但下一次容量压力会兑现错误的删除；分裂测试也观察相对次序。

**数组压缩后保留旧下标。** 数据本身仍有序，却把旁边活跃key标成已删。症状可能只在迭代时出现，比越界更隐蔽。

**遇到结构变化就清空所有tombstones。** 逻辑集合暂时相同，但破坏固定k的延迟删除行为与删除历史；该项目不只检查最后可见集合。

### 3.4 每种结构变化都做两份证明

| 操作 | 数据／路由证明 | tombstone证明 |
|---|---|---|
| 页内插入 | key/RID仍配对且有序 | 旧待删除项仍指向同一key |
| 兑现物理删除 | 只移除应兑现的项，容量正确 | 余下下标重映射，旧到新次序保留 |
| 分裂 | 两叶范围与父边界、next链一致 | 每个待删除项归属正确叶，每叶保留相对次序 |
| 借位 | 捐出／接收双方及父边界仍合法 | 搬入待删除项按“比接收者已有项更新”的规则解释 |
| 合并 | 不超布局上限；父child与链连接一致 | 接收叶的旧待删除先于搬入待删除，容量压力按此处理 |
| 复活同键 | 唯一可见项使用新RID | 旧删除标记不再遮住复活项，不留下重复待删除 |

合并方向是设计选择，而一旦选定，谁是 donor、谁是 recipient 必须明确。不能用“左页删除早，所以左页一定更旧”替代题面的迁移规则；也不能将借位中根本没搬动的项错误归入接收页。

### 3.5 空树要分别问两个问题

“没有活跃项吗？”与“没有任何物理页吗？”不等价。带 tombstone 的树可保持物理页但逻辑为空。把 `IsEmpty`、Begin／End、GetValue、再次 Insert 的行为一起考虑；不要为了让其中一个函数简单，提前丢弃全部待删除历史。k=0 的最后物理项删除则要考虑 invalid root 的规范路径。

## 4. 查插删：父边界与根页才是传播的原因

### 4.1 点查应能解释每一次下行

给每个内部 child 标注一个区间，检查目标key为何被选到这个child。对于有效分隔键，固定注释采用左闭右开区间；最左孩子没有有效第0个key，不能把其无效字节拿来比较。

删掉叶首key后，父分隔键不一定必须永远等于“当前叶最小活跃key”：一个仍能正确分隔子树的边界可以继续有效。相反，借位把key搬过边界后，旧路由可能真正失效。**证明区间，不要把某种教材图的精确键值当作唯一树形。** 这也影响乐观删除是否确实只需写叶。

### 4.2 插入需要回答的检查问题

- 首次建树前，header、根页、叶页各自由谁创建／初始化？
- 拒绝活跃重复键时，是否完全保留原RID和结构？
- 同key只是tombstoned时，是否错误地返回重复失败？
- 需要结构变化时，父页能否接收新的路由项？若不能，传播路径是否仍受到保护？
- 叶split是建立新的叶边界，内部split是重组路由；为什么二者不能共享一段未经区分的“搬一半数组”？
- 新页何时对其他线程可达？在发布其页号之前，页类型、容量、内容和链关系是否已合法？

这不是要求对所有路径保留整条祖先链；而是要求在可能传播时有正确的保留／重启协议。

### 4.3 删除需要回答的检查问题

- 不存在和已删除键是否均不改变其他记录？
- 此次逻辑删除是否触发兑现旧删除？物理占用是否实际下降？
- 若需要借位／合并，兄弟选择、父分隔键、next链是否一起更新？
- 内部父页失去child后，是否可能继续向上影响占用？
- 根收缩后，header是否发布新根？旧根／被移除页是否仍可被已有读者或iterator引用？
- 不能立即释放物理页时，是否有一致的资源规则，而不是持guard调用DeletePage后忽略失败？

不要通过只测试“删到剩一个键”掩盖删除最后一个键，也不要仅用当前页面的大小判断所有祖先都无需处理。

### 4.4 Header不是根内容的一部分

header中只保存root page id；根可能换页，header本身仍由构造器传入的page id标识。`Context::root_page_id_` 是一次操作的辅助快照，不会自动跟随并发变化。

想象线程A读取旧根id后尚未保留根页，线程B让根收缩并回收旧页。A随后凭旧id进入树，是否仍有任何保证？设计应解释“读header—取得根访问权”之间的保护关系，而非只声明root id是一个整数。反过来，始终持header写guard到操作结束虽容易避开这一竞态，却会串行化整棵树并违反要求。

## 5. Iterator：一次递增不一定只加一个下标

用统一的“当前位置可解引用／尾后状态”规则覆盖：首叶开头是 tombstone、叶尾连续 tombstones、中间整叶逻辑空、所有叶逻辑空、跨到最后一叶、空树，以及 `Begin(key)` 位于叶边界。

### 5.1 页内对象与guard必须共存

`operator*` 返回两个const引用，意味着调用者观察的是页内对象，不是独立复制品。要证明：

- 解引用时当前guard有效；
- 返回的不是局部变量／临时对象中的引用；
- 递增换页或iterator销毁后，调用者不会被鼓励继续使用旧引用；
- End不需要为了比较而读取无效页；
- iterator相等不是仅比较槽号：不同页同一个槽号并不相等。

固定类显式声明了析构函数；若你的成员使用 move-only guard，需要自行审视C++移动构造／赋值的生成规则，不能假设“加了成员后编译器仍会自动给出所有移动操作”。这属于资源设计检查，不要求恢复已删除的guard复制。

### 5.2 Begin(key)的范围边界

先看固定声明和用例：已存在的起始键要能正常扫描。对于不存在、被tombstoned、低于全树最小值、高于最大值的输入，写明你采用的下界约定，再设计私有测试；不能把“能找到应在的叶”误当成“该叶一定有可返回的活跃项”。

### 5.3 并发扫描的边界不要过度承诺

官方不测试线程安全叶扫描，并不等于已经提供了快照扫描。普通页latch只能维持结构访问安全，不会让多页扫描自动看到同一事务时刻的数据。若实现并发扫描，应处理兄弟latch无法立即取得的失败／重试契约，而不是持左叶等右叶，另一线程持右叶等左叶。固定公共API没有现成try-read，不要在设计草稿里写一个不存在的方法后就认为问题解决了。

## 6. 并发：safe是一份针对操作的证明

### 6.1 从“为何可以放祖先”倒推条件

safe的含义是：在当前保护关系下，这个操作不会再要求修改已释放的祖先。它不是“当前节点看起来没满”。

| 操作情形 | 判定前要考虑 |
|---|---|
| 新活跃键插入 | 物理项数、预留空间、runtime max、split策略、可能传播的路由变化 |
| 活跃重复键 | 是否真的无需修改，并且重复判断在适当保护下完成 |
| tombstoned同键复活 | 是否仅恢复本页项、是否更换RID与删除状态，而非不必要地新增物理项 |
| k>0的删除 | 是否只加标记，还是兑现最旧删除而改变物理占用；边界仍否有效 |
| k=0或缓冲满的删除 | 物理下溢、借位／合并与父调整的可能性 |
| 根的修改 | 是否创建、分裂、收缩或失效；header是否需要排他保护 |

不要从表中提炼出一个固定 `size > min` 或 `size < max` 就结束；阈值还取决于自己选择的分裂时机及根规则。

### 6.2 乐观不是不加锁

乐观路径假设多数更新只需改叶，因此尽量以读方式经过上层，在目标处判断能否安全完成局部修改。若必须结构变化，必须通过合法重启或更强保护重新获得所需祖先；不能拿已经Drop后的父指针继续写。

在释放读保护、获取写保护之间，另一个线程可能已改变叶内容甚至路由。请标出需要重新核实的事实：目标叶归属、键是否仍存在、容量与tombstone状态、根是否变更。不要将“先前检查过safe”当作跨越无保护窗口仍成立的凭证。

固定公开测试不仅看结果，也用 tracer 检查安全局部插删走过读访问且只取得目标叶的写访问。因此“每次从header一路全写”即使暂时正确，也不满足要求。保留官方 `bpm_` tracer，不要为通过计数绕开它。

### 6.3 三张必须自己画的等待图

1. **重复读锁**：同线程持某页read guard，又调用会再次读取该页的辅助函数；不同平台可能表现不同，不能依赖macOS上的偶然成功。
2. **锁升级**：线程持叶read guard，等待该叶write guard；先解释自己持有的read访问如何消失，不能假设shared mutex支持原地升级。
3. **横向锁序**：两个线程分别持相邻叶，尝试向相反方向取得兄弟；自上而下的树路径顺序没有自动消除这一环。

沿树取得与释放均按题面的header→下层方向。检查deque的哪端是祖先，所有早退／异常／重启是否也遵守同一协议。不要只在正常成功路径释放资源。

### 6.4 结构正确与事务正确是不同目标

线程安全Insert／Remove／GetValue意味着不会因为同时访问而破坏索引不变量，不代表业务级“查库存再减库存”自动原子，也不代表范围扫描没有phantom。当前P2没有实现事务隔离；不要把未来事务项目的锁、时间戳或undo方案塞进来作为替代。

## 7. 自测要覆盖交叉边界，而不是复制公开用例

下面是原创检查矩阵，不是可运行测试或答案。选择自己的小key集合，在私有工作区实现后观察不变量，避免只对某一种最终树形作断言。

| 维度 | 建议交叉情形 | 优先观察 |
|---|---|---|
| 页容量 | 小奇数／小偶数、leaf与internal不同 | 稳定占用、临时越界、根特例 |
| k | 0、1、多个正数；与小页容量组合 | 恰好满缓冲与下一次压力的差别 |
| key | 递增、递减、打乱、负数、边界相等 | comparator和路由区间，而非整数捷径 |
| 重复键 | 活跃重复；删除后同key不同RID；反复删 | 唯一可见项、旧RID不被错误保留或覆盖 |
| 结构 | 叶split、连续向上传播、两向借位、两向合并、根收缩 | 父路由、叶链、tombstone迁移与顺序 |
| 逻辑空 | 一叶全tombstoned、多叶全tombstoned、重新插入 | Begin/End/IsEmpty一致；不强求物理全无 |
| Iterator | tombstone在首／中／尾、连续空叶、Begin(key)各种边界 | 不漏项、不重复、不解引用End、guard驻留 |
| 缓冲 | 较少frame、反复点查和跨叶、作用域早退 | pin是否回落、无意保留整条路径 |
| 并发 | 同键竞争、不同叶更新、稳定键读与邻近分裂／合并 | 唯一性、无等待环、无丢页／错页 |
| 资源 | iterator移动／结束、重启、失败返回、被移除页 | 无悬空引用、重复解锁或泄漏 |

不要以sleep作为并发正确性的依据；使用明确同步点、线程栈和有限重现轨迹诊断。不要把测试故障简单归为“随机问题”：错误通常对应一个缺失的保护边界或无效状态转换。

### 诊断时如何缩小范围

- **点查对、扫描错**：先比对逻辑集合与叶链，再检查跨叶和tombstone跳过；不是先重写分裂。
- **小数据对、规模大错**：检查父递归传播、buffer pin泄漏、实际页布局和二分边界。
- **复活后返回旧RID**：区分活跃重复与逻辑删除恢复，不只看key存在。
- **只在借位后删除顺序错**：区分donor／recipient规则和物理下标重映射。
- **单线程对、并发挂起**：先画等待环，特别是header、重复读锁、升级、兄弟方向和BPM内部依赖。
- **图形与点查矛盾**：固定 `LeafPage` alias遗漏NumTombs，需要检查实际实例布局与调试解释一致；图形工具不是独立正确性oracle。

公开 helper／测试中的某些表达式从临时 `ReadPage` guard取得指针，临时量很快析构。阅读测试是理解意图，**不是照抄不安全的guard寿命写法**；自己的代码必须让有名guard或明确所有权覆盖全部指针使用期。
