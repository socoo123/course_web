# L2 阅读导引：从 SQL 查询走向约束与应用边界

## 先用目录发现课堂没有展开的部分

L2 重点是现代 SQL 的表达能力与方言差异。指定的 Chapters 3–5 范围更广：除了聚合和子查询，还有更新、视图、完整性、授权、程序接口、触发器与递归。阅读时不要把“看完 L2”误认为这些主题已经全部学过。

这份导引不重讲课堂 slides，而是用几个与 Orders/Stock 相关的问题帮助安排独立阅读。与课堂已经重叠的聚合、子查询、窗口推导集中在[本讲笔记](#/c/cmu-15-445-2025/lec/lec02?v=notes)。

## 第 3 章：查得对，还要说清未知值与修改

| 官方目录定位 | 建议带着的问题 | 阅读后可自行完成的小检查 |
|---|---|---|
| §3.2 SQL Data Definition | 表不仅列出列名，还声明哪些事实？ | 区分类型、主键与是否允许 NULL。 |
| §3.5 Set Operations | 去重是语义选择还是显示习惯？ | 用两笔内容相同但编号不同的订单解释差别。 |
| §3.6 Null Values | 未知数量为什么不是数量为零？ | 比较没有订单与有订单但数量未知。 |
| §3.7 Aggregate Functions；§3.8 Nested Subqueries | 输入行、组与子查询结果如何连接？ | 回到笔记核对 COUNT、NOT EXISTS 的反例。 |
| §3.9 Modification of the Database | 查询一个状态，与修改一个状态有何不同？ | 写出“把某订单数量改大”前后需要保持的约束，不写整套作业实现。 |

**原创思考题：** 某报表把 NULL 数量统一显示为 0，是否意味着可以把数据库中的 NULL 全部更新为 0？

<details>
<summary>参考思路</summary>

不意味着。显示层为了阅读方便使用某个替代值，与修改原始事实不同。前者仍可保留“未知”的证据，后者会把未知改写成已知为零，之后无法仅凭这个字段恢复区别。读 §3.6 与 §3.9 时，应分别问“结果如何解释”和“存储事实是否改变”。

</details>

## 第 4 章：把正确性从报表里移到边界上

| 官方目录定位 | 原创阅读任务 |
|---|---|
| §4.1 Join Expressions | 对照内连接与外连接，追踪 Stock 中没有订单的商品会不会消失。 |
| §4.2 Views | 思考固定一个业务查询名称，是否等于存了一份独立结果；不要把视图与物化视图混为一谈。 |
| §4.3 Transactions | 把“检查库存”和“扣减库存”看成一个业务动作，记下为什么两个独立语句之间可能出现问题；事务内部实现留待后续讲次。 |
| §4.4 Integrity Constraints | 哪些规则可以用主键、外键、非空或 CHECK 表达？哪些跨行规则不能随口说一个 CHECK 就能完成？ |
| §4.5 SQL Data Types and Schemas | 区分 DATE、时间点和持续时间；给数量、金额、时间各选类型时先写下需求。 |
| §4.6 Index Definition in SQL | 创建索引改变的是物理访问机会，还是逻辑上“哪些行符合条件”？暂不提前学习索引内部实现。 |
| §4.7 Authorization | 谁可以读取、更新、创建对象？报表只读账户不应自动获得业务库写权限。 |

**原创小任务：** 不写应用程序，只给 Orders 与 Stock 列出三项数据约束和两项权限需求。每一项都说出防止什么具体错误。

<details>
<summary>一种非作业答案式参考</summary>

订单编号唯一，防止两个订单共享身份；商品编号非空，防止订单失去关联目标；若业务禁止负库存，则声明库存非负。权限方面，可让报表角色只读某个允许的业务视图，而负责库存修改的角色才有相应更新能力。这些是需求样例，不是声称所有数据库都用同一条 SQL 实现；实际权限继承、视图安全与并发约束还需目标系统文档。

</details>

## 第 5 章：查询如何嵌入应用，什么时候会出现隐藏行为

| 官方目录定位 | 原创阅读问题 |
|---|---|
| §5.1 Accessing SQL from a Programming Language | 应用参数怎样传给查询？为什么数据值不应该靠字符串拼接混进 SQL 结构？ |
| §5.2 Functions and Procedures | 把业务逻辑放在函数或过程里，怎样界定输入、输出、副作用与调用权限？ |
| §5.3 Triggers | 一条 UPDATE 是否可能引发额外动作？排查错误时，如何避免只看应用发送的那一条语句？ |
| §5.4 Recursive Queries | 普通 WITH 是命名中间关系，递归还需要终止条件。沿商品分类或组织层次遍历时，循环与重复意味着什么？ |
| §5.5 Advanced Aggregation Features | 对照 L2 的汇总与窗口，先确定输出粒度，再查看高级语法。 |

这里不提供递归查询、触发器或存储过程的可提交项目代码。阅读目标是识别它们各自解决的问题与引入的边界，不是把本讲没有讲过的内容冒充课堂逐段译文。

## 与 dbt 演讲连接，但不要混淆层次

嘉宾把 SQL 模型放进版本控制、测试与依赖管理流程。教材的视图、约束、授权和应用接口，则帮助你理解这些模型最终运行在什么数据库语义之上。

可以带着三张清单阅读：

- **关系语义：** 每个模型一行代表什么，是否保留重复，NULL 怎样解释？
- **数据库边界：** 谁能修改源数据，哪些约束由数据库维护，哪些需要应用或数据检查？
- **工程流程：** 变更如何评审、如何在开发环境验证、依赖如何构建？

数据测试发现“订单编号不唯一”，与数据库主键约束拒绝插入冲突数据，并不是同一个时间点上的同一种机制。二者可能互补，不能只因为都检查唯一性就视为可互换。
