# L2 学习笔记：SQL 的答案契约与数据转换流水线

本页用自拟的 **Orders / Stock** 场景推导查询结果，课堂逐段内容见[译稿](#/c/cmu-15-445-2025/lec/lec02?v=draft)，教材目录定位见[阅读导引](#/c/cmu-15-445-2025/lec/lec02?v=materials)。

## 先问四件事，再写 SELECT

“查每种商品的需求量”还不是完整规格。至少要回答：

1. **一行代表什么？** 一笔订单、一种商品，还是某商品在某天的统计？
2. **重复行是否有意义？** 两笔内容相同的订单不能因为投影后相同，就被悄悄当成一笔。
3. **没有值与没有行如何处理？** 未知数量是 NULL；没有订单是零行。这两者不等价。
4. **顺序是什么契约？** “前两笔”需要排序规则；并列时还要决定保留全部还是用唯一键打破并列。

本讲前半讨论如何表达这些要求，后半的 dbt 演讲讨论：当许多查询组成一个长期运行的数据项目时，如何管理依赖、测试与发布。**写对一条 SQL，与维护一条可靠流水线，是不同层次的问题。**

## 贯穿示例与预期答案

**Orders**

| order_id | sku | qty | ordered_on |
|---:|---|---:|---|
| 101 | A | 2 | 2025-08-25 |
| 102 | A | 2 | 2025-08-25 |
| 103 | A | NULL | 2025-08-26 |
| 104 | B | 5 | 2025-08-27 |

**Stock**

| sku | available |
|---|---:|

这里有三个容易混淆的量：A 有 **3 笔订单**，其中 **2 笔数量已知**，已知需求合计 **4**。不能把 `SUM(qty)=4` 解读成 A 的最终全部需求已知；也不能把 `COUNT(qty)=2` 说成只有两笔订单。

## 1. 多重集和 NULL：别让“清理数据”改变问题

课堂定位：**11:26–12:54、14:11–18:26**。

```sql
SELECT sku FROM Orders;
```

得到三个 A 和一个 B。这里保留重复是正确的：我们只投影商品列，没有声明把不同订单合并。若写 DISTINCT，就改成“出现过的商品种类”，输出粒度已经变化。

```sql
SELECT sku,
       COUNT(*) AS order_count,
       COUNT(qty) AS known_qty_count,
       SUM(qty) AS known_demand
FROM Orders
GROUP BY sku;
```

A 的结果是 `(A, 3, 2, 4)`。理由逐项是：COUNT(*) 计算输入行数；COUNT(qty) 忽略 NULL；SUM(qty) 对非 NULL 值求和。一般情况下，空输入或全 NULL 的 SUM 不等于自动得到零，业务是否允许补零要另作决定。

**反例：** `SUM(DISTINCT qty)` 会把两个不同订单中的 2 合并，得到 2。这不是“去掉重复订单”，而是“只对不同的数值求和”。重复检测必须先明确订单的身份与事件的身份。

<details>
<summary>自测：COUNT(1)、COUNT(qty)、COUNT(NULL) 在 A 的三笔订单上分别是多少？</summary>

分别为 3、2、0。常量 1 非空，所以 COUNT(1) 计每行；qty 有一行 NULL；表达式 NULL 每行都为空。不要把课堂特定 WHERE 条件下几种 COUNT 的相等结果推广到任意输入。

</details>

## 2. 聚合改变行的粒度，HAVING 判断的对象也变了

课堂定位：**16:02–24:10**。

![同一订单输入经过分组聚合与窗口计算后，输出粒度不同](assets/group-window.svg)

图为编者根据本讲语义自绘：上支路把三行 A 订单压成一行；下支路保留三行，每行附带同一个商品级统计。未知 qty 不参与求和，但那笔订单仍然是一行。

不能一边把整个输入聚合为一个平均值，一边随意选出一个不受约束的商品名。输出列必须能由该组确定。ANY_VALUE 可以表达“任取一个”，却不能把“任意一个值”变成“有业务意义的代表值”。实际系统对函数依赖等情况可能有额外规则，初学时不要依赖模糊宽松行为。

想筛选“已知需求合计超过 3 的商品”：

```sql
SELECT sku, SUM(qty) AS known_demand
FROM Orders
GROUP BY sku
HAVING SUM(qty) > 3;
```

这里 A、B 都保留。若误写成先 `WHERE qty > 3`，A 的两个 2 都在聚合前被删除，结果就变了。**WHERE 决定哪些输入行参与计算；HAVING 决定哪些计算后的组留下。**

逻辑层次可以记成：

`FROM / JOIN → WHERE → GROUP BY / 聚合 → HAVING → 输出与窗口 → 最终排序 / 截取`

这是帮助解释语义的模型，不是要求执行器按这串顺序逐步物化。优化器可以在等价条件成立时改写。

**一个关键不变量：** A 组的累计状态可写作 `(row_count, known_count, known_sum)`。读完三行应是 `(3, 2, 4)`；最终平均已知数量是 `known_sum / known_count = 2`，不是 `known_sum / row_count = 4/3`。不要让 NULL 悄悄改变分母。

### 同时统计多个粒度

`GROUPING SETS ((sku, ordered_on), (sku), ())` 表达“商品日粒度、商品粒度、总体”三个汇总层级。更高层汇总中的缺席维度常以 NULL 占位，但这不意味着原始数据中的 NULL 就与汇总行相同。

在输出设计中应保留“这是哪一种汇总”的标识；不要只靠 `sku IS NULL` 猜它是否为总计。它是一组结果语义的声明，不是“一定只扫一次表”的性能承诺。

<details>
<summary>自测：SELECT 和 HAVING 都出现 SUM(qty)，是不是一定做两次求和？</summary>

不是。表达式出现次数不等于物理计算次数；系统可能识别共享聚合。应先写清语义，再由执行计划判断具体实现，而不是为了少写一次字符串去依赖某个系统不支持的别名作用域。

</details>

## 3. 子查询的关键是作用域与重复数，不是缩进层数

课堂定位：**47:22–55:26**。

### 成员判断不等于无条件换成普通 JOIN

“有订单的商品”可以描述为：Stock 的 sku 是否属于 Orders 的 sku 集合。对示例而言，A、B 各一行，C 不出现。

但若简单把它改成 `Stock JOIN Orders USING (sku)`，A 会出现三行。原因是普通连接输出匹配的**行对**；存在性判断只问有没有至少一个匹配。

因此，“优化器把子查询改写成连接”不是叫你在文本里机械换成 INNER JOIN。它可能使用半连接、反连接、聚合与其他变换来保持原来的重复数。

### 找没有订单的商品

```sql
SELECT s.sku
FROM Stock AS s
WHERE NOT EXISTS (
  SELECT 1
  FROM Orders AS o
  WHERE o.sku = s.sku
);
```

结果是 C。内层 `s.sku` 引用外层当前行，所以是相关子查询。对 A，存在匹配，NOT EXISTS 为假；对 B 同理；对 C，没有匹配，条件为真。

**编者补充：** `NOT IN` 有 NULL 陷阱。若候选集合中含 NULL，`'C' NOT IN ('A', NULL)` 不是简单的真，而会受 UNKNOWN 影响；WHERE 只保留 TRUE。NOT EXISTS 则根据是否存在满足内层条件的行判断。要证明改写等价，必须把 NULL 前提也列出来。

### 成本直觉，而不是 SQL 文本测速

若外层有 n 行、内层扫描 m 行，真的逐行重跑可能接近 n×m 次检查；若非相关内层只算一次，再建立合适的成员查找结构，便可避免大量重复。相关查询也可能被去相关，不能仅看它引用外层就断言性能差。

相反，“改写成一个巨大连接”若产生庞大中间结果，也可能消耗更多内存。课堂 49:48–50:48 的研究例子恰好提醒：**等价性与代价是两个问题。** 本页未独立阅读所提研究论文，不把其全部算法结论写成已核实材料。

<details>
<summary>自测：把存在性查询改写成 JOIN 后再 DISTINCT sku，总是正确吗？</summary>

不总是。若外层原本允许多行具有相同 sku，DISTINCT 会连外层本来应保留的重复也删除。必须先确定外层键与结果粒度。本页 Stock.sku 唯一时，按 sku 去重可以恢复这个特定例子的结果，但不是一般改写定理。

</details>

## 4. CTE 命名中间关系，LATERAL 表达输入依赖

课堂定位：**55:26–61:42**。

CTE 适合把复杂查询拆成可以命名、检查的关系：

```sql
WITH demand AS (
  SELECT sku, COUNT(*) AS order_count,
         SUM(qty) AS known_demand
  FROM Orders
  GROUP BY sku
)
SELECT s.sku, s.available,
       d.order_count, d.known_demand
FROM Stock AS s
LEFT JOIN demand AS d ON d.sku = s.sku;
```

输出仍以 Stock 中的商品为粒度。C 没有匹配的 demand 行，右侧字段为 NULL。是否把订单数补为零，可以按这个指标的含义决定；但补完数值后，不要忘记区分“没有订单”和“有订单但数量全未知”。

CTE 的名字是语句内的组织方式；它不保证建临时表，不保证只执行一次，也不等于带参数的函数。递归 CTE 是另一种能力，课堂没有展开，教材目录导引将它列为后续阅读。

LATERAL 的核心则是**后面的 FROM 项能使用前面输入项的值**。例如，对每个 Stock 商品计算自己的订单统计。理解它时可以画依赖箭头，而不是只背关键字位置。

- 依赖输入：当前商品的 sku。
- 内层结果：只针对该 sku 的统计关系。
- 外层保留策略：内层无行时，是丢掉当前商品，还是保留并填空？这取决于连接形式。
- 聚合特别情况：没有 GROUP BY 的 COUNT 通常仍返回一行统计值 0，不能把它与“内层返回零行”混淆。

SQL Server 的 APPLY 与标准 LATERAL 有相关用途，但语法不应混写。此页是语义学习，不提供未经版本核验的跨产品转换表。

## 5. 窗口：保留明细，又拿到商品级上下文

课堂定位：**61:42–64:33**。下列完整窗口框架与并列处理是编者扩展，老师受时间限制没有把它们全部讲完。

```sql
SELECT order_id, sku, qty,
       SUM(qty) OVER (PARTITION BY sku) AS known_demand,
       ROW_NUMBER() OVER (
         PARTITION BY sku
         ORDER BY ordered_on, order_id
       ) AS sequence_no
FROM Orders
ORDER BY sku, ordered_on, order_id;
```

A 的三行都保留，并附上 `known_demand=4`；行号依次为 1、2、3。与 GROUP BY 相比，输入明细没有被压缩掉。

两个 ORDER BY 各有职责：

- OVER 内的 ORDER BY 定义窗口计算中 A 的行先后。
- 最外层 ORDER BY 定义读者看到的结果顺序。
- `order_id` 是同日订单的稳定次级键。只按日期，两笔同日订单之间的编号次序未被完全定义。

想计算“当前和前一笔订单”的已知数量平均值，可以明确写：

```sql
AVG(qty) OVER (
  PARTITION BY sku
  ORDER BY ordered_on, order_id
  ROWS BETWEEN 1 PRECEDING AND CURRENT ROW
)
```

对 A，前三个结果分别为 2、2、2；第三个窗口是 `(2, NULL)`，AVG 忽略 NULL，所以仍为 2。这个结果不是说第三笔数量也是 2，更不是说“两日平均需求为 2”。**两行窗口与两天窗口不同。**

若窗口内按 qty 排名，两个 2 可以并列：ROW_NUMBER 分配不同序号，RANK 对相同排序键给同一排名，后面的排名可能留空档。要取每组“前两名”，先明确是前两行还是所有进入前两名的并列对象。

<details>
<summary>自测：有窗口 ORDER BY 就能删除最外层 ORDER BY 吗？</summary>

若需求包括最终显示顺序，就不能这样推论。窗口排序服务于窗口语义，最终查询的顺序契约仍应由最外层 ORDER BY 表达。某次执行恰好顺序相同，不是语言保证。

</details>

## 6. 可移植性：先定义类型和语义，再选函数

课堂定位：**25:46–45:51**。

### 字符串：三个不同问题

| 问题 | 需要确认的规则 |
|---|---|
| `'A'` 与 `'a'` 是否相等 | 字符串比较、collation、类型 |
| `Orders` 与 `orders` 是否指同一对象 | 未加引号标识符的折叠规则 |
| `"Orders"` 是名字还是字符串 | 标识符引号、SQL 模式、兼容配置 |

可移植代码通常用单引号表达字符串值；不要因为课堂某个 MySQL 或 SQLite 环境接受双引号，就把它当作普遍规则。LIKE 中 `%` 与 `_` 也不是通用正则语法；ILIKE、正则函数、拼接运算符要分别核对目标系统。

### 日期：238 与 726 都来自“减法”，但不是同一种减法

2025 年不是闰年。从 1 月 1 日到 8 月 27 日，前七个月共有：

`31 + 28 + 31 + 30 + 31 + 30 + 31 = 212` 天。

再加上八月已经经过的 26 天，得到 **238 天**。这是日期间隔。

但如果把年月日当作十进制数字，得到：

`20250827 - 20250101 = 726`。

它不是某种奇怪的日历，只是做了不同的数值运算。因此错误可能不是减号算错，而是操作数已被转换成错误的类型。

在迁移日期代码前，依次问：

1. 我在处理 DATE、时间点、带时区时间戳，还是一段持续时间？
2. 输入字符串如何解析，隐式转换是否发生？
3. 函数返回的是整日、边界跨越次数、秒数，还是区间值？
4. 需要本地日历天数，还是固定 86400 秒长度？
5. 当前时间基于哪个时区、哪个时间基准？

课堂逐个产品的终端输出是 **2025 年演示事实**，不是本页复测结论。不要把 NOW、CURRENT_TIMESTAMP、GETDATE、DATEDIFF 的名字拼起来当作跨数据库代码。

<details>
<summary>自测：把日期计算的错误结果 CAST 成整数，能不能修复语义？</summary>

不能。把 726 变成整数仍是 726。显式转换只在你已经选对表示和运算时控制类型；它不能替代对日期、时区与间隔含义的判断。

</details>

## 7. 从一条查询到一组有版本的数据产品：dbt 的位置

课堂定位：**65:54–76:17**，包括两个完整问答。

![dbt 将受版本控制的转换模型按依赖交给数据仓库执行](assets/dbt-boundary.svg)

图是编者自绘的 Orders 场景，不是嘉宾图像的截图。上方实线表示数据关系依赖；下方表示 dbt 管理 SQL 定义、测试与构建，真正执行读写的是数据仓库。

想象三个团队各自计算“可发货订单”：

- 财务认为付款成功才算订单；
- 运营把取消订单过滤掉；
- 库存团队又单独处理未知数量和缺货。

若每张仪表盘独立拼这些规则，就可能出现三个都能运行、却彼此不同的数字。把查询上传 GitHub 也不会自动消除重复定义。

嘉宾提出的组织方式是：从原始数据建立 staging 模型，再组成共享业务模型，最后给报表使用。每个模型的粒度与假设应清楚，例如：

| 层次 | 原创示例契约 | 可检查的不变量 |
|---|---|---|
| 原始订单 | 保存来源事件 | 不擅自删掉重复事件证据 |
| staging 订单 | 一行对应一个确定版本的订单 | 订单身份非空；去重规则确定 |
| 商品需求 | 一行对应一个商品 | sku 唯一；未知数量另作计数 |
| 报表模型 | 明确定义“已知需求是否超库存” | 不把未知需求判定成已满足 |

**Jinja 与依赖图。** SQL 定义关系转换；模板可以把模型引用、源引用与重复展开表达出来。依赖图让工具知道构建顺序，也帮助人追溯数据。模板并不是一个新的数据仓库执行引擎。

**物化。** 用户的 SELECT 描述业务逻辑，dbt 可围绕它生成建表或建视图等操作。嘉宾还提到增量更新，但没有给出增量键、迟到数据、删除传播的完整算法；本页不把“支持增量”延伸成“所有增量维护都自动正确”。

**两个不能混淆的边界：**

1. dbt 不只是血缘可视化：它实际按依赖构建数据集。
2. dbt 不替代仓库执行器：查询运行在客户已有的 Snowflake、BigQuery、Redshift、Databricks 等环境。

**可维护性推论：** 一条 `not null` 或 `unique` 测试只能检查声明过的假设，不能证明“客户”或“收入”的业务定义正确。SQL 评审、数据测试、版本控制、开发与生产隔离，解决的是互补的问题。

没有。还缺少明确依赖、可复用模型、构建顺序、环境隔离、数据断言和发布流程。反过来，即使有这些工具，SQL 的粒度、重复、NULL 和顺序语义也仍需作者负责。
