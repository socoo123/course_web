# 索引并发：证明路径有效，再追求并行

## 一个库存查询，至少有三份不同的承诺

设 `Stock(sku, quantity)` 的 B+Tree 索引把业务键 `sku` 映射到记录 RID。执行者沿树找到了叶子，准备返回结果。此时另一个执行者正在删键并合并页。

先不要急着问“加什么锁”。把承诺分开，才能知道该保护什么：

| 问题 | 对应机制 | 不能代替的机制 |
|---|---|---|
| 使用中的页会不会被驱逐、frame 会不会改装其他页？ | pin／页驻留生命周期 | pin 不能防止另一个 worker 改内容 |
| 读到的键、槽位、路标、指针是否构成有效结构？ | latch 与结构访问协议 | latch 不自动决定事务可见性 |
| 我两次读取库存是否必须相同，能否看见别人未提交的修改？ | 事务隔离、lock／版本等高层协议 | 多持有几秒页 latch 不是完整事务设计 |

**Page 是逻辑持久页，frame 是暂存页内容的内存容器；RID 标识表记录位置，业务 key 决定索引顺序。** 索引内部孩子通常由 page ID 指向；叶项中的 RID 是表记录位置，不是“这个叶子自己的 page ID”。frame 地址既不等于业务键，也不能当作永久页身份。

对于 `Orders(order_id, ...)`，找到一个 RID 后是否可以直接相信对应记录对当前事务可见，是另一层问题。本讲首先确保找 RID 的结构不会因为并发修改产生坏指针或错误漏查。

<details>
<summary>自测：pin_count 大于零，是否已经能无锁修改节点？</summary>

不能。它只约束驻留与替换，不赋予内容写权限。另一个 worker 仍可能读取或修改同一页。还需按协议取得写 latch；dirty 元数据同样需有合法同步，普通布尔赋值不是并发正确性的证明。
</details>

## 原子指令不是整棵树的原子性

一个原子 CAS 可以表达“该状态仍等于旧值时才安装新值”；test-and-set 可以返回并设置一个标志。它们解决一个同步状态的不可分割更新，不会自动把分裂涉及的孩子数组、父分隔键、兄弟指针和 root ID 一起提交。

考虑未经保护的两步：先读 `parent.child = H`，稍后访问 H。即使单独读取 page ID 是原子的，也不代表两步之间 H 的角色不变。并发者可能把键移到 I，并修改路标；读者拿着过时路径继续找，便会漏键。课堂 43:45–45:31 的 44／41 示例正是这种反例。

Latch 的实现选择也不能脱离成本模型：

- **紧凑自旋**：低竞争快速，长期争用会浪费周期，NUMA 下还会争夺缓存行。
- **阻塞式 mutex**：竞争时可让 CPU 做其他工作，但可能引入内核等待、唤醒及调度开销。无竞争路径不必每次都系统调用。
- **读写 latch**：允许多个读者，但增加计数与排队开销，并需要明确饥饿策略。不是读多就必然胜过简单 mutex。
- **队列／自适应方案**：可改善特定争用模式；课程只给直觉，不提供可直接照抄的低层实现。

工程上的问题是“短暂失败后能否做别的有效工作”，而不只是“要不要自旋”。持有者被抢占时，其他核越忙着空转，未必越快。课堂对 OS 与数据库的争论应理解为调度控制权的权衡，不是普适性能结论。

## safe 的真正定义是影响不能越过边界

把 safe 写成一个语义命题，比背“未满／半满”更可靠：

> 在当前节点受到适当 latch 保护、当前操作的局部规则成立时，来自下层的这次变化能够被该节点吸收，不需要修改它的父节点。

普通、固定容量且没有延迟删除的简化模型中，设节点当前物理占用为 $n$，最大允许占用为 $M$，非根最低占用为 $m$：

- 若一次插入至多新增一个项，且算法允许使用最后一个槽位，则 $n+1\le M$ 可以保证不因容量而分裂。
- 若一次删除至多物理移除一个项，则 $n-1\ge m$ 可以保证不因占用而借位或合并。
- 这只是指定模型下的推导。若实现约定“插入后到达 `max_size` 就分裂”，safe 阈值必须与该约定一致，不能直接沿用上一条。
- 内部节点按孩子数还是有效分隔键数计数，可能不同；根的最低占用与普通节点也不同。证明时必须写清单位。

**读操作不改变节点大小，因此不会自己引起上推或合并；但仍要证明下一跳有效。** “读不需要 safe 容量检查”绝不等于“读不需要 latch”。

### 为什么遇到 safe 孩子能释放全部祖先

假设沿路径持有 A、B、C 的写 latch，下层修改可能让 C 分裂。只要 B 能吸收 C 上推的一个项，变化最多到 B；无需修改 A。更往下若发现叶子本身就能吸收操作，则连 B、C 也不需要了。

这是一个“向上影响的上界”证明：保留下来的路径覆盖所有仍可能被修改的祖先；已释放区域不再属于本次操作的结构修改范围。若 safe 判断错误，释放的是以后实际还需要的修改权，算法便不能靠“重新拿回来应该没事”补救。

### 固定 tombstone 叶页为什么不能套一个半满公式

Fall 2025 Project 2 的叶子不仅有键值数组，还有有限长度的 tombstone 缓冲，记录已逻辑删除项的物理下标。逻辑删除可能不立即收缩数组；缓冲容量触发时，要应用最旧的待删除项。

以纯概念示例说明：物理数组有六项，其中两项已有 tombstone，逻辑上只剩四个有效键。**有效键数为四，不等于数组自动空出了两个可写槽位。** 同样，“再删除一个键”可能只是添加 tombstone，也可能引发旧项压缩；不能只看活跃键数判断这次操作是否触发结构变化。

因此至少要区分：物理大小、逻辑有效集合、tombstone 容量与顺序、将要执行的物理整理以及父分隔键／兄弟关系是否需要改变。`KeyAt` 按题面仍读取物理项，迭代器才应跳过逻辑删除项；搬动数组后 tombstone 下标必须仍指向原来被删的键。分裂、合并、借位不能丢失这些关系和删除顺序。

这里给出的是判断边界，不提供项目的 safe 函数或可提交实现。完整固定版本规则见 [Project 2 导读](#/c/cmu-15-445-2025/lab/project2?v=zh) 与[指导](#/c/cmu-15-445-2025/lab/project2?v=guide)。该版本是 `v20251119-2025fall`，固定提交 `d49b823f829a4bf311a2c80b239ab5a9864c9c41`，不是任意年份的普通 B+Tree。

<details>
<summary>自测：一个叶子“逻辑上不满”，能否立刻认定插入 safe？</summary>

不能。必须看物理数组是否有空间、项目的分裂时机、是否以及何时整理 tombstone，以及操作是否要求更新父层或其他页。逻辑空位不自动等于物理槽位。safe 必须在正确 latch 保护下判定，否则刚读出的容量也可能马上过时。
</details>

## coupling 保护的是交接窗口

查找交接的核心顺序是：

1. 在父节点受保护时读取合法的孩子标识。
2. 不先放开父节点，取得孩子的驻留与读保护。
3. 交接完成后释放父节点，继续下行。
4. 读完叶子后释放叶子资源。

若把第 2、3 步颠倒，父层修改者就可能在空档中移除或改接该路径。仅仅保存一个裸指针或 page ID，不足以证明下一次解引用仍然合法。

基础修改协议把路径上的保护换为写模式，并在每次取得孩子之后检查操作相关的 safe。父层可能要接住分裂项、删除孩子或改变分隔键，因此在尚未证明安全前不能提前释放。

课堂 51:24 明确区分：在已经确定可释放的一组祖先中，**释放顺序本身是性能问题**；优先释放更高层往往让更多无关子树早些恢复通行。固定 Project 2 的题面则明确要求从 header 向下取得并按同方向释放。课程一般论证与具体任务要求不是一回事：完成项目应遵守其额外约束。

不要把“我持有父节点”扩大成“我独占整棵子树”。已经进入下层的 worker 可能仍在运行；横向叶扫描还可能从兄弟入口进入。真正写一个节点时，仍需对应的写保护及一致的结构协议。

<details>
<summary>自测：为何静态哈希表例子可以先放旧页，而 B+Tree 要先拿孩子？</summary>

课堂静态哈希表假定布局与探测顺序不变，且只需保护一个页／槽位；释放旧页不会让下一步的布局依据失效。B+Tree 的孩子关系会随并发分裂、合并而改变，交接有结构依赖。若哈希表也允许动态扩容或复杂跨页修改，就需额外协议，不能直接搬用该简化例子。
</details>

## 乐观路线不是“先做错，再随便修”

基础协议的代价是每次更新先争用根的写 latch。乐观路线依赖一个常见但要验证的假设：叶子能单独完成操作。

| 阶段 | 持有与判断 | 合法后续 |
|---|---|---|
| 沿内部节点下降 | 读 latch coupling | 只读取路径，不修改父层 |
| 将进入叶子 | 父层仍受读保护，取得叶写保护 | 在稳定叶状态下判断操作 safe |
| 假设成立 | 不需要修改父层 | 释放不再需要的父层读保护，完成局部更新 |
| 假设失败 | 当前权限不足以做结构变更 | 释放本次资源，从根按写路径重新开始 |

这是 optimistic **latch** coupling，不是“完全不拿 latch”，也不是事务 optimistic concurrency control。它尽量把常见操作的独占范围缩到叶子，但仍要同步。

![乐观路径的成功与重新开始](assets/optimistic-restart.svg)

*原创状态示意，依据课堂 54:55–1:01:38。失败分支先清理再重走，不持有叶写 latch 向上追讨祖先。*

### 为何不能拿着叶子向上补锁

另一个 worker 可能已持有父亲，正在按从上到下的顺序等你手里的叶子。你若持有叶子反过来等待父亲，形成等待环。即使当时没有这个 worker，祖先在你释放读保护后也可能改变；过去看见 C 安全，不代表现在仍是同一个路径事实。

### 为什么普通共享 latch 不等于安全升级

两个读者都保留读 latch，同时等待成为唯一写者，双方都可能等另一个读者退出。升级需要专门协议，或释放、重取与重新验证；普通接口不能凭愿望获得原子升级能力。固定项目还明确提醒，同一线程不要重复取得同一读 latch，它不保证递归获取安全。

<details>
<summary>自测：为什么读路径缓存不等于可用于重启的写路径？</summary>

缓存的是过去观察，不是当前权限。祖先读 latch 一旦释放，指针、分隔键、容量甚至节点角色都可能改变。中途重启要额外验证身份与结构关系；基础重启从根重新建立事实与持有顺序。
</details>

## 横向扫描：先分清冲突、死锁和饥饿

这三个词不是同义词：

- **冲突／等待**：T2 想读 C，T1 正写 C，模式不兼容。
- **死锁**：T2 持有 B 等 C，同时 T1 持有 C 等 B，形成环，双方按当前协议都无法前进。
- **饥饿**：没有固定等待环，但某个任务总在冲突时让步，长期完不成。

课堂 1:04:37–1:08:41 的例子中，T1 只在 C 删除键 4，不合并，不申请 B，因此此刻**只是冲突，不是已证明的死锁**。然而 T2 只知道 C 被不兼容地持有，不知道 T1 的完整后续计划。协议需要适用于另一个确实要合并、申请 B 的执行过程，不能靠读者猜测持有者行为。

两个纯读扫描即使方向相反，也能共享 B、C 的读 latch，故不因相向行进而自动死锁。问题是横向边加上不兼容持有模式，可以破坏原本按树深度下降的统一顺序。

### no-wait 的承诺很窄，但重要

申请兄弟 latch 应能立即返回失败。取不到时，不无限抓着当前叶子等待；本次操作负责清理自身状态、释放所持资源，再依据有效路径重试。这里的“终止自己”是放弃一次操作尝试，不是终止 OS 线程、进程，更不是强杀持有者。

有限等待与退避可以调节性能，但需要保持有界与完整清理规则。no-wait 排除了某类永久持有等待环，**不保证无饥饿、无活锁或范围扫描的事务快照语义**。高层可记录反复失败并调整调度；若所有写入都命中同一记录，热点本身仍然序列化。

固定 Project 2 题面说不测试迭代器的线程安全叶扫描，并讨论申请兄弟失败应报告异常以避免死锁。这是测试边界与接口提示，不是“迭代器随意忽略 latch 也正确”；更不是完整并发范围快照的承诺。

<details>
<summary>自测：T2 在等写者 T1，但 T1 不等任何人，这就能删掉 no-wait 规则吗？</summary>

不能。这个具体状态没有等待环，但执行者通常没有足够信息证明所有未来请求都安全。通用协议要覆盖会申请兄弟、借位或合并的场景；no-wait 提供不依赖猜测的失败出口。
</details>

<summary>自测：能否跳过被占用叶子，返回其他叶子的结果？</summary>

不能把不完整扫描声称为完整答案。可以另行设计分区访问、补读与去重协议，但必须记录未完成范围，并保证不遗漏或重复；还需要事务层定义可见性。简单忽略一个叶子会丢结果。

## 根变化与资源释放是算法的一部分

根并不是永不改变的全局常量。插入可能分裂根、提高树高；删除可能收缩根；空树与第一次插入也会改变根标识。固定题面要求更新 header 中的 `root_page_id`。因此要保护的既有根页内容，也有“从哪里找到根”的发布入口。

一个可用于审阅设计的反例：读者先无保护地读取旧 root ID，写者随后安装新根并回收旧根，读者再取得旧页。即使它后来拿到了某个 latch，也没有证明这个页仍是合法树入口。保护必须覆盖根标识读取、取得合法根保护的交接，以及根切换时的发布关系。不要等树分裂以后才补想 header 的生命周期。

这里不提供固定源码的加锁实现，给出的是端到端检查问题：

| 退出情形 | 必须交代的事情 |
|---|---|
| 找到／没找到 | 最后一个 guard 何时释放，返回的结果是否依赖已失效指针 |
| 重复插入／不存在的删除 | 不应因为早返回漏掉持有的资源 |
| 乐观失败重启 | 旧路径 guard 与裸指针都不能被当作新尝试权限 |
| 兄弟获取失败 | 处理本次已修改状态，释放路径与兄弟资源，再重试或报告 |
| 分裂／合并成功 | 新路标、孩子关系、叶链、root ID 一致；被移除页无悬空访问 |
| 异常或分配失败 | 清理责任明确，不能留下半发布节点或长期 pin |

复用 Project 1 的读写 page guard，帮助把 latch 与 pin 生命周期绑定到明确拥有者；不要重做缓冲池。guard 析构能帮助释放资源，却不能自动证明修改顺序正确，更不会自动撤销你已经写进多个节点的内容。guard 释放或转移后，先前取得的页内指针不能继续被当作受保护访问。

课堂末尾的 worker-local write set 是“要知道改了什么才能清理”的思想。题面中的 `Context.read_set_`／`write_set_` 用于追踪访问页及相关状态，不能仅因为名字相同就断言它已经实现了课堂所说的撤销日志。

同理，有些工业算法可以撤销键而保留有效分裂后的树形，**不等于课程项目可以保留非法占用或损坏路标**。事务回滚、结构性修改恢复、guard 资源释放，是三个相关却不相同的责任。

<details>
<summary>自测：所有 guard 都正确析构，能否证明这次失败已经安全回滚？</summary>

不能。析构主要解决资源释放；若父页已指向未初始化的新页，或旧孩子已被移除但兄弟链未更新，释放 latch 只会把错误公开给其他 worker。先保证失败状态满足结构不变量，再退出保护范围。
</details>

## 如何审阅协议，而不是猜测线程调度

不必先跑出罕见崩溃，便能用以下四个问题检查设计：

1. **访问权**：每次读写节点前，谁拥有哪一种 guard，页是否仍驻留？
2. **交接依据**：从哪里读取下一跳标识，读取到取得下一页之间谁阻止关系变化？
3. **影响边界**：safe 判断基于什么占用、tombstone 和根规则，哪些祖先仍可能被修改？
4. **失败出口**：拿不到后续资源时，谁负责恢复、释放和重新建立路径，是否可能向上形成等待环？

然后构造原创交错而非学生实现答案：让 Stock 热点键的点查与邻叶合并相遇；让两个不同叶子的普通插入观察根读共享；让乐观访问叶子时恰好触发分裂；让长期扫描不断遇到写热点。每个场景都分别判断物理结构、进展与业务可见性，不用一个“线程安全”标签把三个结论混在一起。

<details>
<summary>自测：同一事务先插入订单，再读不到订单，是否一定是索引 latch 错误？</summary>

不一定。先区分是否有结构路径失效或漏查，再考虑是否存在合法删除及事务隔离规则。若索引漏掉仍存在、按有效路径应可达的键，是物理协议问题；若结构完好但另一个事务已合法删除，是否允许当前事务看不到，属于逻辑语义。
</details>
