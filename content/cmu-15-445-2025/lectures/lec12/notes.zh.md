# 第12讲：连接的配对、不变量与外存成本

## 先确定究竟要输出哪些配对

设`Orders(order_id, sku, qty)`与`Stock(sku, warehouse, available)`按`Orders.sku = Stock.sku`做内连接。这不是“每个订单找一个库存行”，而是**每个订单与每条同sku的库存行配对**。一个sku在Orders有a行、Stock有b行，就产生a×b行；除非存在经过确认的唯一约束，不能只保留第一个匹配。

```sql
SELECT o.order_id, s.warehouse, o.qty
FROM Orders AS o
JOIN Stock AS s ON o.sku = s.sku;
```

这份笔记用上述原创例子解释课堂思想，不是Project 3执行器指南，也不提供可提交实现。

| 问题 | 连接契约 |
|---|---|
| 哪些行配对 | 等值键相同，且满足其他残余谓词 |
| 重复是否保留 | 普通SQL连接保留所有合法配对，不自动DISTINCT |
| 没匹配怎么办 | 内连接不输出；左外连接、反连接的处理不同 |
| NULL怎么办 | 普通`=`不把两个NULL认定为相等；空值安全谓词另论 |
| 输出顺序是什么 | 无ORDER BY不承诺顺序 |
| 可以交换两侧吗 | 内连接的逻辑配对可交换，输出布局、物理代价及外连接语义不能忽略 |

后三项为编者的语义边界补充，并非声称课堂逐项讲解SQL NULL。

**反例：** 把Stock的多仓库记录塞进`sku → 单个Stock行`的映射，就算哈希完全没有冲突，结果仍然错误。算法首先要正确保存多重匹配，再谈速度。

## 一对结果携带值，还是携带位置

早物化把后面需要的值放进连接结果；晚物化先传连接键和两侧记录标识，等后续确实需要其他列时再读取。两者改变的是数据搬运，不是配对集合。

- 若后继过滤会扔掉大多数结果，晚取宽列可能省掉大量读取。
- 若后面几乎要用每一列，而RID访问很离散，晚取可能引入随机访问。
- 早物化不等于复制表中所有列：已经确认不会再使用的列可以裁剪。
- 业务`sku`、`order_id`不是RID；RID不是磁盘页号；磁盘页又不同于当前缓存该页的内存frame。中间流也不一定来自基表，不能假定永远存在稳定基表RID。

在成本公式中，两种结果表示可能需要不同页数。只有固定逻辑结果和物理输出策略之后，才能把共同输出成本从比较中省去。

## 成本表前的五个前提

R有M页、m行；S有N页、n行；B是**给当前算子的可用缓冲帧预算**，不是机器总内存。下面讨论单机页I/O，不计CPU、网络与最终结果写出；若发生中间溢写，其写与读必须计入。B至少为3。

| 算法 | 页I/O简化模型 | 成立条件与隐藏工作 |
|---|---|---|
| 逐行nested loop | M+mN | 每条外行重扫内表，无有效缓存复用 |
| 一页block nested loop | M+MN | 每个外页重扫内表 |
| 多页block nested loop | M+ceil(M/(B−2))·N | B−2外页、1内页、1输出页 |
| index nested loop | M+mC | 内侧有可用索引；C含所需匹配访问；临时建索引另算 |
| sort-merge | sort(M)+sort(N)+M+N | 最后一项假定无重复组外存重读 |
| 内存hash join | M+N | build哈希表能驻留；probe可流过 |
| 一轮Grace hash join | 3(M+N) | 两侧完整分区写盘一次，局部build表都能驻留 |

表中“hash join三倍输入”特指外部分区版本，不是所有哈希连接的固定税率。模型里“内存nested loop与内存hash都只读一遍”也不意味着二者CPU代价一样：前者可能做m×n次比较，后者在良好分布下以约m+n次构建/探测加实际匹配工作为主。

## 循环算法真正优化了什么

### 从行复用变为页复用

外层每一行触发一轮内表扫描，需要m轮；外层每一页触发一轮只需要M轮；每批B−2页触发一轮，只需要ceil(M/(B−2))轮。减少的是**内表重读次数**，不是删除语义要求的匹配。

用课堂数据M=1000、m=100000、N=500、n=40000：

| 配置 | I/O | 每次0.1ms的模型时间 |
|---|---:|---:|
| R外侧，逐行循环 | 50,001,000 | 约1.39小时 |
| S外侧，逐行循环 | 40,000,500 | 约1.11小时 |
| R外侧，B=102 | 6,000 | 0.60秒 |
| S外侧，B=102 | 5,500 | 0.55秒 |
| 整个外侧放进B−2帧 | 1,500 | 0.15秒 |

这些是代数换算，不是实测benchmark。课堂23:08的ASR“100 milliseconds”与这些数量级矛盾，应区分0.1毫秒与100毫秒。官方notes汇总表对B=100的block示例写6.5秒；代入其公式应为6500次I/O，即0.65秒，不能沿用十倍误差。视频使用B=102的例题则是6000/5500次，二者也不能混用。

### “小表放外侧”为什么不是定理

逐行循环应该比较M+mN与N+nM，而非只比M和N。多页循环应比较两方向的带ceil表达式；页面边界会造成台阶。更关键的是，若只有Stock.sku有好索引，则让Orders在外侧、Stock在内侧可能明显更好，即使Orders更大。

对索引探测，C可能包括树路径、跨叶页重复键扫描与回表。若一次探测返回十万条候选，不能仍把它当成一次常数页访问。对小而高度选择性的外输入，已有索引常有吸引力；对几乎扫描所有行的批量连接，反复随机探测未必优于一次build。

## 排序如何证明可以跳过候选

设两侧按同一个连接键比较规则升序排列。当前R键小于S键，则后续S键不可能再等于该R键，可以推进R。这条单调性就是跳过无用比较的依据。它要求排序顺序、连接相等判断和键编码相容。

### 重复组不是一对一拉链

![重复键组必须产生全部配对](assets/duplicate-groups.svg)

图：自拟Orders/Stock示例。两个订单、三个仓库库存行共形成六对，说明课堂38:07–45:11中“回到组开头”的意义；不是课堂截图。

实现应保存内侧**重复组起点**，或缓存该组。只有“最后看到的值”而没有位置或可重放内容，不足以回退。内侧游标抵达末尾，也不能立即丢弃最后一组：外侧可能还有同键行。

若组能留在内存，重复配对不必反复读盘，但输出和CPU仍然可能很大；若组超过预算，可能需要重新读取或溢写组。全部键相同的a×b结果是语义本身要求的，不能靠更好哈希函数消除。

### 排序成本的ceil不能丢

假定初始每B页产生一个run，每轮最多B−1路归并，每轮都完整读写到磁盘；X>0：

$$r_0(X)=\left\lceil X/B\right\rceil.$$

$$p(X)=\left\lceil\log_{B-1} r_0(X)\right\rceil.$$

$$\operatorname{sort}(X)=2X\,[1+p(X)].$$

这是完整物化有序文件的模型。如果输入已经有序，排序可以省掉；如果最终排序输出直接流入连接，可能省掉最后一次写回与重读；不能一边使用上述完整物化公式，一边又口头说没有中间文件。完全内存排序也应按实际是否写盘另算，而非机械收取2X。

对M=1000、N=500、B=100，两侧初始run分别10个与5个，一轮99路归并足够；排序4000+2000，连接扫描1500，合计7500次I/O。**无重复组重读**时是0.75秒模型时间；有大量重复时，M+N不是普遍上界。

### 已排序并不自动赢

若最终只保留很少结果，先hash join再排序小结果，可能比先排序两大输入更便宜。有ORDER BY时也要看要求的列、方向、排序规则是否与join所用顺序一致，以及后继算子是否保留该顺序。

## 哈希排除的是不同分区，不是键比较

核心正确性不变量为：

$$r.key=s.key\ \Longrightarrow\ h(r.key)=h(s.key).$$

反方向不成立。因此要区分两层判断：哈希定位候选；真实键比较确认相等，之后还要检查残余谓词。普通hash join面向等值条件，不能用键哈希直接定位所有`r.x < s.x`候选。带有等值部分加其他条件的连接可以先用等值部分缩小候选，再检查余下条件。

build侧要保留全部同键记录，不能以覆盖更新代替插入重复项。需要驻留的是哈希表实际字节：键、载荷或RID、桶、指针、装载因子预留等，不能仅用原表页数推断“刚好放得下”。probe侧不必一次装入，只要顺序扫描并探测。

### Bloom的安全边界

build完成的Bloom filter可以横向交给probe路径。只有“不可能存在”可跳过完整哈希探测；“可能存在”仍必须查表。没有假阴性要求所有有效build键都已插入、使用一致编码和哈希规则，并保证发布与读取正确。

当多数键都会匹配，额外过滤本身可能得不偿失。课堂侧向过滤的例子不保证磁盘I/O必然下降：probe输入通常仍须读取；节省的可能主要是内存随机访问和键比较。外连接遇到“明确无匹配”还要走补NULL分支，反连接则可能应当输出该外行。

## 溢写时保留什么不变量

![两侧相同路由与局部驻留](assets/partition-invariant.svg)

图：原创分区流程。相同键走相同分区，局部build驻留、probe流过；仅超预算的对应分区需要递归。对应课堂59:45–1:07:40，非实现代码。

Grace先读两表并顺序写出分区，再逐对读回：

$$
\begin{aligned}
C={}&\underbrace{(M+N)}_{\text{读原表}}\\
&+\underbrace{(M+N)}_{\text{写分区}}\\
&+\underbrace{(M+N)}_{\text{读分区}}.
\end{aligned}
$$

若均匀分为k份，粗略希望每份build数据连同哈希表额外空间都小于驻留预算；与此同时分区阶段需要给各分区输出缓冲，并预留输入缓冲。预算不足时，不能随意提高k而不计算缓冲占用。

递归时，两侧**同一对应分区使用相同的新规则**。只递归R、不让对应S按相同路径继续分区，会漏掉配对；对所有已经足够小的分区重复处理，又会浪费I/O。若额外一层处理的两侧分区合计T页，在页数不膨胀的简化模型里，额外读写分区约增加2T，而非必定再给整张表收2(M+N)。

### 两种倾斜不是同一个问题

1. **不同键恰好聚到一起：** 换种子/函数可以改善分布，但不是保证。
2. **同一个热键有大量记录：** 确定性哈希必须让相等键同路由，换函数不能拆散这个等值组。若超预算，需采用块式处理等策略；课堂明确提出局部退回block nested loop。

若不断递归后分区没有缩小，就应改变处理策略，不能把“继续分区直到能装下”写成无条件终止论证。

Hybrid hash join保留一个或多个**确实放得下**的分区，其余照常溢写，省掉驻留部分的写出与读回。它的收益受内存预算、预测和分区大小影响，不等于“最热分区无论多大都留内存”；也不以混用nested loop为必要定义。

## 用输入性质选择，而不是背算法冠军

| 已知事实 | 候选与需要追问的问题 |
|---|---|
| 外输入很小，内侧有合适索引 | index NL；一次探测到底返回多少行、要回表多少页？ |
| 两侧小到能驻留 | hash或简单循环；建表常数与m×n比较哪个更贵？ |
| 大型等值内连接，无可用顺序 | hash/Grace；build尺寸、倾斜、溢写深度？ |
| 两侧已有兼容键顺序 | sort-merge；重复组能否缓存？ |
| 输出也需要按相同键排序 | 比较sort-merge与hash后排结果；谁需要排序的数据更少？ |
| 任意非等值谓词 | 不能直接套普通hash；排序能否利用谓词单调性？否则循环基线 |
| 单个键形成巨大多对多组 | 首先估算结果规模；没有算法能免去必须产生的配对 |

没有测量、统计或输入约束，不应声称某算法一定更快。所有成本估算都应注明是否把输出物化、溢写、CPU和缓存算进去。

## 自测：先说明前提再计算

<details>
<summary>1. Orders的sku=7有2行，Stock有3行。Bloom返回“可能存在”后输出一行，错在哪里？</summary>

Bloom不能确认真实相等，必须查表；真有匹配也应输出2×3=6对，而不是一行。哈希冲突校验与重复记录枚举是两个不同要求。

</details>

<details>
<summary>2. R为980页、S为500页、B=100。交换block NL两侧一定更好吗？</summary>

R外侧：980+ceil(980/98)×500=5980。S外侧：500+ceil(500/98)×980=6380。这个ceil边界反例说明“小表外侧”是启发式，非此公式下的无条件定理。输出成本、CPU与其他约束仍未计入。

</details>

<details>
<summary>3. build基表只有90页，预算100帧，能断言内存hash join不会溢写吗？</summary>

不能。还要计入哈希桶、键/载荷表示、装载因子余量和输入输出缓冲。需要比较实际哈希结构体积，不是只比较原始基表页数。

</details>

<details>
<summary>4. 为什么sort-merge遇到相等键后不能同时推进两边？</summary>

可能两侧都有重复组。一个外侧行要配对全部内侧同键行，下一条同键外行还要复用内侧组。需要组起点/缓存以及明确枚举状态；否则会漏掉笛卡尔组配对。

</details>

<details>
<summary>5. 为什么换十次哈希函数也不一定救得了超大分区？</summary>

若是同一个热键的记录占据大部分空间，所有相等键仍必须送到同一个对应分区。再哈希不能缩小该等值组；需要块式处理等策略，并接受实际结果规模带来的成本。

</details>

<details>
<summary>6. 一轮Grace为何是3(M+N)，不是2(M+N)？</summary>

读原输入一次、写出分区一次、读回分区一次。若某分区一直驻留，可省它的写回与再读；若递归则要增加相关分区的额外读写。最终结果写出另算。

</details>

<details>
<summary>7. 最终ORDER BY sku是否意味着sort-merge必胜？</summary>

否。可先hash连接再排序更小的结果；已有顺序是否相容、是否被后继算子保留、重复组重读和两侧排序成本都要比较。ORDER BY其他列更不能直接复用连接键顺序。

</details>

<details>
<summary>8. “两表都在内存，所以嵌套循环只要线性时间”是否正确？</summary>

不正确。输入磁盘I/O可以仅M+N，CPU候选比较仍可能m×n。本讲省略CPU的页I/O模型不能被当作总运行时间复杂度。

</details>
