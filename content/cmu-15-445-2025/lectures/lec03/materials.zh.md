# L3 资料导引：把课堂简图与产品契约分开

把“页里有槽，槽里能找元组”变成实现知识，需要多问一步：这个具体系统究竟承诺了什么？本页用三个小阅读任务练习识别边界，不再重复课堂幻灯片，也不提供教材或产品手册的全文翻译。

## 1. 同叫行标识，稳定范围却不同

先画一张只有两列的表格：左边是**逻辑行身份**，右边是**当前存储定位**。遇到一个标识，不要急着归类，先问四件事：

1. 唯一性在哪个范围内成立，是一张表还是整个数据库？
2. 更新非键属性会不会让它改变？
3. 整理文件、重写表或迁移数据会不会改变它？
4. 应用能否显式声明一个稳定键与它绑定？

### PostgreSQL：ctid 是行版本的位置

阅读 *System Columns* 的 `ctid` 段，并对照 `xmin` 段理解“row version”。更新产生新行版本，`ctid` 可变化；`VACUUM FULL` 搬迁也可改变位置。因此，`ctid` 适合解释物理布局，却不适合成为发给客户的长期订单编号。

**原创任务**：订单 103 的数量从 1 改为 2。如果新版本出现于另一个位置，哪些东西应该保持“这是订单 103”，哪些东西允许变化？写出业务键、行版本、物理位置三层，避免一句“行没变”混合三个问题。

还要注意：`xmax` 非零并不自动表示当前行不可见，文档说明它可能涉及尚未提交或已回滚的删除。此处只用于提醒“元组头字段必须按协议解释”，不在 L3 提前实现事务可见性判断。

### SQLite：rowid table 有明确适用范围

阅读 *Rowid Tables* 的 Definition 和 Quirks。普通 rowid table 用唯一、非 NULL 的有符号 64 位整数 rowid 作为底层 B-tree 访问键。它不是数据库页号与槽号的直接编码。

需要同时记住三个限定：

- `WITHOUT ROWID` 表和 virtual table 不属于该页定义的 rowid table。
- `INTEGER PRIMARY KEY` 可以作为 rowid 别名；不能把所有名叫 PRIMARY KEY 的声明都当作同一种绑定。
- 对没有该别名的表，`VACUUM` 可能改变 rowid，因此应用通常应声明并使用适当的主键。

**原创反例**：把 PostgreSQL 的 `ctid` 和 SQLite 的 `rowid` 都写成 `(page,slot)`。即使两者都能帮助找行，这也不是合法的实现归纳。名字和用途相近，只能提示你继续读接口定义，不能代替定义。

## 2. 2 KB 阈值不等于一个 2 KB 字段直接占一张页

阅读 TOAST 时先把三层分开：主表行、大属性的逻辑值、用于承载大值的物理块行。

PostgreSQL 通常使用 8 KB 页，元组不能直接跨页。TOAST 在适用类型的大行需要缩小时尝试压缩或移出字段。正常约 2 KB 的触发量级针对待存行；具体还取决于策略和可获得的压缩收益。

移出的内容放在与主表关联的 TOAST 表中，按块组织为行，包含值标识、块序号和实际块数据；索引帮助重新找到各块。主行里的小引用并非“应用随便挑的文件路径”，数据库仍管理这些数据。

### 用四种策略检查自己的概括是否过头

| 策略 | 阅读时要回答的问题 |
|---|---|
| PLAIN | 为什么某些类型根本不允许压缩／移出？ |
| EXTENDED | 为什么通常先试压缩，再考虑移出？ |
| EXTERNAL | 名称为何不意味着“数据库之外的文件”？不压缩会怎样影响局部取子串？ |
| MAIN | 说“优先内联”为什么比说“绝不移出”准确？ |

**原创任务**：订单行有短订单号和很长的发票正文。比较只查询订单号、查询完整正文、只修改数量三种操作。对于没有改变的外置正文，不能想当然地每次更新都完整重写；也不能在查询确实需要正文时说永远只读主行。

### 内存指针不应原样持久化

TOAST 文档还讨论进程内的 indirect／expanded 表示。它们有助于避免大值复制或重复处理，但其指针只在相应进程与生命周期中有效；落盘前需要转换成可持久化表示。

这给出一个与课堂 RID 相呼应的不变量：**磁盘格式中保存的定位信息，必须在进程重启后仍可按约定解释。** 一个 C++ 地址不是这种保证。不要因为它们都叫 pointer，就把磁盘引用和进程地址混成同一种东西。

## 3. SQLite 的动态类型不等于“全部字符串化”

阅读 *Datatypes In SQLite* 的 Storage Classes 与 Type Affinity 部分，先看值的存储类别，再看列的 affinity。

值可以属于 NULL、INTEGER、REAL、TEXT 或 BLOB。整数可采用不同长度的二进制表示，REAL 使用浮点表示；TEXT 采用数据库编码。所谓动态类型，是值携带类型、列的 affinity 影响转换偏好，不是所有内容都编码成十进制字符串。

**原创任务**：把“声明为 DECIMAL”“最终使用 NUMERIC affinity”“实际存储为 INTEGER 或 REAL”“提供精确十进制算术”写成四张卡片，检查哪几张可以由已读文档推出。不能仅看到 DECIMAL 的名字，就套用另一产品中精确 NUMERIC 的实现与语义。

另外，存储编码和字符串比较规则也不同。能存 UTF-8 不代表默认排序就是某语言用户期望的排序；本次只要求识别这个问题，不把未精读的全部 collation 规则塞进 L3。

## 5. 阅读后交付一张“契约卡”，而不是一串名词

对任一存储方案，填完下面五项才算能解释：

1. **对象**：它存的是页、元组、版本还是大属性块？
2. **标识**：标识在什么范围唯一，多久有效？
3. **映射**：从标识到字节需要哪些间接层？
4. **变化**：删除、更新、整理后，哪些映射必须改？
5. **失败**：进程重启、部分写入或对象丢失时，靠什么恢复？本讲尚未回答什么？

用同一张卡比较 slotted page、PostgreSQL `ctid`、SQLite rowid 和 TOAST，可以看见相同设计动机，同时避免把概念图误认成通用文件格式。
