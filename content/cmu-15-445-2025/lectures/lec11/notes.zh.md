# L11 学习笔记：结果装不下时，怎样仍然算对？

外存算子的关键不是给 Quicksort 换一个名字，而是同时回答三个问题：**哪些数据必须在内存；什么时候能确认一部分结果已经完整；每次物化到底读写多少页。** 嘉宾报告再把这三个问题扩展到本地与云端之间。

## 1. 先确定语义，再确定要保留的字节

用以下原创小模型贯穿推导：

```text
Orders(order_id, sku, amount, created_at, customer_note)
Stock(sku, warehouse, available)
```

| 请求 | 所需性质 | 不能偷换成什么 |
|---|---|---|
| 最近 20 个订单 | `created_at` 降序的前 20 条 | 任意扫描得到的 20 条 |
| 每种 sku 的平均金额 | 同组全部有效 amount 的均值 | 每个分片平均值的无权平均 |
| 所有出现过的 sku | 精确去重；未必需要有序 | 哈希摘要相同就认为同一个 sku |
| 按 sku 导出全部订单 | 完整且满足指定顺序 | 只把每个磁盘页内部排好 |

**key 与 payload 是不同预算。** 排序键可以只含 `created_at`，但输出若还需 `customer_note`，就必须携带该数据，或携带稍后能正确找回它的 RID。RID 是记录标识，不是业务 `order_id`，也不是某次 buffer pool frame 的裸指针。page 是磁盘／逻辑页，frame 是暂时承载它的内存槽；跨页释放 guard 后不能继续依赖失效地址。

- **早物化：** 把需要的 tuple 数据随键传递。排序记录更宽，但可能避免后续随机回表。
- **晚物化：** 先传键与记录位置。临时 run 更窄，但结果阶段还有读取 payload 的成本。
- 两者不是“行存永远早、列存永远晚”的法规。选择率、压缩、远程存储、后续列需求和访问局部性都影响结果。
- 对没有 `ORDER BY` 的查询，不应把某次观察到的顺序写进应用契约。哈希聚合结果尤其没有固有排序保证。

原讲定位：04:09–07:56、12:12–17:17、46:02–51:22。

## 2. Top-K：保存当前赢家，不是把输入全部排序

为避免与页数 N 混淆，本页用 **K** 表示返回条数、**T** 表示输入记录数、**N** 表示输入页数。

以升序取 K 条为例，维护一个最大堆，堆顶是当前候选中最差的一条。只要保持下列不变量，就能安全丢弃记录：

> 处理任意输入前缀后，堆里恰好保留该前缀最小的 K 条；若不足 K 条，则全部保留。被丢弃的记录不优于当前第 K 名。

新记录比堆顶更差时跳过；更好时替换堆顶并恢复堆性质。最终堆还不是 SQL 要求的完整有序输出，需要再排序候选或按合适方向取出。普通实现扫描 T 条、更新 $O(\log K)$，CPU 上界为 $O(T\log K)$，最后排序候选约 $O(K\log K)$；**单次顺序扫描只说明输入 I/O 约 N 页，不说明总 CPU 时间为 O(T)。**

### WITH TIES 的内存反例

`ORDER BY amount FETCH FIRST 20 ROWS WITH TIES` 保留与第 20 行完整排序键并列的所有记录。若全表 `amount` 都一样，输出就是全表，不能把内存锁死为 20 条。

当边界不断变好时，旧边界的并列候选也可能全部失去资格。因此不变量应以**当前第 K 个排序位置的边界**表述，而不是“遇到重复就永远保存”。实际实现可以使用辅助 tie 容器或其他策略，但必须有预算不足时的正确处理路径。

若希望固定最多 K 行而又要稳定选择，可以明确添加业务唯一键作为次级排序键；这改变了并列定义，不能由执行器擅自添加。`OFFSET L LIMIT K` 一般还需要覆盖前 L+K 个位置，不能仍只留 K 个。

原讲定位：17:17–24:03。OFFSET 与显式 tie-breaker 是编者补充，课堂未展开。

## 3. 外排的两个不变量，比公式更先

**初始 run 不变量：** 每个 run 的记录在整个 run 范围内有序，不只是逐页有序。若一次在内存排序 B 页，写出的这 B 页作为一个整体有序。

**归并前沿不变量：** 每个未耗尽输入 run 的当前键，是该 run 剩余部分的最小键。因此全局下一条只可能是这些当前键中最小的一个。

这解释了为什么一个 run 即使有十万页，也只需当前页在内存。消费完该页才推进到下一页，不能把“输入 run 数”误写成“全部输入页数”。输入一侧耗尽后，另一侧剩余记录本来有序，可以连续输出。输出缓冲满时写盘并复用；输入缓冲无需因此重新加载。

实现还要处理空输入、不满页的尾部、最后不足一组的 run、相等键、跨页移动、变长记录和输出页生命周期。不能把临时排序写到原表覆盖有效数据；临时文件和持有页面的 guard 也要在正常结束、失败与取消时正确释放。

## 4. 内存预算、run 数与页 I/O

下面是**明确限制的教学模型**：

- 非空输入共 N 个等尺寸数据页；排序记录的总页数在各轮保持 N。
- 算子独占 B 个有效页框，B≥3；不计比较器、堆节点、线程栈等额外字节。真实系统必须从总预算中先扣这些开销。
- pass 0 能用 B 页同时做内存排序；每次归并用 B−1 个输入页与 1 个输出页；没有双缓冲。
- 不利用自然有序 run、压缩、提前去重或部分聚合；每轮全部写出，下一轮再读回；缓存不跨轮免除磁盘 I/O。
- 成本单位是**页读／页写次数**，不是操作系统调用次数，也不是耗时、网络请求数或 CPU 比较次数。

令 $R_0$ 为初始 run 数，$F$ 为归并扇入，$L$ 为归并轮数：

$$
R_0=\left\lceil\frac{N}{B}\right\rceil,\qquad F=B-1
$$

$$
R_{i+1}=\left\lceil\frac{R_i}{F}\right\rceil
$$

$$
L=\left\lceil\log_F R_0\right\rceil,\qquad P=1+L
$$

$$
C_{\text{materialized}}=2NP
$$

P 包含 pass 0。若 $N\le B$，$R_0=1$、L=0，仅初始内存排序；在“读入后物化到磁盘”的模型里是 2N，若直接返回则没有那次 N 页写出。空输入单独处理，不把 N=0 塞进对数。

课堂最简 two-way 模型故意让初始 run 长度只有一页，归并扇入为 2，于是 P 为 $1+\lceil\log_2N\rceil$。不要把它和“B=3、pass 0 一次排序 3 页”的一般版本混成同一个计数模型。

### 原创例：40 页、5 页预算

![外部归并预算和逐轮页数](assets/external-budget.svg)

图为编者原创，不是课堂画面。N=40、B=5，初始 8 个五页 run；4 路归并后变成 2 个二十页 run，再合成 1 个四十页 run。共 3 个 pass，每轮读 40、写 40，总计 240 次页 I/O。

课堂例另为 N=108、B=5：run 数 **22→6→2→1**。长度依次是“21×5+3”“5×20+8”“80+28”“108”，共四轮、全部物化 864 次页 I/O。分组不足时用上取整，不能丢最后一个 run。

### 输出是否物化，必须写进答案

若外排至少有一轮归并，且最终归并结果可直接流给后继／客户端，不需要随机重访或落盘，则省去末轮 N 页写出：

$$
C_{\text{stream}}=2NP-N
$$

40 页例由 240 降至 200。若比较的是“排序完落盘，再被下游扫描一次”的完整链，则物化链原本还有 N 页读取；融合可同时避免最终 N 页写和下一算子那次 N 页读，但**不能再从已经没有计入这次下游读的 2NP 中减第二次 N**。

还要检查前提：后继算子能逐条消费；两算子同时存活的状态不挤掉假定的 B 页；不需要回退或复用完整结果；输出页布局、序列化和最终输出本身的持久化成本另计。若早投影让 run 更窄，或者末轮去重让结果变成 M 页，不能机械地给每轮都算相同的 N。

原讲定位：24:03–38:40；输出成本与融合推导为编者补充。

## 5. 双缓冲省的是等待，可能增加轮数

单线程同步循环近似经历“读→算→写→读”。双缓冲允许“处理当前块”的同时“预取下一块／写上一块”，把阶段重叠起来。理想情况下某段耗时更接近 CPU 与 I/O 两者的较大者，而非简单相加；实际仍受设备带宽、请求队列和同步开销约束。

**不能把 B 页全给归并后，再免费添加 B 页双缓冲。** 若每路输入都用两个页框，输出也用两个页框，一个明确的预算例子为：

$$
2F+2\le B
$$

$$
F\le\left\lfloor\frac{B-2}{2}\right\rfloor
$$

这是一个具体分配方案，不是所有实现的唯一公式。也可只对某些流预取或异步写出，但都必须重新列账。扇入下降可能让总 pass 增加；例如额外一轮意味着又读写整份数据，隐藏延迟的收益可能被抵消。

原讲说“有效缓冲约减半”是在解释这个取舍。多线程是一种手段，异步 I/O 也能实现阶段重叠；不能由此推导“只要开线程就一定更快”，更不能把双缓冲说成消除了磁盘访问。

原讲定位：32:27–35:14、38:40–41:15。

## 6. 排序聚合：完整性来自组边界

考虑：

```sql
SELECT sku, AVG(amount)
FROM Orders
GROUP BY sku;
```

按分组键排序后，同组记录连续。维护当前键、sum 和非 NULL 的 count，看到下一组才输出上一组；EOF 也是一个组边界，最后一组不能漏。没有分组键的全局聚合还需单独处理空输入的 SQL 语义，不能照搬“没看到组就不输出”的分组逻辑。

![排序和哈希分别怎样确认分组完整](assets/group-state.svg)

原创示例 `(A,10),(B,30),(A,20)` 中，A 的正确均值是 15。排序时只需当前组状态，不必把该组全部记录放入内存；哈希时则需要为尚未结束的各组保留状态。

| 聚合 | 可合并的常见状态 | 常见错误 |
|---|---|---|
| COUNT(*) | 记录数 | 把 NULL 行也丢掉 |
| COUNT(amount) | 非 NULL 数量 | 当成 COUNT(*) |
| SUM(amount) | 和及必要的“见过非 NULL”标志 | 空集返回值处理错误、溢出 |
| AVG(amount) | sum 与非 NULL count | 平均值直接再平均 |
| MIN/MAX | 当前值及初始化标志 | 用一个普通业务值冒充“尚无值” |

两份状态 `(sum=30,count=2)` 与 `(sum=90,count=1)` 合并应得到 `(120,3)`，均值 40；把两个局部平均 15 与 90 再平均得到 52.5，是错的。浮点结合顺序也会影响末位，不能把代数结合律直接当成二进制浮点逐位相同的保证。

### 何时可以把排序和聚合融合

若排序键使每个完整分组连续，最后一轮归并就可以更新组状态，组边界时输出一条聚合结果。要求不仅是“也做了某种排序”：例如仅按 `amount` 排序，不能据此认为相同 `sku` 连续。

有 `ORDER BY sku` 的聚合可复用组键顺序；有 `ORDER BY AVG(amount)` 则仍需对组结果重新排序。提前过滤与投影通常能缩小排序输入，但不能删掉后续过滤、分组或输出还要使用的属性。

本节针对 count/sum/avg 等小状态聚合。`array_agg`、精确中位数、某些 DISTINCT 聚合可能需要更多状态，不能泛称所有聚合都只占常数空间。SQL 的 NULL 计数规则与可合并状态边界是编者补充。

原讲定位：51:22–55:20、1:02:13–1:04:23。

## 7. 哈希聚合：完整性来自同键同分区

### 内存方案的预算不是输入大小

用哈希表保存 `(group key → aggregate state)`。若 Orders 有十亿行但只有 100 个 sku，状态可能很小；反之每行一个不同 sku，就可能接近输入规模。预算要包括键字节、状态字节、槽位／控制字节、负载率余量、变长分配、输入和输出缓冲，不能只乘“组数×sum 的 8 字节”。

哈希相同只说明候选位置相同，仍须按 SQL 分组语义比较完整键。NULL 的分组行为也不能照搬普通 `NULL = NULL` 的三值逻辑；系统的哈希与相等判定必须一致。

### 外存两阶段及 I/O 账本

第一阶段有 B 页：1 页输入、B−1 个分区输出缓冲。用 $h_1$ 将键送入分区，满页写盘。一个分区有很多页，但内存只留它当前的输出页。

第二阶段逐分区流式读取，使用 $h_2$ 建立内存聚合表。同一键的全部记录已在同一分区，因此处理完一个分区就能输出它的最终组结果，再复用状态。$h_2$ 应避免重复利用已被 $h_1$ 固定的低熵分区信息；可以另一个 seed／不同有效位，不必把“两个不同名字的函数”当作充分条件。碰撞仍要处理。

令第一阶段输入为 N 页、写出的全部分区为 $N_p$ 页、最终聚合输出为 M 页。没有递归、预聚合或缓存绕过时：

$$
C_{\text{hash,stream}}=N+2N_p
$$

$$
C_{\text{hash,materialized}}=N+2N_p+M
$$

含义分别是读原输入、写分区、读分区，以及可选的最终结果写出。仅在分区不膨胀也不缩小、页利用率相同即 $N_p=N$ 时，才简写为 3N 或 3N+M。不要给哈希聚合套排序的“每轮都输出 N 页”：聚合结果可能远小于输入。已有内存哈希表且没有溢写时，输入只读 N 页，物化输出再加 M。

### 分区溢出与热点反例

第二阶段必须满足：该分区**全部不同组的状态**加处理缓冲能放入预算。原始分区文件能放入内存是一个更强的简化充分条件，不是必要条件。若状态太大，递归重分区可把不同键分散，但不是无条件成功：

- 分布倾斜可能让某个分区持续很大，平均 $N/(B-1)$ 不是每个分区的上界。
- 同一个热点 key 无论换多少普通哈希函数，仍必须保持同键同分区，不能靠重哈希把它拆成不同“组”。
- 对 SUM/COUNT，重复热点可压缩成小型局部状态，再正确合并；对状态随组内数据增长的聚合，仍需适用的外存状态算法。
- 若对 x 页的数据额外做一次完整重分区，会额外读 x、写 x；之后叶分区处理的读取仍要算。仅部分分区重做时不该把全体 N 页都再收费。

排序与哈希的选择因此要比较输入是否已有序、最终是否要求有序、组数与状态宽度、偏斜、可合并性、I/O 与 CPU，并非“哈希永远优于排序”。

原讲定位：55:20–1:04:23；递归处理根据已读官方 notes §3，精确成本与热点反例为编者推导。

## 8. 比较器与索引也是代价模型的一部分

**排序语义必须一致。** 多列排序中后列只在前列相等时决胜；升降序、NULLS FIRST/LAST、collation 与字符串编码都属于比较规则。前缀快速比较只有在确实保持目标顺序时才能提前判定；前缀相等必须有后备比较。不同文件的字典编号不一定能跨字典直接比较大小。

**专门化不是改答案。** 模板、预生成代码或 JIT 只是在相同语义下减少类型分派、间接调用和解码成本。不能因排序快而省略完整键复核，或违反 C++ 对齐与对象生命周期规则。

**“已有索引”要补四个条件。**

1. 键列顺序、方向和比较语义能提供本次请求的顺序；前缀扫描是否适用要逐计划判断。
2. 需要哪些 payload？覆盖索引可能免去回表；非覆盖索引则要取实际 tuple。
3. 索引顺序与表页物理局部性如何？聚簇通常更有利，不代表页面绝对连续或读一次没有 CPU 开销。
4. 要多少结果、缓存如何？全量非聚簇回表可能接近每行随机读一页，但 Top-K、小选择率或热缓存可完全改变判断。

因此课件的“clustered always better / no computational cost”应理解为其**顺序匹配、全量读取、局部性好、简化冷页 I/O 模型**的说明，而非普适定理。同样，非聚簇索引也不能仅因名字就被排除。

原讲定位：41:15–51:22。

## 9. MotherDuck：把预算问题扩展到网络边界

嘉宾报告的价值不是一个“单机胜过分布式”的口号，而是重新选择优化单位：**仓库总量、单条查询扫描量、活跃组状态、并发用户数不是同一个量。**

| 维度组合 | 嘉宾提出的方向 | 仍须询问的条件 |
|---|---|---|
| 数据小、计算小 | 嵌入式 DuckDB，本地使用；云端提供协作 | 数据是否已在本地、授权与共享怎样处理 |
| 数据大、计算小 | 在云端近数据扫描并聚合，只回传汇总 | 汇总是否真的小、下推是否保持语义 |
| 数据小、计算大 | 按需使用更强云实例 | 启动／传输成本是否超过计算收益 |
| 多用户同时工作 | 每个用户的 duckling，按需启动和关闭 | 总容量与共享存储争用如何约束 |
| 数据大、计算也大 | 大单机效率与 DuckLake 生态方向 | 报告未给通用扩展证明，不能补成任意规模保证 |

以 Orders 的云端数据和本地 Stock 为例，若查询先按 sku 汇总订单，再与本地库存结合，可能只需跨网络传每个 sku 的摘要。**但不能任意把 join 与 aggregation 对调。** 例如 Stock 的同一 sku 有多个仓库，连接会复制订单；应先明确要按仓库重复计量、去重，还是按 sku 汇总库存，然后才能证明下推等价。这里是编者的边界例子，不是嘉宾已经证明过的优化。

嘉宾讲到扩展要贯穿 parse／bind／optimize／execute：认识云表、决定在哪算、实现两侧执行。浏览器中的样本预览降低交互延迟，但样本结果不等于完整数据结果；可视化静帧也不是延迟基准。报告在计算层与容器隔离处结束，未讲完存储层；不能根据架构截图补齐未讲出的协议。

## 11. 原创自测

<details>
<summary>1. 已经把每页内部排序，可以顺序拼接所有页吗？</summary>

不可以。例如第一页 `[2,9]`、第二页 `[1,8]` 各自有序，拼接却不是全局有序。需要对 run 的当前键做归并；或者从一开始对整个多页块排序，才把它认作一个多页 run。

</details>

<details>
<summary>2. N=40、B=5，为什么不是五路归并？所有结果落盘与末轮直出分别多少页 I/O？</summary>

归并必须预留一页输出，所以是四路。初始 8 个 run，再变成 2、1，共三轮。全部物化 240；末轮直出省 40 页写入，得到 200。这里没有额外算下游从最终文件再扫描的 40 页，也没有计算 CPU、网络或结果序列化。

</details>

<details>
<summary>3. 给归并加双缓冲，仍沿用 B−1 路对不对？</summary>

除非增加了总预算，否则不对。预取和异步写出的缓冲必须占页。如果输入和输出都双缓冲，满足 `2F+2≤B`，扇入下降可能增加 pass。是否更快需要比较隐藏等待的收益和额外 I/O，不能只说“多线程快”。

</details>

<details>
<summary>4. LIMIT 10 WITH TIES 一定只保存十条吗？</summary>

不一定。与第十条完整排序键并列的都要保留；全表同键时结果可能是全表。统计可以帮助选策略，但不能代替预算耗尽时的正确处理。只有明确的无 ties 语义或唯一排序键等额外条件才限制返回数量。

</details>

<details>
<summary>5. 一个哈希分区有十亿条同 sku 订单，递归换哈希函数就一定解决吗？</summary>

不能。相同键仍进同一分区。但若计算 SUM/COUNT，十亿条记录可以流式压成一份小状态，并不需要原分区整体入内存。真正的问题是状态大小、不同组数或不可压缩的组内数据；普通递归分区不是热点万能药。

</details>

<details>
<summary>6. 两组局部平均 15、90，直接输出 52.5 是否正确？</summary>

只有两组有效计数相同等额外条件下才恰好正确。若第一组两条、第二组一条，应合并 `(sum,count)` 为 `(120,3)`，得到 40。SQL AVG 还要排除 NULL，不能用总行数替代非 NULL count。

</details>

<details>
<summary>7. 外部哈希输入 200 页、实际写分区 220 页、最终 8 页，不递归时成本是多少？</summary>

流出结果：`200+220+220=640` 次页 I/O；物化结果再加 8，合计 648。不能直接写 3×200，因为分区实际页数已经因布局等因素增长。此题不假设额外预聚合，也不含最终文件被客户端再次读的成本。

</details>

<details>
<summary>8. B+Tree 上按 sku 有序，SELECT * ORDER BY sku 就一定优于外排吗？</summary>

不一定。先确认比较语义和方向吻合，再看覆盖性、是否要随机回表、读取范围、缓存与物理局部性。聚簇全量扫描通常很有利；非聚簇少量 Top-K 或覆盖索引也可能很有利。“有序索引”不是对全部 payload 访问成本的保证。

</details>

<details>
<summary>9. 云端先按 sku 聚合，再连接本地 Stock，总可以减少传输且保持结果吗？</summary>

不能只看传输量就交换算子。Stock 若同 sku 多行，join 的重复与过滤会影响原查询的计数和求和。必须先写明目标语义并证明变换等价，再讨论只传汇总。嘉宾的 dual execution 是优化方向，不是允许随意重排关系算子的许可证。

</details>
