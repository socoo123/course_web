# L6 资料导读：从课堂概念图到 Parquet 格式契约

读列式文件格式时，先分清三个契约：**别把文件分组当成一次 I/O，别把字典编码当成保序承诺，别把简化整数编码当成可直接互操作的格式。**

## 1. 元数据到底用什么协议

官方 Metadata 文档区分 file metadata 与 page header metadata，明确说明 Thrift 结构使用 **TCompactProtocol** 序列化。文件元数据提供定位文件内容所需的偏移和大小；页头元数据与页数据内联存放，用于读取和解码。

这直接修正课堂 43:43–47:00 讨论中把 Parquet 称为 protobuf 的口述。但不要从这一点进一步臆测所有元数据都必须一次性读入，或所有格式都把每组元数据放在课堂图示的相同位置。格式字段、客户端读取策略与缓存策略是三个不同问题。

**阅读时问自己**：知道某列块的偏移，是否已经知道其中一个值的字节地址？不一定。还要知道页、编码、NULL／嵌套层次和该编码的定位方式。本文只全文读了网页正文；页面引用的两张结构图没有做图像细读，也没有阅读全文链接到的 `parquet.thrift` 源码。

## 2. 为什么 row group 与 data page 可以采用不同尺度

官方 Configurations 文档对两者分别讨论：

- 大 row group 能形成较大 column chunk，支持更大的顺序 I/O；代价是写入时更多缓冲，或者两遍写入。页面给出 512 MB–1 GB 行组的建议，并在其 HDFS 场景下讨论与 block 的配合。
- data page 作为不可再任意拆分的解码／读取单位，小页利于较细访问，大页减少页头和解析开销。该页面给出 8 KB 页大小建议，同时特别说明：顺序扫描并不意味着一次只读一页，page 不是 I/O chunk。

这些是**该官方页面给定语境中的建议**，不是所有 Parquet 写入库的默认值，更不是一个格式必须恒定的行数。不要把课堂近似提到的“百万行”与这里的字节建议互相覆盖，也不要把它们混成一个尺寸。

### 原创纸面推演

假设一份订单文件有一个较大的行组，查询只读 `sku` 和 `qty`。先由元数据找到相关列块，再决定读取哪些页。此时：

1. 行组包含所有列，不等于本次必须传输所有列。
2. 一列分成很多 data page，不等于读取器每页发一个网络请求。
3. 一次请求取回较大范围，不等于每个解码操作必须处理整个范围。

这三句话把“文件组织、请求合并、编码边界”分开了，才有可能解释真实系统的性能。

## 3. 字典编码：格式说明并没有替你保证整数范围语义

官方 Encodings 的 Dictionary Encoding 节说明：字典存于 column chunk 的 dictionary page，放在相关 data pages 之前；字典项使用 PLAIN 表示，数据页中的字典索引用 RLE／bit-packing hybrid。字典太大时可以回退到 plain encoding。

从这些已读文字能确认“码索引字典”的机制，**不能得出字典项必须按业务字符串顺序排列**。因此课堂的 `LIKE 'And%'` → 整数范围，是额外具有保序性质时的优化示例，不是读到 `RLE_DICTIONARY` 就能盲用的规则。

同理，字典不是整张表必定共用的一份全局数据。不同 column chunk 的码需要按自己的字典解释；NULL 也不能简单假设为字典里某个随便挑选的整数。当前编码页没有替应用规定 SQL 的全部空值与排序语义。

## 4. 课堂的“小整数”到真实比特流，中间还差什么

已全文读过 Encodings 页，包括 PLAIN、字典、RLE／bit-packing hybrid、旧 BIT_PACKED、delta、delta-length byte array、delta strings、byte stream split 和当前 ALP 概述。这里只抽取与本讲直接相关的阅读结论，不转载完整规范：

### 位序与运行长度是格式契约

现代 RLE／bit-packing hybrid 与已弃用的 BIT_PACKED 在位打包次序上不同。即使两种实现都能把八个三位数装入三个字节，如果位序不一致，仍然不能互读。混合编码还规定 run header、长度与何时携带额外长度字段；它不是把课堂 `(值, 起点, 长度)` 三元组原样序列化就算实现完成。

### Delta 需要分块、位宽与溢出约定

`DELTA_BINARY_PACKED` 先计算相邻差值，再在块内找最小差值作为参考，把相对值分 miniblock 打包，各 miniblock 可以有自己的位宽。页上给出了块尺寸约束、最后一块填充及符号处理规则。

规范还明确处理求差与恢复时的整数回绕；在 C++ 中不能直接依赖有符号溢出的未定义行为。读者应区分“数学上两次加减抵消”与“语言和文件规范允许怎样做”。

该页为解释使用了块大小为 8 的小例子，并明确说这在真实格式中不合法。**教学例子能算通，不等于产生了合规文件。** 本页不要求学习者实现 Parquet 编解码器，也不把它加入 Project 1 任务。

### 有些变换本身不缩小字节数

Byte stream split 把同一字节位置的数据聚在一起，输出总字节数仍与输入相同，但可能让后续通用压缩更有效。这提示“编码有价值”的理由不必是该步骤单独缩小了文件，也可能是改善后续阶段的数据规律。
