# FineWeb 与 DataComp-LM：数据配方必须放进固定协议中比较

## 第一篇：The FineWeb Datasets

### §3 构建 FineWeb

FineWeb 的设计主要基于经验实验：我们进行了一系列“数据消融”实验，测试流水线每个阶段的不同方法。本节按顺序记录实验结果与设计选择。除非另有说明，所有消融都遵循迭代构建数据集的过程，即每个小节的基线模型只包含前面各小节的处理步骤。我们的结果可以使用 datatrove 仓库中的代码完整复现。

### §3.1 实验设置

我们通过训练数据消融模型，比较各阶段的流水线设计。模型除了训练数据之外完全相同：参数量和架构超参数相同，并从每个版本的数据中随机抽取相同数量的 token 进行训练。随后，在同一组下游任务基准上评测这些模型，具体基准见下文。为了尽量减少随机数据子集选择对评测分数的影响，我们为每个数据版本训练两个模型，分别使用不同但大小相同的随机子集，以及不同的初始化种子，然后比较平均分数。

所有训练均使用 nanotron 库。数据消融模型均有1.71B参数，包含 embedding 参数；采用 Llama 架构[2]，序列长度2048，全局 batch size 约200万 token，并使用 GPT-2 tokenizer[20]。在同一实验中，所有模型使用同样数量的数据、训练同样步数。过滤消融训练约28B token，这大致是该模型大小的 Chinchilla 最优训练数据量[1]；部分去重消融，以及确认每个过滤步骤累计相对收益的实验，则训练350B token。完整训练超参数见原附录D。我们在数据集仓库中公开全部消融模型。我们总共在内部集群训练了70多个模型，估计合计消耗80,000个 H100 GPU 小时。

评测使用 lighteval 库。我们希望选出的基准在相对较小的数据消融规模上仍能提供有效信号。具体而言，我们选择的基准满足：用同一数据集的不同随机样本训练时，模型分数的方差较小；在一次训练过程中，分数单调或近似单调上升；这种大小的模型得分高于随机基线。这些标准使数据子集上的分数能够代表整个数据集，并可靠地反映训练数据对模型性能的影响。最终选用了 CommonSense QA[42]、HellaSwag[43]、OpenBook QA[44]、PIQA[45]、SIQA[46]、WinoGrande[47]、ARC[11]和 MMLU[10]；较大的基准截取1000个样本，以便在训练过程中高效评测。我们的精确评测设置也已公开。

### §3.2 文本提取

Common Crawl 数据有 WARC 和 WET 两种格式。WARC，即 Web ARChive 格式，包含爬取的原始数据，包括完整页面 HTML 和请求元数据。WET，即 WARC Encapsulated Text，使用 htmlparser[48]提供被爬网站的纯文本版本。虽然创建数据集时经常以 WET 文件为起点，但与 Gao 等人[29]的观察类似，我们发现 WET 保留了过多模板文字和菜单文本。因此，我们尝试使用开源 trafilatura 库[49]从 WARC 中提取正文；从人工查看结果来看，与其他可用库相比，它的提取质量较好，保留的模板和菜单文字更少。

自定义文本提取成本相对较高，但会反映到模型性能上。图1比较了两类消融模型：一类使用 trafilatura 从 WARC 提取的文本，另一类使用 WET 数据；两者都只做了极少的额外过滤，即使用 fastText 语言识别保留英语为最高概率标签的样本，并且没有去重。WARC 经 trafilatura 提取的文本明显带来更好的模型，因此后续所有实验都采用基于 WARC 的数据。

**原图1图注译文：trafilatura 提取的 WARC 与 WET。** 28B token 消融实验。自定义文本提取优于默认 WET 数据。除 fastText 英语语言过滤外，没有应用任何过滤或去重。

**原图2图注译文：经过基础过滤的 WARC 与未过滤的 WARC。** 28B token 消融实验。基础过滤步骤显著提高性能。

> **编者读图注。** 图1、2横轴均为训练 token 数，以十亿计；纵轴为聚合准确率。此处§3.2的“英语是概率最高标签”不同于下一节的“英语得分至少0.65”，不能混写成同一实验条件。

### §3.3 基础过滤

我们首先采用 RefinedWeb[50]设置中的一部分作为基础过滤流水线。具体做法是：使用屏蔽列表[51]进行 URL 过滤，移除成人内容；使用 fastText 语言分类器[52,26]，只保留英语得分不低于0.65的文本；应用 MassiveText[41]的质量和重复过滤器，并沿用原始阈值。将这些过滤操作应用于撰写本文时可用的96个快照中、从 WARC 提取出的全部文本后，按 GPT-2 tokenizer 计量，得到约36T token。图2显示这些步骤提高了模型性能。

### §3.4 去重

网络上存在许多聚合站、镜像站、模板页面，以及分散在不同域名和网页上的其他重复内容。移除这些重复内容，即去重，与模型性能改善[5]以及对预训练数据记忆程度降低[53,54]有关。重复数据既有不同的识别方法，也有不同的定义。常见方法依赖哈希技术，或者后缀数组等高效数据结构[55]。方法可以是使用相似度度量的“模糊”方法，也可以是检查两个文本块完全相同的“精确”方法[56]。

参考 RefinedWeb[50]，我们尝试 MinHash。这是一种基于模糊哈希的去重技术，可以高效扩展到许多 CPU 节点；通过控制桶数及每桶哈希数，可以调整相似度阈值，通过控制 n-gram 大小，可以调整所考虑的子序列长度。我们使用英语分词器[57]收集每篇文档的5-gram，使用总计112个哈希函数计算 MinHash，分成14个桶，每桶8个哈希值，目标是找出相似度至少75%的文档。只要两个文档在任一桶中的8个 MinHash 值完全相同，就将它们视为重复。随后进行传递性聚类：如果A与C重复，B与C重复，那么A、B、C进入同一个重复簇，即使A与B之间不存在任何一个8个 MinHash 全匹配的桶。每个簇随机保留一篇文档，删除其余重复文档。附录E.1进一步讨论去重参数。

**原图3图注译文：全局 MinHash 去重研究。** 对整个数据集应用全局 MinHash 去重，只带来有限的性能提升；得到的模型仍远落后于在 RefinedWeb 上训练的模型。

**原图4图注译文：2013-48快照上的全局 MinHash 影响研究。** 全局去重提高了最后被去重的快照中低质量数据的相对占比，导致保留数据的性能差于被移除的数据。

我们的第一种方法是在整个数据集，即全部96个快照上，全局应用 MinHash 去重。具体采用迭代方式：从实验时最新的快照2023-50开始，按时间向更早的快照推进，直到最老的快照。对最老的快照应用该过程时，由于需要与大量其他快照去重，最多移除了原先基础过滤后数据的90%。以这种方式对整个数据集去重后，剩下4T token。然而，从中随机抽取350B token训练，消融模型相对于未去重数据训练的模型几乎没有提高，在我们的任务聚合指标上远低于 RefinedWeb，见图3。

这一结果挑战了我们最初的假设：全局去重必然带来更高的基准分数。因此，我们又做了一项实验，调查剩余数据的质量。我们从较老的2013-48快照构造两个数据切片并分别训练模型：（a）完整去重后保留下来的约31B token，称为“原先保留的数据”；（b）迭代去重过程中从该快照移除的约460B token，单独去重、不考虑其他快照后得到171B token，称为“原先移除的数据”。图4给出了结果。对这个旧快照单独考察时，原先保留的数据，即原数据的约10%，质量实际上比移除的约90%更差。人工查看也确认了这一点：与原先移除的数据相比，原先保留的数据包含更多广告、缺乏连贯性的关键词列表，以及总体格式较差的文本。

因此，我们尝试另一种方法：沿用此前参数，分别对每个快照独立去重，不考虑其他快照。这样得到了20T token。从这个数据集中随机采样，样本覆盖所有快照，训练后达到了与 RefinedWeb 相当的性能，见图5。

我们的一个假设是，去重的主要收益来自移除所有快照中都存在的大型重复簇，这些簇包含数十万篇文档[50]；继续对重复数量较少的簇去重，例如重复少于约100次、与快照数量相近的簇，反而可能损害性能。对这部分数据，更有针对性地过滤质量长尾，可能比继续去重更合适。

为了改进逐快照独立去重，我们也尝试了更“轻量”的全局去重技术。最终，没有一种优于逐快照独立去重。原附录E.3完整描述了这些方法和结果。

**原图5图注译文：独立 MinHash 去重研究。** 与全局 MinHash 不同，逐快照独立去重提高了平均分数。

> **编者边界：75%不是硬门槛。** 上述“目标至少75%”是概率性的 LSH 工作区间，不是先计算精确 Jaccard 再按0.75截断。原论文的簇边由桶碰撞产生；不能把 A4 的“候选后验证真实 Jaccard”要求反套成 FineWeb 已执行的步骤。传递闭包也不保证同簇任意两篇文档都具有75%相似度。完整概率见本页附录E.1译文。

### §3.5 加入 C4 的过滤器

到这一步，通过基础过滤与独立 MinHash，我们已经达到了 RefinedWeb[50]的性能。不过，我们注意到 C4[15]虽然比 FineWeb 小，在评测套件中的某些基准上仍表现更好，特别是 HellaSwag[43]；它是聚合任务组中信噪比较高的基准之一。虽然 C4 是较早的大规模 LLM 训练数据集之一，但仍经常出现在 Llama 1[2]等较新模型的预训练混合数据中。我们于是研究额外过滤步骤，希望达到或超过 C4。自然的起点就是检查 C4 自身的处理过程。

C4 来自2019-18快照，构建时采用启发式过滤：删除末尾没有终止标点的行、提及 javascript 的行、包含“使用条款”或“cookie政策”声明的行；删除过短文档，以及包含“lorem ipsum”或左花括号的文档。我们以基础过滤并逐快照独立去重的2019-18快照为基线，尝试添加这些过滤器，同时与 C4 本身比较。

图6表明，应用全部过滤器，可以达到 C4 的 HellaSwag 性能。花括号过滤器和词长过滤器只带来小幅提高，分别移除2.8%和4.3%的 token。终止标点过滤器单独使用时，带来最大的单项收益，但会删除约30%的全部 token。`lorem_ipsum`、`javascript`和`policy`规则各自移除的训练 token 少于0.5%，因此没有单独为它们训练模型。“除终止标点外的所有过滤器”优于只使用终止标点过滤器，同时总体只删除约7%的数据。我们决定应用上面提到的所有 C4 过滤器，但不应用终止标点过滤器，因为它删除的数据量过大。

**原图6图注译文：比较 C4 过滤器对 HellaSwag 基准性能的影响。** 终止标点过滤器带来的性能提升最显著。

**原图7图注译文：FineWeb 自定义过滤器研究。** 组合过滤器优于基础过滤基线，也优于表现最好的 C4 单项过滤器，即终止标点过滤器，同时移除的数据更少。

> **编者校读。** 原图6图注的“最显著”指单项过滤器，不是说它胜过“所有过滤器”或“除终止标点外的组合”。两类组合与单项的区别在正文中保留。

### §3.6 开发额外的启发式过滤器

以往工作主要通过查看数据来开发启发式过滤器[15]。本研究设计了一个更系统的流程，用来选择过滤规则及调整阈值。我们先在一个高质量和一个低质量网页数据集上，收集50多种高层统计量：从文档级指标，例如行数、平均行长和词长，到受 MassiveText[1]启发的文档间重复指标。具体来说，我们把§3.4中提及的2013-48快照的独立去重版本和全局去重版本，分别作为“高质量”和“低质量”数据集。然后找出在两个数据集上分布显著不同的指标，查看两种分布的直方图，并根据经验选择阈值，针对低质量数据集频率高于对应高质量数据集的直方图区间进行过滤。

例如，图8绘制了“以标点结尾的行所占比例”的分布。可以看到，在该指标较大的区间，高质量数据集的文档密度通常更高；尤其在数值低于0.12时，低质量数据集的文档密度高得多。因此我们推断，以标点结尾的行占比低于0.12的文档，通常质量较低，并把这个值作为文档过滤的候选阈值。对所有指标重复这个流程，得到16组候选的“指标—阈值”。

随后，我们在2019-18快照上进行多次28B token消融训练，评估这16个新过滤器。完整实验细节见原附录E.4。在这些实验中，我们找出了对聚合基准分数提高最显著的三个过滤器，消融结果见图7。具体而言，删除满足以下一个或多个条件的文档：

| 文档删除条件 | 单独使用时移除的 token | 原文对照 |
| --- | ---: | --- |
| 以标点结尾的行占比不高于0.12 | 10.14% | 原 C4 终止标点过滤器约移除30% |
| 重复行中的字符占全部字符的比例不低于0.1 | 12.47% | MassiveText 原阈值为不低于0.2 |
| 短于30个字符的行占比不低于0.67 | 3.73% | 本文新选择的短行规则 |

三个过滤器一起应用时，约移除22%的 token，并在28B token消融中使聚合分数提高约1%。这些过滤器进一步提高了性能，尤其是在删除数据比例较小的情况下，超过了 C4 数据集的表现。

**原图8图注译文：去重方法对2013-48快照的影响。** 直方图显示，相对于独立 MinHash，全局 MinHash 得到的数据中，“以终止标点结尾的行占比很小”的文档出现得更频繁。图中也标出了选定的过滤阈值。

> **编者校读。** 原文在候选阈值讨论中写“小于0.12”，在最终过滤规则中写“不高于0.12”；这里分别保留，不静默统一。三个单项移除率不能相加当作联合移除率，因为命中的文档会重叠。原文“约1%”及图10“约2%”沿用其写法；纵轴是百分数准确率，不应据此声称已经报告相对百分比改善。

### §3.7 最终的 FineWeb 数据集

综合前面各节的决策，并把所得流水线应用于96个 Common Crawl 快照，就得到了15T token的 FineWeb 数据集。具体步骤是：从 WARC 文件提取文本（§3.2），应用基础过滤（§3.3），逐快照独立做 MinHash 去重（§3.4），应用选定的 C4 过滤器（§3.5），最后应用自定义过滤器（§3.6）。图9表明，每一步都在我们的基准任务组上带来相对性能收益。对于公开发布的数据集，我们还进行了个人可识别信息（PII）移除，方法是匿名化电子邮件地址和公网 IP 地址。

图10将 FineWeb 与以下常用、公开可获取的网页规模数据集比较：RefinedWeb（500B token）[50]、C4（172B）[15]；Dolma 1.6（3T）和1.7（1.2T）的 Common Crawl 部分[58]；The Pile（340B）[29]；SlimPajama（627B）[35]；RedPajama2 的去重版本（20T）[34]；Matrix 的英语 Common Crawl 部分（1.3T）[59]；英语 CC-100（70B）[60]；以及 Colossal-OSCAR（850B）[61]。FineWeb 表现强劲，而下文详述的 FineWeb-Edu 在我们的聚合任务组上优于参与比较的其他所有开放数据集，进一步支持了这些设计选择。注意，训练这些模型时，我们从每个数据集中随机抽样350B token，没有对任何单个 Common Crawl 快照进行上采样。

**原脚注1译文。** RedPajama2 包含40多项质量注释，但实际只使用 CCNet 流水线[28]进行过滤。

**原图9图注译文：FineWeb 的每一个处理步骤都提高了性能。** 相对于基础过滤（§3.3），应用逐快照 MinHash 去重（§3.4）、C4 过滤器（§3.5）以及额外启发式过滤器（§3.6），每一步都能提高性能。

**原图10图注译文：FineWeb 系列与其他公开数据集的比较。** 基础 FineWeb 表现强劲；教育子集 FineWeb-Edu 超过其他所有被比较的公开数据集，并进一步使聚合分数提高约2%。

> **编者边界。** 这里的“PII移除”只有原文明确列出的邮箱与公网IP匿名化，不是“已证明没有个人信息”。“公开可获取”也不等于所有网页原文都具备相同再利用许可。上述数据集大小是论文在各自版本与计量口径下的报告，不可直接与另一篇的数字拼接成严格同口径排名。

### §4 FineWeb-Edu

最近出现了一种有趣的 LLM 训练数据过滤方法：利用合成数据开发识别教育内容的分类器。该技术已用于 Llama 3[6]和 Phi-3[8]等未公开的预训练数据集，但其对大规模网页数据过滤的影响还没有得到公开研究。我们把这项技术应用于 FineWeb：用 Llama-3-70B-Instruct[62]生成合成标注，再利用这些标注开发教育质量分类器，进而过滤 FineWeb。得到的 FineWeb-Edu 包含1.3T token。它专门针对教育内容优化，在 MMLU、ARC、OpenBookQA 等多项知识与推理密集型基准上，以明显优势超过所有公开可获取的网页数据集。

为了构建合成标注，我们使用 Llama-3-70B-Instruct，对从 FineWeb 的 CC-MAIN-2024-10快照中随机抽取的460,000个网页，按0至5分评定教育质量。我们探索了多种提示格式，希望自动提取教育评分，发现 Yuan 等人[63]使用的累加量表效果最好。它允许 LLM 逐项评估标准、逐步累积得分，不同于依据预定义类别直接给出固定分数的单次评分量表[64]。为了避免 LLM 偏爱 arXiv 摘要和投稿等高度技术化页面，我们在提示中要求它聚焦小学和初中层次的知识。合成标注提示见原附录F.1。

为了把过滤扩展到整个 FineWeb，我们在 Snowflake-arctic-embed-m embedding 模型[65]上训练了一个线性回归模型。用410,000条 Llama 3 合成标注，以学习率 $3\times10^{-4}$ 训练该线性回归器20个 epoch，同时冻结 embedding 和 encoder 层。在由剩余50,000个样本组成的留出验证集上，将 Llama 3 标注视为真值，选择 F1 最高的 checkpoint。训练后，将模型输出四舍五入为0至5的整数，再用固定阈值判断 FineWeb 中的文档是否具有教育性。我们研究了不同过滤阈值的影响，最终为 FineWeb-Edu 选择最低分数3，因为它在知识和推理密集型基准的性能与 HellaSwag[66]等其他基准的性能之间，提供了最好的折中。阈值为3时，模型在验证集上取得82%的 F1，显示出较强的高质量教育内容识别能力。

将这一分类器应用于 FineWeb 的15T token，花费了6,000个 H100 GPU 小时。

为了在更大规模上确认教育过滤的有效性，我们进行了更大的消融实验，类似前述 FineWeb 过滤消融，使用350B token训练一个1.71B模型。如图10、11所示，FineWeb-Edu 超过 FineWeb 及其他开放网页数据集，在 MMLU、ARC、OpenBookQA 等教育基准上的提高尤其显著。具体来说，MMLU 从33%提高到37%，相对提高约12%；ARC 从46%提高到57%，相对提高约24%。

在 MMLU 上，FineWeb-Edu 用接近十分之一的 token 就能达到 Matrix 的最终性能，说明用 LLM 标注训练分类器，可以有效支持大规模数据过滤。更多评测图见原附录F.2。

**原图11图注译文：MMLU 性能比较。** FineWeb-Edu 仅训练38B token，MMLU 准确率就达到33.6%，显著优于该指标上排名第二的 Matrix；后者训练到300B token才达到相近准确率。

### §5 偏差分析

语言模型会反映预训练数据中的偏差，这一点已有研究[72–77]。为了简要描绘 FineWeb 和 FineWeb-Edu 中的数据集偏差，我们聚焦于英语国家认为“敏感”或“受保护”的子群体。它们是历史上受到歧视的群体的一部分，也更容易成为刻板印象等负面社会规范的对象；这些现象会反映到数据集吸收的文本语言中。

我们发现，FineWeb 中体现主导性规范的词相对过度出现，例如“man”和“christian”；这些词已知在在线文本中被过度代表[72]。虽然所检查的性别、宗教和年龄子群体间的偏差并不强，但最偏斜的关联出现在宗教词与亲密关系之间，例如“christian dating”和“jewish singles”。与其教育定位相符，FineWeb-Edu 捕捉到的关联较少涉及亲密关系，更接近历史和健康教育内容中可以预期的关联，例如“man”与“king”关联，“woman”与“pregnancy”关联。更多细节见原附录G。

### 附录E.1 去重参数

如§3.4所述，我们的 MinHash 去重使用5-gram和112个哈希函数。每个5-gram都由112个函数分别哈希；对每个哈希函数，取文档全部5-gram上的最小哈希值，得到一个文档签名。随后把112个 MinHash 值分成14个桶，每桶8个。如果两篇文档至少在其中一个桶上具有完全相同的8个 MinHash，就认为它们匹配。

在这些参数下，两篇文档的 n-gram 相似度 $s$ 分别为0.7、0.75、0.8和0.85时，被识别为重复的概率分别约为56%、77%、92%和98.8%。因此，这种分桶方案有较高概率匹配相似度至少75%的文档，而相似度达到85%及以上的文档几乎肯定会被匹配。计算这些数值时，依次考虑以下概率：一个哈希函数的值相同，概率为 $s$；一个桶的8个值不全部相同，概率为 $1-s^8$；14个桶都没有8个值全匹配，概率为 $(1-s^8)^{14}$；最后，至少一个桶的8个值全部匹配，概率为：

$$
P(\text{至少一桶匹配})=1-(1-s^8)^{14}.
$$

图13比较了我们的112个哈希值设置，与 RefinedWeb 的9000个哈希值设置；后者分为450个桶，每桶20个值。

虽然 RefinedWeb 的大量哈希函数使截断更陡峭、更明确，即阈值附近的文档对更可能得到正确识别，但它也需要明显更多的计算资源，因为每个哈希值都必须计算、存储，再与其他文档的哈希值比较。我们认为，计算与存储节省足以补偿阈值附近文档上增加的不确定性。

**原图13图注译文：FineWeb 与 RefinedWeb 的文档匹配概率比较。** 图内两条曲线分别为：

$$
\begin{aligned}
P_{\mathrm{FineWeb}}(s)&=1-(1-s^8)^{14},\\
P_{\mathrm{RefinedWeb}}(s)&=1-(1-s^{20})^{450}.
\end{aligned}
$$

> **编者解释。** 这里使用理想 MinHash 的 Jaccard 碰撞性质及独立性近似。$s=0.75$并不意味着100%召回，而约为77%；$s=0.70$也不是绝不入簇。这个概率既不是精确 Jaccard 验证结果，也不是整个传递聚类的任意两点相似度保证。

### §3 面向语言模型的 DataComp（DCLM）基准

本节介绍 DCLM 的主要组成部分。我们首先介绍支撑基准的原始文本语料 DCLM-POOL（§3.1），接着介绍图2展示的工作流程：选择竞赛规模（§3.2），通过过滤 DCLM-POOL 并可能加入其他来源来构建数据集（§3.3），使用固定超参数训练模型（§3.4），最后评测模型，为数据集评分（§3.5）。

**原图2图注译文：DCLM 工作流程。** （A）参赛者先选择一个规模，更大的规模意味着更多训练 token 或更多模型参数。（B）接着过滤一个数据池，即过滤赛道，或混合自己的数据，即混合赛道，构成数据集。（C）使用整理后的数据集，按标准化训练代码和特定规模的超参数训练语言模型。（D）随后在53个下游任务上评测，以判断数据集质量。

### §3.1 DCLM-POOL

DCLM-POOL 是一个未过滤的网页文本语料，包含2023年之前的全部 Common Crawl[45]数据。根据§4.2的结果，我们使用 resiliparse[20,21]从 HTML 重新提取文本，而不使用 Common Crawl 预先提取的文本。DCLM-POOL 包含200B篇文档，gzip压缩后为370TB，按 GPT-NeoX[24]计数共有240T token。其他细节见原附录E。

**去污染。** 测试集样本经常污染语言模型训练集[52,55,190]，不过，这类样本对下游性能的影响在很大程度上仍不明确[94,122,157]。为了让研究者更好地研究污染，我们发布去污染工具，而不直接对 DCLM-POOL 去污染。首先，我们为两个热门任务 MMLU 和 HellaSwag[78,195]实现了自己的去污染流程，§4.6使用了该流程。其次，我们提供基于 Lee 等人[94]的工具，用来检查数据集与全部测试集之间的重叠。我们要求所有提交披露去污染报告，并避免使用高度污染的数据。对于得分最高的提交，我们计划专门评估其污染情况。

### §3.2 竞赛规模：支持不同计算约束的参与者

为了让具有不同计算约束的研究者都能参与 DCLM，并便于研究缩放趋势，我们设置了计算量跨度达三个数量级的不同竞赛规模，见表1。每个规模，即400M-1x、1B-1x、3B-1x、7B-1x、7B-2x，都指定模型参数量，例如7B，以及一个 Chinchilla 倍数，例如1x。每档训练 token 数等于：

$$
D=20\times N\times m,
$$

其中 $N$ 为参数量，$m$ 为 Chinchilla 倍数。因此1x对应 Hoffmann 等人[79]认为接近最优的计算分配。

### §3.3 基准赛道：过滤与混合

选择规模后，参与者从两个赛道中选一个。（i）在**过滤赛道**中，参与者提出算法，从候选池中选择训练数据。我们提供五个起始数据池，对应表1的五档规模，都是 DCLM-POOL 的随机文档子集。我们根据规模限制初始池大小，以鼓励可扩展的过滤策略，也反映实际下载与存储约束。（ii）在**混合赛道**中，一项提交可以把 DCLM-POOL 中的文档与任意外部来源，即 Common Crawl 以外的来源，组合起来。例如，可以直接从 StackExchange 和 Wikipedia 数据转储中整理文档，如 RPJ[168]的做法，也可以使用自行爬取的数据。原附录C给出更详细的赛道规则，原附录D介绍用于执行过滤和混合操作的可扩展开源工具。

### §3.4 训练

为了隔离数据集干预的影响，我们在每个规模固定一套训练配方。根据此前对模型架构与训练的消融研究[4,31,39,62,79,93,134,169,170,183]，我们采用 decoder-only Transformer，例如 GPT-2、Llama[134,169,173]，以 OpenLM[76]实现。我们还提供统一的数据处理工具。其他训练细节见原附录F。

### §3.5 评测

完整评测套件基于 LLM-Foundry[115]，包含53个适合基础模型评测，即不经过微调的下游任务：从问答到开放式生成格式，涉及数学、教科书知识、常识推理等不同领域。为了评估数据整理算法，我们重点关注三个主要性能指标。

第一，**MMLU 5-shot准确率**[78]，它被广泛用于比较 GPT-4[122]、Llama 3 70B[4]等先进模型。第二，提出 **CORE 中心化准确率**：在22个任务的子集上计算，包括 HellaSwag[195]和 ARC-E[43]等；这些任务即使在小规模上，也能提供低方差信号。每项任务的准确率被线性缩放，使0对应随机猜测，1对应完全正确。最后，报告 **EXTENDED 中心化准确率**，即全部53个任务的中心化性能的平均值。指标细节见原附录G。

> **编者解释与原创算例。** CORE不是“53项中的额外22项”，而是53项中的22项子集；EXTENDED包含全部53项。若某任务随机准确率为 $b$，观察准确率为 $a$，上述线性映射可写为 $(a-b)/(1-b)$。四选一任务若 $b=0.25$、$a=0.55$，中心化值为0.40，而不是0.55或0.30。先在各任务上归一化再取平均，不等于混合所有题目直接算准确率。负值也可能出现，表示低于随机基线。

### §4.1 评估已有训练数据集

我们先在表2中评估几个知名开源数据集：C4[52,137]、RefinedWeb[128]、RedPajama[168]和 Dolma-V1[157]。虽然四者都使用各种启发式过滤器与数据清理步骤，但在7B-1x规模上，RefinedWeb 在 CORE 和 EXTENDED 上表现最好。它使用的流水线是：从 Common Crawl 提取文本，应用启发式选择规则，例如去除垃圾内容，再对重复内容去重。

有趣的是，RefinedWeb 完全通过过滤 Common Crawl 构成；RedPajama 和 Dolma-V1 则额外混入 Wikipedia 等经过整理的“高质量”来源。这个比较说明了过滤的相对优势，我们将在后续实验中继续研究。

**原文结论框译文。** 对 DCLM-BASELINE 和其他实验，我们采用 RefinedWeb 的启发式过滤器。

**原表2及表注译文：与已有数据集比较，7B-1x规模。** 虽然不像 Dolma-V1和 RedPajama 那样混入高质量来源，RefinedWeb 仍表现最好。

| --- | ---: | ---: |
| C4 | 34.2 | 18.0 |
| Dolma-V1 | 35.0 | 18.4 |
| RedPajama | 35.3 | 18.2 |

### §4.2 文本提取

文本提取是关键的早期处理步骤，用来从原始 HTML 中取出内容。为了理解它的影响，我们比较三种方法：resiliparse、RefinedWeb 使用的 trafilatura，以及 Common Crawl 提供的、含预提取文本的 WET 文件。然后对每种提取结果应用 RefinedWeb 的启发式质量过滤器。表3中，resiliparse 与 trafilatura 相对 WET 提取都使 CORE 至少提高2.5分。这一点很重要，因为 C4、RedPajama、Dolma-V1等大多数开源数据集使用 WET 文件，这可能部分解释了它们在表2中的较差表现。

虽然 resiliparse 和 trafilatura 的下游性能相近，但 resiliparse 运行速度快8倍，因此更适合大规模处理。更多分析见原附录K。

**原文结论框译文。** DCLM-POOL 及其余实验使用 resiliparse 提取文本。

**原表3及表注译文：文本提取器比较，1B-1x规模。** 使用三种方法从 HTML 提取文本，随后用 RefinedWeb 启发式过滤器处理输出，再评估所得数据训练的模型。resiliparse、trafilatura 等更严格的提取器优于 Common Crawl 提供的 WET 文件。

| 提取方式 | CORE | EXTENDED |
| --- | ---: | ---: |
| resiliparse | 24.1 | **13.4** |
| trafilatura | **24.5** | 12.5 |
| WET文件 | 20.7 | 12.2 |

> **编者校读。** 正文“至少2.5分”是原文的保守描述；表3实际差值分别为3.4与3.8。提取器运行速度来自论文条件，不是“训练语言模型快8倍”。

### §4.3 去重

网页爬取数据往往包含大量重复或近重复字符串。去重一方面通过降低记忆来改善性能[35,94]，另一方面增加数据多样性。我们研究了 MinHash[29]，将其作为后缀数组流水线[94,128]的一部分；也研究了近重复 Bloom filtering，它是对一种精确文档与段落去重方案[157]的修改。两种方法下游表现相近：7B-2x规模上的 CORE 相差不超过0.2个百分点。然而，我们修改后的 Bloom filter 更容易扩展到超过10TB的数据集。其他分析见原附录L。

**原文结论框译文。** DCLM-BASELINE 使用 Bloom filter，其他实验使用 MinHash。

### §4.4 基于模型的质量过滤

近期文献[28,59,157]表明，训练模型充当质量过滤器可以改善下游表现。本节研究不同的模型过滤方式。

**比较模型过滤方法。** 我们比较了多种策略：（1）PageRank得分过滤，根据文档被其他文档链接到的可能性保留文档；（2）语义去重 SemDedup，移除信息内容相似的文档[1]；（3）在预训练 BGE 文本 embedding[185]上拟合线性分类器；（4）AskLLM，通过提示语言模型判断文档是否有帮助[146]；（5）困惑度过滤，遵循 CCNet[178]，保留低困惑度序列；（6）top-k平均 logits，对文档所有词位置的前k个模型 logits 取平均，以衡量模型对“正确词处于k个合理候选之中”的信心；（7）fastText[87]二分类器，区分数据质量。

训练分类器时，我们使用约400,000篇文档，正负类别各占一半。我们尝试不同的正例数据，负例固定为从某个版本的 RefinedWeb 复现数据中随机抽样得到的文档。对于困惑度过滤和 top-k平均 logits，我们使用154M参数的因果 Transformer，在英语 Wikipedia、RedPajama-v1的书籍子集以及 peS2o 的混合数据上训练[156,168]，实现细节见原附录J。表4比较了这些方法，fastText 过滤优于其他方法。接下来，我们希望理解不同 fastText 训练配方如何影响其作为数据过滤网络的有效性[59]。

**原表4及表注译文：质量过滤比较，1B-1x规模。** 评估不同模型质量过滤器；训练 fastText 分类器进行过滤表现最好。

| 过滤器 | CORE | EXTENDED |
| --- | ---: | ---: |
| RefinedWeb复现基线 | 27.5 | 14.6 |

| SemDedup[1] | 27.1 | 13.8 |

| AskLLM[146] | 28.6 | 14.3 |

### §4.5 数据集混合

人们经常把 Common Crawl，简称CC，与 Wikipedia、StackExchange和 peS2o[156]等被认为高质量的其他来源组合[63,70,168,170]。由于 DCLM 混合赛道允许额外来源，我们研究了向只来自 Common Crawl 的训练集加入高质量来源的潜在收益。我们比较：使用100%过滤后CC数据训练的模型，以及采用 Llama 1和 RedPajama 混合比例训练的模型；后者为67% CC，剩余33%来自 Wikipedia、Books、StackExchange、arXiv和 GitHub。

对于CC部分，我们考虑 DCLM-BASELINE 的一个子集、RedPajama的CC部分、RefinedWeb、C4。表6显示，对表现较弱的CC子集，即C4、RedPajama-CC、RefinedWeb，混合可以改善性能。但对 DCLM-BASELINE，混合平均而言反而损害性能，说明当过滤已很有效时，混入这些来源可能适得其反。更多混合结果见原附录M。

### §4.6 去污染

本节检查，评测数据混入预训练数据是否影响 DCLM-BASELINE 的结果。我们选择 MMLU 和 HellaSwag，因为它们是7B规模语言模型的常用性能指标。

具体而言，我们尝试移除这两个测试集中存在于 DCLM-BASELINE 的样例。对两项任务，都先标记同时包含某个样例的题目文本和至少一个对应答案选项的页面。对于被标记页面，移除所有匹配到的题目及选项字符串。MMLU 含有基于长篇段落的问题，为提高召回，我们只检测每个题目的最后一句，以降低因格式差异而漏检的概率。人工检查发现，这仍然会产生许多误报。

然后，使用移除了这些已检出重叠的 DCLM-BASELINE，训练一个7B-2x模型。如表7所示，模型性能没有降低，因此，在这两个任务上的性能收益不太可能是由于数据集中存在更多测试样例造成的。

**原表7及表注译文：MMLU与HellaSwag重叠移除，7B-2x规模。** 当检测到问题及它的某个选项时，移除与这两个基准匹配的重叠。比较去污染前后训练的模型，性能没有下降。$E$表示相应评测集。

| --- | ---: | ---: |
| DCLM-BASELINE | 51.8 | 77.9 |

> **编者边界。** “没有观察到降分”支持作者对这两个任务、这套检测规则的有限判断，不等于证明240T池或全部53项评测均无污染。原文删除的是匹配的**字符串**，不是统一删除整篇网页；MMLU只检测题目最后一句以提高召回，会引入误报。答案选项不要求是正确答案。更深的模板改写、语义近似或间接泄漏不由这项字符串实验自动排除。

### 附录C 基准规则

本节给出 DCLM 两个赛道的详细提交指南。

#### C.1 通用规则

以下要求同时适用于过滤和混合赛道。

1. 提交应包含文档，详细说明其关键组成部分。
2. 排行榜提交所使用的数据集，或者能够完整复现该数据集的可工作代码，应当免费公开，以鼓励提交的可复现性。不满足这一要求的提交仍可能被接受，但会在排行榜上明确标记。
3. 必须使用我们提供的脚本进行 tokenization；该脚本同时执行全局随机打乱。
4. 提交不得对训练或评测代码做任何更改。
5. 禁止将评测数据，即本评测任务的测试数据，用于评测和去污染以外的目的。

#### C.2 过滤赛道

过滤赛道提交的定义性特征是：只对所选计算规模对应的 DCLM-POOL 子集应用处理流水线，形成数据集，不纳入任何外部数据，参见表1。理由有两点。第一，过滤所用初始数据的大小和质量，会影响处理成本以及最终数据集质量。固定初始数据集可以使比较条件公平，让比较聚焦于核心整理技术。第二，我们希望鼓励可能在前沿模型规模上仍然适用的方法。假如用约16T token的7B-2x池，服务于只需要约8B训练 token的400M-1x规模，就会允许只保留不到0.1%数据的过滤策略；这样的策略无法扩展到生成万亿 token的数据集。

为了鼓励有创造性且表现良好的提交，只使用 DCLM-POOL 的要求带有以下限定说明。

1. **修改 HTML 提取。** 我们用 resiliparse 从 Common Crawl 归档提取文本，构成 DCLM-POOL，以降低没有资源自行提取文本的参与者的计算负担。不过，我们也指定了各个池对应的 Common Crawl 归档，允许研究文本提取。参与者可以从已解析的 DCLM-POOL 开始，也可以直接处理对应的 Common Crawl WARC 归档。
2. **使用在外部数据上训练的模型。** DCLM-POOL 处理流水线可以利用模型进行质量过滤、改写等操作。模型允许在外部数据上训练，但按照通用规则，不得使用评测数据。我们不接受滥用此例外、通过后门引入外部数据的提交；例如把 DCLM-POOL 文档“改写”为模型记忆中的外部数据。

#### C.3 混合赛道

混合赛道可以使用任意数据来源，只要符合通用指南：可以免费获取，并且不包含评测数据。提交应清楚记录各数据来源、赋予各来源的权重，以及训练所用 token 数量与整体自定义池大小之比；每个基准规模的训练 token 数量是固定的。

> **编者教学边界。** 这些是论文基准的规则，不是允许自动生成 CS336 作业实现的授权。外部训练的过滤模型可以被允许，不等于可以把评测题目作为正例训练过滤器，也不等于可以靠“改写”灌入模型记住的外部文本。DCLM 与 A4 都需要固定比较协议，但两者的数据版本、tokenizer、训练配方和执行权限不能互换。

以下为本课程编者解释，不属于两篇论文译文。

| 问题 | FineWeb v2 | DCLM v4 |
| --- | --- | --- |
| 比较的控制条件 | 1.71B架构固定；同实验相同token；两组子集/初始化取平均 | 五档固定训练预算；禁止修改训练与评测代码 |

| 评测警戒线 | domain-fit明确未去污染 | 池不预先去污染；另提供工具、报告要求与两任务实验 |

**自测1：** 同样保留10%的文档，是否意味着训练 token 数也相同？

**答案：** 不意味着。文档长度分布可能改变，且两个10%可能来自不同的前置池。必须另报 token 数、tokenizer、前置步骤和实际训练 token 预算。

**自测2：** FineWeb 的一个文档簇有A—C和B—C两条碰撞边，能否推出A—B的 Jaccard 至少0.75？

**答案：** 不能。碰撞本身是概率事件，且图连通性只提供传递连接，不提供所有点对的相似度下界。

**自测3：** 既然 DCLM 的某个混合实验降分，是否应总是删除 Wikipedia？

**答案：** 不能。实验比较的是特定来源组合、配比、基线和固定预算下的替换效果，并没有穷尽所有混合权重和任务目标。

**自测4：** 能否把 FineWeb-Edu 的领域困惑度优势或 DCLM 的去污染后升分称为“证明无污染”？

**答案：** 都不能。前者主动省略去污染；后者只反映特定匹配规则和两项任务的干预结果。未检出、未降分与不存在污染是不同命题。
