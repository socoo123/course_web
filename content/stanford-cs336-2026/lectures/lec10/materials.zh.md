# PagedAttention：把 KV 状态的逻辑顺序与物理位置分开

一个注意力 kernel 可以稍慢，整个服务系统却能显著提高吞吐。这篇论文的关键是：**减少 KV cache 预留、碎片与重复副本，使更多请求真正放得进同一个批次**，而不是把注意力换成近似算法。

## §3 大语言模型服务中的内存挑战

虽然细粒度批处理减少了计算浪费，使请求能以更灵活的方式组成批次，但可以同时组成批次的请求数量仍受 GPU 显存容量限制，尤其受用于保存 KV cache 的空间限制。换言之，服务系统的吞吐受到内存约束。要突破这一约束，内存管理必须解决以下挑战。

**庞大的 KV cache。** KV cache 的大小随着请求数量迅速增长。例如，对130亿参数的 OPT 模型，一个 token 的 KV cache 需要800 KB，其计算为：2（key与value向量）×5120（隐藏状态大小）×40（层数）×2（FP16字节数）。由于 OPT 能生成最长2048 token 的序列，一个请求的 KV cache 最多可占1.6 GB。同期 GPU 的显存容量为数十 GB；即便把所有可用显存都分给 KV cache，也只能容纳几十个请求。内存管理效率低下还会进一步减小 batch size，见原图2。此外，按当时的发展趋势，GPU 计算速度的增长快于内存容量的增长。例如，从 NVIDIA A100 到 H100，FLOPS 增加超过2倍，但最大显存容量仍为80 GB。因此，我们认为内存会成为越来越显著的瓶颈。

**复杂的解码算法。** LLM 服务提供多种解码算法供用户选择，不同算法对内存管理复杂度有不同影响。例如，用户可能希望从一个输入 prompt 得到多个随机样本；这在程序建议中很常见。prompt 部分的 KV cache 在我们的实验（§6.3）中占总 KV cache 内存的12%，可以共享以减少内存用量。另一方面，自回归生成阶段的 KV cache 应保持不共享，因为各样本结果不同，并且依赖上下文与位置。KV cache 可共享的程度取决于所用解码算法。在 beam search 等更复杂算法中，不同 beam 可以共享更大部分的 KV cache，内存节省最高达55%（见§6.3），并且共享模式会随解码过程演化。

**对未知输入和输出长度的调度。** LLM 服务请求的输入、输出长度各不相同，内存管理系统因而必须适应各种 prompt 长度。而且，当请求的输出在解码过程中变长时，其 KV cache 所需的内存也随之增长，可能耗尽接纳新请求或继续现有生成所需的可用内存。系统必须做出调度决定，例如删除某些请求的 KV cache，或者把它们换出 GPU 显存。

> **编者注：容量与带宽是不同约束。** 本节讨论可容纳请求数时，重点是显存容量；单请求 decode 读权重/读KV慢，还涉及带宽。论文“当时的GPU”判断不应改写成2026年全部硬件的现状。上面的乘积精确为819,200 bytes，即800 KiB；2048 token 为1.5625 GiB。原文采用约800 KB/1.6 GB的写法，本译文保留原数字并在此澄清单位。

### §3.1 现有系统的内存管理

由于当时深度学习框架中的大多数算子要求张量存放于连续内存，已有 LLM 服务系统也把一个请求各位置的 KV cache 存成连续张量。LLM 的输出长度不可预测，因此它们按请求可能达到的最大序列长度静态分配一整块内存，而不考虑实际输入长度或最终输出长度。

原图3展示了两个请求：请求A可能达到的最大序列长度为2048，请求B为512。这种预分配连续大块的方案有三种主要浪费来源：为未来 token 预留的槽位；按可能达到的最大序列长度过量分配造成的内部碎片；以及 buddy allocator 等内存分配器产生的外部碎片。外部碎片永远不会用来存储生成的 token，这在服务请求之前便已知道。内部碎片也不会被使用，但只有在请求采样结束后才能确定。两者都是纯粹的内存浪费。预留内存虽然最终会被使用，却在请求的整个生命周期中一直被占住；尤其当预留空间很大时，它会挤占本可用于处理其他请求的空间。原图2展示了我们实验中的平均浪费比例：以前系统的实际有效内存利用率可能低至20.4%。

尽管内存压缩整理（compaction）曾被提出作为碎片问题的潜在解法，但 KV cache 规模很大，在性能敏感的 LLM 服务系统中执行整理并不现实。即使做了整理，已有内存管理系统为每个请求预分配的大块空间，仍然妨碍利用解码算法特有的内存共享机会。

**原图3图注译文**：现有系统中的 KV cache 内存管理。存在预留、内部碎片和外部碎片三种内存浪费，妨碍其他请求装入内存。每个内存槽中的 token 表示它的 KV cache。注意：同一个 token 处于不同位置时，KV cache 也可能不同。

## §4.1 PagedAttention

为解决§3中的内存挑战，我们提出 PagedAttention：一种受到操作系统经典分页思想启发的注意力算法。与传统注意力算法不同，PagedAttention 允许把逻辑上连续的 key 和 value 存在物理上不连续的内存空间。具体地，PagedAttention 将每个序列的 KV cache 分为 KV blocks；每个块包含固定数量 token 的 key 和 value 向量，这个数量称为 KV block size，记为 $B$。

**原脚注1译文**：在 Transformer 中，每个 token 都有跨层、跨层内注意力头的一组 key/value 向量。可以把所有 key/value 向量放在一个 KV block 中统一管理；也可以让不同头、不同层的 key/value 各有独立块，并用不同块表管理。两种设计没有性能差异，我们为便于实现选择第二种。

记第 $j$ 个 key 块与 value 块分别为：

$$
\begin{aligned}
K_j&=(k_{(j-1)B+1},\ldots,k_{jB}),\\
V_j&=(v_{(j-1)B+1},\ldots,v_{jB}).
\end{aligned}
$$

注意力计算可以改写为分块形式。$A_{ij}$ 是第 $j$ 个 KV 块上注意力权重的行向量：

$$
A_{ij}=(a_{i,(j-1)B+1},\ldots,a_{i,jB}).
$$

> **式(4)校读说明——不静默修正原版。** v1 p.5 的分母印为对各块的 $\exp(q_i^\top K_t\mathbf1/\sqrt d)$ 求和，即把块内求和放进了指数；这一般不等于 softmax 的归一化分母。我们已对照原PDF p.3式(3)，以下用其一致的数学含义重排式(4)：先对每个位置取指数，再把所有有效位置相加。原文引导句也误指“Eq.4”，这里按其意指的常规注意力计算理解。此处为明确标记的编者数学校正，不是声称原版无误。

$$
\begin{aligned}
s_{ij}&=q_i^\top K_j/\sqrt d,\\
Z_i&=\sum_{t=1}^{\lceil i/B\rceil}
       \exp(s_{it})\mathbf1,\\
A_{ij}&=\exp(s_{ij})/Z_i,\\
o_i&=\sum_{j=1}^{\lceil i/B\rceil}V_jA_{ij}^{\top}.
\end{aligned}
$$

这里指数逐元素计算，$\mathbf1$ 用于块内求和；最后一块未填充位置与因果上不可见位置不参与归一化，等价于把对应 score 设为 $-\infty$。以上补全的 mask 说明也是编者注。

在注意力计算期间，PagedAttention kernel 分别定位并读取各个 KV block。原图5给出一个例子：key/value 分散在三个块中，这三个块在物理内存中并不连续。每次，kernel 将查询 token “forth”的查询向量 $q_i$ 与一个块中的 key 向量 $K_j$ 相乘，例如块0对应 “Four score and seven”，计算注意力权重 $A_{ij}$；之后再将 $A_{ij}$ 与该块中的 value 向量 $V_j$ 相乘，得到最终注意力输出 $o_i$。

总之，PagedAttention 允许 KV block 存在不连续的物理内存里，从而使 vLLM 能进行更灵活的分页内存管理。

## §4.2 KV Cache 管理器

vLLM 内存管理器的核心思想类似于操作系统的虚拟内存。操作系统把内存划分为固定大小的页，并把用户程序的逻辑页映射到物理页。连续的逻辑页可以对应不连续的物理内存页，让用户程序像访问连续内存一样进行访问。而且，物理内存空间无需提前全部预留，操作系统可以按需动态分配物理页。vLLM 使用虚拟内存背后的思想管理 LLM 服务中的 KV cache。在 PagedAttention 的支持下，我们把 KV cache 组织成固定大小的 KV blocks，就像虚拟内存中的页。

一个请求的 KV cache 表示为一系列逻辑 KV blocks；随着新 token 及其 KV cache 生成，这些块从左向右填充。最后一个 KV block 尚未填充的位置预留给未来生成。GPU worker 上的 block engine 分配一片连续的 GPU DRAM，并把它划分成物理 KV blocks。CPU RAM 也这样组织，以支持交换，见§4.5。KV block 管理器还维护每个请求的块表，记录逻辑与物理 KV blocks 的映射。每个块表项记录一个逻辑块对应的物理块，以及已填充位置的数量。分离逻辑和物理 KV blocks，使 vLLM 能动态扩展 KV cache 内存，而不必提前为全部位置预留空间，从而消除现有系统中的大部分内存浪费，见原图2。

**原图6图注译文**：vLLM中的块表地址转换。

## §4.3 使用 PagedAttention 与 vLLM 解码

接下来沿原图6的例子，说明 vLLM 在单个输入序列的解码中如何执行 PagedAttention 并管理内存。

1. 与操作系统虚拟内存一样，vLLM 无需一开始就为可能生成的最大序列长度预留内存，只预留容纳 prompt 计算所产生 KV cache 必需的块。在这个例子里，prompt 有7个 token，所以 vLLM 把前两个逻辑块0、1分别映射到物理块7、1。在 prefill 步，vLLM 用常规 self-attention 算法，例如原文引用的 FlashAttention，生成 prompt 的 KV cache 和第一个输出 token。然后，前4个 token 的 KV cache 存入逻辑块0，后3个存入逻辑块1；剩下的1个槽位预留给后续自回归生成。
2. 在第一次自回归解码步，vLLM 对物理块7和1执行 PagedAttention，生成新 token。由于最后一个逻辑块还剩一个槽位，新产生的 KV cache 存在这里，同时更新块表中的已填充数量。
3. 在第二次解码步，最后一个逻辑块已经填满，vLLM 把新产生的 KV cache 存入新逻辑块；为它分配一个新物理块3，并将映射存入块表。

从全局看，每次解码迭代，vLLM 首先选择一组候选序列组成 batch，详见§4.5，并为新需要的逻辑块分配物理块。然后，把当前迭代的所有输入 token 拼接成一个序列送入 LLM：prompt 阶段请求送入所有 prompt token，generation 阶段请求送入最新的 token。LLM 计算过程中，vLLM 用 PagedAttention kernel 访问以逻辑 KV blocks 形式存储的历史 KV cache，并把新产生的 KV cache 保存到物理 KV blocks。

一个 KV block 存储多个 token，即块大小大于1，可以让 PagedAttention kernel 并行处理更多位置的 KV cache，从而提高硬件利用率、降低延迟。但更大的块也会增加内存碎片；§7.2研究块大小的影响。

随着更多 token 及其 KV cache 生成，vLLM 动态地给逻辑块分配新的物理块。由于所有块从左向右填充，并且只有前面的块都填满才分配新物理块，vLLM 将一个请求的所有这类内存浪费限制在一个块内，因此可以有效利用全部内存，如原图2所示。这样便能让更多请求装入内存组成 batch，提高吞吐。请求生成结束后，其 KV blocks 可以被释放，用于存储其他请求的 KV cache。

原图7展示 vLLM 同时为两个序列管理内存的例子。两个序列的逻辑块映射到 GPU workers 上 block engine 所预留空间中的不同物理块。两个序列各自相邻的逻辑块，在物理 GPU 内存中都不必连续；物理块空间因此可以被两个序列有效利用。

**原图7图注译文**：在 vLLM 中同时存储两个请求的 KV cache。

## §4.4 其他解码场景的应用

§4.3展示 PagedAttention 与 vLLM 如何处理贪心解码和采样等基本算法：输入一个用户 prompt，生成一个输出序列。但在很多成功的 LLM 应用中，服务必须支持更复杂的解码场景；它们具有复杂的访问模式，也提供更多内存共享机会。本节展示 vLLM 对这些场景的普适性。

### 并行采样

在基于 LLM 的程序助手中，模型针对一个输入 prompt 生成多个采样输出，用户可以从候选中选择喜欢的结果。此前我们隐含假定一个请求只生成一个序列；在论文余下部分，我们采用更一般的情形，即一个请求生成多个序列。在并行采样中，一个请求的多个样本共享同一个输入 prompt，因此也能共享 prompt 的 KV cache。借助 PagedAttention 与分页内存管理，vLLM 可以很容易地实现这种共享，节省内存。

原图8给出两个输出的并行解码例子。由于两个输出共享同一个 prompt，prompt 阶段只需为一份 prompt 状态预留空间；两个序列的 prompt 逻辑块映射到相同物理块：两者的逻辑块0和1分别映射到物理块7和1。一个物理块可以被多个逻辑块映射，因此我们给每个物理块引入引用计数。在本例中，物理块7与1的引用计数均为2。

进入生成阶段后，两个输出采样到不同 token，需要各自存放 KV cache。对于需要由多个序列修改的物理块，vLLM 实现块粒度的写时复制（copy-on-write），类似操作系统虚拟内存中的写时复制，例如进程 fork。具体地，在原图8中，当样本A1需要写入最后一个逻辑块1时，vLLM 发现对应物理块1的引用计数大于1，便分配一个新物理块3，通知 block engine 从物理块1复制已有信息，并把原物理块1的引用计数减至1。之后，样本A2写入物理块1时，引用计数已经为1，因此A2直接把新生成的 KV cache 写入物理块1。

总之，vLLM 使多个输出样本可以共享存储 prompt KV cache 的大部分空间，只有最后一个逻辑块需要由写时复制机制处理。在多个样本间共享物理块可以大幅减少内存使用，输入 prompt 很长时尤其如此。

### Beam search

在机器翻译等 LLM 任务中，用户希望模型给出最合适的前 $k$ 个翻译。Beam search 广泛用于解码模型认为最可能的输出序列，因为它缓解了完整遍历样本空间的计算复杂度。算法依赖 beam width 参数 $k$，它决定每一步保留多少个最佳候选。解码时，beam search 对 beam 中每个候选序列考虑所有可能的 token，用 LLM 计算各自概率，并从 $k\cdot|V|$ 个候选中保留概率最高的 $k$ 个序列；$|V|$ 为词表大小。

与并行解码不同，beam search 不仅能共享起始 prompt 块，还能在不同候选之间共享其他块，且共享模式随着解码推进不断变化，类似操作系统多次 fork 形成的进程树。原图9展示 beam width 为4时 vLLM 如何管理 KV blocks。图中虚线所示迭代之前，每个候选已使用4个填满的逻辑块。所有候选共享第一个块0，即 prompt；候选3从第二块起与其他候选分叉；候选0–2共享前三个块，在第四块分叉。

接下来，概率最高的4个候选全部来自之前的候选1和2。由于原候选0和3不再属于最佳候选，它们的逻辑块被释放，对应物理块引用计数下降。vLLM 释放所有引用计数降至0的物理块，即块2、4、5、8；然后分配新的物理块9–12，以保存新候选的新 KV cache。此时，全部候选共享块0、1、3；候选0和1还共享块6，候选2和3还共享块7。

此前的 LLM 服务系统需要频繁在 beam 候选间复制 KV cache。例如在原图9的虚线之后，候选3若要继续生成，就需要复制原候选2的很大一部分 KV cache。vLLM 通过共享物理块显著减少了这种频繁复制的开销。在 vLLM 中，不同 beam 候选的大部分块都可以共享；只有新生成 token 落入旧的共享块时，才像并行解码一样进行写时复制。这只涉及复制一个块的数据。

### 共享前缀

通常，LLM 用户会提供一段较长的任务描述，包括指令和输入/输出示例，也称为 system prompt。任务描述与实际任务输入拼接，构成请求的 prompt；LLM 根据整个 prompt 生成输出。原图10给出一个例子。此外，还可以通过 prompt engineering 进一步调整共享前缀，提高下游任务准确率。

对于此类应用，许多用户 prompt 共享一个前缀。因此，服务提供者可以事先存储前缀的 KV cache，减少在前缀上重复的计算。在 vLLM 中，只需为服务提供者预先定义的一组共享前缀保留一组物理块，就能方便实现这一点，类似操作系统在不同进程间处理共享库。带有该共享前缀的用户输入 prompt 可以直接把逻辑块映射到已缓存的物理块，最后一个块标记为写时复制。prompt 阶段便只需计算用户的任务输入部分。

### 混合解码方式

前述解码方式表现出不同的内存共享和访问模式。但 vLLM 能同时处理具有不同解码偏好的请求，而已有系统无法高效做到这一点。原因在于，vLLM 通过一个把逻辑块转换为物理块的共同映射层，隐藏不同序列之间复杂的内存共享关系。LLM 及其执行 kernel 只看到每个序列的一串物理块ID，无需处理序列之间的共享模式。与已有系统相比，这种方式增加了对不同采样需求请求进行批处理的机会，最终提高系统总体吞吐。

## §4.5 调度与抢占

当请求流量超过系统容量时，vLLM 必须优先处理一部分请求。在 vLLM 中，我们对所有请求采用先来先服务（FCFS）策略，以确保公平并防止饥饿。需要抢占请求时，vLLM 保证最早到达的请求先得到服务，最新到达的请求最先被抢占。

LLM 服务面临一个特殊挑战：输入 prompt 长度差异很大，而输出长度事先未知，取决于输入 prompt 和模型。随着请求数量及输出增长，vLLM 可能耗尽用于存储新 KV cache 的 GPU 物理块。此时，vLLM 要回答两个经典问题：第一，应驱逐哪些块？第二，如果以后还需要这些块，应如何恢复？

通常，驱逐策略会用启发式方法预测哪个块最晚才会再次访问，并驱逐它。但在我们的场景中，已知一个序列的所有块会一起被访问，所以采用全有或全无的驱逐策略：要么驱逐一个序列的全部块，要么一个也不驱逐。另外，同一请求中的多个序列，例如一个 beam search 请求的多个候选，作为一个序列组进行成组调度（gang scheduling）。由于这些序列可能共享内存，同一组中的序列始终一起被抢占或重新调度。对于如何恢复被驱逐块的第二个问题，我们考虑两种技术。

**交换（swapping）。** 这是多数虚拟内存实现采用的经典技术：把被驱逐的页复制到磁盘上的交换空间。在我们的场景中，被驱逐的块复制到 CPU 内存。如原图4所示，除了 GPU block allocator，vLLM 还包括 CPU block allocator，用于管理交换到 CPU RAM 的物理块。

当没有空闲物理块可供新 token 使用时，vLLM 选择一组序列驱逐，并把它们的 KV cache 传到 CPU。一旦抢占序列并驱逐其块，vLLM 就停止接纳新请求，直到所有被抢占的序列完成。某个请求完成后，它的块会被释放；被抢占序列的块便可以换回，继续处理。注意，在这个设计下，交换到 CPU RAM 的块数不会超过 GPU RAM 中的物理块总数，因此 CPU RAM 中的交换空间上界是 GPU 上分配给 KV cache 的内存大小。

**重计算（recomputation）。** 这种方式在被抢占序列重新得到调度时，直接重算它的 KV cache。注意，重计算的延迟可能显著低于最初生成这些内容的延迟，因为可以把解码阶段已经生成的 token 与原用户 prompt 拼成一个新 prompt；所有位置的 KV cache 都可在一次 prompt 阶段迭代中生成。

交换和重计算的性能，取决于 CPU RAM 与 GPU 显存之间的带宽以及 GPU 的计算能力。论文§7.3进一步比较两者的速度。

> **编者注**：以上是固定v1的调度描述，不是对任意版本vLLM的现行行为保证。重算已知 token 的 KV 不等于重新随机采样文本；“全有或全无”也不是把任意一个物理页当作独立调度请求。

**工作负载。** 我们基于 ShareGPT 和 Alpaca 数据集合成工作负载；其中包含真实 LLM 服务的输入与输出文本。ShareGPT 收集了用户分享的 ChatGPT 对话。Alpaca 是采用 self-instruct 方式、由 GPT-3.5 生成的指令数据集。我们对数据集进行 tokenization，使用其输入与输出长度合成客户端请求。如原图11所示，ShareGPT 的平均输入 prompt 长度为 Alpaca 的8.4倍，平均输出长度为5.8倍，方差也更大。由于这些数据集没有时间戳，我们以不同请求率的泊松过程生成请求到达时间。

**原图11图注译文与必要读图值**：ShareGPT与Alpaca数据集的输入、输出长度分布。图中标出的均值分别为：ShareGPT输入161.31、输出337.99 token；Alpaca输入19.31、输出58.45 token。

**基线一：FasterTransformer。** FasterTransformer 是为降低延迟而高度优化的分布式推理引擎。由于它本身没有调度器，我们实现了自定义调度器，使用类似 Triton 等现有服务系统的动态批处理机制。具体地，根据 GPU 显存容量，为每项实验把最大 batch size $B$ 设得尽可能大。调度器取至多 $B$ 个最早到达的请求，将整个 batch 发给 FasterTransformer 处理。

**基线二：Orca。** Orca 是当时面向吞吐优化的先进 LLM 服务系统。由于 Orca 不能公开获取使用，我们自行实现了一个版本。我们假设 Orca 用 buddy allocation 算法确定 KV cache 存放的内存地址，并按为请求输出过量预留的程度，实现三个版本：

- **Orca（Oracle）**：假设系统预先知道请求最终实际生成的输出长度。这展示了 Orca 的性能上界，在实践中不可实现。
- **Orca（Pow2）**：假设为输出过量预留的空间至多是实际长度的2倍。例如实际输出25个 token，就为输出预留32个位置。
- **Orca（Max）**：假设系统始终预留到模型的最大序列长度，即2048 token。

**关键指标。** 我们关注服务吞吐。具体地，对具有不同请求率的工作负载测量系统的归一化延迟，沿用 Orca 的定义：先将每个请求的端到端延迟除以该请求的输出长度，再对所有请求取平均。高吞吐服务系统应该在较高请求率下仍保持低归一化延迟。多数实验采用1小时的 trace；OPT-175B 因成本限制，例外地采用15分钟 trace。

> **编者注：比较对象与指标不可偷换。** 这里的 Orca 是本论文作者重实现并附带上述分配/预知假设的基线，不是原 Orca 作者公开系统的直接实测；Pow2也是有利的长度预留假设，不是已经提供了一种可部署的预测器。设请求 $r$ 的端到端时间为 $T_r$、输出长度为 $O_r$，指标是：
>
> $$
> \overline t_{\rm norm}
> =\frac1R\sum_{r=1}^{R}\frac{T_r}{O_r}.
> $$
>
> 它不是 $\sum_rT_r/\sum_rO_r$，不是TTFT，也不是去除排队/prefill后的TPOT，更不是P95/P99尾延迟。横轴是输入请求率；队列稳定时才能把可维持的请求率理解为服务吞吐能力，不能把过载时的到达率直接当完成吞吐。图中“相近延迟”的倍数也不是所有负载下单请求生成速度的倍数。

## §6.2 基础采样

我们在三种模型、两个数据集上评估 vLLM 的基础采样性能，即每个请求采样一个输出。原图12第一行给出 ShareGPT 上的结果。曲线表明：请求率提高时，延迟最初缓慢增加，随后突然爆发。这是因为，当请求率超过系统容量，队列长度会不断增长，因而请求延迟也不断增长。

## §7.1 Kernel 微基准

PagedAttention 中动态的块映射，会影响涉及已存 KV cache 的 GPU 操作性能，即块读写和 attention。与已有系统相比，我们的 GPU kernels（原§5）多出访问块表、执行额外分支和处理变长序列的开销。如原图18a所示，相比高度优化的 FasterTransformer 实现，这使 attention kernel 延迟高20%–26%。

我们认为这一开销较小，因为它只影响 attention 算子，不影响模型中 Linear 等其他算子。尽管存在该开销，PagedAttention 仍让 vLLM 在端到端性能上显著优于 FasterTransformer，见§6。

## §7.2 块大小的影响

块大小的选择会显著影响 vLLM 性能。如果块太小，vLLM 可能无法充分利用 GPU 并行性来读取和处理 KV cache；如果块太大，内部碎片会增加，共享的可能性会下降。

原图18b使用固定请求率、基础采样的 ShareGPT 与 Alpaca trace，评估不同块大小的 vLLM 性能。在 ShareGPT trace 中，块大小16到128具有最佳性能。在 Alpaca trace 中，16和32表现较好；更大的块会显著损害性能，因为序列可能比块还短。实践中，我们发现块大小16已足够大，能有效利用 GPU，同时又足够小，可在多数工作负载中避免严重内部碎片。因此，vLLM 将默认块大小设为16。

**原图18图注译文**：消融实验。(a) Attention kernels 的延迟；(b) 不同块大小下的端到端延迟。图18a横轴为context length，纵轴为微秒，分别比较batch size 8与32时的vLLM/FasterTransformer；18b横轴为block size，纵轴为归一化延迟（秒/token）。

> **编者注**：16是这篇固定版本、所测硬件与工作负载下的选择，不是所有平台永远最优的页大小。也不能把“kernel慢20%–26%”改写成“全模型慢20%–26%”；反过来，系统吞吐更好也不能声称该kernel本身更快。

## 编者读后检查：三个不变量，比记一个加速倍数更有用

以下为独立教学补充，不属于原论文翻译。

### 1. 分块不能改变 softmax 的归一化范围

无论物理块如何排列，所有有效历史位置必须共享同一个归一化分母。自拟两块各一个位置，score分别为0与 $\log3$，value分别为0与4：全局权重为 $1/4,3/4$，输出为3。如果每块各做一次softmax再把输出相加，就会得到4，计算对象已经改变。

### 2. 共享的是相同前缀状态，不是相同字面 token

同一个词处于不同上下文/位置，其KV一般不同，不能仅凭 token ID 合并。共享尾块写入前必须保证独占，或执行写时复制；释放序列只是减少引用计数，只有计数归零才能回收物理块。以每块4个token为例，两条有6-token共同前缀的分支最初共享2块；分叉写入共享尾块后，完整首块仍共享，尾块各一份，总计3块，而不是4份完整副本。

### 3. 把算子速度、系统吞吐与用户延迟分开

更高显存利用率 → 更多可并行请求 → 权重读取更好摊销，是一种可能的收益链；一旦计算已经饱和，继续增加可容纳请求数不一定增加吞吐。用户还可能关心首token、后续token间隔与长尾等待；本论文的平均归一化延迟不能替它们给出服务承诺。

**自测与答案**：

- **每个请求尾部至多浪费一块，是否系统显存完全无浪费？** 不是。它约束的是这套增量KV分配中的尾块碎片，权重、临时激活、块表、预留池与调度状态仍需空间。
- **知道最终输出长度为何还不够？** 即便Oracle消除长度估计误差，整个未来区间仍可能提前预留，且连续分配仍有外部碎片；分页按需增长解决的是另一个维度。
- **请求数较多但输出长短差异很大，平均秒/token能否说明P99很好？** 不能，均值会掩盖尾部，且按请求归一化与按token加权不是同一个统计量。
