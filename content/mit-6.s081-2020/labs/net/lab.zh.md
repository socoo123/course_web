# 网络：实现 E1000 网卡驱动

这个实验要求你为 xv6 编写一个网络接口卡（NIC）的设备驱动，让内核能够发送和接收网络包。

在已经取得的实验仓库中切换到 `net` 分支：

```sh
$ git fetch
$ git checkout net
$ make clean
```

仓库获取与工具链安装见[公共资料](#/c/mit-6.s081-2020)的「实验环境」「实验代码与 11 个实验」。

## 背景：模拟网卡与网络环境

开始写代码前，可以复习 xv6 教材第 5 章「中断与设备驱动」，中文阅读见[第 9 讲课程资料](#/c/mit-6.s081-2020/lec/lec09?v=materials)。

本实验使用 E1000 网络设备。对 xv6 和你的驱动而言，它看起来像一块连接到真实以太网局域网的硬件。实际上，网卡和局域网都由 QEMU 模拟：

- xv6 是客户机（guest），IP 地址为 `10.0.2.15`。
- 运行 QEMU 的计算机是宿主机（host），在这段模拟网络中表现为 `10.0.2.2`。
- xv6 通过 E1000 向 `10.0.2.2` 发送包时，QEMU 会把包交给宿主机上相应的真实应用程序。

实验使用 QEMU 的 user-mode network stack（用户模式网络栈）。提供的 Makefile 已启用该网络栈和 E1000 网卡；更多背景可查看 [QEMU 文档](https://www.qemu.org/docs/master/system/net.html#using-the-user-mode-network-stack)。

Makefile 还让 QEMU 把所有输入、输出包记录到实验目录的 `packets.pcap`。你可以检查这些记录，判断 xv6 是否真的收发了预期的包：

```sh
tcpdump -XXnr packets.pcap
```

实验新增文件的分工如下：

| 文件 | 已提供的内容 |
|---|---|
| `kernel/e1000.c` | E1000 初始化代码，以及需要你补全的收发空函数 |
| `kernel/e1000_dev.h` | E1000 寄存器、标志位与描述符格式定义，对照 Intel 手册使用 |
| `kernel/net.c`、`kernel/net.h` | 实现 IP、UDP、ARP 的简单网络栈，以及保存包的灵活数据结构 `mbuf` |
| `kernel/pci.c` | xv6 启动时在 PCI 总线上寻找 E1000 的代码 |

## 任务：补全发送与接收（困难）

补全 `kernel/e1000.c` 中的 **`e1000_transmit()` 和 `e1000_recv()`**，让驱动能够发送和接收包。**`make grade` 判定全部测试通过，才算完成实验。**

### 怎样读设备手册

写代码时会经常查阅 Intel 的 *PCI/PCI-X Family of Gigabit Ethernet Controllers Software Developer’s Manual*。尤其有用的章节是：

| 章节 | 原页推荐用途 |
|---|---|
| 第 2 章 | 必要的设备整体概览 |
| §3.2 | 包接收概览 |
| §3.3，结合 §3.4 | 包发送与发送环 |
| 第 13 章 | 各寄存器的参考说明 |
| 第 14 章 | 理解已经提供的初始化代码 |

手册涵盖多个相近型号，QEMU 在这里模拟的是 **82540EM**。先略读第 2 章，建立设备的整体印象；实现驱动时应熟悉第 3、14 章和 §4.1（不必读 §4.1 的子节），并把第 13 章作为查阅资料。其他章节主要描述驱动不会接触的部件。开始时不用纠缠所有细节，先知道在哪里找信息即可：E1000 的大量高级功能可以忽略，本实验只需要少量基本功能。

### DMA、描述符与环

已经提供的 `e1000_init()` 会配置 E1000，使它从 RAM 读取待发送包，把收到的包写入 RAM。这叫作 DMA（直接内存访问）：直接读写包数据的是 E1000 硬件。

突发到达的包可能比驱动处理得更快，因此初始化函数为 E1000 提供了多个接收缓冲区。设备要求用 RAM 中的一个**描述符数组**说明这些缓冲区；每个描述符含有一个地址，指明设备可以把收到的包写到哪里。`struct rx_desc` 定义了这种描述符的格式。

这个数组叫接收环（receive ring），也叫接收队列。设备或驱动走到数组末尾后，会绕回开头。`e1000_init()` 通过 `mbufalloc()` 分配供 DMA 写入的 mbuf。发送方向也有一个环，用来放驱动希望设备发送的包。两个环的大小分别是 `RX_RING_SIZE`、`TX_RING_SIZE`。

`net.c` 的网络栈要发送包时，会把保存该包的 mbuf 传给 `e1000_transmit()`。发送代码应把包数据的指针放到 TX 环描述符中，格式见 `struct tx_desc`。每个 mbuf 最终都需要回收，但只能在设备完成对应操作后回收；设备用描述符中的 `E1000_TXD_STAT_DD` 位报告完成。

> 编者注：这里的 DD 是驱动可回收缓冲的完成依据，不代表对端应用已经收到包。Intel 手册还区分“数据已经取入设备”与“真正发送到线路”；详见[实验指导](#/c/mit-6.s081-2020/lab/net?v=guide)。

E1000 从以太网收到包后，先 DMA 到下一个 RX 描述符指向的 mbuf，再产生中断。`e1000_recv()` 要检查 RX 环，将每个新包的 mbuf 通过 `net_rx()` 交给 `net.c` 的网络栈。然后为描述符分配一个新的 mbuf；设备再次绕到这个位置时，就有新的缓冲可写。

除了 RAM 中的环，驱动还要访问 E1000 的内存映射控制寄存器，获知接收状态，并通知设备已有待发送的描述符。全局变量 `regs` 指向第一个控制寄存器，通过数组下标可以访问其他寄存器，尤其要用到 `E1000_RDT` 与 `E1000_TDT`。

## 测试：从一次往返到全部测试

先在一个宿主机终端运行：

```sh
make server
```

在另一个宿主机终端运行：

```sh
make qemu
```

进入 xv6 后运行：

```sh
$ nettests
```

第一个测试向宿主机上 `make server` 启动的程序发送 UDP 包。驱动没写完时，它不会真正发送，因而通常看不到后续进展。

实现完成后，驱动发送包，QEMU 把包交给宿主机，服务器收到后发送回复，回复再经驱动到达 `nettests`。不过，在宿主机发回复前，它会先发 ARP 请求，询问 xv6 的 48 位以太网地址，并等待 ARP 回复。只要驱动写好，`kernel/net.c` 已能处理这件事。顺利时：

- xv6 的 `nettests` 显示 `testing ping: OK`。
- 宿主机服务器显示 `a message from xv6!`。

## 官方提示

先给 `e1000_transmit()`、`e1000_recv()` 添加打印语句，再运行 `make server` 和 xv6 中的 `nettests`。你应该能从打印确认：`nettests` 确实调用了 `e1000_transmit()`。

### 发送函数的六条提示

1. 读取控制寄存器 `E1000_TDT`，得到设备期望放入下一个待发送包的 TX 环索引。
2. 检查环是否已经没有可用位置。如果该索引处描述符的 `E1000_TXD_STAT_DD` 没有设置，说明设备还没完成这个槽原先的发送请求，应返回错误。
3. 否则，如果该描述符上次发送时关联过一个 mbuf，用 `mbuffree()` 释放它。
4. 填写描述符：`m->head` 指向内存中的包数据，`m->len` 是包长；设置必要的 `cmd` 标志（查手册 §3.3），并保存 mbuf 指针，以便以后回收。
5. 最后把 `E1000_TDT` 加一，并对 `TX_RING_SIZE` 取模。
6. 成功把 mbuf 加入环时返回 `0`；失败时，例如没有可用描述符，返回 `-1`，让调用者知道应由它释放这个 mbuf。

### 接收函数的七条提示

1. 读取 `E1000_RDT`，加一后对 `RX_RING_SIZE` 取模，得到下一个可能有待处理接收包的位置。
2. 检查描述符 `status` 中的 `E1000_RXD_STAT_DD`。如果没有设置，就停止。
3. 否则，把描述符报告的长度写入 mbuf 的 `m->len`，再用 `net_rx()` 将 mbuf 交给网络栈。
4. 用 `mbufalloc()` 分配新的 mbuf，替换刚交给 `net_rx()` 的那个；将新 mbuf 的数据指针 `m->head` 写入描述符，并把描述符状态位清零。
5. 最后把 `E1000_RDT` 更新为刚处理完的最后一个环描述符的索引。
6. 查看 `e1000_init()` 怎样初始化 RX 环中的 mbuf；可以借鉴其中代码。
7. 累计到达的包数迟早会超过环的大小 **16**，确保代码能够处理这种情况。

还需要用锁处理并发：xv6 可能从多个进程使用 E1000，也可能在内核线程正使用设备时收到中断。

## 选做挑战

原页说明：以下部分挑战的收益只能在真实的高性能硬件上测量或检验；原文在 2020 年语境下将其表述为 x86 计算机。

1. **用发送中断补充 TX 环（容易）。** 当前网络栈用中断处理入站包，但不以中断处理出站包。可以先在软件里排队，每次只交给 NIC 有限数量的包，再依靠 TX 中断补充发送环。这样还能对不同类型的出站流量安排优先级。
2. **补全 ARP（中等）。** 已提供的代码仅部分支持 ARP。实现完整的 [ARP 缓存](https://tools.ietf.org/html/rfc826)，并接入 `net_tx_eth()`。
3. **每核一对环（中等，但难以测试或测量）。** 原页称 E1000 支持多个 RX/TX 环；尝试为每个 CPU 核配置一对环，让网络栈支持多环，从而提高吞吐、减少锁竞争。
4. **改进 socket 查找（容易，但严肃实现难以测试或测量）。** `sockrecvudp()` 目前用单链表找目标 socket，效率不高；尝试使用哈希表和 RCU 提高性能。
5. **传递 ICMP 错误。** [ICMP](https://tools.ietf.org/html/rfc792) 能报告网络通信失败。检测这些通知，通过 socket 系统调用接口把它们传递为错误。
6. **利用卸载功能（中等，但难以测试或测量）。** 原页将校验和计算、RSC、GRO 列为 E1000 的无状态硬件卸载功能，建议使用其中一种或多种提高网络栈吞吐。
7. **解决接收活锁（中等，但难以测试）。** 实验网络栈可能发生 receive livelock；结合课堂和指定阅读，设计并实现解决方案。可从[第 21 讲笔记](#/c/mit-6.s081-2020/lec/lec21?v=notes)与[课程资料](#/c/mit-6.s081-2020/lec/lec21?v=materials)继续。
8. **为 xv6 实现 UDP 服务器（中等）。**
9. **实现最小 TCP 栈并下载一个网页（困难）。**

> 编者注：第 3、6 项忠实保留了原页的泛称，不能据此认定本实验的 **82540EM / QEMU `e1000` 模型**拥有任意多队列或所列全部卸载能力。具体型号、模拟器版本及功能配置需要分别核对；尤其 **GRO 通常指软件接收聚合机制，不能笼统写成该芯片的硬件能力**。这里没有验证这些选做扩展，也不把它们变成基础实验的通过条件。
