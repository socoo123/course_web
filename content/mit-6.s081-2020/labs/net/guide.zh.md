# 网络实验指导：把描述符环当作所有权交接协议

这个实验最容易写错的不是取模，而是：**哪一刻设备可以读写这块内存？哪一刻软件可以回收它？发生失败时谁负责释放？** 两个函数虽短，却同时涉及异步 DMA、并发调用、协议栈回调与缓冲生命周期。

先读[实验说明](#/c/mit-6.s081-2020/lab/net?v=zh)。下文是编者的机制解释与实施骨架，不是额外评分要求，也不提供可直接替换空函数的答案。

## 1. 先画清楚五种对象

| 对象 | 在哪里 | 主要作用 | 谁会使用 |
|---|---|---|---|
| `regs` 指向的控制寄存器 | 设备的 MMIO 地址区域 | 配置设备、发布 tail、确认中断 | CPU 访问、设备响应 |
| `tx_ring` / `rx_ring` | RAM | 按硬件格式描述缓冲地址、长度、命令与状态 | CPU 与设备 |
| `tx_mbufs` / `rx_mbufs` | RAM | 记录每个槽对应哪个软件对象 | 驱动；设备不理解这两个指针数组 |
| `struct mbuf` | 内核分配的内存 | 保存包字节及其当前有效视图 | 驱动、网络栈、socket 队列 |
| socket 的 `rxq` | 内核软件队列 | 让已收包等待用户读取 | 网络栈、读取进程 |

在已核对的分支中，两种描述符都为 16 字节，两个环都含 16 项；环内存为 256 字节，满足初始化代码检查的 128 字节倍数要求。`regs` 是 `volatile uint32 *`，头文件把寄存器的字节偏移除以 4 后定义成下标；**不要对已有宏再除一次 4**。[C20: `e1000.c`、`e1000_dev.h`]

mbuf 不是只有一个指针：`buf[2048]` 是实际存储，`head` 指向当前有效数据的起点，`len` 是有效长度，`next` 用于软件队列。发送时网络栈会逐层向前添加头部；接收时会逐层移动 `head`、减少 `len`。因此，设备应看到 `m->head` 指向的数据，而不是 mbuf 结构体头地址。

`mbufalloc(0)` 为接收准备从缓冲起点写入的空间。发送方向使用的默认 headroom 是 128 字节，为各层加头留位置；不要把默认发送 headroom 机械搬到 2048 字节接收缓冲配置里。

### 三条路径先读通

```text
发送：用户 write → sockwrite → net_tx_udp → net_tx_ip → net_tx_eth → 驱动 → NIC
接收：NIC → 中断 → 驱动 → net_rx → IP/UDP → sockrecvudp → rxq → sockread
ARP： 接收 → net_rx_arp → net_tx_arp → net_tx_eth → 再次进入发送驱动
```

这些路径来自该分支的 `net.c`、`sysnet.c`、`trap.c`。第三条路径会决定锁能放在哪里。

## 2. 发送：成功返回意味着接管，不意味着发送完毕

发送接口的所有权约定是整个实验的第一条不变量：

| `e1000_transmit(m)` 结果 | 谁持有新包 m | 接下来谁释放 |
|---|---|---|
| `0`：成功提交 | 驱动／正在使用它的设备 | 驱动在确认设备完成后回收 |
| `-1`：无法提交 | 调用者仍持有 | `net_tx_eth()` 的失败分支调用 `mbuffree(m)` |

所以发送失败时，驱动不能既释放新包，又返回 `-1`；否则调用者还会释放一次。也不能已经让设备看到它，却返回失败让调用者释放。这不是抽象建议，`net.c` 的 `net_tx_eth()` 已明确写出失败回收路径。

### 用四个状态推导 TX 槽位

1. **可复用**：当前目标槽的 DD 表示先前任务已经结束。初始化代码把 TX 描述符的 DD 置位，但 `tx_mbufs` 为空，这表示“从未提交过”，无需释放旧对象。
2. **软件准备中**：如果有旧 mbuf，确认 DD 后才能回收；随后准备新地址、长度、命令与软件对象记录。新一轮使用不能沿用旧的完成状态。
3. **已发布给设备**：更新 TDT 后，设备可以异步获取描述符和包。即使函数返回，mbuf 仍必须存活。
4. **设备已完成**：设备写回 DD，此槽可以在后续复用时回收旧 mbuf。官方提示采用这种延迟回收方式；没有新发送时，尾部少量完成 mbuf 可暂时保留在有限槽位中，不等于必须添加 TX 中断来通过基础任务。

**核心不变量：**已提交、尚未报告完成的描述符和 mbuf 都不能被软件重写或释放。软件锁只协调软件，设备不会来获取这把锁。

### DD、EOP、RS 各回答一个问题

| 字段 | 本实验里要理解的含义 | 常见误读 |
|---|---|---|
| TX `status.DD` | 设备完成了这个描述符的处理，可按协议回收缓冲 | 等同对端收到／应用处理完 |
| TX `cmd.EOP` | 这个描述符结束一个包；一个包一般可以由多个描述符组成 | 它是“发送完成”位 |
| TX `cmd.RS` | 请求设备写回状态，软件才有 DD 可检查 | 它就是 CPU 的中断使能 |
| RX `status.DD` | 这个接收描述符已经完成 | 一定是完整包，不用区分 EOP |
| RX `status.EOP` | 本描述符是接收包的最后一段 | 与 TX 同一个字段、由软件设来发送 |

已核对的头文件给出 `E1000_TXD_CMD_EOP`、`E1000_TXD_CMD_RS`、TX/RX 的 DD 及 RX EOP。手册 §3.3.3.1 明确：只有请求 RS 的发送描述符才会报告 DD。忘记请求状态，可能首次发送正常、绕环后却再也无法复用。

手册对 RS 的完成含义是设备处理描述符、取入数据后的状态，不是端到端送达证明；82544 特有的 RPS 语义不能套到本实验的 82540EM。§3.4 还解释了为什么检查内存中的 DD 比直接拿 TDH 推进来推断回收更稳妥：I/O 写缓冲可能使观测到的寄存器与内存写回次序不同。

基础实验用一个 mbuf 表示一帧，提供的 RX 配置是 2048 字节缓冲且未启用长帧。原页提示只要求检查 DD，并未要求你实现任意多描述符接收包的拼接。理解 EOP 的意义即可；如果扩展到跨描述符包，必须另设计拼接或完整丢弃策略，不能把片段直接当完整帧交给 `net_rx()`。

## 3. 环索引：TX 的当前槽与 RX 的下一槽不同

按官方提示的实现约定：

| 操作 | 从哪里开始 | 处理后发布什么 |
|---|---|---|
| TX 提交 | `TDT` 指向的当前槽 | 下一个位置，即当前索引加一取模 |
| RX 检查 | `(RDT + 1) % RX_RING_SIZE` | 最后一个已处理并补好缓冲的索引 |

例如初始化后 TX 的 TDT 是 0，首个发送槽是 0；RX 的 RDT 是 15，首个接收检查位置也是 0。处理到 15 后，两边都要能绕回 0。

但两者不能简单理解成同一个“队尾”算法。手册里 RX 的 RDT 是硬件可用区间的**排他边界**；初始化 `RDH=0, RDT=15`，不意味着硬件同时可任意消费全部 16 项。驱动把处理后的索引写回 RDT，是沿环推进这条边界；不应声称“写 RDT=i 就立即授权设备使用 i 本身”。下一次软件检查 `(RDT+1)%N` 是本实验使用 RDT 兼作消费进度标记的约定。[I8254X: §3.2.6、§13.4.29]

真正决定有没有可消费数据的是相应槽的 DD。取模只保证不越界，不能代替所有权检查。也不要把[第 24 讲](#/c/mit-6.s081-2020/lec/lec24?v=draft) 63:00–69:00 中讨论的“每次扫描整环”当作已验证替代解法；讲者当时没有验证它。

## 4. 接收：旧对象交出去，新对象才能交给设备

接收流程中有两种“回收”，必须分开：

- **回收描述符槽位**：把它补成下一轮设备可用的接收位置。
- **释放旧 mbuf**：由网络栈或最终消费者完成，不一定发生在驱动函数返回前。

静态阅读 `net.c` 和 `sysnet.c` 可以看到：ARP、未知协议、格式错误等路径可能立即释放旧 mbuf；合法 UDP 则可能排入 socket 的 `rxq`，由 `sockread()` 拷贝到用户空间后释放，或在 socket 关闭时清理。

因此，调用 `net_rx(old)` 是一次**所有权转移**。函数返回后，不要再读取 `old->head` 来重置描述符，更不能再释放 old；它可能已经被释放，也可能仍在等待用户。

### 需要你落实的顺序约束

官方提示的顺序是：检查 DD → 设置旧 mbuf 长度 → 交给网络栈 → 分配并安装替代 mbuf → 清状态 → 推进 RDT。

把这串步骤理解为三个必须成立的条件：

1. **读取条件**：设备报告完成后，才能信任该接收项的数据和长度；给上层的长度是描述符报告值，不是缓冲容量。初始配置剥离 Ethernet CRC，不应再无条件减去一次 CRC 长度。
2. **替换条件**：环中软件记录和描述符地址应共同指向新的、仍有效的 mbuf。旧 mbuf 交给上层后，绝不能同时作为下一轮 DMA 的目标。
3. **发布条件**：新缓冲、状态清理和软件进度均安排好之后，才能向设备推进 RDT。不能先交还边界，再分配缓冲。

**编者建议：**可先取得替代缓冲，再做不可撤销的旧对象交接，这样分配失败时仍掌握旧对象。若采用这一局部重排，要保持对上层交接、环内状态和发布次序的完整说明；它不是把 RDT 提前更新。

`mbufalloc()` 可能返回空指针，初始化代码采取 panic。运行中的补充缓冲失败如何处理，原页没有指定唯一方案，至少不能把空指针放进环后继续运行。一个可分析的本地策略是丢弃当前包、保留并重新准备原缓冲；另一种是停止并明确报错。若选择暂留完成项等待以后重试，必须说明谁会触发重试，否则可能永远没有下次进展。不要在中断上下文里等待一个需要睡眠才能获得的资源。

### 一次中断不等于一个包

假设 CPU 开始处理时，槽 0、1、2 都已经有完成项。如果只处理槽 0 就返回，槽 1、2 可能再也没有新通知来驱动处理。正确退出依据应是“按协议检查的下一槽没有 DD”，而不是“已经处理过一个”。循环中每交接一个包，都要补充缓冲、推进相应进度，然后再检查下一个位置。

这也不能反向推导成“无限高负载下永远清到空最好”。基础实验的批量处理保证已到达工作不被遗漏；高负载的预算、公平性和 receive livelock 属于选做，见[第 21 讲课程资料](#/c/mit-6.s081-2020/lec/lec21?v=materials)。

## 5. 锁、发布顺序与中断确认是三件事

### 先保护软件共享状态

两个发送进程可能都读到同一个 TDT，然后分别把自己的 mbuf 填入同一槽。保护范围必须覆盖“选槽、判断能否复用、回收旧对象、登记新对象、发布新进度”这整个状态变化，不能只锁最后一次寄存器赋值。所有失败出口也必须释放已取得的锁。

xv6 的自旋锁还会管理本核中断状态，但关本核中断不能排除另一核。反过来，只说“接收在中断里”也不足以证明 RX 永远不会并发；需要结合实际入口、PLIC claim/complete 和是否新增其他调用者判断。本实验起始代码仅由 `e1000_intr()` 调用静态 `e1000_recv()`，但不要把这个局部前提推广为所有网卡驱动都不需要 RX 同步。

### 不要带着发送锁调用 net_rx

下面的依赖是该分支中真实存在的：

```text
持有 e1000 发送锁
  → net_rx
    → net_rx_arp
      → net_tx_arp
        → net_tx_eth
          → e1000_transmit
            → 再次申请同一把锁
```

xv6 自旋锁不是递归锁，这条链会导致重复获取错误／自锁等待。设计时把 RX 与 TX 的保护对象分清；如果接收侧需要锁，先完成受保护的交接，再在合适的无锁边界调用网络栈，并保证不会有另一个接收者重复消费同一描述符。不能只为消除 panic 随意删掉并发保护。

### 发布前的数据次序

更新 TDT/RDT 相当于告诉设备“可以继续工作”。因此，设备不能先看到新 tail，却看到旧的地址、长度、状态或尚未准备好的数据。

`volatile` 不能自动建立所有普通内存写入与 MMIO 之间所需的顺序；锁也不代表设备会参与互斥。应分别审视编译器次序、处理器／I/O 次序以及平台的 DMA 一致性约定。分支初始化中已有 `__sync_synchronize()`；课堂 57:00–60:00 讨论了发布前的屏障，但**普通屏障不等于任意真实机器上的 DMA cache clean/invalidate**。本指导没有验证跨平台移植，也不要求为了基础实验加入一套新的 DMA 框架。

### 三层中断状态别混在一起

1. 设备侧：`e1000_intr()` 在调用接收函数前写 `E1000_ICR = 0xffffffff`，清除设备的中断原因。手册 §13.4.17 说明 ICR 可读清，也可写 1 清相应位。
2. 平台侧：`devintr()` 在驱动处理后调用 `plic_complete(irq)`，结束这次 claim 的服务。
3. CPU 侧：RISC-V 的中断使能由相应状态位及 trap 返回路径控制。

所以 ICR 确认不等于打开 CPU 中断，PLIC complete 也不等于释放 mbuf。基础任务无需重写已提供的确认路径。

另一个阅读细节：分支初始化把 IMS 位 7 的注释写为 `RXDW`，手册对应名称为 **RXT0（Receiver Timer Interrupt）**；RDTR 为 0 时每个收到的包可触发这类事件。不要把源码这句注释扩写成新的硬件寄存器定义。[C20: `e1000.c:89–92`；I8254X: §3.2.7.1.1、§13.4.17]

## 7. 按证据定位，不盲改网络栈

| 现象 | 优先检查 | 能据此确认什么 |
|---|---|---|
| 发送函数没有被调用 | 是否进入正确分支、是否在 xv6 运行 nettests | 只能定位到驱动之前 |
| 发送已调用，但 pcap 没有请求 | TDT、描述符数据地址／长度／命令、发布次序 | 软件调用不等于硬件已取走包 |
| 宿主机收到请求，只有 ARP 请求没有回复 | RX 的 DD、长度、交接、ARP 回调锁重入 | TX 部分可用，不能断言完整收发可用 |
| 第一轮成功，约绕环后卡住 | 未清旧 DD、未请求 RS、mbuf 未替换、索引错误 | 常见于生命周期与复用协议 |
| 串行成功，并发卡住 | TX 临界区、RX 是否一轮只取一个包 | 暂不能仅凭现象认定是协议错误 |
| 内核出现 double free／内存损坏 | TX 失败回收、net_rx 后再次用旧对象、提前释放 DMA 缓冲 | 需要逐一追踪对象的最终所有者 |
| pcap 有宿主机回复，但 read 不返回 | 驱动是否交上层、长度是否正确、上层协议与端口匹配 | 抓到包不等于交到 socket |
| 只卡在 DNS 或显示 wrong ip address | `8.8.8.8:53` 可达性、实际 DNS 回答、2020 测试硬编码 | 不应直接归因于驱动，也不能自动豁免为通过 |

调试打印以“槽位、原状态、操作、下一索引”即可，避免在中断路径持续打印整包掩盖时序。需要看包字节时优先用 pcap。

另外，抓包中请求的目的 MAC 为广播不一定是你的驱动写坏：这个分支的 `net_tx_eth()` 明确因 ARP 支持不完整而统一使用广播目的 MAC。这是**已核对的实验分支事实**，不是替第 21 讲当时没有解释清楚的录课工作树补一个确定结论。

## 自测：动手前把不变量说完整

<details><summary>TX 返回 -1 前已经释放新 mbuf，会怎样？</summary>

调用者 `net_tx_eth()` 还会释放同一对象，造成重复释放。失败表示驱动没有接管新包；成功表示已接管，但不能据此立即回收。

</details>

<details><summary>设备完成接收后，把旧 mbuf 给 net_rx，再让描述符继续指它，为什么不行？</summary>

旧对象可能马上被释放，也可能留在 socket 队列中等待读取。下一次 DMA 会写入已回收内存或覆盖尚未读完的包。描述符槽可以复用，包对象的生命周期不能因此提前结束。

</details>

<details><summary>只给 TDT 的写操作加锁，能阻止两个发送者选择同一槽吗？</summary>

不能。冲突从读取当前索引及判断可用时就已开始。临界区需要覆盖整个共享状态转换，包括软件 mbuf 记录。

</details>

<details><summary>一个中断到来时有三个完成项，为什么不能只交付第一个？</summary>

通知并不与包一一对应。剩余完成项可能没有后续通知，应根据下一个描述符是否完成决定何时退出。

</details>

<details><summary>清 ICR 后是不是就能安全复用所有 TX/RX 缓冲？</summary>

不是。ICR 是事件原因，描述符 DD 与缓冲交接是数据生命周期；确认中断不会替你证明设备已完成所有 DMA，更不会证明上层已用完包。

</details>

<details><summary>数据已经写入设备 FIFO，就能说宿主机应用收到了吗？</summary>

不能。描述符完成、本机发出、对端收包、应用读取是不同事实。应分别用 DD、抓包、服务器与 nettests 输出作为相应证据。

</details>
