# 页表实验指导

本实验的主线是：**不改变用户虚拟地址的含义，让内核在正确的进程上下文中直接读到同一份物理内存。** 打印页表帮助你看见映射；每进程内核页表使映射能随进程变化；双页表同步使直接读取始终正确。

## 1. 先分清三个对象

| 对象 | 描述什么 | 谁使用 |
|---|---|---|
| `p->pagetable` | 进程的用户地址空间，另有陷阱用的特殊映射 | 用户态及陷阱过渡阶段 |
| 每进程内核页表 | 内核运行所需映射；第三阶段再加入该进程的低地址映射 | 代表该进程执行的内核代码 |
| 全局 `kernel_pagetable` | 启动、调度器等无当前进程环境需要的内核映射 | 没有进程运行时 |

“两张页表指向同一物理页”不等于“复制了一份页内数据”。第三阶段要建立映射别名；`fork` 为子进程复制用户内存则是另一件事。页表本身也占用物理页，要与叶项指向的程序数据页区分。

前置概念可按问题回看 [LEC 4 课程资料](#/c/mit-6.s081-2020/lec/lec04?v=materials)：三级索引与权限见 §3.1，内核布局见 §3.2，页表函数见 §3.3，分配器见 §3.4–3.5，用户布局、`sbrk` 和 `exec` 见 §3.6–3.8。

## 2. vmprint：遍历结构，不跟着数据走

先研究 `freewalk` 怎样区分有效非叶项和有效叶项：`PTE_V` 决定是否存在，`R/W/X` 则帮助判断它是否指向下一级页表。打印器借用的是这种遍历结构，不执行释放动作。

思路骨架：

1. 顶层入口打印传入的根页表地址。
2. 在一页中的 512 个槽位里，按索引递增检查 PTE；无效项跳过。
3. 对有效项打印当前深度、当前页内索引、完整 PTE 和 `PTE2PA` 得到的地址。
4. 仅当它是非叶项时继续向下遍历；到叶项就停止。

检查两条不变量：**每个有效项恰好打印一次；递归指针只指向页表页。** 如果把叶数据页也当成页表，可能产生一大串看似随机的“映射”，甚至读到非法地址。

打印里的索引只是所在页表页中的位置，不是完整虚拟页号。要解释某个叶项，把沿途的三级索引放回各自的位段，再结合 12 位页内偏移。不要把各层物理地址拼接起来。

回答官方图 3.4 的问题时，按以下证据链自行分析：

- 在 `exec` 中找到 ELF 加载区的范围，以及追加两页和 `uvmclear` 的位置。
- 对照样例末尾权限位，分别检查 `V/R/W/X/U`，不要只看“PTE 有效”。
- 区分 `userinit` 创建的 `initcode` 和 `exec("/init")` 成功后的映像；要求打印的是后者。

输出调试优先看层次、索引和标点，不要硬编码样例物理地址。第一任务只添加观察能力，适合先独立完成并按官方 `pte printout` 要求验收。

## 3. 每进程内核页表：先走通生命周期

这一阶段先保持内核映射正确，再引入用户低地址映射。可以在纸上列出五个动作及其责任：

| 动作 | 应当保证的条件 |
|---|---|
| 创建 | 新页表能映射内核指令、数据、RAM、所需设备与 trampoline |
| 安装内核栈 | 当前进程的栈 VA 指向它自己的栈物理页，旁边保护页保持不可用 |
| 切入进程 | 使用该进程的内核页表，并刷新本 hart 的翻译缓存 |
| 返回调度器 | 回到适合无进程状态的全局内核页表 |
| 回收 | 不再有人使用该页表；私有页表页回收，叶页按所有权分别处理 |

### 构造函数不能偷偷写全局表

参考 `kvminit` 拆出“为指定页表安装映射”的逻辑时，注意旧 `kvmmap` 内部直接使用全局 `kernel_pagetable`。只分配一个新根、却继续调用写全局表的旧辅助函数，并不能构造出独立的映射树。

也不要只复制根页的 PTE 就认为整棵树独立：那些非叶 PTE 仍可能指向原来的下级页表页。之后修改用户低地址映射或递归回收，会影响其他进程或全局页表。此任务最容易理解的方案是独立拥有页表结构，按需要共享叶物理页。

### 切换时，下一条指令和当前栈仍要有效

`satp` 是每个 hart 的寄存器；更换它不会替你保存线程上下文，也不会自动满足 TLB 刷新要求。结合 `scheduler` 的 `swtch` 前后，逐点写出当前使用哪张页表、当前栈是什么：切入前是调度器栈，切入后是进程内核栈；返回时顺序相反。

任何切换点都必须能继续访问正在执行的内核代码、当前仍在使用的栈以及紧接着访问的数据。只在“下一次调度”才补映射已经太迟。

参考快照的 `usertrapret` 把当前 `r_satp()` 存入 `trapframe->kernel_satp`，随后 `trampoline.S` 在下次用户陷阱时恢复它。因此还要沿“调度 → 返回用户 → 再次陷入内核”这条路径核对，不能只观察 `scheduler` 的切换。

### 栈位置变化会影响软件地址翻译

在参考快照中，`kvmpa` 固定查全局页表；`virtio_disk.c` 有把内核栈上对象转换为物理地址的调用。如果你把内核栈改为只映射在每进程页表中，就应审查这类旧假设：软件查表所用页表必须能解释该地址。

这不是让你无条件把所有查表函数改成 `myproc()`：启动或调度器环境可能没有当前进程。先明确调用场景和栈映射策略，再调整相关接口。

## 4. 释放所有权：删映射不等于释放内存

用下面的表解释你的回收设计，比记住某个释放函数名字更可靠：

| 内存对象 | 所有权与回收原则 |
|---|---|
| 私有内核页表的根页、下级页表页 | 该进程的页表结构拥有；在无人使用时递归回收 |
| 用户数据物理页 | 用户地址空间负责分配和回收；内核低地址别名不再释放一次 |
| 内核指令、共享内核数据、RAM 直接映射所覆盖的页 | 不是这张进程页表私有的叶资源；销毁该页表不能据此逐页 `kfree` |
| 设备寄存器页 | 不是分配器分配的 RAM；绝不能 `kfree` |
| trampoline 物理页 | 全局代码资源，只撤销相应映射 |
| 进程内核栈物理页 | 若改为按进程分配，需在该进程不再使用栈后单独回收一次 |
| trapframe 物理页 | 由进程生命周期管理；不是看到页表叶项就再释放一次 |

`uvmunmap` 的 `do_free` 区分撤销映射与释放叶页。原 `freewalk` 则要求叶映射已经移除，否则报 `freewalk: leaf`。直接对整张内核页表调用 `uvmfree`，既不满足映射布局假设，也不满足资源所有权。

特别注意内核栈的高地址 VA：它不是可以直接传给 `kfree` 的物理地址。若通过页表寻找它的 PA，必须在销毁那份映射证据之前取得。

回收包括成功退出，也包括 `allocproc`、`fork` 或映射构造中途失败。为新字段明确“尚未分配”的状态；失败只回收已经取得所有权的对象。不要释放当前 CPU 仍在使用的页表或内核栈。

## 5. 用户映射副本：四个同步入口

对每一个需要供新复制函数读取的普通用户页，目标关系是：两张表在相同 VA 上指向相同 PA，但内核侧的权限适合 supervisor 访问。**用户页表继续保留用户权限；修改的是内核侧副本。**

先让 `copyin_new` 所需映射工作，再接入 `copyinstr_new`。这可以把“映射不存在”与“字符串结束条件”两类问题分开定位。

| 入口 | 同步时机与常见遗漏 |
|---|---|
| `userinit` | 第一页建立后、进程可运行前准备好内核别名；它不是通过普通 fork 创建的 |
| `fork` | 子进程用户页复制完成后，以**子进程的物理页**建立子进程内核映射；不能照搬父进程的 PA |
| `exec` | 新映像准备成功后同步替换旧映射；失败时旧程序的用户页表和内核别名都应仍可用 |
| `sbrk` → `growproc` | 增长添加新页别名，收缩撤销已释放页的别名；只同步增长不够 |

### 页粒度与字节大小

`p->sz` 按字节计，页表按页管理。`sbrk(1)` 有时不需要新物理页，有时会跨到下一页；收缩同样只回收完全不再需要的页。结合 `PGROUNDUP` 推导变化区间，防止重复映射末页触发 `remap`，或把仍含有效字节的页提前撤销。

收缩后不能留下可用的旧别名：一旦物理页重新分给别的对象，旧别名就会指向别人的数据。修改正在使用的页表时，也要考虑本 hart 的旧翻译缓存；“PTE 已清零”不代表旧 TLB 项自动消失。

### exec 应保持成对提交

参考 `exec` 的原有原则：先构造候选映像，确认成功，再替换旧映像。加入内核副本后，这个原则仍成立。问自己：如果为新的内核别名分配页表页失败，旧用户程序还能否正常返回？如果新映像比旧映像小，旧映像尾部的别名是否也清理了？

不要因为优化了 `copyin` 就顺手把 `copyout` 也改成当前内核页表上的直接写。`exec` 会用 `copyout` 写入尚未成为当前映像的新页表，调用语义与当前进程的直接读取不同。

### 权限与保护页要分别想清楚

本实验不通过打开 `SUM` 来代替内核副本的权限处理。保留原用户页表的权限，确保内核副本没有妨碍 supervisor 读取的 `PTE_U`；同时不能给任意未映射地址凭空增加合法性。

教材 §3.6 的校注尤其重要：2020 用户栈保护页有物理页，只清除了用户表里的 `PTE_U`；内核栈保护页则没有有效映射。这意味着“在用户表中不允许用户访问”与“没有物理页”不是同一回事。`p->sz` 的范围检查也不能独自证明其中每页都具备用户权限。

核对你手中的实验 `vmcopyin.c` 如何界定可读地址，区分实验简化策略与一般内核的严格指针检查；不要擅自修改该文件来适配自己的映射。此处不把未取得的实验实现当成已经验证的权限规则。

## 6. PLIC 上界与参考快照差异

官方 2020 任务指定的分界是 **`PLIC = 0x0c000000`（192 MiB）**。其含义是低地址普通用户映射不能覆盖 PLIC，而不是“机器最多只有 192 MiB RAM”。使用半开区间理解：若某次申请描述 `[0, newsz)`，实际被映射的任何字节都应低于 PLIC，页基址不能等于 PLIC。官方以“小于 PLIC”描述进程大小；实现中的边界比较应结合排他终点与页舍入核对，不能允许多映射一页。

上界检查不能只放在 `sbrk`：`exec` 加载段并追加保护页、栈页时也会扩大地址范围。做整数加法或页对齐前，还需防止候选大小已经回绕，使一个超大请求伪装成小请求。

**参考源码的具体差异：** 固定提交 `e23d53f…` 的 `kvminit` 还映射了 `CLINT = 0x02000000`，低于 PLIC；若不加核对地把这张表原样用于第三任务，用户增长会先撞到这段映射。这一快照不是实验 `pgtbl` 分支，不能据此把官方上界改成 CLINT，也不能声称实验分支已经删除了该映射。

实际动手时，先检查 2020 实验分支的 `kvminit`、设备访问和启动路径，分清启动/M-mode 使用的地址与运行中 S-mode 内核必须保留的映射，再落实官方要求。本站没有获取该分支，因此这里只指出差异，不提供未经分支核实的删映射补丁。

## 7. 溢出问题：按无符号算术推导

题目中的 `srcva + len < srcva` 检测的是相加回绕。对 64 位无符号数，加法结果按模 $2^{64}$ 计算：数学意义上跨过最大值的区间，其机器表示的终点可能变成一个很小的数。于是，“终点没有超过大小上限”不必然意味着整个区间合法。

自行构造官方要求的例子时：

1. 先读实验 `copyin_new` 的参数类型和前三项检查，记下当前进程大小这一前提。
2. 让起点满足第一项范围要求，再选能让 64 位和回绕的长度。
3. 同时列出数学和、截断后的机器和；把机器和代入第二项检查。
4. 最后验证第三项确实为真。不能只给出一对溢出的数，却让第一项已经把它拒绝。

这里保留推导方法，不代写题目所要求的具体数值答案。参考快照中的旧 `copyin` 逐页调用 `walkaddr`；它不是题目中的 `copyin_new`，不要拿它猜测“前两项检查”的精确代码。

## 8. 最小调试路线

以下是供学习者实际实现后执行的路线，不是本站已完成的测试：

1. 第一阶段核对官方 `vmprint` 格式及 `pte printout`。
2. 第二阶段用 `usertests` 验证内核页表生命周期；此时保留原复制逻辑，较容易定位切表和内核栈问题。
3. 第三阶段先接 `copyin_new`，再接 `copyinstr_new`，最后按[实验说明](#/c/mit-6.s081-2020/lab/pgtbl?v=zh)完成 `usertests` 和 `make grade`。

| 现象 | 优先查看 |
|---|---|
| 一切到进程就发生内核异常 | 内核代码、当前栈、调度器栈是否在切换前后都可访问；`satp` 编码是否正确 |
| 系统调用第一次读取用户指针就失败 | `userinit` 是否同步；当前是否真的使用该进程的内核表；内核副本的 `PTE_U` |
| fork 后读到父进程后来改写的数据 | 子进程内核别名是否错误地仍指向父进程 PA |
| exec 失败后原程序也坏了 | 是否在新映像完全准备好前破坏了旧别名 |
| sbrk 收缩后偶发读到异常内容 | 旧别名、TLB 和物理页释放的先后关系 |
| `freewalk: leaf` 或 `kfree` panic | 页表页与叶页是否混用释放路径；是否重复释放或把栈 VA 当 PA |
| 磁盘操作时 `kvmpa` 失败 | 栈映射策略是否与软件查表所用页表不一致 |

页异常中的 `sepc` 指向出错指令，`stval` 有助于看出所访问的地址。按官方提示在 `kernel/kernel.asm` 找指令，再检查当时实际生效的页表。不要靠修改 `kernel/vmcopyin.c`、`kernel/stats.c`、`user/usertests.c` 或 `user/stats.c` 消除测试失败。

## 9. 选做的思考起点

- **大页：** Sv39 在更高层提前使用叶项时可形成 2 MiB 或 1 GiB 映射。除了少建页表页，还要考虑物理对齐、遍历如何识别高层叶项，以及部分撤销时怎么办；不能只改 `PGSIZE`。
- **突破 PLIC 上界：** 同一张表的同一 VA 不能同时表示用户数据和设备寄存器。先说明如何消除地址重叠，以及是否还能让 `copyin_new` 原样直接使用用户 VA，再谈扩大上界。
- **空指针触发异常：** 用户代码起点改到 4096 后，低地址会出现有意留下的空洞；检查加载、`userinit`、复制、释放和程序链接布局中的“从 0 连续存在”的假设。
