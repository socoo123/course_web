# Lab traps · 实验指导

这次实验围绕一个问题展开：**一段执行被另一段执行打断后，怎样保证还能回去？** 汇编题观察调用约定，backtrace 读取调用留下的记录，alarm 则主动改变用户执行路线，并承担恢复现场的责任。

正式任务与测试要求见[实验说明](#/c/mit-6.s081-2020/lab/traps?v=zh)。下面按“先理解现有路径，再做最小改动”的顺序提供思路。

## 1. 三种状态不要混在一起

| 状态 | 所在位置 | 保存的是什么 | 用于本实验的哪一部分 |
|---|---|---|---|
| 普通函数栈帧 | 当前执行栈 | 返回地址、旧帧指针、局部数据等 | 汇编题与 backtrace |
| `struct context` | 进程／CPU 的内核状态 | `swtch` 所需的内核寄存器子集 | 用来对照，不能直接当 alarm 备份 |
| `struct trapframe` | 每进程的 trapframe 页 | 用户通用寄存器、用户 `epc`，以及内核入口所需字段 | alarm 的用户现场 |

普通调用发生在编译器知道的位置，调用方能遵循 ABI 提前保护值。时钟中断可以落在计算的中间，被中断程序没有机会先保存临时寄存器。因此，不能只用“callee-saved 寄存器必须保持”来推导 alarm 的保存集合。

开始前顺着这条链读一次代码：

```text
用户代码
  → uservec：把用户寄存器保存到 trapframe
  → usertrap：保存用户 pc，分派系统调用／设备中断
  → usertrapret：准备 sepc、入口字段和特权状态
  → userret：恢复用户寄存器，sret 返回用户态
```

硬件没有替软件保存全部通用寄存器；这部分工作在 `trampoline.S`。`epc`、栈上的 `ra` 和内核切换用的 `context.ra` 也不是同一个“返回位置”。

## 2. 汇编题：用证据回答，不猜地址

先在实验分支生成 `user/call.asm`，再把它与 `user/call.c` 并排阅读。每道题写下“结论 + 对应指令或数据布局依据”，而不是只写一个数字。

- 参数题：先数清 `printf` 的所有实参，格式字符串本身也占一个位置，再检查调用前装入寄存器的指令。
- 调用题：分别追踪源代码里的调用关系与实际机器指令。源码中有函数，不代表每次使用都会留下独立的调用指令；题面已提醒内联。
- 地址题：看本次构建中的符号及指令地址。`printf` 的入口与调用完成后继续执行的位置是两回事。
- `ra` 题：分清汇编伪指令与真正的指令编码，结合实际指令长度判断下一条指令在哪里；不要给所有反汇编行机械加同一个长度。
- 字节序题：分别处理整数格式化和“把一块内存按字符串读取”这两条路径。先按地址递增画出 `i` 的四个字节，再找字符串终止位置。
- 缺少实参题：比较格式串要求读取的项目与调用者实际提供的项目。某次运行看到的数字不足以证明它是语言保证的结果。

调用约定和栈帧背景见 [LEC 5 笔记 §2–§4](#/c/mit-6.s081-2020/lec/lec05?v=notes)；本页不提供六组问题的答案。

## 3. Backtrace：沿“上一帧”走，不沿固定帧大小走

### 3.1 先确定布局适用条件

本实验利用的是保留帧指针的 RV64 帧记录：

```text
较高地址
fp        当前帧的定位基准
fp - 8    保存的返回地址
fp - 16   保存的上一帧 fp
          其余保存值／局部变量（大小不固定）
sp        当前栈顶
较低地址
```

这里 `fp` 是 `s0` 的别名，偏移以**字节**计。若先把地址转成 `uint64 *` 再做指针运算，每一步就是 8 字节；混淆这两套单位会读错位置。

固定 2020 Makefile 使用 `-fno-omit-frame-pointer`，与题面思路相符。但帧记录不是硬件规则：手写汇编、被内联的函数、某些叶函数或其他优化情形不能一概套用。简单 fp 回溯也不能穿过 trampoline，把用户栈接成内核调用链。GDB 可借助额外调试信息，能力不等同于这个练习。

### 3.2 分三步建立回溯

1. **只确认起点。** 用题面给出的 `r_fp()` 读取当前帧指针，确认观察的是当前内核执行栈。
2. **只解释一层。** 对照反汇编说明两项保存值分别指向什么；返回地址通常落在调用者调用指令之后，不等于当前函数入口。
3. **再沿链前进。** 每轮打印保存的返回地址，下一轮使用保存的旧 fp。各帧大小不固定，不能通过给 `sp` 或 `fp` 加 16 来遍历。

需要保持的不变量是：**当前读取属于最初那一页内核栈；每次前进沿保存的帧链向较高地址移动；到边界就停止。**

### 3.3 页边界为何容易写错

`procinit()` 为每个进程分配一页内核栈，旁边留有无效的 guard page。以最初位于栈页内部的 fp 求出页边界后，把这一范围固定下来；不要每追到一个新 fp，就重新认定一页新的栈。

- 对本实验的正常调用链，上界可用来终止遍历；不能把到达栈页顶部的 fp 当成下一页的起点继续追。
- `PGROUNDUP(x)` 在 `x` 已经页对齐时返回 `x` 自身，**不会再加一页**。如果你的观察点恰好在边界，必须先认清它属于哪一页／是否已到终止点，不能套“上下取整总相差一页”。
- 解引用前，应确认 `fp - 16`、`fp - 8` 对应的记录仍在选定范围内。不要先读内存、发生异常后才检查边界。
- 判断的是可以按当前规则展开的帧链，而不是“地址还能读就一直读”。越过普通内核 C 调用链，得到的旧 `s0` 未必仍是内核帧。

这足以完成实验中的小型回溯；无需在本题实现跨栈、无帧指针展开器。

### 3.4 从正常路径移到 panic 路径

先在 `sys_sleep` 中验证 `bttest` 输出，再用同次构建的 `kernel/kernel` 做 `addr2line`。这样可以分清“遍历错误”和“符号文件不匹配”。

最后将调用加入 `panic`。固定快照中 `panic` 会关闭 printf 的锁机制，输出 panic 信息，然后设置 `panicked` 并停住；UART 输出遇到 `panicked` 也会停住。**回溯输出必须在冻结输出和无限循环之前完成。** 不要让 backtrace 自己再次调用 panic，形成递归错误路径。

## 4. Alarm 第一阶段：先接通入口，再改变用户返回位置

### 4.1 接口应是一条完整链

从用户声明开始，逐层核对：`user/user.h` → `user/usys.pl` 生成的桩 → 系统调用号 → `kernel/syscall.c` 分发表 → 内核实现。再让 `Makefile` 把 `alarmtest` 放进镜像。只写内核函数而没有接通调用链，用户程序仍无法调用它。

`sigalarm` 的参数一个是间隔，一个是用户函数地址。地址是用户虚拟地址：内核保存它以安排后续用户执行，**不是在 supervisor 模式下直接调用这个 C 函数指针**。

### 4.2 先列每进程状态

| 概念 | 必须回答的问题 |
|---|---|
| 间隔与处理函数地址 | 进程是否启用 alarm？目标用户地址是什么？ |
| tick 进度 | 表示已过去的数量，还是剩余数量？什么时候重新开始？ |
| 处理中标志 | 当前是否有一次尚未通过 `sigreturn` 结束的处理？ |
| 被中断现场 | 保存在哪块独立存储中？什么时候写入，什么时候才可覆盖？ |

这些属于进程状态，不能用一个全局变量替所有进程记账。进程槽会复用，新字段要有明确初始化。若选择动态分配备份，还要配对处理分配失败与释放；若选择内嵌保存空间，则不需要额外分配生命周期。

“是否启用”不能用 handler 地址非零来判断：题面明确允许地址 0。`sigalarm(0, 0)` 关闭未来周期投递，但若调用发生在 handler 内，它不等于“原现场不再需要”；当前 handler 仍需靠 `sigreturn` 回去。

### 4.3 tick 是哪条路径上的计数？

官方把目标描述为进程消耗的 CPU ticks，并给出了 `usertrap()` 中 `which_dev == 2` 的实现提示。按这条路径理解：

- 在**来自用户态的定时器中断**中处理当前进程的 alarm 计数。
- 普通 `ecall`、磁盘／串口中断和异常，不因为也进入 `usertrap` 就算一次 alarm tick。
- 进程没有运行、正在睡眠时，不应随着系统全局 `ticks` 的增加而自动消耗自己的 alarm 额度。`uptime` 或 `sys_sleep` 使用的全局时钟不能替代本题的计数。
- 时钟也会中断内核代码，此时走 `kerneltrap`。原题的提示没有要求把这条路径计入 alarm；不要把本题称作精确统计用户态加内核态全部 CPU 用时的设施。

tick 只提供采样粒度，不承诺“每隔固定多少毫秒墙上时间”就调用一次。进程可能被调度出去，实际回到用户态执行 handler 也可能晚于到期瞬间。

### 4.4 沿返回路径找唯一需要改变的执行目标

在正常路径中，`usertrap` 把 `sepc` 存入 `trapframe->epc`，`usertrapret` 再从该字段准备 `sepc`，最终 `sret` 使用它。对照这条链思考题面的提问：要让下一段用户执行进入 handler，应该影响哪份状态，而不是在哪里直接调用 handler。

这一阶段只要求打印 `alarm!`。原页允许临时让 `sys_sigreturn` 返回零和打印后崩溃；它们都不是最终可交付状态。

## 5. Alarm 第二阶段：原现场必须独立、完整、最后仍然有效

### 5.1 只保存 epc 不够

handler 会执行普通函数调用，也可能发起系统调用；它们会改变寄存器。原用户程序没有主动调用 handler，因此没有为这次“插入执行”保存 caller-saved 状态。

从当前 xv6 的 `trapframe` 出发，至少逐项审视用户 `ra`、`sp`、`gp`、`tp`、`t0–t6`、`s0–s11`、`a0–a7` 与原用户 `epc`。`zero` 恒为零，无需保存可变值。这里讨论本版本使用的整数现场；题面没有要求新增浮点或向量上下文支持。

`context` 只保存内核切换所需子集，不能代替这份用户现场。trapframe 中还有 `kernel_satp`、`kernel_sp`、`kernel_trap`、`kernel_hartid`，它们是内核返回／下次入口的辅助字段，不是用户寄存器；阅读恢复逻辑时也要核对 `usertrapret` 如何重新设置它们，尤其不要把过时的 hart 信息当成用户状态。

### 5.2 备份必须是值的独立副本

handler 执行期间，新的 trap 会继续改写进程当前的 trapframe。只保存 `p->trapframe` 的指针，仍然指向正在变化的那块内存，不能保住中断前现场。

正确的设计必须能说明：

1. 原现场在改变用户执行目标之前已被保留。
2. handler 内后续系统调用不会改写这份备份。
3. handler 尚未结束时，不会用第二次 alarm 覆盖第一份备份。
4. 最终恢复的是同一进程、同一次投递前的现场。

### 5.3 `sigreturn` 不是普通的函数返回

进入 handler 并不意味着原程序曾执行过一次 `call handler`，因此不能靠普通 `ret` 假定存在正确的调用返回点。实验要求 handler 以 `sigreturn` 结束，由内核恢复先前被中断的状态。

还要分清两种 `epc` 变化：

- 普通系统调用陷入时，`epc` 指向 `ecall`，正常路径会推进 4 字节，使它返回到调用后的指令。
- timer 中断保存的是应继续执行的位置，不能照搬 `ecall` 的加 4。
- `sigreturn` 本身也是一次 `ecall`；但完成恢复后，最终应返回原计算的中断位置，而不是 handler 中 `sigreturn` 后面的指令，也不能再给已恢复的原 `epc` 加一次 4。

### 5.4 特别检查 a0：恢复之后还有谁会写它？

固定 2020 `kernel/syscall.c` 的分派逻辑，会在系统调用实现返回后，把它的 C 返回值写入 **`p->trapframe->a0`**。

这意味着：即使 `sys_sigreturn` 内部已经恢复了原 `a0`，普通系统调用的返回值写回仍可能随后将它覆盖。第一阶段“直接返回零”的占位实现不能原样用于最终恢复。

调试时沿调用链问两次：

1. `sys_sigreturn` 完成恢复时，原 `a0` 是否还在？
2. `syscall()` 返回、即将进入 `usertrapret` 时，它是否仍然是同一个 64 位值？

最终不变量是：**恢复路径上最后一次写入之后，用户可见的 `a0` 仍等于中断前的值。** 特别留意内核实现使用的返回值宽度，不能因接口声明中的 `int` 就把需要保存的寄存器内容截断。具体如何安排返回协议，留给你结合分派代码完成。

## 6. Alarm 第三阶段：不重入，而且还能周期触发

用三个状态推演足够，不需要实现完整 Unix signal 子系统：

| 状态 | 发生什么事 | 必须成立的条件 |
|---|---|---|
| 未启用 | `sigalarm` 建立正间隔配置 | 新周期的进度明确，handler 可为地址 0 |
| 等待到期 | 当前用户进程遇到 timer tick | 只有允许投递时才保存原现场并开始 handler |
| handler 正在执行 | 又发生 tick 或普通系统调用 | 不递归进入 handler，不覆盖尚待恢复的现场 |
| handler 正在执行 | `sigreturn` | 恢复原现场并结束处理中状态；按仍有效的配置继续后续周期 |
| 任意已配置状态 | `sigalarm(0, 0)` | 停止未来周期投递；不破坏尚需恢复的现场 |

handler 自己在用户态执行时也可能被 timer 中断。原页明确要求“不重入”和“重新布置计数以周期执行”，但**没有完整规定 handler 执行期间的 tick 是否累计、是否排队补发，以及下一周期的精确相位**。选择与测试相容的简单计数策略，并清楚解释重置点；不要把“必须在 `sigreturn` 才清零”或“必须补发所有过期 alarm”写成官方要求。

`test2` 检查未返回时不能再次调用 handler。与此同时，跳过第二次投递不能跳过正常的 timer 处理和 `yield`：限制的是用户回调重入，不是取消内核调度。

## 7. 分阶段检查与常见症状

以下是供你在实验分支中执行的检查路线，本页没有运行这些测试。

| 阶段 | 观察目标 | 失败时先看哪里 |
|---|---|---|
| 汇编 | `call.asm` 能为六组回答提供证据 | 是否用了实验分支、本次编译结果 |
| 回溯 | `bttest` 输出返回地址，`addr2line` 落在合理调用链 | 偏移单位、页边界、符号文件版本 |
| alarm 入口 | `test0` 打印 `alarm!` | 系统调用是否接通、Makefile、到期条件、返回目标 |
| alarm 恢复 | `test1` 完成而不是崩溃或悄悄退出 | 备份是否独立、寄存器是否完整、`epc`、最后写回的 `a0` |
| alarm 不重入 | `test2` 完成 | 活跃标志是否过早清除、备份是否被覆盖 |
| 回归 | 原版 `alarmtest`、`usertests`、`make grade` | 是否保留调度行为、进程新字段是否初始化、临时占位是否移除 |

原版 `alarmtest.c` 才是验收依据，不要以改过的调试版本替代。具体输出和命令见实验说明；共同记录耗时与提交流程见[公共资料](#/c/mit-6.s081-2020)的「实验的共同验收与提交步骤」。选做题需要解决地址到符号／行号的映射，与基本 fp 链遍历是不同工作，不应为了做必做部分提前实现它。
