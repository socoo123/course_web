# Lab lazy 实验指导

## 1. 把“获准使用”与“已经有物理页”分开

惰性分配改变的是一个旧假设：**`p->sz` 以下不再处处都有物理页。** `sbrk` 成功只表示进程的逻辑地址范围增长；对应的数据页可以等到实际使用时再分配。

| 状态 | 逻辑含义 | 页表可能是什么样 |
|---|---|---|
| 合法、尚未触碰的堆页 | 地址已获准使用，尚无数据页 | 叶 PTE 无效，甚至整段中间页表都不存在 |
| 已实际分配的用户页 | 数据页已存在 | 有效叶项，具有用户及所需访问权限 |
| 栈保护页 | 明确不允许用户访问 | 本次核对的 2020 快照中 V=1、U=0 |
| 申请范围之外 | 没有分配依据 | 不应因为缺页就补成合法内存 |

“没有找到用户可访问的 PA”并不能唯一说明是第一种情况。惰性分配需要结合**地址范围、页表状态与访问类型**判断。

假设编者示例中旧堆顶是 `0x4000`，调用 `sbrk(3 * 4096)` 后新堆顶为 `0x7000`。此时三页都可保持未映射。第一次写 `0x5008`，只需为 `[0x5000, 0x6000)` 补一个数据页；另外两页仍可为空。页表路径缺失时，还要分配管理映射的页表页，它们不能与数据页混为一谈。

页表、`walk` 与直接映射的基础见 [LEC 4 笔记 §4](#/c/mit-6.s081-2020/lec/lec04?v=notes)；教材原有 `sbrk` 与栈布局见 [LEC 4 资料 §3.6–3.8](#/c/mit-6.s081-2020/lec/lec04?v=materials)。

## 2. 先沿调用链找旧假设

| 入口 | 需要理解的路径 | 惰性分配打破的假设 |
|---|---|---|
| 申请堆内存 | `sys_sbrk → growproc → uvmalloc` | 逻辑扩展必须立即准备全部数据页 |
| 用户读写 | `usertrap` | 不能处理的用户异常只能终止进程 |
| 收缩、退出、替换映像 | `uvmdealloc/uvmfree → uvmunmap` | 遍历范围内每页都有映射 |
| 创建子进程 | `fork → uvmcopy` | 父进程范围内每页均可复制 |
| 系统调用数据传递 | `copyin/copyout → walkaddr` | 合法用户缓冲区一定已存在物理页 |

第一阶段只拆掉申请路径上的立即分配，用失败来观察后续依赖。第二阶段让一次真实访问成功，第三阶段才把同一规则带到复制、回收与系统调用。不要以 `echo hi` 成功代替完整验收。

## 3. 一次缺页处理应做什么？

### 看清三个寄存器

| 寄存器 | 本实验中的用途 | 原页样例 |
|---|---|---|
| `scause` | 异常种类：13 为 load page fault，15 为 store/AMO page fault | `0xf` 即 15 |
| `stval` | 引发缺页的虚拟地址 | `0x4008` |
| `sepc` | 发生异常的指令位置 | `0x1258` |

`sepc` 不是待映射地址。用 `stval` 检查访问是否合法，再把地址向下对齐，才得到应映射的页。

### 思路骨架

1. 识别用户 load/store 缺页；保留系统调用、设备中断及其他异常的原有分流。
2. 判断该地址是否属于允许按需补页的范围，排除越界、保护页和已有映射的权限错误。
3. 为对应虚拟页准备一个物理数据页，并将整页清零。
4. 建立到该物理页的用户映射；同时处理页表页分配失败。
5. 成功时沿正常陷阱返回路径继续；失败时让当前进程按既有终止路径退出。

这是一组职责，不是可粘贴的实现。可以把“确保某个合法页已经可用”整理成一个小辅助函数，供缺页和内核复制路径复用；但必须先说清它接收哪张页表、哪份地址范围，以及失败由谁处理。

**不要给缺页分支照搬 `epc += 4`。** `ecall` 返回时跳过的是已经执行的系统调用指令；缺页时访存尚未完成，映射建立后应重新执行原指令。否则读写被跳过，程序可能悄悄算错。

还要检查返回用户态时切换页表与 `sfence.vma` 的配合。写入 PTE 和让硬件使用新翻译是两件事；不要绕开既有的陷阱返回流程。

### 地址与权限的边界

- **先检查原始地址，再考虑对齐。** 若 `sz=0x5001`，故障地址 `0x5fff` 虽与最后一个合法字节同页，但该地址本身已超出逻辑范围。只比较 `PGROUNDDOWN(va)` 与 `sz` 会误放行。
- **上界不包含在范围内。** `va == p->sz` 已不属于当前申请范围。超出 xv6 可处理范围的地址也应在调用可能 panic 的 `walk` 前排除；不能把 trampoline、trapframe 等保留映射当作堆扩展。
- **`va < sz` 仍不充分。** 用户栈保护页也在进程地址空间大小之内；本版通过 `uvmclear` 清 U，故 V=1、U=0 的页必须继续禁止用户访问。
- **不要把权限错误当作缺少内存。** 已映射页若不允许相应访问，不应重新映射或提升权限。这也避免 `mappages` 的 `remap` panic。
- **不要把当前 `sp` 当作整个地址空间的下界。** 合法代码、数据也可能位于 `sp` 以下；应根据地址空间布局和 PTE 区分栈保护与合法内存，而非笼统禁止所有低地址访问。

页粒度有一个实际限制：最后一页一旦映射，CPU 不知道字节级 `sz`，页内超过堆顶的访问未必再次缺页。上面的原始地址检查针对**进入缺页处理器的访问**，不能被描述成完整的字节级内存保护。

本次核对的普通 2020 参考 `uvmalloc` 使用 R/W/X/U；这与新版本细分代码、数据权限的实现不同。本实验要求处理 13/15，不等于要求把取指缺页 12 也当作惰性堆分配。设置新页权限时，应明确自己的设计与实验起始代码，不要无意中扩大既有映射权限。

## 4. 稀疏页表怎样回收？

原来的 `uvmunmap` 把“没有 PTE 路径”和“有 PTE 槽位但 V=0”都当作错误。惰性分配后，这两种情况都可能只是合法空洞：

- 从未触碰过的大段地址，连下层页表都没有。
- 某段下层页表因相邻页被使用而存在，但当前叶项仍为空。

回收时只处理确实存在的数据页；不要为了释放未分配页反而创建页表或数据页。允许空洞不意味着删除全部检查：页对齐、叶项结构、重复释放等错误仍应能被发现。释放数据页后清除对应映射，最后再让原有页表树回收流程释放页表页。

### 负数 sbrk

最终版不能只让 `sz` 减少而留下全部旧映射。收缩时应取消已经不在范围内的整页映射，并释放实际存在的物理页；未分配的空洞直接略过。

以编者示例说明页边界：从 `oldsz=0x6500` 缩到 `newsz=0x5200`，包含 `0x5200` 的 `0x5000` 页仍有合法字节，应保留；`0x6000` 页若已分配，则应释放。可以沿 `uvmdealloc` 的 `PGROUNDUP` 边界推导这个结果，而不是向下取整后误释放最后一页。

`sbrk(0)` 应继续返回当前堆顶。正负增量与无符号大小混合计算时，要避免下溢或回绕把小范围变成巨大范围；失败后应保留原来的逻辑大小。这里只需维护正确边界，不必引入新的通用虚拟内存框架。

## 5. fork 复制什么，保留什么？

`fork` 的语义仍是：子进程观察到与父进程相同的初始内容，之后各自写入互不干扰。

| 父进程页的情况 | 子进程应保留的性质 |
|---|---|
| 已分配的普通用户页 | 内容相同，拥有独立物理页，权限按原映射保留 |
| 合法但未分配的空洞 | 逻辑范围仍有效，暂时无需物理页 |
| 已存在的用户栈保护页 | 保留其禁止用户访问的属性，不能误变成可补的普通空洞 |

因此 `uvmcopy` 要理解空洞，而子进程的 `sz` 仍要继承父进程的逻辑大小。之后父子若分别首次触碰同一个空洞，各自得到独立的清零页。

不要把所有 `!PTE_U` 页直接当作空洞：保护页虽不可被用户读写，仍是有效映射。也不要直接让父子共享普通可写物理页；本实验不是 COW 实验。

复制中途失败时，回滚路径同样面对稀疏区间。检查已经建立的子进程映射是否被释放，空洞是否被安全跳过，避免只有正常退出能用、失败清理却 panic。

## 6. 为什么只改 usertrap 还不够？

考虑用户程序申请一页后，**完全不碰它**，立即将该地址传给 `read`。首次写入缓冲区的是内核，未必有用户态 load/store 触发 `usertrap`。

| 调用意图 | 数据方向 | 典型复制函数 |
|---|---|---|
| `read(fd, buf, n)` | 内核把读取结果写入用户缓冲区 | `copyout` |
| `write(fd, buf, n)` | 内核读取用户缓冲区，交给文件或设备 | `copyin` |

普通 xv6 的这些函数是**软件查用户页表，再通过内核直接映射访问 PA**。`walkaddr` 失败会返回 0，复制函数返回错误；这条路径不会自动变成一次用户缺页。所以应在适当的复制路径中处理合法的尚未分配页，成功补页后重新取得 PA，再继续复制。

注意四个约束：

1. `walkaddr == 0` 也可能表示保护页或非法地址，不能无条件分配。
2. 缓冲区可以跨页；每一页都必须正确处理，不能只补起始页。
3. 复制函数接收的是显式 `pagetable` 参数，不保证总是 `myproc()->pagetable`。例如 `exec` 会向尚未替换当前映像的新页表写入参数。若引入补页逻辑，必须保持页表与所属地址范围匹配；不要拿旧进程的 `sz` 去解释所有新页表。
4. 数据复制失败应沿调用链传播错误；不要把低层复制函数写成在任意调用环境都直接 `exit`。官方明确要求的是缺页处理器中 `kalloc` 失败要终止当前进程。

`copyinstr` 另负责以零结尾的字符串；梳理调用路径时也应理解它与按长度复制的差别。原页没有将修改它单列为一个额外评分任务，这里也不虚构这一要求。

### 选做：简化 copyin 的额外难点

若采用 pgtbl 实验中“内核页表也映射用户内存，再直接复制”的方案，用户页表补齐并不保证内核使用的对应映射同步存在。需要考虑映射建立、缩小与释放的一致性，以及复制发生时使用的页表。

此时直接解引用用户地址可能在内核态 fault，处理路径与普通软件 `walkaddr` 不同。先说明你准备在哪里确保映射就绪，再决定怎样复用补页逻辑；不要把所有内核缺页都解释成用户堆申请。

## 7. 内存耗尽不只发生在 kalloc 数据页时

一次按需映射可能消耗一个数据页及若干页表页。因此需分别考虑：

- 数据页分配失败：缺页路径终止当前进程，不能继续 `memset` 空指针。
- 数据页成功，但 `mappages` 为页表路径分配内存失败：尚未交给有效映射的数据页由失败路径释放，并报告失败。
- `fork` 中途失败：释放已建的子进程数据映射及页表结构，父进程仍可正常使用自己的页。
- 进程被终止后的清理：地址范围可能很大且很稀疏，必须能回收已有页，略过空洞。

物理页必须在暴露给用户前清零。`kalloc` 返回的页不是“天然零页”；遗漏清零既破坏首次读取应有的内容，也可能暴露旧数据。

## 8. 按现象定位，而不是不断加例外

| 现象 | 优先检查 |
|---|---|
| `echo hi` 首次访问就退出 | 13/15 分流、`stval` 地址判断、分配与映射是否成功 |
| 返回后同一指令反复缺页 | 页表是否是该进程的，VA 是否对齐，权限及返回路径是否正确 |
| `panic: remap` | 是否把已有保护映射或权限故障当成空洞 |
| `uvmunmap: walk` / `not mapped` | 是否同时处理缺失中间路径与无效叶项 |
| `uvmcopy: pte should exist` / `page not present` | `fork` 是否仍假定逻辑范围处处有页 |
| `read/write` 对新缓冲区失败 | 是否只处理了用户异常，遗漏软件复制路径 |
| 收缩后数据异常或重复释放 | 最后一页的取整、PTE 清除、数据页所有权 |
| 耗尽内存时内核 panic | 分配失败、映射失败和退出清理是否均有正确路径 |

这些诊断字符串中，第一阶段报错来自官方原页，其余函数断言来自已读的固定 2020 参考源码；实际 lazy 分支日志以自己的构建为准。

动手验收顺序见[实验说明](#/c/mit-6.s081-2020/lab/lazy?v=zh)：阶段一观察失败，阶段二使 `echo hi` 工作，最终运行 `lazytests`、`usertests`，再按[公共资料](#/c/mit-6.s081-2020)执行 `make grade`。这里没有把任何一项标作已运行或通过。

## 自测

<details><summary>申请三页但只使用中间一页，退出时应释放几个数据页？</summary>

仅就这次申请的三页而言，释放实际建立的一个数据页；另外两页没有可释放的数据内存。页表管理页另由页表回收流程处理，进程其他已有页面也另计。

</details>

<details><summary>栈保护页在 sz 以下，walkaddr 返回 0，能补成用户可写页吗？</summary>

不能。该返回值无法区分空洞与禁止用户访问的映射。本版保护页 V=1、U=0；为它增加用户权限会破坏保护，也可能撞上 remap。

</details>

<details><summary>为什么缺页返回不增加 epc，而 ecall 返回要增加？</summary>

缺页导致原访存尚未完成，需要重新执行；ecall 已进入系统调用并完成对应服务，返回应继续下一条指令。

</details>

<details><summary>fork 后子进程先写入父进程从未触碰的堆页，父进程后来读到什么？</summary>

父进程自己的对应页仍可保持空洞；它第一次读取时获得独立的清零页，不能读到子进程刚写入的值。子进程继承的是逻辑可用范围，不是提前存在的共享可写数据页。

</details>

<details><summary>新缓冲区跨两页，第一页已映射，第二页没有，read 会自动触发 usertrap 吗？</summary>

普通软件复制路径不会因 walkaddr 失败自动进入 usertrap。copyout 必须能在逐页复制时识别第二页的合法空洞、准备映射，再继续；非法第二页则应传播失败。

</details>

<details><summary>kalloc 成功，是否足以保证本次缺页一定修复？</summary>

不够。建立映射可能还需要页表页并失败；必须释放尚未映射的数据页并处理失败。原始故障也可能是权限错误，根本不应开始分配。

</details>

<details><summary>负数 sbrk 后最后一页仍有几个合法字节，是否应释放整页？</summary>

不应。保留仍包含合法范围的最后一页，只移除完全退出范围的页；这也是 uvmdealloc 使用向上取整边界的原因。

</details>
