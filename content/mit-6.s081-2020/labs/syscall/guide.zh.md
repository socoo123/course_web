# 系统调用实验指导

本实验要打通两条路径：**用户请求怎样进入内核，内核结果怎样回到用户空间。** `trace` 练习每进程状态与系统调用分派；`sysinfo` 练习跨模块统计与用户地址复制。

先阅读[实验说明](#/c/mit-6.s081-2020/lab/syscall?v=zh)中的官方要求。以下是**编者建议与机制推导**，不增加官方必做任务；不提供完整补丁或可直接提交的答案。

## 1. 先认清每一层的职责

用户程序调用一个系统调用时，路径可简记为：

```text
用户 C 调用 → 用户汇编桩（a7 放调用号，ecall）
           → 陷阱入口 → usertrap → syscall → sys_处理函数
           → 返回值写入 trapframe 的 a0 → 返回用户空间
```

这是正常返回路径的概括，`ecall` 并不自动完成换栈、切页表和保存全部通用寄存器。`usertrap()` 识别用户态 `ecall` 后调用 `syscall()`，后者用保存的 `a7` 查分派表。`a0` 在进入时可能是第一个参数，返回时则是结果。

| 层次 | 需要查阅的位置 | 能解决什么问题 |
|---|---|---|
| 用户接口 | `user/user.h` | C 编译器知道函数声明吗？ |
| 用户桩生成 | `user/usys.pl` | 有对应汇编符号吗？桩传了哪个调用号？ |
| 编号约定 | `kernel/syscall.h` | 用户侧和内核侧用的是同一个编号吗？ |
| 内核分派 | `kernel/syscall.c` | 有处理函数声明、表项和正确的参数读取吗？ |
| 具体服务 | `kernel/sysproc.c` 及各子系统 | 真正执行操作、统计数据、返回错误的是谁？ |
| 镜像中的程序 | `Makefile` 的 `UPROGS` | xv6 文件系统里能找到测试程序吗？ |

**原型、桩、分派表和处理函数是四件不同的事。** 仅加原型只能解决一部分编译问题；仅实现内核函数，也不会让用户请求自动找到它。`user/usys.S` 是生成文件，持久修改应放在 `user/usys.pl`。

机制背景可读 [LEC 3 课程资料](#/c/mit-6.s081-2020/lec/lec03?v=materials) §2.2、§2.5；完整陷阱细节按实验指定的 rev1 §4.3–4.4 阅读。

## 2. trace：先定义不变量，再选修改位置

### 掩码是位集合，不是一个调用号

若系统调用号为 $n$，它是否被追踪取决于 **mask 的第 $n$ 位**。`SYS_read = 5`，因此只追踪 read 的掩码是 $2^5=32$；`SYS_fork = 1`，只追踪 fork 的掩码是 2。同时选择多个调用，要组合对应的位。

常见错误包括把 `mask` 当调用号比较，或只判断右移后的值是否非零。后者会把更高位的 1 误认为目标位被选中。先在纸上用“仅第 5 位为 1，询问第 4 位”的例子验证判定逻辑。

### 状态属于进程，并有生命周期

可以把需要维持的关系列成四行：

| 时刻 | 应成立的关系 |
|---|---|
| 尚未启用追踪 | 当前进程不产生追踪输出 |
| 当前进程调用 `trace(mask)` | 更新当前进程自己的掩码，不改全局配置 |
| `fork` 创建子进程 | 子进程得到创建时父进程掩码的副本 |
| 同一进程执行 `exec` | 新程序仍受追踪，才能得到官方 `trace ... grep ...` 的效果 |

父子持有的是**各自的值**。子进程以后更改自己的掩码，不应回写父进程。父进程也不应在后来调用 `trace` 时，自动修改已经存在的孩子。后代继续 fork 时再次复制，才形成原页要求的继承链。

阅读 `allocproc()`、`freeproc()` 与 `fork()`，决定新字段的初始化、复用和复制位置。`proc` 表槽位会重复使用；不要只依赖系统启动时全局内存为零。继承应在子进程可以运行之前完成，同时保留现有分配失败的清理路径。

### 为什么把打印放在公共分派路径？

如果每个 `sys_read`、`sys_open` 等处理函数各写一次打印，很容易漏调用，也会把格式散落到各模块。`syscall()` 已经掌握调用号、当前进程和返回值，是官方指定的集中修改位置。

思路骨架是：**确认有效调用 → 执行处理函数 → 保存其返回值 → 按当前掩码决定是否输出。** 这里有三个关键点：

1. 输出过早，`a0` 还是输入参数，不是最终返回值。
2. `trace` 本身也可能被追踪。官方全掩码样例第一行就是 `syscall trace -> 0`，因此本次调用设置的新掩码要能影响这次返回时的判断。
3. 名称表按调用号对应，并和分派表保持一致。保留原本的有效编号检查，不要对未经检查的编号做数组访问或移位。

`printf` 是内核函数时，不是再发起一个用户 `write` 系统调用，不会因此递归进入本实验的系统调用追踪。

### 两个容易误读的样例细节

- **`exec -> 3` 不表示 exec 失败。** 固定 2020 源码的内核 `exec()` 成功时返回 `argc`，它经 `a0` 送入新程序。`grep hello README` 有三个参数，包括程序名。成功后不回到原用户程序的 `exec` 下一行，但内核处理函数仍会回到分派路径。
- **不要凭空补出子进程的 `fork -> 0` 或正常的 `exit` 返回行。** 固定快照中，新子进程经 `forkret()` 首次返回用户空间，不重新经过父进程那次 `syscall()` 的返回位置；`exit()` 则不返回。原页 fork 样例追踪的是各后代自己发起 fork 时的父侧返回值。

返回值显示还要与 xv6 内核 `printf` 的格式能力、用户接口的有符号返回语义一致；尤其失败的 `-1` 不应被当作正常的正数结果解释。

## 3. sysinfo：统计和复制是两项职责

用户传进来的是一个**用户虚拟地址数值**。内核先在自己的局部 `struct sysinfo` 中收集结果，再借助当前进程页表复制到用户目标地址；不能把传入值强转成内核指针直接写字段。

### freemem：数空闲页，返回字节数

固定 2020 分配器的 `kmem.freelist` 把空闲物理页串成链表，每个节点代表一整页。因此，统计思路是：

$$
\text{freemem}=\text{空闲链表节点数}\times\text{PGSIZE}.
$$

在本版普通页大小下 `PGSIZE = 4096`。不要乘 `sizeof(struct run)`；链表节点只是放在空闲页起始处的管理信息，不是可分配容量。也不要用 `PHYSTOP - end` 作为运行时空闲量——那反映初始化可供管理的范围，没有扣除已经分配出去的页。

`kalloc()` 和 `kfree()` 修改链表时使用 `kmem.lock`；统计遍历也应遵守同一保护约定。若不加锁，另一颗 CPU 可能刚把当前节点取走并覆盖其内容，你继续读 `next` 就不再是在读合法链表。只观察链表，不通过反复分配、释放来“测量剩余量”。

把统计函数放在 `kernel/kalloc.c`，通过内核函数声明供调用者使用，比把链表内部布局暴露给 `sysproc.c` 更贴合官方提示。计数结果的类型应和实验分支 `struct sysinfo` 的字段类型匹配。

详细分配器背景见 [LEC 4 课程资料](#/c/mit-6.s081-2020/lec/lec04?v=materials) §3.4–3.5。

### nproc：按 state，不按“正在用 CPU”

官方定义是 **`state != UNUSED`**。这意味着睡眠、可运行、正在运行及尚未回收的僵尸进程都应被计入；不能只数 `RUNNING`，也不能用 `pid != 0` 替代原要求。

统计遍历 `proc` 表，由 `kernel/proc.c` 提供函数。`proc.h` 已注明使用 `state` 时需要持有该进程的锁：检查一个表项时锁住它，读完后释放，再访问下一项。不需要把所有进程锁同时持有。

固定参考快照的状态枚举没有新版常见的 `USED`；不要据此硬编码一份“允许计入的状态白名单”。按照实验分支实际的 `state != UNUSED` 判断即可。

### copyout：拿到地址不等于验证了内存

固定 2020 `argaddr()` 取得指针参数数值，但不验证目标内存；地址转换与检查发生在 `copyout()` 及其调用的 `walkaddr()` 中。参照官方提示的 `sys_fstat()` → `filestat()`，按以下职责组织：

1. 提取用户目标地址，注意地址宽度，不能用 32 位整数截断。
2. 在内核局部结构中填好两个统计值。
3. 统计结束后释放相关锁，再复制整个结构到调用者的用户页表所描述的地址空间。
4. 检查复制结果；失败不能报告成功。按现有内核接口习惯，成功返回 0，失败返回 -1。

检查复制长度是否是**结构本身的大小**，不是指针大小。`copyout` 会按页分段，因此跨页缓冲区不能用“只验证起始地址”替代完整复制。

该固定快照的 `walkaddr` 检查地址上界、映射有效位和用户位，没有额外检查 `PTE_W`。不要把新版行为或“完整验证任意 C 指针”的承诺套到这里。跨页复制也不保证失败时撤销已复制的前半段；这不是要求你为本实验添加事务机制。

两项统计各自受其数据结构的锁保护，并不因此构成全系统某一时刻的原子快照。官方没有要求同时冻结全部进程和内存分配器。

## 4. 分层定位问题

| 现象 | 优先检查 |
|---|---|
| `trace.c` 或 `sysinfotest.c` 编译失败 | 用户原型、结构前置声明、包含关系 |
| 链接时缺系统调用符号 | `usys.pl` 是否生成对应桩 |
| xv6 找不到用户测试程序 | `UPROGS`、是否重新生成镜像 |
| 内核输出 unknown sys call | 调用号、分派表、处理函数是否接齐 |
| 所有进程都被追踪 | 是否把掩码错放在全局变量中 |
| 当前程序能追踪，后代不能 | `fork` 的继承时机与字段复制 |
| 掩码为 read，却输出其他调用 | 位检查是否只保留了目标位 |
| 返回值看起来像参数 | 打印是否发生在处理函数返回之前 |
| 空闲量差 4096 倍 | 返回的是页数还是字节数 |
| 进程数偏小 | 是否漏计 SLEEPING、RUNNABLE 或 ZOMBIE |
| 传入不合法缓冲区导致内核异常 | 是否直接解引用用户地址、是否检查 `copyout` 结果 |

## 5. 验收边界与自测

**官方验收：** 先核对实验说明中的四组 `trace` 场景，再运行 `sysinfotest`，确认打印 `sysinfotest: OK`，最后完成全部 `make grade` 测试。命令输入位置要分清：`trace`、`grep`、`usertests`、`sysinfotest` 在 xv6 shell 内运行；`make qemu`、`make grade` 在宿主机实验目录运行。通用收尾见[公共资料 →「实验的共同验收与提交步骤」](#/c/mit-6.s081-2020)。

**编者建议的边界检查**如下；这些不是对未读取评分脚本的描述，也不必为了本指导另建一套庞大测试：

- `trace` 掩码为 0 时不输出；只设置某一位时不误选更低位；开启追踪后，未追踪的 shell/独立进程不受影响。
- 子进程继承后自行修改掩码，不影响父进程；`exec` 后追踪继续；表槽复用不残留旧状态。
- `sysinfo` 使用合法结构缓冲区时成功；目标完全未映射，或结构跨到未映射的下一页时，应让复制错误返回用户态，而不是使内核崩溃。两页均有合法用户映射的跨页目标，应能完整复制。
- 观察分配和释放物理页前后的空闲量，以及 fork、退出、wait 回收前后的进程计数。同步父子后再比较，不要把调度瞬间的变化误判为计数错误。页表等额外分配也会影响 `freemem`，不能无条件断言任意 `sbrk(PGSIZE)` 都恰好减少一页。

<details><summary>为什么不把 trace 掩码保存在用户空间的全局变量中？</summary>

内核分派需要可靠的每进程状态；用户变量既不是内核的 `proc` 字段，也会随 exec 的用户映像替换而消失。实验要求通过系统调用设置内核维护的状态。

</details>

<details><summary>为什么 trace 自身能出现在新启用的追踪输出中？</summary>

处理函数先保存新的掩码，公共分派路径在它返回后再检查当前掩码；若包含 trace 对应位，就能输出这次调用的返回值。

</details>

<details><summary>进程已 exit，但父进程还没 wait，nproc 应不应该包含它？</summary>

如果其状态仍为 ZOMBIE，就要包含。官方统计标准是非 UNUSED，而不是“还在执行用户指令”。

</details>

<details><summary>为什么只拿到 sysinfo 的地址还不够？</summary>

地址参数只是数值。它是否映射到用户可访问页、整个结构范围能否复制，需要依靠用户页表和 copyout；起始地址合法也不能推出下一页合法。

</details>
