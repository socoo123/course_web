# 文件系统实验指导

本实验的两个核心问题是：**固定大小的 inode 怎样指向更大的文件？一个保存路径的文件怎样在 open 时变成另一个文件？** 前者改变“文件块号到磁盘块号”的映射，后者改变“路径到最终打开对象”的过程。

本页以下均为**编者指导**；官方任务、完整提示和验收输出见[实验说明](#/c/mit-6.s081-2020/lab/fs?v=zh)。

## 1. 先认清四种对象

| 对象 | 保存什么 | 本实验关心什么 |
|---|---|---|
| 目录项 `struct dirent` | 名字、inode 编号 | `path` 在目录中指向哪个 inode |
| 磁盘 inode `struct dinode` | 类型、长度、链接数、块地址 | 不增大结构，重新分配 13 个地址槽的职责 |
| 内存 inode `struct inode` | 磁盘字段的副本，加锁、引用数等 | 地址数组要与磁盘格式匹配；持锁读写内容 |
| 块缓存 `struct buf` | 某个磁盘块的内存副本 | 间接块也是磁盘块；修改须纳入日志，使用后须释放 |

文件描述符又是另一层：`struct file` 保存打开模式、当前偏移以及 inode 引用。跟随符号链接时，应先确定最终 inode，再把它交给原有的打开文件逻辑。

### 建议的代码阅读顺序

1. `kernel/fs.h`、`kernel/file.h`：磁盘与内存 inode，`BSIZE`、`NDIRECT`、`NINDIRECT`、`MAXFILE`。
2. `kernel/fs.c`：`bmap` → `readi` / `writei` → `itrunc`；再看 `balloc` / `bfree`、`iupdate`。
3. `kernel/sysfile.c`：`create`、`sys_open`、`sys_link`、`sys_unlink`；回到 `fs.c` 看 `namei` / `nameiparent`。
4. 遇到资源释放或日志疑问时，看 `bio.c` 的 `bread` / `brelse`、`log.c` 的 `begin_op` / `end_op` / `log_write`。

教材阅读定位：§8.10 解释文件内容映射，§8.8–8.9 解释 inode 与引用，§8.11–8.14 解释目录、路径和系统调用，§8.4–8.6 解释日志。原书第 8 章仍是官方完整前置阅读要求；这里的路线只是针对本实验的阅读抓手。教材入口见[公共资料](#/c/mit-6.s081-2020)，LEC 14–15 尚未制作，不把它们当作已有中文阅读材料。

## 2. 大文件：地址槽数量不变，层数增加

原结构有 13 个地址槽：12 个直接地址，加 1 个一级间接地址。现在仍只有 13 个槽，但改成 11 个直接地址、1 个一级间接地址和 1 个二级间接地址。

```text
inode 的 addrs[0..10] ───────────────────→ 数据块
         addrs[11] ─→ 一级地址表 ─────────→ 数据块
         addrs[12] ─→ 二级地址表 ─→ 一级地址表 ─→ 数据块
```

这是编者依据官方布局要求绘制的文字示意。地址表中的项是磁盘块号，不是指向内存的 C 指针。二级地址表里的每一项指向一张一级地址表，不能直接把它当作数据块来读写。

### 为什么是 65803，而不是 65804？

一个块为 1024 字节，一个块号为 4 字节，因此一张地址表有 `1024 / 4 = 256` 项。三个区域分别覆盖：

| 区域 | 容量（数据块数） | 从 0 开始的逻辑块号 |
|---|---:|---|
| 直接区域 | 11 | 0–10 |
| 一级间接区域 | 256 | 11–266 |
| 二级间接区域 | 256 × 256 | 267–65802 |

总数为 `11 + 256 + 65536 = 65803`；最后一个合法块号是 **65802**。最大文件内容为 `65803 * 1024` 字节，地址表块本身占磁盘空间，却不计入文件内容长度。

`MAXFILE` 的单位是**块**；`ip->size` 的单位是**字节**。扩大文件系统总容量 `FSSIZE`，并不会自动扩大 `MAXFILE`，反过来也一样。

### 二级下标怎么拆？

先判断逻辑块落在哪个区域。落入二级区域后，减去前两个区域覆盖的块数，得到相对于二级区域开头的编号 `r`。接着问两个问题：

- 它属于第几组 256 个数据块？用整除决定二级表的槽位。
- 它是该组内第几个数据块？用余数决定一级表的槽位。

先在纸上验算 `r = 0、255、256`：它们应依次落到第一组首项、第一组末项、第二组首项。还要检查整个文件的块号 10/11、266/267、65802/65803。把“文件中的编号”和“二级区域内部的编号”写成不同变量含义，能避免反复减偏移造成的错位。

## 3. 分配、持久化、释放必须配套

### 按需分配一条路径

写入二级区域的一个数据块时，沿映射路径逐层检查：二级根块是否存在？对应的一级表是否存在？最终的数据块是否存在？只补齐当前访问路径上缺少的部分。

一开始就分配 256 张一级表，既浪费空间，也违背官方“按需分配”的提示。反过来，每次调用都分配新表会丢掉旧映射：已有非零块号应当复用。

### 修改在哪里，日志就记在哪里

| 修改对象 | 应追踪的持久化路径 |
|---|---|
| `ip->addrs[]` 的地址槽 | 内存 inode 的修改最终由 `iupdate` 写入磁盘 inode |
| 某个地址表块中的项 | 修改相应 `buf` 后用 `log_write` 登记该块 |
| 新块的占用位与初始化内容 | 沿已有 `balloc` 路径处理，不自行绕开位图和日志 |

`brelse` 是释放缓冲区锁和引用，**不等于把修改登记进日志**。一级表和二级表是两个不同的缓冲区：改了哪一张，就应审视哪一张需要 `log_write`。把二级表地址、一级表地址、最终数据地址混放在一个不断覆盖的变量中，很容易把日志记错对象。

`bread` 返回持锁的缓冲区。安排好每次 `bread` 对应的 `brelse`，包括已有块直接返回的路径；不要释放缓冲区后继续把其 `data` 当作自己独占的地址表使用。已有 `bmap` 位于调用者的文件系统操作与 inode 锁范围中，应沿用这套调用关系。

### itrunc 是映射树的逆过程

把二级结构看成树，释放时要先处理子节点，再处理保存子节点地址的表：

1. 遍历实际存在的一级表，释放其中实际分配的数据块。
2. 用完一张一级表后释放它的缓存引用，并释放这张表占据的磁盘块。
3. 全部子表处理完后，释放二级根表。
4. 清理 inode 的地址槽、长度，并保持原来的 inode 更新路径。

这里有两个不同的“释放”：`brelse` 结束对缓存的使用；`bfree` 把磁盘块归还空闲位图。只做前者会泄漏磁盘空间，只做后者会留下缓存锁或引用。

不要借助会分配块的 `bmap` 去枚举本不存在的分支。一个只写了一部分的文件也必须能正常截断；遇到零项就说明相应子树不存在。

### 格式变了，旧镜像不能继续当作新格式使用

即使 `sizeof(struct dinode)` 没变，地址槽的含义也变了。内核和 `mkfs` 必须使用同一布局，内存与磁盘的 `addrs[]` 都要保持 13 项。若只将 `NDIRECT` 改成 11，而让某个数组仍写成 `NDIRECT + 1`，数组就会少一项。

按实验说明重建 `fs.img` 后再测，避免旧镜像中的第 12 个直接地址被新内核误认为一级地址表。重建镜像会重置 xv6 内的文件，这是该步骤本来的效果。

## 4. 符号链接：创建名字与解析目标是两件事

设普通文件为 `a`，符号链接为 `s`，其内容表示路径 `a`：

```text
目录项 s → 符号链接 inode → 路径字符串 "a"
                                  ↓ open 时再次查找
目录项 a → 普通文件 inode → 文件内容
```

硬链接则是两个目录项直接指向同一个 inode。创建符号链接不应给目标 inode 增加硬链接计数；目标甚至可能尚不存在。

先把以下行为写成自己的检查表：

| 操作 | 本实验要求的对象与结果 |
|---|---|
| `symlink("a", "s")` | 在 `s` 创建新的符号链接，保存目标路径 `a` |
| `a` 暂不存在时创建 `s` | 允许成功；创建时不要求解析目标 |
| 普通 `open("s", ...)` | 跟随链接；最终目标不存在则失败 |
| 带 `O_NOFOLLOW` 打开 `s` | 打开 `s` 的符号链接 inode 本身 |
| `s → t → a` | 连续跟随，直到普通目标或错误 |
| `s → t → s` | 以错误结束，不能无限跟随 |
| `unlink("s")` | 删除 `s` 这个名字，不删除目标 `a` |
| `link("s", "u")` | 为符号链接 inode 增加硬链接名字，不跟随到 `a` |

目录符号链接不在任务范围内。官方也没有在本页完整规定各种 Unix 路径边界语义；不要把宿主系统 man 手册里的全部行为自行升级为本实验的评分要求。

## 5. symlink 的实现骨架

### 先打通系统调用入口

新调用号、用户头文件声明、`user/usys.pl` 的生成入口、内核处理函数必须一致。还要检查 `kernel/syscall.c` 的处理函数声明和分发表：只有 `sys_symlink` 函数体，并不意味着系统调用号已经能分派到它。无需手改自动生成的 `user/usys.S`。

`T_SYMLINK` 是文件类型；`O_NOFOLLOW` 是打开方式的位标志。这两者处在不同的命名空间。检查当前分支已有标志，选择未使用的位，并用位运算判断它是否出现。不要用“整个 `omode` 是否恰好等于 `O_NOFOLLOW`”替代检查，因为它可以和读写模式组合。

### 创建过程只负责保存目标字符串

可沿现有 `sys_mkdir` / `create` 的结构思考：

1. 取出两个路径参数，明确哪个是新名字，哪个是要保存的内容。
2. 在文件系统操作的日志范围内创建新类型 inode。
3. 将目标路径写入选定的存储位置，检查写入结果。
4. 释放 inode 锁与引用，结束操作，返回成功或失败。

这是工作顺序，不是完整实现。需要自行决定目标字符串的磁盘编码：是否保存结尾 NUL，还是依赖 inode 长度？选哪种都要让写入方和读取方一致，并保证读入内核缓冲区后有合法的字符串终止位置。把路径读到内核缓冲区再传给 `readi` / `writei` 时，要核对“用户地址还是内核地址”的参数含义。

`create` 成功返回的 inode **已经持锁**，`namei` 返回的 inode **没有持锁**；二者不能照抄同一套上锁步骤。每条失败分支也要明确当前持有什么资源。

日志的崩溃原子性不等于 C 函数返回 -1 时会自动撤销前面所有修改。尤其是创建成功但目标写入失败的情况，要检查自己留下了什么状态；`end_op` 本身不是回滚函数。

## 6. open：逐次跟随，每次只管理当前对象

在原有 `open` 找到并锁住 inode 后，思考一个有界的跟随过程：

1. 当前不是符号链接，或本次带有 `O_NOFOLLOW`，就不再跟随。
2. 否则读取并检查当前链接保存的路径。
3. 结束对旧链接 inode 的使用，再查找并锁住下一个目标。
4. 目标不存在或达到跟随深度上限，走错误清理；否则继续检查当前对象。
5. 取得最终 inode 后，再衔接原有设备检查、文件对象与 fd 分配、读写模式设置，以及适用的截断处理。

“递归跟随”描述的是语义，不要求用 C 递归。循环加计数器同样可以表达链接链；深度上限是环检测的近似，因此过长但没有环的链也可能被拒绝，这正是官方允许的取舍。

### 为什么必须先放下旧锁？

如果 `s` 指向自身，拿着 `s` 的 inode 锁又尝试锁住查找到的 `s`，会在第二次加锁时死锁，甚至还没来得及执行下一轮深度检查。更长的环也有同类问题。把目标字符串复制出来后，明确交接旧 inode 的锁与引用，不让跟随过程积累一串 inode 锁。

inode 的三个量不要混淆：

- 锁保护当下对内容的访问。
- `ref` 保护内存 inode 引用的生命周期。
- `nlink` 记录有多少目录项指向这个 inode。

仅 `iunlock` 不会释放引用；对未持锁的对象调用 `iunlockput` 也不正确。可在纸上为每个返回路径标注“无 inode／有引用未锁／有引用已锁”，再检查是否恰好释放一次。

### 为什么不要直接让所有 namei 都跟随？

因为 `link`、`unlink` 等调用必须操作符号链接本身。把跟随语义无条件塞进共享的路径查找函数，可能让 `open` 看似成功，却改变了其他系统调用的对象。按任务要求，把新增行为约束在需要它的调用路径中。

## 7. 用现象定位问题

下表是编者排错建议，不是已取得的评分器测试清单。

| 现象 | 优先检查 |
|---|---|
| 文件仍只能写到原来的长度 | `MAXFILE`、`writei` 上限、是否运行了新内核和正确分支 |
| 在 11、267 等边界附近出错 | 区域起点、偏移是否重复扣减、地址槽位置 |
| 二级区域第 256/257 个数据块交界出错 | 商与余数是否用反，是否仍误用第一张子表 |
| 大文件能写，读取却错位 | 返回的是数据块号还是某一级地址表的块号；旧镜像是否重建 |
| 删除后再建大文件，越来越早耗尽空间 | `itrunc` 是否回收所有叶子和两级地址表，是否清零 inode 地址 |
| `bget: no buffers` 或逐渐卡住 | `bread` / `brelse` 是否配对、是否有缓冲区锁泄漏 |
| 创建悬空符号链接失败 | 是否错误地在 `symlink` 内要求 `target` 已存在 |
| `O_NOFOLLOW` 无效 | 新位是否冲突；是否把组合标志当作相等值比较 |
| 自环测试挂住而不是报错 | 是否带着旧 inode 锁再次锁同一 inode；深度计数是否推进 |
| 普通测试通过，并发测试失败 | inode 锁、引用、日志范围和失败清理是否沿用现有协议 |
| 删除符号链接影响了目标文件 | 是否让 `unlink` 也跟随了链接 |

先完成大文件，再做符号链接，最后跑官方完整验收。官方专用命令在 xv6 shell 内执行：`bigfile`、`symlinktest`、`usertests`；`make grade` 在宿主系统的实验目录执行。应看到哪些输出，直接对照[实验说明](#/c/mit-6.s081-2020/lab/fs?v=zh)。时间统计与提交见[公共资料「实验的共同验收与提交步骤」](#/c/mit-6.s081-2020)。

除了官方测试，若出现疑点，可用上述映射边界与“创建—写入—读取—删除—再次创建”序列缩小范围。不要把本文建议的检查项当作对未取得的评分器行为的描述。

## 8. 自测：能否解释自己的修改？

<details><summary>文件有 65803 个内容块，是否只占 65803 个磁盘块？</summary>

不是。一级、二级地址表也占磁盘块，但不是用户文件内容；最大文件长度只计算数据块。目录和 inode 等元数据又有各自的存储位置。

</details>

<details><summary>为什么只改 bmap、不改 itrunc 不够？</summary>

新增的地址树让文件能够分配更多块，也增加了需要回收的节点。旧的释放逻辑不认识二级子树，会漏掉数据块或地址表；一次成功写入不能证明生命周期完整。

</details>

<details><summary>为什么创建时目标不存在可以成功，打开时却可能失败？</summary>

创建只把目标路径保存到符号链接 inode；打开才查找该路径。两次操作发生在不同时间，也解决不同的问题。

</details>

<details><summary>增加深度上限后，为什么符号链接仍可能死锁？</summary>

深度上限只保证能继续执行循环时最终结束；若拿着旧锁去锁住同一个 inode，线程可能在进入下一轮之前就阻塞。因此循环次数与锁交接都要正确。

</details>
