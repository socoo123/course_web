# 锁实验指导 · 先拆共享关系，再拆锁

这两个任务看起来都是“把一把锁变成很多把锁”，真正的区别却在于：**空闲物理页可以分给不同 CPU 管理，而同一个磁盘块必须仍由全系统共享唯一缓存身份。** 因此，第一项按 CPU 分区，第二项按块的身份分区。

具体任务、官方提示、命令与输出见[实验说明](#/c/mit-6.s081-2020/lab/lock?v=zh)。本页是编者的设计与调试指导。

## 1. 先画清楚锁保护的东西

不需要先写代码；先补全这张表：

| 对象 | 必须一直成立的性质 | 哪些路径会修改它 |
|---|---|---|
| 空闲页集合 | 每个空闲页只属于一条空闲链，已分配页不在链上 | 初始化、`kfree`、`kalloc`、偷取 |
| 缓存身份集合 | 同一个 `(dev, blockno)` 至多对应一个已登记缓冲区 | `bget` 命中、未命中、淘汰、桶间移动 |
| 缓冲区引用 | `refcnt > 0` 时不得把缓冲区换成另一个块 | `bget`、`brelse`、`bpin`、`bunpin` |
| 块内容 | 使用者取得缓冲区睡眠锁后才读写数据 | `bread`、`bwrite`、上层文件系统 |

锁保护的是这些关系，而不只是某一行赋值。一般互斥、不变量和锁顺序的完整推导见[第 10 讲笔记 §§1–4](#/c/mit-6.s081-2020/lec/lec10?v=notes)；睡眠锁的两层结构见[第 13 讲笔记 §5](#/c/mit-6.s081-2020/lec/lec13?v=notes)。

### 建议的源码阅读顺序

1. `kernel/kalloc.c`：`kinit → freerange → kfree`，再读 `kalloc`。
2. `kernel/spinlock.c` 与 `proc.c:cpuid`：为什么关中断必须覆盖 CPU 编号的读取和使用。
3. `kernel/buf.h` 与 `bio.c`：把“身份与引用”同“内容与睡眠锁”分开。
4. `bio.c:bpin/bunpin` 与 `log.c` 的相关调用：不要遗漏引用计数的其他写入者。
5. `sleeplock.c:acquiresleep`：确认它可能睡眠，理解为什么不能带着桶自旋锁调用它。

上述文件可帮助理解原机制；实现必须对照实际 `lock` 实验分支。本站固定参考提交不是实验起始分支，尤其没有实验计数器与专用测试。

## 2. 内存分配器：让普通路径只触及本核链表

### 2.1 空闲页不是永久归某个 CPU 所有

原始 `kalloc.c` 在空闲页自身开头放一个 `struct run`，通过 `next` 串起链表；取出页后，它的空间就归调用者使用。每核链表只是空闲页的管理分区，并不要求一页必须回到最初分配它的核。

释放时，可以把页交给当前执行 `kfree` 的 CPU。将所有初始空闲页交给执行 `freerange` 的核也是官方允许的做法。这意味着其他核可能一开始就需要偷取：偷取不是只有“很少见的内存压力”才会用到的装饰路径。

初始化所有链表的锁应先于任何可能调用它们的释放路径。数组容量可以依据 `NCPU`；不要把测试示例恰好显示三条锁统计误当成必须硬编码三个 CPU。

### 2.2 为什么不能先 cpuid，再依靠 acquire 关中断？

考虑以下不正确的时序：

1. 读出 CPU 0 的编号。
2. 时钟中断触发调度；进程后来在 CPU 1 继续运行。
3. 才进入根据旧编号选择的临界区。

如果设计依赖“这个编号就是当前 CPU”，第 3 步已经破坏了前提。`acquire` 内部确实调用 `push_off`，但它只能关闭**调用时**的中断，不能补救更早的迁移窗口。

应使 `push_off` / `pop_off` 覆盖“读取当前 CPU 编号并依赖它操作”的区间，逐一检查正常、偷取成功和失败返回路径的配对。内部锁也有嵌套计数；不能用无条件 `intr_on()` 代替 `pop_off()`。

关本核中断也不意味着不需要链表锁：其他核仍会从这条链表偷页。

### 2.3 偷取是一次所有权转移

先决定自己需要转移一页还是一批页：单页转移容易推理，但频繁耗尽时可能反复访问远端；批量转移可摊薄开销，却增加链表截断、接回和局部持有页的处理。官方没有规定固定批量。

不论选择哪一种，都应能解释三个阶段：

- **摘下之前：** 页仍是捐赠链的一部分，受捐赠链锁保护。
- **摘下之后：** 其他 CPU 不能再从捐赠链取到这些页；当前执行者暂时独占转移中的页。
- **交付之后：** 一页交给分配调用者；若还有剩余，按接收链的协议发布。

这是推理骨架，不规定具体指针实现。关键是不能出现“同一页同时挂在两条链上”，也不能在失去最后一个引用后再想办法找回转移中的链段。

尤其要避免：CPU 0 持本地锁等 CPU 1 的链表锁，同时 CPU 1 持本地锁等 CPU 0。可以通过避免同时持有这两把锁，或为确实需要的多锁操作制定一致顺序来排除这个环；选择之后检查每条路径是否遵循同一规则。

### 2.4 保留原有内存接口语义

`kalloc` 仍返回一页或空指针，`kfree` 的地址范围、对齐要求仍成立。还应保留用于暴露悬空引用的垃圾填充行为。

注意填充与链表发布的关系：`next` 就存放在页内。若把页放进空闲链以后再对整页 `memset`，可能覆盖自己的链指针，或者覆盖另一核已经分配出去的内容。先明确这时谁独占该页，再安排填充。

本核链表为空不等于全系统没页。`usertests sbrkmuch` 之所以重要，正是因为一个能在常见路径分配页的程序，也可能把其他核的空闲页“藏”起来，或在偷取时漏页。

## 3. 块缓存：把身份保护与内容保护分开

`struct buf` 可以看作一个可反复使用的槽位，而不是永久对应某个磁盘块的对象。

| 状态 | 含义 | 重构时必须保留的保证 |
|---|---|---|
| `dev`、`blockno` 与桶中位置 | 这个槽当前代表哪个磁盘块 | 查找和改身份遵守一致的桶协议 |
| `refcnt` | 有多少引用阻止它被重用，含等待者及 pin | 计数非零时身份稳定 |
| `valid` | 当前身份的数据是否已经有效装入 | 换成新块时旧内容不能冒充新块内容 |
| `b->lock` 睡眠锁 | 谁可使用该块的内容 | 即使多个调用者取得同一 buf，也不能并发修改内容 |

`valid == 0` 不是“这个槽没有身份”。在原始 `bget` 的未命中路径中，槽已经登记新 `(dev, blockno)`，`refcnt` 已为 1，但 `bread` 还没有从磁盘装入内容。如果另一个查找者因为 `valid == 0` 就忽略它，会再次为同一块创建副本。

哈希函数可以只使用块号来决定桶，但**实际匹配仍应比较设备号和块号**。哈希碰撞表示两个身份被分到同一桶，不表示它们是同一个磁盘块。

### 3.1 命中路径中的交接点

在身份锁保护下确认命中并增加引用，然后释放身份锁，再取得缓冲区的睡眠锁。这段顺序有两个理由：

1. 先增加引用，才能保证等待睡眠锁期间槽位不会被淘汰并改成另一块。
2. `acquiresleep` 可能睡眠；不能在仍持桶自旋锁时进入它。

因此，“先解桶锁，再加引用”留下重用窗口；“始终拿着桶锁直到拿到睡眠锁”又可能使系统无法调度。不是把临界区随意放大或缩小，而是用引用承担两种锁之间的身份稳定保证。

### 3.2 只有每桶锁，为什么还可能生成重复副本？

一个错误交错如下：

| 时刻 | 请求者 A | 请求者 B |
|---|---|---|
| 1 | 查目标桶，没有块 X；释放桶锁 | |
| 2 | | 查目标桶，也没有 X；释放桶锁 |
| 3 | 找到可替换槽 a，准备登记 X | 找到可替换槽 b，准备登记 X |
| 4 | 登记 a → X | 登记 b → X |

每次链表操作都有锁，但“检查不存在→建立映射”没有成为一个原子决定，最终有两个 X。

官方允许串行化未命中时的淘汰。若使用一把负责这一慢路径的锁，进入它后要考虑**重新查找目标块**：第一次查找与获得慢路径锁之间，别人可能已完成插入。二次查找不是可有可无的性能细节，而是消除上述交错的一种必要设计环节。

你仍需自行明确：谁能创建新映射、哪个临界区决定创建，以及桶的读者能观察到哪些中间状态。只加一把“淘汰锁”却不约束所有插入路径，并不能证明唯一性。

### 3.3 找到空闲候选，不等于已经占有候选

扫描某桶时看到 `refcnt == 0`，然后释放该桶锁，记下一个裸指针，再回来改身份，这段间隔内可能发生命中并增加引用。最终重用前，必须在保护该状态的锁下重新确认，或通过明确的保留协议保证别人无法再获得旧身份。

移动槽位时要同时维护：旧桶中不可再查到旧身份、新桶中只能查到一个新身份、引用与内容有效标记符合新身份。新旧桶相同是普通情况；不能对同一把非递归自旋锁获取两次。若需要两个不同桶锁，先约定一致的顺序，不能按“我先遇到哪个桶”随意加锁。

静态 `buf` 数组中的所有槽位也要有明确的初始去向。若把默认零值当作有效身份发布，很容易制造重复 `(0, 0)` 条目。设计中要区分“从未赋予身份的空闲槽”与“已有身份但内容尚未读取的槽”，无须为了这个区别照搬某一种完整实现。

### 3.4 去掉全局 LRU 链以后，检查所有引用写入点

原始 `brelse` 先释放睡眠锁，再减少引用；引用在这两步之间仍然保护身份。重新设计后也要保留这个承诺，并根据自己的时间戳规则记录最后使用时间。

不要只修改 `bget/brelse`：`bpin` 与 `bunpin` 也改变 `refcnt`。参考源码中的 `log_write` 通过 `bpin` 把待提交块留在缓存，安装日志内容的路径通过 `bunpin` 解除这份保留。它们若继续使用与桶访问无关的旧全局锁，引用计数仍会竞争；若丢掉 pin 的效果，尚需保留的块可能过早被重用。

官方建议用 `ticks` 替代全局 LRU 链。使用时写清楚：时间戳在哪个时刻更新，由哪把锁保护，选择候选时怎样读取。参考源码中 `ticks` 的写入受 `tickslock` 保护；若读取也取得该锁，就要把它加入锁顺序分析，并考虑它是否成为新的热点。相同 tick 的多个候选并不奇怪，可采用一致的平局规则，不应为了重排全局链又把每次释放串行化。

## 4. 按功能、并发、测量三个阶段推进

| 阶段 | 做什么 | 能说明什么 |
|---|---|---|
| 功能骨架 | 桶结构已建立，暂时保留原本串行化元数据路径的全局锁；必要时 `make CPUS=1 qemu` | 找初始化、链表、引用和回收错误；不能证明多核正确或争用达标 |
| 并发协议 | 移除命中/释放公共全局锁，保留设计所需慢路径锁 | 用交错分析检查唯一性、身份交接和锁顺序，再在多核上验证 |
| 测量与回归 | 在空闲多核宿主机运行两组专用测试、内存大分配与全套 usertests | 查看争用与功能表现，最后以实际分支 `make grade` 验收 |

第一阶段的“保留全局锁”是指原本保护缓存元数据的区间，不是把全局自旋锁延长到 `acquiresleep`、磁盘等待或整个 I/O 过程。

在 xv6 shell 中执行的命令是：

```text
$ kalloctest
$ usertests sbrkmuch
$ bcachetest
$ usertests
```

回到宿主机的实验目录再执行 `make grade`。具体输出与官方通过要求见实验说明；共同提交步骤见[公共资料「实验的共同验收与提交步骤」](#/c/mit-6.s081-2020)。

### 怎样读争用数字？

- `#acquire()` 是获取调用次数，不是失败次数；多条分片锁仍有很多调用是正常的。
- `#fetch-and-add` 是原实验输出标签；这里关注失败自旋次数，不应凭这个名字推断参考源码使用某种同名 RISC-V 指令。
- `top 5` 里 `proc`、磁盘锁的数值仍很高，不等于本实验的 `kmem/bcache` 改造失败。先读相关锁的统计。
- 仅把锁改名成统计范围之外的名称，不能称为减少争用；前缀是官方要求的一部分。
- `bcachetest test0` 更强调低争用命中访问，`test1` 使用超过缓冲区数的不同块。只看 test0 会漏掉淘汰错误。
- 官方块缓存阈值为总数 **小于 500**；内存任务要求显著降低争用并通过测试，原页没有给出一个可另行硬编码的评分阈值。

## 5. 常见故障按不变量排查

| 现象 | 优先检查 |
|---|---|
| 空闲页数下降、`sbrkmuch` 失败 | 是否只查本核就返回失败；偷取是否漏链段、重复分配；填充是否覆盖已发布的 `next` |
| `panic("acquire")` 或无输出地卡住 | 同桶锁是否重复获取；偷取双方是否互等；桶锁、慢路径锁的顺序是否反转 |
| 多核才错、单核正常 | CPU 编号是否跨开中断使用；命中加引用与改身份是否处于同一保护协议 |
| 同一块出现多个槽 | 未命中后二次查找是否缺失；是否把 `valid == 0` 当作身份不存在 |
| `test0` 通过、`test1/usertests` 失败 | 候选淘汰前是否失效；`bpin/bunpin` 是否同步；新旧桶相同是否正确处理 |
| 程序正确但争用仍高 | 命中或释放是否仍取全局锁；哈希分布是否碰撞；是否过频偷取 |
| 调度相关 panic | 是否持桶自旋锁进入睡眠锁或 I/O 等待；`push_off/pop_off` 是否配对 |

先修复能解释症状的不变量，再调整桶数或偷取批量；否则一次较低的计数很可能只是没有触发错误的运行。

## 自测：用一个交错检验理解

<details><summary>本核链表只由本核释放页，为什么仍要加锁？</summary>

其他核可能偷取该链表；“通常本地访问”不等于“只有本核能访问”。关闭本核中断也不阻止远端执行者。

</details>

<details><summary>缓冲区睡眠锁未被持有，为什么不能直接淘汰？</summary>

可能已经有调用者增加引用、正在等待取得睡眠锁，也可能存在日志 pin。重用判据必须遵守引用与身份协议，不能只看当前睡眠锁是否空闲。

</details>

<details><summary>已串行化淘汰，为什么还要在慢路径中重新查目标块？</summary>

首次查找未命中之后，到拿到慢路径锁之前，另一个请求者可能已经建立目标映射。不重新确认就会再建一个副本。

</details>

<details><summary>把引用计数增减换成原子指令，就能完成无锁挑战吗？</summary>

不能。读到身份、取得有效引用、确认身份未被替换是一组关联步骤，还涉及发布顺序与槽位重用。官方选做要求思考正确性证明，不是只替换单个加减法。

</details>
