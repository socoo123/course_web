# mmap 实验指导

这个实验的核心不是“把文件一次性读进内存”，而是建立一个承诺：**某段虚拟地址对应文件的某个范围；用户真正访问某页时，内核才兑现这个承诺。**

先读[实验说明](#/c/mit-6.s081-2020/lab/mmap?v=zh)。下面是编者的设计推导，不是可直接粘贴的实验答案；官方范围以实验说明为准。

## 1. 把三类状态分开

| 状态 | 回答的问题 | 谁维护 |
|---|---|---|
| VMA 元数据 | 这个地址是否合法、对应哪个文件、可以怎样访问？ | 进程的映射区域表 |
| 页表中的叶 PTE | 这一页现在是否驻留、对应哪个物理页、硬件准许什么访问？ | 页表及缺页处理 |
| 打开文件对象 | 文件是否仍存活、普通 read/write 的位置在哪里？ | `struct file`、引用计数及 inode |

VMA 存在而 PTE 不存在，是惰性映射的正常状态。PTE 存在也不意味着该页归普通堆管理。把这两点弄混，常会表现为“第一次 mmap 成功，退出时却 panic”。

可以用下面的最小状态链理解一个页：

```text
登记 VMA（尚无数据页）
        ↓ 首次合法访问
分配、清零、按文件位置读入、建立 PTE
        ↓ munmap 或 exit
按共享策略写回 → 解除 PTE、释放页 → 更新或移除 VMA
```

若某页从未被访问，它可以从第一步直接走到解除映射，不需要先读入再丢弃。

## 3. VMA 记录的是区域承诺

先用自然语言写清一条 VMA 至少需要表达什么，再决定 C 字段名字：

- 这一项是否使用中；
- 虚拟起点与有效范围；
- 访问权限和共享／私有策略；
- 持有引用的 `struct file *`；
- 当前虚拟起点对应的文件位置。

原页建议每进程固定 16 项即可。选择地址时，既要避免已有 VMA，也要避免程序、栈、堆、`TRAPFRAME` 和 `TRAMPOLINE`；不能只检查“当前没有 PTE”，因为另一条惰性 VMA 可能已经预订了那里。

### 字节范围和页面范围不是一回事

`length` 的单位是字节；分配、映射、释放的单位是 4096 字节页。需要清楚区分请求长度与页向上取整后的覆盖范围，避免整数溢出、零长度进入页表循环，以及对尾页写回过多字节。具体字段可以不同，但所有路径必须采用同一种范围约定。

### 不要随手扩大 p->sz

起始分支的 `uvmcopy` 假设 `[0, sz)` 中每页都存在，`uvmfree` 也用这个连续范围释放内存。若把一个远处的 mmap 终点直接写入 `p->sz`，会把中间空洞误报为已分配内存，导致 fork 或释放失败。

一种清晰的思考方式是分别描述普通进程内存和映射区域，并明确各自负责哪些页的复制与清理。无论选择什么布局，都要检查“普通内存增长是否会撞上 VMA”和“最后回收页表前是否还有映射叶子”。这里不规定唯一的地址放置算法。[C1: `vm.c`、`proc.c`、`memlayout.h`]

## 4. 最容易错的地方：三个 offset

本实验可以假设 mmap 的输入 `offset = 0`，**不等于后续每次读文件都从 0 开始**。

设一条 VMA 的当前虚拟起点为 $s$，它对应的文件位置为 $o$。发生缺页的虚拟地址为 $a$，所属页起点为 $p=\operatorname{PGROUNDDOWN}(a)$。在页对齐的 VMA 中，该页应从文件位置

$$
o + (p-s)
$$

开始装入。页内偏移 $a-p$ 则用于访问这页中的某个字节。

| 名字 | 意义 | 会被什么改变 |
|---|---|---|
| mmap 输入 `offset` | 初次映射的文件起点；本题为 0 | 由调用参数给定 |
| VMA 当前文件起点 $o$ | 当前剩余区域的起点对应文件哪里 | 解除前缀后需要相应调整 |
| `file->off` | 普通 `read`/`write` 的流式读写游标 | 成功的普通读写；同一打开对象的持有者共享 |

`fileread` 和 `filewrite` 使用并推进 `file->off`；`readi`、`writei` 接收显式偏移。用户可能先访问第三页，再访问第一页，还可能在同一 fd 上做普通读写。因此，不能把缺页处理写成“从当前文件游标读下一页”。也不要为了写回临时修改共享的 `file->off`。[C1: `file.c` 104–180、`fs.c` 451–517]

这个错误在两个文件测试中尤其明显：程序刚向文件写了 5 字节，普通游标已经在 5；但 `mmap(..., offset=0)` 仍应读出开头的 `12345` 或 `67890`。

## 5. 缺页路径：先判定，再分配，再发布

一个好检查点是：**缺页处理返回后，CPU 能否重试同一条指令，且只获得 VMA 允许的访问？**

按下面的问题审视自己的路径：

1. 异常是用户数据访问缺页吗？故障地址属于哪条有效 VMA？读写类型是否被该 VMA 允许？不属于映射、或写只读区域，都不能被“补一页”掩盖。
2. 这是尚未驻留的页，还是一个已存在 PTE 的保护错误？不要把任何异常都交给 `mappages`；它会拒绝重复映射。
3. 分配成功后是否先把页清零？再使用正确的文件偏移、持有 inode 锁，通过 `readi` 把文件内容读入。
4. 传给 `readi` 的地址究竟是内核地址还是用户虚拟地址？新页由内核填充时，要与 `user_dst` 的选择一致；不能把尚未映射的用户地址当作有效目的地。
5. 短读是否保留剩余的零？真正的读错误或页表分配失败是否释放了本次新分配的页？失败后不要留下一个看似可用但内容未初始化的 PTE。
6. 建立映射时是否设置了用户访问位与所需读写位，并避免无故授予执行权限？成功后返回用户态重试；不要照抄 `ecall` 路径中的 `epc += 4`。

### 为什么清零在本题中直接影响结果

`makefile` 实际只写出 **1.5 页的 `A`**，`_v1` 却检查两页：前 1.5 页为 `A`，最后半页必须为 0。测试源码上方注释说“文件含 1.5 页 A 和半页零”，但函数体没有写最后半页；这是映射时短读后零填充的效果，不能按注释误读文件长度。[C1: `mmaptest.c` 33–77]

本题的这项尾页检查，不应扩展为“已经实现真实 Unix 对任意 EOF 之外访问的全部规则”。

### 权限有两道判断

文件能否被写回，与当前页能否被程序写，是两回事：

- 只读打开的文件可以创建 **可写 `MAP_PRIVATE`** 映射，因为私有修改不写回；测试明确要求这一点。
- 只读打开的文件不能创建 **可写 `MAP_SHARED`** 映射，因为它会绕过文件的写入限制；测试要求 mmap 直接失败。
- 映射被允许之后，PTE 仍要兑现 `prot`。不要为了“先让测试跑起来”把所有页都设为可写。

本分支测试只使用 `PROT_READ` 与 `PROT_READ | PROT_WRITE`，没有单独使用 `PROT_WRITE`。题面允许只写参数，但本任务无需实现测试没有使用的特性；若自行扩展，须额外核对 RISC-V 页权限编码，不能把仅设置 `PTE_W` 当成已验证方案。

## 6. munmap：先处理数据，再缩小承诺

`munmap` 有两个工作对象：已经驻留的页面，以及不管是否驻留都存在的 VMA。只做其中之一都不完整。

### 没有 PTE 不一定是错误

起始分支 `uvmunmap` 的前提是“映射必须存在”，找不到中间页表或有效 PTE 会 panic。惰性映射不满足这个前提。应在映射清理路径中识别尚未分配的页，或有意识地调整底层函数的契约；不要为了跳过空洞而吞掉非叶 PTE、错地址等真正错误。

`test not-mapped unmap` 解除的是**VMA 内尚未访问的第三页**，不是要求接受任意从未登记过的地址。跳过该页的数据回收后，仍然要更新 VMA 和文件引用。[C1: `mmaptest.c` 158–199]

### 前缀、后缀和全部解除

用区间 `[s,e)`、文件起点 $o$ 表示当前 VMA。下面只是页对齐范围的状态推导：

| 操作 | 剩余虚拟区间 | 剩余文件起点 | 文件引用 |
|---|---|---|---|
| 删除前缀 `[s,u)` | `[u,e)` | $o+(u-s)$ | 保留 |
| 删除后缀 `[u,e)` | `[s,u)` | $o$ | 保留 |
| 删除全部 `[s,e)` | 无 | 无 | 释放这一条 VMA 的引用 |

例如原映射三页，文件起点为 0；解除前两页之后，第三页仍对应文件偏移 8192。若只移动虚拟起点而忘记推进文件起点，后来访问第三页就会错误地读到文件第一页。

处理被删除页时，先用**原来的区域信息**确定写回位置，再调整剩余区域。不要先改 `s`，又拿新 `s` 计算旧页偏移。原页允许删除后缀；当前 `mmaptest.c` 没有单独覆盖“只删除末尾但保留前段”的用例，仍应按题面处理它。

### 共享写回的四个条件

1. **策略正确。** `MAP_PRIVATE` 修改不写回。`MAP_SHARED` 的可写页需要写回；只读映射不能因此绕过文件写权限。
2. **时机正确。** 写回必须发生在释放物理页和释放最后文件引用之前。无驻留页就没有该页的内存修改可写回，不必为解除映射额外触发缺页。
3. **位置与长度正确。** 文件偏移用 VMA 推导；地址种类与 `writei` 的 `user_src` 一致。区分页长、映射有效字节和文件现有长度，避免把尾页补零无意写成文件扩展。测试的 dirty 检查只读回原来的 1.5 页，不证明任意 EOF 扩展策略正确。
4. **文件系统协议正确。** `filewrite` 的可借鉴部分包括 inode 锁和日志事务分块；它本身使用流式 `file->off`，不宜原样套用。不要假设一页或整个 VMA 一定能放进一次日志事务。核对短写／错误，再按自己的失败策略清理，不能悄悄宣称写回成功。

原页允许省略 `D` 位优化，即对可写共享映射的驻留页做保守写回。`test mmap dirty` 检查修改是否回到文件，**没有检查你是否读取了硬件 `D` 位**。课程起始 `riscv.h` 也没有现成的 `PTE_D` 宏，不能把后续版本的宏当作已经存在。

## 7. close、fork、exit：谁还拥有文件和页？

### close 后映射继续有效

把 `fd` 仅仅存进 VMA 是不够的：`close(fd)` 之后，这个整数槽可以被复用来打开另一个文件。VMA 应持有自己的 `struct file` 引用，不依赖 fd 槽仍然有效。

以一次打开、一条映射为例，忽略其他持有者：

| 时刻 | fd 表持有的引用 | VMA 持有的引用 | 结果 |
|---|---:|---:|---|
| open 后 | 1 | 0 | 文件可用于系统调用 |
| mmap 成功后 | 1 | 1 | 两个独立的持有者 |
| close 后 | 0 | 1 | 映射仍可缺页读文件 |
| 整条映射解除后 | 0 | 0 | 最后引用可关闭 |

部分 munmap 不应关闭这个引用；同一文件映射两次，需要两条 VMA 各自拥有引用。测试还会 `unlink` 文件名：删除名字不等于销毁仍被打开对象持有的 inode。[C1: `filedup`、`fileclose`、`iput`；`mmaptest.c` 203–238、259–269]

### fork 继承区域，不要求共享物理页

子进程需要自己的 VMA 表项以及相应的文件引用。父子任一方解除映射，不应修改另一方的 VMA；复制一个指针值本身不会增加引用计数。

题面允许子进程缺页时重新分配、从文件装入物理页，因此本实验无需先完成共享物理页管理或 COW。`fork_test` 也没有验证“fork 前父进程的私有脏页如何成为子进程的初始内容”：它使用只读共享映射。不要把测试允许的简化宣称为完整 POSIX fork/mmap 实现。

如果自己扩展到私有脏页继承，必须保留 fork 时的内容，直接复制页也可以；**COW 是优化手段，不是 `MAP_PRIVATE` 的定义**。若选择共享物理页方案，才需要进一步讨论页引用计数、最后一次释放和私有写隔离，那已经超出基础解法的要求。

### exit 应复用解除映射的规则

退出时要清理所有 VMA：写回所需的共享页、解除驻留页、释放文件引用。不能只在进程结构最终回收时清零 VMA 数组，否则会丢失写回机会或泄漏引用。

尤其注意执行上下文：`exit` 后半段会持有进程锁；文件 I/O、inode 睡眠锁以及 `begin_op` 可能等待。把可能睡眠的映射清理放在合适的退出阶段，不要塞进持有自旋锁的 `freeproc` 路径。`freewalk` 开始递归回收页表之前，所有 mmap 叶映射必须已经解除。[C1: `proc.c` 140–203、336–400；`vm.c` 261–289]

新进程初始化、失败回滚和进程槽复用也应与 VMA 的所有权配套：取得了什么引用，失败时就释放什么；不能把已经释放过的表项留给下一次清理。

## 8. 用官方阶段目标定位进度

先逐步跑通正常路径，再按明确失败点排错。下面是**预期阶段现象**，没有在本站执行：

| 阶段 | 应完成的事情 | 官方建议观察的现象 |
|---|---|---|
| A | 用户声明、调用桩、内核分派、镜像加入测试 | 测试能运行，第一次 mmap 返回错误 |
| B | 地址选择、VMA 登记、文件引用 | mmap 成功，第一次访问因缺页终止 |
| C | 缺页装入、零填充、页权限 | 到达第一次 munmap |
| D | 区域解除、共享写回、exit 清理 | `mmap_test` 通过，fork 部分可能失败 |
| E | 子进程 VMA 与文件引用 | `mmap_test`、`fork_test` 都通过 |
| F | 回归及正式评分 | `usertests` 与宿主机 `make grade` 全部通过 |

实际测试内容也应按源码理解：

| 测试名 | 主要检查 | 不应从名字推断的结论 |
|---|---|---|
| `test mmap f` | 只读私有映射，跨页内容及尾部零填充，整体解除 | 不代表已覆盖任意文件大小 |
| `test mmap private` | 只读 fd 上的可写私有映射，close 后访问，修改与解除 | 这里不直接重读文件证明私有修改未写回；不写回仍是题面语义 |
| `test mmap read-only` | 拒绝只读 fd 上的可写共享 mmap | 不是主动写只读 PTE 的保护异常测试 |
| `test mmap read/write` | 可写共享映射、close 后访问、修改并解除前缀 | 只访问了三页映射中的前两页 |
| `test mmap dirty` | 原文件的 1.5 页内容已变为 `Z` | 不检查硬件脏位策略或文件是否意外变长 |
| `test not-mapped unmap` | 解除 VMA 内尚未驻留的第三页 | 不是任意非法地址解除测试 |
| `test mmap two files` | 两文件并存，close/unlink 后可读，解除一个不影响另一个 | 不是跨进程即时共享一致性测试 |
| `fork_test` | 同一文件两次映射，部分页驻留后 fork，子解除前缀并退出，父映射继续可用 | 不检查物理页共享，也不检查私有脏页继承 |

分支评分脚本运行 `mmaptest` 并匹配这些成功行，再运行 `usertests` 匹配 `ALL TESTS PASSED`，最后检查耗时文件。源代码阅读只说明它检查什么；成功输出仍需实际运行获得。[C1: `grade-lab-mmap`]

## 9. 常见故障与检查顺序

| 现象 | 优先检查 |
|---|---|
| 首次访问就被杀死 | VMA 范围、异常类型、用户访问权限、缺页入口是否接通 |
| 重复出现同一缺页／`remap` | 已存在 PTE 的权限错误是否误走分配路径；页权限是否正确 |
| 第二页内容重复第一页 | 文件偏移是否始终为 0，或误用了 `file->off` |
| 最后半页不是 0 | 新页是否清零，`readi` 短读是否被错误当成读满 |
| 私有可写映射遭拒绝 | 是否把所有 `PROT_WRITE` 都要求为可写 fd |
| close 后映射坏掉 | VMA 是否持有独立文件引用，是否只存了 fd |
| `uvmunmap: walk` / `not mapped` | 是否对合法但未驻留的页直接调用了要求 PTE 存在的函数 |
| `freewalk: leaf` | 是否遗漏 mmap 区域的叶 PTE；清理是否只遍历 `p->sz` |
| 前缀解除后剩余页读错 | 剩余 VMA 的虚拟起点与文件起点是否同步推进 |
| 解除一个映射后另一个失效 | 是否误共享 VMA 表项，或过早减少文件引用 |
| 共享修改未写回／写错位置 | 是否先释放了页；偏移、写入字节数、地址种类、日志事务是否正确 |
| 退出或 fork 后 panic | 空洞被纳入连续 `sz` 范围、引用重复释放、遗漏子 VMA、持自旋锁做 I/O |

调试输出只需记录足以解释当前故障的几项：故障地址、VMA 起止、权限／flags、计算出的文件偏移、PTE 是否存在。用这些状态回答“下一步应该发生什么”，比在每个函数里大量打印更有效。

## 10. 自测与扩展边界

<details><summary>输入 offset 总是 0，为什么 VMA 仍需要表达非零的文件起点？</summary>

解除前缀后，剩余虚拟区间的起点已经对应文件中间。可以保存并更新当前文件起点，也可以用等价的原始基准表示；关键是继续维持虚拟位置到文件位置的对应关系。

</details>

<details><summary>一个三页 VMA 只有第一页有 PTE，解除整个 VMA 应释放几个数据页和几个文件引用？</summary>

在基础独占数据页方案中，释放一个驻留数据页，跳过两个从未分配的数据页，释放这一条 VMA 的一个文件引用。页表中间节点由相应页表回收逻辑管理，不能混作数据页释放。

</details>

<details><summary>MAP_PRIVATE 可写是否意味着首次写一定产生 COW 异常？</summary>

不是。基础实现可以在首次缺页时分配自己的可写页，之后直接修改，解除时不写回文件。COW 是可以选择的共享与复制优化。

</details>

<details><summary>父进程 close(fd) 后 fork，子进程为什么仍能继承映射？</summary>

文件已由父 VMA 保持存活。fork 为子 VMA 再取得引用，继承的是映射关系，不依赖已关闭的 fd 槽。

</details>

<details><summary>两个 MAP_SHARED 映射各有一个数据页，为什么不能据此保证双方立刻看到对方修改？</summary>

它们是两份内存副本，单纯写回文件并不会立即刷新另一份。2020 基本任务明确允许不共享物理页，不应把这份简化实现描述成完整实时共享一致性。

</details>

五项官方选做见[实验说明](#/c/mit-6.s081-2020/lab/mmap?v=zh) §7。共享页需要物理页寿命管理；复用 buffer cache 还涉及块大小和 pin；统一 lazy/VMA、按需加载可执行文件、换入换出则进一步改变地址空间模型。先完成基础要求，再选择一个方向扩展。

基础题也没有要求增加 `msync`、中间挖洞、任意偏移、完整内核 copyin/copyout 缺页机制或所有 exec 与映射的交互。若扩展这些用途，应重新检查它们的语义，不要把“现有测试通过”推广为“完整 mmap 已实现”。
