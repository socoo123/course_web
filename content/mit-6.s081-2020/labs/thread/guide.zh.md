# 多线程实验指导

这三个任务分别回答三个问题：**怎样接续另一条执行流，怎样让共享数据保持正确，怎样让一组线程按轮次会合？**先区分它们的执行环境，再动手。

## 1. 先划清两种线程模型

| 任务 | 在哪里运行 | 谁负责线程调度 | 主要约束 |
|---|---|---|---|
| uthread | xv6 用户程序 | 用户级线程库选择并切换 | 独立栈、寄存器保存、首次启动 |
| ph | 多核宿主机的 pthread 程序 | 宿主操作系统 | 共享哈希表的正确性及并行吞吐 |
| barrier | 宿主机的 pthread 程序 | 宿主操作系统 | 同一轮全部到达后才能放行 |

uthread 的多个执行流共享一个 xv6 进程；切换不会自动产生新进程或新页表。ph 和 barrier 则可能真正同时在多个核心上执行。前者能交替打印，不等于后者已经没有数据竞争。

建议顺序：读[实验说明](#/c/mit-6.s081-2020/lab/thread?v=zh) → 画出 uthread 保存状态 → 完成 ph 的正确性阶段 → 减小锁的作用范围 → 设计可重复使用的屏障。第 11 讲[笔记 §2–3、§7](#/c/mit-6.s081-2020/lec/lec11?v=notes)分别解释保存边界和首次启动；教材第 7 章的译文仍在原讲次，不在这里重复。

## 2. Uthread：把一次函数调用暂停起来

### 2.1 切换的是「继续执行所需的状态」

把线程 A 暂停，至少要回答两个问题：

1. 将来从哪里继续？
2. 继续时使用哪条调用栈、哪些需要跨调用保留的值？

普通函数调用已经提供了保存协议。调用 `thread_switch` 时，编译器知道正在跨越函数调用边界；caller-saved 寄存器中若有以后还要使用的值，调用者必须负责保存。切换例程则保全应由被调用者维护的寄存器，并保存栈指针与返回位置。

固定参考代码 `kernel/swtch.S` 的保存集合为 `s0–s11`、`sp`、`ra`。它是理解机制的对照，不能直接当作已经取得的 `user/uthread_switch.S`。尤其要注意：**`ra` 按 ABI 分类通常是 caller-saved，但切换例程仍要保存它，用于恢复返回位置。**官方题目“只需 callee-save”的提示不是让你忽略返回路径。

恢复目标线程的 `sp`，并不会复制它的栈；它原有的调用帧仍留在内存里。恢复 `ra` 后执行返回，才接续目标线程以前暂停的调用。不要把这与任意指令处发生中断、保存用户 trapframe 混为一谈。

### 2.2 C 数据布局和汇编偏移必须是一份契约

先在纸上列出你设计的上下文保存区，不急着写成串的加载、存储指令：

| 要检查的对象 | 必须回答的问题 |
|---|---|
| 保存区地址 | 传给汇编的是整个 thread，还是其中的 context？ |
| 字段宽度和位置 | C 字段的偏移、大小，与汇编使用的偏移是否相同？ |
| 保存与恢复方向 | old 是当前执行流，new 是即将恢复的执行流吗？ |
| 栈 | 每条活跃线程是否独占自己的栈区域？ |
| 返回位置 | 目标是首次运行，还是从之前的切换点继续？ |

RV64 的寄存器宽度、栈向低地址增长、函数入口的栈对齐要求都要落实。不要把数组起点自然地当作空栈的栈顶；也不要在已经更换 `sp` 后，无意间再用旧 C 栈上的局部变量寻址。用本机生成的 `user/uthread.asm` 检查真实指令。

### 2.3 首次启动和再次恢复是两条不同入口

再次恢复的线程有以前保存的状态；刚创建的线程没有。初始化时，应构造一份状态，使通用切换路径能够把执行接到指定入口，并使用该线程自己的栈。先解释清楚这个效果，再决定字段如何设置。

逐项追踪：

- 创建后，该线程何时变成可被调度的对象？
- `thread_schedule()` 找到 `next_thread` 后，保存旧执行流所需的指针是否仍有效？
- 更新“当前线程”记录，与汇编真正切走之间，是否用错了保存目标？
- 线程让出后，恢复的是暂停的调用链，还是错误地又从入口开始？
- 线程结束后，起始框架要求如何退出调度循环？不要假定线程入口可以随意 `return` 到一个并未安排的调用者。

这里的任务是补齐官方框架的缺口，不必照搬内核的进程锁、每 CPU scheduler 或页表管理。内核切换的相关完整解释见[第 11 讲课程资料 §7.2–7.3](#/c/mit-6.s081-2020/lec/lec11?v=materials)。

### 2.4 按失败阶段定位

| 现象 | 优先检查 |
|---|---|
| 第一次运行就陷阱或无输出 | 初始入口、栈顶、栈对齐、保存区基址 |
| 能输出一次，切回来就错 | 保存/恢复对应关系、`ra`、`sp`、字段偏移 |
| 循环变量或局部状态异常 | callee-saved 寄存器是否遗漏或存错位置 |
| 总是重新打印 started | 是否每次调度都重新构造了首次运行状态 |
| 执行到了已结束线程 | 状态转换和 runnable 选择是否一致 |

GDB 中先看 `next_thread`，再在 `thread_switch` 入口逐条执行。切换前后同时观察**返回位置和栈指针**，单看 PC 不足以判断恢复了谁。原页的 `uthread.c:60` 属于它给出的示例；修改代码后应按当前行号或符号定位。

关于“尚未运行 uthread 就触发断点”的提示，思考调试器设置的是符号名称还是最终指令地址，以及不同用户程序会不会使用相同的用户虚拟地址。不要因此立刻认定是线程库先运行了。

## 3. Ph：先定义锁保护的对象

### 3.1 从共享结构追踪丢失的键

单线程正确，只能说明顺序执行时逻辑成立。两个线程的每次读、改、写可以交错，某次操作作出的判断在真正写回时可能已过期。

本题要求你自己给出丢失键的具体事件次序。阅读实验分支的 `put()`、`insert()` 后，画两列表格：一列线程 A，一列线程 B，每行只放一个关键读取或写入；在旁边记录桶入口和链结关系。最后检查是否有已创建节点从桶入口不可达。提交时说明读到了什么旧状态、哪次写入破坏了另一线程的结果，不能只写“发生了 race”。

这里只给分析方法，不预先填写可直接提交的 `answers-thread.txt`。

### 3.2 临界区不一定是一条赋值

如果一个操作包含“查找键 → 判断存在与否 → 更新或插入”，保护范围通常需要围住维持该操作不变量的整段过程。只给最后一次写入加锁，可能仍基于已经过期的查找结果行动。

先用简单的互斥方案达成 `ph_safe`。锁必须在线程使用之前初始化；每条返回路径都应考虑是否还持锁；读路径也按题目要求参与同步。不能仅凭基准测试把 put/get 分阶段执行，就忽略官方要求对 `get` 的保护。

**正确性先于速度：**若两个线程每秒做了更多 put，却丢失大量键，这不是完成了要求的加速。

### 3.3 按桶划分互斥范围

官方已经提示“每桶一把锁”。核心判断是：两个操作到底会不会修改同一份共享结构？

- 不同键不一定落入不同桶。锁的归属应对应桶和它保护的链结构，而不是“这个键由哪个线程处理”。
- 同一桶的查找、更新和插入必须遵守同一套同步规则。
- 不同桶应能独立推进；如果所有操作外面还套着一把全局锁，分桶锁并没有释放并行性。

比较单线程和双线程时，使用**总 puts/second** 的比值：

$$
S = \frac{\text{双线程总 puts/second}}{\text{单线程 puts/second}}
$$

官方阈值为 $S \ge 1.25$，同时要求零丢失。锁操作自身有开销，桶冲突也会串行化操作，所以线程数翻倍不保证吞吐翻倍。宿主机负载会影响测量；应在相近条件下比较，而不是把官方示例中的绝对数字当验收线。

## 4. Barrier：等待的是本轮完成，不是一声通知

### 4.1 明确计数的含义

区分两个量：参与者总数是本题的固定规模；`bstate.nthread` 是框架用于跨轮复用的到达计数，不能因为它也叫 nthread 就当作同一个东西。

设计前先写出不变量：

1. 每个参与线程在每轮只贡献一次到达。
2. 本轮未全员到齐，任何参与者都不能离开本轮屏障。
3. 本轮完成后，下一轮能够重新计数，上一轮的等待者仍能判断自己已经获准离开。

第三条是可重复屏障与一次性会合的区别。单独看到“当前计数是多少”，可能分不清它属于旧轮还是新轮；`bstate.round` 就是区分轮次的线索。

### 4.2 用条件谓词理解 wait

互斥锁保护计数和轮次。条件变量让未满足条件的线程暂时让出执行权。`pthread_cond_wait` 的重要契约是：**等待时释放 mutex，返回前重新获得 mutex。**因此等待不会一直霸占锁，其他线程才有机会更新到达状态。

条件变量不是存放通行许可的计数器。一次 broadcast 也不表示每个被唤醒的线程马上运行，更不表示它们已经退出屏障。返回后的线程仍需在锁保护下检查自己等待的条件；条件变量允许虚假唤醒，也可能在重新取得锁前发生其他状态变化。设计时用“条件是否成立”的循环思维，而不是“收到通知就直接返回”。

考虑等待者在进入本轮时需要记住什么，才能在很晚才重新获得锁时，依然判断**自己的这一轮**是否已经完成。具体字段更新顺序由你在官方框架中实现。

### 4.3 专门推演跨轮抢跑

用三名参与者推演，比只看两线程一次运行更容易发现问题：

1. A、B 已到达第 r 轮，在等待；C 最后到达。
2. C 完成本轮放行所需的状态转换，并唤醒等待者。
3. A 很快运行，已经进入第 r+1 轮；B 仍未重新获得 mutex。
4. B 此时醒来，应知道第 r 轮已完成，而不把第 r+1 轮的计数当作自己还需等待的依据。

检查你的状态设计能否解释这四步：轮次推进是否只发生一次？复用计数前，旧轮等待者是否已不再依赖该计数？快线程的新一次到达会不会被旧轮的清零操作抹掉？

不要把规则误读为“必须等所有线程都从函数返回，任何人才能进入下一轮”。关键是旧轮完成与新轮计数之间没有混用，慢线程能识别自己那轮已经完成。

### 4.4 常见失败模式

| 错误思路 | 会发生什么 |
|---|---|
| 持锁忙等，等待别人增加计数 | 别人拿不到锁，永远无法到达 |
| wait 前手动解锁，再分开进入等待 | 条件检查和入睡之间可能丢失通知 |
| 醒来只看当前计数，不区分轮次 | 下一轮到达污染上一轮的退出判断 |
| 把 broadcast 当成所有人已经离开 | 快线程与仍在醒来的慢线程发生跨轮干扰 |
| 只测试两个线程的一轮 | 漏掉单线程自放行、多参与者以及计数复用问题 |

线程数为 1 时，也要能正常完成每轮；线程数大于 2 时，要保证一次放行覆盖全部等待者。官方现成测试循环中的随机睡眠用于扰动到达顺序，不是正确性证明。

## 6. 自测

<details><summary>为什么恢复了返回地址，还不能保证恢复了线程？</summary>

还需要对应的栈和跨调用保留的寄存器值。相同函数位置可以由不同线程在各自的栈上执行，代码位置不等于执行流身份。

</details>

<details><summary>每个线程一把锁，是否能让哈希表安全？</summary>

不一定。两个线程用不同锁操作同一桶，彼此没有互斥。锁应绑定共享数据及其不变量，而不是只绑定访问者。

</details>

<details><summary>屏障唤醒后为什么还要检查条件？</summary>

唤醒与取得 mutex 不是同一时刻；还可能出现虚假唤醒。真正允许离开的依据是自己所处轮次已经完成，而不是发生过一次通知。

</details>

<details><summary>给 uthread 的调度函数加锁，就能实现多核并行吗？</summary>

不能。锁只能限制同时访问，不能让 xv6 内核自动发现、调度更多用户级执行流。选做题要求另行设计内核支持，以及共享地址空间等配套机制。

</details>
