# 第 11 讲 · 切换的不是代码，而是继续执行的条件

**核心问题：一个正在计算的进程被暂停后，CPU 怎样运行别的进程，再像什么都没发生一样回到原来的位置？**答案不只在 `swtch.S` 的几条加载和保存指令里，还在调用约定、栈的独占权以及进程锁共同维持的约束中。

## 1. 先把三个层次分开

| 层次 | 本讲所指 | 不要混淆为 |
|---|---|---|
| 进程 | 用户地址空间、资源，以及与它对应的内核执行状态 | 一份磁盘上的程序文件 |
| 线程 / 执行流 | 一个顺序执行位置，加上寄存器和栈 | 必须有一份独立代码 |
| CPU | 当前真正执行指令的硬件 | 某个线程永久独占的私有对象 |

一个函数可以由不同内核线程同时调用，因为函数代码可共享；但每条执行流必须有独立的调用栈与运行状态。xv6 的用户进程只有一个用户执行流。课堂所谓“用户线程与内核线程”，描述的是同一进程在两个权限层次的执行阶段，不是两个能同时运行的用户线程。见[中文译稿](#/c/mit-6.s081-2020/lec/lec11?v=draft) 06:00–09:00、39:00–42:00。

调度与切换也不是同一件事：**调度决定接下来运行谁；切换负责把那个人真正接上 CPU。**`swtch` 不扫描进程表、不选择优先级、不自行设置 `RUNNABLE`。

## 2. 两份寄存器状态，是两个不同的“稍后回来”

用户代码可以在任意指令处被中断；内核线程则是在明确的 `swtch` 函数调用边界暂停。两个暂停位置不同，所以保存协议也不同。

| 保存处 | 回答的问题 | 谁保存 / 恢复？ |
|---|---|---|
| `p->trapframe` | 将来返回用户态，接着执行哪条用户指令、使用哪些用户值？ | `uservec`、`usertrap` 与用户返回路径 |
| `p->context` | 将来继续这条内核调用链，从哪次 swtch 返回？ | `swtch`；首次值由 allocproc 构造 |
| `c->context` | 本核的 scheduler 在哪里暂停了？ | scheduler 与进程线程之间的 swtch |
| 进程内核栈 | 这条内核调用链更早的函数帧是什么？ | 普通函数调用维护；切换时保留原地 |

不要把 `trapframe->epc` 和 `context.ra` 当成同一个地址。课堂的 `epc = 0x62` 位于用户 `spin` 的计算循环；`context.ra` 指向内核的 sched 返回位置。完整观察见译稿 48:00–63:00。

**为什么不把 trapframe 直接交给 swtch？**不是因为存储上绝对不可能合并，而是它们表示两种不同恢复协议。当前内核线程暂停时，用户 trapframe 必须继续保留，不能拿内核寄存器覆盖它。教材的系统说明见[课程资料 §7.2](#/c/mit-6.s081-2020/lec/lec11?v=materials)。

## 3. 用函数调用约定推导最小保存集

在 `swtch(old, new)` 入口，调用者承诺遵守 RISC-V ABI：若某个 caller-saved 值还要跨调用使用，编译器负责保全它。swtch 再保存 `s0–s11`、`sp`、`ra`，就能把这条内核调用链接续起来。

三个关键点：

1. **保存 sp 不等于复制栈。**旧栈一直在内存里；加载另一个 sp，只是让后续代码改用另一条已有的栈。
2. **保存 ra 不等于保存当前 PC。**swtch 内部的 PC 可预测；真正需要的是返回后的继续位置。`ret` 使用恢复出来的 ra，所以能接续目标线程以前的调用。
3. **不能把这份保存清单套到任意中断。**用户代码没有预告会在该指令被中断，不能依赖它先保存 caller-saved 值。trap 入口必须采用自己的完整保存协议。

`ra` 在 ABI 中通常归于 caller-saved，但在此处具有特殊用途，因而包含在 context 的 14 项里；不能简单说“这 14 个全是 callee-saved”。`tp` 也不是某个内核线程必须带着迁移的 CPU 身份：线程换核后，要使用新核的 hart ID。

**结果：一次 swtch 看起来从 A 发起、却在 B 中返回。**若按“当前这次 C 调用必须马上回到原调用者”的直觉调试，会迷失；应把每条栈上的 swtch 当成一个独立的、可能暂停很久的调用。课堂 `where` 的变化见译稿 60:00–72:00。

## 4. 最难的证明：为什么改完 state 仍不能解锁？

关键不变量不是“state 赋值不会撕裂”，而是：**一个可被别核选中的进程，必须已经不再被任何核使用其内核栈，且保存状态完整。**

考虑错误实现：

```text
CPU 0：获取 P.lock → P.state = RUNNABLE → 提前释放 P.lock
CPU 1：获取 P.lock → 发现 RUNNABLE → 恢复 P、开始用 P 的栈
CPU 0：仍在 P 的栈上执行 sched / swtch
```

现在两个核同时向同一条栈压入函数帧，而且 CPU 1 甚至可能恢复尚未更新完成的 context。即使 `state` 的每次读写本身都是原子的，也救不了这个错误。

正确做法是让进程锁覆盖整个交接区间：

| 转换方向 | 持锁期间完成的事 | 哪个执行流释放？ |
|---|---|---|
| 进程让出 CPU | 设为 RUNNABLE → 保存 context → 换到 scheduler 栈 → 清 `c->proc` | scheduler |
| scheduler 启动进程 | 设为 RUNNING → 设置 `c->proc` → 恢复 context / 栈 | 恢复后的进程路径；首次是 forkret |

因此，可以在持锁的内部过渡期暂时出现“标记 RUNNABLE，但当前核尚未停止执行”的状态；其他合规的观察者必须先取得锁，届时过渡已完成。课程资料 §7.3 给出完整不变量说明。

另一个关键保护是本核关中断。切入 P 时，若 state 已是 RUNNING、寄存器却尚未恢复完整，定时器中断再把“当前寄存器”保存进 P.context，就会损坏它。锁的跨核互斥与获取自旋锁时的本核关中断，处理的是两种不同干扰。

**跨线程交接锁，不等于允许任意跨 CPU 解锁。**这里进程与本核 scheduler 的切换不换 CPU，锁的获取与对应释放发生在同一个核。固定实现的 `holding()` 记录锁所属 CPU；当进程以后在另一个核恢复，是新核 scheduler 重新获取其锁后再交给它。

## 5. 为什么还要有一条 scheduler 栈？

直觉上，A 直接切到 B 可以少一次 swtch。问题在于 scheduler 可能暂时找不到 B，还要继续扫描，而 A 的状态可能已经允许其他 CPU 运行它。如果仍借用 A 的内核栈，就又出现栈的归属冲突。

每 CPU 的独立 scheduler 栈提供了明确的接收方：进程交出寄存器和栈的使用权后，本核仍有地方继续运行调度代码。它还让“当前进程退出，后续需要回收资源”的情形更容易组织。见课程资料 §7.1–7.2，图 7.1。

原始 xv6 的 scheduler 逐项扫描进程表，寻找 RUNNABLE 进程。它可能重新选择刚让出的进程；yield 不保证其他进程一定取得过 CPU。策略简单不代表严格的实时公平承诺。

## 6. myproc 能保留，mycpu 为什么不行？

构造一个反例就够了：

```text
P 在 CPU 0：c = mycpu()
发生定时器中断，P 让出 CPU
CPU 1 的 scheduler 恢复 P
P 继续使用旧 c，却把 CPU 0 的结构当作“当前 CPU”
```

所以，取当前 CPU 编号或 cpu 指针时，要关闭中断，并覆盖整个依赖“仍在这个核”的使用区间。只保护查数组的瞬间不够。

`myproc()` 在内部短暂关闭中断，取出 `c->proc` 后恢复先前的中断状态。返回的是 P 自己的进程结构；迁移只改变 P 在哪个核执行，不改变 P 的身份，因此这个指针不因迁移而失效。这里不是说任何进程指针都可以无锁访问全部字段，而只是说指针不受此次迁移影响。详细入口与 tp 的设置见课程资料 §7.4。

## 7. 首次运行不是凭空“返回”

新进程没有过去的 swtch 调用，所以 `allocproc` 构造一份可供恢复的 context：`ra` 指向 `forkret`，`sp` 指向其内核栈顶。恢复后，ret 跳入 forkret，先完成锁交接，再进入用户返回路径。

还需要区分两种用户初始状态：

- **fork 子进程：**复制父进程的 trapframe，并调整子进程应见的返回值，接着父进程原来的用户执行位置走。
- **启动时第一个用户进程：**没有父进程可复制，必须人工设置用户 EPC 与用户栈。

这揭示了一个通用实现思路：**把首次启动表示成一个特别构造的恢复状态，就能复用普通切换路径。**课堂的完整问答见译稿 84:00–91:27，包括为什么文件系统初始化要等到首个进程具备可睡眠的上下文。

## 8. 提纲补充与常见误区

官方提纲尾部还有课堂没有展开的几个问题。下面只作必要推理补充，不声称它们是视频中的完整讲授：

- **为什么 sched 只允许持有 p->lock？**若 P1 持普通自旋锁 L 让出，P2 随后在同一核上获取 L，acquire 会关中断并自旋；P1 无法恢复来释放 L，P2 也无法被定时器抢占，形成死锁。`noff == 1` 是这套调用契约的一项检查；它是关中断嵌套计数，不是通用的“所有锁对象个数”检测器。对应教材 §7.3 与源码 `sched` / `spinlock.c`。
- **为什么 scheduler 要允许设备中断？**若所有进程都等待 I/O，没有设备完成中断来唤醒它们，扫描进程表不会自动变出 RUNNABLE 进程。固定代码在外层循环调用 `intr_on()`。
- **内核执行中也能抢占吗？**可以；`kerneltrap` 只在满足条件时调用 yield。被打断的内核寄存器由 `kernelvec.S` 保存在当前内核栈，而不是覆盖已经保存用户状态的 trapframe。更完整的中断保存流程衔接[第 9 讲](#/c/mit-6.s081-2020/lec/lec09?v=notes)。

几条需要随时提醒自己的区别：

| 误解 | 应改成 |
|---|---|
| sleep 和 exit 都调用 yield 函数 | 都会让出 CPU，但固定源码分别设 SLEEPING / ZOMBIE 后调用 sched |
| RUNNABLE 表示“已经在运行” | 表示具备运行条件，正在等调度 |
| 一次系统调用一定切线程 | 可以不阻塞、直接回到原进程 |
| 中断关闭了，就不需要进程锁 | 关中断只限制本核，另一核仍可并行访问 |
| 视频说十毫秒，所以 xv6 时间片是十毫秒 | 课堂是举例；固定 start.c 配置 interval=1000000，注释约为 QEMU 的 0.1 秒 |
| 参考快照就是实验答案所用版本 | 固定提交只供源码核对，录课工作树与 thread 实验分支另有身份 |

## 9. 自测：能否预测失败点？

<details><summary>1. 把 swtch 中保存 sp 的指令删掉，其他寄存器都保存，为什么仍不行？</summary>

目标代码恢复了返回位置，却仍使用另一执行流的栈；它的局部变量、保存值和后续返回地址都无法对应。寄存器组与栈指针必须来自同一条暂停执行流。

</details>

<details><summary>2. 把 yield 的解锁移到 sched 前面，仅单核演示没出错，能证明正确吗？</summary>

不能。多核调度器可能在旧核尚未离开进程栈时接走同一进程。单核运行结果没有覆盖该不变量破坏。

</details>

<details><summary>3. swtch 返回到 sched，是否证明恢复了刚才那个 PID？</summary>

不证明。许多进程会在同一个函数位置暂停；要结合 context、栈和进程身份判断。课堂从 PID 3 切到 PID 4，两者都经过 sched。

</details>

<details><summary>4. P 从 CPU 0 迁到 CPU 1 后，哪些旧值还可靠：myproc 的返回值、mycpu 的返回值、内核 tp？</summary>

myproc 返回的 P 指针仍标识同一个进程；先前的 mycpu 返回值不能继续当“当前 CPU”；内核 tp 应表示新核身份，不能把旧 CPU 的 tp 当成必须恢复的线程私有状态。

</details>

<details><summary>5. 为什么新进程的 context.ra 不直接指向用户 main？</summary>

context 恢复的是内核执行。还必须交接进程锁、安排用户页表与返回权限、从 trapframe 恢复用户状态。直接以普通 ret 跳用户 main 无法完成这些要求。

</details>

<details><summary>6. 所有进程都睡眠时，scheduler 是否也必须找到一个进程才能前进？</summary>

它可以继续在自己的栈上运行扫描循环，并允许设备中断；外部事件处理可以使某个进程变成 RUNNABLE。scheduler 不属于必须有普通进程可运行才存在的执行流。

</details>
