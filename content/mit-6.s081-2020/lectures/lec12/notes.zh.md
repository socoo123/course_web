# 第 12 讲 · COW 难在保持语义，不只在推迟复制

这一讲最值得学的，不是一份最终补丁，而是怎样从**一个与预期不符的现象，走到可验证的原因**。同一个不完整的 COW 实现，先后表现为 fork 失败、写缺页、非法指令、启动 panic、内存耗尽、错误的文件描述符，以及非法用户指针导致内核 panic。它们并不是彼此无关的偶然故障。

## 2. COW 要同时守住三条约定

### 约定一：共享的是初始内容，不能共享未经允许的修改

fork 的应用语义仍然是：父子初始内容相同，但各自修改普通内存不会改变对方。COW 只是把“立即复制”换成“先共享，必要时分裂”。因此，只把子页表指向父物理页是不够的。

必须让所有相关写入路径都遵循分裂规则：

- **父进程与子进程的用户态 store：**两边的共享映射都要受到写保护。只保护子进程，父进程仍能直接破坏子进程看到的内容。
- **内核代用户写数据：**`copyout` 不能通过内核直接映射偷偷绕开 COW。必须先确保目标映射可按其语义写入，再执行复制。

课堂 `file` 测试揭示第二点的后果：被污染的不一定是最后一次 `read` 的数据缓冲区，也可能是**更早由 pipe 写回的 fd 数组**。错误发生在 A 操作，直到 B 操作使用被污染的数据时才显现。详见译稿 63:00–72:00。

### 约定二：放弃一个映射，不等于释放物理页

把一个用户页的共享引用数记作 $r$，一个最小例子是：

| 事件 | 旧物理页 | 新物理页 |
|---|---|---|
| 父进程最初拥有页 | $r=1$ | 无 |
| fork 让子进程也映射它 | $r=2$ | 无 |
| 子进程写入，复制并改用新页 | $r=1$ | $r=1$ |
| 父进程放弃旧映射 | $r=0$，可回收 | 仍由子进程拥有 |

这张表是机制推导，不是课堂新执行的一组测试。它说明：

1. **过早回收**会让别人的映射变成悬空引用，物理页内容可能被垃圾填充值或其他分配者覆盖。
2. **只增加、不完整地减少**会泄漏；课堂 `three` 第二轮耗尽内存，就是 COW 分裂遗漏旧页减引用造成的。
3. **计数是物理页层面的信息。** 同一个虚拟地址在不同进程中可以指向不同页，不能拿用户虚拟地址直接当全局物理页计数的身份。

还要注意计数的实现口径：课堂把计数放入整个物理页分配器，因此 `kalloc` 把页交给调用方时就设置初始引用，即使调用方还没把它放入用户页表。页表页、内核栈等分配器对象也会经过这套接口。不要机械地把每一时刻的计数都解释为“只数用户 PTE”，更不要把内核长期存在的直接映射也当成每页都多一个必须释放的用户引用。

### 约定三：新增的使用方式要满足旧函数的契约

原 `kfree` 接受一页并把它回收到空闲链表。课堂把它改成“减引用，归零才回收”，就改变了所有调用者共同依赖的约定。

最容易漏的是启动过程：`freerange` 在没有先调用 `kalloc` 的情况下调用 `kfree`，本来就是分配器的特殊入口。新 `kfree` 却要求计数至少为 1，所以启动就 panic。修复不是删除断言，而是让初始化流程也满足新的记账规则。

同理，从 `walkaddr` 改成 `walk` 不只是“得到更多信息”。前者会对过大的地址返回失败，后者在 `va >= MAXVA` 时 panic。使用更底层的接口，就要接过其调用前提。详见译稿 27:00–30:00、57:00–60:00、75:00–81:00。

## 3. 一张 PTE 中的“只读”，不能回答所有问题

读 PTE 时，应分开问：

1. 这个地址有没有映射，映射是否有效？
2. 用户是否有权访问？
3. 当前是否允许写？
4. 不允许写，是因为 COW，还是本来就必须只读？

前三问与 PTE 的存在性、V/U/W 位相关；第四问是页的语义。成熟系统可能需要额外的软件元数据。2020 COW 原页提示可用 PTE 的 RSW 位标记 COW，正是为了表达硬件权限位本身不直接表达的信息。

课堂 72:00–75:00 使用了“有效用户页且没有 W，就按 COW 处理”的捷径。这与它使用的简化地址空间相关。固定基础快照的 `uvmalloc` 给用户页分配 R/W/X/U 权限，能帮助理解背景；但固定快照**不是录课工作树或实验分支**，也不能证明另一年份代码具备相同假设。

同样，引用数与权限是不同维度：

- 引用数为 1，不说明 PTE 已自动恢复 W。其他共享者离开后，剩下的只读映射可能还在。
- 引用数大于 1，也不单独证明应该把某个映射变成可写。共享只读文本页未必允许修改。
- 替换物理页时，应维护该映射本来的权限语义；课堂直接组合 R/W/X/U 的中间代码不能作为普遍的权限策略。

这些是读懂课堂假设的边界，不是要求把本讲扩展成包含所有虚拟内存特性的系统。2020 原页明确要求从新鲜的 `cow` 分支开始，合并 lazy allocation 属于选做。

## 4. 为什么引用计数的锁必须放在正确位置？

设共享页计数为 2，两个核各放弃一次引用。如果两边都读到 2、各自计算 1、再写回 1，就丢失了一次减少。页已无人使用，计数却永远不是 0。这是共享的“读—改—写”操作需要同步的原因，和计算 `pa / PGSIZE` 本身无关。

同时，**任何破坏页面内容的操作都必须等到最后引用消失以后**。旧 `kfree` 为排错填充垃圾的 `memset`，不是无害的日志；把它放在引用检查之前，即使最后没有真正入空闲链表，也已经损坏了其他进程的数据。

课堂允许为计数单设一把锁，也允许用已有的 `kmem.lock`。关键是所有共享计数的访问遵循一致的同步和所有权规则。这里不重复锁教材，详见[第 10 讲课程资料](#/c/mit-6.s081-2020/lec/lec10?v=materials)；课堂具体提问在译稿 51:00–57:00。

## 5. 从本讲提炼一套排错动作

### 先写清“应该看到什么”，再读报错

清除写位之后，合理预期是用户 store 触发 `scause=15`（十六进制 `f`）。实际若是 `scause=2`，就不能把它泛称为“又一次 page fault”然后进入 COW 复制逻辑：2 是非法指令，12（十六进制 `c`）才是取指缺页。

把 `scause`、PID、`sepc`、`stval` 放在一起解释。`sepc` 是出问题的指令地址，`stval` 在这次写缺页里是目标地址；查哪一个 `.asm`，还取决于这个 PID 此刻是在 fork 后、exec 前，还是已经完成 exec。

### 静态文件与运行中内存是两种证据

第一次 `0x9da` 对不上 store，是查错了程序；切换 `sh.asm` 就能解释。后面的非法指令则可能来自内存已被踩坏，原文件的反汇编未必还对应 CPU 实际看到的字节。此时应查看实际内存，而不是强行用 `.asm` 解释一切。

### 每次观测只回答一个明确问题

`file` 排错链可以压缩为四个可检验的问题：

1. `read` 到底返回多少？——打印发现是 -1。
2. -1 来自 `fileread` 吗？——对应调用没走到那里，看到的正常值是 4。
3. 哪个参数检查失败？——`argfd` 发现当前进程没有 fd 9。
4. 9 从哪里来，为什么多个进程都看到它？——沿 `fds ← pipe ← copyout` 回溯，发现共享页被内核写回污染。

这比一开始就根据测试名修改 `read` 更有解释力。课堂没有逐个证明所有并发进程的精确执行顺序；“三败一成”为何恰好这样，不能靠补写一个未经观测的调度故事来伪装确定性。

## 6. 自测：判断机制，而不是背补丁

<details><summary>子进程清除了 PTE_W，父进程保留可写，共享页仍能正确实现 fork 吗？</summary>

不能。父进程可以直接修改原物理页，子进程会看到修改。父子共享期间都必须遵循相同的隔离规则；不能只拦截子进程的写。

</details>

<details><summary>一个物理页的计数从 2 降到 1，剩余进程下次写它还会缺页吗？</summary>

可能会。计数变化并不会自动改变另一份页表的写位。课堂没有主动寻找并恢复另一个映射，故它仍可保持只读。进一步利用唯一所有者避免复制，是另一个要明确设计的优化。

</details>

<details><summary>copyout 已经调用 cowfault 成功，为什么还可能污染父进程？</summary>

如果它继续使用处理前取得的旧 PA，数据仍会写入共享原页。处理成功后要根据更新后的映射取得目的物理地址。成功返回不是“所有局部缓存变量也自动更新”。

</details>

<details><summary>为什么不先用 memset 填充旧页，再查看引用计数决定是否真的释放？</summary>

填充本身就在修改页内容。计数尚未归零时，其他进程仍可能读它或从中取指；不把页插入空闲链表也救不回已经被覆盖的数据。

</details>

<details><summary>看到 PID 3 和一个 sepc，为什么不能立即去查 cowtest.asm？</summary>

PID 表示进程身份，不直接说明当前执行映像。shell 的子进程在 exec 前仍执行 shell 代码。课堂第一次缺页就在 `parsecmd` 的函数序言中。

</details>

<details><summary>cowtest 全过，能推出所有地址边界都正确吗？</summary>

不能。课堂后续 `usertests` 向系统调用传入超大指针，才揭示新 `copyout` 直接调用 `walk` 的 panic。官方 2020 要求本来就包括 `cowtest` 和 `usertests`，两者都要检查。

</details>

<details><summary>COW 让某次 usertests 的复制字节数下降约 90%，能否推出程序总耗时下降 90%？</summary>

不能。这是特定程序、特定统计口径的复制量，不是耗时。如果后来所有共享页都需要写入，复制工作仍要做，还多出缺页成本。应把复制量、峰值内存、fork 延迟与总运行时间分开测量。

</details>
