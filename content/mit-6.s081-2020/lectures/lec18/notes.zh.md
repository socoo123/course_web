# 第 18 讲 · 内核边界应当画在哪里

**本讲最重要的区分：接口能做什么、代码放在哪里、最终跑得多快，是三个相关但不相同的问题。** 微内核并不要求应用放弃文件、进程或 Unix 接口，而是尝试把这些高级服务的实现移到受控的用户态环境中。

## 1. 用三个问题分析一种操作系统组织

| 问题 | 单体 Unix 的典型回答 | L4 路线的典型回答 |
|---|---|---|
| 应用需要什么？ | 文件、进程、网络等高层接口 | 仍可需要这些接口，也可以直接使用专门服务 |
| 谁执行高级策略？ | 大量策略在内核中 | 用户态库、pager、OS 服务器等 |
| 谁最终实施隔离与资源转移？ | 内核与硬件 | 仍然是微内核与硬件，不是用户代码自行改硬件页表 |

把“用户态服务”理解成“普通函数库”，会漏掉独立地址空间的保护；把“有保护边界”理解成“自动安全”，又会漏掉授予服务的实际权限。

例如，论文的 Linux 服务器能访问整个 Linux 环境的内存，并复用大量驱动。它在用户态，并不表示 Linux 内部各子系统相互隔离。**L4 小，不等于整个可信系统只有 L4 那么大。**

课堂为何批评单体结构、又肯定 `exec` 的集成便利，见[中文译稿](#/c/mit-6.s081-2020/lec/lec18?v=draft) 00:00–15:00；论文究竟拆分到哪一层，见[课程资料](#/c/mit-6.s081-2020/lec/lec18?v=materials) §1、§3。

## 2. 推导：没有 fork 系统调用，仍能有 fork 服务

试着把“内核必须实现 fork”拆成真正需要完成的工作：

1. 建立一个新的受保护地址空间和执行线程。
2. 为新空间安排代码、数据、栈的映射。
3. 确定父子看到的内存语义，准备各自的寄存器状态和返回值。
4. 让新线程从合适位置开始执行。

其中，创建执行实体、受控映射和启动线程可以是微内核机制；哪些页共享、何时复制、父子关系如何登记，则由上层服务决定。若要做 COW，还必须能捕捉写故障、区分读写权限、复制并撤销相应映射，不能只共享页面就声称实现了 fork。

这是**机制与策略的分工练习**，不是本课现场演示过一份可运行的 L4 fork 程序。官方提纲列有更具体的 fork 步骤，而视频主要讲到建 task、映射、pager 与 Linux 服务结构；不能把提纲例子补成虚构的课堂操作。

pager 的本质也是这个分工：

> 故障线程触发异常 → L4 暂停它并送出缺页 IPC → pager 决定给什么页 → L4 检查并实施映射 → 故障线程继续。

检查这个链条时，要问的是“谁拥有这张页、谁同意映射、谁决定故障是否合法”，而不只是“消息发给谁”。机制详见课程资料 §2，课堂建任务与缺页推导见中文译稿 33:00–45:00。

## 3. IPC 优化的是一条完整路径

朴素请求—回复路径有四次独立系统调用、请求/回复的中间缓冲、多次复制，以及通用的睡眠与调度。L4 把常见模式收窄为“客户等待回复、服务器已等待请求”，才能用同步会合与直接交接缩短路径。

可以用下面的检查表分析类似优化：

| 要减少的工作 | 依赖的条件 | 不能因此声称 |
|---|---|---|
| 内核消息队列与中间复制 | 双方都已提供缓冲区，通信同步 | 永远不需要等待或调度 |
| 消息数据的内存复制 | 短消息能装入约定寄存器 | CPU 完全没有执行开销 |
| 大块数据复制 | 可通过页映射交付访问权 | 接收者读取数据也免费 |
| 多次用户/内核往返 | 合并 call、reply-and-wait | 请求与回复变成同一个方向 |
| 通用调度开销 | 已知且可运行的接收者等待消息 | 没有发生执行主体变化 |

因此，“同步”不是天然比“异步”优越。同步语义把某些状态变得确定，从而允许专门化；如果应用确实需要异步缓冲，就要在某个地方重新实现缓冲和相应资源管理。课堂完整路径与问答见中文译稿 45:00–63:00，语义不同的性能比较见课程资料 §5.1。

## 4. 两层线程，必须分别画账

读 L4Linux 时，建议脑中保留两张不同的表：

- **L4 的表**：有哪些 task、用户线程、主服务器线程、中断线程；它们的优先级和就绪状态是什么。
- **Linux 服务器的表**：哪些进程有尚未完成的系统调用，哪个内核协程等磁盘，哪个可以继续。

Linux 内部的 `schedule()` 切到另一个协程，不等于 L4 马上调度那个进程的用户线程。主服务线程阻塞，也不意味着所有 Linux 应用一定都不能运行。

论文尽量保留单处理器 Linux 的同步假设，所以没有简单把每个内核协程都替换成可独立调度的 L4 线程。这里讨论的是特定移植方案，不是“Linux 2.0 没有 SMP”的普遍历史断言；实际中断线程和调度级别见课程资料 §3.2，课堂见 69:00–78:00。

## 5. 推导：getpid 慢约 2.35 倍，应用为何可能只慢一点

下面是**编者用于理解测量的简化模型**，不是论文测出的时间构成。假设一个原生程序总时间为 $T$，其中比例 $f$ 是会被新边界放大的短调用成本，剩余部分完全不变；这部分成本放大为 $r$ 倍，则：

$$
\frac{T'}{T}=(1-f)+rf=1+f(r-1).
$$

用表 2 的时间比 $r=3.95/1.68\approx2.35$ 举例：若 $f=0.04$，整体约慢 $0.04\times1.35=5.4\%$；若 $f=0.5$，就会慢约 67.5%。同一个 IPC 实现，在两种工作负载中可以得到完全不同的应用代价。

实际系统还有缓存、调度、等待时间与不同系统调用的差异，不能反过来用 AIM 的 5% 数字精确推断 $f$。更不能把一次 `getpid` 的比值施加到所有内核代码上：较重的文件操作中，真正的文件系统工作可能并未按同样倍数增加。

这说明需要两类测量：**微基准找机制成本，宏基准看它是否重要。** 也解释为什么“IPC 很快”与“应用足够快”之间仍需要证据。具体测量平台、表 2–3、图 7–9 及各类百分比口径见课程资料 §4。

## 6. 一个比“硬件快于软件”更好的性能问题

dual-space mistake 的启发不是“不要用 MMU”，而是：**局部便利是否破坏了整条路径的复用？**

硬件翻译通常能凭 TLB 缓存映射取得优势。但如果为了让用户指针直接可用而扩张、复制服务器地址空间，导致每次调用都失去 small-space 优化并刷新 TLB，局部省下的软件查询就可能换来更大的工作集重建成本。

因此，比较两个方案时要数完整生命周期：建立映射、切换空间、保存缓存内容、首次访问重填、后续复用、撤销映射。不要只拿“单次硬件查询”和“单次软件查询”比较。

课堂课后问答见 84:00–90:00，论文精确失败链条及周期解释见课程资料 §3.4；最后关于 tagged TLB/small spaces 的追问见 93:00–94:19。

## 7. 常见误读速查

| 误读 | 修正 |
|---|---|
| 微内核不能支持 Unix 应用 | 高层接口可以由服务器提供；接口与实现位置分开判断 |
| L4Linux 把所有驱动都隔离为独立服务 | 论文保留一个大 Linux 服务器，驱动大多复用其中实现 |
| 服务在用户态就与普通应用同等无权 | 是否能访问内存、设备、控制中断，取决于授予的资源与权限 |
| 一个 Linux 主服务线程意味着没有其他线程 | 中断 top-half、bottom-half 及用户进程中的信号线程另有安排 |
| 缺页一定由一个系统级 pager 统一处理 | pager 可按线程关联，还能形成层次 |
| 图 8 横轴就是并发进程数 | 原文标注 AIM simulated load，不能凭提纲概括替换正式单位 |
| 95% 吞吐等于所有程序运行时间只多 5% | 吞吐比与时间比不同，工作负载与饱和点也不同 |
| 相同主频的处理器能直接比较架构优劣 | 表 6、SPIN 对照使用不同架构，需保留平台限制 |
| 微内核安全且性能可用，所以必然取代 Linux | 采用还取决于功能、兼容、工具与迁移收益；论文只解决部分问题 |

## 8. 自测：先回答，再展开

<details><summary>文件服务器能发映射 IPC，为什么不能据此读任意进程的秘密？</summary>

映射原语基于调用者已经拥有的页面和相应授权，并要求接收条件成立；它不是任意物理地址读写接口。但某个真实服务器若被授予所有用户内存，本来就处在更大的信任范围内。必须分析具体权限，不能只背“微内核安全”。

</details>

<details><summary>服务器未在 receive 等待时，客户端仍能走“直接返回到服务器”的同一快路径吗？</summary>

不能直接假定可以。同步语义要求会合；需要等待或处理其他状态。课堂优化以服务器闲时已阻塞在接收点为常见情况，并没有消除所有慢路径。

</details>

<details><summary>把 Linux 中每个等磁盘的内核协程改成独立 L4 线程，会自动更快吗？</summary>

不会。论文硬件单核，没有多核并行收益；原有同步假设还可能被破坏，需要新同步并增加切换成本。必须先判断解决的是阻塞、并发组织还是并行吞吐问题。

</details>

<details><summary>假设原来只有 1% 的时间受边界开销影响，这部分变成 3 倍，总时间变成多少？</summary>

在其他部分不变的简化假设下，$0.99+0.01\times3=1.02$，只慢 2%。若系统其他部分也变化，不能继续直接使用这个结果。

</details>

<details><summary>映射 RPC 的带宽达数千 MB/s，能否据此承诺应用按同样速度处理数据？</summary>

不能。测试主要支付映射和撤销的通信成本，没有支付生成或消费全部数据的工作。获取页面访问权与真正读取每个字节不同；缓存和应用逻辑仍会限制速度。

</details>

<details><summary>要验证“把 Linux 拆成多个服务器仍只慢 5%”，本文哪组实验足够？</summary>

没有一组足够。兼容实验测的是单 Linux 服务器；扩展实验提供局部可行实例。需要真正的多服务器实现、可比负载与通信路径分析，才可检验该新命题。

</details>
