# 第 18 讲 · 课程资料

## §1 研究问题：反驳的是“架构必然慢”

把 Unix 服务搬出内核，会增加地址空间边界与通信。早期实现的性能不佳，究竟说明这种结构不可能高效，还是说明当时的通信与内存管理机制没有做好？这是理解论文实验设计的起点。

作者使用第二代微内核 L4，将 Linux 改造成用户态单服务器，再分别与裸机 Linux、基于 Mach 的 MkLinux 比较。这样可以尽量保持上层 Unix 功能相似，集中观察底层机制的影响，而不是拿两个功能完全不同的操作系统比较快慢。[P18 §1–2，pp.1–2]

论文有两条证据链：

1. **兼容性能**：已有 Linux 程序不改业务逻辑，改跑在 L4Linux 上，损失多少？更快的微内核是否真的改善应用表现？把服务器塞回内核地址空间的 co-location，又能挽回多少？
2. **扩展价值**：如果只是慢一点地重复 Linux 功能，用户为什么迁移？论文另做直接 IPC、用户态分页、缓存分区实验，展示兼容层以外可获得的能力。

相关工作部分把讨论放在更大的设计空间里：一种路线认为微内核提供的层次过低，于是增加安全的内核扩展；另一种认为 IPC 等抽象仍过高，希望更直接暴露受保护的硬件机制。作者不是宣布这些路线都错，而是以实际系统检验“纯微内核也能有效工作”的可能性。

需要保留一个重要边界：**本文不是把 Linux 拆成了彼此隔离的文件、网络、驱动服务器。** 它复用的是一个大 Linux 服务进程。性能结果不能直接证明，进一步拆成多服务器、增加更多 IPC 后也会得到相同数字。

## §2 L4 提供哪些构造原语

### §2.1 地址空间不是由一个内置 Unix VM 统一安排

L4 的基本执行对象是地址空间中的线程，跨地址空间通信由 IPC 实现。RPC 可以在 IPC 上构造；“发送消息”是机制，“为客户打开文件”则是某个服务器赋予消息的含义。[P18 §3，pp.2–3]

地址空间可以由用户态服务器递归构造。初始地址空间 **σ0** 大体代表物理内存；持有页面的服务再把页面交给其他空间。可操作单位是大小为 $2^n$ 的 **flexpage**，范围从一个物理页到整个地址空间。

三种操作需要分开理解：

- **map**：把已有页映射给另一个地址空间，用于共享访问。
- **grant**：转交页面映射的控制，不能一概理解成发送者永远还保留访问。
- **unmap**：撤销由相关映射派生出的访问，可沿直接或间接的映射关系起作用。

这些操作使用调用者已经拥有的虚拟页，而不是接受一个任意物理页号。接收方还须同意接收。因此，“用户态能管理地址空间”不表示“用户态能随意取得机器上的任何物理内存”。

发生缺页时，L4 将故障作为 IPC 交给该线程关联的 **pager**。线程可以关联不同 pager，复杂系统也可以形成分页服务的层次。内核执行映射和保护，pager 决定是分配零页、共享页、读入文件内容，还是拒绝访问。论文按线程描述 pager 关联，比课堂按 task 概括更精确。

### §2.2 驱动、异常与处理器专用优化

I/O 端口也纳入可控制的地址空间资源；硬件中断变成发给相应线程的消息。这允许用户态驱动处理设备协议。对同步异常和 trap，Pentium 版本还把相应处理转到线程的用户态处理程序，提供系统调用兼容所需的入口。

L4 不是因为“用户态”三个字就让所有代码权限相同。论文移植可让有权限的驱动任务禁用中断，Linux 服务器也持有大量系统内存。评价安全性时，必须看实际授予了哪些资源，不能只看 CPU 执行模式。

Pentium 版本有 **small-address-space optimization**。当所使用的空间较小（文中给出 4 MB 至 512 MB 范围）时，利用共同页表映射与 x86 分段保护，避免某些地址空间交接中的 TLB 刷新，效果类似带标签的 TLB。默认所有小空间合计受 512 MB 范围限制；访问超出小空间后，可自动回到普通 3 GB 空间模型。这个优化改变实现成本，不改变给应用的逻辑功能。

这不是所有架构都照抄的一套机器码。论文还介绍 Alpha 21164、MIPS R4600 上重新实现 L4：逻辑 API 保持一致，寄存器、字长、调用编码以及内部算法按处理器优化。Alpha 版本使用重新实现的 PALcode；短小关键路径在其中完成，较长且需可中断的操作再转入一般内核代码。

## §3 Linux 单服务器怎样建立兼容环境

### §3.1 移植约束与两套页表账本

作者希望现成 Linux/x86 二进制可以运行，并尽量只修改 Linux 的架构相关部分；同时，不为 Linux 专门修改 L4。这既降低工程量，也检验底层 API 是否足够通用。[P18 §4–4.2，pp.3–5]

Linux 的进程与资源管理、文件系统、网络以及大量驱动属于可复用部分。所谓“架构无关”不等于“设备无关”：驱动仍依赖具体设备，但只要硬件平台相近，就可能在新移植中继续使用。

**图 1（p.4）画的是映射关系，不是调用顺序。** σ0 向 Linux 服务器提供内存；Linux 服务器再把其中页面映射给用户进程。箭头含义是 mapping，图中较小的用户空间方框不表示用户虚拟地址范围一定小于服务器。

真正的硬件页表由 L4 持有，Linux 服务器不能直接改。服务器保留原 Linux 风格的**逻辑页表**，记录自己认为的用户映射，再通过 L4 实施。原实现因此增加了一套页表账本，论文称页表占用约加倍；这不是所有内存占用翻倍。

### §3.2 一条主服务线程，加独立中断线程

系统调用和缺页等常规工作复用一个 L4 主线程；Linux 在其中切换多个内核协程，保存各个未完成调用的执行状态。某个调用等磁盘时，服务器仍能处理另一个调用，而无需把每个内部上下文直接做成一个 L4 调度实体。

**图 2（p.4）补上了“只有一个线程”这句话的限定。** 设备中断先到 L4，再作为消息送往相应中断线程；每个中断源有自己的 top-half 处理线程，另有一个 bottom-half 线程。它们优先级高于主服务线程，以保持所用单处理器 Linux 的执行顺序和同步假设。

因此，准确说法是“一个处理常规调用的 L4 主线程”，而不是“Linux 服务器地址空间里总共只有一个线程”。复用旧驱动时，硬件寄存器访问与底层设备支持基本保留，但中断到达方式改变了。

L4 实际调度用户线程。论文实现采用 10 ms 时间片，使用 256 级优先级中的四级：top half、bottom half、Linux 主服务、Linux 用户进程。用户进程基本按同级轮转运行，没有恢复传统 Unix 的动态优先级衰减策略。L4 并非完全没有供用户层调节优先级与时间片的能力；这是该 L4Linux 版本尚未完整重建 Linux 调度策略的问题。[P18 pp.5–6]

### §3.3 系统调用、信号与 copyin/out

论文同时支持三条系统调用路径：

1. 改过的共享 `libc.so`，直接通过 L4 IPC 调用服务器。
2. 改过的静态 `libc.a`，重新链接后采用同样的 IPC 路径。
3. 用户态异常处理 trampoline，接住原二进制的 Linux 系统调用 trap，再转入兼容库。

前两条较快，第三条保证旧静态二进制仍可运行。同一进程也可混用。兼容库负责通信，不把 `getpid` 等请求偷偷改成用户态缓存返回，因此短调用基准确实跨越服务器边界。论文的 trampoline 是 x86 Linux ABI 兼容机制，不是 xv6 RISC-V 的 `trampoline.S`。

**图 3（p.5）说明信号传送。** L4 不允许随意跨地址空间改另一个线程的 SP、PC，于是每个 Linux 用户进程有一个同地址空间的信号线程。服务器通知它，它再调整本进程主线程的状态，令主线程进入处理流程；必要状态保存后还能恢复。用户程序能破坏自己空间中的库或信号线程，但“终止进程”等全局效果仍由 Linux 服务器执行，不依赖目标进程善意配合。

服务器可访问分配给 Linux 环境的物理内存。在最终设计中，系统调用传来的用户虚拟地址先经服务器的逻辑页表转换成对应的服务器内地址，再做 copyin/out。IPC 因而可只传调用号、地址、长度等小参数，而不必把所有读写数据都塞进控制消息。

### §3.4 dual-space mistake：方便的硬件翻译为何输给软件翻译

原生 x86 Linux 常让用户映射和受保护的内核映射共存于活动页表。作者曾尝试在服务器地址空间中也映入当前客户的用户空间，让 copyin/out 直接使用硬件地址转换。[P18 §4.3，pp.6–7，图4]

问题链条如下：

1. 单个客户可能占用约 2.5 GB 用户空间，服务器可用地址空间约 3 GB，不可能同时容纳所有客户的完整映射。
2. 每次客户变化就重建映射显得昂贵，于是为每个客户复制一份服务器地址空间。
3. 各服务器空间共享同一份 Linux 代码和数据，但映射不同的客户内存；这还要求多条服务器线程及额外同步，才能维持单处理器 Linux 的正确语义。
4. 更致命的是空间变大，不能再用 small-space 优化。每次切换都需要刷新并重建 TLB 工作集。

图 4 中两条条带分别是用户进程空间和服务器空间，箭头表示内存读写；它不是“又复制了一份用户数据”的图。真正复制的是地址空间组织和线程，而 Linux 核心数据仍共享。

旧设计 `getpid` 约 18 µs，最终单服务器空间方案约 4 µs。作者还给出 Pentium 上的解释：页表项在 L2 中时，硬件 TLB miss 约 25 cycles；软件走逻辑页表约 11–30 cycles，取决于命中 L1 还是 L2。硬件翻译通常胜在 TLB 可复用，但失败设计恰恰每次把这份复用收益清掉。这里不能推出“软件翻译普遍快于硬件”，只能说要把切换与缓存后果一起计入。

### §3.5 工程量与兼容性证据

**表 1（p.7，单位为非空白、非注释 C 代码行）**：Linux/x86 架构相关部分约 4,500 行；L4 移植约 8,500 行，其中 2,000 行复用、6,500 行新写。表中另列 Linux 核心约 105,000 行、驱动约 232,700 行，用来显示复用规模，不能把 8,500 行误当作整个系统。

作者报告约 14 人月用于构建、稳定系统并准备论文实验，日常运行 X、Emacs、Netscape、X-Pilot，并能完成 AIM 压力测试。这是实用兼容性的证据，不是对所有 Linux 二进制的形式化兼容证明。[P18 §4.4]

## §4 兼容性能：先把实验条件固定下来

### §4.1 硬件、软件和测量误差

第 5、6 节主要实验使用同一台 **133 MHz Pentium**：ASUS P55TP4N 主板、Intel 430FX 芯片组、256 KB pipeline-burst L2、64 MB 的 60 ns Fast Page Mode RAM。L4 为 version 2；L4Linux 基于 Linux 2.0.21，MkLinux 基于 2.0.28。作者认为其间主要为不影响性能的修复，但二者不是逐字相同的版本。[P18 §5.1，pp.7–8]

比较组包括原生 Linux、用户态 L4Linux、用户态 MkLinux，以及 **co-located MkLinux**：后者把 Linux 服务放入微内核地址空间并在内核态执行。这样可降低部分通信代价，却削弱服务器与微内核之间的隔离边界。

对只有 1–5 µs 的短操作，重复测量得到很小标准差，仍不代表测得“真实绝对开销”。测量代码与被测代码的缓存冲突、对计时本身开销的估计，都会形成系统性偏差。因此作者并列紧循环计数、lmbench、hbench:OS，而不是只给一个漂亮的误差条。

### §4.2 表 2 与图 5：getpid 的 303 个额外周期

表 2（p.8）使用紧循环重复最短系统调用，通过 Pentium 周期计数器测量：

| 实现 | 单次耗时（µs） | 周期（cycles） |
|---|---:|---:|
| 原生 Linux | 1.68 | 223 |
| L4Linux，共享库路径 | 3.95 | 526 |
| L4Linux，trampoline | 5.66 | 753 |
| MkLinux，内核内服务器 | 15.41 | 2050 |
| MkLinux，用户态服务器 | 110.60 | 14710 |

L4Linux 快路径比 Linux 多 $526-223=303$ cycles，约为原来的 2.36 倍周期；trampoline 另加 227 cycles。MkLinux 的 co-location 明显有用，但仍远慢于用户态 L4Linux，说明“把服务挪回内核”不能替代高效的底层设计。

**图 5（p.8）**把 526 cycles 拆成进入兼容库 20、请求方向 168、Linux 工作 131、回复方向 188、离开库 19。两段 IPC 合计 356 cycles。原生 Linux 的基础进入/退出模式开销为 82 cycles；扣除边界成本后，两边剩余部分分别约 141 与 170 cycles。因此，额外成本主要集中在跨域路径，而不是 Linux 的 `getpid` 逻辑突然膨胀。

作者还统计除去中间 Linux 逻辑后的兼容路径占 45 条 cache line，约为一级缓存的 9%。优化不只是少几个函数调用，还包括控制代码工作集。

### §4.3 表 3 与图 6：不同操作的损失不一样

表 3（p.10）列出 lmbench 与 hbench:OS 的 OS 相关部分，覆盖空调用、进程创建、mmap、上下文切换、pipe、UDP/TCP 及 RPC、文件和映射重读。**延迟单位是 µs，带宽单位是 MB/s，括号里是标准差的百分比**。这些括号不是相对 Linux 的减速百分比。

用几个条目观察结构比只背一个“平均慢几成”更有用：

- lmbench 的 `/dev/null` 写延迟从 2.00 到 5.26 µs，短路径很容易显出额外边界成本。
- 两进程切换从 7.00 到 16.22 µs，表明线程交接相关开销确实存在。
- 文件 reread 带宽为 41.51 对 40.43 MB/s，差距很小；而 TCP 带宽为 18.03 对 13.23 MB/s，不能据文件缓存结果推断所有 I/O 都差不多。
- hbench 的 4 KB mmap 为 25.2 对 35.0 µs，8 MB mmap 却为 53.7 对 54.0 µs。负载规模不同，固定成本占比就不同。
- hbench 测得 `getpid` 为 1.69 对 4.55 µs，与表 2 的 1.68 对 3.95 µs 不完全一致，正是作者保留多种测量方法的理由。

**图 6（p.9）**把 lmbench 结果按原生 Linux 归一化。横向柱的数值是无量纲的 slowdown；延迟越大越差，带宽则取反向比例后再画，所以两类指标都是柱越短越好，Linux 基准为 1。图中部分极慢结果用越界标注表示，不能把绘图区右边缘当作实际最大值。

本页用文字分析代表项，不把整张表重新复制；完整数值与每项标准差可定位原文 p.10。图 6 的用途是看性能形状，不是把所有指标平均成一个总分。

### §4.4 图 7–9：应用级别的代价与坐标含义

**图 7（p.9）**测重新编译 Linux 服务器所需的实际经过时间，单位为秒：Linux 476 s；L4Linux 506 s（+6.3%）；trampoline 版本 509 s（+6.9%）；MkLinux 内核内版本 555 s（+16.6%）；用户态版本 605 s（+27.1%）。短调用几倍的差距，没有等比例传递到完整编译任务。

另一个宏基准是 AIM Multiuser Benchmark Suite VII。它使用混合负载逐步增加系统压力，并寻找最大吞吐量；作者声明这些结果**没有经过 AIM Technology 认证**。AIM 动态链接共享 libc，因此 L4Linux 在这里不承担旧静态二进制的 trampoline 路径开销。

看图 8、9 时要分清：

| 图 | 横轴 | 纵轴 | 正确读法 |
|---|---|---|---|
| 图 8，p.9 | AIM simulated load，AIM 负载单位 | Real time，一次基准运行的经过时间；原图没有标明时间单位 | 同一负载下越低越好；不自行把横轴改成进程数，也不擅自给纵轴补单位 |

MkLinux 曲线较早结束，是因为基准达到该系统最大吞吐附近就停止增加负载，不表示图中遗漏后半段记录。

论文正文报告的最大吞吐是：原生 Linux **130 jobs/min**，L4Linux **123 jobs/min**，MkLinux 内核内 **95 jobs/min**，用户态 **81 jobs/min**。L4Linux 约保留原生的 95% 吞吐。不要把这项“约 5% 吞吐损失”与所有负载的运行时间差混用：论文另报 L4Linux 跨负载平均运行时间慢 8.3%，最大负载处慢 6.8%。MkLinux 用户态相应为平均慢 49%、最大负载处慢 60%，内核内为 29% 与 37%。

这些结果支持“在这套实现、硬件与负载下，兼容层典型成本约 5%–10%”。它们不证明任意应用、任意微内核、任意服务拆分都只损失这个比例。[P18 §5.3–5.4，pp.8–10]

## §5 扩展性能：不要把不同语义当成同一个接口

### §5.1 管道、RPC 和映射传输

第 6 节先说明：以下是具体可行实例，尚不知道对大型系统的总体收益。作者比较传统 Linux 管道、L4 用户态管道模拟、同步 RPC、通过页映射完成的 RPC，观察绕开兼容服务器后能得到什么。[P18 §6.1，p.11，表4]

L4 的 IPC 本来同步，用户态管道模拟需要额外线程负责缓冲，才可提供接近 POSIX 的异步管道语义；论文明确说它**不支持 signaling**。同步 RPC 则直接使用阻塞式通信，没有管道缓冲，因此并非语义完全等价的替代。

| 代表路径 | 表 4 延迟（µs） | 带宽（MB/s） | 解释 |
|---|---:|---:|---|
| 原生 Linux pipe | 29 | 41 | 通用管道 |
| L4Linux 的 Linux pipe | 46 | 40 | 仍经过 Linux 服务器 |
| 用户态直接 L4 pipe | 22 | 48–70 | 在 L4 IPC 上补缓冲语义 |
| 同步 L4 RPC | 5 | 65–105 | 改用同步请求—回复语义 |
| 同步 mapping RPC | 12 | 2470–2900 | 改变映射而非复制全部字节 |

表 4 的其余对照包括 trampoline pipe（56 µs、38 MB/s）、MkLinux 用户态 pipe（722 µs、10 MB/s）和内核内 pipe（316 µs、13 MB/s）。这些是该表自己的测量，不应拿表 3 中不同测量结果替换。例如表 3 的 L4Linux pipe 延迟为 52.07 µs，不是表 4 的 46 µs。

延迟测试通常用 1 字节反复 ping-pong；**映射路径改为一页**，而且计入之后 unmap 的成本。带宽测试约传 50 MB，以 64 KB 块传递；映射用对齐的 64 KB 区域。表中只测通信，不测生成和消费数据的成本。

因此，2470–2900 MB/s 不是那台 Pentium 突然拥有相应的数据复制吞吐。接收者获得的是页面访问权，真正读取数据仍须走存储层次。作者还分析 L2 直接映射缓存的冲突、目的区预读，以及测试反复发送相同 64 KB、接收方不真正读取内容的特性。只看“复制一次或两次”不足以解释全部带宽差异。

### §5.2 用户态分页操作：Fault、Trap 与 Appel 测试

表 5（p.12）使用处理器时间，单位 µs：[P18 §6.2，pp.11–12]

- **Fault：6.2 µs，Linux 对照为 n/a。** 完整路径包含故障指令、page fault、给独立 pager 的 IPC、映射一张已有页，并最终完成原指令。n/a 表示标准接口没有这项对等能力，不是零耗时。
- **Trap：L4 3.4，Linux 12。** 从写一个写保护页到进入相应处理程序，不等同完整故障恢复时间。
- **Appel1：L4 12，Linux 55。** 访问随机受保护页；处理程序解除该页保护、保护另一个页，然后继续。对应 `trap + prot1 + unprot`。
- **Appel2：L4 10，Linux 44。** 先保护 100 页，再随机访问；每次故障解除当前页保护并继续，对应批量保护摊入的 `protN + trap + unprot` 模式。

L4 版本把专用 pager 关联给测试线程。它处理自己能解决的故障，把不能解决的继续交给 Linux 服务器。这展示了服务层次的组合，而不是用“所有故障都成功映射同一页”的玩具方案替代全部 Linux VM。

Appel/Li 原论文的机制背景由[第 17 讲课程资料](#/c/mit-6.s081-2020/lec/lec17?v=materials)负责；这里仅解释本篇重复这些测试的目的与结果，不重复整篇阅读。

### §5.3 缓存分区：实时系统关心最坏情况

实时任务的关键不是平均有多快，而是能否在最坏情况下按时完成。另一个任务占用了同样的 cache line，即使 CPU 调度时间分配准确，也可能通过缓存扰动显著延长运行时间。[P18 §6.3，p.12]

论文用用户态内存管理 pager 控制物理页的选择，从而对 L2 缓存占用进行分区。一个 64×64 矩阵乘法在不受干扰时耗时 10.9 ms；每 100 µs 被制造缓存冲突的合成负载打断时，最坏执行时间变成 96.1 ms。分区后，pager 从总计 64 个 secondary-cache pages 中给矩阵计算独占 3 个，最坏时间降到 24.9 ms。

这仍比无干扰慢，因为没有消除 L1 干扰，也没有让 64 KB 工作集完全免于 L2 miss。论文列出的 slowdown 为 8.85 和 2.29；从公开四舍五入后的时间计算会有少量差异，不应假装拥有更精确原始数据。

“快约四倍”比较的是受干扰的两种最坏情况，不是平均吞吐量；也不是整个系统获得免费加速。给实时任务保留资源会减少分时任务可用资源。它展示的是：不同策略可以在同一 L4 上共存，并由用户态服务实施，而不必让所有应用接受一套固定 Linux 内存策略。

## §6 替代方案：更低层或放进内核，一定更快吗

### §6.1 PCT 与 IPC 的比较必须数同等工作

**Protected Control Transfer（PCT）** 是通过被调方定义的入口进行受保护的跨地址空间控制转移，接口比带同步和消息语义的 IPC 更低层。作者最初估计 PCT 可能明显更快，但优化后的 Alpha 21164 实现缩小了差距。[P18 §7.1，pp.12–13，表6]

表 6 的单位是 **cycles**，平台是 **Alpha 21164**，不是前面的 133 MHz Pentium。最终 PCT 为 38 cycles，IPC 为 45 cycles；进入/离开 PAL mode、建立/关闭栈帧、切换地址空间号等占了共同成本。多出的 IPC 工作包含接收条件检查、参数保存、调度状态等，为同步、消息传送及线程执行提供支持。

不能看到差 7 cycles 就认定 PCT 的完整服务一定快。若服务需要同步、消息与执行栈，低层原语之外仍要补上这些工作。表的 PCT 假设还包括入口位置已由内核维护、被调用方能够指定或验证栈、需要保存返回信息；用户态身份验证所需周期没有算进去。

两种模型的资源特征也不同：PCT 让同一线程进入另一个空间；IPC 在发送线程与接收线程之间传消息。若要在服务器中同时保有 $n$ 个活动 RPC，IPC 模型需准备相应线程资源；PCT 主要需要用户态栈。反过来，预先分配接收线程和栈，也方便为实时客户保留服务资源。这是语义与资源组织的权衡，不是单个延迟值能决定的。

论文还提到 **Clans & Chiefs**：跨 clan 边界的消息被内核强制转送到用户态 chief，便于实施访问控制或将远程消息交给网络服务器。这里是当年 L4 的安全与转发机制，不能直接称为所有现代 L4 的通用接口。

### §6.2 Grafting 的成本从哪里来

把扩展代码下载进内核可以减少用户/内核与地址空间切换，但扩展必须完全可信，或通过语言、检查、事务、沙箱等方式限制行为。论文讨论 Vino、Exokernel 和 SPIN，是为了问：这些机制的总成本，是否必然小于用户态服务加高效 IPC？[P18 §7.2，pp.13–14]

SPIN 的虚拟内存微基准表面上比本文的 L4 数值慢 2–4.7 倍，几何平均约 3.1 倍；但作者明确警告，SPIN 在 133 MHz Alpha 21064，L4 在 133 MHz Pentium。即使主频相同，也不是同一机器，不能把这个比值当作架构优越性的严格证据。

论文因此保留问题：内核扩展是否能超过微内核路线，仍未定论。用户态 L4Linux 超过 co-located MkLinux，也只说明 co-location 本身不足以弥补一个低效基础实现，不等于证明 co-location 在任何快速微内核里都没有用。

## §7 可以带走哪些结论，哪些仍未证明

1. **较快的底层机制会传递到真实应用。** L4 与 Mach 上的 Linux 环境比较，说明不能只用旧系统的 IPC 结果给整个微内核路线判定上限。
2. **兼容性可用较小的应用级性能代价取得。** 但 5%–10% 是这套单服务器系统及所测负载的范围，不能推广成任意微内核的固定税率。
3. **小接口可以容纳不同策略。** 用户态 pager、专门化通信和缓存分区给出具体证据；扩展部分主要是实例，未测出所有大型应用的总体收益。
4. **比较前先对齐语义和平台。** 异步管道不等于同步 RPC；映射访问权不等于搬运字节；最坏时延不等于平均吞吐；相同 MHz 不等于相同硬件。
5. **尚未由本文证明的事情**包括：多服务器拆分后的整体性能、现代多核上的可扩展性、整个 Linux 服务的故障隔离与恢复、完整安全证明，以及现代 CPU 上是否保持相同比例。

论文 §8（p.14）把这些结果作为继续探索“专用应用与普通 OS 共存”的理由，而不是宣布研究结束。可用性段落给出当年的发布地址；pp.14–15 的致谢和 36 项参考文献已阅读核对，但不作为另行完成这些外链论文阅读的证据。
