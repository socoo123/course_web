# 第 21 讲 · 网络系统要保证谁能前进？

本讲串起两个问题：**字节怎样交给正确的应用？系统怎样在输入过量时仍完成有用工作？** 前一个问题靠协议与寻址，后一个问题靠调度。认识每一层头部，不等于已经理解每一层何时获得 CPU。

## 1. 四种名字，不要混成一种地址

| 信息 | 主要回答的问题 | 作用范围 |
|---|---|---|
| 以太网目的地址 | 当前链路上交给哪个接口？ | 当前一跳／LAN |
| IPv4 目的地址 | 最终要到哪个 IP 端点，下一跳怎么选？ | 跨网络路由 |
| UDP 目的端口 | 目的主机内应交给哪个协议端点？ | 本地主机的传输层分派 |
| 文件描述符 | 当前进程怎样访问自己的 socket？ | 当前进程 fd 表 |

ARP 连接的是“本地链路的 IP 下一跳”与“该下一跳的 MAC”，并不在整个互联网查找最终服务器的 MAC。

**推演一次远端 UDP 发送：**先用路由信息选本地网关；取得网关的 MAC；外层以太网目的地址填网关，IP 目的地址仍填远端服务器；UDP 目的端口填远端服务端口。路由器逐跳更换链路封装，直到最终网络可以把包交给目的主机。

原片的逐字节演示与实际地址见[中文译稿](#/c/mit-6.s081-2020/lec/lec21?v=draft) 12:00–39:00；这里不再复制整份抓包。

## 2. 用字段计算，而不是凭外观猜包边界

对于课堂那份没有 IP options 的包：

$$
\text{UDP 头起点}=14+20=34\text{ 字节},\qquad
\text{UDP 负载起点}=34+8=42\text{ 字节}.
$$

这是针对该包的计算，**20 字节不是所有 IPv4 头的固定长度**。实际解析要先检查足够的缓冲长度，并按协议字段判断头长与总长。

再看两个很容易混淆的数量：

- IP 协议号 `0x11 = 17`，说明后面是 UDP；不是“UDP 端口 17”。
- 示例 UDP 长度 `0x001b = 27` 包含八字节 UDP 头，所以应用负载为 19 字节；`tcpdump` 上的 `UDP, length 19` 并不与头里的 27 冲突。

接收时每层检查并剥离本层头，发送时反向添加。ARP 是以太网中的一种负载，IP 是另一种；不要画成所有包都按“以太网→ARP→IP”依次解析。

## 3. 分层图与执行图回答不同问题

协议分层解释“哪个模块懂哪些字节”。执行图解释“谁在什么时候运行”。同一个网络线程可以调用 IP、UDP、socket 入队函数；一个协议层也可能涉及中断、线程、定时器等多个上下文。**协议层数不等于线程数。**

课堂典型执行路径为：

```text
NIC → 接收处理 → 输入队列 → 网络线程 → 出口队列 → 发送处理
                              └→ socket 队列 → 用户应用
```

队列让各段可以分别调度，吸收短时突发，也让 CPU 与 NIC 的工作重叠。代价是需要确保消费者获得资源：队列只能延迟出现拥塞，不能从根本上弥补长期服务能力不足。

若输入平均速率为 $\lambda$、可完成速率为 $\mu$，且持续 $\lambda>\mu$，大小为 $B$ 的额外缓冲大致只增加

$$
\Delta t\approx\frac{B}{\lambda-\mu}
$$

的积压时间。这个编者简化模型假设速率恒定、每包大小不影响计数；它说明加缓冲主要应对暂时突发，不会把持续过载变成可持续无损状态。

课堂控制流与缓冲讨论见中文译稿 48:00–60:00；论文的具体优先级与队列见[课程资料](#/c/mit-6.s081-2020/lec/lec21?v=materials) §2。

## 4. 一个最小模型解释“CPU 越忙，完成越少”

以下为编者建立的两阶段模型，不是论文原始拟合公式。假设单 CPU 每秒有 1 秒可用时间：

- 每个到来的包都必须先花 $a$ 秒做高优先级接收处理；
- 每个最终完成的包还需 $b$ 秒做后续处理；
- 输入速率为 $\lambda$，有效完成速率为 $T$。

轻载时可完成所有包，总需求为 $\lambda(a+b)$，容量约为 $1/(a+b)$。越过这一点后，若仍给每个新包绝对优先接收，留给后级的时间只有 $1-\lambda a$，因此：

$$
T\le\min\left(\lambda,\frac{\max(0,1-\lambda a)}{b}\right).
$$

当 $\lambda$ 从容量继续上升，右边第二项反而下降；到 $\lambda\ge1/a$ 时，后级完全没有时间。**不是硬件容量会随负载自然下降，而是调度让越来越多资源花在最后会丢掉的工作上。**

真实系统还包含中断批处理、多个队列、变动的每包成本等，所以不能拿这条直线精确拟合论文散点。课堂的 5000 包／秒→200 微秒换算，也只有在主机每包处理成为瓶颈时才成立。见中文译稿 69:00–81:00；精确测试条件与原图边界见课程资料 §5–6。

## 5. 四个控制点，各保护不同的进度

| 机制 | 控制什么 | 单独使用仍可能漏掉什么 |
|---|---|---|
| 忙时轮询、闲时中断 | 不让重复接收中断任意抢占协议处理 | 单个回调仍可能无限取包 |
| 每次回调的配额 | 让不同接口及发送完成获得机会 | 网络线程仍可能饿死应用 |
| 下游队列反馈 | 下游积压时暂停上游，让消费者追上 | 与网络无关的用户任务仍需 CPU |
| 网络 CPU 预算 | 为其他用户工作保留执行机会 | 网络丢包仍会影响远端交互 |

“把一个包处理到底”应读成尽可能完成已接受的有用工作，并给必要后级资源，不是要求在任何情况下无限阻塞直到远端应用收包。一个出口比入口慢、一个应用停止读取，都仍需要等待或丢弃策略。

判断优化有没有成功，可以按顺序问：**最终完成量是否保持？谁还会饿死？丢包在投入多少资源之后发生？轻载是否仍能迅速醒来？**

## 6. DMA 与通知是两条不同的线

DMA 解决“谁搬字节、搬到哪里”；中断解决“什么时候通知 CPU 有事件”。因此关掉 NIC 的中断不等于关闭 NIC 接收，也不等于停止 DMA。设备可以继续接收，并在自身队列或主存接收环中等待软件处理；可用空间耗尽后才出现相应丢弃。

课堂把 DMA ring 先画成缓冲指针数组，是理解地址交接的起点；实际描述符还包括状态等字段。驱动需要从这些状态知道硬件是否完成，以及何时能重用缓冲。缓冲还被硬件使用时就释放或改写，会破坏这份交接关系。

课堂旧 NIC 复制模型、E1000 环与 DMA 问答见中文译稿 57:00–69:00。讲者对 DMA 地址翻译的回答有明确不确定性；不应把它读成“设备地址一定就是进程虚拟地址”或“所有平台都自动缓存一致”。

## 7. 自测：把错误解释改成完整解释

<details><summary>1. 我给远方 DNS 服务器发包，ARP 请求里查询的应当永远是 DNS 服务器的 IP 吗？</summary>

不是。先看路由结果。远端通常经由本地网关，当前以太网帧需要的是网关的 MAC，所以查询本地下一跳；IP 目的地址仍保持为 DNS 服务器。

</details>

<details><summary>2. 输入超过容量时一定丢包，因此图中输出下降也合理，对吗？</summary>

持续过载下丢弃一部分合理，但已能完成的吞吐不应仅因额外输入继续增加就崩塌。理想目标是在容量附近保持平台；下降提示资源被无效前置工作或不公平调度吞掉。

</details>

<details><summary>3. 我删除了 IP 输入队列，直接从接收回调执行 IP，然后一直处理到 NIC 空，是否已经解决活锁？</summary>

没有。NIC 在持续高负载下可能永远不空，发送完成回调与其他接口得不到机会，输出队列继续满。论文无配额轮询正暴露这种问题；必须为每次服务设置边界，并轮转必要阶段。

</details>

<details><summary>4. 网络线程以满速转发，能否证明普通应用也有公平的 CPU 时间？</summary>

不能。网络内部进度与普通进程进度是不同要求。论文还要增加网络 CPU 预算；涉及包消费者时，也可通过消费者队列反馈暂停上游。

</details>

<details><summary>5. 两个包都被丢了，一个在 NIC 满时丢，另一个在执行完 IP 后丢，有区别吗？</summary>

有。后者已消耗主机复制、协议检查、队列等资源。持续过载时，这些浪费会挤掉本能完成的包。尽早丢弃的价值是保护有效处理能力，不是保证永远不丢包。

</details>

<details><summary>6. 图 7-1 的 threshold 25% 表示给用户程序 25% CPU 吗？</summary>

不是，它是网络处理预算。高负载下对应用户程序约 65% 可用 CPU，而非精确 75%；系统开销、发送处理与批次检查粒度等造成差别。见课程资料 §8。

</details>
