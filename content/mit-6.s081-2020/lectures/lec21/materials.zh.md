# Receive Livelock：接收工作为何能饿死整个系统

## 1. 问题定义：吞吐量要数完成的包

“收到了多少包”不能独自说明网络系统工作得好不好。路由器只有把包送出出口，才完成一次转发；端系统只有把包交给需要它的消费者，网络处理才产生应用价值。如果 CPU 不停响应输入，后续协议或应用却没有机会运行，机器可以极忙而有效吞吐量趋近零。

论文把这种状态称为 **receive livelock（接收活锁）**。它区别于死锁：外部输入下降后，系统通常可以重新前进，不需要打破循环等待；过载期间停滞的原因是资源持续被输入侧占用。

### 1.1 为什么原有中断设计会失效

中断有很好的轻载性质：没有事件时不用反复检查设备，事件发生后又能迅速响应。早期操作系统面对的磁盘等设备，事件频率相对低，而且磁盘完成中断通常对应操作系统先前发出的请求；系统能通过控制请求量影响完成事件量。

网络接收不同。别人可以主动向本机发送数据，广播、组播甚至会把不感兴趣的流量送到本机。RPC、实时媒体等业务也未必采用能约束输入的端到端流控。输入事件率提高后，固定高优先级的接收处理就可能占满系统。只提高硬件速度可以推迟饱和点，不能消除“任何有限容量都可能遇到过载”的问题。

### 1.2 应用与设计要求

作者从三类实际应用中遇到问题：通用操作系统构建的路由器／防火墙、混杂模式的被动网络监测，以及 NFS 等网络文件服务。论文的测量重点选在主机式路由器，因为其最终完成量容易数清楚。

目标不只是提高峰值，还包括：

- **过载仍能保持吞吐。** 输入低于最大无损接收率 MLFRR（Maximum Loss Free Receive Rate）时应基本都能完成；高于它时可以丢包，但完成速率不应向零坍塌。
- **控制延迟与抖动。** 不应为了处理后来的一大串输入，把先到且已处理一部分的包长期搁置。
- **让必要参与者都前进。** 接收、发送、协议处理、其他 I/O、系统维护和用户进程都需要资源。
- **避免把局部过载传播到网络。** 路由控制消息被大量丢弃或延迟，可能让其他节点误判链路失效，触发更多控制流量，形成不稳定反馈。

这些是设计目标；后面的实验直接测得的是转发速率与用户进程可用 CPU，并没有逐一测量上述所有指标。

## 2. 三种病态行为与优先级根源

### 2.1 接收路径的“优先级下降”

4.2BSD 风格的输入路径可以概括为：

```text
接收设备中断 → 驱动取包／链路处理 → ipintrq
                                     ↓
                               IP 协议处理
                                     ↓
                              出口发送队列 → 发送完成处理
```

驱动运行在设备中断优先级 `SPLIMP`；IP 软件中断运行在较低的 `SPLNET`。Digital UNIX 的相近结构则将 IP 处理放在线程中，IPL 为 0。普通进程调度器并不能把设备中断当作普通线程来公平分时。

各阶段间的有界队列可吸收突发，但满了就只能丢包。原设计尽快把数据从小容量 NIC 缓冲搬到主存，避免设备溢出，这个局部目标合理；问题是它被赋予了压倒后续处理的优先权。队列并没有创造 CPU 时间，也没有保证消费者能运行。

**图 6-2，PDF p.9：**原图纵向箭头表示中断优先级递增，不是时间轴。接收处理高于 IP 转发，发送处理也有自己的执行位置；图中的 `ipintrq` 与输出 `ifqueue` 是两条不同队列。看图时应问各队列的消费者是否真能获得运行机会，而不只是顺着箭头读数据流。

### 2.2 Receive livelock

输入高到驱动始终有工作后，较低优先级的 IP 处理不再运行。`ipintrq` 满了，但驱动仍花时间取包，最后发现无法入队而丢弃。已投资的 CPU 工作全部变成浪费。

中断批处理可以摊薄每次进入中断的固定开销，提高 MLFRR；然而如果批处理本身无限占用高优先级执行，仍会饿死后级。因此“每包少一次中断”与“保证后级前进”不是同一个结论。

### 2.3 延迟放大

一个突发中的首包已经到达，系统却先对整个突发做高优先级链路处理，再处理首包的高层协议。首包的有效交付时间因此被后来的包推迟。以多条 NFS RPC 请求为例，本可开始磁盘工作的请求被挡在前面，磁盘却还闲着。

论文用这个机制说明中断并非在所有负载下都保证低延迟；本篇没有给出覆盖所有修改方案的独立延迟分布曲线。

### 2.4 发送饥饿

完成发送不只是把包塞进队列。还要把包交给接口、获知发送完成、回收描述符或缓冲，并给硬件提供后续数据。若接收优先级总高于这些操作，就可能发生出口有待发包而发送器空闲。

即使收发中断等级相同，驱动若总先处理接收、永不返回发送处理，也会出现同样问题。后文的“无配额轮询”正说明去掉硬件中断抢占以后，协作式代码内部仍可能把发送饿死。

## 3. 作者提出的调度工具

### 3.1 限制输入活动，而不是无限优先抢救新包

系统可以从队列满、上层无进展、CPU 占用等信号推断过载，并暂时抑制输入中断或输入处理。已经在内部队列中的包代表投入过的工作；与其继续接新包、再在内部丢弃，不如先完成旧包。

恢复输入也需要条件：内部缓冲腾出空间，或定时器到期。只有“关掉”没有“何时重新开启”，会把减载机制变成永久停收。

如果有细粒度时钟，可以累计网络处理消耗的 CPU 周期；没有时，也能用时钟中断采样等粗略办法估计。但这些是机制选项，不是论文主实验里每一种都同时使用。

### 3.2 中断与轮询混合

纯定期轮询有一个两难：轮询太频繁会浪费 CPU，太稀疏又增加事件响应延迟。因此作者采用混合模式：没有待处理工作时允许中断；中断只启动轮询；轮询期间抑制相应设备的后续中断；待处理工作全部完成后再恢复中断。

高负载下，输入本来就几乎总是存在，轮询有用且可以显式分配处理机会；轻载下，睡眠加中断保留快速唤醒的优势。轮询在这里更重要的作用，是为公平调度提供一个可控位置，而非单纯“忙等更快”。

### 3.3 避免前级任意抢占后级

论文讨论两条一般路线：

1. 把几乎全部包处理放在高 IPL，尽量把一个包处理到底，不让下一次输入抢占；但仍需另加办法保证用户进程前进。
2. 在高 IPL 几乎不做工作，只设置需要服务的状态并调度线程；主要包处理在线程中完成。

作者实现采用第二条。两种路线都可以省掉驱动到 IP 之间的排队与软件中断开销，但不能消灭所有队列：等待用户进程读取、等待 IP 分片重组、等待出口发送，都仍有需要排队的理由。

## 4. Digital UNIX 实现：回调、配额与尽早丢弃

系统启动时，修改后的驱动向轮询系统注册接收、发送以及重新使能中断的回调。中断处理只登记某个接口需要服务，并在必要时调度轮询线程，随后保持该设备中断未重新使能。

线程检查已注册设备中哪些需要服务，再调用对应回调。接收回调直接调用 IP 输入处理，而不是把包放进 `ipintrq` 等待另一段处理。这使一个获准从 NIC 进入软件的包，尽可能连续走到下一处真正必须等待的位置，例如出口队列或用户进程输入队列。

每次回调都有**包数配额**，用完就必须返回轮询循环。循环于是可以在多个接口以及接收／发送之间轮转。某接口没有剩余待处理事件后，才调用它的中断使能回调。

如果软件跟不上，接口缓冲先承受短时积压，超出的包在接口端丢弃。这样主机不会已经花费协议处理成本，才发现内部队列根本不能接收。

这里有两个不能省略的条件：

- **直接调用 IP 不等于无限吞吐。** CPU 与出口都有上限；目标是保住可达到的完成速率。
- **轮询不等于公平。** 如果单个接收回调不受限，它可能永远不返回，其他回调仍无法运行。配额负责把公平从口号变成实际控制流。

## 6. 图 6-1–6-4：逐步修复，也逐步暴露下游瓶颈

### 6.1 图 6-1：原系统确实出现过载退化

**定位：PDF p.8。** 横轴输入速率，0–12000 包／秒；纵轴输出速率，0–5000 包／秒。实心圆是不经 `screend` 的内核转发，空心方块是经过 `screend` 的路径。

论文文字报告：纯内核转发峰值约 4700 包／秒，随后随输入上升明显下降；若继续增大输入，作者推测会在低于以太网约 14880 包／秒极限的位置达到完全活锁。图中实测最高输入附近仍有非零输出，**不能说图已经实测到该曲线归零**。

`screend` 路径在约 2000 包／秒后就出现明显退化，作者将约 6000 包／秒附近描述为完全活锁。散点在高负载区仍有很小的非零值，因此读图时更准确地说“接近零”，不应把“约 6000”当成精密阈值。

课堂把峰值约读成 5000，用来估算每包 200 微秒；这与论文正文报告 4700 的差别来自量级估算，不能把前者当成重新测量的精确结果。

### 6.2 图 6-3：有配额的轮询与无配额的轮询

**定位：PDF p.10 上图。** 横轴 0–12000 包／秒，纵轴 0–6000 包／秒；全部是不使用 `screend` 的配置。

| 标记／配置 | 观察与解释 |
|---|---|
| 实心圆 `Unmodified` | 原系统，过载后下降 |
| 空心圆 `No polling` | 修改后的代码配置成不轮询；略差于真正原系统，作者不能确定原因，提出路径长度、编译器、指令缓存冲突等可能性 |
| 空心方块 `Polling (quota = 5)` | 到约 5000–5200 包／秒后保持平台；具体点有波动，属于读图近似 |
| 灰色菱形 `Polling (no quota)` | 饱和后骤降至很低输出；并非“改成轮询就都解决了” |

无配额时，接收回调可能不断取包并执行 IP，然后把它们放到输出队列；却一直不返回调度发送完成回调，导致发送描述符不能及时回收。于是原来在 IP 输入队列的丢弃，迁移到输出队列。丢之前做的工作更多，甚至比原系统更坏。

输出队列也不能简单删除，因为出口未必与入口一样快。解决方法是调度必要的发送服务，而不是假设所有包都能同步离开机器。

### 6.3 图 6-4：本地应用需要队列反馈

**定位：PDF p.10 下图。** 横轴 0–12000 包／秒，纵轴 0–3000 包／秒。三种配置均使用 `screend`。原系统与“轮询但无反馈”在高输入下仍会下降；“轮询加反馈”能维持约 2800–3000 包／秒的平台。

原因是 `screend` 的队列仍然存在，而且它是一个用户进程。轮询线程即使公平服务各个网卡，也可能让应用没有 CPU。队列满时继续接新包，只会把活锁往后移动一段。

作者据筛选队列状态暂停输入：

- 本组试验包数配额为 10，筛选队列容量 32 包。
- 队列达到约 75% 满时抑制输入处理和输入中断。
- 队列降至约 25% 满时重新允许输入，形成高低水位滞回。
- 另设约一个时钟 tick、即 1 ms 的超时，避免 `screend` 挂住后永远阻塞其他消费者的输入。

水位是作者任意选择的实验参数，可能还能调优；不是普适最优值。作者指出，同样思想可以用于出口、抓包过滤器等队列，但复杂路径上更难判断某条队列满是否确实由于输入负载饿死其消费者。`screend` 通常是该机唯一应用，所以这里的反馈信号格外直接。

## 7. 图 6-5–6-6：配额不是越大越高效

两图均位于 **PDF p.12**，比较 5、10、20、100、无限配额。

### 7.1 不经过 screend：大批次可能再次饿死发送

图 6-5 横轴 0–12000 包／秒，纵轴 0–6000 包／秒。五包配额在过载区约维持 5100 包／秒，十包约 4400；二十包在高负载区约降到 2200–2500；一百包与无限配额更低。这些是原图可读出的量级，非提取自原始测量表。

这说明“降低每次回调调度开销”不是唯一目标。批次越大，其他方向等待越久，越容易发生发送饥饿。即使较大的有限配额比无限循环更好，也不代表它保持了峰值转发能力。

### 7.2 经过 screend 并有反馈：较大配额的风险被反馈限制

图 6-6 横轴仍为 0–12000 包／秒，纵轴改为 0–3000 包／秒。不同配额在高负载下大多稳定于约 2700–2900 包／秒。论文认为较小配额可能使最大吞吐略低，量级约 5%，因为回调固定开销摊销较差；但增加配额也可能增加最坏单包等待时间。

配额一旦大到足以一次把筛选队列推到高水位，队列反馈就接管了限制，继续增大配额的作用趋于有限。

作者综合两组试验提出“约 10–20 包”作为该硬件上的可调经验范围，但这一总结不能掩盖图 6-5 中二十包配置的明显过载损失，更不能照搬为所有平台的最优值。配额与队列反馈必须结合目标负载、吞吐和延迟要求来理解。

## 8. 图 7-1：网络完成进度不等于用户进程公平

解决网络路径内部的活锁以后，作者又运行一个纯计算用户进程，同时向路由器灌入最小包。路由器仍能以完整速率转发，用户进程却几乎没有可测进展。也就是说，“包能出去”还不是通用操作系统的全部目标。

### 8.1 CPU 周期预算

Alpha 提供低开销周期计数器。实现每约 10 ms 开一个统计周期，累计轮询循环花在输入与输出处理上的 CPU 周期；每轮进入、退出时读计数器并求差。累计值超过给网络处理配置的预算，就抑制进一步输入处理；周期结束时由定时器恢复。空闲线程运行也可清空累计量并恢复输入中断。

预算检查不是每条指令都发生，而是在一小批处理之后，所以包数配额仍有作用：它限制一次检查间隔里的工作量。实验直接修改内核全局变量控制网络预算百分比，未实现公开的配置接口。

### 8.2 图的单位与结果

**图 7-1，PDF p.12 下图。** 横轴是输入包率，范围 0–10000 包／秒；纵轴为用户进程可获得的 CPU 时间百分比，图面范围 0–80%。图例 25%、50%、75%、100% 指的是**网络处理预算阈值**，不是用户进程所获得的份额。

高输入区的读图近似如下：

| 网络预算阈值 | 用户进程可用 CPU |
|---|---|
| 25% | 约 65% |
| 50% | 约 43%–44% |
| 75% | 约 15%–17% |
| 100% | 接近 0 |

结果并不精确等于 `100% − 阈值`。论文给出几类原因：系统本来就有开销，无输入时用户进程也只有约 94%；达到预算后暂停的是输入而非所有发送处理；还有未计入预算的中断成本，以及每批之后才检查造成的超额。

本组测试配额为五包。在约 5000 包／秒的处理速度下，五包可耗约 1 ms，已经占 10 ms 预算窗口的约 10%，因此控制粒度不容忽略。低到中等输入区的短暂下探，作者推测与尚未批处理、逐次中断的额外开销有关。

作者报告本地交互主观上明显改善；但 Telnet 这样的网络交互仍可能因大量丢包而差。给用户进程保留 CPU，并不等于保证它的网络请求一定送达。

## 9. 证据边界、相关工作与结论

### 9.1 本篇没有完成什么测量

作者尚未把修改移植到能充分测出端系统差别的高速网络接口，如 FDDI。测试机已经能塞满所用以太网，因而测 TCP 吞吐未显出差异；论文关于减少排队、锁开销和改善内核间交互延迟的论述有机制依据，但不能冒充本篇提供了完整的 TCP／NFS 性能数据。

硬件、单处理器调度条件、小包流量、空闲测试网络及 `screend` 全部放行，都限制结果的外推。本文没有用这些旧数字预测现代多核、多队列 NIC 的容量，也未复现任何实验。

### 9.2 与早期轮询工作的区别

早期轮询常以减少中断开销为目标；本文更强调公平和完成进度。周期性“clocked interrupts”同样面临频率过高浪费、过低增加延迟的问题；4.3BSD 的多端口终端接收曾在输入较高时转用轮询，也可从避免输入压倒系统的角度理解。

论文没有改变“挑哪个包丢”的尾丢弃策略，改变的是**在何时、投入多少工作后丢弃**。其他丢包选择策略可能有额外收益，但不属于本篇已实现的结论。

### 9.3 最值得迁移的设计判断

不要只让每个局部阶段看起来都很勤奋。必须明确整个请求完成需要哪些阶段、这些阶段争夺什么资源，以及过载时谁应当主动停下来。

本篇的组合是：中断触发轮询、轮询配额分配机会、队列状态反馈保护下游、CPU 周期预算保护其他用户工作、过载时尽量早丢包。它们针对不同失衡，不能互相替代。优化常规路径可以提高饱和点，显式调度与反馈则决定越过饱和点后系统是否还能做成事情。
