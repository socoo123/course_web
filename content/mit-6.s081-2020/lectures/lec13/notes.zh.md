# 第 13 讲 · 让“准备睡眠”与“有人通知”不再错过

本讲要解决的不是怎样把进程状态写成 `SLEEPING`，而是：**在允许其他执行者改变条件的同时，怎样保证等待者不会错过通知？** 同一个问题继续延伸到退出：如何让父进程观察到孩子已经结束，又不会过早回收仍在执行的孩子？

## 1. 先分清条件、channel 和状态

| 对象 | 回答的问题 | UART 教学例子 |
|---|---|---|
| 条件 predicate | 我现在能不能继续工作？ | `tx_done != 0` |
| 条件锁 L | 谁保护条件的检查、修改与消费？ | `uart_tx_lock` |
| 等待通道 channel | 这次通知对应哪些等待者？ | `&tx_chan` |
| 进程锁 P | 谁保护睡眠登记与调度状态交接？ | 当前等待者的 `p->lock` |
| 调度状态 | 进程是否有资格被运行？ | `SLEEPING` / `RUNNABLE` / `RUNNING` |

**channel 不是条件值，也不是事件计数器。** `wakeup` 只比较 channel，不会读取 `tx_done`。没有等待者时，它不会为未来保存一张“唤醒券”。真正记录事实的是调用者自己的状态，例如 `tx_done`、管道计数、子进程的 `ZOMBIE` 状态。

**`wakeup` 也不把 CPU 直接交给等待者。** 它只使匹配的睡眠者进入 `RUNNABLE`，实际运行还要经过调度器。若多个进程都醒来，资源可能先被别的进程拿走。

这里说的是内核 `sleep(chan, lock)`，不是用户程序的按 tick 暂停的 `sleep(n)` 系统调用。后者可以使用这种等待机制实现，但接口不是一回事。

定位：[中文译稿](#/c/mit-6.s081-2020/lec/lec13?v=draft)18:00–27:00、39:00–43:00；[课程资料](#/c/mit-6.s081-2020/lec/lec13?v=materials)§7.5–7.6。

## 2. 一个反例就能检验你的等待协议

设条件初始为假，读者 R 想等写者 W 产生数据。错误写法的危险交错是：

| 顺序 | 等待方 R | 通知方 W |
|---|---|---|
| 1 | 持 L，检查条件为假 | |
| 2 | 释放 L | |
| 3 | 尚未登记睡眠 | 取得 L，令条件为真 |
| 4 | 仍未登记 | 调用 wakeup，没有匹配睡眠者 |
| 5 | 登记 `SLEEPING` 并切换 | 通知已经结束 |

这个例子中，条件已真，却没有新的事件保证 R 醒来。错误不是“缺少 while”；R 在睡眠前就已经错过唯一通知，根本回不到 while 的下一次检查。

反过来，如果 R 不释放 L 就睡下去，W 连修改条件的机会都没有，也会卡住。于是两种简单修补都失败：

- **自己先解锁再 sleep：** 有无保护的间隙；
- **拿着条件自旋锁 sleep：** 阻止生产者推进，并违反调度约束。

课堂把它做成可见故障：`broken_sleep` 使启动信息、`ls`、`cat README` 的输出反复停住。输入句点偶然产生额外 UART 中断，临时把写者救回来，但这不是正确性保证。完整演示及恢复原因见中文译稿 33:00–45:00。

## 3. 正确性证明：锁的连续保护，而非一句“原子睡眠”

用 L 表示条件锁，P 表示等待者自己的进程锁。普通 `L != P` 情形：

1. 调用者持 L 检查条件；若不满足，保持 L 进入 sleep。
2. sleep 先取得 P；此刻两锁重叠。
3. sleep 释放 L，但仍持 P。
4. 记录 channel 与 `SLEEPING`，调用 `sched` 切换。
5. 调度器离开原线程后，才释放 P。

![条件锁与进程锁的重叠交接](assets/lock-handoff.svg)

*编者根据 2020 `proc.c:sleep/scheduler/wakeup` 自绘。色带表示阻止唤醒方检查这个进程的保护范围，不表示睡眠期间仍持有这两把锁。*

唤醒方先在 L 下更新条件；通用 wakeup 检查目标进程前还要取得 P。因此不存在“条件已检查为假、唤醒已经越过、睡眠尚未登记”的合法交错。证明可以分成两种情况：

- W 在 R 检查前完成更新：R 看到条件已真，不睡；
- W 在 R 检查后推进：先被 L 阻止，随后被 P 阻止；等能检查 R 时，R 已登记睡眠。

**“原子”是对参与协议的观察者而言。** sleep 实际先释放 L、后写 `SLEEPING`；这仍然正确，因为 P 补上了保护。不能只看两条写语句是否紧挨着。

醒来后，sleep 先清理 channel，释放 P，再重新取得 L，然后返回调用者。此时调用者仍有权在 L 下读取条件。若 L 本来就是 P，例如 2020 的 wait，则走特殊分支，既不能重入同一自旋锁，也不能按普通路径把它先解锁再重锁。

定位：中文译稿 45:00–57:00；课程资料 §7.6 与习题 1。

## 4. 两条调度约束怎样嵌进证明？

### p->lock 必须跨过切换

把状态改成 `RUNNABLE` 不代表当前 CPU 已停止使用线程栈。若马上释放 P，另一核可能同时运行该线程。让调度器在切换完成后解锁，把“状态转换”和“栈/上下文所有权交接”纳入同一保护区间。

这不仅对 yield 有用。sleep 的登记、exit 的僵尸状态也必须在真正离开执行现场之前，阻止其他核作出过早决定。

### 其他自旋锁必须先释放

如果 P1 持 L 交出单核 CPU，P2 自旋等 L，则 P1 无法重新运行以释放 L。时钟也救不了：`acquire` 在自旋前已关闭本核中断。因此 `sched` 要求只持自己的进程锁，`noff == 1` 是相关检查。

这里说的是**自旋锁**，不是禁止持有睡眠锁跨越等待。二者的区别见下一节。线程切换的更完整背景在[第 11 讲](#/c/mit-6.s081-2020/lec/lec11?v=materials)，不必在这里重新推导寄存器保存。

## 5. 把协议映射到 pipe 与 sleeplock

| 使用点 | 继续工作的条件 | 条件锁 | channel | 谁改变条件并通知 |
|---|---|---|---|---|
| 管道读 | 有数据；写端全关时可结束等待 | `pi->lock` | `&pi->nread` | 写者或关闭写端的路径 |
| 管道写 | 有空闲容量；读端关闭时报告错误 | `pi->lock` | `&pi->nwrite` | 读者或关闭读端的路径 |
| 取得睡眠锁 | `lk->locked == 0` | 内部 `lk->lk` | 睡眠锁对象地址 `lk` | `releasesleep` |
| 2020 wait | 有可回收的僵尸子进程；无孩子则返回 | 父进程自己的 `p->lock` | 父进程指针 `p` | 子进程 exit 的专用 `wakeup1` |

管道的全文说明见课程资料 §7.7。最需要记住的是：**空不等于 EOF，满不等于错误。** 仍有写端时，空管道读者等待；所有写端关闭且数据读尽，读取才结束。计数用于判定空/满，地址用作 channel，不可混淆。

### 指定源码补充：sleeplock 的两层锁

课堂主要演示 UART 和管道，未逐行展开指定阅读的 `kernel/sleeplock.c`。它展示怎样在 sleep/wakeup 上搭建更高层互斥：

- `lk->lk` 是内部短期自旋锁，保护 `locked` 与 `pid`；
- `lk->locked` 表示逻辑上的睡眠锁是否已被持有；
- 等待者在内部自旋锁下发现 `locked` 为真，调用 `sleep(lk, &lk->lk)`；
- 成功取得逻辑锁后设置 `locked = 1`、记录 PID，便释放内部自旋锁；
- `releasesleep` 在内部自旋锁下清除逻辑持有状态，调用 `wakeup(lk)`，再释放内部自旋锁。

所以“持有睡眠锁”的进程并不一直持有那把内部自旋锁。其他请求者可以进入短临界区，发现忙，再主动睡眠；持有者也能跨越磁盘 I/O 等等待继续保持逻辑独占。这没有违反 `sched` 不允许额外自旋锁的规定。

## 6. exit/wait 是跨线程的回收协议

可以把进程终止分为三步：

1. **自行清理可安全结束的资源：** exit 关闭文件、释放 cwd 引用，安排孩子的新父进程。
2. **发布终止事实并离开执行现场：** 保留退出状态，置 `ZOMBIE`，持子进程锁切换到 scheduler。
3. **由另一个线程收尾：** 父进程 wait 在锁下确认僵尸，复制退出状态，调用 freeproc，最后让槽回到 `UNUSED`。

`ZOMBIE` 是尚待回收的终止记录，不是仍在后台运行的进程。父进程晚调用 wait 仍能发现它，靠的是持久保存的状态，而非缓存某次 wakeup。

2020 版本须特别看清以下细节：

- wait 先持父锁，再取子锁；exit 也遵守父到子的顺序。这里没有新版 `wait_lock`。
- `wakeup1` 要求已经持有目标父锁，只检查父亲是否睡在自己的 wait channel 上；不能简单换成会遍历并重新加锁的通用 wakeup。
- 先唤醒父亲、后置 `ZOMBIE` 仍安全：父亲查看孩子还需子锁，必须等孩子切换完毕才能取得。
- `original_parent` 保存一次父指针快照，使加锁与解锁针对同一个对象；否则父进程并发退出、重挂孩子时，前后读 `p->parent` 可能不一致。课堂未给完整逐行证明，不能把这个源码说明冒充讲者的现场回答。
- 固定快照在启动时为各 proc 槽分配内核栈，freeproc 不逐次释放它。这里回收的是用户页、页表、trapframe 等，并重置进程槽。

教材习题 2 还提示一个很好的追问：为什么不能把关闭文件也推迟到 wait？考虑父进程正在读管道直到 EOF，孩子退出前仍持有写端。如果必须等父亲 wait 才关闭孩子写端，父亲可能永远等不到 EOF，也就永远走不到 wait。

定位：中文译稿 59:00–72:00；课程资料 §7.8。

## 7. kill 的“安全点”与一个真实限制

`kill` 设置标志，不从外部销毁目标栈。目标在 `usertrap` 的检查处自行 exit；睡着的目标还会被改为可运行，从而有机会回到等待循环处理终止请求。

| 等待位置 | 被 kill 唤醒后的处理 | 理由 |
|---|---|---|
| 管道/控制台读取 | 可在循环中发现 killed，释放锁并返回 | 这里可以放弃等待，经系统调用返回路径退出 |
| Virtio 磁盘请求 | 条件未满足则继续等 | 可能位于必须完成的文件系统多步骤操作中 |

不能由“当前没执行指令”推断“随时销毁也安全”。睡眠的线程仍可能承担一个尚未完成的事务性操作。

另一个容易过度概括的地方是“加了 killed 检查就一定立即退出”。教材 §7.9 明确指出 2020 实现仍有竞态：目标先检查 killed 为假，随后 kill 设置标志并尝试唤醒，目标再进入 sleep。kill 不遵循具体条件锁的更新协议，前面关于正常生产者通知的证明不能直接覆盖它。习题 4 要求修复这个窗口；本讲没有运行或提交修复。

## 易错点速查

| 误解 | 更准确的判断 |
|---|---|
| 有 while 就不会漏通知 | while 处理醒后条件变化；进入睡眠前的空隙要靠锁交接 |
| wakeup 已经发生，之后 sleep 会立刻返回 | wakeup 不为未来保存通知 |
| wakeup 返回说明目标已经运行 | 只是把匹配睡眠者改为可运行 |
| 睡眠时仍拿着条件锁 | sleep 中间交出条件锁，返回前再取回 |
| 内核中的任何时间都能由时钟抢占 | 持有或等待自旋锁时本核中断关闭 |
| kill 成功意味着目标已释放所有资源 | 请求、目标退出、父进程回收是不同阶段 |
| 用当前 GitHub proc.c 就能解释 2020 每一行 | 必须核对父锁、wakeup1、sleep 特殊分支等版本差异 |

## 自测：尝试用交错顺序作答

<details><summary>1. 把 sleep 中“取得 P、释放 L”对调，且 L 与 P 不同，哪里会出错？</summary>

释放 L 后、取得 P 前，通知者可以取得 L、修改条件，再取得 P；因为等待者尚未设置 SLEEPING，通知者什么也不做。等待者随后取得 P 并睡眠。两把锁都存在，但没有重叠，仍然漏通知。

</details>

<details><summary>2. 已唤醒两个读者，但管道只来一个字节，可以把 while 改为 if 吗？</summary>

不可以。第一个读者在条件锁下消耗字节，第二个真正拿到锁时条件可能又为假。必须重新检查，而不是根据已经被唤醒就直接消费数据。

</details>

<details><summary>3. 把 UART 的 channel 从 &amp;tx_chan 换成 &amp;tx_done 能否工作？</summary>

在地址生命周期适当、所有 sleep/wakeup 使用同一个新值的前提下，可以。channel 是标识；tx_done 的值才是条件。不能把 channel 改成 tx_done 的当前数值，然后让它随 0/1 变化。

</details>

<details><summary>4. 父进程还没调用 wait，孩子就退出了，是否丢失了退出事件？</summary>

不会。孩子保留为 ZOMBIE，退出状态也保存着。未来 wait 在锁下扫描能发现并回收它。这里不是让 wakeup 帮忙记住历史。

</details>

<details><summary>5. 已持有父进程锁，能否直接调用通用 wakeup(parent) 替代 wakeup1？</summary>

在本讲固定 2020 实现中不能。通用 wakeup 会遍历并取得每个进程锁，碰到已经持有的锁就出问题；wakeup1 是专门在目标父锁已持有时使用的辅助函数。

</details>

<details><summary>6. 已被 kill 的磁盘等待者再次 sleep，是否一定是实现漏写检查？</summary>

不一定。本版本有意等磁盘请求及当前系统调用完成，以免中途破坏文件系统操作。若要支持更快取消，必须设计完整的中止/清理协议，而不是只往每个循环里加 return。

</details>
