## 1. 先列出参与者，再决定同步手段

“这里有并发，所以加锁”缺了一半推理。应先把参与者与共享状态列出来：

| 参与者 | 可能共享的状态 | 当前课堂采用的协调方式 |
|---|---|---|
| 多个发送执行流 | TX 槽位、软件 mbuf 记录、尾部更新 | 发送锁 |
| CPU 与网卡 | 描述符、包缓冲、完成状态 | 设备规定的所有权与完成协议，以及发布次序 |
| 单个接收处理与发送处理 | 本实验收发 ring 状态分离 | 不因为“同属驱动”就共享一把入口锁 |
| 中断输入路径与读取线程 | 若共享输入队列 | 对这份共享队列同步，或采用相应队列协议 |

**判断锁是否必要，靠的是会被并发修改的不变量，而不是函数名。** 软件锁不让网卡停止 DMA；关掉本核中断也不让别的核停止执行。

课堂“不需要接收锁”的前提是本实验同一接收入口不并行重入，且 RX/TX 的相关状态分开。把它推广成“中断处理函数从不需要锁”是错误的。换成多个队列、多个设备或其他可并发调用路径，必须重新画参与者与共享状态。[译稿 27:00–39:00]

### 自锁等待不一定需要两个线程

用一个最小依赖链检查：

1. 外层调用持有锁 L。
2. 外层调用的某个回调再次要求 L。
3. 内层等待 L，而 L 要等内层返回后才由外层释放。

即使只有一个执行流，也已经构成等待环。ARP 回复把这个抽象变成了真实调用链，见译稿 30:00–37:00。

递归锁可改变重复获取的行为，但它不替代对共享状态和调用关系的分析。课堂列出的递归锁、分开锁、不取不必要的锁，是针对已讨论路径的不同安排，不是通用修复菜单。

## 2. 把 ring 看作所有权协议，不只是循环数组

描述符是硬件规定的数据格式；ring 是这些描述符的固定大小数组；寄存器和完成位决定谁能使用哪些槽。普通的取模索引只解决“如何绕回开头”，没有解决“现在能不能改”。

从本讲可抽出两个必须分别满足的条件：

- **空间条件：** 目标槽已经可以复用，没有覆盖设备尚在使用的任务。
- **时间条件：** 设备获知新任务之前，新任务的数据和描述符已经按所需次序准备好。

前者需要检查完成状态，后者涉及发布操作和内存次序。保护多发送者的锁，不能替代其中任何一条。[译稿 42:00–60:00]

容易记错的两处边界：

- TX 的当前可提交位置从 `TDT` 取得；不能因为 RX 有“加一”，就在 TX 上机械照搬。
- RX 从 `(RDT + 1) % RX_RING_SIZE` 找下一待检查槽；检查 DD 后才消费，补好新缓冲再把槽交还设备。

这里保留的是阅读代码的定位线索，具体实现要求见[网络实验](#/c/mit-6.s081-2020/lab/net?v=zh)。课堂发送画面还专门用 DD 判断可回收状态，而不单凭 head 的推进推断数据缓冲已经安全可释放。

## 3. 通知与工作数量是两种状态

**编者抽象：** 中断是一种“值得检查设备状态”的通知，不能当作数据包计数器。

设接收处理真正开始前，已经有 $k$ 个包到达。若每次中断只取一个，处理后仍有 $k-1$ 个完成项。除非另外证明这些项都会得到后续处理机会，否则算法可能把工作永久留在队列中。

因此，退出接收循环应由“按协议查看下一个槽，没有可消费的完成项”决定，不能由“已响应过一次中断”决定。课堂十个并发请求的反例见译稿 63:00–69:00；串行的一问一答测试可能恰好隐藏这个错误。

这也解释了为什么课堂对“扫描整环一次”的建议没有直接认可：改变遍历方式，还要重新证明所有权、推进顺序与设备同时到达新数据时的行为。讲者明确没有试过该方案，不能把那段探索性回答摘成标准解法。

> 延伸辨析：循环清理已到达工作解决本例的遗漏问题；高负载下如何限制接收处理占用 CPU，是另一个问题。可回看[第 21 讲笔记](#/c/mit-6.s081-2020/lec/lec21?v=notes)的接收活锁讨论。本讲没有实现有预算的轮询方案。

## 4. 分清“存储对象”“数据视图”“硬件说明书”

| 对象 | 回答的问题 | 不能替代什么 |
|---|---|---|
| mbuf 的 `buf` | 包的字节实际存在哪里？ | 不是只有一个指针 |
| mbuf 的 `head`、`len` | 这块存储中，目前哪一段是有效数据？ | 不会自动分配 backing store |
| mbuf 的链接 | 包如何在 socket 等软件队列中等待？ | 不是硬件 ring 的格式 |
| 硬件描述符 | 设备到哪里读/写、长度和状态如何交换？ | 不负责上层对象的全部生命周期 |
| `tx_mbufs` 等软件记录 | 某个硬件槽对应哪个需要回收的软件对象？ | 网卡不会自动读取这份 C 指针数组 |

这一分层来自两个生命周期不一致：设备完成接收，不意味着用户马上读取；发送函数返回，也不意味着设备已经用完数据。对象需要活到最后一个使用者结束，而不是活到当前函数返回。[译稿 21:00–24:00、54:00–72:00]

接收后既然把旧 mbuf 交给网络栈，就不能同时让网卡把下一个包覆盖到它里面。重用的是描述符槽，交给上层的数据对象可以继续存活。这是“槽位复用”和“对象释放”最容易混淆的地方。

## 5. mmap 的优势来自访问模式，而不是魔法般地省掉文件语义

流式 API 隐含维护当前位置，适合连续读写；结构化随机访问需要频繁指定目标位置，指针形式的映射可能更自然。[译稿 72:00–81:00]

课堂反例可浓缩为下面的状态变化，假设读写都成功完成 16 字节：

$$
\text{offset}=0 \xrightarrow{\text{read 16}} 16
\xrightarrow{\text{write 16}} 32.
$$

在中间修改内存缓冲，不会自动改变文件偏移。想写回原记录，就必须重新定位，或使用明确定位到该区域的访问方式。mmap 把文件区域放入虚拟地址空间，便于按结构成员访问；它没有让“共享可见”“写回存储”“崩溃后仍保留”变成同一个保证。

课堂讨论只到接口动机，没有覆盖 mmap 的完整页故障实现。实验范围另见[内存映射实验](#/c/mit-6.s081-2020/lab/mmap?v=zh)。

## 自测：先预测错误，再解释修正条件

<details><summary>1. 收发环彼此分开，为什么在接收入口加发送锁仍可能出问题？</summary>

因为接收路径可能通过 ARP 回复再次调用发送函数，进而重复获取同一把非递归锁。问题是调用链和锁的组合，而不是 RX 与 TX 数组重叠。定位：译稿 30:00–39:00。

</details>

<details><summary>2. 发送函数返回成功后，调用者能立即释放包吗？</summary>

不能仅凭函数返回推断设备已完成 DMA。需遵循接口的所有权转移约定，并在设备完成后回收。课堂实现把成功提交的 mbuf 记在对应槽中，之后检查 DD 再释放旧对象。定位：54:00–60:00。

</details>

<details><summary>3. 一个进程发送一个请求能通过，十个并发请求会卡住，首先检查什么？</summary>

检查接收是否只处理一个包、是否在已有完成项时过早退出。多个包可以对应一轮通知；剩余包可能已在 ring 中，但没有新的通知促使错误实现继续取包。定位：63:00–69:00。

</details>

<details><summary>4. 既然 head 指向包数据，删掉 mbuf 的 buf 数组是否等价？</summary>

不等价。head 是地址，buf 是实际存储；若删掉数组，必须有其他实际分配的存储与正确的生命周期，不能仅保留悬空地址。定位：69:00–72:00。

</details>

<details><summary>5. 用锁把发送过程包起来，就能删掉“发布前的内存次序”要求吗？</summary>

不能这样推断。锁主要协调软件发送者；设备不取得这把锁。必须保证设备获知新 tail 时，已能按协议看到描述符和数据。具体锁/屏障能提供哪些次序，要由平台语义决定。定位：57:00–60:00。

</details>

<details><summary>6. 读出第一条记录，修改缓冲，再 write，为什么可能改到第二条？</summary>

read 已推进打开文件对象的当前偏移。修改缓冲不回退偏移，所以 write 从新位置开始。课堂用 16 字节记录说明，随后对比 lseek 与 mmap。定位：72:00–81:00。

</details>

<details><summary>7. 确认网卡的中断原因后，CPU 是否立即响应下一次中断？</summary>

不一定。设备事件状态、平台控制器状态和 CPU 中断使能是不同层次。84:00 画面显示对 E1000_ICR 的确认/清除，不能把它当作 CPU 的中断使能指令。定位：81:00–84:49。

</details>

## 学习路线如何选

学完 xv6 后，可以根据自己最想解释的现象选择一个方向：

- 想理解硬件为何影响软件：体系结构、硬件项目。
- 想把单机机制扩展到多机协作：分布式系统、网络。
- 想研究数据组织和可靠存储：数据库。
- 想讨论隔离、攻击面或形式化保证：安全、系统验证。
- 想探索内核设计本身：研究生 OS 课程与系统论文。

课堂课程编号和当时的安排见译稿 03:00–09:00。更可复用的建议是：从一个具体问题出发，读相关论文、看系统实现，再做一个能观察结果的小项目。
