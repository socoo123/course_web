# 第 23 讲 · RCU：把协调成本从高频读路径移走

**RCU 要解决的不是“怎样让所有访问都不加锁”，而是“怎样让大量读者不必为了读数据而修改同一份共享状态”。** 它把负担放到版本构造、写者协调与延迟回收上，换取便宜且可并行的读取。

## 1. 先找真正的共享写

应用看上去只做读，不代表硬件只做读。获取一个传统读写锁的读锁，需要修改共享读者计数；引用计数的增减同样如此。多个核反复写同一缓存行，会让它的所有权在核之间转移，冲掉原本可以利用的缓存局部性。

分析一个热点时，按以下顺序提问：

1. 数据本身需要更新吗，还是只有同步元数据在被写？
2. 每次读取是否都触碰同一计数器或锁？
3. 实际业务只要几十个周期时，同步是否反而成了主要成本？
4. 读写比例与一致性要求，是否允许读者继续使用一个完整旧版本？

课堂的 CAS 交错与缓存通信推导见[中文译稿](#/c/mit-6.s081-2020/lec/lec23?v=draft) 12:00–30:00。其 `O(N²)` 是同时竞争模型中的累计工作推演，不是所有锁的通用复杂度结论。

## 2. 把正确性拆成三份证明

仅仅写下 `rcu_read_lock()` 并不构成正确性证明。对一个版本替换，必须同时回答三件不同的事：

| 义务 | 要证明什么 | 失败后会怎样 |
|---|---|---|
| 内容完整 | 读者不会看到正在被逐字段改写的半成品 | 新旧字段混合 |
| 发布有序 | 读到新入口时，其目标已经按要求初始化 | 指针有效，内容却未就绪 |
| 寿命足够 | 最后一个可能持有旧引用的读者结束前不回收 | use-after-free、内存复用 |

本课最直接的解决组合是：**构造新版本 → 正确发布入口 → 等宽限期 → 回收旧版本**。写者之间另用锁等机制协调；这不属于 RCU 自动提供的承诺。

注意“入口已切换”只能说明新查找不再沿该入口进入旧对象，不能说明旧对象没有读者。保存到另一个核局部变量里的指针，不会因共享表头改变就自动消失。

课堂三条规则的详细建立见中文译稿 30:00–57:00。不同 API 与论文的类型安全内存例外，见[课程资料](#/c/mit-6.s081-2020/lec/lec23?v=materials) §2–3。

## 3. 宽限期证明：等旧读者，不是等到全局无人读取

考虑某个旧对象 `old`，时间点按以下顺序排列：

| 时刻 | 写者 | 可能的读者状态 |
|---|---|---|
| A | 尚未摘除 `old` | 有读者已经取得 `old` |
| B | 发布新入口，阻止通过该入口新取得 `old` | 原来的读者仍可使用 `old` |
| C | 等待覆盖这些旧读者的宽限期 | 新读者可以读取新版本，不必停止 |
| D | 等待返回，回收 `old` | 相关旧临界区已结束 |

本讲用“读侧不可跨上下文切换；摘除后所有核均经过切换”构造充分条件。关键是**事件必须发生在正确的起点之后**，不是看某核历史上“切换过很多次”。

这份证明依赖本课非抢占教学模型。`preempt_disable` 不是全面关闭中断；论文还讨论其他 RCU 变体，不能推出所有 Linux RCU 都不允许抢占或睡眠。具体限定见课程资料 §2.1。

`call_rcu` 只让调用者不必同步等在 C；对象仍要到 D 才能回收。把所有写者改成异步调用，可能用内存积压换来较低的调用延迟。

## 4. 生命周期正确，不等于业务结果一定正确

RCU 首先让对象可安全访问，但可能仍需回答：

- **完整性：**一个节点的多个字段是否来自同一版本？
- **新鲜度：**接口是否允许操作期间继续使用旧配置？
- **跨对象一致性：**连续查看两个节点，是否要求来自同一个全局快照？
- **业务资格：**对象虽然尚未回收，是否已经逻辑删除、不能再用于新操作？

一次正确发布只能解决选定对象版本的可见性，不自动解决后面所有问题。论文据此提出增加间接层、obsolete 标志、版本检测与重试，见课程资料 §5。

同样，查找函数能返回什么取决于寿命契约：返回复制出的字符串通常可以；返回刚刚退出 RCU 临界区的节点内部地址则不可以。若确实需要长期持有，可由调用者维持保护范围，或在合法保护下转成独立的长期引用，但必须明确设计，不能默认裸指针永远有效。

## 5. 选择机制时看哪种操作最多

| 访问形态 | 优先考虑的方向 | 成本移到哪里 |
|---|---|---|
| 读多写少、可容许完整旧版本 | RCU 与合适的发布/回收协议 | 构造、写者协调、宽限期与内存 |
| 写多读少的统计计数 | 每核计数，少见时全局汇总 | 读取总和与快照协调 |
| 频繁本地分配、偶尔跨核调剂 | 每核分区 | 缺货时的跨核协调 |
| 复杂原地更新、强互斥语义 | 先保留合适的锁，分析瓶颈再改 | 互斥等待，但证明相对直接 |

这不是性能排名。读路径长到业务工作占主导时，省下锁的收益也可能不大；写频繁时，复制与回收反而昂贵。论文的 6、89、6654 ns 是特定旧系统上的同步微基准，不是现代机器的常数；图 8 还有明确图文差异，见课程资料 §4。

本讲提到 locking 实验，是在对比每核分区思想。已有[实验说明](#/c/mit-6.s081-2020/lab/lock?v=zh)保持独立，本讲没有新增实验任务。

## 6. 易错点速查

- **“lock” 就会阻止写者？** `rcu_read_lock` 主要建立读侧保护范围，不能按普通互斥锁理解。
- **有屏障就能立即 free？** 屏障处理顺序，不能证明另一个核已放弃旧引用。
- **等待后再摘除也一样？** 不一样，等待期间仍可产生指向旧对象的新引用，证明起点错了。
- **加引用计数不会影响纯读性能？** 热点共享计数正是潜在的缓存行竞争来源。
- **看到旧值都是缓存没刷新？** 读者可能正合法访问被保留的旧对象，屏障不能把它变成新对象。
- **旧 slides 上的 API 拼法就能照抄？** 提纲与 slides 是教学材料；`rcu_synchronize` 等旧 slides 写法、课堂变量笔误不能替代实际 API 与代码核对。
- **所有 RCU 都必须“单指针提交”？** 这是本课最直接的版本替换模式；论文还组合其他机制，不是全部 RCU 使用方式的定义。

## 7. 自测：能给出反例，才算理解

<details><summary>新节点已经完整初始化，写者改完表头就 free(old)。还缺哪份证明？</summary>

缺旧对象寿命证明。读者可能在改表头之前已经保存 `old` 指针，随后继续访问。初始化正确与发布原子，都不能排除这位旧读者；必须先完成对应的宽限期或其他有效生命周期协议。

</details>

<details><summary>一个核持续进入新的读侧临界区，宽限期就永远结束不了吗？</summary>

不必如此。同步契约等待的是相应起点前已经存在的读者，不要求全系统同时没有读者。新读者按正确发布规则取得新对象，不妨碍旧对象的回收证明。具体实现仍需要各核或相关任务能够报告必要进展。

</details>

<details><summary>为什么普通“先检查 n≥0，再 n++”不能实现读锁？</summary>

在检查与更新之间，写者可能先把零改为 -1。无条件加一会破坏状态。CAS 必须用局部保存的预期值进行原子比较，若共享值变化就失败重试，而不是把几个独立读写误当成一次原子动作。

</details>

<details><summary>读者返回节点内的字符串指针，与返回复制出的字符串有什么本质区别？</summary>

前者继续依赖 RCU 节点的寿命，临界区退出后可能被回收；后者拥有独立存储，其寿命由副本自己的所有权规则决定。返回类型都是指针，不代表它们引用同一种生命周期。

</details>

<details><summary>用 RCU 保证信号量对象还没 free，是否足以允许操作它？</summary>

不够。它可能已被用户逻辑删除。内存存在性与对象是否仍有业务资格不同，论文的 obsolete 标志与相应并发协议就是为此引入的。见课程资料 §5.2。

</details>

<details><summary>异步回收越来越快地登记成功，为什么系统却可能更缺内存？</summary>

成功登记不代表回收完成。若登记速率长期超过宽限期与回调处理的消化能力，旧对象积压。必须把调用延迟、完成延迟和未回收内存分别测量，不能用其中一个替代其他两个。

</details>

<details><summary>本讲“禁止抢占”能改写成“RCU 关掉所有中断”吗？</summary>

不能。原片 61 分钟明确区分中断发生与由中断触发调度切换。这里只讨论一个不可抢占读侧教学模型，论文还提到允许抢占或睡眠的其他变体。

</details>
