# 第 23 讲 · RCU 课外阅读

## §1 从“读者不加锁”到生产内核的要求

RCU 的目标不是单纯省掉几个函数调用，而是同时满足三类要求：更新过程中仍可并行读取；同步本身的时间与空间开销很低；读侧同步的执行可预测。论文 §1–2 用真实内核对象说明这些要求为什么重要。

**并行性。** 虚拟文件系统的目录项缓存保存 dentry。应用打开路径时要逐分量查找缓存，另一些线程却在装入新条目、驱逐旧条目。理想状态是读取者互不干扰，更新者也不必让所有读者停下来。把锁做细能够缓解竞争，但如果每次读取仍要改动共享同步状态，就可能在热点上形成新瓶颈。

**空间。** 论文举出的某台服务器缓存约八百万个 dentry。每个对象多几个字节，累计就相当可观。因此不能只说“一个锁只占一个整数，很小”，而要乘以对象总数。RCU 不要求每个读者为每个对象维护共享读计数，但旧版本与回调的延迟回收仍然消耗内存；它不是任何情况下都零额外空间。

**执行开销。** SELinux 的 access vector cache（AVC）可能在一次系统调用中被查多次。原文说，在不自旋、没有缓存未命中时，一次读取只有数百个周期；额外一次代价也是数百周期的缓存未命中，就可能把访问成本翻倍。因此短临界区尤其承受不起跨核同步开销。

**可预测性。** 非屏蔽中断与实时路径不能无限等待一个被打断的持锁者，也不希望因不断重试而没有可预测的结束时间。这里讨论的是 RCU 读侧进入、退出与适用算法的性质，不保证任意放进临界区的业务代码都具有固定执行时间。后面与序列锁组合后，读者也可能重试，不能把简单模型的性质不加区分地继承过去。

课堂已完整推演自旋锁、读写锁、CAS 与缓存行竞争，见[中文译稿](#/c/mit-6.s081-2020/lec/lec23?v=draft) 06:00–30:00；这里继续研究论文独有的使用模式及测量依据。

## §2 准确的同步契约，以及教学模型的边界

论文 §3 的关键承诺是：`synchronize_rcu()` 返回时，**在它开始等待时已经存在的相关读侧临界区已经结束**。它不会禁止新读者开始，也不需要等到全系统某一刻完全没有读者。删除对象的调用方要先撤销共享结构中的可达入口，再等待宽限期，最后回收对象。

理解这个承诺，要区分三个层次：

| 层次 | 解决的问题 | 不能自动推出的结论 |
|---|---|---|
| 发布与取得指针 | 读者取得完整初始化的对象 | 对象此后永不改变、整个结构是同一时刻的快照 |
| 读侧临界区与宽限期 | 原有读者结束前不回收其对象 | 写者之间已经互斥、任意裸指针可永久保存 |
| 应用自己的写侧与语义协议 | 更新冲突、旧对象、跨字段一致性 | 调用一个 RCU API 就自动完成所有业务正确性证明 |

### §2.1 非抢占教学模型，不是所有 RCU 变体

PDF p.3 图 2 使用每核 `preempt_disable` 计数；读侧进入加一，退出减一，支持嵌套。这个计数是 CPU 本地状态，并不是所有读者争抢的全局变量。简化的等待函数让当前线程在每个核上执行一次，以证明各核都经过调度切换。

在这个模型中，读者不能在保护范围内主动睡眠；禁止抢占的目的，是避免线程保留旧对象指针时被切走，使“每核已经切换”失去证明作用。**禁止抢占不等于禁止所有中断。** 本片 61:32–61:59 明确说定时器中断仍可能发生，只是不因此切换线程；官方 `l-rcu.txt` 第 155 行的 “Disable timer interrupts” 是更粗的教学简写，不能据它把 API 解释成一律关闭中断。

论文 p.11 §7 还明确提到其他 RCU 实现：采用不同系统事件，有的支持读侧被抢占，有的允许睡眠，也存在用户态实现。这些属于不同规则和实现，不是把本课 `preempt_disable` 模型原封不动搬过去。使用实际 Linux 接口时必须明确对应 RCU flavor；本页不把 2020 课堂模型冒充所有年份、所有配置下的 Linux 行为。

### §2.2 批处理把通信摊薄，也延长回收等待

真正的实现不必让每一个调用者逐核迁移。论文说明，内核可记录每核经过静止状态的进展，等待所需报告到齐。每次读侧退出都立即向所有等待者发消息，会重新增加共享通信；利用调度事件批量汇报，则让大量读侧活动共享较少的通知。

论文 p.3 描述大约每个调度时钟 tick 报告一次每核状态，并引用一次批处理满足超过 1000 次 `synchronize_rcu` / `call_rcu` 请求的能力。这里的 **1000 是同批完成的请求数，不是每秒吞吐率**。它说明摊销方式，而不是保证任意负载都固定达到这个数字。

代价是延迟：某个对象的最后一位读者其实可能很早就结束，但实现为了便宜地收集证据，仍等到较晚的批次。异步回调把这段等待从调用者路径移走，却保留未释放对象；加急同步则以更高协调成本减少延迟。论文没有给出一个对所有负载成立的固定宽限期长度。

### §2.3 屏障接口不能简化成“总会发完整 fence”

`rcu_assign_pointer` 的作用，是按要求发布一个已经初始化的对象；`rcu_dereference` 则表达按 RCU 规则读取共享指针并使用其目标。论文 p.3–4 说明它们包含依架构而定的编译器约束与必要机器指令，并特别举出 DEC Alpha 的读侧屏障需求。

FAQ 用 `__sync_synchronize()` 加赋值的形式帮助理解“初始化先于发布、取得指针先于使用”的关系。这是**教学近似**，不是完整的现代 Linux 宏展开，更不能推出所有平台的 `rcu_dereference` 都执行全硬件内存屏障。真实实现还必须约束编译器对共享指针的重取、推断或重排；不能自行用普通指针读写、`volatile` 或一条看起来相似的 fence 替代正式接口。

课堂 46:21–48:18 对“地址依赖已存在，为什么还需要读侧机制”的问答没有给出确定的硬件例子；本节给出论文的限定，不把讲者现场猜测写成已证事实。

## §3 五种使用模式：RCU 不只是替换一个读锁

### §3.1 等待已经开始的活动完成：NMI 处理器注销

论文 §4.1、p.5 图 4 的例子是动态注册与注销 NMI handler。NMI 是 non-maskable interrupt，可用于硬件故障、CPU 性能采样、看门狗等；普通屏蔽中断的办法不能把它挡住。

内核维护一个处理器链表。中断发生时，遍历链表并执行处理函数；注册、注销则改变链表。读者很多、配置修改少，符合 RCU 的访问模式。但这里不仅有性能动机，还有死锁问题：若普通代码持有链表锁时被 NMI 打断，而 NMI handler 又尝试取同一把锁，它会等待一个暂时根本无法继续执行的持锁者。

RCU 让中断路径在读侧保护范围内遍历，不争抢那把写者锁。注销按两个阶段进行：

1. 在写者互斥保护下，把 handler 从可发现的链表中摘除，然后释放写者锁。
2. 等宽限期，确保摘除前可能已经进入 handler 的执行都结束。

随后才可卸载模块并释放其代码内存。图 4 的 `unregister_nmi_handler` 只画到同步等待，**没有画出释放模块代码的调用**；不能把图里不存在的调用当作实际实现。

这个模式说明，RCU 的“读者”不必只是读取几个字段，也可以是需要等它完成的一段活动。确定性与低开销来自读侧不等待写者；注销操作本身仍需等待，而且同步等待应发生在允许阻塞的上下文，不是在 NMI 中任意调用。

### §3.2 临时存在性保证：IP options 与长期引用

论文 §4.2 将一种用途称为 Reference Counting，但其中并没有对共享整数执行逐读者增减。它要达到的是引用计数常见的目的：**有人使用对象时，内存不能被回收。**

p.6 图 6 给出 socket 的 IP options。`udp_sendmsg` 在准备数据包时进入读侧临界区，通过 RCU 指针取得当前 options，若非空就把选项复制到包中，然后退出临界区，之后才把包排队发送。退出后使用的是包内副本，不再依赖旧 options 对象的寿命。

更新侧用完整的新选项对象替换 socket 指针，并通过 `call_rcu` 延后释放旧选项。发送线程若先取得旧版本，可以完成那次复制；之后取得新版本的线程则复制新选项。接口必须容许与设置操作重叠的发送采用旧配置，而不能要求修改时所有在途读取瞬间重启。

若调用者需要在睡眠后继续持有对象，短期读侧保护不够。论文提出与传统引用计数组合：在短读侧保护仍有效时取得长期引用，随后退出 RCU 临界区；回收必须同时满足长期引用消失和相关宽限期结束。FAQ 也指出，xv6 `struct file` 这样的长期引用不能仅靠本课 RCU 模型替代。

> 编者注：图 6 是省略许多上下文的伪代码，没有展示完整的写者序列化、参数分配和错误处理。它演示的重点是发布新选项与延后释放旧选项，不是一份可直接复制到 Linux 的函数实现。

### §3.3 保持类型，不一定保持对象身份

论文 §4.3 讨论更微妙的 type-safe memory。通常的存在性保证要求一个对象在读者使用期间不被回收复用；类型安全内存则允许某个位置被**同类型的新实例**复用，但不让它突然变成另一种布局。读者仍需要检查身份或版本，发现复用后放弃、回滚或重试。

Linux slab 分配器把页切成相同类型的对象。对象可以在 slab 内被释放与重用；整个 slab 页完全空闲后，才可能归还页分配器，继而分配给其他类型。论文使用当时的标志名 `SLAB_DESTROY_BY_RCU`：把“页可能转变为其他类型”的时机延后到宽限期之后。**这不等价于每一个槽位里的旧对象都保持原身份不变。**

例子是反向页映射。内核从物理页相关信息找到匿名虚拟内存映射对象 `anon_vma`，而另一线程可能正在取消映射并释放它。若在每个物理页描述符中增加锁，空间成本很高；直接把全部析构移到 RCU 回调也有问题，因为旧代码的释放路径可能需要 mutex，阻塞一个回调就可能拖住整批回调处理。

类型安全分配提供一个工程折中：在允许辨认对象复用的条件下，保住布局与检查所需信息，同时避免立刻重写所有依赖既有析构行为的代码。论文脚注还提醒，一个 `anon_vma` 通常对应多个物理页，不能把它误读成严格的一页一对象关系。

### §3.4 发布—订阅：动态系统调用扩展表

论文 §4.4、p.7 图 7 用 PowerPC Cell 的系统调用扩展表说明 publish-subscribe：写者初始化整张扩展表，再发布其入口指针；读者取得指针并调用表中的函数。这个模式强调“通过一个受控入口，使准备好的整体可见”。

撤回时先把入口指针发布为 `NULL`，使之后的查找知道扩展表不可用；然后等待宽限期，确保先前取得该表并正在执行其中函数的读者已经结束，才释放表。发布与存在性保证在这里组合使用。

图 7 把进入、调用、退出都放进一个读侧区间，是面向所讨论模型的伪代码；不能据此推断任意会睡眠的系统调用都能直接放进这种不可抢占读区间。单纯管理表指针和管理被调用代码的生命周期，也必须按实际系统共同设计。

### §3.5 替代读写锁：PID 查找及其语义变化

论文 §4.5 的 PID 表使用读侧临界区查找，更新者用桶级锁管理修改；需要在查找返回后继续使用进程对象时，另取得引用。它兼顾热点查找与长期持有，不要求把整个调用过程都留在 RCU 临界区内。

然而，“用 RCU 替代读锁”并不保证原有读写锁的所有观察结果都保留。两个写者往不同桶加入 A、B；两个并发读者以相反次序查看它们，可能各自看到自己的第一个目标，却没看到第二个。论文用此说明，多个对象之间的观察次序与快照性质需要重新分析，不能只证明单个指针有效就结束。

> 原文伪代码问题：已查看 p.8 图 9。其 `pid_remove` 先通过 `p` 把槽位置空，再判断 `*p` 并把它传给回调，没有显式保存被摘除对象；照抄会丢失需要回收的旧指针。`pid_free` 的减引用返回值语义也未完整定义。这里解释模式，不把该图当可运行的正确实现。实际设计应在写锁保护下保存旧对象，并依据真实引用计数 API 判断何时释放。

## §4 性能结果：条件、单位、图文差异

论文 §4 的实验条件为：**16-CPU、3 GHz Intel x86 系统，Linux 2.6.23，测试写成内核模块**。这些是该论文历史测量条件，不是 2020 录像时的新测试，更不是本次制作页面运行出来的结果。

### §4.1 图 5：空读侧临界区与共享引用计数

每个 CPU 一个线程，循环执行一种同步动作：或者进入、退出一个空 RCU 读侧临界区，或者把同一个共享引用计数加一再减一。

- 横轴：参与的 CPU 数。
- 纵轴：一次完整同步动作的开销，单位 **nanoseconds（ns，纳秒）**，对数刻度。
- 比较对象是同步开销，不包括遍历对象、处理数据包或完整系统调用的业务工作。

| 测试项 | 1 CPU | 16 CPU | 原文定位 |
|---|---:|---:|---|
| 空 RCU 读侧区间 | 6 ns | 保持大致恒定，正文未另给精确端点 | p.4 §4.2；p.5 图 5 |

### §4.2 图 8：读锁比较存在明显的图文不一致

论文 p.7 §4.5 的文字明确给出：

| RCU 进入、退出 | 6 ns | 描述为相对恒定，未给精确值 |

### §4.3 这些测量没有回答什么

微基准说明“读者修改同一共享位置”可能非常昂贵，但它没有单独给出应用改造后的端到端吞吐量，也没有系统扫描读写比例、对象大小、复制成本、宽限期尾延迟与待回收内存的全部组合。

更不能把 Linux 2.6.23 的传统共享整数读写锁结果推广成所有现代读写锁实现。论文脚注本身就提到后来一些更可扩展的读写锁使用 RCU 或类似技术。本文没有复现实验，也不以“原文有图”替代对部署负载的实际测量。

## §5 三类算法改造：让应用容许并发读写

论文 §5 针对的不是内存安全一个问题，而是去掉读写互斥后，应用可能观察到不允许的状态。

### §5.1 增加一层间接访问，发布一致的对象版本

如果多个字段原先依靠写锁一次性对读者生效，机械去锁会让读者看见中间状态。把需要一致更新的字段放到同一个独立对象中，写者准备完整新版本，再发布一个入口指针，能把这些字段的一致性绑定到版本选择上。

这一原则在课堂链表与树的推导中已经展开，见中文译稿 36:00–45:00。论文进一步强调，链表、哈希表和搜索树原本就常有间接访问，因此不一定需要为 RCU 引入全新的组织形式。

### §5.2 标记已失效对象，防止“内存还活着”被误当作“仍有业务资格”

完整旧版本不等于合法当前对象。System V 信号量被应用删除后，即使为了旧读者安全还没释放其内存，继续把它当作可用信号量也可能违反接口语义。

论文描述为每个信号量对象增加 obsolete 标志：删除时设置，查找者在 RCU 保护下找到对象后检查；若已失效，则按查找失败处理。这里解决的是逻辑删除后的资格问题，而不是对象内容半初始化的问题。

标志并非脱离上下文的一次普通检查就足够。原文给的是模式，实际仍要把检查、并发状态变化及后续操作纳入同一语义协议。本课没有展开具体 System V IPC 的全部实现，不能把这个小节当作可直接编译的补丁。

### §5.3 检测版本变化并重试，避免从不同时间拼出不存在的路径

有些时候，发现对象过期后不应直接失败，而应重新查找新版本。论文举出 RCU 与 sequence lock 的组合：写者开始修改时把序号从偶数推进为奇数，结束时再推进为偶数；读者只有在前后看到相同的偶数序号时，才能接受读取结果。

读者先读取序号；若正在写，则等待或重试。随后在 RCU 保护下访问对象，再检查序号是否改变；若改变，丢弃这一轮观察并重新执行。RCU 负责对象寿命，序号校验负责判断观察是否跨越了更新，职责不同。

VFS 路径查找的例子尤其直观：目录项可被并发重命名或移动，读者逐分量查找时，可能把不同时刻的片段拼成一条从来没完整存在过的路径。序号验证帮助识别这种不一致并重试。

这一改造带来代价：更新很多时，读者可能多次重来。RCU 本身的读侧进入/退出便宜，并不保证与重试协议组合后的整个操作仍有固定延迟。

## §7 与其他回收方式的关系

论文 §7 把 RCU 放进更广泛的并发回收背景中。DYNIX/ptx、Tornado、K42 等系统有相近思想；不同方案选择不同的“所有旧使用者已经离开”证据。Hazard pointers 则让读者发布自己正在保护的引用，因此也能推迟回收，但读者需要写保护状态，某些架构上还需屏障。Epoch-based reclamation 以阶段推进组织类似的安全条件。

这些方法共享的核心问题是：**如何在不误回收的前提下，廉价地证明旧使用者已经结束？** 具体成本落在读者、回收者还是批次之间，各不相同。本文只整理指定论文对这些工作的定位，没有声称实际阅读了所有被引论文或复现其比较。

RCU 也不是完整垃圾收集器。程序员仍要指出哪些对象已经从结构中摘除、可以候选回收，并保证访问处在正确保护范围内；RCU 帮助决定这些候选对象何时可以安全回收，不会自动追踪任意 C 指针的可达性、找出所有垃圾。

论文 §8 的结论可归纳为：RCU 的成功来自一组可组合的模式——等待完成、临时引用、类型安全内存、发布订阅、替代读写锁——以及为了保住应用语义而进行的算法改造。它的普及不意味着普通锁已经无用，而是表明生产内核需要多种机制共同处理不同访问模式。

## §8 FAQ 阅读对照与补充

官方 FAQ 有 13 个实际问题；第 27 行把第三题答案误写为 `Q:`，不是第十四个独立问题。为避免重复课堂或论文解释，下面保留每题定位，并只展开新增边界。

| FAQ 问题（按原文顺序） | 回答要点与阅读位置 |
|---|---|
| 1. 等待可能几毫秒，为什么还能快？ | 看收益是否覆盖少量写者的额外成本。课堂 54:00–57:00、69:00–72:00；微基准边界见本页 §4。 |
| 2. `synchronize_rcu` 与 `call_rcu` 有何区别？ | 前者等完成再返回，后者登记回调并先返回；异步仍占着待回收内存。课堂 54:00–57:00，本页 §2.2。 |
| 3. `rcu_read_lock/unlock` 做什么？ | FAQ 说防止定时器引发抢占式切换，退出后恢复。应按本页 §2.1 的非抢占教学模型理解，不等于关闭全部中断。 |
| 4. 指针发布、解引用如何实现？ | FAQ 的全屏障伪代码解释顺序，不是跨架构真实实现；见本页 §2.3。 |
| 5. 谁保护写者之间的竞争？ | RCU 本身不保护，调用方另用锁等办法。课堂 60:00–66:00。 |
| 6. RCU 是否更容易出错？ | 规则与证明责任更多，FAQ 指向内核 RCU review checklist。这里保留这一工程判断，未把外链 checklist 当作已读材料。 |
| 7. 论文的“替代引用计数”指什么？ | 提供临时存在性保证，不是真的数引用；长期引用仍需其他机制。见本页 §3.2。 |
| 8. NMI 是什么？ | 非屏蔽中断；普通关中断不能挡住，锁使用尤其受限。见本页 §3.1。 |
| 9. 读者能看到被替换的旧数据吗？ | 能，重复查共享入口也可能看到不同版本。旧值是否允许取决于接口；见课堂 81:00–84:00、本页 §5。 |
| 10. 为什么 xv6 不使用 RCU？ | xv6 优先教授通用、易解释的自旋锁；QEMU 下也难用教学负载可靠判断这种优化收益。不能由此推论 RCU 对所有真实小机器都无用。 |
| 11. `synchronize_rcu` 怎样实现？ | FAQ 给出每核上下文切换计数的基本思路，并链接另一篇实现论文；本页 §2.2 依据已读指定论文解释批处理，未宣称读完此外链。 |
| 12. 不挡住写者，为什么还能有效？ | 大部分正确性来自写者遵守组织规则，而不只是读者调用一个名字带 lock 的函数；机制负责等待，应用负责正确发布和使用。 |
| 13. 哪些情况不适合？ | 写频繁、必须跨睡眠持裸指针、必须原地更新、不能形成合适提交结构、必须在不能阻塞的上下文同步等待；限制针对本课模型。见本页 §2、§5。 |

FAQ 对旧值窗口提及“纳秒或微秒”的经验尺度，但这不是 API 规定的固定上界；本片 75:00–78:00 也强调不能简单给出统一界限。尤其不要把它理解成“睡眠几微秒就可以释放”，回收需要实际宽限期证据。

对“读者不更新，所以不会丢增量”的解释，也要注意前提：读取计数再写回加一属于读改写，已经不是本讲的纯读路径，不能套用“读者无需协调”来维护共享计数。
