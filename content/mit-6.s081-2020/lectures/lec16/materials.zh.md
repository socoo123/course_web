# 第 16 讲 · 为 ext2 增加事务日志

文件系统崩溃后，恢复时间为何会随磁盘容量不断增长？如果系统可以准确指出“哪些更新尚未完成”，恢复是否还需要检查整块磁盘？这篇论文用给既有 ext2 增加事务日志的设计回答这两个问题。

## §1 问题、目标与证据边界（第 1 页）

当磁盘容量增长快于扫描速度时，传统启动检查会越来越久。机器虽然已经重启，服务却仍要等文件系统完成扫描和修复。作者希望减少的是这段不可用时间，而不只是提高正常运行时的文件读写速度。

设计受到三项约束：正常性能不能显著下降，现有应用接口不能被破坏，可靠性也不能因优化而退步。外部接口规定文件名、属性及其语义；内部的磁盘布局、缓存方式、I/O 调度则有较大设计自由。论文以 UMSDOS 在既有磁盘格式上实现另一套接口语义为例，说明应用接口与内部表示不必一一绑定。

这里研究的是 **1998 年尚在开发中的设计**。标题里的 ext2fs 是起点，并不是说成熟 ext2 本来就有这套日志。课程后来把这一演进方向称为 ext3；阅读时应把论文的历史方案与课堂介绍的后续实现分开。

## §2 “可靠恢复”要分别满足什么（第 2 页）

作者把可靠性拆成三个性质：

| 性质 | 要保证的事情 | 不能混淆的结论 |
|---|---|---|
| Preservation，保存性 | 崩溃之前已经稳定在磁盘的数据，不应被恢复过程破坏 | 正在进行的写不因此自动完整 |
| Predictability，可预测性 | 中间磁盘状态遵循规则，恢复能解释它 | 中间状态可解释，不代表恢复不必全盘扫描 |
| Atomicity，原子性 | 一项包含多次 I/O 的文件系统操作，恢复后完整发生或完整未发生 | 原子性不是每一步都立刻落盘 |

跨目录重命名是原子的典型需求：恢复后应保留旧名字或新名字，不能留下操作执行了一半造成的错误组合。

论文把当时 ext2 的恢复描述为具有保存性，但缺少足够的原子性与可预测性。它关心的是如何让更新过程具有可解释的结构，而不是靠恢复程序在任意碎片之间猜测原先想做什么。

## §3 几条候选路线及其代价（第 2–3 页）

### §3.1 同步更新、延迟有序写与 soft updates

最直接的做法是：先完成第一批磁盘写，再发下一批，从而强制更新顺序。BSD Fast File System 是论文讨论的重要背景。缺点是每次调用都可能等待设备，缓存中的多次修改难以合并。例如连续创建十几个目录项，如果它们都在同一目录块，逐次同步会让同一块反复写盘。

可以改为在内存中记录依赖，到真正写回时确保前驱块已经持久化。这样调用不必立即等待，但依赖可能成环：同时把文件从目录 A 改名到 B，又把另一个文件从 B 改名到 A，两个目录块便可能互相等待。

论文介绍 soft updates 的思路是选择性回退某个缓存块里尚不满足依赖的更新，先写一个安全版本，之后依赖满足再恢复遗漏部分。这个方法帮助摆脱块级循环依赖。这里是对相关工作的概念比较，不是对其实现或后续版本的完整说明。

这些方案即使使中间状态更可预测，传统恢复仍可能需要扫描整个文件系统，才能找出哪些操作尚未完成。因此“可恢复”与“恢复快”是两个不同目标。

### §3.2 写时复制树、日志结构文件系统与 journaling

实现原子更新的共同思路，是暂时保留旧、新版本，并通过一个明确的持久化动作决定采用哪一组。论文讨论三种组织方式：

- **WAFL 式树更新：**把被修改节点写到新位置，通过根部更新切换到新结构。旧空间随后可回收。
- **Log-Structured File System：**把文件数据和元数据持续写成日志流。写入可以很顺序，但要另外解决从逻辑对象找到其最新位置的问题。文中引用 Sprite LFS、Berkeley LFS 与 Linux LFS 项目作为背景。
- **Journaling：**保留传统文件系统的固定原位置，先把新版本写进独立 journal；提交完成后，再把更新安装到原位置。

第三种方式尤其适合给现有 ext2 增加恢复能力，因为不需要把所有永久数据重新组织成日志。不要把“文件系统有日志”与“整个文件系统是日志结构布局”画等号。

未提交时，丢弃日志中的新版本即可保持旧状态；已提交时，把日志版本复制到原位置完成更新。文中将这两种结果概括为 undo/redo，但这里的“放弃未提交更新”不要求去原位置执行一批反向写——原位置本来就不应被未提交元数据覆盖。

## §4 为什么 journal 能缩小恢复工作量（第 3 页）

如果可能导致原位置不一致的更新都还有日志记录，恢复便可只扫描 journal，把完整提交的更新重放到文件系统。journal 通常远小于整个文件系统，恢复不必为寻找少数未完成更新而检查全部历史数据。

这同时意味着，必须维护一个完整证据链：未提交更新不能提前覆盖旧结构；已提交但尚未写回的更新不能提前丢失日志。快速恢复不是凭空省略检查，而是正常运行时主动把“需要检查的范围”限制在日志中。

作者希望复用 ext2 的磁盘布局与代码，只增加日志相关功能。这是一种兼容性策略：已有的文件访问算法和磁盘结构继续使用，新增事务层负责规定哪些版本何时能成为持久状态。

## §5 一次文件系统操作隐含的依赖（第 4 页）

### §5.1 修改集合不仅是文件内容

一次写至少可能更新 inode 的修改时间；若扩展文件，还会改长度、块映射，分配块时又牵涉配额信息、空闲空间统计和位图。要使操作保持一致，这些修改必须按完整集合处理。

这里的 transaction 起初指单个文件系统请求的更新集合。论文稍后引入 compound transaction，把许多这样的操作合起来提交。因此不要把这两个层次的“事务”误读为彼此矛盾。

### §5.2 只看共同写了哪些块，还不够

操作会读取已有状态，再根据读到的内容作决定。假设先从一个目录块删除某名字，后续操作在另一目录块里插入同名项。即使两次操作没有写同一个块，后者的合法性也依赖前者已经删除旧名字。

如果后者持久化了，前者却在崩溃后消失，就可能出现重复目录项。因此依赖不仅来自写写冲突，也来自读到前一操作效果后形成的决定；提交顺序必须尊重这些关系。

### §5.3 dependent data：新增可达性之前先写内容

分配新数据块时，还要先让新内容真正到达磁盘，才能提交使它归属某文件的元数据。否则，崩溃后新 inode 指针可能指向旧内容，而那块内容原本属于已删除的其他文件。

从位图和指针关系看，磁盘结构甚至可能完全一致，但用户却读到他人的旧数据。论文把这些必须先写的数据称为 dependent data。因此它讨论的是**元数据日志加相关内容的顺序约束**，不是简单地只管元数据、不管内容写入时机。

## §6 为什么合并事务既简化实现又提高吞吐（第 4–5 页）

论文借用数据库术语，但没有直接照搬通用数据库事务模型。作者依赖两个特点：文件系统操作相对短；在开始实际修改前，已完成必要合法性检查，不需要提供数据库那种任意中途 abort 的通用机制。若发现同名文件等错误而尚未修改，作为没有更新的操作结束即可。

这是论文对目标实现的设计假设，不能推广成“现实文件系统永远不会遇到中途错误”。

短操作使顺序提交成为可接受选择：不必支持任意长事务独立提交、再维护复杂的跨事务依赖。系统周期性建立一个全局复合事务，让这段时间内的文件系统调用都把修改加入它，最后整批提交。

收益在于热点块的写吸收。某个 inode、位图或配额块被反复修改，最终只需把这一批的最后版本记录一次；无需为每个小更新产生一个独立日志副本。

提交周期是策略参数，不是纯粹的正确性常数。等得更久，合并机会更多，长期 I/O 可能更少；代价则包括：

1. 占用更多内存和日志空间；
2. 崩溃时可能丢失更长时间内尚未提交的更新；
3. 积攒后集中写盘，可能形成突发 I/O，使响应延迟不够平稳。

因此不能仅以总吞吐评价“提交间隔越长越好”。

## §7 论文中的磁盘格式（第 5–6 页）

### §7.1 利用保留 inode 保存 journal

ext2 已有保留 inode 编号，论文计划使用其中一个存储日志文件。并通过已有的兼容性位图标记 journaling 扩展：旧内核能够辨认原有布局，但不应在不理解日志约束的情况下直接写这个文件系统。

兼容磁盘布局不等于允许任意旧实现忽略新协议进行写入。前者降低迁移成本，后者会绕过原子更新规则。

### §7.2 三类记录及整块日志

论文的日志包含元数据块副本、descriptor blocks 与固定位置的 header blocks。

| 记录 | 论文中承担的职责 |
|---|---|
| 元数据块副本 | 保存被修改的整个块的新内容，即使只改了一个位 |
| Descriptor | 说明随后有多少元数据块，以及它们对应的原位置块号 |
| Header | 保存日志 head、tail 与序号，恢复时选择序号最新的有效头并按其范围扫描 |

整块写看起来浪费，但论文给出两项理由。日志写往往是顺序的，容易合为大批 I/O；直接把缓存块内容写出去，也比构造细粒度修改记录省 CPU 工作。

Linux 的 `buffer_head` 描述缓存缓冲区及其磁盘位置。要把现有缓冲内容写到日志，可建立临时 `buffer_head`，复制描述信息并把目标设备块号改为 journal 中的位置，再提交给设备 I/O；完成后释放这个临时描述。**复制的是描述结构，不要求为每次日志写都复制整块内容。**这与跨事务冲突时的内容复制是不同机制。

日志顺序写到末端后绕回。head 表示写入进度，tail 表示尚未释放的最老记录；二者追上时，新日志写需要等待清理旧事务来取得空间。

### §7.3 不把 1998 方案改写成后续 ext3

论文用固定位置的 header 记录 head/tail/序号，更新 header 完成提交；课堂则用日志 superblock 定位最老事务，描述块和独立 commit block 表示每个事务，扫描有效提交前缀。

它们都解决“哪些更新已经完整提交、哪些日志可回收”，但物理格式不同。本页保留论文自己的设计，不用课堂术语把它静默替换。后续 ext3 的 magic 转义与残留提交块问答，见[中文译稿](#/c/mit-6.s081-2020/lec/lec16?v=draft)63:00–69:00、84:00–87:00。

## §8 提交、checkpoint 与不能过早删除的日志（第 6 页）

达到时间阈值，或日志空间趋紧时，系统希望提交当前复合事务。**提交**使事务有完整的持久恢复证据；**checkpoint** 则推进其更新到文件系统原位置，使旧日志最终不再必需。二者不是一个事件。

论文描述的流程可以读成以下阶段：

1. 关闭旧事务，建立新事务来容纳后来的操作；已经属于旧事务的未完成操作仍归旧事务，不能把一次操作拆开。
2. 独立日志写线程开始把旧事务修改的元数据写向 journal，同时写出 dependent data。被 journal 保存的缓冲区继续“钉住”这个事务的日志，直到不再需要它来恢复。
3. 等待旧事务尚未完成的操作结束。论文明确允许前一阶段的日志输出与这些操作的结束有一定重叠。
4. 等待该事务的全部更新完整记录到日志。
5. 更新 journal header 的 head/tail，完成提交；随后允许将更新写回原位置。
6. 等最后一个需要该事务日志的缓冲区也已安全写回，更新日志 tail，才能复用相应空间。

原 PDF 的编号从 5 跳到 7；上面按语义整理为六个阶段，没有凭空补出一个“原文第 6 步”。论文的早期重叠安排也不同于课堂明确画出的“先等旧系统调用全部结束，再放行新事务调用”屏障，不能把两份材料当成同一份逐行实现规范。

### 阅读入口的思考题：删除日志过早会怎样？

课程入口要求为“原位置写回未完成前，不能删除 journal 副本”构造具体反例。以下是编者给出的推演：

- 一次追加要把 inode 的新块指针和位图的分配标记一起更新。
- 两块都已记录并提交到 journal，因而事务已经承诺恢复后成立。
- 原位置只写回 inode，位图仍显示这块空闲。
- 若这时回收并覆盖 journal，然后断电，恢复已找不到新位图。
- 重启后 inode 使用该块，位图却允许再次分配它，两个文件可能错误地共享存储。

可见，提交意味着“日志可用来补完”，并不意味着“日志已可丢弃”。日志必须一直保留到它所弥补的缺口已经消失。

## §9 两个事务争用同一缓存块（第 6–7 页）

为了让旧事务提交时仍能处理新调用，需要解决缓存版本问题。若新事务只是读取旧事务更新后的块，它建立了一个读写依赖；论文利用复合事务严格顺序提交来处理这个方向的依赖。

若新事务还要修改同一块，情况不同：旧事务必须把自己的完整版本写进 journal，不能夹带新事务的一半修改。论文提出在发生这种冲突时复制缓冲区：一个副本供新事务继续修改，另一个仍归旧事务用于提交。

旧事务完成日志提交后，专供它提交的缓存副本可以删除；但这不等于可以立即回收它的日志空间。论文要求这份信息已在文件系统其他安全位置保存，并指出更新后的缓冲会进入下一事务的 journal，从而继续维护恢复责任。

这是区分**内存副本寿命**与**磁盘恢复证据寿命**的好例子。不要因为某个临时内存对象可以释放，就推论同一事务的全部持久记录也已经无用。

## §10 作者提出的后续研究方向（第 7–8 页）

### §10.1 调参和差量日志

论文当时还没有稳定代码基线的完整测试结果。提交频率、日志大小和具体瓶颈都被列为接下来需要研究的对象。

一种可能优化是只记录被修改的值，而不是整块保存。这样可能减少 journal 字节量，但作者没有断言它一定更快：现方案多数写不需要整块内存复制，顺序 I/O 又可以从内存直接交给设备控制器；为了压缩更新所做的 CPU、内存和总线工作，可能抵消省下的磁盘流量。

### §10.2 NFS 改变“快”的定义

论文指出，NFS 服务端不能在请求尚未安全持久化时就报告完成，否则服务端重启后客户端已获确认的数据会消失。这使服务性能取决于**磁盘提交延迟**，而不仅是本地应用修改缓存后返回的延迟。

文中比较的 Calaveras 方案为每个应用文件系统请求记录独立事务，以更快完成单次持久化；复合事务则优先合并多次更新，提高吞吐，代价是单次落盘延迟可能更长。

作者提出两条可能方向：缩小事务以降低等待，或者把普通文件数据也纳入日志，使数据能快速进入顺序持久化路径。这里是未来设计空间，不是本文已经测得的优胜结论，也不是说“数据日志在任何负载下都更快”。

### §10.3 独立日志盘与多个文件系统

同一套机制原则上可以让多个文件系统共享单独设备上的日志。独立日志盘承担近乎连续的写流，主文件系统磁盘则保留带宽处理正常数据和回写。论文把它作为潜在性能改进，没有提供多设备负载实验来量化收益。

## §11 结论以及论文没有证明什么（第 8 页）

作者预期，这种扩展能使恢复更快、更可预测，提高系统可用性，同时只需对 ext2 主体代码做有限修改。沿用既有磁盘布局，还意味着用户有机会在不重新格式化的情况下给原文件系统增加日志。

不过，相关新数据必须尽快写盘，才能提交相应的创建与分配事务。这会减少原先延迟写回带来的合并机会，因此短命临时文件密集的 `/tmp` 负载可能不适合该设计。不能把“正常性能应当损失不大”读成对所有工作负载的保证。
