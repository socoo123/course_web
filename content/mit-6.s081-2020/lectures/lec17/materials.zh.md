# 把页保护变成应用的算法原语

应用每次读写内存时，处理器本来就要检查访问是否合法。如果应用能决定何时让这个检查失败，并在失败后补做工作，就能把原本散落在每次访存周围的软件判断，转成较少发生的页级处理。

这篇论文关注的不是“如何写一个通用分页器”，而是三个相互关联的问题：**哪些应用需要操纵 VM？它们需要哪些共同机制？现有 OS 的实现成本是否合适？** 阅读时应把算法正确性、接口可表达性和性能三个层次分开。

## §1 核心主张与六种原语（p.96–97）

传统虚拟内存让地址空间大于物理内存，并提供进程隔离。但内核还使用页保护完成共享、只读代码、按需清零与写时复制。论文主张，用户程序也应能以受控方式利用相同的硬件机制。

只把用户级 fault handler 当作“崩溃前打印友好错误信息”的设施，会掩盖更重要的性能要求。错误退出很少发生，慢一些不明显；如果 handler 是 GC、共享内存或 checkpoint 的常规路径，其开销就会进入应用的主要成本。

| 论文名 | 应用需要的能力 | 需要区分的语义 |
|---|---|---|
| Trap | 由用户态代码响应页面访问异常 | 硬件异常仍先由内核承接 |
| Prot1 | 降低一页的可访问程度 | 例如读写→只读，或只读→不可访问 |
| ProtN | 批量降低 N 页的可访问程度 | 不是仅在语法上包一层循环，要允许摊薄固定成本 |
| Unprot | 增加一页的可访问程度 | 常在一页工作完成后恢复访问 |
| Dirty | 得到自上次查询以来被修改的页集合 | 与“当前页是否存在”无关 |
| Map2 | 同一物理页在同一地址空间有两个地址、不同权限 | 共享内容，权限按映射区分 |

作者单列 ProtN，是因为许多算法在某一时刻批量设置保护，却在后续按需逐页解除保护。既然调用形态并不对称，就不必假设降低和增加权限必须提供完全对称的批处理接口。

Dirty 可以用其他能力模拟：把待观察页设为只读，首次写入触发 Trap，在软件中登记该页后 Unprot。以后本轮对同页的写入不再陷入。原生 Dirty 仍有意义，因为内核或硬件可能更便宜地提供这一信息。

Map2 解决的则是“客户暂时不能看，但服务线程必须处理”的情况。两种地址最好处在同一页表中，避免为每次处理切换重量级进程上下文。它并不是把物理页复制两份。

## §2 八类应用怎样使用这些机制（p.97–101）

### §2.1 并发复制式垃圾收集

复制式 GC 从根出发追踪活对象，把它们由 from-space 移到 to-space；不被追踪到的对象成为可整体回收的旧区域内容。Baker 的增量算法把工作拆小，让 mutator（修改堆的应用）在收集期间继续分配和计算。

理解这一算法，关键是论文 p.97 给出的分区不变量：

- 应用寄存器中的有效对象指针指向 to-space。
- 新分配对象中的指针来自应用已经持有的安全引用，因此指向 to-space。
- 已扫描对象的内部指针都已修正为 to-space 指针。
- **未扫描对象可以同时含有 from-space 和 to-space 指针。**

原始方案在从对象取得指针时检查其目标；必要时复制目标并修正指针。代价是每次相关访问要增加指令，并且应用与 collector 同时复制同一个对象时需要处理竞态。

VM 版本把未扫描 to-space 页对应用设为不可访问。应用碰到这样的页面，handler 扫描本页的对象，把其中指针指向的旧目标搬到新空间，再修正指针并开放本页。被搬来的目标可以继续处于未扫描状态，只要应用在真正访问其内部字段之前仍会被保护机制拦住。

collector 也可在后台主动扫描，因此局部性好、后台推进快时，应用触发的 fault 会更少。Map2 使 collector 能通过可读写别名处理仍对应用隐藏的页。所需核心能力是 Trap、ProtN、Unprot、Map2；更小的页可能降低一次前台处理的延迟。

课堂中这套机制的对象追踪过程与代码走读已在[中文译稿](#/c/mit-6.s081-2020/lec/lec17?v=draft)45:00–75:00展开。这里的分区不变量比一句“所有新空间指针都已修正”更精确。

### §2.2 共享虚拟内存 SVM

图1（p.98）画的是多节点系统：每个节点有 CPU、本地内存和 mapping manager，节点之间用消息网络通信，却向程序提供一个共享虚拟地址空间。图中“共享”不是说底层突然多出一条硬件共享内存总线。

基本协议在页粒度维护 **多读者、单写者**：

1. 只读页可以同时缓存在多个节点。
2. 想写某页的节点必须取得最新内容和写权限，并使其他节点的旧副本失效。
3. 页不在本地，或本地只有只读副本却要写时，访问异常把请求交给 mapping manager。
4. manager 从其他节点或后备存储取得页面，调整保护状态，再让访问继续。

因此本地物理内存可被视作共享虚拟空间的一块缓存。论文借助页保护实现的是协议需要的访问控制与通知；消息传递和一致性状态机仍是实际算法的一部分。该方案需要 Trap、Prot1、Unprot；并发服务代码访问受保护内容时也需要 Map2 一类能力。页越大，协议的协调粒度越粗；论文因而把较小页列为值得考虑的参数。

### §2.3 并发 checkpoint

checkpoint 要保存某一时刻可恢复的程序状态。如果暂停所有线程，把全部可写内存都复制完再恢复，停顿可能太长。

论文描述的并发方法是：先短暂停止线程，取得必要的执行状态并建立内存快照边界，把待保存区域设为只读；随后恢复应用，由后台线程逐页复制。已复制完的页可以恢复写权限。

应用若抢先写一张还没复制的页，就触发异常。必须先保存该页在快照时刻的旧内容，再开放写入并重试原操作。不能先让写成功，再复制新内容，否则快照会混合不同时间点的状态。

论文引用 DEC Firefly 多处理器上的既有测量：约90%的 checkpoint 工作与目标程序并发进行，单次线程中断不超过0.1秒（p.99）。这是**被引用算法的测量条件与结果**，不是本论文表1的微基准，也不是所有应用的实时保证。

增量 checkpoint 可以只保存上轮之后的脏页；Dirty 提供这些页的集合。原文相关段落列出 Trap、Prot1、ProtN、Unprot、Dirty，表2强调的主要路径是批量保护加逐页处理。读表时不宜把每个勾选都理解为一个不可替代的同名系统调用。

### §2.4 分代垃圾收集

论文依赖两个经验规律：年轻对象更容易很快死亡；新对象通常指向已存在的较老对象。因此频繁收集年轻代可能比每次扫描全堆便宜。

难点是老对象后来被修改，开始指向年轻对象。只从栈和寄存器找根可能漏掉这些跨代引用。软件方案在写入处插入检查，维护相关记录；论文指出，对它讨论的 Lisp、Smalltalk 等系统，这种检查序列可能占总执行时间约5%–10%，即使这种非初始化写入本身并不常见。

VM 方案可以把老年代设为只读。第一次写某页时，登记这个页并恢复写权限。年轻代收集时，扫描登记的老年代页，找出其中指向年轻代的引用；若 OS 提供 Dirty，则可以直接使用脏页集合。

必须注意：**脏页只说明“这里可能有需要追踪的引用”**，并不直接告诉 collector 哪个字段是跨代指针。页内扫描依然需要对象布局信息。较小页可减少因一次写入而额外扫描的不相关内容。

### §2.5 持久化对象存储

持久化存储把堆中的对象图延续到多次程序运行之间。程序希望像访问普通堆那样，直接用指针遍历对象；同时修改可以 commit 或 abort，崩溃后数据不能消失。

内存映射让普通 load/store 成为访问路径，缺页负责把尚未读入的部分带入内存。但修改内存副本不应立即破坏永久副本：在 commit 前，磁盘上的已提交状态必须保持可恢复。程序提交时，才把脏页及必要的新页写回，必要时可在提交阶段收集垃圾。

论文把这与传统数据库的访问函数进行比较：后者通过每次过程调用执行同步和事务规则；持久化对象系统希望保留直接访存的快速路径，同时另行提供事务、锁和恢复。**把文件 mmap 进来，本身并不等于实现了事务。**

所需能力包括 Trap、Unprot，以及带写时复制语义的文件映射；缺少原生 COW 时，可用保护与多重映射模拟。p.105 还讨论了暂时阻止未完成事务的页面过早写回，以及让应用参与换出决策等更丰富接口。

### §2.6 扩大可寻址对象集合

这是32位地址时代的动机：持久化存储可能超过32位指针所能标识的对象范围，但一次运行通常只访问其中一小部分。

一种方案是在磁盘中保存长指针，在当前运行的内存中使用短指针。论文的示例是磁盘64位、内存32位：调入页面时，通过转换表把磁盘引用转换为当前进程的地址；某个短指针还指向尚未实际读入的页时，访问会触发 handler，再进行下一批转换。

转换表只服务本次运行实际涉及的子集，所以内存地址空间不必同时容纳持久化存储的所有对象。论文“磁盘页是内存页两倍长”的描述属于该示例的数据表示安排，不能泛化成所有64/32位转换系统的规则。

这一方案需要 Trap、Unprot 和保护操作；多线程情形还需 Map2 类能力。课堂后半段讨论更大地址空间时，强调了时代背景已经变化；不能拿1991年的寻址限制直接描述今天所有机器。

### §2.7 压缩分页

链式数据中往往有很多空指针、小整数、零以及指向相邻对象的地址；数据的有效信息量可能远小于原始字宽。论文引用一些对象布局研究，说明32位字组成的页面在适当条件下可能压缩到原大小约四分之一。

于是冷页不一定立刻写磁盘：先压缩后留在内存，下次访问时缺页触发解压；比等待磁盘读取更有吸引力。长期不用的压缩页仍可继续换出。

这类工作当然可以放进内核，但应用运行时可能更了解对象之间的关联，甚至能通过移动对象改善可压缩性，因此用户参与具有额外价值。还需要某种方法识别近期不活跃页面，例如暂时保护页面来观察是否又被访问，或者由 OS 提供使用情况通知。

这里的压缩比是特定数据特征下的可能性，不是论文证明所有内存都能无损压到四分之一。也不能把冷页压缩与课堂“平方根表丢弃后重算”混为一谈：前者保存信息，后者依赖结果可以重新生成。

### §2.8 堆溢出检测

栈常用 guard page 检测越界。类似地，某些 GC 分配器可以让分配区末尾紧邻不可访问边界；分配跨过边界时触发异常，启动回收，从而减少每次分配的显式上限检查。

p.101 的估算设分配区为64 KiB，每个 cell 为8字节，每50条普通指令分配一个 cell；若每次分配额外执行比较和分支两条指令，则：

$$
\text{cell数}=64\times1024/8=8192,
$$
$$
\text{普通工作}\approx8192\times50=409600\text{ 条指令},
$$
$$
\text{检查开销}=8192\times2=16384\text{ 条指令}.
$$

原文使用近似记法 $400k$ 和 $16k$，得到约4%的检查开销；若一次 trap 约1200 cycles，则其示意比例约0.3%。这只是原文的简化成本比较，不能忽略机器 CPI 后把 cycles 与 instructions 在任何平台上直接等同。

> 编者核对：同页前面的句子称64 Kbyte能放16k个8-byte cell，与除法和紧随的公式不一致；应为8k个。这里保留可核算的容量和公式，不沿用该处数量笔误。

作者还指出，可以通过合并连续分配的边界检查等方式优化，因此这并非文中最有说服力的应用。更重要的是，它对异常现场的要求比前面几种方案更苛刻，见§4.4。

## §3 怎样读这篇论文的性能结果（p.101–103）

### §3.1 测量的是哪条路径？

论文的两个主要微基准测量的是**组合操作**：

- 单页路径：访问一个随机选择的受保护页；handler 保护另一页，并解除当前页保护，重复执行以获得稳定计时。
- 批量路径：先保护100页，以随机顺序访问这些页；每次 handler 仅解除出错页的保护。

计时前都先写过各页，减少缓存和 TLB 初次填充的瞬态影响。论文描述了100次操作和重复测量过程；表1对保护基准报告的是 **每页耗时**，不是整批100页的总时间。

比较对象包括 SunOS、Ultrix、Mach 及 NX/2，机器有 Sun 3/60、SparcStation 1、DEC 3100、μVax 3 和 i386/iPSC/2。Mach 的 `xp` 是 external pager 接口，`exc` 是 exception port 机制，不能把它们当成两台机器。

另外测量 ADD 作为处理器速度标尺：使用含18条 add、一次比较和一次分支的20指令循环。部分系统还报告不修改内存保护的 Trap 时间。**这不是 OS 整体吞吐基准，也不应主要反映磁盘速度。**

### §3.2 表1的单位、选择性数据与陷阱

以下是核对 p.102 表1后抽取的几行，用于比较同机实现与批量效果；时间单位均为微秒：

| 机器 / OS | 单页组合 Trap+Prot1+Unprot | 批量组合的每页成本 Trap+ProtN+Unprot | Map2 | 页大小（字节） |
|---|---:|---:|---|---:|
| Sun 3/60 / SunOS 4.0 | 1238 | 1016 | yes | 8192 |
| Sun 3/60 / SunOS 4.1 | 2080 | 1800 | yes | 8192 |
| SparcStation 1 / SunOS 4.1 | 1008 | 909 | yes | 4096 |
| DEC 3100 / Ultrix 4.1 | 393 | 344 | no | 4096 |
| DEC 3100 / Mach 2.5 (xp) | 937 | 766 | no | 4096 |
| i386 on iPSC/2 / NX/2 | 302 | 252 | yes | 4096 |

不要把组合列都简称为“单独 trap 花多少时间”。表中独立 Trap 一列还包括 OS 开销和标准库用户侧 handler 路径；例如 Sun 3/60 / SunOS 4.0 的该列是760微秒，而不是1238微秒。

两个脚注尤其重要：

- SparcStation 1 / SunOS 4.0.3c 的919与839带星号；脚注说明相应 `mprotect` 实现没有正确刷新 TLB。不能把不满足正确性的快结果当作同等有效的优化。
- SparcStation 1 / SunOS 4.1 的独立 Trap 230微秒带匕首标记，是估算值。

原文也测试同一进程对共享对象的双重映射：SunOS 和部分 Mach 平台支持，Ultrix 不允许对同一共享对象在同进程两处 `shmat`。实际支持情况以表中机器/系统组合为准；“某 OS 有共享内存”不等于它一定实现了 Map2。

### §3.3 图2比较的是“相当于多少条指令”

图2把组合路径耗时除以相应机器的 ADD 标尺，以便跨架构观察实现效率。黑条表示批量保护路径，白色延伸表示逐页保护额外增加的成本；横轴不是微秒，而是相当于可执行的 ADD 数量。

不同平台的归一化差距约可达一个数量级，说明慢并不完全是硬件或机制本身注定的，也与 OS 实现有关。但 ADD 只是校准标尺，不是声称异常路径中实际退休了恰好这么多条机器指令。

### §3.4 500微秒的工作，为什么会被1200微秒的机制开销压住？

作者给出并发 GC 的说明性计算：每个字扫描约10条指令，页为4096字节、每字4字节，共1024个字；处理器速度20 MIPS，平均每条指令约0.05微秒。因此一页扫描计算约为：

$$
10\times1024\times0.05\ \mu s=512\ \mu s\approx500\ \mu s.
$$

如果异常处理与页面保护等 OS 开销约1200微秒，机制成本就比有效扫描本身还大。对于有磁盘 I/O 的传统分页，几毫秒额外 CPU 开销可能被约20毫秒磁盘等待掩盖；这里全部在 CPU 内处理，没有这种掩盖。

吞吐与延迟也应分开。如果程序要求单次暂停不能超过1毫秒，即使500微秒扫描看起来可以接受，再加1200微秒就无法满足。局部性可减少发生次数，却不能自动缩短一次慢 fault；连续多个 fault 的情况还需要进一步分析。

这些是论文用来论证接口效率重要性的历史数据与模型，**不是2020课堂实测，也不是当前 Linux 的基准结果**。

## §4 从算法反推 OS 与硬件设计（p.103–105）

### §4.1 降低权限和提高权限的 TLB 后果不对称

降低权限后，旧 TLB 项若仍允许访问，可能让本应被阻止的指令成功执行，直接破坏算法正确性。多处理器系统因此需要把可能缓存旧翻译的 CPU 都纳入一致性处理，常见方式是软件 shootdown。

相反，提高权限后若某 CPU 暂时保留更严格的旧项，通常只是多出一次可以修复的 fault 或 miss，而不是非法放行。论文脚注仍要求异常路径正确处理相关条目的刷新，不能把这一论点读成“提高权限永远不需要任何 TLB 处理”。

许多应用恰好批量降低权限、逐页提高权限。因此可以把跨 CPU 通知等固定代价摊到一批页上。作者还讨论把批量化用于传统换出，但特别提醒：若页面加入待回收储备后、真正完成 shootdown 前又被引用，就必须正确处理其状态，不能直接重用。

### §4.2 最佳页大小取决于工作内容

大页可以摊薄某些分页成本，传统磁盘分页尤其受固定 I/O 延迟影响。但本论文不少 handler 的工作量大致与页大小成正比：扫描一页、复制一页或解压一页。

于是小页能降低一次前台处理的计算量，甚至减少不相关对象被一起扫描的工作。不过异常入口与改权限的固定成本不会随页大小同比下降；若它们本来就很慢，把页切小反而可能频繁触发昂贵路径。

论文建议把页大小与 Trap/保护性能一起考虑。它还讨论硬件采用较小保护粒度、磁盘传输则聚合多个连续小页的可能性。这是接口与硬件的设计空间，不是要求所有应用一律使用最小页面。

### §4.3 服务线程怎样访问客户不能访问的页面？

p.104 比较了四条路线：

| 路线 | 好处 | 代价或限制 |
|---|---|---|
| 同一地址空间双重映射 | 无需每次切进程，不必额外拷贝整个页 | 多一组页表项，虚拟缓存需处理别名一致性 |
| 系统调用复制进出受保护区域 | 不要求用户直接访问受保护别名 | 为扫描等步骤增加内存复制 |
| collector 在独立进程 | 可以用另一张页表访问共享物理页 | 每次异常可能需要重量级切换；多处理器RPC有不同权衡 |
| collector 放进内核 | 接近底层，可能高效 | 内核需理解各语言运行时布局，复杂性和可靠性代价大 |

作者倾向在物理寻址缓存架构上使用同地址空间的多重映射。论文估计额外 PTE 的空间代价可能在约1%量级，取决于页表项和页大小的比例。

虚拟寻址缓存可能把同一物理数据的两个虚拟别名缓存成不同内容；GC 的单向阶段转换可以帮助处理：扫描期间应用不能访问，扫描完成后先处理必要的缓存同步，再开放应用视图，而 collector 不再访问已发布页面。这一前提不能随意推广到两个别名永久并发读写的场景。

### §4.4 异常可恢复性不是一条口号

论文讨论了深流水线和不精确异常机器上的顾虑：发生 fault 时，后续指令可能已有部分结果，未必能假设所有指令都能简单倒回重执行。

多数应用只需要把缺少的页面或权限准备好，再恢复被阻塞的访问，不依赖改写应用寄存器；它们对机器的要求与常规磁盘分页较接近。

堆溢出检测却是例外：GC 可能要移动对象、修改根寄存器，还要把“下一可分配位置”改到新区域，再重试先前失败的指令。如果已有后续操作或寻址副作用完成，这种改写就可能不安全。原文据此强调 OS 必须针对硬件提供正确的恢复语义，不能因为能捕获异常就推断可以任意改写现场。

### §4.5 还需要哪些接口信息？

作者提到把页面暂时固定在内存或控制写回，以服务事务语义；还讨论 Mach external pager 能通知用户哪些页面即将换出。

应用可能知道某些页可重建、可压缩，或者只包含垃圾。若内核先把这些页原样写到磁盘，用户再做自己的处理，就可能重复工作。让应用参与决策的价值，来自它知道内核不知道的数据语义，而不是单纯把所有分页代码移出内核。

## §5 表2与结论：共同形态比接口名单更重要（p.105–106）

表2汇总了各算法使用的能力。读它时应连同脚注理解：Dirty 可以通过保护和异常模拟；一些算法只在淘汰冷页时需要单页保护，也可能通过批量化重构；堆边界检测只要存在可用的访问边界，未必依赖显式保护调用。

论文最终归纳的共同形态包括：

1. 经常批量降低权限、逐页提高权限。
2. 很多 fault 的有效处理全在 CPU 内完成，成本与页大小近似相关。
3. 处理 fault 后通常让出错页更容易访问。
4. 应用局部性越好，前台故障次数往往越少。
5. 服务端用户代码可能需要访问客户用户代码暂时不能访问的页。
6. 大多数这些服务不必检查或改写客户的 CPU 寄存器状态。

不是每一个算法都满足每一项；作者明确把堆溢出检测作为重要例外。不同应用利用局部性的方式也不同：GC 降低前台 fault 次数，分代与 checkpoint 利用写入集中，SVM 则依赖不同处理器的访问局部性。

因此，阅读结论不能停在“OS 加六个系统调用”。真正的要求是：接口能够表达算法需要的权限转换与服务视图；实现正确维护翻译与缓存一致性；性能适合CPU内的细粒度任务；并允许应用与内核各自利用掌握的信息。
