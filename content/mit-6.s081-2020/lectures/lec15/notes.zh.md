# 第15讲 · 把多次磁盘写变成一次恢复决定

文件系统的难题不是“磁盘会忘记已经写好的字节”，而是：**一次逻辑操作要改多个块，崩溃可能只保留其中一部分。** 日志把这个问题改写为一个更小的判断：磁盘上是否已有一个可信的提交记录？

## 1. 先定义要保护的关系

前置知识：能区分 inode、目录项、位图、数据块，以及缓存副本和磁盘副本。需要补习时先看[第14讲](#/c/mit-6.s081-2020/lec/lec14?v=notes)。

用“给文件增加一个数据块”作最小例子，设 inode 要引用块 `b`，位图要把 `b` 从空闲改成已占用。只把其中一个结构改到磁盘，会产生两种不同的错误：

| 崩溃后磁盘状态 | 后果 |
|---|---|
| 位图已占用，但没有 inode 引用 `b` | 泄漏：分配器不再使用它，文件也找不到它 |
| inode 已引用 `b`，位图仍为空闲 | 错误共享：以后可能再次分配 `b`，两个独立文件互相覆盖 |

后者通常更危险。但仅把写入顺序反过来，不能得到“整次操作全部生效或全部不生效”的保证。想要的性质是：在恢复完成后，磁盘结构重新满足分配与引用之间的不变量。

这里的“一个块只属于一个文件”说的是独立文件的内容分配；合法硬链接是多个名字指向同一个 inode，并非这种错误共享。日志也不负责恢复已经烧毁的磁盘或重建丢失的进程内存。[课堂15:00–27:00；教材§8.4]

## 2. 日志保存新值，提交头决定是否采用

xv6 使用**物理重做日志**：记录修改后的完整块，以及每个块的正常磁盘位置。恢复时不重跑“分配一个 inode”“再追加一次”这样的高层动作，而是把确定的新字节复制到确定位置。

```text
执行阶段：修改缓存 + 登记块号 + pin
                    ↓
write_log：全部新块内容写入磁盘日志
                    ↓
write_head：写非零 n 与目的块号  ← 提交点
                    ↓
install_trans：复制到各 home location
                    ↓
write_head：写 n = 0，允许日志区复用
```

这张文字图是编者归纳；课堂真实板书见[中文译稿](#/c/mit-6.s081-2020/lec/lec15?v=draft)33:00–36:00。

核心顺序可以写成：

$$
\text{全部日志数据持久化}
\prec \text{提交记录持久化}
\prec \text{任意原位置写入}
$$

最后还要满足：本事务的全部安装完成，才能持久化清零；清零完成，才能用同一个日志区写下一事务的数据。否则旧头可能指向新数据。

**内存里 `log.lh.n > 0` 不等于提交。** 它可能只是“本轮已经登记若干修改”。重启只读得到磁盘日志头，因此真正的提交点是 `write_head` 内的持久化写，而不是给字段赋值。[课堂39:00–54:00；教材§8.5–8.6]

## 3. 用一张故障表证明全有或全无

以下推理依赖课堂的简化设备模型：提交决定原子写入，已完成写确实持久化，规定的顺序得到保证，不考虑静默损坏。

| 故障时刻 | 重启读到的头 | 为什么恢复正确 |
|---|---|---|
| 修改缓存时 | `n = 0` | 内存丢失；原位置仍是旧值 |
| 写了一部分或全部日志数据，但未提交 | `n = 0` | 忽略日志；原位置仍没改 |
| 非零头已持久化，尚未安装 | `n > 0` | 全部新数据已经在日志，完整重放 |
| 安装一半 | `n > 0` | 从头重放；已安装块写同样的内容 |
| 安装完成，清零前 | `n > 0` | 再安装一次仍是正确的新状态 |
| 清零后 | `n = 0` | 忽略旧日志数据；原位置已经全部更新 |

若恰好在写头时断电，原子写假设把状态归入写前或写后；不能出现半个可信提交决定。

幂等性的形式是，固定事务的安装函数 `R` 满足：

$$R(R(D)) = R(D)$$

这里的 `D` 是磁盘状态。它成立的原因是覆盖固定位置的新值，而不是执行次数被自动记住了。还要求恢复期间没有新文件系统修改插入；否则旧重放可能覆盖更新的值。反复在恢复途中崩溃，也只是不断尝试同一个 `R`。[课堂30:00–39:00、54:00–60:00]

## 4. 三种“写”不能混为一谈

| 动作 | 改哪里 | 是否表示事务已持久化 |
|---|---|---|
| 修改 `bp->data` | RAM中的缓存内容 | 否 |
| `log_write(bp)` | RAM中的块号集合、pin引用 | 否 |
| `bwrite` | buffer对应的设备位置 | 取决于写的是日志数据、头还是原位置 |

因此，`log_write` 的打印次数既不是实际磁盘写次数，也不是不同块数。设一组操作对相同 inode 块改了5次，只要都在同一事务里，**吸收后只占一个日志槽位，提交最终内容**。

在无并发、没有其他设备写的简化计数中，若事务涉及 `k` 个不同 home blocks，则一次正常非空提交的块写数量为：

$$k + 1 + k + 1 = 2k + 2$$

分别是日志数据、非零头、安装、清零。这个式子不计算磁盘读取、缓存命中、设备内部行为，也不是吞吐性能保证。课堂 `echo hi > x` 的 `k=3` 创建事务恰好可用它解释，真实轨迹只在译稿60:00–63:00展开。

## 5. pin 不是锁，也不是“已经落盘”

对未提交的修改块，有两个不能做的动作：

1. 丢掉缓存副本：尚未写日志时，它可能是新数据的唯一副本。
2. 先写回原位置再淘汰：这绕过提交点，会把部分事务暴露给崩溃。

`bpin` 增加 buffer 的 `refcnt`，使原调用者 `brelse` 后它仍不能被回收；固定快照的 `bget` 只选择 `refcnt == 0` 的槽位。pin 保证的是**缓存对象的生存期**，buffer 的 sleep lock 负责对内容访问互斥，二者不能互相替代。

同一个块重复 `log_write` 只在第一次登记时 pin；否则吸收多次更新后仅解除一次 pin，会留下错误的引用计数。正常提交的安装路径在适当时刻 unpin。[课堂66:00–72:00；教材§8.6；`bio.c`]

> 版本提醒：参考提交 `e23d53f` 的 `install_trans(void)` 在恢复路径也会调用 `bunpin`；课堂51:00的画面已经显示 `install_trans(1)`。不能用旧快照的签名推断录课树完全相同，也不能把重启后“重新读取的buffer”说成仍持有上次运行的pin引用。旧快照的这个边界未通过运行验证，本笔记不将它包装成已验证实现。

## 6. 预留的是完成能力，不是写满以后再想办法

单个操作开始后可能已改了一些共享结构。如果半途发现日志满了，不能提交半个操作，也不能简单返回错误而放任已有修改。因此必须先保证它有机会完成。

固定参考代码的入口检查为：

```c
log.lh.n + (log.outstanding + 1) * MAXOPBLOCKS > LOGSIZE
```

满足时，新操作睡眠。记当前不同块数为 `n`，已进入且未结束的操作数为 `o`，每项保守上界为 `M`，入口使用的容量界为 `L`，放行要求是：

$$n + (o+1)M \le L$$

- `+1` 预留新操作的完整最坏需求。
- `oM` 给现有操作保留继续执行的空间；它并不精确减掉每项已经用过的配额，因此是保守估计。
- `n` 计算本轮已经登记的不同块，可能包含已结束但尚未组提交的操作留下的修改。
- 醒来后需要重新检查；被唤醒不等于条件必然满足。

课堂把日志简称为30块。实现还受物理日志大小减去头部的约束：`log_write` 检查 `log.size - 1`。`LOGSIZE=30`、`NBUF=30` 这两个相同的常量，也不是“任意并发负载绝不会耗尽buffer”的证明。课后问答实际确认了无空闲buffer会panic；不能据此宣称已有完善的资源不足处理。[课堂69:00–81:00、84:00–90:00]

大 `write` 则先在 `filewrite` 中切成小事务。固定快照按 inode、间接块、分配位图及非对齐余量计算一段的上限；不是简单地把“日志能放多少数据块”全部给用户数据。崩溃可能留下已完成的一段前缀，但每一段自己的结构更新仍要完整。

## 7. 为什么等 outstanding 归零

`log.outstanding` 数的是进入 `begin_op`、尚未执行完 `end_op` 的操作，并不是“日志有多少块”。`end_op` 把它减为零时，说明没有操作还会继续修改当前事务涉及的缓存数据，这时才适合取最终块映像并提交。

一个比“保持顺序”更具体的理解方法如下，属于编者依据源码的推导：

1. 两个并发调用修改不同 inode，但两个 inode 恰好位于同一个磁盘块。
2. buffer cache 对这个块只有一个副本，其中可能同时包含两个调用已做的部分修改。
3. 如果第一个调用结束就把整个块提交，也会把第二个尚未完成调用的一部分状态带到磁盘。
4. 若第二个调用的其他块没跟着提交，崩溃原子性就被破坏。

等待所有在途操作结束，再组提交整个块集合，是 xv6 对这个共享块问题的简单解法。提交时 `committing` 阻止新操作进入，保证取快照及安装期间没有新修改混入。

另一个层次是跨操作依赖：看到某个结果后才写“完成”标志，恢复不能只留下完成标志而丢掉结果。文本提纲用 `echo 99 > result ; echo done > status` 说明这一点。课堂78:00–81:00及片尾讲了顺序问题，但没有把上面的“共享inode块”例子完整展开；它是本笔记的源码推导，不冒充课堂问答。

组提交也意味着：某个非最后结束的调用可以先返回，而本组尚未持久化。**崩溃一致性、调用返回、应用级持久性保证不是同一个概念。** xv6这里也没有通用的运行中事务回滚接口；不能把redo恢复当成任何失败路径都能自动撤销。

## 自测：给出原因，再展开答案

<details><summary>1. 日志数据已全部写盘，内存n也大于0，为什么事务仍可能被恢复程序忽略？</summary>

磁盘日志头还可能是0。恢复只能依据持久化的提交决定，不能知道断电前RAM里的n。此时原位置尚未改变，所以忽略准备好的日志数据是安全的。

</details>

<details><summary>2. 安装完一半后重启，为什么不需要在日志里保存“已安装到第几块”？</summary>

已提交日志保存确定的新块映像及其目的块号。再覆盖一次同样的位置，结果不变。重放必须先于正常文件系统活动，且只有全部安装完成后才能清零头。

</details>

<details><summary>3. 一个事务对同一块调用了10次log_write，会写10份日志数据吗？</summary>

不会。吸收只登记一次块号，保留缓存中的最终内容，并只为首次登记增加pin引用。若事务还修改其他块，仍需分别登记它们。

</details>

<details><summary>4. n=4、o=2、M=10、L=30时，入口是否允许再加入一个操作？若不允许，为什么不能先把已有4块安装掉？</summary>

不能放行，因为4+(2+1)×10=34大于30。已有操作可能还未结束，当前4块可能只是部分修改；提前安装会违反提交顺序。等待是为了让已获准的操作先完整结束，而不是把半个事务赶到磁盘。

</details>

<details><summary>5. 用大write写入整份数据库文件，成功调用一次就说明断电后整份文件全新或全旧吗？</summary>

不说明。xv6将大write切成多段事务，每段保证自己的结构一致性，整个调用可能留下已完成部分。应用需要的整体事务语义不能从这个日志机制自动推出。

</details>

<details><summary>6. 为什么brelse之后修改块仍应留在缓存？pin可以代替buffer锁吗？</summary>

日志持有额外pin引用，防止尚未提交的新数据被回收。pin不保证互斥；buffer锁负责安全访问内容，refcnt负责可否回收，作用不同。

</details>

<details><summary>7. 先清零日志头，再安装最后一个块，只有一行之差，为什么不安全？</summary>

在这两步之间崩溃，恢复读到0就忽略日志，而原位置仍只更新了一部分。必须先安装全部块，再持久化清零。反过来，先全部安装、还没清零就崩溃，重复安装安全。

</details>

<details><summary>8. 两个并发调用修改不同文件，为什么不能仅凭“不是同一个文件”就单独提交先结束者？</summary>

不同inode可能共享一个磁盘块，位图块也常共享；缓存的整个块可能混有另一个调用尚未完成的修改。此外还可能存在可观察的操作依赖。独立提交需要额外设计，xv6通过等在途操作归零再组提交简化推理。

</details>
