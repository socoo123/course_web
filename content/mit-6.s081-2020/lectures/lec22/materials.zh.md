# Meltdown（2018）· 课程资料

## §1 论文究竟证明了什么

一个用户程序最终因权限错误而崩溃，并不足以证明它什么秘密也没有获得。Meltdown 的贡献在于展示一条完整的信息路径：**秘密短暂参与计算 → 改变微架构状态 → 普通、可提交的测量恢复秘密。** 这个过程不要求内核包含常见的缓冲区溢出或漏检查问题。

论文的威胁模型是攻击者能够在目标系统上执行任意普通用户代码，但没有物理接触机器，也没有内核权限。作者甚至假定操作系统软件没有可利用漏洞，并启用 ASLR、KASLR、SMAP、SMEP、NX、PXN 等当时常见保护。这里的“任意普通用户代码”是重要能力前提，不能直接换成“只向一台服务器发送一个网络包”。

“与操作系统无关”指漏洞根源在受影响处理器如何执行指令，而非某个 OS 特有软件错误；**实际可泄漏范围仍取决于映射、硬件型号和补丁状态**。没有当前地址空间中的相应映射，就不能从抽象意义上的“任意物理地址”凭空拿到数据。论文的广泛影响来自许多系统当时恰好把大量物理内存映射进内核区域。

作者还把它与 Spectre 区分：Meltdown 在攻击者自己的指令流中暂态使用无权限数据；Spectre 则诱使受害代码用它本来有权访问的秘密产生可观察效果，通常更依赖受害程序的具体结构。KAISER 对前一种映射前提有用，不是对两类攻击的统一修复。

**阅读边界：** 这里讨论的是课程指定历史论文与其中的实验。文中有关 Intel、AMD、ARM、Windows、Linux、Android 的陈述均按该快照理解，不据此判断 2026 年某台机器的漏洞状况。

## §2 背景图怎样把“执行”与“提交”分开

### §2.1 图1：乱序不是不遵守数据依赖

PDF 第 3 页图 1 是一个简化的 Skylake 核心。前端取出 x86 指令并解码为微操作 `µOP`，这些操作进入分配队列和执行引擎。调度器把准备好的微操作送到不同执行单元，包含算术、分支、加载、存储和地址生成单元；数据缓存与地址转换结构位于内存子系统。

图中应沿两条线阅读：

- **执行线：** 操作数到位、执行单元空闲，就可能先执行；结果还可以通过内部数据通路供其他依赖操作使用。
- **提交线：** 最终结果要满足指令顺序所规定的架构状态，处理器不能因为较晚指令先算完，就先越过较早的异常。

寄存器重命名解决的是复用寄存器名字造成的假依赖；真正需要前一条 load 结果的操作仍需等结果可用。Meltdown 也不违背这条依赖：秘密先暂时到达，后面的编码才利用它。

论文特别约定术语：这里的 speculative execution 较窄地指分支之后的推测路径，而 out-of-order execution 更广泛地指前面结果未提交时就先执行后续操作。课堂用“推测执行”统称了一些暂态行为；理解论文时，不能因此认定每个 Meltdown 序列必须包含一次分支预测错误。

### §2.2 图2：同一物理页的两个入口

PDF 第 4 页图 2 上方是物理内存，下方是用户／内核虚拟地址区域。一块物理页既可能通过某个用户映射访问，也可能通过内核 direct map 中的另一地址访问。图中不是复制出两份数据，而是**两个虚拟地址指向同一份物理内容**。

这解释了为什么“泄漏内核虚拟地址”会影响其他进程：内核为了管理物理内存，会建立到那些物理页的映射。攻击者不需要当前用户页表直接拥有受害进程原来的用户虚拟地址，只要能够利用相应内核映射，就可能观察到背后的数据。

论文对 Linux／OS X 的 direct map 和 Windows 的 pools、system cache 作了区别。后者不是把全部物理内存统一线性映射进去，因此不能把“Linux 上可扫描的物理范围”原样移植成 Windows 上的承诺。

### §2.3 侧信道与隐蔽通道的区别

普通缓存侧信道中，观察者利用别人运算无意留下的时间差来推断信息。论文将 Meltdown 的缓存传输视作一个 covert channel：攻击者同时控制暂态“发送方”和正常执行的“接收方”，刻意让秘密决定缓存状态，再把它解码出来。

发送方和接收方甚至不必是同一个线程。它们跨越的关键边界，是无法直接保留的暂态状态与可以正常使用的架构状态。论文选择 Flush+Reload，是因为它便于实现且信噪比较好，不是说只有这一种微架构通道才可能泄漏。

## §3 玩具实验：图3与图4证明了哪一步

PDF 第 5 页的 Listing 1 先触发异常，再在正常控制流绝不会到达的位置访问探测数组。图 3 将正式控制流画成转向异常处理器，而把后续提前执行的指令放进另一块阴影区域。后者没有退休，不会留下正式寄存器结果，但能够改变缓存。

图 4 则把这种改变测出来：

| 图中项目 | 正确读法 |
|---|---|
| 横轴 `Page` | 探测数组的页编号，覆盖 256 个候选值；轴刻度标到约 250 |
| 纵轴 `Access time [cycles]` | 再读取的耗时，单位是周期，不是纳秒或吞吐率 |
| 设定的数据值 | `data=84`，由紧接图的正文明确给出 |
| 主要曲线 | 大多数候选页约在 400 多周期附近 |
| 明显向下的谷值 | 页 84 附近读取更快，约落到 200 多周期；这是看图的近似值，不是原始数据表 |

探测位置的间隔是 4096 字节。在原文假设的 1 字节元素与 4 KB 页条件下，256 个值分别落到 256 页的相同偏移处。这样可以减少相邻预取造成的假阳性；访问的是每页里的特定缓存行，不是一次把整页都读进 cache。

这个实验只证明“被取消的指令仍可留下可测缓存效果”。若 `data` 本来就是合法可读的输入，它还没有独立证明可以越过用户／内核权限。完整攻击还要补上：如何让无权限秘密真的进入这段暂态依赖链。

> 编者说明：图 4 的周期数来自特定测量路径，不能把课堂口头所说的“L1 几周期”拿来要求这个图一定降到几周期。计时序列、序列化和实验设置都有额外成本。

## §4 图5：把异常控制与信息传输组合起来

PDF 第 6 页图 5 上半部分画出异常处理／抑制包围的暂态指令，它读取秘密并改变微架构状态；下半部分把这个状态转回正常程序可用的信息。这是论文的方法结构图，而不是一款 CPU 的电路图。

### §4.1 异常处理不等于“异常没有发生”

作者讨论两种处理真实异常的方法。其一，先创建子进程，让它执行会失败的访问，父进程随后观察相关缓存状态；其二，安装相应信号处理程序，避免每次都创建新进程，并在错误后继续执行测量。

这些机制不赋予正常读取内核数据的权限。它们只解决“完成一次暂态尝试后，谁来继续读出痕迹”的控制流问题。异常本身仍然按架构规则阻止非法 load 正常提交。

### §4.2 抑制异常也不等于“什么都没留下”

硬件事务内存允许一次事务失败后回到备用路径，不必把事务里的故障作为普通异常一路传给 OS。论文使用 Intel TSX 来降低恢复成本。但事务回滚保证的架构原子性，不要求把缓存状态恢复成进入事务前的每一个细节；因此发送端留下的缓存信号仍可能被接收端观察。

论文还讨论把非法访问放在错误预测的路径中：正常路径不走它，因而异常可被取消。但这里可能需要对分支预测器作专门安排，论文没有用它替代所有评测里的 TSX 方案。不能把“存在另一种构造”与“本表数据是在该构造上测的”混为一谈。

### §4.3 为什么通道不局限于 cache

作者举出执行端口占用之类的可能状态：如果暂态指令根据秘密占用某个资源，另一段代码可以通过竞争延迟观察它。本文采用缓存通道，是实现选择；更深的安全问题是暂态信息能否进入任何持久、可观察的共享状态。

## §5 完整攻击的关键条件与权衡

### §5.1 从读取到恢复：关注数据流而非照抄汇编

PDF 第 8 页 Listing 2 用 x86 汇编表达三件事：从一个用户无权限的映射加载字节，使用这个暂态值选择探测数组的一页，随后通过正常测量辨认哪一页变热。课堂已经按时间逐步推导了单比特版本，见中文译稿 48:00–58:00；这里补足论文特有的条件。

在相关 load 执行时，地址转换与权限检查可以并行推进。CPU 可能已把后续微操作放入等待队列；秘密一到内部数据通路，依赖它的操作便可能执行。只要编码访问在异常撤销效果前留下缓存痕迹，架构回滚就不能抹去接收方将来能看到的全部信息。

因此，应该说“无权限数据未被及时阻断”，而不是把内部过程武断画成“CPU 完全不查权限，直到退休才开始查”。论文并没有公开受影响芯片所有门级细节。

发送端还要快：探测数组的地址转换若已在 TLB 中，某些机器上的成功率会更高。读取目标离核心的远近、前面指令拖延退休的程度、缓存和预取行为，都会影响是否赶得上暂态窗口。

### §5.2 零值偏置与失败不能混为一谈

作者观察到恢复结果偏向零，提出两种可能解释：失败权限检查把 load 结果屏蔽为零，或者数据尚未就绪时存在相关内部行为。论文把具体内部原因保留为推断。

这会带来二义性：一次测得零，可能是真秘密为零，也可能是本轮没有得到真实秘密。论文在暂态序列中加入零值重试，并在外层通过多次尝试降低错误率。重试上限在性能与可靠性之间折中，不是“只要多读几次一定正确”。

PDF 第 10 页给出的示例也要带上上下文：i5-6200U 使用异常处理的未优化版本，读到零的平均比例为 5.25%（标准差 4.15），简单重试后为 0.67%（标准差 1.47）；i7-8700K 的对应报告为 1.78%（标准差 3.07），使用 TSX 后降到 0.008%。这组“零值偏置”观察不应直接替代后面 §6.2 的端到端字节错误率。

### §5.3 一字节一页号，还是一次只传一位

若一次传 $k$ 位，并把每个值编码为一个不同候选缓存位置，就有 $2^k$ 个候选需要辨认。传一个字节的通用方案需要 256 个候选位置；按 4096 字节跨度计，数组大小为 $256\times4096=1{,}048{,}576$ 字节，即 1 MiB。

更多位会减少发送次数，却增加接收扫描成本。论文发现通用方案几乎把时间都花在 Flush+Reload 上，因此评测采用单比特传输。进一步可只测代表一的候选：测到命中表示一，没有命中暂按零处理，配合重试降低误判。

代价是零值歧义更突出：普通数据中的一个 bit 大约有一半机会为零，而若一次编码多位，“所有位都为零”的比例可能更低。这是信号可靠性与测量开销的权衡，不是“一个 bit 信息少，所以一定慢”。

### §5.4 地址随机化会增加工作，但不是权限检查

论文分别讨论 direct map 的搜索和附录中的内核位置恢复，两者不可合并成一个随机化位数。正文的示例假设 direct map 搜索空间约 $2^{40}$ 字节，目标有至少 8 GB 物理内存，按 8 GB 跨度取候选，最坏约需 $2^{40}/2^{33}=128$ 次测试。这个计算依赖线性、连续映射等设定，不表示任意现代内核都只有 128 个可能布局。

附录 A.2 使用特定内核构建的已知字符串与符号信息，给出另一个 6 位、64 个偏移的历史配置。它与正文 40 位 direct-map 空间是不同对象、不同前提。二者都说明地址隐蔽可被额外工作削弱，不能代替数据访问边界。

## §6 评测：把“可以泄漏”与“多快、多准”分开读

### §6.1 表1与测试范围

PDF 第 11 页表 1 列出实验室、云端和手机共 12 项配置。实验室包含 Celeron G540、多代 Core i5／i7、Xeon E5-1630 v3；云端列出 Xeon E5-2676 v3 与 E5-2650 v4；手机为 Exynos 8890。云环境涉及 Amazon EC2 与 DigitalOcean。作者说明没有读取不属于其控制范围的其他租户内存。

表头 `Cores` 下，i7-8700K 写为 12，Xeon E5-1630 v3 写为 8。原页确实如此，但本表没有把物理核心与逻辑处理器计数分清，不能直接拿这一列断言芯片物理核心数量；本页因此保留型号与环境，不据它再作核数推导。

| 系统或场景 | 论文测试／讨论的边界 |
|---|---|
| Linux | 2.6.32–4.13.0 的未引入 KAISER 补丁配置；当内核与 direct map 映射在当前地址空间中，可泄漏相应范围 |
| Linux + KAISER | 测试中阻止了通常的内核／物理内存泄漏；少量必须保留的过渡映射另作限制分析 |
| Windows 10 | Meltdown 补丁推出前的更新状态；通过内核调试器核对地址与泄漏结果；受 pools、system cache 等实际映射限制 |
| Android 手机 | Galaxy S7，LineageOS 14.1、Linux 3.18.14、Exynos 8890；成功的是 Exynos M1 自定义核心，Cortex-A53 未成功 |
| 容器 | Docker、LXC、OpenVZ 共享同一内核；作者在自己控制的不同用户容器间验证了泄漏 |
| 虚拟机 | 影响取决于隔离方式与映射；论文强调半虚拟化及共享内核情形，不能推成所有全虚拟化 VM 都能互读宿主任意页 |

原文写“LineageOS Android 14.1”容易误读：14.1 是这里记录的 LineageOS 版本，不应写成后来发布的 Android 14.1。论文的实验时间也决定了不能作这种跨年代解释。

### §6.2 没在 L1、不缓存、不可缓存是三种情况

PDF 第 12 页 §6.1.6 专门验证“目标必须在攻击者 L1”是否成立。作者把两个进程固定在不同物理核：刷出目标，再只让另一个核重新读取。即使目标不在攻击者核心自己的 L1，仍能在较低速率下恢复。因此“L1 命中有利”不能改写成“L1 命中是必要条件”。

**Uncached** 是目标数据此时没有缓存副本；**uncacheable** 是页面被标记为不按正常方式缓存。这两个词并不等价。后者的实验还有额外条件：若攻击者能在同一核心触发对目标地址的合法读取，例如通过系统调用，作者观察到某些不可缓存页也能泄漏。他们怀疑与 line fill buffer 有关，但明确留下进一步研究。

论文还限定，这一观察不意味着 memory-mapped I/O 区域也可同样操作；原文在第 13 页说明该方式不适用于其所述 MMIO 区域。不能把“普通未缓存 DRAM”“设置内存类型的不可缓存页”“设备寄存器”合成一个类别。

### §6.3 吞吐与错误率：必须连条件一起引用

§6.2 使用已知内核数据，才能同时计算恢复速度与字节错误率。该节说明使用 Flush+Reload 通道和 Intel TSX 异常抑制；i7-8700K 的描述明确给出 10 次、每次 10 秒的运行。下面按原文保留 **KB/s、B/s** 写法；它没有在此澄清 KB 的十进制或二进制口径，不能擅自换成 KiB/s。

| 条件 | 读取速率 | 错误率与统计限定 |
|---|---|---|
| i7-8700K，目标靠近核心／L1 情形，TSX | 报告最高 582 KB/s；均值 552.4、标准差 10.2 KB/s | 最低 0.003%；均值 0.009%、标准差 0.014 个百分点 |
| i7-6700K，同段的近核心情形，TSX | 报告 569 KB/s；均值 515.5、标准差 5.99 KB/s | 最低 0.002%；均值 0.003%、标准差 0.001 个百分点 |
| Xeon E5-1630，较快配置 | 报告 491 KB/s；均值 466.3、标准差 16.75 KB/s | 最低 10.7%；均值 11.59%、标准差 0.62 个百分点 |
| Xeon 段落随后描述的较慢版本 | 平均 137 KB/s | 该次评测观察到错误率降为 0；不等于所有未来读取都无错误 |
| i7-6700K，目标在 L3、不在 L1，TSX | 平均 12.4 KB/s | 最低 0.02% |
| 未缓存目标，多数受测系统，未加所述优化 | 低于 10 B/s | 竞争窗口难以赶上；不是 10 KB/s |
| 未缓存目标，结合并行线程与预取相关优化 | 提高到 3.2 KB/s | 是优化后的特定结果，不是所有未缓存数据的保证 |

“最高速度”与“最低错误率”不一定来自同一轮；表中没有将两者包装成一个可同时保证的配置。尤其不能拿 582 KB/s 去描述冷内存扫描，也不能忽略 Xeon 快版本超过 10% 的错误率。

该 PDF 的导言和结论仍写 3.2–503 KB/s／最高 503 KB/s，而 §6.2 出现最高 582 KB/s。这是**同一快照内部的口径不一致**，不是本页测量得出的修正。引用性能时应定位到具体小节与条件，不能悄悄统一成一个“论文速度”。

### §6.4 未复现的机器说明什么

作者未在所测试 AMD 和若干其他 ARM 核心上复现论文的内核读取攻击；Exynos M1 则成功。对于 Cortex-A75，论文引用当时厂商报告，说明未持有设备做本文测试，因此它不应被算入作者亲自验证的成功清单。

PDF 第 13 页存在一句 AMD 描述的双重否定笔误。结合前后明确的“未能在 AMD 上复现”和“实现差异可能阻断数据”讨论，应理解为转述 AMD 当时声明其处理器不受这项 Meltdown 影响，而不是反向读成所有 AMD 都受影响。

还要区分两种实验：无权限内核读取失败，不代表所有乱序执行的缓存副作用都消失。作者说明第 3 节玩具实验在这些平台上仍可工作。这再次证明“有暂态痕迹”与“能读取受保护秘密”需要分开验证。

## §7 防御：撤映射、阻传播，以及残余边界

### §7.1 软件防御解决哪个前提

KAISER 原本为妨碍针对 KASLR 的侧信道而提出：用户态页表尽量不保留内核映射。它意外地也破坏了 Meltdown 的关键前提。没有到秘密页的转换，处理器就不能沿同一条虚拟地址访问路径暂态取得秘密。

第 14 页还讨论残余映射：x86 的进入／退出机制需要用户页表保留少量过渡代码或数据。这些区域即使不放密码，也可能含指针；若泄漏指针指向随机化内核位置，仍会削弱 KASLR。作者提出更严格安排 trampoline 与其随机化偏移，避免把整个内核的偏移暴露出来，但把具体性能／安全权衡留给后续工作。

因此，“KAISER 阻止了实验中的广泛内核泄漏”与“任何保留页都绝对安全”不是同一命题。软件修复是缩小可寻址范围，并不是把受影响硬件本身改成没有暂态泄漏能力。

### §7.2 论文的方案与已经部署的机制

论文列出 Linux KAISER 后续改名 KPTI，并提到 PCID 等优化；Windows 采用 KVA Shadow；Apple 使用 Double Map。各实现目标和细节不完全相同，例如论文指出 KVA Shadow 并不同时提供其讨论的 KASLR 侧信道保护。

文中还指出，旧 macOS `-no-shared-cr3` 选项在内核态取消用户映射，方向与“用户态取消内核映射”不同，所以它本身不能按同一逻辑阻断 Meltdown。防御不是只看“有没有两张页表”这个标签，必须追问**不可信代码运行时能翻译哪些地址**。

### §7.3 硬件方案不要混成一条已验证结论

作者认为完全关闭乱序执行代价太大；把每次读取彻底串行化为“权限全部查完后再取数据”也可能延迟正常路径。论文另提出可选的用户／内核地址空间硬划分，由地址位快速识别边界，预期能减少开销。这个 hard-split 是设计建议，不是本文已经实现并实测的防御芯片。

课堂后来讨论“不给无权限暂态操作提供真实数据”，属于理解修复目标的另一种抽象说法。无论具体如何实现，重要的是在秘密影响可观察微架构状态以前阻止传播，同时保留正确的异常语义。

## §8 附录：能恢复部分字节与能定位目标不是一回事

附录 A.1 在 PDF 第 17–18 页说明两份转储：Ubuntu 16.10、Linux 4.8.0、i7-6700K 上的 HTTP 数据，以及同机 Firefox 56 密码管理器相关内容。第 18 页 Listing 3／4 的右侧是可读字符，左侧是恢复的字节；`XX` 表示本轮通道没有给出结果。它不是零字节，也不是原始数据的掩码格式。

这些转储展示了部分敏感信息足以产生实际影响，也暴露了读取不连续、需要重试的局限。单凭几段可读文字，不能推导整块内存已被无误转储。

附录 A.2 讨论从已知内核构建定位特定进程的端到端示范：先恢复必要的布局信息，再利用内核进程结构找到目标，最后借助其页表解释目标虚拟页。它把“读某个地址的原语”与“找到有价值的数据”之间的空隙补起来，但依赖具体内核二进制／符号和结构布局。本文只解释这条论证链，没有复现或执行相关程序。

研究人员在受控条件下证明了可用性，不等于论文记录了真实恶意攻击事件；课堂的泛化猜测也不能代替事件证据。

## §9 读完后应怎样评估一个结论

论文最终改变的是观察模型：以前认为回滚后“结果没有变化”就够了，现在还要问被回滚的计算是否改变了时间、缓存、共享执行资源等后续可测状态。只在软件里避免分支、避免数组越界，并不能自动修复底层把无权限数据送进暂态路径的问题。

阅读这种论文时，至少分清四层证据：

1. **机制证据：** 图 3／4 说明被取消执行能够留下痕迹。
2. **越权证据：** 完整攻击恢复了受权限保护的已知数据。
3. **实用性证据：** 在明确硬件、缓存位置、恢复方式下测了吞吐与错误率。
4. **外推边界：** 某个配置成功，不能保证所有处理器、所有虚拟化方式、所有缓存状态都一样。
