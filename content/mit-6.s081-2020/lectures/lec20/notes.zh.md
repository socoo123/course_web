# 第 20 讲 · 语言安全之外，内核还要证明什么

本讲最重要的变化不是“把 C 语法换成 Go”，而是重新划分责任：**对象何时可回收由 GC 判断；系统何时有足够资源接收新工作，仍由内核判断。** 学完后，应能解释为什么内存安全、资源安全与性能可接受是三件不同的事。

## 1. 一张问题表，而不是语言排行榜

| 想回答的问题 | 应寻找的证据 | 不足以回答它的材料 |
|---|---|---|
| 能否操作硬件、进入内核、处理中断 | shim、汇编、unsafe 边界，页表与中断设计 | “Go 编译成机器码”这一句话 |
| 能否降低开发负担 | 具体生命周期例子、错误类别、复用的运行时设施 | 静态代码行数较少 |
| 纯语言执行代价多少 | 功能尽量一致的路径与热点指令对齐 | 未对齐功能的 Linux 总吞吐量 |
| 完整系统是否够快 | 接近目标环境的吞吐、尾延迟、内存与多核结果 | 只有平均值，或只有两个微基准 |

课堂研究动机见[中文译稿](#/c/mit-6.s081-2020/lec/lec20?v=draft) 00:00–21:00；实验条件与数字见[课程资料](#/c/mit-6.s081-2020/lec/lec20?v=materials) §4。不要让“内核也能用高级语言”这个正确结论，替代更细的工程判断。

## 2. 推导入口预留：先看依赖，再看可用字节

### 2.1 为什么有 GC 仍会 OOM

GC 能回收不可达对象；如果用户程序仍持有大量打开文件和映射，内核记录仍然可达。它们不是垃圾。因而下面两句话可以同时成立：

- 每一个对象的释放时机都正确，没有 use-after-free。
- 当前负载仍要求超过机器容量的活跃内存。

这也解释了为什么 GC 不能直接替代内核的准入与资源回收策略。

### 2.2 从“在哪里等”推出设计

假设 A 持锁 L 后分配失败，决定等待；能释放相关资源的 B 又必须取得 L。依赖是：

`A 等空闲内存 → B 要运行到释放 → B 等 L → L 被 A 持有`。

问题不是缺了更多锁，而是等待位置不对。若把等待移到尚未持锁、尚未修改状态的系统调用入口，就消除了这个特定环。入口检查不是性能装饰，而是改变了内部代码可以依赖的契约。

预留的目标为最大**同时存活**量 $s$，而非累计分配量。例如一个请求顺序执行十个阶段，每阶段最多产生一块 4 kB 临时对象，且进入下一阶段前旧对象已不可达，那么这部分峰值可能只有 4 kB，而累计分配是 40 kB。若阶段把对象存入全局表，旧对象仍然活着，这个推理便失效。这个小例子是编者推导，实际 MAXLIVE 还要分析逃逸、循环与并发。

完整计数 $g,c,n$、跨 GC 预留和 deep reservation 例外只在课程资料 §2 展开。尤其要记住：物理页分配不在这个 Go 堆契约里；GC 工作栈与碎片在原型中仍有未完成的边界处理。

## 3. GC 为什么特别适合共享对象，却不能替你加同步

把共享数据结构拆成两种正确性：

1. **内容正确性：**读者能否看到完整、合法、一致的数据？需要锁、原子操作、发布顺序等。
2. **生命期正确性：**读者尚持有指针时，内存会不会被回收或重用？GC 可以承担这部分工作。

从链表摘下节点只证明“新读者不会再从这个入口找到它”，没有证明“旧读者已经停止使用”。课堂 `get/pop` 图和原子更新过程见译稿 57:00–63:00。GC 能延后回收旧读者持有的对象，但不会自动让节点内部的并发修改免于数据竞争。

还要区分**释放内存**和**释放资源**：关闭 TCP 连接、提交日志、解除文件引用等有协议语义，不等于 GC 回收几块字节。论文仍对某些清理动作使用引用计数，详见课程资料 §3.3。

## 4. 从成本模型读懂“多给内存可以更快”

令存活对象扫描工作为 $W$，可用于下一轮分配的余量为 $F$，单位时间分配速率为 $A$。一个粗略直觉是：

$$\text{收集频率}\approx A/F,\qquad
\text{GC 工作速率}\propto W\cdot A/F.$$

这不是 Go 的精确调度公式，只用于解释实验：同样存活数据与分配速率，增加余量可以减少收集频率；同样总堆大小，存活数据增加会让每轮更贵、可用余量更少，形成双重压力。

论文图 8 的比值是 Live/Total，课堂表格用 Live/Free。设存活 640 MB、余量 1280 MB，总堆是 1920 MB：两者分别为 1/3 与 1/2。写“需要三倍内存”时，应说清楚是**总内核堆为存活堆的三倍**，不是把整台机器或所有用户数据乘三。

平均 GC CPU 占比低，也不能推出尾延迟小。一次请求可能触发多次分配，每次分配承担一点 GC 工作，最后累积到请求级延迟。分配级、系统调用级、请求级最大值分别统计，详见课程资料 §4.4。

## 5. 五个容易读错的结论

- **“内核性能只差约一成，所以 Go 的语言税就是一成。”** 完整系统还有功能与优化差异；更直接的语言比较是两条受控路径，而它们又不包含 GC。
- **“去掉 GC 就等于没有高级语言成本。”** 稳态不分配的 ping-pong 仍有序言、安全检查、写屏障开关检查等指令。
- **“40 个漏洞会避免，所以 Go 内核没有漏洞。”** 研究另有逻辑错误、无法分类项；unsafe、运行时以及访问控制设计仍需正确。
- **“入口预留让所有请求最终成功。”** 只改变特定内核堆资源不足时的处理；请求可以长时间等待，也有其他错误与物理页分配失败。
- **“用 C 教课，说明 C 总是工程上的最佳选择。”** xv6 要暴露线程、内存等底层实现；工程项目可能恰好希望复用 runtime 隐藏这些细节。

## 6. 自测：用反例检验理解

<details><summary>1. 系统调用累计分配 100 MB，最多只有 1 MB 同时可达，可以只预留 1 MB 吗？</summary>

在相关分配都被正确分析、GC 能及时回收死对象且底层分配条件成立时，峰值原则支持这么做。还要排查对象逃逸、容量扩张、并发工作、尺寸碎片，以及未受预留覆盖的物理页。累计量本身不是预留依据。见课程资料 §2。

</details>

<details><summary>2. 系统调用返回时，把全部预留当作空闲即可吗？</summary>

不行。它可能创建了仍然打开的文件对象等长期状态。论文用 c 保守承接已结束调用的占用；GC 更新精确可知的存活基线。解除“承诺额度”不等于对象已消失。

</details>

<details><summary>3. 写者持锁移除节点后立即释放，为什么读者仍可能 use-after-free？</summary>

读者不拿这把锁，可能在摘除前刚拿到旧指针。锁保护写者之间的更新，不证明旧读者结束。GC／RCU 负责的延迟回收必须另行成立。

</details>

<details><summary>4. 实验测得最大请求 GC 延迟 582 微秒，可以承诺任意请求都不超过它吗？</summary>

不可以。这是给定硬件、版本、对象规模、负载与运行时长内的观测最大值，不是硬实时上界。不同的对象图、堆余量和分配量都可能改变尾部。

</details>

<details><summary>5. 编译器已把 Go runtime 编成机器码，为什么启动时仍要 shim？</summary>

编译不会消除 GC 堆、执行上下文等运行资源需求。普通 runtime 向下层 OS 请求这些资源；裸机环境要由 shim 建立它们。与 xv6 进入 C 前先准备栈是同类依赖问题。见译稿 87:00–93:00。

</details>

<details><summary>6. 某实验 SSD 版 Biscuit 比 Linux 略快，能证明 Go 比 C 更快吗？</summary>

不能。该行主要受 SSD 限制，两者功能和路径也未严格一致。瓶颈不在语言执行速度时，微小吞吐差不能承担语言归因。

</details>
