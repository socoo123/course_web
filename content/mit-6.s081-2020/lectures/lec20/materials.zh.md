# 第 20 讲 · Biscuit 论文与课外补充

## 1. 读这篇论文应拆开的四个问题

“高级语言能否写内核”其实包含四个不同问题：能否表达硬件操作，是否降低开发难度，语言本身增加多少开销，以及最后造出的系统是否具有实用性能。一个问题的答案，不能代替另一个问题的证据。

论文使用 Go 1.10 构建 x86-64 单体 POSIX 风格内核，尽量保留传统 Unix 组织。这与许多利用类型安全探索新架构的研究不同：它希望减少架构变量，聚焦语言选择。已有的 Pilot、Lisp machine、SPIN、Singularity、J-kernel、KaffeOS 等说明高级语言内核早已可行，却不直接给出同功能 C／Go 的成本差。用户程序的 GC 研究也不能直接推出内核结果，因为对象、并发与资源耗尽条件不同。〔论文 §1–3，p.89–91〕

课堂已经详细讲过 C 的控制力、内存安全和开发收益，见[中文译稿](#/c/mit-6.s081-2020/lec/lec20?v=draft) 03:00–21:00、51:00–63:00。这里补充论文的精确机制、实验口径与限制，尤其关注“入口预留为何成立”与“漂亮数字的适用条件”。

### 1.1 系统边界：内核用 Go，不等于应用必须用 Go

论文图 1（p.92，PDF 第 5 页）的层次从上往下是用户进程、Biscuit、Go runtime、shim。用户／内核隔离仍使用硬件页权限；用户程序可以用任意语言，评测程序主要是 C／C++。每个用户线程有对应的内核 goroutine，承接系统调用、用户缺页与异常处理。

支持的功能包括 COW fork、按需清零、懒文件映射与 `mmap`，用户线程与 futex、日志文件系统、TCP/IP 和 POSIX sockets。目录查找先走读无锁缓存，失配再按路径逐个锁目录；日志批量提交，数据写可绕过日志。磁盘驱动使用 DMA、命令合并、NCQ 与 MSI，网卡驱动也用 DMA／MSI。这些设计是取得高性能的工程条件，而不是选择语言后自动获得的东西。〔§4〕

论文也明确列出缺失：没有进程优先级，未面向大规模多核与 NUMA 优化，没有交换到磁盘、页面回收所需的反向映射，也没有完整的多用户、ACL、地址随机化等安全功能。不能把类型安全替代成这些功能已经齐备。图 4（p.97）列有 58 个系统调用，但不是完整 Linux ABI。

## 2. 入口预留的精确含义

课堂 33:00–48:00 讲解了分配器等待可能造成死锁，以及把等待前移到系统调用入口的动机。论文 §6 进一步给出：**预留的是一个调用引入的最大同时存活堆数据量，不是该调用累计分配的字节数。**〔p.93–95〕

### 2.1 两套分配器，两个失败契约

Biscuit 的 Go 堆用于文件、进程、TCP 状态、映射描述等对象；物理页面由另外的页面分配器管理。进程内存页、文件缓存页、socket／pipe 缓冲页和页表页不从 GC 堆分配。页面可以有多个引用，使用引用计数跟踪。

因此，“堆预留后分配不失败”只适用于相关的 Go 堆分配。**物理页面分配仍会失败，内核仍必须检查并恢复，通常向用户返回系统调用错误。** 普通 I/O、权限或参数错误也不会因预留而消失。把这个方案理解成“Biscuit 的所有系统调用永不失败”，会直接误读论文保证范围。

### 2.2 图 2：怎样保守估计尚可承诺的容量

固定给 Go 堆的 RAM 为 $M$，新调用的需求上界为 $s$。收集器并不在任意时刻都知道精确的存活量，因此系统维护三个保守计数：

| 记号 | 含义 | 为什么需要 |
|---|---|---|
| $g$ | 上一次 GC 测得的存活字节数 | 已有长期对象的基线 |
| $c$ | 自该次 GC 后，已结束调用留下的保守占用记账 | 防止把已完成请求的长期对象误当空闲 |
| $n$ | 正在执行的调用所持预留总额 | 防止多个并发调用承诺同一份空间 |

令 $L=g+c+n$。原图的准入条件是严格不等式：

$$L+s<M.$$

满足时把 $s$ 加入 $n$；否则唤醒 killer thread，在安全入口等待。调用结束，若累计实际分配为 $a$，从 $n$ 扣掉 $s$，并向 $c$ 加入 $\min(a,s)$。即使 $a>s$，静态分析已保证这些分配不可能全部同时存活，所以保留 $s$ 的占用上界足够。这里并没有声称返回时全部对象立即被释放。

GC 更新已知存活量并清零 $c$，但**保留 $n$**，因为一个尚未结束的系统调用可能跨越本次 GC，之后仍会分配。若把它的预留也清掉，就会对后来的请求重复承诺容量。实际实现还要正确同步计数；图 2 是解释算法的伪代码，不是可直接复制的无锁实现。

当堆很空时，真实分配很可能先耗掉 free list，触发普通 GC；当长期对象逐渐填满堆时，也可能先触发准入不足。后者先执行 GC，再决定是否需要终止进程，避免把可回收垃圾误当不可释放的存活对象。〔§6.2，图 2，p.94／PDF 7〕

### 2.3 MAXLIVE：不是给任意程序自动算精确峰值

工具分析 Biscuit 与所用 Go 包，利用 SSA、调用图、指针和逃逸分析确定每处可能分配，以及哪些分配在某个调用返回后必然不再存活。课堂的 `h` 向 `g` 返回对象例子见译稿 45:00–48:00。

论文还处理语言隐式分配：

- 创建 goroutine 被计为一个可能逃逸的最大内核栈分配；新 goroutine 开始工作时另行预留。
- `defer` 的内部状态也要计入，即使 SSA 不把它表示成普通对象。
- map／slice 插入可能扩容，不能只看新增元素。作者补了 **70 个容量注解**。
- 自动无法得到有效边界的循环，补了 **78 个循环上界注解**。部分递归改成更易分析的写法，所用 `time`、`fmt` 包也各有必要调整。

还有约 20 个循环，最坏上界难表达或过大，例如 `poll` 处理唤醒竞争、遍历目录块、逐页处理用户写缓冲区。它们采用 **deep reservation**：每轮只尝试预留这一轮的需求。若失败，退出到调用开头的安全等待位置，之后重试，而不是持锁无限等待。`exec` 与 `rename` 的两个循环仍需要撤销部分更新；所以论文并未声称彻底没有失败恢复代码。〔§6.3.1–6.3.2〕

### 2.4 为什么关闭很多 fd 不必预留很多倍 close 的峰值

`exit`、`fork` 或 `exec` 的清理路径可能多次 `close`。最后一次关闭已删除文件，会触发文件系统更新，甚至临时创建缓存对象。若每次关闭都留下不可回收对象，需求上界会随 fd 数累积。

作者借 MAXLIVE 找出 `close` 返回后仍可能活着的分配，再手工保证它们已不可达，或者只是可在内存紧张时驱逐的缓存。于是后一次关闭能够重复利用前一次的工作空间，预留一个 `close` 的峰值便足以覆盖这部分清理。论文报告除 `rename`（1 MB）、`fork`（641 kB）外，其余系统调用堆上界小于 500 kB。`close` 是唯一需要配合工具进行这种手工生命周期分析的系统调用。〔p.95；FAQ 对此另有澄清〕

后台线程也要预留。特别是进程退出依赖的文件系统日志线程，必须始终持有自己的预留，否则“杀掉占内存进程以释放内存”的步骤可能自己缺少资源。其他如 ICMP 工作线程，可以在工作前申请，空闲时释放额度。

### 2.5 killer thread 与两个尚未解决的边界

killer 的顺序是：先 GC；若不足，要求缓存尽量驱逐并再次 GC；仍不足，再按映射区域、fd、线程等对象数量选一个资源占用较多的进程终止，随后重新收集，够用时唤醒等待者。

这个选择是启发式，不是识别“坏程序”的可靠算法。没有明显资源滥用者时，可能终止重要进程，也可能让请求等很久。POSIX 缺少一种通用、优雅的资源撤回接口，因此入口预留解决的是内核中的一部分失败与死锁复杂性，不是所有 OOM 场景下的用户体验。

论文 §6.4 特别承认两个实现缺口：

1. **GC 自己也可能需要分配。** 标记工作栈可能增长；作者提出可退回扫描标记位图的办法，但没有实现。实验中工作栈最多占堆 RAM 的 0.8%，可以低成本预留，却不等于极端情况已被形式化消除。
2. **碎片。** 非移动收集器不压缩内存；总空闲足够，某个对象尺寸仍可能无处安放。应按尺寸类别分别计算预留上界，但当时实现还没有做。

因此必须把“算法在假设下保证分配”与“原型已处理一切底层分配边界”区分开。

## 3. GC 与实现：课堂框架之外的细节

### 3.1 Go 1.10 收集器到底做什么

该版本使用并发、并行、非移动的标记清扫。平常从已有 free list 分配；空闲空间降到阈值后开始追踪可达对象，分配调用承担一部分标记工作。并发阶段用编译器写屏障处理引用更新；开始与结束各有一次短暂的全局协调暂停，之后清扫重建空闲表，工作仍与内核执行交错。它不是复制式收集，不会移动对象来消除碎片。〔§5，p.93〕

默认启动时给 Go 堆分配总 RAM 的 1/32，并关闭普通 Go runtime 按需扩大堆的机制。在主要实验的 16 GB 机器上就是 512 MB。固定堆是论文方案与测量的条件，不能假设它与今天 Go 程序的默认堆策略相同。

降低收集延迟时，作者还改了 runtime：关闭专门的 GC worker，避免它们抢占应用 CPU；让根标记也产生 allocation credit，避免某个倒霉线程独自承担大量根扫描；把大对象标记分块从 128 kB 缩到 10 kB。这些调节应计入解释结果的背景。〔§7，p.96〕

### 3.2 Go 没有让可信底层消失

图 3 的精确计数为内核 Go 27,583 行；内核汇编 546 行，加 runtime 修改中的约 1,000 行汇编，共 1,546 行。MAXLIVE 另有 1,299 行 Go；runtime 修改另有 3,200 行 Go。还依赖约 50,000 行既有 Go runtime 与 32,000 行标准包代码，不能把“28k 内核”误读成整个可信代码只有 28k。〔p.96／PDF 9〕

内核有 90 处 `unsafe` 使用，不含 runtime 内部：操作设备寄存器与 DMA 描述符、解析网络包、转换物理地址和指针、访问用户内存。`atomic` 用于约束访问顺序，但论文指出某些读无锁代码的可移植性仍不明确。

为了预留记账，runtime 记录每条 goroutine 的分配字节数；为了设备处理，检查待运行设备 goroutine；默认栈从 2 kB 提到 8 kB，减少常见系统调用扩栈。内核 goroutine 的抢占仍依赖 Go 检查，而从用户态来的时钟中断可以强制切走用户线程。继承 runtime 调度也意味着没有自己的完整优先级策略。

### 3.3 GC 回收内存，不替代协议清理

图 5 按每千行代码统计特性使用，比较 Golang（1,140,318 行）、Moby（1,004,300 行）与 Biscuit。它是静态计数，不是动态分配次数；图中的数据类型项按变量、参数或字段声明统计。正文记有 302 处堆对象分配语句，复合对象可含多个内部对象。〔§8.1，p.97〕

`poll` 的辅助对象由等待线程与输入处理线程共同引用，GC 能简化谁最后释放的协调。但 TCP 连接关闭必须执行协议动作，不能只等对象不可达。作者没有用 finalizer 统一解决，因为带 finalizer 的循环对象存在限制；需要清理动作的对象仍使用引用计数。也避免在热点路径反复创建大量 goroutine，因为其数量会影响 GC 暂停。

代码分成 31 个 Go 包，还允许把文件系统等组件放到用户态测试竞争与崩溃安全，并复用它来制作启动盘。这是模块化带来的开发收益；本文没有重新执行这些作者测试。

## 4. 评测数据该怎样读

### 4.1 统一实验条件与三个负载

除特别说明，硬件为四核 Xeon X3460、2.8 GHz、16 GB RAM，关闭超线程；Go 1.10；每次运行一分钟，非最大值统计取三次平均，重复运行变化小于 3%。内存文件系统沿用文件系统逻辑，但不向内存日志追加磁盘块，也不调用磁盘驱动，意在突出 CPU 而不是存储等待。磁盘实验使用 Samsung 850 SSD。〔§8.3，p.98〕

网络用专用 10 Gb 交换机连接客户端与服务器，没有其他流量，Intel X540 网卡，中断合并周期 **128 微秒**，客户端运行 Linux。

| 负载 | 精确设置 | 主要压力 |
|---|---|---|
| CMailbench | 四个服务器和四个本机客户端；每条 1660 字节消息由客户端 fork/exec helper，经 Unix-domain socket 交给服务端，再 fork/exec 投递程序写入文件 | 每消息两次 fork、exec、rename，另含多种文件调用；虚拟内存与文件系统 |
| NGINX 1.11.5 | 四个进程监听同一 socket；关闭请求日志；客户端保持 64 个在途请求，每请求新建 TCP 连接；读取同一 612 字节文件并发回数据与头部 | 短连接、TCP、poll、文件读取 |
| Redis 3.0.5 | 四个单线程服务器；每服务器两份 redis-benchmark，各开 100 连接，每连接一个未完成 GET；随机取 10,000 个键之一，值长 2 字节 | 高频网络 GET 与 socket 路径 |

**兼容性细节：**论文概述强调能跑现有应用，但 §8.3 明说 Redis 从 `select` 改成 `poll`，因为 Biscuit 不支持前者。因此不能笼统宣称所有评测应用完全零源码修改。

人为往 vnode cache 填入两百万或四百万个对象，固定大量存活数据，再运行 CMailbench 改变堆 RAM。图 8 的 `Headroom ratio` 实际定义为 **Live / Total**；课堂 slides 将其中三行改列为 **Live / Free**。两表数值能互相换算，但不能照抄比值而混用分母。

### 4.4 延迟不是单一的“GC pause”

论文 §8.5 区分三个聚合层次，最大值不能互换：

| 观察对象 | 被 GC 延迟的比例 | 被延迟对象的平均 GC 延迟 | 观测最大值 |
|---|---:|---:|---:|
| 堆分配调用 | 0.7% | 0.9 微秒 | 115 微秒 |
| 系统调用 | 2% | 1.5 微秒 | 574 微秒 |
| NGINX 请求 | 22% | 1.8 微秒 | 582 微秒 |

最慢的系统调用是一次 `poll`，里面 25 次分配执行了收集工作。NGINX 平均请求处理时间为 45 微秒；不到 0.3% 请求累计 GC 时间超过 100 微秒。摘要把最大请求累计延迟约写成 600 微秒，而正文是 582；二者不是两轮不同实验。115 微秒也不是对所有 stop-the-world 暂停的统一定义，它是一次分配遇到的收集工作延迟。以上都是有限实验中的观测最大值，不是实时系统的硬上界。

| CMailbench，内存 | 15,862 | 17,034 | 1.07 |
| CMailbench，SSD | 254 | 252 | 0.99 |
| NGINX | 88,592 | 94,492 | 1.07 |
| Redis | 711,792 | 775,317 | 1.09 |

SSD 一行受存储限制，不能用“Biscuit 略快”证明 Go 执行效率更高；其余测试满核，Linux 与 Biscuit 的内核时间比例相差不超过两个百分点。论文把应用差距概括为 Linux 最多快约 10%。它是系统整体结果，包含设计、功能、优化程度的差异，不能当作纯语言税。

### 4.6 两条受控路径：更强的归因，更窄的范围

为对齐路径，作者比完整系统比较做了更多改动：关闭若干调度统计、cgroup、trace、probe、paravirtualization 等功能，去掉管道时间戳／通知，并用更简单的调度器和页面分配器替换 Linux 对应路径。稳态没有堆分配，因此这两项**不测 GC 成本**。〔§8.7〕

- **Pipe ping-pong：**两个进程绑定同一 CPU，以一对管道交换 5 字节，强制上下文切换。Go／C 吞吐量为 465,811／536,193 次往返每秒；C 约快 15%。代码路径 1,200／1,786 行，每轮动态执行 5,259／4,540 条指令。额外指令主要来自序言、写屏障检查、边界及空指针／类型检查。这里写屏障检查仍可存在，即使收集器不执行实际收集。
- **缺页：**反复 `mmap` 4 MB、按 4096 字节页逐页写一个字节，再取消映射。两边懒分配，首次写触发分配、清零与页表更新。Go／C 平均 731／695 纳秒每缺页，C 约快 5%；路径约 480／650 行，主要成本来自异常入口、页面清零和返回用户态。

作者还人工核对热点指令，确认两边主要在做同样工作。优点是减少功能差异这个干扰变量；代价是只涵盖很窄的工作，不能从两条路径推出所有内核程序的统一比例。

### 4.7 图 10 与图 11：课堂未展开的两项验证

**堆耗尽实验（§8.9，图 10，p.101／PDF 14）：**512 MB 堆，一边是反复 fork 子进程、建立大量不连续映射的资源滥用程序，一边是间歇投递邮件的正常进程。正常进程若遇到意外系统调用错误就报告并退出。实验持续 25 分钟，图只画最初 35 秒。

图横轴是时间（秒），纵轴是 GC 后存活堆数据（MB）；红叉记录每次 GC 结果，蓝横线为 512 MB 容量，四条黑竖线标记终止滥用子进程的时刻。存活量能到约 500 MB，即 97%，然后随清理下降。未到 512 MB 的主要原因之一是日志线程保留了 6 MB，实际用得更少。杀进程后释放大量映射描述还需要几秒；正常进程等待预留数十万次，但没有系统调用因这项堆压力返回错误。这验证了特定负载中的进展和预留不过度保守，**没有证明等待延迟很小，也没有证明 killer 永远选对进程**。

**目录缓存读无锁实验（§8.10，图 11，p.102／PDF 15）：**两版都用分桶哈希表与单链表，写者锁桶并发布新节点。区别仅在查找：一版直接读，另一版先取读锁。内存文件系统下 CMailbench 分别达到 15,862 与 14,259 消息／秒，读无锁版约高 11%。所以 GC 的开销并没有抵消避免读锁争用的收益。论文脚注仍提示使用 Go `atomic` 防重排的可移植性不明确；GC 只解决节点生命期，不自动证明发布顺序正确。

## 5. FAQ：补充问题与避免重复的阅读索引

以下保留 FAQ 的实质问题，但课堂已经展开的内容直接定位，不再复述整段。原 FAQ 某处提到 “buddy lab”，是该来源的历史措辞；本课程 2020 实验目录没有因此新增该任务。

### 5.1 课堂之外值得单独补足的问答

**什么是 futex？** 它允许用户态锁在无争用路径直接操作用户内存，在需要阻塞或唤醒时才进入内核，避免每次获取／释放都必须系统调用。FAQ 指向 Linux `man 2 futex` 继续了解，不要求本讲实现它。

**可否用纯引用计数而非追踪 GC？** 在避免或处理环的条件下是一种选择，Biscuit 的结构里仍有一两个环。即使没有环，多核线程竞争同一个引用计数也可能让缓存行反复迁移，显著降低性能。换回引用计数不是免费去掉 GC 税，而是更换成本与约束。

**NUMA 为什么重要？** 多插槽系统中，各内存区域到不同 CPU 的访问距离不同。把内存放在更接近使用者的位置通常有利。Biscuit 没有成熟内核相应的 NUMA 策略；少核单机结果不能据此外推到大型服务器。

**Java 是否能得到同样结果？** 也有成熟 GC 与类型安全，可能具有相近收益，但 Go 把更多变量留在栈上，Java 的分配形态可能不同。论文没有做 Java 版对照，不能把可能性写成实测结论。

**C 内核不是也有检查工具吗？** 有注解、sanitizer 等手段，能够发现或减少某些问题，但不能据此认为错误已经消失。将庞大的 Linux 全部重写代价极高，作者也不建议仅凭这项研究就启动重写。

**继承 Go 调度策略会不会造成网络 receive livelock？** FAQ 说明 Biscuit 可在网络中断与轮询之间动态切换，避免相应活锁问题；同时继承 runtime 也意味着简单的调度策略，不等于获得完整通用 OS 调度功能。活锁背景可接着读第 21 讲。

**Go 没有显式 fence 时怎么办？** 使用 `atomic` 包带来的顺序约束；不过论文对某些写法的跨平台可移植性仍保留疑问，不能把 FAQ 的简短回答理解为任意普通读写都安全。

**类型转换是不是主要性能损失？** 不是。Biscuit 用接口不多，转换开销不是最大的已识别 HLL tax；当时更明显的是函数入口栈增长／GC 协调检查。

**开发用了多久、多少人？** 没有精确统计，因为中途尝试过不同路线。主要作者 Cody 在博士期间花了几年完成大部分工作；不能把 slides 所写“约三天专家工作”误作整个内核开发周期，那是应用分析工具及注解的投入。

**课程实验有哪些功能在 Biscuit 中不可能做？** FAQ 回答没有：Biscuit 从 xv6 演化后大幅扩展，许多实验机制都有更完善版本。这不是对当前实验答案的替代。网络实验只保留入口：[Lab net](#/c/mit-6.s081-2020/lab/net?v=zh)。

## 6. 论文结论怎样用于新项目

作者讨论的是新内核或相近系统项目的选择。已有大型 C 内核积累了开发者经验、生态与流程，转换语言的成本可能超过收益。新项目则可按约束选择：如果最在意避免典型内存安全漏洞、快速尝试设计，Go 的高层设施有吸引力；若 CPU 或内存效率不能让步，当时实验更支持 C。Rust 可能兼顾安全与无 GC，但多线程共享的表达也有自己的约束，这篇论文没有实测裁决。〔§9–10，p.102〕

未来工作包括动态调整堆、允许内核控制调度、扩大多核规模，以及把预留思想用于 C 内核。值得记住的是：**安全语言并没有阻碍常见内核优化，但运行时与内存余量确实有成本；一个优秀平均值也不消除尾延迟和资源耗尽边界。**
