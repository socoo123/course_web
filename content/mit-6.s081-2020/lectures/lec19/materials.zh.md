# 第 19 讲 · Dune 论文精读

## §1 问题定位：应用想要的是硬件机制，不一定是一整台机器

给垃圾收集器一个高效的页表接口，与给应用一台完整虚拟机，是两件不同的事。前者希望调整自己的映射、收到自己的异常，仍然继承父进程文件描述符、使用原有文件系统和 IPC；后者还要承担启动内核、驱动设备、网络栈和进程环境等成本。

Dune 的切入点是把这两种需求拆开。传统应用想用内核专属硬件功能，往往需要修改内核；多个应用的修改未必能组合，还可能影响整机稳定性。若为每个应用做一个定制 guest OS，又会破坏应用与 host 的自然整合。论文提出第三条路：保留 Linux 进程环境，借助 VT-x 安全地开放一部分底层能力。

其组成是一个管理虚拟化硬件与 Linux 交互的内核模块，以及帮助应用操作这些机制的 `libDune`。论文实现面向 **64 位 Intel x86 Linux**。应用选用 Dune 后，并不启动另一份 Linux；文件、网络和进程管理仍由原 Linux 提供。

需要精确理解“无需修改内核”：它指不必为每个应用重新修改 Linux 核心代码，但仍然要加载有内核权限的 Dune 模块。它也不是“普通用户代码从此拥有整机 ring 0 权限”。隔离仍由下层虚拟化配置保证。

本页按论文论证链展开。基础 trap-and-emulate 与课堂沙箱例子的推演见[中文译稿](#/c/mit-6.s081-2020/lec/lec19?v=draft) 21:00–48:00、75:00–84:00；这里重点保留论文独有的实现条件、测量定义与局限。

## §2 硬件接口：两条权限轴与三个能力组

### §2.1 VMX 模式不是 privilege ring 的替代品

VT-x 增加 root/non-root 执行环境，两个环境内部仍有 x86 权限环。VMM 在 root 中配置 non-root 的行为；VMCS 既保存相关架构状态，也控制哪些事件需要 VM exit。`VMLAUNCH/VMRESUME` 进入 guest，`VMCALL` 主动退出。

许多 guest 内部操作可以由硬件直接完成，但是否退出取决于硬件规则和控制配置。论文举 `HLT` 为例，VMM 可选择截获；异常入口和 guest 内部权限转换则可直接为进程使用。Dune 并不是在每次页表操作背后偷偷调用另一个软件模拟器。

真正使开放页表成为可能的是 EPT：应用控制第一阶段 GVA→GPA，下层控制第二阶段 GPA→HPA。哪怕应用故意构造恶意页表，也只能选取 EPT 允许的最终内存。

### §2.2 表 1 的能力分类

论文 p.3 的表 1 是**指令类别表，没有时间或性能单位**：

| 能力 | 论文列举的 x86 指令 | 应用获得的用途 |
|---|---|---|
| 异常与中断相关状态 | `LIDT`、`LTR`、`IRET`、`STI`、`CLI` | 设置并直接接收适当的进程内异常 |
| 虚拟内存 | `MOV CRn`、`INVLPG`、`INVPCID` | 页表根、地址映射、TLB 管理 |
| 权限模式 | `SYSRET`、`SYSEXIT`、`IRET` | 在进程内切换可信与不可信执行级 |
| 分段 | `LGDT`、`LLDT` | 建立相关 x86 环境；论文不深入讨论此传统机制 |

这些能力带来三类优化机会。异常无需先走 Linux 再通过 signal 通知应用；PTE 的权限、访问位、脏位可以直接读写；进程可以利用硬件 ring 保护拦截内部不可信代码的系统调用。应用还可在保证自身算法正确的条件下合并页表更新、选择 TLB 失效范围。

论文分别提到 **PCID** 和 **VPID**，不能混为一个标签：前者支持进程内部切换多个地址空间时保留带标识的 TLB 项，后者用于虚拟化上下文，降低 VM 切换带来的清空需求。两者服务的层次不同。

## §3 内核模块：只开放原进程被允许使用的资源

### §3.1 图 1：进程环境与信任边界（p.4）

原图 1 上部是 non-root ring 3 的不可信代码；其下是 non-root ring 0 的 Dune 程序与 libDune；最下层是 root ring 0 的 Linux 和 Dune 模块。普通进程则在 root ring 3，仍可与 Dune 进程并存。

这张图有两个保护边界：Linux 不信任整个 Dune 进程；沙箱 runtime 又不信任进程内部的部分代码。相对于 host，libDune 不属于可信内核；相对于插件，沙箱 runtime 则必须可信。

进程经 `/dev/dune` 的 `ioctl` 进入 Dune 模式。2012 实现中此转换不可逆；fork 的子进程起初不在 Dune 模式，需要时可以重新进入。VM exit 由模块接住，可能转发系统调用、处理缺页，或在 `HLT` 后让出 CPU。定时器等 host 事件仍可让内核重新得到控制。

Dune 需要 VT-x，所以运行在另一台 VM 内还要求嵌套虚拟化支持；论文没有测出该情形的性能。每个核可以独立控制 VT-x，因此论文也讨论与其他 VMM 在不同核上共存的可能性。

### §3.2 威胁模型与“仍是进程”（pp.4–5）

论文希望 Dune 不改变 Linux 对该进程的既有授权：它产生的外部效果，应能由普通进程通过同一系列系统调用产生。开放的是**内部组织能力**。作者假定 CPU 本身没有可利用缺陷；这是一项威胁模型前提，不是对硬件永远无漏洞的保证。

与普通 VMM 相比，Dune 不需要模拟整台机器。例如读取网络数据时，Dune 进程使用 Linux socket 的 `read`，不是操作一块虚拟网卡；显示也可使用现有 X server、Unix-domain socket 和共享内存。减少暴露的硬件状态，还能减少 VM entry/exit 时的保存恢复成本。

普通 VM 往往呈现平坦的 guest RAM，Dune 的 EPT 却跟随原进程地址空间，可以稀疏，也可以反映多个进程对同一共享内存的映射。这也是“采用虚拟化硬件”不等于“提供虚拟机抽象”的具体含义。

### §3.3 图 2：三种地址与 EPT 同步（p.5）

图 2 左侧是 Dune 路径：GVA 经用户控制的页表成为 GPA，再经 EPT 成为 HPA；右侧是普通进程路径：host virtual address（HVA）经 Linux 页表成为 HPA。两条路径最终访问的是同一类真实 RAM。

理想上，若 EPT 能直接复用 Linux 页表，模块会很简单。但论文遇到两个障碍：

1. EPT 的二进制格式不同，不能只复用同一个页表根。
2. GPA 位宽受物理地址宽度限制，可能小于进程使用的虚拟地址宽度。论文以 36 位物理／48 位虚拟为例。

第一个障碍由按需同步解决：EPT 初始为空，缺失项引发 EPT fault，也就是 VM exit。模块结合 Linux 的缺页处理结果建立相应转换与权限。Linux 后续解除映射时，Dune 利用 MMU notifier 获得通知，撤销相关 EPT 项，并把需要的脏状态反馈给 Linux。

第二个障碍由区域压缩规避：2012 原型只支持进程低地址的代码／数据／堆、mmap 区域、栈三个区域，每区限制为 4GB，合计放入 GPA 前 12GB；用户页表再把这些紧凑的 GPA 映射回程序原来的 GVA 布局。因此它不是把应用所有指针都改成 36 位，而是重新安排两阶段转换中间那一层。

代价是非标准地址布局或超出这些区域限制的程序可能不兼容。论文提出更灵活地打包各 VMA 作为潜在改进，但没有把它当成现有实现。

### §3.4 寄存器、系统调用与信号（p.6）

Dune 没有任由程序改变所有机器配置。许多控制位跟随 Linux，以维持正常进程环境；例如让 64 位应用随意退出 long mode 并无实际意义。论文允许少量特殊控制，并对代价较高的 MSR 修改加以限制，避免每次系统调用都保存恢复大量状态。

FS/GS base 是特殊允许项。系统调用入口 MSR `LSTAR` 则只读，程序可以利用页表在该既定虚拟地址映射自己的处理入口，而非不断修改 MSR。时间戳计数器 TSC 直接暴露，也不按完整 guest OS 的需要制造一条独立虚拟时间线。

普通 `SYSCALL` 只在进程内部的权限环境中转移；进入 Linux 的系统调用改经 `VMCALL`，模块再分派到 Linux syscall table。退出进程等调用还要做 Dune 自己的清理。

信号也要适应新环境。页错误等事件可以直接由硬件异常承担，而 `SIGINT` 等仍需向进程报告；模块可注入合成中断，让硬件正确从内部 ring 3 转入 ring 0 处理。不能因为保留了进程抽象，就假定原 libc 的所有 signal 细节完全不变。

### §3.5 实现规模与尚未解决的状态跟踪（p.6）

内核模块约 2,509 行，部分低层 VT-x 操作沿用 KVM 代码，但高层模型不同。Linux 的线程实现使作者实际上为每个线程设置 VMCS；一个地址空间内可以有 Dune 线程，也可以有普通线程。

原型对 EPT accessed/dirty 状态的高效跟踪尚不完整。为保证 Linux 换页、回写等逻辑的正确性，在 MMU 通知中保守地把相关页报告为已访问、已修改。这里的限制是**下层 EPT 与 Linux 内存管理的协作**，不要与上层 GC 读取自己 PTE 的 dirty bit 混淆。

## §4 libDune：启动过程和兼容性边界（p.7）

libDune 约 5,898 行，提供页表管理、ELF 加载、简单页分配、异常和系统调用辅助。相对于内核它完全不可信，因此应用写错自己的页表不应该破坏 Linux 的隔离。

进入 Dune 前必须准备有效用户页表；由于 GPA 经过压缩，不能随便做一个恒等映射就认为原指针都能继续工作。应用把根地址交给进入用的 ioctl，切换后再建立 GDT、IDT、双重故障用的独立栈以及线程局部状态等环境。

libDune 可以把 ring 0 中普通系统调用重定向为 hypercall；另有修改版 libc 直接使用 `VMCALL`，以减少额外开销。这是兼容性辅助，不应被理解为任意二进制的所有行为已被无条件支持。

论文明确列出以下限制：

- 信号支持还没有完全整合进标准 libc 接口，应用需要使用 `dune_signal`。
- 虽支持 pthreads，页表管理等部分库工具尚非线程安全。
- Linux 系统调用的指针参数必须是有效 **HVA**。若应用把 GVA 布局改得与 HVA 不同，需要转换参数；指针在进程内部可解引用，不代表 Linux 在其地址视图中会读到同一对象。
- API 偏 x86，直接使用特权硬件增加了架构相关代码。移植到其他体系结构需要新的抽象和实现。

这些是评价“仍保留 OS 接口”时不可省略的条件。

## §5 三个应用：安全边界怎样落到代码中（pp.7–9）

### §5.1 沙箱不仅需要 U/S 位，还需要安全的加载和参数检查

论文沙箱支持原生 64 位 Linux 可执行文件。可信 runtime 位于 non-root ring 0，不可信二进制位于 ring 3；PTE supervisor 权限保护 runtime，异常入口拦截不可信代码的敏感动作。

一个容易被忽略的入口是 ELF loader：即便程序运行时在沙箱内，若可信 loader 先解析恶意 ELF 头，就可能在保护建立前被攻击。作者采用两级加载：小型、仅处理静态二进制的可信 loader，先把 `ld-linux.so` 放进不可信环境，再由后者在 ring 3 加载真正的不可信程序。

系统调用过滤同样不能只检查调用号。一个允许的调用若接受错误地址，仍可能让内核替插件改写 runtime 内存。因此即使评测中的 **null policy** 允许系统调用通过，也仍验证参数，以保护 runtime。原型只支持足以运行多数单线程 Linux 应用的一部分系统调用，并未完成所有多线程兼容性。

作者还实现用户态防火墙，检查 `bind/connect` 等网络调用，限制通信对端；以及检查点功能，保存内存、寄存器和打开文件等系统调用状态。它们说明进程内拦截可承载不同策略，而非证明任何策略都会自动安全。

### §5.2 Wedge：sthread 的“快速创建”包含复用

Wedge 的目标是兼有类似 fork 的隔离与接近线程的操作成本。一个 sthread 只能访问策略允许的内存、文件描述符和系统调用。例如 Web 服务把每个请求放入独立 sthread。

快速创建并不一定每次创建新实体。作者在 sthread 干净时保存初始状态，请求结束后恢复被改脏的内存和状态，再供后续请求复用。Dune 在其中提供 ring 保护、页表限制、dirty bit 驱动的恢复，以及 tagged TLB 支持的快速上下文切换。

所以比较 sthread 与 fork 时，要记得前者包含“预建并回收复用”的设计条件，不能把结果宣传成所有新进程分配都能无条件快 40 倍。

### §5.3 GC：从快异常到直接读取 dirty bits

作者修改 Boehm mark-sweep collector。其原有 dirty tracking 可通过 `mprotect` 与 signal 模拟，也可依赖操作系统提供的脏页查询。Dune 给出渐进式改造路径：先加速权限修改和缺页处理，再精细控制 TLB 失效，最后直接读 dirty bits，省去依靠保护异常模拟写追踪的步骤。

论文指出该 GC 的页操作约九成针对单页，因而选择单页失效而非清空整个 TLB 可以避免无关缓存损失。PDF 正文一处把 `INVLPG` 拼成 `INVPLG`，这里按表 1 中的正确指令名校订。

论文还把 Azul C4 所需能力映射到 Dune：快速异常、批量页表提交、大页拆分与合并、释放物理帧但保留用于捕获旧引用的虚拟地址。这里是机制可表达性的分析，不表示论文实现并评测了整个 C4 collector。

## §6 实验：收益、固定开销与负载条件

### §6.1 测试平台与“变慢的操作”（pp.9–10，表 2）

所有本文数据来自论文实验，未在本课程内容制作中重跑。平台为单路 **Intel Xeon E3-1230 v2，四核 Ivy Bridge，3.3GHz，16GB RAM**，64 位 Debian、Linux 3.2；关闭频率调整等电源管理功能。这是 2012 的平台条件，不是对今天所有处理器的预测。

表 2 单位为 **CPU cycles**，越低越好：

| 被测操作 | Linux | Dune | 测量含义 |
|---|---:|---:|---|
| `getpid` | 138 | 895 | 手工调用的往返延迟；调用本身很短，突出跨边界固定成本 |
| 内核处理 page fault | 2,687 | 5,093 | 由内核映射预先清零的页，不是进程内异常交付 |
| page walk | 35.8 | 86.4 | TLB miss 的地址翻译成本 |

page walk 测试在 $2^{16}$ 个页上作随机、页对齐访问，制造差局部性和高 TLB miss 率，再由性能计数器统计 page-walk 等待周期，除以访问次数。PDF 原页确认为指数 $2^{16}$，不是文本提取中看似“216 页”。

两类开销因此分开：进入 Linux 要付 VM entry/exit 成本；TLB miss 要面对 EPT 增加的 page-walk 工作。应用若常命中 TLB、系统调用内部工作又远多于跨边界开销，整体影响可能较小，但这必须用具体负载验证。

### §6.2 更快的操作并不是同一条路径（p.10，表 3）

表 3 同样是 **cycles**：

| 操作 | Linux | Dune | 对比的工作 |
|---|---:|---:|---|
| `ptrace` 型拦截 | 27,317 | 1,091 | 拦截 getpid，转交内核，再返回结果 |
| `trap` | 2,821 | 587 | Linux SIGSEGV 通知，对比 Dune 直接硬件 page fault |
| `appel1` | 701,413 | 94,496 | 100 个受保护页逐个访问；每次异常解保护本页、保护另一页 |
| `appel2` | 684,909 | 94,854 | 批量保护 100 页；访问时逐页异常并解保护 |

如果只在 runtime 内部处理系统调用、不转给 Linux，论文另测 `PTRACE_SYSEMU` 为 13,592 cycles，Dune 硬件调用入口为 180 cycles。因而表中 1,091 cycles 的大头不是本地拦截，而是仍需跨到 Linux 完成 getpid。

这解开了一个表面矛盾：表 2 说 page fault 更贵，表 3 却说 trap 更便宜。前者测**Linux 处理缺失内存映射**，后者测**把异常交给进程处理**；终点不同，不应直接交换数字。

### §6.3 图 3：平均低开销不能掩盖 TLB 敏感负载（pp.10–11）

SPEC2000 使用 null sandbox policy。图 3 纵轴是相对普通 Linux 的 **% Slowdown**：正数表示更慢，负数表示更快；横轴有 gzip、vpr、gcc、mesa、art、mcf、equake、crafty、ammp、parser、eon、perlbmk、gap、vortex、bzip2、twolf。三组柱分别是 Sandbox、Sandbox with large pages、Linux with large pages。

普通页 sandbox 平均慢 2.9%，但 mcf 慢 20.9%，ammp 慢 10.1%。作者将这些异常值联系到高 TLB miss 率和 EPT 成本。不能只引用平均数就说每个程序都接近零开销。

随后作者让大块分配在 guest 页表和 EPT 中都使用 **2MB 大页**；通过拦截 mmap 可以选择性实施。为公平比较，也用 libhugetlbfs 给 Linux 采用同样的大页策略。两者都用大页时，平均性能差在 0.1% 以内。图中某些大幅负值是相对普通页 Linux 的改进，不代表全部改进都来自 Dune。

这张图没有给出每个柱子的精确数值表，本页只报告正文明确给出的数字与原图可确认的方向，不根据小图估读更多小数。

### §6.4 Lighttpd：避免再走一套 guest 网络栈（p.11，表 4）

测试是单进程、单线程、事件驱动的 lighttpd，经过千兆以太网，用 Apache `ab` 反复请求一个小 HTML 文件。并发分别设为 1 和 100。表中数值单位是 **requests/second**，越高越好；尽管作者把单客户端场景称为 latency test，表本身并不是毫秒延迟。

| 环境 | 1 client（req/s） | 100 clients（req/s） |
|---|---:|---:|
| Linux | 2,236 | 24,609 |
| Dune sandbox | 2,206 | 24,255 |
| VMware Player | 734 | 5,763 |

Dune 两种并发下吞吐下降都小于 2%。作者用 strace 观察到每个连接有多次系统调用，把小幅损失归因于 VMX 转换成本。VMware Player 在此配置下降更大，论文主要归因于请求要经过 guest 和 host 两套网络栈。

这个结果比较的是论文当时的 VMware Player 配置，不能外推为“所有虚拟机网络都慢 67%–77%”；设备直通和其他网络设计不在这项对照中。

### §6.5 Wedge：创建、切换与端到端请求（p.11，表 5）

此表单位是 **微秒（μs）**，不要与表 2–3 的 cycles 混用：

| 方案 | create | context switch | HTTP request |
|---|---:|---:|---:|
| fork 方案 | 81 | 0.49 | 454 |
| Dune sthread | 2 | 0.15 | 362 |

sthread 创建通过池化和恢复脏内存而加速，切换利用 tagged TLB 减少刷新。LAN 静态文件服务器把每个请求放入新 fork 进程或 sthread，端到端请求时间减少约 20%，远小于创建子操作约 40 倍的改善。这正说明局部微基准不能直接当成应用总加速比。

实现复杂性也是评价目标。原 Wedge 有约 700 行内核模块加 1,300 行库；纯用户态版本约 5,000 行；使用 Dune 的 Wedge 约 750 行用户代码。比较时要记得 Dune 模块与 libDune 是另有的公共底座，并非整个系统只有 750 行。

### §6.6 GC：哪些负载能偿还 EPT 成本（p.12，表 6）

作者评测三个变体：Dune 是直接移植，Dune TLB 精细管理失效，Dune dirty 直接读取脏位。修改代码量分别约为 52、91、82 行。四个负载为构建二叉树的 GCBench、构建并求和的 LinkedList、使用 Google sparse hash map 的 HashMap，以及用 Mini-XML 解析 150MB 医学文献 XML 并统计作者的完整应用。

表 6 分别使用**次数、MB、ms**三种单位：

| 指标 | GCBench | LinkedList | HashMap | XML |
|---|---:|---:|---:|---:|
| 回收次数 | 542 | 33,971 | 161 | 10 |
| 累计分配（MB） | 938 | 15,257 | 10,352 | 1,753 |
| 堆规模（MB） | 28 | 1,387 | 27 | 1,737 |
| Normal（ms） | 1,224 | 15,983 | 14,160 | 6,663 |
| Dune（ms） | 1,176 | 16,884 | 13,715 | 7,930 |
| Dune TLB（ms） | 933 | 14,234 | 11,124 | 7,474 |
| Dune dirty（ms） | 888 | 11,760 | 8,391 | 6,675 |

直接移植有输有赢，说明“进入 Dune”本身不是优化。三个微基准中，TLB 版本执行时间减少 10.9%–23.8%，dirty 版本减少 26.4%–40.7%；其中 40.7% 是 $(14160-8391)/14160$ 的**时间减少比例**，不是 40.7 倍加速。

XML 对照尤其重要：三个 Dune 变体分别慢约 19.0%、12.2%、0.2%。累计分配 1,753MB 与最大堆规模 1,737MB 接近，且只回收 10 次，意味着很少产生需要反复处理的垃圾；GC 优化的收益不足以补偿 EPT 成本。

作者随后把输入改为连续处理多个文件，让内存被反复回收。顺序处理十个 150MB XML 文件时，dirty 版本执行时间比基线减少 12.8%。这验证的是“收益依赖分配／回收模式”，不是简单地说 XML 解析永远不适合 Dune。

## §7 硬件反思、相关工作与结论（pp.12–14）

作者希望硬件继续降低 EPT page-walk 与 VM entry/exit 成本，并让 GPA 支持与普通虚拟地址相当的位宽，以减少地址布局压缩的复杂度。缓存控制、调试寄存器、`MONITOR/MWAIT`、结合 IOMMU 与 SR-IOV 的直接 I/O 被列为可能扩展，**不属于本论文已经全部实现并评测的功能**。

论文也讨论迁移到 ARM 等架构的机会。相关段落是 2012 年对当时硬件的展望，不应当作今天 ARM 虚拟化机制的完整规范，也不能据此说论文已交付 ARM 版本。

与 Exokernel、SPIN 相比，Dune 不是要替应用全面改写 OS 服务，而是让应用在继续使用 OS 的同时接触特权硬件。与 Fluke 的可递归嵌套进程模型相比，Dune 这里暴露的硬件权限层次有限。与 Native Client 等软件沙箱相比，它利用硬件保护降低实现和运行开销，但需要虚拟化能力与内核模块，可移植性条件不同。

最终应带走的是一种组织原则：**把机制开放给应用，把资源边界留在下层。**论文证明这种方法能简化若干实现、加速特定负载，同时坦诚暴露了两阶段翻译、兼容性与部署方面的代价。它没有证明所有应用都会更快，也没有把机制本身等同于完整沙箱策略。
