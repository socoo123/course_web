# 第 19 讲 · 谁可以管理映射，谁决定最终权限？

虚拟化最值得掌握的不是“模拟另一台电脑”，而是一个更一般的问题：**怎样让不可信软件拥有局部管理能力，又不能扩大它对整机资源的权限？**

先理解页表、trap、用户态与内核态。阅读时始终把“guest 认为发生了什么”和“真实 CPU 做了什么”分开。前半课用 RISC-V 推导软件方案，后半课讨论 x86 VT-x，Dune 是其上的 Linux 研究原型。

## 1. 用三个不变量检查虚拟化设计

### 不变量一：普通操作可以直接跑，敏感操作必须受控

逐条解释所有指令很容易理解，但成本高。trap-and-emulate 让 guest 的普通指令直接执行，只在敏感操作上拿回控制权。这依赖 ISA 的行为：如果一个影响系统语义的操作在低权限下悄悄产生不同结果，VMM 就未必有机会修正。

在课堂的软件方案中，guest 内核和 guest 用户代码都运行在真实用户态；VMM 在真实 supervisor mode。细节推演见[中文译稿](#/c/mit-6.s081-2020/lec/lec19?v=draft) 15:00–36:00。

### 不变量二：虚拟状态必须解释 guest 世界

真实 `scause` 可能是“非法指令”，而 guest 应看到的 `scause` 是“系统调用”。两者没有矛盾：前者解释为什么进了 VMM，后者解释为什么进了 guest 内核。

理解这点后，可以自己推导两次转移：

| guest 动作 | VMM 修改什么 | 真实返回后执行哪里 |
|---|---|---|
| guest 内核 `sret` | 虚拟模式变 user；使用虚拟 sepc 作目标 | guest 用户程序 |
| guest 用户 `ecall` | 记录虚拟 sepc/scause；虚拟模式变 supervisor | guest 的 stvec 入口 |

**VMM 的 trap return，可以对应 guest 的 trap entry。**把这句话想清楚，比背两组寄存器赋值更有价值。

### 不变量三：第一层映射不能扩大第二层授权

令 guest 页表为 $G$，VMM 的内存授权映射为 $H$，真实访问结果是：

$$
\mathrm{HPA}=H(G(\mathrm{GVA})).
$$

无论 guest 怎样改变 $G$，最终能访问的地址都必须落在 $H$ 授权的集合中。安全性不能依赖 guest 自觉只填“合法”的物理地址。

影子页表由软件预先合成 $H\circ G$，CPU 使用合成结果；EPT 让硬件直接执行两阶段转换。二者解决同一隔离问题，**组合映射的位置和维护成本不同**。见中文译稿 36:00–48:00、69:00–72:00。

## 2. 两条权限轴，不要画成一条高低阶梯

| 执行位置 | 谁运行 | 谁约束它 |
|---|---|---|
| VMX root，ring 0 | Linux 与 Dune 内核模块 | 底层可信系统 |
| VMX root，ring 3 | 普通 Linux 进程 | Linux 页表与权限 |
| VMX non-root，ring 0 | Dune 进程的可信 runtime | VMX 控制与 EPT |
| VMX non-root，ring 3 | Dune 内部不可信代码 | runtime 的页表／入口，以及外层 EPT |

non-root ring 0 不是 host ring 0；它能够管理自己的子域，却不能管理整个 host。Dune 的创新是把原本服务于 guest OS 的这组能力，交给仍保留 Linux 进程身份的应用。

这个思想也解释了为什么一个 sandbox 插件不能顺手获得任意 `%cr3` 控制权：限制它的正是内部 ring 3 边界。要给它更多能力，就要重新设计受控接口，不能一边宣称沙箱隔离，一边无条件放开页表。

## 3. 机制给了谁，策略就要由谁承担

EPT 保证 Linux 不被 Dune 进程越界访问；它并不自动保护 Dune 进程内部的浏览器免受插件伤害。后者需要 runtime 正确安排页权限、异常入口、加载过程和系统调用策略。

以 fork 为例，问题不是“Dune fork 的子进程不在 Dune 模式，所以硬件隔离失效”，而是：**谁允许了 fork？子进程重新运行不可信代码前，谁建立其保护环境？**课堂的这段关键问答在 86:00 之后，尤其中文译稿 87:00–90:00。

论文还补充了课堂未展开的工程细节：恶意 ELF 头可能攻击可信 loader；合法系统调用也可能用指针参数破坏 runtime。见[课程资料](#/c/mit-6.s081-2020/lec/lec19?v=materials) §5.1。

设备也有同样的边界选择：

- 模拟既有真实设备：保留旧驱动，软件承担精确兼容的成本。
- 专用虚拟接口：guest 配合，用队列等方式减少频繁同步交互。
- 直通真实设备：依赖硬件隔离与分配能力，缩短数据路径。

不能把“CPU 能直接执行”推导成“设备访问没有虚拟化开销”。

## 4. 性能判断：先区分路径，再谈倍数

一个简化成本账本是：

$$
\Delta T\approx N_{exit}\,\Delta C_{exit}
+N_{walk}\,\Delta C_{walk}
-\text{省去的内核中介工作}.
$$

这是编者用于组织思考的模型，不是论文拟合公式。它提醒我们同时数“新增加的工作”和“被消除的工作”。

例如直接访问 dirty bit，可能省掉权限修改、signal 和大量 TLB 失效；但应用仍承担 EPT 的 page-walk 成本。如果应用几乎不产生可回收垃圾，前者收益很少，后者仍然存在。论文的 XML 单文件负载就是反例，见课程资料 §6.6。

同样，论文的两种 page-fault 数字不能互相替换：

- 内核为应用补映射：需要跨到 Linux，可能更贵。
- 把保护异常交给进程内 handler：可以不经过 Linux signal，更便宜。

图表阅读还要检查单位：表 2–3 是 cycles，表 4 是 requests/s，表 5 是 μs，表 6 的运行时间是 ms。没有测试条件的“快 25 倍”或“慢不到 2%”并不是完整结论。

## 5. 容易误读的五句话

1. **“guest 内核运行在用户态。”**这是前半课软件陷入模拟的方案；VT-x 中 guest 可在 non-root ring 0 执行。
2. **“直接修改页表，所以能访问任何内存。”**忽略了第二阶段授权；Dune 只能重排自己获准使用的资源。
3. **“sfence 之前新 PTE 完全不可能生效。”**不准确。正确理解是需要相应同步，才能依赖规定的地址翻译效果。
4. **“Dune 兼容 Linux，所以任何指针都能原样传给 syscall。”**系统调用仍按 HVA 解释参数；自己重排 GVA 后需处理视图差异，见课程资料 §4。
5. **“并发 GC 不需要暂停。”**课堂最后一问明确说明，这里在主要扫描后暂停其他线程，完成 dirty-page 重扫与收尾。

## 6. 自测：用反例验证理解

<details><summary>guest 用户程序执行 csrr a0, scause，VMM 能否直接返回虚拟 scause？</summary>

不能一概模拟成功。VMM 必须查虚拟模式；guest user 本来无权执行该操作，应向 guest 内核表现权限异常。否则会破坏 guest 内核与用户程序的隔离。

</details>

<details><summary>guest 的直接映射 GVA=GPA 是否要求 GVA=HPA？</summary>

不要求。第二阶段 H 可以把 GPA 放到任意被授权的 HPA。guest 所见的恒等关系仍成立，真实物理布局可以不同。

</details>

<details><summary>有了 EPT，切换 guest 页表是否还必须由 VMM 合成一张影子表？</summary>

课堂讨论的硬件方案不需要这一软件合成步骤。guest 管第一阶段，硬件结合 EPT 翻译。VMM 仍需维护 EPT、处理有关退出与上下文，不能说监控器从此没有内存管理工作。

</details>

<details><summary>把所有系统调用都放行，为什么还不一定是安全的 null sandbox policy？</summary>

即使允许调用种类，也要检查参数不能使 Linux 替不可信代码访问或修改 runtime 的内存。论文的 null policy 仍做这项检查。

</details>

<details><summary>GC 发现某页 D=1，是否知道具体哪个对象、哪条指针被写了？</summary>

不知道。dirty bit 是页粒度的写入证据，只能缩小需要重新检查的范围，不能取代对象级可达性分析。并发结束条件也需另外保证。

</details>

<details><summary>某微操作从 81μs 变为 2μs，整个请求是否就快约 40 倍？</summary>

不是。请求中还有其他工作。论文相应端到端 HTTP request 从 454μs 降到 362μs，时间减少约 20%。这是局部优化与总成本的差别。

</details>
