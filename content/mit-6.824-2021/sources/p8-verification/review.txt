Important interpretation decisions
- Actual case studies are IronRSL (MultiPaxos RSM) and IronKV (sharding for throughput), not a verified Raft implementation or one automatically composed verified service.
- Safety network model permits delay/drop/duplication/reordering but assumes packet integrity and trustworthy source addresses; no Byzantine guarantee.
- Imperative host implementations are single-threaded. Distributed concurrency remains and is handled using protocol reasoning plus constrained reduction.
- Satisfying reduction-enabling I/O obligations is machine checked in the paper; proving these obligations sufficient for reduction remains informal/paper-only.
- IronRSL state transfer after disconnection is not post-crash recovery. No verified client library, member reconfiguration or disk-restart model claimed.
- IronRSL client-reply liveness distinguished from IronKV reliable-transmission liveness; all five IronRSL assumptions retained, including client network path, rate bound, memory and overflow limits.
- Exactly-once transmission component delivery is not generalized to arbitrary client exactly-once operation semantics.
- Paper p6 §3.5 defines PRef(IRef(.)), then reverses the order once in SpecRelation. Materials notes this as a type/order-consistency typo, using definitions rather than silently reproducing it.
- Figure 5 is explicitly simplified, and does not itself establish a complete replay-safe lock implementation. Figure 6 is illustrative proof code; no code snippet has been executed.
- Abstract/§5 call IronKV lease-based, while §5.2 explains delegation, reliable transfer and compact ranges without a complete timed lease protocol. No lease timeout/recovery details inferred.
- Model checking can prove a finite model; testing finite configurations does not establish an arbitrary unbounded system. Related-work comparisons are limited to paper's 2015 descriptions, not asserted as 2026 project capabilities.
