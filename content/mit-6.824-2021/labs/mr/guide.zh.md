# Lab 1：把任务调度写成可推理的状态变化

## 1. 先知道自己正在验证什么

这个实验的难点不是词频算法，而是让多个进程在并发和失败下共同完成一个作业。先把三个问题写在纸上：

1. 谁能决定某个任务可以分配？
2. 哪一刻算任务真正完成？
3. 超时后旧 worker 又回来了，会改变什么？

- [L1 笔记 §3–§4](#/c/mit-6.824-2021/lec/lec01?v=notes)：逻辑任务、尝试、完整发布三个概念。
- [MapReduce 精读 §3–§4](#/c/mit-6.824-2021/lec/lec01?v=materials)：数据路径与原子提交。
- [实验说明](#/c/mit-6.824-2021/lab/mr?v=zh)：硬性要求、运行命令、官方提示。
- Go 的 goroutine、互斥锁、RPC、错误处理；不熟悉时回看 L2/L5 对应主题，公共资料提供 Go 文档入口。

## 2. 先认清实际入口

所有路径相对实验仓库 `src/`：

| 文件 | 阅读时要确认什么 |
|---|---|
| `main/mrsequential.go` | 应用函数怎么调用，如何按键归组，输出格式是什么 |
| `mrapps/wc.go`、`indexer.go` | 两个应用是否只依赖通用 Map/Reduce 接口 |
| `main/mrcoordinator.go` | socket、输入文件怎样传入，何时调用 `Done()` |
| `main/mrworker.go` | 插件怎样加载，socket 如何传给 worker |
| `mr/coordinator.go` | 初始化、RPC handler 与 `Done()` 共享哪些状态 |
| `mr/worker.go` | `KeyValue`、`ihash`、`call()` 与执行循环 |
| `mr/rpc.go` | 你需要定义哪些请求和回复 |
| `mr/mr_test.go`、`Makefile` | 哪些性质被测试，程序和插件如何构建 |

固定 API 为：

```go
func MakeCoordinator(sockname string, files []string, nReduce int) *Coordinator
func (c *Coordinator) Done() bool

func Worker(sockname string,
    mapf func(string, string) []KeyValue,
    reducef func(string, []string) string)
```

启动参数不是旧版教程中的隐式 socket。协调器主程序目前传入 `nReduce = 10`，但实现应使用函数参数，不要把 10 硬编码到分桶逻辑。

另一个源码细节：骨架 `call()` 在 **拨号失败** 时调用 `log.Fatal` 退出进程，RPC 调用本身失败才返回 false。官方提示用“联系失败后退出”解释行为，但不要误以为骨架所有失败都经由 bool 返回。你可以在允许修改的 `worker.go` 中整理控制流程，保持退出语义清楚。

## 3. 先画状态表，再设计 RPC

### 3.1 作业状态与任务状态分开

作业可按 Map、Reduce、完成三个阶段理解；每个阶段有自己的任务集合。单个逻辑任务至少区分未分配、执行中、已完成。

| 事件 | 合理的状态变化 | 要避免的错误 |
|---|---|---|
| 分配未开始任务 | 未分配 → 执行中，记下开始时间 | 两个 handler 同时选中同一个空闲项 |
| 当前执行完成 | 执行中 → 已完成 | 文件未发布就标完成 |
| 超过 10 秒仍未完成 | 允许启动新尝试 | 错把重派当成创建了新的逻辑任务 |
| 已完成任务再次报告 | 保持已完成 | 完成计数再次加一 |
| 当前阶段全完成 | 进入下一阶段 | 以“已派发数量”代替“已完成数量” |

超时不意味着旧尝试被操作系统终止。若你的方案用 attempt 编号识别重派，这只是元数据身份；它不会自动禁止旧进程写共享文件。

### 3.2 回复要表达控制意图

worker 请求任务时至少需要分辨四种结果：执行 Map、执行 Reduce、暂时等待、整个作业结束。可以用清晰的任务类型表示，不必把它们全塞进含糊的“文件名为空”。

再从接收者的工作倒推信息：

- Map 执行需要哪个文件、逻辑 Map 编号、分区数？
- Reduce 如何知道自己负责哪个分区、要收集哪些 Map 输出？
- 完成报告如何确定属于哪个阶段、哪个逻辑任务、哪次尝试？
- 重复完成报告怎样保持结果不变？

不要先发明复杂 RPC 数量。独立完成通知或在下一次请求中附带完成信息，都可以形成合理协议；关键是含义明确、重试后仍可推理。所有待传输字段须导出，每次调用重新创建零值 reply。

## 4. 分阶段推进实现

### 阶段 A：确认顺序程序和通信入口

先按实验说明运行顺序词频，理解结果；阅读示例 `Example` RPC，确认 worker 能连接传入的 socket 并获得一次回复。

**阶段目标**：能解释应用函数和框架分别负责什么，并能跟踪一条请求的发送与处理。此阶段不以全部测试通过为目标。

### 阶段 B：一个 worker 跑通数据路径

先考虑无故障情况：Map 读入文件、调用 `mapf`、按 `ihash(key) % nReduce` 分桶；Reduce 读自己分区对应的所有 Map 输出，按键排序并对同键值调用 `reducef`。

先用小输入手算预期结果。至少包含重复键、跨文件同键，以及没有键落入的空分区。空分区仍然是一个需要完成的 Reduce 任务，最终文件可以为空。

不要把“一个 Reduce 任务”理解成“调用一次 reducef”：一个分区可能包含很多键，每个键需要自己的值集合。

**阶段目标**：数据路径可以与顺序程序对照，输出格式正确，逻辑分桶与物理文件一一对应。

### 阶段 C：增加并发与等待

多个 worker 会同时请求任务；RPC handler 与主程序的 `Done()` 也会并发访问协调器。挑选任务、更新其状态和记录分配时间必须作为一致的状态操作。

锁保护的是任务表和阶段不变量，不是整个计算过程。执行 Map/Reduce、读写大文件或等待远端，不应无意间让所有调度串行化。

无空闲任务不表示结束：其他 worker 可能还在执行。worker 可以等待后再次请求；如果选择协调器端阻塞，要确保等待释放必要的锁，并在条件变化后重新检查条件。

**阶段目标**：能同时运行多个 Map，之后能同时运行多个 Reduce；在阶段间等待时不忙等、不早退。

### 阶段 D：输出先完整，再可见

考虑一个 worker 在写到一半时崩溃。最终路径如果已经暴露，读者可能消费半成品。因此把临时写入与发布分开，临时文件名要区分并发执行尝试。

使用与目标文件同一文件系统中的临时文件，避免跨文件系统 rename。成功路径要确认编码、写入、关闭和重命名的错误；任一步失败都不能回报逻辑完成。

一个 Map 有多个分区文件，不能仅凭“已经写好了第一个文件”就标整个任务完成。若采用常见的 `mr-X-Y` 公共文件名，消费者应在所有 Map 完成后才开始读取，且旧尝试的覆盖必须纳入确定性输出与原子替换的论证。

**阶段目标**：每个可供消费的文件都是一份完整结果，完成报告严格晚于该任务全部必要文件的发布。

### 阶段 E：加入超时重派

让协调器发现执行中但超过 10 秒尚未完成的任务，并使它能被重新执行。可在调度请求时检查，也可使用周期检查；两者都是实现选择，不要求额外心跳服务。

用一次完整事件序列推演：A 领取任务、A 超时、B 重做、B 完成、A 迟到报告。检查逻辑完成计数、文件选择、阶段切换，以及已完成任务是否会被旧消息重新改成执行中。

常见错误是每个分配都启动一个不检查当前状态的延迟回调：十秒后旧回调直接把任务改成空闲，即使它已经完成或已经分配给新尝试。过期事件必须和当前状态一起判断。

**阶段目标**：失败会增加物理执行尝试，但不会增加逻辑输入的贡献，不会破坏已完成状态。

### 阶段 F：收尾与退出

`Done()` 不是独立的“结束按钮”，而是对共享状态的只读判断。它应与正常调度看到同一个一致状态。

只有所有 Reduce 输出已发布，才进入作业完成阶段。在此之前，闲置 worker 等待而不是正常退出；结束后通过明确退出回复或协调器关闭连接，使 worker 收尾。

**阶段目标**：任何正常进程开始结束时，作业输出都已经就绪；不会靠其他 worker 继续补写缺失输出来修复早退。

## 5. 五种故障位置，五个不同问题

| 事件 | 需要检查的状态或机制 |
|---|---|
| worker 领到任务但未生成输出就退出 | 超时后是否仍有人能领到该逻辑任务 |
| worker 写了一半临时文件就退出 | 消费者是否可能误读临时文件 |
| 文件已发布但完成报告没被处理 | 重做或再次报告是否仍安全 |
| 旧 worker 在重派后恢复 | 迟到消息与旧文件写入分别怎样处理 |
| 一份中间文件解码失败 | 是否把坏文件当成正常 EOF，悄悄少算 |

不必先搭复杂故障注入平台。先用事件表推理，再结合官方 `crash.go` 和测试日志定位实际失败。

特别注意本实验的存储条件：worker 进程崩溃不会自动删除共享目录中的已完成文件。所以不能直接移植论文“机器不可达导致本地 Map 输出丢失”的所有恢复动作。你需要满足的是实验实际的进程与文件假设。

## 6. 用官方测试定位性质

以下命令均在实验仓库 `src/` 下执行，`make` 会构建相应程序和插件，默认启用 `-race`：

```bash
make RUN="-run Wc" mr
make RUN="-run Indexer" mr
make RUN="-run 'MapParallel|ReduceParallel'" mr
make RUN="-run 'JobCount|EarlyExit'" mr
make RUN="-run CrashWorker" mr
make mr
```

按你完成的阶段选择相关测试即可；最后跑完整 `make mr`。输出末尾的 `PASS` 才是这次验收结果；教程里列出了命令，不等于命令已经运行。

| 失败信号 | 优先追问 |
|---|---|
| `Wc` / `Indexer` 结果不同 | 分桶、归组、编码、输出格式或重复输入贡献是否错误 |
| `MapParallel` / `ReduceParallel` 失败 | 是否只派一个任务，或在长操作期间一直持有全局锁 |
| `JobCount` 失败 | 是否过早重派，或把已完成任务再次正常分配 |
| `EarlyExit` 失败 | 是否把“没有空闲任务”当成结束，或输出发布前就通知完成 |
| `CrashWorker` 失败 | 是否漏掉重派、读到半成品，或迟到报告破坏状态 |
| race detector 报告 | RPC handler、超时检查和 `Done()` 是否共享无保护数据 |

日志建议记录：阶段、任务编号、尝试编号（若使用）、worker PID、事件、任务状态变化与时间。先找**第一条违背不变量的状态变化**，通常比从末尾错误反向猜测更有效。

不要把普通调试日志写进 `mr-out-X`。手动运行与 `make` 测试还应保持插件和程序的编译设置一致；混用旧插件或 `-race` 设置不同的产物，会造成与调度算法无关的问题。
