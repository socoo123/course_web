# L15 中文译稿：FaRM 与乐观并发控制

## 第一录像：FaRM（独立时间轴 00:00–94:37）

### 00:00–03:00 目标是单数据中心内的高性能事务

讲师向不同时区的同学问好。今天读的是 2015 年 FaRM 研究论文，目标是探索能大幅提高事务性能的新技术。开场给出一个醒目的数字：90 台机器执行 TATP 基准，每秒约 1.4 亿次事务。

讲师请大家回忆 Spanner 的性能：单次事务可能需要 10–100 毫秒。FaRM 的数字看上去完全不同，但两者面向不同环境。Spanner 要同步复制到地理上相距很远的地点，支持一个数据中心失效后仍能运行的应用；FaRM 把机器放在同一个数据中心，面向需要比传统数据库更高吞吐的内存事务。

它仍然要提供严格可串行化，与上一讲的外部一致性在事务语义层面相对应。降低延迟并不是靠取消事务保证。

> **性能校注：** 课堂把 Spanner 的延迟取倒数说成每秒 10–100 次，这仅适用于一条串行请求流，不能作为 Spanner 集群吞吐量。FaRM 的 1.4 亿也不是全部为跨机多对象写事务；基准组成见课程资料 §7。

### 03:00–07:00 从分片到硬件，再到 OCC

第一项提速手段是分片：不同事务访问不同分片时，可以让很多机器并行工作。接下来 FaRM 去掉正常事务路径上的磁盘持久化，使用 non-volatile DRAM；然后用 kernel bypass 降低操作系统网络栈开销，用 RDMA 直接访问远端内存。

讲师把它与复制实验中的持久化联系起来：若每笔事务都等待稳定存储，存储延迟会成为瓶颈。这里要把写 SSD／磁盘移出正常提交的关键路径。课堂此处的时间单位口头较混乱，不据其建立精确设备延迟表。

这些硬件能力推动了并发控制选择。此前常见的悲观方案先取得锁，再执行操作；FaRM 希望读不加锁，先读、先计算，到提交时检查读取依据是否仍有效，失败则中止重试。这就是 OCC。研究原型的目的，是探索这些机制组合后能达到什么性能。

### 07:00–10:00 region、内存容量与主备

讲师强调 FaRM 来自 Microsoft Research，是这篇论文所描述的研究系统；随后画出由高速数据中心网络连接的 90 台机器。

分片单位叫 region，大小为 2 GB。region 位于 DRAM，整个数据库必须装进集群总内存；容量不够就要增加机器，不能默认有一个透明磁盘后备层。

为防止单机崩溃丢掉内存，每个 region 有 primary 和 backup。不同 region 的主备可以交错放在机器上：某机器是 region 1 的主副本，同时可以是 region 2 的备副本。机器是物理节点，primary／backup 是针对某个 region 的角色。

### 10:00–13:00 配置管理与全机房掉电

configuration manager（CM）与 ZooKeeper 管理 region 到主备机器的映射。单机内核崩溃或设备故障时，可以依靠另一份复制数据恢复。

但这没有解决相关故障：如果整个数据中心同时断电，所有普通 DRAM 都会丢失。FaRM 使用电池／UPS，在主电源失效后短时间维持机器运行，把 region、事务状态和日志等内存内容写入 SSD。电源恢复后，再从 SSD 载入。

所以“非易失 DRAM”是硬件和软件协作形成的持久性契约，并不是 DRAM 芯片忽然变成无需供电的介质。这里的 SSD 主要用于掉电保存，而不是每次事务都写一次。

### 13:00–16:00 对象头和简化事务接口

region 可以想作一段字节数组，其中存放对象。对象有 OID 和一个 64 位头：高位是锁标志，其余位是版本号。

应用创建事务，用 OID 读对象，在本地修改字段，登记写入，最后请求提交。提交可能失败，应用通常重试整个事务。课堂先用“给一个对象字段加一”说明接口，随即说明实际事务可以跨多个对象、多个 region。

跨 region 的更新需要某种类似两阶段提交的协调过程；后面要解释如何把它和 RDMA、复制一起实现。

> **接口边界：** 这些是历史 FaRM 的概念接口，不是本路线固定的 2026 Go 实验 API。

### 16:00–19:00 问答：OID 是地址还是偏移

**问：OID 里的地址是某台机器上的绝对地址吗？**

讲师改正板书用词：更准确说是 region 编号加 region 内偏移。region 可以移动或重新复制，实际承载机器及映射地址可能变化。

**问：为什么选择全局地址空间，是否与把数据全放在 DRAM 有关？**

讲师先从内存数据库的背景解释：DRAM 成本下降，使大数据集常驻内存成为可探索的路线。追问之后又区分了两层：每台机器仍有自己的进程地址空间；全局对象名字使应用能指向远端对象，并不表示所有机器的本地虚拟地址天然一致。

接下来把重点从存储瓶颈转到 CPU 和网络开销。

### 19:00–23:00 kernel bypass：把队列交给用户进程

传统网络路径中，应用通过系统调用进入操作系统，操作系统经过网络栈和设备驱动操作 NIC。收到包时，NIC 中断内核，内核再通知应用；复制、调度、系统调用和中断都消耗 CPU。

kernel bypass 让操作系统先配置访问权限，把网卡的发送／接收队列映射给用户进程。之后应用直接向队列投递操作、读取完成结果，不必每次都经过内核。

FaRM 还用轮询减少普通数据路径的中断开销：线程检查队列是否有新内容，在应用执行和轮询之间切换。代价是消耗 CPU 时间，而不是空闲时完全免费等待。讲师提到 DPDK 一类工具作为熟悉这种技术的入口。

> **范围校注：** “不用中断”是这里的普通数据路径概括。论文的高优先级租约管理线程反而使用中断，见课程资料 §4。

### 23:00–27:00 RDMA：远端 NIC 执行内存访问

讲师画出两台机器及它们的网卡。发送方把 RDMA 请求交给本地 NIC，请求包含远端内存位置和操作。远端 NIC 识别请求，直接读取内存，把数据发回；远端应用线程不必接收消息、执行读取函数再回复。

这就是这里重点利用的 one-sided RDMA：操作不需要远端 CPU 在前台运行协议代码。发送方仍须发起操作并处理完成通知，网卡和内存系统也仍有工作，不能理解为“整个系统没有 CPU 成本”。

### 27:00–29:00 问答：谁轮询，普通网卡能做吗

**问：客户端如何知道 NIC 队列里有新结果？**

答：线程读取队列中的状态或完成标志；NIC 放入结果并更新状态，应用下一次检查时便发现它。

**问：网卡是不是像普通网卡一样直接工作，是否还要系统配合？**

答：需要支持这些功能的 NIC。kernel bypass 通常要求多组队列，操作系统把某些队列交给指定应用使用，并设置相应 DMA 支持。队列数量有限，不是每个进程都自动拥有任意数量的专属队列。

### 29:00–32:00 RDMA write 用来写日志，也能构造 RPC

RDMA 不仅能读，还能把字节写入指定远端内存位置。但 FaRM 的事务客户端不会直接用它覆写公开对象数据；重要目标是事务日志和消息队列。

每个发送方／接收方配对有自己的日志及消息队列，位于接收方内存。发送方知道自己日志的尾部位置，可以追加 LOCK、COMMIT 等记录。

另一种用法是构造快速 RPC：发送方把请求写进远端消息队列；接收方线程轮询、运行逻辑，再通过反向 RDMA write 返回结果。这仍需要远端软件参与，只是通信路径比传统 RPC 轻。

### 32:00–34:00 问答：权限、连接规模与内存布局

**问：怎样阻止客户端写到不允许访问的内存？**

讲师说在建立 RDMA 连接时，双方、操作系统与网卡完成设置及访问控制；不是收到一个任意地址就无条件允许写。

**追问：每对机器都建连接，加入新机器不会很贵吗？**

课堂指出，这种全互联设计的连接总量是平方级；若其他实现也用全互联 TCP，同样需要面对连接管理问题。这是架构比较，不是证明所有规模都没有代价。

另一个问题确认：对象 region、消息队列和日志都在内存中，只是用途和位置不同。讲师重新指向内存布局图区分这三类区域。

### 34:00–37:00 问答：硬件协调与 RDMA 完成确认

**问：网卡直接访问内存，是否需要 CPU／内存系统额外配合？**

答：需要相应的硬件接口和初始化设置。讲师用缓存行级访问说明网卡与内存系统的协作，但这里没有展开完整的原子性硬件规格。

同学再次确认 RDMA write 的含义：远端 NIC 把请求中的数据放到给定位置，不需要服务器应用先处理这个请求。

**问：那发送方如何知道写已经完成？**

答：接收端 NIC 可以发回硬件 ACK。后面的协议会利用这个区别：等网卡确认写入内存，与等应用处理日志，是不同的等待条件。

讲师用约数微秒的访问延迟说明 RDMA 的吸引力。不能把某个延迟的倒数当作多机器、多并发条件下的总吞吐。

### 37:00–40:00 真正的研究问题：服务器少运行代码，事务怎么办

前面主要是已有硬件技术。研究挑战在于：如何借助这些操作实现事务？过去的协议经常需要服务器检查锁、等待锁、验证状态或作出回复；RDMA 本身只提供较底层内存访问，不会自动替应用运行整套事务逻辑。

因此不能把传统事务代码里的每个 RPC 简单替换为一次裸内存读写。设计要决定哪些步骤必须让服务器执行，哪些步骤可以只依赖内存布局、版本和 NIC。

### 40:00–44:00 OCC 把检查推迟到提交

FaRM 的选择是先不锁读对象。读时同时带回对象版本，应用在本地计算并缓存写；提交时检查这些版本是否还有效。

若其他事务已经修改对象，版本变化就暴露冲突，当前事务中止，必要时等待一段时间再重试。若检查通过，才继续提交。

讲师用“先做、发现不该做再道歉”对照“先请求许可再做”的悲观策略。准确地说，这里的“先做”是事务内部计算，不是提前把未提交结果公布给别的事务。

### 44:00–48:00 从跨对象一致性问题进入 Figure 4

**问：版本号是每个对象独立的，如何防止先读一个对象、再读另一个对象时，中间有事务修改其中一部分？**

讲师转到 Figure 4，准备详细解释。图中 C 是 coordinator，实际由运行应用的机器承担；为便于讨论，可以把它想成独立客户端。三个 region 各有 primary 和 backup。

执行阶段读取三个对象，其中两个会修改，第三个只读。修改暂存在本地。提交阶段包括 LOCK、VALIDATE、COMMIT-BACKUP、COMMIT-PRIMARY 和后续 TRUNCATE；课堂重点放在前四步，截断用于清理日志。

### 48:00–51:00 LOCK 记录携带旧版本和新值

事务发起提交后，先联系写集合所在的 primaries。Figure 4 的不同线型代表不同通信：读对象是 one-sided RDMA read；写日志是 RDMA write。

LOCK 记录放入对象标识、执行时读到的版本、新值。协调者把它追加到对应 primary 的日志；primary 的线程轮询日志，才会发现并处理请求。

写日志不等于已经锁住对象。这里之所以还要等 primary 回复，是因为锁的判断和获取需要服务器代码执行。

### 51:00–54:00 锁冲突时中止，而不是排队等待

primary 尝试在正确版本上设置锁位，成功后用消息回复协调者。如果对象已被别的事务锁住，便回复失败；协调者中止本事务，释放已经获得的相关锁。

讲师把原子指令口头称作 test-and-set，强调两个核不能同时声称获得同一把锁。

> **论文校注：** 实际 §4 使用 compare-and-swap，把“版本仍等于读到的版本且未锁”原子地变成“该版本已锁”。不能只检查锁位，而漏掉版本比较；否则旧计算会覆盖已提交的新值。

### 54:00–57:00 问答：ZooKeeper 不管理每个对象的锁

**问：这些锁通过 ZooKeeper 取得吗？**

答：不是。ZooKeeper／CM 管理配置，事务对象的锁是 primary 内存对象头里的位。

**问：primary 崩溃时，backup 有同样的锁吗？**

讲师说会启动重新配置和恢复协议，稍后再讲容错；未完成的事务可能中止，不能只看当前 primary 的一个内存位判断最终结果。

**问：为什么不等待锁释放？**

因为应用早已依据旧读值完成计算。另一事务正在修改这个对象，等待后未必还能使用原计算。FaRM 选择立即中止、重跑。此处讲师把写锁全部取得的位置称作写部分的串行化点。

> **校注：** 遇到锁不意味着对方必然最后提交；立即中止是本协议的保守冲突策略，而不是证明所有等待型 OCC 都不可能正确。

### 57:00–60:00 VALIDATE 只读集合，避免额外写锁

对于只读不写的对象，也可以设想像写对象一样加锁，但这样要经过远端软件处理及回复。FaRM 改为再做一次 one-sided RDMA read，取得版本／锁位。

若对象被锁，或版本与执行阶段不同，就中止；若仍未锁且版本相同，则这次验证通过。图中的 region 3 只参加这类验证，不参加写锁阶段。

讲师把这一段描述为确认可以提交的关键时刻，并把版本与严格可串行化联系起来。

> **校注：** 每对象版本号不是跨对象的全局事务时钟。论文把成功读写事务的串行化点选在**全部写锁取得时**，随后验证证明读集合在那个点仍一致；不是把最后一次验证、提交决定和对外返回混成同一个点。见课程笔记 §2。

### 60:00–63:00 COMMIT-BACKUP：先让写数据遍布副本

通过锁和验证之后，协调者决定尝试完成提交。但目前新值只在 primary 日志里；若要容错，还要写入各 backup。

COMMIT-BACKUP 携带与 LOCK 对应的对象、版本、新值等信息。协调者用 RDMA write 放进每个 backup 的非易失日志，等待 NIC 的硬件 ACK；不必等待 backup CPU 应用这些更新。

收齐这些 ACK 后，所有相关 primary 和 backup 都拥有恢复该事务写入所需的数据。课堂图每个 region 两份，容忍一份丢失。

> **口误校注：** 此处字幕曾说成“f+1 failures”。一般规则是 **f+1 份数据副本容忍至多 f 份内容丢失**，且还受配置服务和存活条件约束。

### 63:00–65:00 COMMIT-PRIMARY 与对应用报告成功

随后协调者把 COMMIT-PRIMARY 记录写入各 primary 日志，记录包含事务 ID。前面的其他记录也具有事务身份，只是板书未逐处写出。

至少一个 primary 的 NIC 确认该记录已落入日志，协调者就可以告诉应用事务成功。课堂称这是“真正提交点”；要与之前的串行化点及提交决定区分。

primary 日后处理记录，才把新值写入对象、提高版本、解除锁。后续 TRUNCATE 清理日志，避免无限增长，通常可以附带在其他通信中完成。

### 65:00–69:00 问答：ACK 不代表已经执行，CAS 不能拆成普通读写

**问：硬件 ACK 直接回到协调者 NIC 吗？**

答：是；协调者从完成结果知道远端 RDMA write 已成功。

**问：这里“写已完成”是指进入日志，而不保证应用已经执行它？**

答：正确。backup 要在之后处理日志才能更新对象。

另一个问题指出，多核普通“读锁位、改成 1”会发生竞争。讲师再次强调原子指令：两次竞争操作不能同时成功。64 位版本／锁头便于作为一个整体操作，而不是在多个普通指令之间留下竞争窗口。

### 69:00–73:00 未决追问：验证后，别人还能修改只读对象吗

同学提出：第一笔事务通过 P3 的只读验证之后、真正完成提交之前，第二笔事务能否只修改 P3，并先完成？讲师最初尝试用写锁解释，但同学指出读 P3 并没有设置锁。讲师把问题暂留，准备通过实例讨论。

另一问是拿到锁后崩溃怎么办。课堂简答是恢复协议会清理这些状态；不能让锁永远留着阻止所有后续事务。

还确认了角色分工：coordinator 是运行应用事务的线程，正常提交中由它直接联系 primary 和 backup，不是 primary 每次再转发给 backup。重新配置／恢复有额外通信，图中尚未画出；precise membership 也未在本段展开。

> **问题边界：** 只读对象在验证后被别的并发事务修改，本身未必错误。不能从现场第一句“必须排除”推导读集合实际上暗中持锁；末尾问答重新澄清了重叠事务的排序。

### 73:00–75:00 不进入分组，直接列出加一事务的合法结果

讲师明确决定跳过 breakout room，直接带大家分析。这条录像并没有一段需要补写的分组讨论。

两笔事务 T1、T2 都执行读取 x、加一、写回，初始 `x=0`。什么结果合法？若都成功，最终应是 2；若只有一个成功，可能是 1；若都中止，也可以仍是 0。

关键是把最终值与事务返回结果放在一起看：不能让两者都报告成功，却只得到一个加一的效果。

### 75:00–78:00 同时读到零，锁与版本如何阻止丢失更新

假设 T1、T2 都读到同一版本的 `x=0`，都准备写 1。接着二者竞争 LOCK，只有一个能成功。

同学给出两种失败路径：若 T2 来得早，看到 T1 的锁，直接中止；若来得晚，T1 已经提交并解锁，T2 仍会因为版本改变而失败。讲师确认这正是关键。

失败者重新运行时，读取 `x=1`，才有机会提交 2。讲师因时间已到决定下一次继续第二个例子和容错，邀请需要离开的同学先走，其余留下提问。

### 78:00–81:00 课后问答：为何不把硬件配给悲观并发控制

**问：这套硬件也能帮助悲观并发控制吗？**

答：当然，更便宜的 RPC 仍有收益。OCC 特别吸引人的地方是只读事务：执行阶段读取，提交阶段验证，都可以只用 one-sided RDMA，不必把对象锁或日志写入远端。

讲师以图中只读的第三个对象解释，读不修改服务端状态，验证也只是读。对一般多对象只读事务，是每个对象相应的读取／验证操作，不是整笔事务恒定恰好两次网络访问。

随后再谈安全：RDMA 能访问内存看起来很危险，所以建立连接时必须限制 NIC 能访问的范围，由操作系统参与设置。课堂没有展开具体注册键或攻击模型。

### 81:00–83:00 课后问答：冲突多，读也会失败

**问：若写很多、争用严重，快读的优势还成立吗？**

答：冲突会让事务中止，读事务同样可能因为版本变化而失败。这套设计特别适合冲突较少的工作负载；作者用 TATP 和 TPC-C 展示了其效果。

讲师把它与乐观／悲观并发控制的长期研究联系起来。基准表现好，不等于任何长事务、任何热点对象都适合 OCC。

### 83:00–85:00 课后问答：日志不会互相覆盖，也没有全局消息到达顺序

**问：多个客户端同时 RDMA write，会把同一个日志位置覆盖掉吗？**

答：每个发送者／接收者配对有自己的日志，这正是这样设计的原因。

**问：事务顺序是不是依赖 TrueTime 那样的时间？**

答：这里使用逻辑版本和冲突控制，不使用 TrueTime。

**问：primary 有多条输入队列，该按什么顺序读？**

答：同一发送者队列保持顺序；不同发送者之间本来就是并发，协议不能依赖一个预先存在的全局收信顺序。primary 按某种轮询次序处理，锁和版本负责保证结果正确。

### 85:00–87:00 课后问答：locality hints 与长事务

**问：论文的 locality hints 是什么？**

讲师表示未现场查细节，但直觉是把经常一起访问的对象放到相同 primary／机器集合，避免一笔事务联络许多远端参与者。论文更具体的放置与恢复代价见课程资料 §1、§7。

同学问长事务是否不适合。讲师确认，执行时间越长，越可能遇到并发修改；只读占比高、冲突少的负载有利，但这些都是负载属性。

### 87:00–90:00 课后追问：短事务完全嵌在长事务里

同学重新组织先前问题：T1 先开始，写两个分片并读第三个；T2 后开始，只修改第三个对象 z，而且比 T1 更早结束。

讲师先分析 T2 在 T1 验证之前完成的情况：T1 保存版本 0，验证看见版本 1，就中止。提问者说自己真正关心的是反过来：T1 已验证旧版本，T2 才更新并完成，随后 T1 提交。

现场回答来回修改时间线，并一度把“回复前已更新对象”作为解释。

> **论文校注：** 成功回复的条件是 COMMIT-PRIMARY 的硬件 ACK，不是所有 primary 已应用。正确论证不能依赖这个口头说法；还没应用的对象仍有锁，后来的事务不能成功读取／验证出一个与已完成事务矛盾的历史。

### 90:00–92:00 现场没有立即完成图上证明

讲师准备重画图并把更完整例子留到下一讲。同学互相确认，讨论的正是 T2 插在 T1 验证与后续提交之间的情况；有人提出可以通过可串行化重新排序。

讨论随后聚焦到严格可串行化的“严格”究竟限制哪种先后。这里保留课堂的探索过程，不把暂缓解答改写成已经完成的形式化证明。

### 92:00–94:00 最后澄清：重叠事务不受完成顺序单独约束

讲师说明：如果 T2 **在 T1 已完成之后才开始**，T2 必须观察到 T1 的效果。但若 T2 从开始到结束都落在 T1 的执行区间内，两者是并发事务，串行历史可以把其中任意一个排前，只要整个历史一致。

同学意识到自己把“先结束”误当成“必须在串行历史里先执行”。双方确认理解，并把这个结论接回验证后的并发写问题。

> **校注：** 若 T1 读旧 z、T2 写新 z，且没有其他依赖迫使相反次序，可把 T1 排在 T2 前。允许的是一个符合全部依赖的完整事务顺序，不是每个对象各自选顺序。

## 第二录像：FaRM 续讲（独立时间轴 00:00–27:57）

### 00:00–02:00 重新进入事务协议，随后才转 Spark

开头 4.319 秒没有字幕。讲师问候并确认大家能听见，说今天先完成 FaRM，再讲 Spark。前一次已经讨论无故障执行和一个串行化例子，这次还要看涉及只读验证的例子及容错。

先重新看 Figure 4：执行阶段从三个 region 各读一个对象，其中两个需要修改；每个 region 有一份 backup。然后应用发起提交，进入后续阶段。

### 02:00–04:00 复习 LOCK 与只读验证的区别

LOCK 记录送往写对象所在 primary，携带对象标识、版本、新值。对象头的最高位是锁，其余为版本。

只读对象走单独的 VALIDATE。虚线表示 one-sided RDMA read，不要求远端 CPU 处理；相比之下，LOCK 虽用 RDMA 送入日志，仍需 primary 执行版本检查和原子加锁，再给出软件回复。

### 04:00–07:00 复习备份、提交证据与两条正确性主线

所有写锁取得、所有读验证通过后，协调者写 COMMIT-BACKUP，保证各 backup 有相应更新；然后写 COMMIT-PRIMARY，告诉 primary 该事务应提交。

收到至少一个 primary NIC 的确认后，应用得到成功结果。现在要分开检验两件事：并发控制是否产生严格可串行化结果，以及故障后这个结果能否保住。

### 07:00–09:00 交叉条件写：禁止 x 和 y 都变成一

同学先问 Figure 4 中矩形是什么意思，讲师答是对象数据。随后引入经典例子，初始 `x=y=0`：T1 看到 x 为零就设 y 为一；T2 看到 y 为零就设 x 为一。

若 T1 在前，最终只有 y 为一；若 T2 在前，最终只有 x 为一。两者都变成一没有对应的串行顺序。这个例子是检验理解的工具，不是完整正确性证明。

### 09:00–12:00 写锁都能成功，读验证仍必须打破环

假设两笔事务都先读到版本零。T1 先锁 y，再验证 x；这时 x 还没变化，验证通过。接着 T2 锁 x，准备验证 y。

讲师请同学判断验证是否成功。同学指出另一事务持锁／已经修改值，因此不应通过。讲师补充：即使 y 的版本数字尚未增加，锁位也已设置，T2 必须中止；若 y 后来已经解锁，版本变化同样会使验证失败。

结果不会让两笔基于“对方仍为零”的条件写都成功。这正说明为何不能仅在写集合上防止丢失更新，还要验证读集合。

### 12:00–14:00 问答：只有读的事务省掉哪些阶段

同学从“写是否必须先读”问到纯只读访问。讲师回到 Figure 4，把两个写对象移出写集合：若事务只有读，则执行时读对象，提交时验证，均可用 one-sided RDMA。

没有 LOCK、没有 COMMIT 日志、没有备份写。这也解释为什么 LOCK 和 VALIDATE 要分开，而不是对所有读取统一加锁。

### 14:00–16:00 未决追问：刚读完马上验证，是否多余

**问：纯只读事务读完就再次读版本，好像没必要；若有并发事务，难道不能把只读排在它之前吗？**

讲师先用后来读应该看到先前写来解释，同学指出自己的场景是并发。讲师承认没有仔细想过所有混合读写场景；若整个系统根本没有写，当然不需要冲突验证。

接着有人提出多对象原子读取：先读一个值，中间发生事务，再读另一个值。现场尚未把这个反例完整展开。

> **编者校注：** 单对象优化读确实不同于一般多对象只读事务。论文 §3、§6.2 明确提供前者；后者必须排除跨对象混合状态，不能删除验证。完整最小反例在课程笔记 §3，不把它冒充讲师当场已给出的答案。

### 16:00–18:00 未决追问：验证之后出现盲写

讨论回到条件写例子。有人把 T2 换成没有条件的 `x=1`，问如果它发生在 T1 验证 x 之后、T1 完成之前，T1 使用旧 x 是否有问题。

讲师说需要重新画出准确时间线，先留待课后。本录像后面没有出现这幅重画图，也没有保留一个完整续答。

> **编者校注：** 若事务重叠、其他依赖允许，可把读旧 x 的 T1 排在盲写 T2 前；T2 先返回不单独迫使反向排序。实际 FaRM 写协议仍要取得正确对象版本和写锁，“盲写”是业务层不使用旧值，不是绕开并发控制。

### 18:00–20:00 只读事务的用途与容错目标

**问：只读事务有什么实际用途？**

答：例如计算多个账户的余额合计，需要读取许多账户但不更新；TATP、TPC-C 等负载也有大量读取。

讲师总结，条件写例子说明 VALIDATE 的必要性，但仍不是完整证明。接着转容错，不逐项讲全部恢复协议，只检查最关键的承诺：协调者已经告诉应用成功，之后崩溃，也不能丢掉事务写入。

### 20:00–23:00 最坏残留组合：有的 region 只剩 LOCK

先看每一阶段留下什么。LOCK 后，P1、P2 保存新值，但 LOCK 本身不证明读验证通过。COMMIT-BACKUP 后，B1、B2 保存提交记录。至少 P1 再有 COMMIT-PRIMARY，协调者才向应用报告成功。

假设这时发生故障，B2 丢失，P2 还来不及收到 COMMIT-PRIMARY。region 2 可能只剩 LOCK；但 region 1 的 primary 和 backup 都有能证明提交路径的记录，至少一份会在容错范围内存活。

恢复可以结合“某处有有效提交证据”和“每个写 region 仍有新值”，完成整个事务。不能因为 P2 只剩 LOCK，就把全局已成功事务独立中止。

> **校注：** 讲师此处口头把更新数据主要说成来自 backups。更完整地说，数据也可能来自 surviving primary 的 LOCK；论文的投票规则及连续故障处理见课程资料 §5。

### 23:00–26:00 高性能的适用条件

讲师强调，实际恢复仍需复杂协议搜索、汇合和传播这些残留信息；课堂这里只建立“为什么有足够证据”的直觉。

最后总结限制：OCC 需要较少冲突才不会大量重做；整个数据集要放进 DRAM；复制局限在单个数据中心，无法替代 Spanner 的跨地域目标。数据太大又不愿增加内存机器，就需要别的存储路线。
