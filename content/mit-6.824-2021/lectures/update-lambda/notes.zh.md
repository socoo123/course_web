# AWS Lambda：把大镜像变成低延迟的按需数据

## 1. 核心问题：代码很小，为什么启动要搬很多东西？

一个事件处理函数可能只有几行，但它依赖解释器、标准库、第三方库、证书和配置文件。容器镜像把这些依赖一起封装，解决“在我的机器上能跑”的问题，却也把大量暂时用不到的数据带进部署包。

如果每次扩容都先下载并解包完整镜像，那么镜像越大、同时启动的实例越多，数据搬运就越容易成为瓶颈。Lambda 要解决的不是单台机器如何更快下载文件，而是：**许多互不信任的客户同时扩容时，如何只搬必要的数据，同时保持隔离、完整性和可恢复的性能？**

先区分四个对象：

| 对象 | 含义 | 何时变化 |
|---|---|---|
| 函数部署版本 | 一组代码、依赖及配置 | 发布或修改配置时 |
| 镜像 | 部署版本所携带的文件及其分层包装 | 构建新版本时 |
| 执行环境 / slot | 某个 worker 上承载函数的 MicroVM 环境 | 扩容、回收、故障时 |
| 调用 / invoke | 一次事件处理请求 | 每个请求都会发生 |

**一次调用不一定创建一个新环境，一次新环境也不一定下载一份完整镜像。** 这是后面一切优化的起点。

以下机制以 2023 论文为基线。2026 幻灯片补充 SnapStart 等学习线索；两者参数差异集中列在[课程资料 §1](#/c/mit-6.824-2021/lec/update-lambda?v=materials)。这些材料不是今日 AWS 配额、SLA 或功能支持矩阵。

## 2. 从数量级推导：减少数据，比加带宽更重要

设镜像大小为 $S$，每秒新增执行环境数为 $r$。完整复制需要的输入带宽至少是：

$$
B_{\mathrm{full}}=rS
$$

这还没有计算解包、重复写盘、协议和冗余的代价。假设启动实际只触及镜像的一部分，比例为 $f$，按需加载的理想搬运量才可能接近 $rfS$。

但 $f$ 不是一个固定产品参数。论文和幻灯片提到的 **6.4% 来自 Slacker 研究的启动平均值**，不是 Lambda 所有函数的测量结果，也不是所有函数都能只读 6.4%。比如一个启动时遍历全部模型权重的函数，启动工作集就可能接近整个模型。

真正有用的是三个不同维度的机会：

1. **稀疏性（sparsity）**：一个环境只读自己真正需要的块。
2. **共同性（commonality）**：不同函数、不同版本可能使用相同基础依赖；相同块可以去重。
3. **可缓存性（cacheability）**：突发请求可能反复启动少数热门函数；同一块可反复从近端读取。

它们不能简单乘成一个“固定加速倍数”。唯一块比例是上传侧统计，缓存命中率是访问侧统计，两者受数据热度相关性影响。一个独有但极热门的块也很值得缓存；一个被很多镜像引用、却从未被读取的块，对启动缓存几乎没有帮助。

### 2.1 工作集不等于镜像大小

可以把一段启动过程访问的块集合记为 $W_{\mathrm{start}}$；某次调用的额外块集合记为 $W_{\mathrm{invoke}}$。后者随输入和执行分支改变，镜像中“现在未读”的块，不等于以后永远不读。

整个 worker 的工作集又是多个环境在一个时间窗口内的访问集合之并，不能简单把每个镜像大小相加：共享块会重合，私有写入则不能这样合并。去重降低的是可共享部分的物理占用。

还有**块粒度放大**：应用只需要一个块中的少数字节，后端却可能取回整个块。论文采用 512 KiB chunk，不应把应用读了 4 KiB 就解释成网络只传了 4 KiB。大块减少请求和元数据，小块减少无用搬运及不相关内容被绑在一起的程度。

## 3. 把工作移出启动关键路径

### 3.1 调用路径与创建路径分开

2023 论文中的请求先到无状态 frontend：加载函数元数据、认证和授权，再向 Worker Manager 请求容量。Worker Manager 是有状态、具有粘性的容量管理和负载分配组件，跟踪各函数的已有环境及所在位置，并预测容量需求。

- 有可用环境：frontend 被指引把请求发给相应 worker。
- 没有可用环境：选择有 CPU、内存余量的 worker，先创建该函数的 sandbox，再执行请求。

因此，读镜像不应塞进每次调用的公共路径。更进一步，**解读容器各层的工作也不应在每次新建环境时重做**。

### 3.2 在发布时确定文件系统，在读取时提供块

容器镜像本来是有顺序的 tar 层，常规容器栈可以在运行时叠加这些层。论文把这一步提前到低频的函数创建阶段：

```text
发布阶段：镜像各层 → 确定性展平 → ext4 镜像 → 分块、加密、manifest → S3
运行阶段：guest 读块 → local agent → 本机缓存 / AZ 缓存 / S3
```

为什么强调“确定性”？如果相同文件因为并行写入顺序、分配顺序或修改时间不同而产生不同磁盘字节，内容哈希就会把它们视为不同块。论文使用串行、确定性选择相关参数的文件系统实现，让相同内容更有机会形成相同块。

这里要守住两个语义：

1. **层顺序的语义必须保留**：后层对前层的修改必须体现到最终镜像。
2. **只读基础镜像稳定**：发布后可共享的块不被某个运行实例直接改写。

确定性不是“不允许函数改变文件内容”；它约束的是部署镜像的构造。运行时写入有单独路径。

### 3.3 为什么选择块接口，而不是共享文件系统？

Lambda 的客户代码不可信。若在跨客户共享的宿主组件中处理复杂文件系统和 overlay 语义，攻击面会扩大。

论文保留 Firecracker 和 guest 之间较简单的 `virtio-blk` 接口，让 ext4 等文件系统操作留在 guest 内。外部只需回答“某个偏移处的块是什么”。应用和 guest 可以继续把它看成普通磁盘，实际内容则按需补齐。

“透明”指应用读到的文件语义不需要因远程加载而改写，不表示没有网络等待、不需要隔离，也不表示系统已经形式化证明了整个存储栈。

## 4. 一次读、一次写分别发生什么？

### 4.1 读路径：别遗漏 guest 自己的缓存

论文的新环境有一个公共 root block device，另一个设备由 per-function local agent 提供。MicroVM 启动监管组件和客户代码后，读取大致经历：

1. 应用访问文件，guest 内核先处理文件系统语义；guest page cache 命中时无需进入远端加载链。
2. 未命中的块读经 `virtio-blk` 到 Firecracker，再经论文实现中的 FUSE 路径交给 local agent。
3. local agent 根据镜像 manifest 定位 chunk；基础镜像的数据可从本机共享缓存读取。
4. 本机缺失时尝试 AZ 级共享缓存；再缺失则由 worker 从 S3 origin 拉取，并填充缓存。
5. 数据必须经过相应完整性检查和解密，才能作为预期镜像内容交回 guest。

因此，论文的 L1/L2/L3 是 **chunk 加载体系**，不是所有缓存的总清单。guest page cache 还在其前面；AZ 缓存内部也有内存和 flash 两级。

### 4.2 写路径：共享基础层，私有覆盖层

如果两个环境共享同一 chunk，A 直接覆盖共享 chunk，B 就可能看到 A 的修改。这不仅破坏镜像不可变性，还可能跨越隔离边界。

论文把写入放进该环境的私有 block overlay，底层是 worker 上的加密存储；以页粒度位图记录数据应来自 overlay 还是基础镜像。

由此可以提炼出一个读取不变量：

$$
\operatorname{Read}(p)=
\begin{cases}
\operatorname{Overlay}(p), & p\text{ 已被私有写入覆盖}\\
\operatorname{Base}(p), & \text{否则}
\end{cases}
$$

若只写一页的一部分，未修改字节也必须保留，因而需要读—改—写。页粒度写时复制与 512 KiB 的远端 chunk 粒度是两个不同层次。

**反例**：只保存某次小写入的几个字节，却把整页标成 overlay 有效。下次读取同页的其他位置时，返回的就不再是原始内容。位图的含义必须和实际持有的数据范围一致。

这是论文解释存储虚拟化的机制，不是“今日所有 Lambda 应用目录都可写”或“本地写入跨环境持久”的产品承诺。

## 5. 去重以后，信任边界放在哪里？

去重产生一个矛盾：希望相同块只存一份，又不希望所有 worker 都拿着可解开全部客户数据的主钥匙。

普通的“每客户随机密钥加密所有内容”会使相同明文产生不同密文，失去直接去重机会；而“全系统共享一把密钥”把故障和泄露范围放得太大。

论文的思路是分离两层：

- **数据层**：由块内容及去重域相关元数据确定性派生 chunk 密钥，使同一域内的相同块产生相同密文。
- **授权层**：客户的 manifest 记录需要哪些 chunk 和相应密钥；密钥表由客户专属的 KMS 管理密钥保护，manifest 整体受认证。

读者应把 manifest 理解成“经过认证的镜像地址空间与取数能力的组合”，而不只是文件名列表。缓存中的密文可以共享，授权读取和解密的范围仍应受函数放置及密钥分发控制。具体密码模式、命名顺序和 GC 可见字段见[课程资料 §3](#/c/mit-6.824-2021/lec/update-lambda?v=materials)。

### 5.1 三个不能互相代替的保证

| 保证 | 要回答的问题 | 不能由什么单独推出 |
|---|---|---|
| 隔离 / 保密性 | 谁能获得不属于自己的明文？ | “块有哈希”不能代替授权和密钥隔离 |
| 完整性 | 收到的是否是 manifest 指定的内容？ | “能解密”不等于内容未被恶意替换 |
| 可用性 | 需要时能否及时取得正确内容？ | “损坏能检测”不等于损坏能修复 |

一个被篡改的 chunk 被拒绝，维护了完整性，却可能让所有依赖它的函数读失败。去重越充分，一块的故障可能影响越多人。

论文用可变化的 salt 控制去重域：相同明文跨不同 salt 不再共用密文。salt 可随时间、热门程度和基础设施位置变化，主动牺牲部分去重率，缩小故障影响范围。它不是替代 KMS 的权限机制；论文把轮换主要作为运维控制，而非安全成立的必要条件。

也不要把“由内容导出密钥”当成通用保密方案：已知相同内容的一方可能本来就能推导其内容密钥。完整安全论证还依赖系统暴露哪些接口、谁拿得到受保护元数据等。这里学习的是该系统的组合边界，不自行承诺它消除了所有内容确认或侧信道风险。

## 6. 为什么缓存也需要冗余？

“缓存丢了可以回源，所以只存一份就够”遗漏了性能可用性。

单份缓存至少带来三个问题：一个节点慢会拖慢很多请求；节点重启使一批对象突然回源；一个热门块的吞吐受单节点带宽限制。即使 S3 中的数据未丢，启动延迟仍可能显著变坏。

### 6.1 小概率慢请求，在多块启动中很常见

做一个独立、同分布的简化模型：单块超过某个延迟阈值的概率为 $p$，一次启动必须读取 $n$ 个块。那么至少遇到一个慢块的概率为：

$$
P(\text{至少一个慢块})=1-(1-p)^n
$$

取 $p=0.001$、$n=1000$，结果约为 63.2%。单请求的 p99.9 尾部并不意味着“一千次启动才遇到一次”。真实请求存在相关性，这个公式用于解释尾延迟放大，不能直接当生产预测器。

### 6.2 4-of-5：用少量冗余跳过一个慢分片

2023 论文的缓存将一块编码为五个 stripe，任意四个足以重构。读时请求五个，收到四个有效结果即可继续。

- 与无冗余的四分片相比，存储从四份分片变成五份，即增加 25%。
- 请求数也从四次变成五次，增加 25%；不是“相对单对象一次 GET 只增加 25%”。
- 在分片分散且其余四份可读的前提下，可以绕开一份缺失或迟缓的分片。

这不是共识 quorum：没有多个副本争论“哪个版本最新”。这里处理的是不可变内容，阈值来自编码能否重构。它也不意味着任意多个节点故障、整个 AZ 故障都能被这层解决。

论文强调 **constant work**：正常情况就发送固定的冗余读取，在可容忍的故障下沿用这一路径，减少失败后追加大量重试所造成的负载跳变。它不是“全系统永远执行同样的 CPU 指令”，也不消除回源或超出编码容忍范围的故障处理。

2026 幻灯片写的是 “Any 4 of 6”。学习原理时两者都是阈值重构，但容量代价和容错数量不同；不得把幻灯片参数套进论文 25% 的计算。

## 7. 高命中率为什么可能导致恢复更困难？

设整体缓存命中率为 $h$，正常回源流量只占 $1-h$。突然全空时，相对于正常回源量的放大倍数为：

$$
A=\frac{1}{1-h}
$$

若用 $h=99.8\%$ 举例，放大是 500 倍。这里的分母是**正常回源流量**，不是所有调用数，也不是“系统整体慢 500 倍”。

论文说 S3 能承受该系统完全未缓存的流量，但这仍不够。原因是反馈回路：

```text
缓存变冷 → 读变慢 → 请求占用环境更久 → 并发需求增大
       → 需要更多新 slot → 工作集及加载压力变化 → 缓存更难恢复
```

Little 定律 $L=\lambda W$ 在稳定平均意义下提示：请求率 $\lambda$ 不变、每请求停留时间 $W$ 增大，所需并发数 $L$ 就会上升。它不直接预测崩溃过程，却解释了“下游还没压垮，整个系统已经难以恢复”的可能性。

论文的对策是在上层限制并发；启动变慢、并发达到上限时拒绝新启动，让在途工作先完成，并测试最大允许并发下从空缓存恢复的能力。这是在保护系统重新进入正常状态的机会，代价是部分新工作被拒绝。

**反例**：为保持表面成功率而无限排队、无限重试。队列占用资源，重试继续制造工作，反而可能让最初的短暂事件变成持续故障。

### 7.1 不只是容量，还要防止缓存被一次性工作冲掉

大量小时级、日级定时任务可能各自只用一个 sandbox，却在同一时刻访问很多冷块。普通 LRU 只认最近一次访问，会让这些一次性读驱逐经常复用的块。论文采用记录最近 $k$ 次访问的 LRU-k 来抵抗扫描污染；没有给出一个适用于所有负载的固定 $k$。

缓存大小要同时满足成本和延迟：保留一个块的成本可以与未来重新读取的成本比较，但满足成本最优的容量未必能满足延迟目标。工程上取这两种要求所需容量的较大者。关于淘汰、定容与代际回收的完整细节见课程资料 §4–§5。

## 8. 从磁盘块到内存快照：少做初始化，仍要补齐状态

容器按需加载减少的是数据搬运；程序自身的初始化、类加载或其他计算仍可能很昂贵。2026 幻灯片把思路延伸到 SnapStart：预先完成初始化并保存快照，以后从快照恢复多个环境。

不要混淆三个概念：

- **warm reuse**：继续使用一个已有执行环境。
- **按需镜像加载**：让一个新环境只拉取实际读到的磁盘内容。
- **snapshot restore**：从此前保存的机器状态恢复，避免再次做相同初始化；内存内容也可按需加载。

幻灯片提到 `userfaultfd`，即让用户态程序处理缺页事件：触及尚未驻留的内存页时，装入对应内容再继续。它提供接入点，不代表网络 I/O 或校验成本消失。

由快照复制状态还引出一个编者思考题：如果初始化时生成的随机状态或身份标识被多个副本直接复制，什么属性会失效？可能是每实例唯一性或随机序列独立性。幻灯片给出相关论文入口，但未展开修复协议；本讲不据此编造当前 SnapStart 的具体实现或产品兼容范围。

## 9. 用反例检查是否真正理解

| 说法 | 错在什么地方 |
|---|---|
| “镜像只读 6.4%，所以所有函数都快约 16 倍” | 把其他研究的平均值当成每函数常数，还忽略初始化、缺页与粒度放大 |
| “有相同基础层，就一定得到相同 chunk” | 展平布局、元数据、分块位置和 salt 都会影响最终内容或密文 |
| “L2 命中 99.9%，所以 99.9% 的所有读都由 L2 服务” | 条件命中率的分母是到达 L2 的请求；guest 与 L1 已先拦截大量读取 |
| “数据有认证，就不会不可用” | 认证拒绝损坏内容，不负责生成缺失的正确内容 |
| “缓存不持久，故障无所谓” | 回源延迟与并发反馈可能损害整个系统的服务能力 |
| “4-of-5 是多数派，所以能决定最新版本” | 纠删码阈值不是一致性协议的投票规则 |
| “图上是毫秒，所以测的是用户冷启动” | 必须先看测量点；local agent 读延迟并非完整启动延迟 |

若每个版本只发布一次，却启动十万次，把展平从每次启动挪到发布阶段，改善了什么？代价是什么？

<details><summary>展开答案</summary>

消除了重复解释层结构和构造文件系统的工作，也把确定性构造与去重放进低频控制路径。代价是发布需准备派生镜像、chunk 和元数据，系统也必须正确管理它们的生命周期。它没有保证每次调用都完全不用等待数据。

</details>

### 题 2：两个相同 chunk 的使用者为什么不必共享客户主密钥？

<details><summary>展开答案</summary>

相同去重域内内容可得到相同 chunk 密钥与密文，但不同客户各有受其 KMS 管理密钥保护的 manifest 密钥表。共享的是数据表示，不是解开其他客户 manifest 的主密钥。实际授权仍依赖谁能获得相应 manifest 和密钥。

</details>

### 题 3：如何计算命中率？

假设一个统一观测窗口中，10,000 次 chunk 请求有 6,700 次 L1 命中；剩下 3,300 次里 L2 命中 3,297 次。求 L2 条件命中率和总体回源比例。

<details><summary>展开答案</summary>

L2 条件命中率为 $3297/3300\approx99.909\%$；总体回源比例为 $3/10000=0.03\%$。L2 服务的总体比例为 32.97%。这是人为构造的同窗口例子，不能用它要求论文中不同分布的中位数刚好相加或相乘吻合。

</details>

### 题 4：为什么不把所有缓存预算都用于更多唯一块？

<details><summary>展开答案</summary>

没有冗余可以容纳更多唯一块，却更依赖单节点的可用性、吞吐和尾延迟。纠删码牺牲部分有效容量，换取绕过少量慢或失败分片的能力。最优取舍必须同时考虑命中率、读取成本和尾延迟。

</details>

### 题 5：回源能成功，为什么仍要拒绝一些新启动？

<details><summary>展开答案</summary>

回源成功不等于回源足够快。变慢提高并发占用，可能进一步触发新环境创建及工作集膨胀。并发上限防止在途工作无限增长，使有限资源能完成已有工作并重建缓存。

</details>

### 题 6：哪条信息不足以证明一个新性能结论？

有人引用幻灯片中的一条 CDF，称“2026 全部 Lambda 冷启动 p99 已降到 2 ms”。应要求补什么？

<details><summary>展开答案</summary>

必须确认测量对象、计时起止、样本负载、部署范围、单位、时间窗口和比较基线。单次缓存读取或 local agent 延迟不是整次冷启动；一张无完整实验说明的图也不能变成全产品承诺。

</details>
