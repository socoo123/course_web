# L2：把并发和 RPC 的边界想清楚

## 1. 一次请求有三种不同的“完成”

调用一个函数很容易产生错觉：函数返回，工作就完成了。但并发与网络让这句话分成三个问题：

1. **本地控制流是否完成？** 启动 goroutine 的函数可以先返回，工作仍在后台。
2. **远端状态是否改变？** RPC 没收到回复，不代表服务器没执行。
3. **调用者是否知道结果？** 服务器完成写入、回复却丢失时，真实结果和客户端知识不同。

本讲的共同方法是：先明确共享状态、完成条件和通信约定，再选择 mutex、channel 或 RPC。语法不会自动提供这些约定。

goroutine 是 Go 运行时调度的执行流，不等于“一条独占 CPU 的操作系统线程”。它能在网络等待时让其他工作推进，也可能被调度到不同 CPU 核心并行执行。**并发是组织方式，并行是执行方式。** 更深入的结构设计见 [L10 笔记](#/c/mit-6.824-2021/lec/lec10?v=notes)。

## 2. 锁保护的是一个不可拆开的判断

两个执行流都执行 `n++`，不代表最终增加 2。若都先读到 0，再各自写回 1，就丢失了一次更新。即使某次运行输出 2，也不能证明没有数据竞争。

爬虫的重复抓取问题更能揭示锁的范围：

| 时刻 | A | B |
|---|---|---|
| 1 | 读到 URL 尚未领取 | |
| 2 | | 读到 URL 尚未领取 |
| 3 | 标记已领取，开始抓取 | |
| 4 | | 标记已领取，也开始抓取 |

只分别保护一次读和一次写，仍可能出现这个交错。需要原子化的是**检查并领取**，而不只是 map 的单次访问。

可以将不变量写成：每个 URL 最多有一个执行流从“未领取”改为“已领取”。检查与更新必须使用同一把锁；`Fetch` 这样的慢操作移到锁外，否则一个网络等待会阻塞其他 URL 的领取。完整课堂走读见[中文译稿 45:00–48:00](#/c/mit-6.824-2021/lec/lec02?v=draft)。

另一个易混淆点：代码字段叫 `fetched`，但它在实际 `Fetch` **之前**变成 true，表达的是“已经尝试／领取”，不是“抓取成功”。失败后不再重试是这个教学爬虫的选择，不能直接当成生产爬虫的完成状态机。

## 3. 互斥解决安全，等待解决推进

投票示例维护 `count`（赞成数）和 `finished`（已返回数）。实验性目标是“收够 5 票，或者 10 个请求全部返回”。这里的 5 是示例阈值，**不是十节点 Raft 的严格多数**。

从这个停止条件反推等待谓词：

$$
\text{继续等待} \iff count < 5 \;\land\; finished \ne 10.
$$

锁让读取两个计数与修改两个计数互不交错，却不会让等待者自动休眠。用一个循环不停加锁、检查、解锁，会忙等；加固定 `Sleep` 则在额外延迟与唤醒开销之间折中。

条件变量把这两个问题接起来：

- **状态才是真相**：是否能继续由上述谓词决定。
- `Wait` 需要在持锁时调用；它将释放关联锁与进入等待协调起来，返回前重新取得锁。
- 更新者在锁保护下改变状态，并通知等待者重新检查。
- `Wait` 放在 `for` 中，因为一次通知可能只意味着又收到一票，离目标还很远；其他等待者也可能先改变状态。

`Broadcast` 不保存“已经达成目标”的事实，也不等待接收者来接通知。若目标早已达成，新来的等待者应通过检查状态直接继续。反过来，**先无锁检查、再单独去睡**可能错过检查与入睡之间的通知。

课堂六个文件的演变及实际问答见[中文译稿 21:00–41:00](#/c/mit-6.824-2021/lec/lec02?v=draft)。归档中的 `vote-count-6.go` 收完全部十个结果，避免第 5 版提前停止接收造成的发送者滞留，但会放弃“够票便提前返回”的响应速度；课堂没有逐行讲解第 6 版。

## 4. 用所有权消除共享，不是用 channel 掩盖共享

channel 版爬虫让 coordinator 独占 `fetched` 和计数 `n`。worker 只抓取网页、送回链接列表。于是 map 不需要锁，因为只有一个执行流访问它。

推理 `n` 时，不要只说它是“goroutine 数”。更精确地说，它是**尚未消费的结果份数**：

- 起始 `n=1` 对应装有初始 URL 的种子消息；
- 每派出一个新 worker，`n` 加一；
- 每消费一份结果，`n` 减一；
- 失败 worker 也必须发送一份空结果，否则计数永远无法归零。

当一份结果中的新链接都已处理，且 `n=0`，才没有未来工作会从已派出的任务中产生。这里对完成的证明依赖“每个 worker 恰好回报一次”，不是依赖“channel 眼下为空”。

多个 worker 可以同时 `Fetch`，即使 coordinator 每次只接一份结果。串行化短小的调度决策，不等于串行化昂贵的网络抓取。

channel 自身可以安全地被多个 goroutine 使用，**发送的对象却不因此自动变成深拷贝**。若传递 slice，双方仍可能指向同一个底层数组。安全的交接需要发送前写完、发送后不再并发修改等所有权约定。完整例子见中文译稿 48:00–52:00。

## 5. 为每个 goroutine 写下退出理由

投票 channel 版在收够 5 票后停止接收；剩余发送者可能永远卡住。`main` 结束会让整个进程退出，掩盖这个泄漏；把相同代码搬进长寿命服务器，问题就暴露了。

对每个后台工作问三件事：

1. 正常情况由谁接收它的最后一个结果？
2. 调用者提前返回时，它还能否结束？
3. 哪个事件宣布以后不会再发送／接收？

WaitGroup 适合等待一批工作的结束，但要在启动工作前登记 `Add`，并在所有返回路径配对 `Done`。它不保护工作内部的数据。条件变量、结果缓冲、继续排空结果或协作取消各解决不同约束，不能只靠“再开一个 goroutine”修复退出问题。

## 6. RPC 像函数调用，失败语义却不同

调用路径是：客户端封装参数 → RPC 库编码 → 网络 → 服务端分派 → handler → 回复编码 → 客户端解码。2021 `kv.go` 使用 `net/rpc`、TCP `:1234` 和 `KV.Get`／`KV.Put`；2026 Lab 2 的测试 RPC 接口、方法名和 Put 参数均不同。

至少区分两层结果：

- **传输层**：是否收到可用回复；
- **服务层**：收到的回复表示成功、键不存在，还是版本不匹配。

例如，收到了 `ErrNoKey` 仍是一次成功完成传输的 RPC。没有收到回复则可能是请求丢了、处理尚未完成、服务器执行后崩溃，或回复丢了。

| 语义 | 能承诺什么 | 不能推出什么 |
|---|---|---|
| 至少一次 | 在服务最终可达等推进条件下，持续重试可使操作执行 | 效果只发生一次 |
| 至多一次 | 某个逻辑操作的效果不超过一次 | 操作必定执行；调用者必定知道结果 |
| 恰好一次效果 | 重试、重复抑制与故障恢复共同维护一个效果 | 永久分区时仍保证及时返回；普通 RPC 库天然具备此性质 |

2021 讲义进一步讨论 XID、缓存回复、回收去重信息、正在执行的重复请求以及崩溃后的去重状态；课堂 63:00–67:07 只做概述，不能把这些内容说成逐项讲过。上述是通用机制，**本路线 Lab 2 不要求引入按客户端增长的去重表**，它用键版本约束写入，并通过 `ErrMaybe` 暴露不确定性。

进入 [Lab 2 指导](#/c/mit-6.824-2021/lab/kvsrv?v=guide)前，先读[线性一致性笔记](#/c/mit-6.824-2021/lec/update-linearizability?v=notes)：RPC 的交付次数与服务的外部一致性规格是两个层次。

## 7. 自测

### 同一个锁分别保护“检查”和“写入”，为什么仍会重复领取？

<details><summary>展开答案</summary>

两段临界区之间释放了锁，另一个执行流可以插入并同样读到“未领取”。需要让检查与改变状态组成一个不可分割的事务式决策。没有数据竞争不代表没有逻辑竞争。

</details>

### `Wait` 被唤醒后能否直接宣布收到足够票数？

<details><summary>展开答案</summary>

不能。通知只说明值得重新检查。应在重新持有同一把锁时再次检查计数谓词，不能把通知次数当成票数。

</details>

### 一次 RPC 超时以后，可以向用户报告“写入失败，状态未变”吗？

<details><summary>展开答案</summary>

不能。服务器可能已修改状态，只是回复丢失。必须遵守上层 API 对不确定结果的约定；2026 Lab 2 还有明确的重发后 `ErrVersion` → `ErrMaybe` 规则。

</details>

### race detector 没报错，是否就证明程序正确？

<details><summary>展开答案</summary>

不是。它检查实际执行中缺乏同步的冲突访问；没有覆盖的路径、死锁、重复逻辑任务或错误的停止条件仍可能存在。默认保留 `-race`，同时用不变量推理。

</details>
