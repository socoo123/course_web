# L16 课程笔记：何时可以保存配方，而不复制每份结果

## 1. 先分清权威状态与可重算状态

本讲最重要的问题是：**一台机器丢失内存后，哪些信息必须幸存，才能重新得到原结果？**

在复制 KV 中，用户的一次新写可能是系统里唯一的新信息；不能仅靠一段固定程序推导出它。因此要让写的证据、日志或数据副本可靠保存。

RDD 中间结果不同：若输入已可靠保存，转换及其参数确定，结果可以从配方重建。内存保存结果是为加速，而不是唯一的真相来源。这并非“不要持久化”，而是把可靠性责任移到稳定输入、计算配方以及必要的 checkpoint 上。

| 对象 | 主要作用 | 丢失后的可能办法 |
|---|---|---|
| 稳定输入 | 原始事实 | 依赖输入存储自己的容错；RDD 不能凭空造回输入 |
| lineage 与闭包参数 | 怎样计算 | 必须仍可获得；配方也丢了则不能保证恢复 |
| 普通缓存分区 | 避免重复计算 | 从可用祖先或输入重算 |
| shuffle 物化结果 | 阶段间交换与恢复边界 | 可读则复用，丢失则补上游缺失任务 |
| 可靠 checkpoint | 截短昂贵的重算路径 | 从选定版本继续恢复 |

与 [Raft](#/c/mit-6.824-2021/lec/lec05?v=notes)、[FaRM](#/c/mit-6.824-2021/lec/lec15?v=notes) 相比，差别首先是数据模型与失败后要保住的承诺，而不是谁“更先进”。

## 2. 可重算不变量：同一版本的名字必须指向同一结果

把一个分区的结果表示成

$$
R_{i,p}=F_{i,p}(P_1,\ldots,P_k;\theta),
$$

其中 $P_j$ 是确定的父版本/分区，$\theta$ 是代码、闭包捕获值、随机种子、分区规则等。恢复需要保持这些输入不变，才可把同名分区的丢失视为“缺了一个可重新算出的副本”。

### 2.1 反例：重试时重新读墙钟

若函数给每条记录加“当前时间”，第一次与第二次执行会产生不同值。RDD 对象本身再不可变，也不能让一个不确定的函数自动确定。类似地，读取一个后来被覆盖的外部文件，或忘记保存随机种子，都破坏了恢复前提。

可行方向是把影响结果的状态明确成为输入版本或固定参数；论文 sample 保存分区随机种子就是一个具体例子。这里只推导前提，不声称 Spark 会自动检查所有用户函数。

### 2.2 反例：map 里给账户扣款

task 因超时重跑，内部纯计算可以重做；已经向外部数据库发出的扣款却可能再次发生。lineage 恢复不等于对任意外部副作用提供 exactly-once。

这与实验中的重复 RPC、请求身份是同类“重试可否改变结果”的问题，但本讲没有提供替代幂等、去重或事务提交的通用机制。

## 3. 三个图的粒度不要混成一个

1. **RDD lineage：** 数据版本之间通过什么转换产生。
2. **分区依赖：** 一个输出分区需要哪些父分区，父分区是否向多个子分区分发。
3. **执行图：** 哪些转换合为 stage，哪些分区 task 在哪些 worker 执行。

程序中一行 map 生成新 RDD，不一定对应一个独立远程阶段。一个 RDD 框中的单箭头，也不能证明内部是窄依赖。某个 stage 可以在很多分区上并行，每个 task 内再用 iterator 串接多个转换。

源代码中的循环也不意味着 lineage 有环：第 t 轮产生 $ranks_t$，下一轮产生另一个 $ranks_{t+1}$。变量重新赋值与修改旧数据不是同一件事。

课堂图解及学生关于 DAG 的追问见[中文译稿 44:00–53:00、74:00–78:48](#/c/mit-6.824-2021/lec/lec16?v=draft)。

## 4. 窄依赖的正确判据：问父分区要服务几个子分区

**不要把“一个子分区有两个输入”当作宽依赖的充分条件。**

对某项父子 RDD 关系，给父分区 p 定义使用它的子分区集合 $C(p)$。论文窄依赖的条件是

$$
\forall p,\quad |C(p)|\le 1.
$$

这没有要求一个子分区最多只能读一个父分区。共分区 join 可以读左右两侧各一个父分区，仍满足每个父分区只交给对应输出分区。

宽依赖常见于按新键重分区：某父分区内的记录分别属于多个输出桶，因此下游需要 shuffle。其代价不只是字节流量，还有阶段边界、最慢上游的等待以及失败后的依赖扩散。

同分区不等于永远同机。partitioner 描述“键应该去哪一个分区”，实际节点位置与调度、缓存、故障恢复有关。因此窄依赖使局部流水线成为可能，却不是绝不联网的契约。

完整原页依据、join 的一窄一宽情况，见[课程资料 §4](#/c/mit-6.824-2021/lec/lec16?v=materials)。课堂 20:00–23:00 和 65:00–71:00 的争论没有解决定义问题，正文不继承其中的一对一说法。

## 5. PageRank 的优化必须逐条数据路径检查

每轮可以分为三件事：

| 步骤 | 使用的键 | 能否因 links/ranks 共分区而免去 shuffle |
|---|---|---|
| 链接表与当前 rank 做 join | 源 URL | 可以避免为这次 join 重新分区 |
| 沿出边生成贡献 | 从源 URL 改成目标 URL | 本地生成即可，但输出已不再遵循源键布局 |
| 同目标 URL 的贡献求和 | 目标 URL | 一般仍需跨分区汇聚 |

**反例：** u1 与 u2 在不同机器，但都指向 u3；u3 的新 rank 必须合并两处贡献。无论 links 与 ranks 在各自源键上如何对齐，这次信息汇合都不能凭空省略。

控制 partitioning 的收益是：把贡献聚到目标应在的位置后，下一轮可直接与那里的 links 连接，不再额外打乱一次。不要把“省了一次 shuffle”扩写成“所有迭代都无通信”。

图结构 links 适合多轮内存复用；ranks 的 checkpoint 则控制长 lineage 恢复成本。缓存谁、可靠保存谁，答案可能不同。算法数值的 $\alpha/N$ 与讲义缩放约定见课程资料 §3.3，课堂实例不在本页重复推演。

## 6. 缓存与 checkpoint 优化的是两张不同的账

### 6.1 缓存：平时要不要重复做同一工作

设一个中间结果有 k 次使用，每次重算成本 C，缓存读成本 L，首次额外保存成本 P。忽略淘汰与内存机会成本时：

$$
T_{recompute}=kC,\qquad
T_{cache}=C+P+(k-1)L.
$$

于是缓存有利的粗略条件为 $(k-1)(C-L)>P$。这只是编者的决策模型：k=1 时，没有跨次复用收益；热门但很便宜的数据也未必值得挤掉昂贵数据。真实执行还受并行度、内存大小、I/O 与倾斜限制。

FAQ 用单次扫描聚合作业说明这一点：支持更多算子不保证每个 MapReduce 作业在 Spark 上都显著更快。

### 6.2 checkpoint：失败后从哪里恢复

普通 cache 丢了还能重算，但如果要跨几十轮宽依赖才能重建，恢复可能很慢。checkpoint 用正常路径的可靠写出，截断这段计算历史。

因此评估一个候选边界，应问：保存的数据量多大？失败时可跳过多少计算？哪些祖先其实仍活着？恢复能并行到什么程度？不能只按“每十轮”或“最大 RDD”机械选择。

论文的自动选择是研究方向，不是已完成的通用策略。其内存保存选项也不等价于 HDFS checkpoint；完整实现与命名差异见课程资料 §5–6。

## 7. 容错范围：配方能恢复结果，但不能恢复不存在的配方

worker 丢失缓存，有稳定输入和 lineage 可补算；driver/scheduler 连同唯一 lineage 都丢失，则不是同一问题。2012 论文明确尚未容忍 scheduler failure，不能拿“RDD 是 resilient”推导整个系统无单点。

同样，某宽依赖下游丢失，不意味着全部上游立即作废。应从所需分区向上检查：存活物化结果、缓存、checkpoint 都可停止回溯；只有缺失且需要的部分继续重算。

与 [Memcached](#/c/mit-6.824-2021/lec/lec17?v=notes) 的对照也有帮助：两者都有缓存，但 Memcached 缓存外部可变数据库结果，必须防止过期回填；RDD 缓存固定版本的纯转换结果，不需要用 delete 把同一版本“更新成新值”。可变权威源若未纳入版本边界，RDD 的简单性同样会消失。

继续学习 [Ray](#/c/mit-6.824-2021/lec/update-ray?v=notes)时，可追问任务粒度、对象依赖、可重算性和控制面的存活条件。Ray 的 Ownership 论文在该专题独立精读；本讲的 RDD 阅读仍限定于 Spark。

## 8. 自测

### 题 1：调用 persist 后，为什么第一次 count 仍然很慢？

<details><summary>答案</summary>

persist 标记保存意图，并未立即执行。第一次 action 仍需读取输入和计算分区，随后才有可复用缓存；后续查询是否更快还取决于分区是否仍在内存。

</details>

### 题 2：一个输出分区读取 A0 与 B0，就一定是 wide 吗？

<details><summary>答案</summary>

不是。共分区 join 可以如此，每个父分区只服务对应的一个输出分区。应检查父分区向子分区的扇出，而非仅数子分区的入边。

</details>

### 题 3：links 与 ranks 使用相同 hash，PageRank 还要通信吗？

<details><summary>答案</summary>

通常要。join 的重新分区可省，但跨源网页指向同一目标的贡献仍须汇聚。hash 对齐没有消除 Web 图的跨分区边，数据放置变化也可能带来读取通信。

</details>

### 题 4：RDD 不可变，为什么每轮 ranks 还能更新？

<details><summary>答案</summary>

更新的是程序变量的指向；每轮生成新 RDD。旧版本不原地变化，lineage 连接不同版本，所以图仍可为 DAG。

</details>

### 题 5：逻辑回归与 PageRank 都有循环，是否都在最后 collect 才开始算？

<details><summary>答案</summary>

不是。论文逻辑回归每轮用 reduce 求梯度，这是 action，当轮就必须计算后才能更新 w。只有纯 transformation 构成的链才会继续延迟到后续 action。

</details>

### 题 6：丢一个宽依赖的输出分区，是不是所有祖先都必须重跑？

<details><summary>答案</summary>

不一定。回溯所需父分区，遇到可用的 shuffle 输出、缓存或可靠 checkpoint 就可复用。长宽依赖链可能扩散重算，但“可能”不是“必然全部重跑”。

</details>

### 题 7：函数每次用新随机种子，还能保证重算得到同一分区吗？

<details><summary>答案</summary>

不能。必须把种子等影响结果的状态纳入配方。论文 sample 按分区保存种子；不可变只读接口不会自动把任意用户代码变成确定性代码。

</details>

### 题 8：links 比 ranks 大，是否应优先给 links 做可靠 checkpoint？

<details><summary>答案</summary>

不一定。links 可以从稳定输入经短链重建，ranks 可能依赖很多轮全局汇聚。缓存价值与故障恢复价值是不同指标，不能只按尺寸判断。

</details>

### 题 9：论文展示 worker 故障恢复，能推出 driver 故障可恢复吗？

<details><summary>答案</summary>

不能。2012 实现明确尚不容忍 scheduler failure。lineage 需要仍然可得；课堂“也许重新连接”的说法属于未核实推测。

</details>

### 题 10：把 HDFS 放进内存，是否就得到与 RDD 同样的性能？

<details><summary>答案</summary>

不一定。文件系统栈、内存复制、校验、反序列化与作业控制开销仍在。论文 Figure 9 专门拆出这些成本；具体收益随算法每字节计算量变化。

</details>
