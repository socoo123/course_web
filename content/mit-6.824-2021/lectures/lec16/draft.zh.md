## 02:00–05:00 内存复用与这堂课的历史范围

短暂停顿后继续。如果程序需要做一轮 MapReduce，再把结果交给下一轮，然后再做下一轮，Spark 可以把中间结果留在内存，并提供相应的编程支持，避免轮轮写出、重新读取。

## 05:00–08:00 一个 RDD 可以先只是“怎样得到数据”的描述

从论文中的日志分析例子开始。用户可以启动 Spark，以交互方式输入命令。第一步定义 `lines`，它代表 HDFS 文件中的各行。文件很大，分散在多个分区；例如第一批记录属于 P1，下一批属于 P2。

输入这行定义时，还没有把整个文件读入集群、处理所有记录。此时得到的是一个 RDD 对象，说明数据在哪里、怎样取得它。这就是惰性计算：真正工作推迟到需要结果的时候。

RDD 的操作大体分两类：transformation 描述从一个 RDD 得到另一个 RDD；action 才触发计算，例如 `count` 或 `collect`。RDD 本身只读、不可变，转换不会原地改写已有数据集。

## 08:00–12:00 过滤日志，标记复用，再把转换串成流水线

第二步对 `lines` 过滤，只保留以 `ERROR` 开头的行，得到新 RDD `errors`。此时仍然只是积累配方，形成 lineage graph，即数据如何由前面的数据产生的依赖图。

等真正开始运行时，读取和过滤不必先把整份中间数据写成文件。可以读取一些记录，马上交给过滤，再继续下一批；后面还有转换时，就继续向下传递。讲师用流水线描述这个过程。

调用 `errors.persist()` 表示，希望这份错误日志在计算出来后留在内存，供后续查询复用。它并不立即触发计算。以后继续分析同一批错误信息，就不必每次从 HDFS 重读全部日志，再重复过滤。

这已与多次独立 MapReduce 作业不同：作业之间若通过文件系统交换结果，要付出重新读取等成本；这里让跨查询复用成为编程模型的一部分。

## 12:00–14:00 问答：分区并行、lineage 与事务日志

**问：P1 和 P2 中的错误日志能并行提取吗？** 可以。调度器把不同分区的任务交给不同 worker；各 worker 可以同时处理自己的分区。讲师同时提到流水线中的并行直觉，后面会进一步区分。

**问：lineage 与以前见到的事务日志，区别只是操作粒度吗？** 讲师说，事务日志通常按线性顺序记录操作，而 lineage 可以分叉、合并，一个转换可能依赖多个 RDD。两者都有“从开始状态按确定性操作恢复结果”的相似性，但不是同一种结构或协议。

**问：filter 可以各分区独立做，join、sort 呢？** 它们更复杂，稍后讨论。

**问：persist 是开始计算的时刻吗？** 不是。当前还都是描述，必须等到 action。

## 17:00–20:00 driver、worker 与分区任务

用户程序运行在 driver 上，driver 构建计算描述并与集群协作；调度器知道 lineage，安排 worker 处理输入文件的分区。分区数量通常多于 worker 数量，这样一台机器做完较小分区后还能继续领取任务，减少由于工作量不均而闲置的情况。

在日志例子中，读取、两次过滤和字段提取，都可以在单个输入分区对应的流水线上完成。不同 worker 同时跑各自的分区任务，不必在每个简单转换之间交换全体数据。

最后的动作需要汇总各分区结果。`collect` 将元素返回应用，`count` 汇总数量；它们的返回内容不同。讲师在图上描述等待分区结果并做最终汇合。

## 20:00–23:00 窄依赖与宽依赖：学生指出定义方向的问题

讲师借 MapReduce 类比：有些步骤只依赖本地父分区，可以直接向下计算；另一些需要汇集不同分区的信息，往往涉及网络通信。他把前者称为 narrow dependency，后者称为 wide dependency。

**问：论文说的是“每个父 RDD 分区最多被一个子 RDD 分区使用”，没有说“一个子分区最多使用一个父分区”，对吗？** 学生准确指出两个方向并不等价。讲师先确认，又继续用“子分区需要多个父分区就是宽依赖”的直觉解释，并用 count 类比；同时承认 count 是 action，不是另一个 RDD。

学生再次强调，论文文字允许多对一，并没有规定一对一。讲师暂时没有厘清，决定稍后返回这个问题。

> **校注：** 学生的方向性疑问成立。窄依赖的论文定义约束父分区向子分区的扇出，不等于严格一对一。共分区 join 就可让一个输出分区依赖两个输入 RDD 的对应分区。不能把任意 action 的汇总直接当作 RDD 间 shuffle dependency 的形式定义。课后 65:00–71:00 继续此问答；准确解释见课程资料 §4。

## 23:00–26:00 问答：不 persist 会怎样，初始分区从哪里来

**问：不调用 `errors.persist()` 呢？** 下一次独立查询需要重新从初始文件构造 `errors`，重复前面的读取与过滤，而不是自动复用上一查询的所有内存结果。

**问：MapReduce 会保存本地中间文件，Spark 不 persist 的中间结果也会保存到持久存储吗？** 讲师将一般路径概括为在内存中传递，并提到可以要求可靠保存，把选定数据集写到 HDFS，形成 checkpoint。

**问：初始分区是 HDFS 决定的，还是 Spark 决定的？** 对这个文件 RDD，初始划分来自文件系统中的数据块与文件布局。Spark 也允许重新划分数据，甚至给出自定义 partitioner；后面的 hash partitioning 会说明好处。

> **实现边界：** “全部在内存”是课堂简化。论文 §5.1 明确将 shuffle 中间记录物化在父分区所在节点以简化恢复；§5.3 有磁盘保存选项。普通 persist、shuffle 物化和可靠 checkpoint 是三件事。论文还分别使用 `RELIABLE` 与 `REPLICATE` 两种历史 flag 名称，不能据此构造现代 API 使用说明。

## 26:00–30:00 worker 失败：丢失的是可重算分区

现在考虑 worker 崩溃：它的内存与当前计算状态消失，下游仍可能需要它所负责的分区。调度器发现任务没有返回，可以在其他 worker 上重新执行相关阶段。

这类似 MapReduce 重新执行 map 或 reduce 任务，但这里的任务可能是一串转换。输入相同、转换具有确定性，就能再次生成相同输出。RDD 的不可变性正好与这个思路配合。

**问：这就是 RDD 不可变的原因吗？** 是，这是重要原因之一。这里的容错对象是分析计算 worker 的中间数据，不是前面 Raft/复制 KV 实验中任意客户端写入的持久状态；不能省略两者的输入假设区别。

对窄依赖，只需沿丢失分区对应的祖先向回找，并行重算所需部分。下一步看依赖横跨多个分区时的麻烦。

## 30:00–33:00 宽依赖让一次失败影响更多祖先

假设某一步需要多个 worker 的父分区，随后又经过一些转换。下游 worker 失败，要重建其结果，便可能需要重新获得多个父分区。如果这些中间数据也不可用，就必须继续向上重算。

不同祖先可以并行恢复，但一次机器故障仍可能触发大量计算，尤其是很长、包含宽依赖的计算链。不是只把最后那个函数重跑一次就一定够了。

程序员可以在合适位置做 checkpoint，把某个 RDD 可靠保存。此后恢复可以从 checkpoint 读取分区，不必一直追溯到起始输入。这是用正常执行时的写出成本，换取失败后的较短恢复路径。

## 33:00–35:00 问答：缓存不等于可靠检查点

**问：普通 persist 与 reliable flag 有何区别？** 课堂解释，普通 persist 主要为了把 RDD 留在内存供后续复用；checkpoint 则可靠写出，例如写到 HDFS，worker 失败后仍可从那里恢复。

**问：后面的计算再也不用某个已缓存 RDD，能主动释放吗？** 讲师推测可以，但没有现场给出接口；他提到内存不够时可能移除或写出某些数据，并承认不确定具体策略。应用和 driver 退出后，这些内存自然也不再由本应用保留。

> **论文补充：** §5.3 实际明确给出 RDD 级 LRU 淘汰、避免同一个 RDD 分区循环替换的规则和 persistence priority；这里不把口头“可能溢写到 HDFS”升级为已经确认的统一实现策略。具体细节集中在课程资料 §5。

## 35:00–38:00 PageRank：适合展示复用的迭代例子

下面用 PageRank 说明 Spark 的长处。PageRank 根据链接关系衡量网页重要性；来自重要页面的链接，对被指向页面的排名有贡献。讲师回顾它与早期 Google 搜索排序的关系。

小图有三个网页 u1、u2、u3。u1 指向自己与 u3，u2 指向自己与 u3，u3 指向 u1。讲师在随后讲解中补上遗漏的边。

论文中的程序先描述计算，最后需要结果时才执行。这里与前面日志例子一样：建立 RDD 依赖关系不意味着已经运行整个集群作业。

## 38:00–41:00 links 不变，ranks 每轮产生新版本

`links` 按网页记录出边列表：u1 对应 `[u1,u3]`，u2 对应 `[u2,u3]`，u3 对应 `[u1]`。课堂只有三个网页，真实输入却可能有数十亿网页，必须分区存放。

另一个 RDD `ranks` 存当前排名。例子把各网页初始值设为 1.0。`links` 被标记为 persist，因为每一轮都要使用同一份链接结构，而各轮 `ranks` 会变化。

每轮先 `links.join(ranks)`：根据 URL 连接，让同一网页的出边列表与当前 rank 出现在同一记录里。比如 u1 的结果带有它的两条出边以及 r1。join 的目的不是把任意两行拼起来，而是按相同键匹配。

## 41:00–44:00 平分出边贡献，再按目标网页求和

接下来 flatMap 遍历各网页的出边，把当前 rank 平均分给每条边。u1 有两条出边，所以产生 `(u1,r1/2)` 与 `(u3,r1/2)`；u3 只有一条出边，产生给 u1 的全部 r3。

然后 `reduceByKey` 按目标 URL 聚合，把所有指向同一网页的贡献相加。u1 接到自己的一半及 u3 的全部贡献，即 $r_1/2+r_3$。再经过更新公式，产生下一轮 `ranks`，形状仍是每个 URL 对应一个排名数值。

课堂把这些记录口头称为 triples，但描述出的贡献实际是二元组“目标 URL、数值”。公式归一化、悬挂节点和完整算法边界没有在此展开；不能把这个教学片段当成任意 Web 图的完整实现。

## 44:00–47:00 循环展开成增长的依赖图

若用多轮独立 MapReduce 实现，每轮结束把结果写出，下一轮再读入；`links` 也要反复参与计算。Spark 可以复用内存中的链接数据，并让中间结果交给后续计算。

看 Figure 3：`links` 建立后被多次使用；rank 的各个版本依次连接。虽然源代码写了循环，图里不是一条回边，而是不断增加新 RDD：ranks0、contribs0、ranks1、contribs1……旧 RDD 不被改写。

讲师开始讨论 join 可能需要跨机器收集两侧数据，但这取决于输入的分区方式。若两侧布局相配，可以省下重复重分区。

## 47:00–50:00 相同 partitioner 让 join 更局部

对 `links` 与 `ranks` 使用相同的键分区方式，例如把 URL 哈希到分区，那么一个 URL 的链接列表与 rank 就能安排在相应位置处理。u1 的两条记录在同一个分区位置，u2、u3 同理。

这来自数据库常见的分区连接优化。调度器看到两侧已有兼容 partitioner，不必再为 join 做全体数据重新分布。讲师把它描述为原本宽依赖的 join 可以变成窄依赖。

同时，迭代次数增加会拉长恢复路径；因此可以考虑每若干轮对 ranks 做 checkpoint，例如每十轮一次。这只是说明取舍的示例，不是 Spark 固定规定的周期。

> **物理位置校注：** 相同 partitioner 确定的是键到分区的映射；要把 join 完全变成本地读取，还需要调度与数据放置配合。故障重调度后不能仅凭 hash 相同就断言两个分区永远在同一台机器。

## 50:00–53:00 问答：复用、并行，以及一个不能照抄的结论

**问：links 每轮都重算吗？** 不用，它是明确 persist 的那一份。各轮 ranks 则是新 RDD；可视恢复成本偶尔可靠保存，但不必把每个中间结果都永久缓存。

**问：不同分区的 contribs 能并行算吗？** 可以。讲师再次区分不同分区在不同 worker 上运行，与一条流水线内部的转换衔接。

**问：如此一来，只有最后的 collect 才是宽依赖了吗？** 讲师在约 51:45 给予肯定，并说明最后需要收集所有分区。

> **关键校注：** 这个回答若用于整个 PageRank 计算，会误导。相同 partitioner 只消除了 `links.join(ranks)` 的重新分区；flatMap 把源 URL 的记录改成目标 URL 的贡献后，`reduceByKey` 一般仍须跨分区汇聚。不能推导“整个迭代只在最终 collect 通信”。原字幕确认了这段问答，本文保留并校正，而不是将它悄悄删去。

讲师总结，显式数据流让系统有机会利用分区、局部性、内存复用和并行性，既改善性能，又比固定的 MapReduce 两阶段模型更能表达多步计算。

## 55:00–57:00 课后问答：自动 checkpoint 在优化什么

**问：论文说可利用计算耗时自动选择 checkpoint，这到底在优化什么？** checkpoint 自己消耗时间与存储带宽；不做 checkpoint，失败后又可能从头重算。频繁保存虽然缩短重算，却可能让大部分时间耗在写检查点上。

所以要权衡正常执行成本与故障恢复成本。很昂贵的计算值得保留，小检查点可以更频繁；PageRank 的 ranks 每页一个数，面对巨大的 Web 图仍然可能很大。每十轮只是例子，周期需结合数据量和重算代价。

> **状态校注：** 论文 §5.4 把自动选择仍写作正在研究的方向，当时由用户指定；这段是在解释优化目标，不是展示已经实现的自动算法。

## 57:00–60:00 课后问答：driver 故障未明，哈希分区再解释

**问：driver 在客户端一侧，若它崩溃，整张图不就丢了吗？** 讲师承认不确定具体行为，推测 scheduler 也保存信息、也许能重新连接。字幕中关于 scheduler 容错的语句本身含混。

> **版本校注：** 指定的 2012 论文 §5.1 明确说其实现尚不容忍 scheduler 故障。不能用这句课堂推测给论文添加 driver/scheduler 高可用保证；2021 具体实现也未在本任务中查证。

另一名学生要求详细解释 hash partitioning。讲师画两份带键的数据集，使用相同哈希函数把 k1、k2 等放到对应桶。两份数据的相同键落在对应位置，连接时只需处理配对分区，不必再次向全体机器寻找匹配记录。

## 60:00–61:00 哈希桶不是“消灭所有图边通信”

学生把它理解为把相同键分到同一台机器，讲师确认。还有人问哈希函数是否需要保证计算不依赖另一机器上的链接，讲师继续从相同键的匹配角度回答。

这里的保证针对两份数据中同键记录的连接，不是说 Web 图的任意出边都留在同一台机器。不同 URL 的贡献传播仍是另一项工作，不能与 join 的局部性混在一起。

先前提出窄依赖定义疑问的同学准备回到论文原文；讲师先问其他人是否还有问题。

## 61:00–64:00 课后插问：FaRM 提交以后，恢复必须留下证据

有学生回到 FaRM：失败发生在决策点之前是否总是中止，之后是否由恢复机器再问 coordinator？讲师说明，不是简单等故障机器回来逐个重新询问。恢复过程会处理、排空相关日志，根据系统中留下的状态决定提交还是中止。

最关键的要求是：**一旦 coordinator 已告诉应用事务提交成功，系统里必须留有足够证据，使恢复流程仍然决定提交。** 这些证据来自相应日志记录、backup 提交记录与 primary 的提交记录。

**问：某个 primary 尚未收到 COMMIT-PRIMARY 就失败呢？** 讲师解释，如果已有足够 backup 证据，恢复仍可完成提交，不一定必须从失败 primary 获知决定。

**问：若失败的是 backup？** 可以利用仍存活的 primary 提交信息以及其他数据/日志副本完成恢复。这里讲的是先前 FaRM 协议中的证据组合，不能简化成“看见任意一条记录就提交任意事务”。

## 64:00–65:00 FaRM 的故障预算不因恢复而消失

学生继续问是否必须先选出新 primary。讲师用“把 recovery process 看作处理这项工作的角色”解释，并说不确定是否在这一步显式提升 primary。

**问：所谓足够 backup 是多少？** 课堂回到 $f+1$ 副本、容忍 $f$ 个故障的设定；每个相关分片必须仍有可用副本。在画出的 $f=1$ 示例中，不能把两份相关副本都丢掉后仍期待恢复。

> **跨讲边界：** 这里保留真实插问，不把讲师对角色切换的简略口述当成完整 FaRM 重配置协议。FaRM 的复制、日志与恢复阶段见 [L15 课程资料](#/c/mit-6.824-2021/lec/lec15?v=materials)。

## 65:00–68:00 再读论文定义：多对一为什么不必然是宽依赖

回到 Spark，师生打开第 6 页 Table 3 下方的定义。学生重复指出：每个父分区最多被一个子分区使用，不意味着每个子分区只能使用一个父分区。

讲师先画 map 的一对一关系，再画多个父分区进入一个子分区。学生指出，根据文字定义，后一种多对一关系仍可能是窄依赖，并举共分区 join：输出分区确实读取两边的父分区。

讲师承认 join 是这样的例子，但一度怀疑原句有笔误。双方并未立刻达成形式化一致。讨论还提到，实现某个转换的人需要向框架提供依赖信息，调度器依据这些信息判断执行方式；不是只看源代码中画了多少个箭头。

## 68:00–71:00 争论没有消除定义差异，正文保留并校正

学生建议把多个子分区也画出来：如果同一父分区的记录会被多个下游分区使用，那就明确是宽依赖。讲师补图，双方同意这类一对多/多对多情形属于宽依赖。

但对于只有一个子分区的多对一关系，讲师仍倾向于把“需要多个来源/通信”称为 wide，甚至概括 narrow 为一对一。学生表示，自己主要困惑于这与论文文字之间的差异；最后讨论以承认文本容易令人困惑结束。

> **定点核验结论：** PDF 第 6–7 页的定义、共分区 join 图与实现说明相互一致，没有证据支持把该定义判成笔误。判别应按每个父分区被多少子分区依赖，而非把“子分区有多个父亲”当充分条件。窄依赖也不绝对等于零网络传输：丢失、本地性未满足时仍可能远程取数据。此处是课堂未澄清的概念边界，不能写成学生已接受一个正确的一对一定义。

## 71:00–74:00 课后问答：流水线不是为每个函数单开并发任务

师生短暂谈到阅读难度：FaRM、Spanner 是本学期较复杂的论文。随后有人问，除了不同分区并行，同一条链上的转换怎样并行？

讲师重新找图，先把一串转换作为 stage：调度器对不同分区运行这样的 stage，各 worker 之间是真正并行的。

stage 内部则是流水式处理：读一批记录，经过 filter 留下较少记录，再交给下一步，不必先完成整份 RDD 才进行下一个简单转换。讲师随后特意弱化“同时执行”的说法：这些转换未必真正并发，而是以 pipeline 方式衔接。它不意味着每个 filter 都对应一个独立线程或远程任务。

学生说这澄清了批量传递的直觉。这里的批次是课堂解释方式，论文还给出逐元素 iterator 串接；不能仅据此推定固定批大小或多线程实现。

## 74:00–76:00 使用过 Spark 的学生追问 DAG 与 RDD

另一名学生说自己实习时使用过 Spark，未来工作还会用，这堂课帮助理解了背景。讲师笑说，本讲未必直接教会写 Spark 程序，重点是系统机制。

学生问：Spark 会构造任务的有向无环图，那么 RDD、task 和图里的依赖是什么关系？讲师先纠正名称，应该说 narrow/wide dependencies，而不是 narrow/wide partitions。

接着准备重新画图区分数据与计算。不能把“一个 RDD”“一个任务”“一条依赖”当成三个可互换的名字。

## 76:00–78:00 RDD 是分区集合，箭头是转换关系

讲师画出 RDD 内部的多个分区，再画下一份 RDD。RDD 之间的箭头表示转换；每次转换产生新的 RDD。执行时，调度器再据此形成阶段与分区任务。

仅在 RDD 层级画一根箭头，无法看出具体分区之间是怎样连接的。图上看起来都是单箭头，不代表都是窄依赖；必须了解操作、partitioner 与分区依赖。

讲师再次用最后的汇总说明“图中一根箭头可能代表多来源工作”。这个解释帮助区分图的粒度，但仍须遵循前面对 action 与 RDD 依赖的校注。
