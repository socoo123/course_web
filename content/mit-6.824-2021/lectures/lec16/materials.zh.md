# RDD 论文精读：用可重算的数据抽象换取高效共享

## 1. 问题不是“磁盘太慢”，而是多次计算怎样共享数据

**摘要、§1–2.1，PDF 第 1–2 页。**

MapReduce 与 Dryad 让程序员不用亲自处理每个 worker 的任务分配和故障，却没有提供一个足够通用、可控的分布式内存共享抽象。跨作业复用数据，常见办法是先写入可靠文件系统，再由下一作业读出：这同时带来复制、磁盘 I/O、序列化和反序列化成本。

论文关注两类复用：迭代算法反复扫描同一训练集或图结构；交互分析对同一筛选结果提出多个临时查询。Pregel、HaLoop 等专用系统分别优化某种计算形状，RDD 则把“选择保留什么、如何分区、接下来做什么”直接交给程序表达。

RDD 是**只读、分区化的记录集合**，通过稳定输入或其他 RDD 上的确定性转换产生。其身份不要求所有分区此刻都已物化；保存构造它的 lineage，就能在需要时计算，丢失时恢复。

这里有一个交换：不提供任意位置的细粒度原地写，而提供 map、filter、join 等对大量记录应用同一操作的粗粒度转换。这样可记录“做过哪个转换”而不是为每个值的修改记录日志。它没有解决所有共享内存问题，而是选择了适合批量分析的接口。

## 2. 只读限制省掉了什么，又没有省掉什么

**§2.2–2.4，PDF 第 2–4 页；Figure 1、Table 1。**

### 2.1 可复用，不等于把整个输入永久搬进内存

日志例子的课堂过程见[中文译稿 05:00–26:00](#/c/mit-6.824-2021/lec/lec16?v=draft)。论文 Figure 1 更值得注意的是：真正选择保留的是过滤后的 `errors`，不是原始 `lines`。如果错误只占原始日志的小部分，就可以用少得多的内存支撑许多后续查询。

第一次 action 使相关分区计算出来，随后将标记持久化的分区保留。再查询这份数据时，调度器可以直接从已有分区出发。若其中一个 errors 分区丢失，只需重新过滤对应原始分区；它不是一个只能“整体读入或整体失效”的巨型数组。

### 2.2 Table 1：写的限制，换来恢复与调度的自由

| 比较维度 | RDD 的选择与收益 | 必须保留的边界 |
|---|---|---|
| 读取 | 可批量，也可以将只读集合用于细粒度查询 | 不等于只有整表扫描一种接口 |
| 写入 | 粗粒度转换生成新版本 | 不是可任意并发修改的共享地址空间 |
| 一致性 | 同一 RDD 版本不可变，副本不会被独立写成不同版本 | 用户函数和外部输入仍需满足重算前提 |
| 失败恢复 | 重建缺失分区，不必让整个程序回滚 | 长宽依赖链可能使重算范围很大 |
| 慢任务 | 可以启动备份任务，接受其中一个结果 | 对外部系统有副作用的任意代码不因此获得 exactly-once |
| 放置 | 按数据局部性调度任务 | 局部性是优化目标，不是永远同机的公理 |
| 内存不足 | 扫描式工作可以用磁盘分区，逐渐降速 | 不保证所有访问形状都无性能 cliff |

不可变不是“变量永远不能重新赋值”。程序中的变量可以在不同迭代指向不同 RDD；lineage 记录的是各个数据版本。论文脚注也指出，用带版本数据集描述相同思想是可行的。

反过来，Web 服务的细粒度异步写、增量爬虫不断更新共享状态，不是这篇 RDD 模型的强项。数据库、RAMCloud、Percolator、Piccolo 有其他接口取舍；本论文没有证明把它们都改写成 RDD 就更好。

## 3. API、闭包与两种迭代模式

**§3，PDF 第 4–6 页；Figure 2–3、Table 2、两组算法公式。**

### 3.1 driver 构图，worker 处理分区

Figure 2 中，driver 是用户程序，构造 RDD 并调用 action；长寿命 worker 可以跨操作保存 RDD 分区。论文实现采用 Scala，是因为它表达简洁、有静态类型，并能把闭包作为 Java 对象序列化到其他节点。RDD 抽象本身并不要求函数式语言。

闭包不只包含函数体，还要携带捕获的变量。例如创建 `map(_ + x)` 时若 x 是 5，论文说明保存当时的捕获值，后续 x 变化不应让这份转换偷偷变成另一配方。这是确定性重算所需的环境边界之一。

Table 2 的重点不是背一张现代 API 表，而是识别结果类型：

- map、filter、flatMap、sample、union、join、cogroup、crossProduct、sort、partitionBy 等生成 RDD；sample 明确是确定性采样。
- groupByKey 与 reduceByKey 面向键值记录；mapValues 只改值，并保留分区信息。
- count 返回数目，collect 返回元素序列，reduce 返回聚合值，lookup 对已分区 RDD 按键找值，save 写外部存储。这些属于 action。

不能把 collect 翻成计数，也不能因为所有 action 都“拿到结果”，就认为它们有相同的流量和 driver 内存需求。

### 3.2 逻辑回归：缓存大训练集，driver 更新小参数

课堂主要展开 PageRank，论文还给出逻辑回归。训练数据经过解析形成 `points` 并 persist；每轮使用当前权重向量 w 计算各样本梯度贡献，reduce 求和，driver 更新 w。

将样本写为 $(x,y)$，论文代码中的梯度贡献可重写为

$$
g(x,y;w)=x\,y\left(\frac{1}{1+e^{-y(w\cdot x)}}-1\right),
\qquad w\leftarrow w-\sum g(x,y;w).
$$

这里保留论文示例的更新尺度，没有凭空补入学习率或正则项。它说明的是数据流结构，不是一份完整训练工具。每轮 reduce 是 action，所以**不是所有含循环的 Spark 程序都等到循环结束才计算**。PageRank 的惰性链与这个例子要分别看。

### 3.3 PageRank：图结构与每轮数值的生命周期不同

Figure 3 中，links 是固定图结构，各轮 ranks 是新版本；程序变量可变，RDD 不可变。论文使用归一化形式：

$$
r_{t+1}(v)=\frac{\alpha}{N}+(1-\alpha)
\sum_{u\to v}\frac{r_t(u)}{d^+(u)}.
$$

式中 N 为网页数量，$d^+(u)$ 为 u 的出度；对无出边节点还需要额外约定，论文短代码没有展开一般 Web 图的全部处理。

2021 讲义给出的 SparkPageRank 示例则以各节点 1.0 起步，并用 `0.15 + 0.85 * sum` 更新。对课堂三节点、均有出边的封闭小图，它是总和为 N 的缩放分数，不是总和为 1 的概率。讲义十轮输出约为 u1=1.739、u2=0.261、u3=1.000，合计 3。这与论文的 $\alpha/N$ 形式不能不加解释地拼成同一数值约定。

讲义还有 distinct、groupByKey、cache、spark-shell 和本地运行命令，提供从每行一条边构造邻接表的具体路线。现有视频字幕只逐步讲解论文例子，没有记录执行这些命令后的屏幕结果；本包没有运行它们，也不把讲义输出说成视频演示。

links 往往比 ranks 大，因为每页有许多出边但只有一个 rank；然而 links 能直接从稳定输入通过较短 lineage 重建。因此值得可靠 checkpoint 的，反而可能是较小但 lineage 很长的 ranks，而不是“把内存里最大的对象全备份”。

## 4. 依赖方向是这篇论文最容易读反的地方

**§4，PDF 第 6–7 页；Table 3、Figure 4。**

### 4.1 五项接口让调度器不必认识每种操作的业务含义

Table 3 为 RDD 暴露五种信息：有哪些 partitions；各分区 preferredLocations；对父 RDD 的 dependencies；怎样用父分区迭代器计算本分区的 iterator；以及描述 hash/range 分区方式的 partitioner。

以 HDFS 文件为例，分区对应文件块，preferredLocations 提供块副本所在节点，iterator 负责读取；map 沿用父分区与局部性，iterator 在读出的记录上应用函数。调度器只需要通用依赖与放置信息，不必为日志过滤、网页排名分别写一套调度算法。

union 拼接两边的分区集合，**不去重**；sample 保存每个分区的随机种子，才可确定性重放。实现这些转换不能只保存“我曾调用 sample”而不保存决定输出的参数。

### 4.2 看父分区的扇出，而不是只看子分区有几个输入

论文的窄依赖定义是：**对于这项父子 RDD 依赖，每个父分区最多被一个子分区使用。** 宽依赖则允许一个父分区的数据进入多个子分区。Figure 4 的共分区 join 很明确：输出一个分区可以读取左、右两个父 RDD 的对应分区，这仍是窄依赖。

设左侧 $A_0,A_1$、右侧 $B_0,B_1$ 使用相同 partitioner，连接得到 $C_0,C_1$：

$$
C_0=join(A_0,B_0),\qquad C_1=join(A_1,B_1).
$$

每个 C 有两个输入，但 A0 只供 C0，B0 也只供 C0，没有要求 A0 分发给所有 C。于是两项依赖都可为窄依赖。这直接反驳“子分区输入数大于一，所以一定 wide”。

一个普通未预分区的 groupByKey 则可能在 A0 内同时遇到属于 C0、C1 的键，因此要按目标桶拆分数据。需要 shuffle 的判断来自这种分区级关系，不来自 RDD 图上箭头的数量。

### 4.3 join 甚至可以一边窄、一边宽

论文第 7 页给出的三种情形是：两侧使用相同 partitioner，可有两项窄依赖；两边都不具备所需布局，可有两项宽依赖；只有一侧已合适分区，则可能一窄一宽。不能把 join 这个函数名永久分类成“必然 wide”。

hash partitioning 让同一键归入相应分区；还要通过调度与放置实现同机处理。故障后搬迁数据、远程读取缓存，仍可能有网络通信。因此“窄依赖允许局部流水线”比“窄依赖绝对不会用网络”准确。

### 4.4 PageRank 每轮仍需把贡献送到目标键

同分区 join 连接的是“某源网页的链接列表和该源网页 rank”。随后 flatMap 把键改成目标 URL，同一个源分区可以产生发往不同目标分区的贡献。reduceByKey 仍要把相同目标的贡献汇合。

论文第 6 页“把贡献聚到保存链接的位置，再计算新 rank 并连接”的描述，省掉的是**聚合之后再次为 join 打乱布局**，不是取消沿图边传播贡献。课堂 51:00–53:00 的“只剩最终 collect 是 wide”需按此校正。

## 5. 执行与存储：不是每条箭头一个任务，也不是所有内容只在 RAM

**§5.1–5.3，PDF 第 7–8 页；Figure 5–6。**

### 5.1 从 lineage 到 stage，再到分区 task

action 到来时，scheduler 回溯 lineage，尽量把窄依赖转换合在同一 stage 内。shuffle 是重要边界；已经计算并缓存的分区则可截断上游工作。每个阶段再产生处理缺失分区的 task。

Figure 5 中 A 通过 groupBy 产生 B，B 已在内存；另一支 C 经 map 到 D，再与 E union 成 F，最后 B 与 F join 得到 G。要计算 G，不必再跑生成 B 的 Stage 1，而是计算所缺的 Stage 2 和 Stage 3。E 里也有已缓存的分区，图中的黑色小块是在标记可复用的数据，不是“任务正在运行”。

实际任务选择考虑局部性：优先已有内存分区所在机器，其次 preferredLocations，并采用 delay scheduling。stage 内 iterator 可以把一个元素经过多个转换后再读下一个，避免每一步物化整份中间 RDD；不要求为每个转换创建独立线程。

### 5.2 shuffle 中间记录有物化边界

论文 §5.1 明确说：wide/shuffle 依赖的中间记录物化在父分区节点，以简化恢复，类似 MapReduce 的 map 输出。丢失任务时，如果父阶段数据仍可用，直接重跑；若部分上游 shuffle 输出丢失，再并行补算相应缺失分区。

所以“丢一台机器后所有祖先必然重算”过强；“只需重跑最后一步”又过弱。实际边界由缺失的分区、仍存活的物化结果和 checkpoint 共同决定。

论文当时的实现约 14000 行 Scala，运行于 Mesos，复用 Hadoop 输入接口。**同一节明确说尚不容忍 scheduler 失败。** 这限制了“lineage 可以恢复一切”的说法：恢复配方本身也必须存活。课后对 driver 重新连接的猜测没有改变论文实现边界。

### 5.3 交互解释器为什么需要特殊处理闭包

Scala 解释器将用户输入的每一行编译成类，变量保存在对应对象中。若下一行的闭包通过静态方法访问上一行对象，Java 序列化不一定沿着这条静态访问关系，把实际变量一起送到 worker。

Figure 6 以 `query="hello"` 和后续包含 query 的过滤为例，展示两项改造：解释器通过 HTTP 提供新生成的类字节码；生成代码直接引用上一行的实例对象，让序列化能够追踪捕获值。这不是仅仅“把源代码字符串发过去”就能解决的问题。

### 5.4 持久化有多种表示与淘汰策略

论文提供三种保存方式：反序列化 Java 对象、内存中的序列化数据、磁盘数据。第一种省掉反序列化最快，第二种节约内存但增加读取成本，第三种适合过大且重算昂贵的数据。

内存不足时采用 RDD 级 LRU：为新分区找空间，从最久未使用 RDD 中淘汰分区；但若候选恰是同一个 RDD，宁可保留已有分区，避免扫描整份 RDD 时不断相互替换。用户还能设置 persistence priority。

各 Spark 应用的内存空间在该实现中分离；跨应用统一共享 RDD 是未来工作。FAQ 关于主动释放、现代接口或运行时状态的历史措辞不能代替此处具体规则。

## 6. checkpoint 保存的是数据边界，不是“函数名再多存一份”

**§5.4，PDF 第 8–9 页；对照 §3.2.2 第 6 页。**

lineage 保证有办法重算，不保证代价低。长迭代链中的宽依赖可能使一次故障追溯很多轮；将选定 RDD 写到可靠存储，可从那一版本继续恢复。

相反，points、links 这类从稳定文件经短窄依赖链产生的数据，分区可在其他机器并行恢复，checkpoint 整份数据未必划算。选择依据是恢复成本，不仅是缓存大小。

不可变 RDD 可在后台写出：没有其他任务正在原地修改同一版本，不必为整份应用拍一个分布式瞬时快照。但仍需正确追踪 checkpoint 是否完成及可用，不能把尚未写完的部分当作可靠边界。

原论文存在**命名不一致**：第 6 页称 persist 的 `RELIABLE` flag，第 8 页称 `REPLICATE` flag。两处实际页面均核对；本文只使用“可靠 checkpoint”的机制概念，不拼造统一历史接口，更不宣称这些是当前 Spark 的调用方式。

第 8 页把自动选择 checkpoint 写作正在研究：scheduler 已知数据大小与首次计算耗时，可据此优化恢复时间，但当前由用户选哪些数据保存。本包没有实现或验证自动策略，也没有将每十轮视为作者给出的通用最优周期。

## 7. 读性能图：究竟省的是哪一笔成本

**§6.1–6.2，PDF 第 9–10 页；Figure 7–10。**

默认实验平台是 EC2 m1.xlarge：4 核、15 GB RAM，HDFS 块 256 MB；测量前清理 OS buffer cache。Hadoop 版本为 0.20.2。这些是 2012 论文实验，不是今天产品性能对比。

### 7.1 第一次迭代与后续迭代必须分开

Figure 7 在 100 台机器、100 GB 数据下分别测逻辑回归和 k-means，灰柱为首次、黑柱为后续迭代，单位秒。逻辑回归：Hadoop 约 80/76，HadoopBinMem 139/62，Spark 46/3；k-means 则约 115/106、182/87、82/33。

HadoopBinMem 先将输入转为低开销二进制格式，再放进内存 HDFS；首次多了一次转换与复制，所以可能更慢。Spark 后续迭代对逻辑回归收益很大，对计算更重的 k-means 则较小。**内存优化无法消除用户算法自身的 CPU 工作。**

Figure 8 比较 25、50、100 台机器的后续迭代。逻辑回归三组 Hadoop/HadoopBinMem/Spark 值依次为 184/116/15、111/80/6、76/62/3 秒；k-means 为 274/197/143、157/121/61、106/87/33 秒。正文报告的 25.3 倍、20.7 倍是特定逻辑回归对照；概括性“up to 20×”与这些细分比值不是一张任意负载性能保证。

### 7.2 “放到内存文件系统”仍可能重复支付转换成本

Figure 9 是单机、256 MB 逻辑回归输入实验，不是前面的百节点总时间。内存 HDFS 的文本/二进制输入为 15.4/8.4 秒，内存本地文件为 13.1/6.9 秒，Spark RDD 为 2.9/2.9 秒。

差异分解为：Hadoop 作业控制开销；HDFS 读取路径的复制和校验；文本解析；即使是二进制数据，仍要重建可用 Java 对象。RDD 直接复用对象，避免这条反复转换路径。正文另测 Hadoop 空作业至少约 25 秒，是框架控制开销实验，不能与 Figure 9 的单机处理时间直接相减。

### 7.3 PageRank 的两步改进可分别测出

Figure 10 使用 54 GB Wikipedia 数据、约 400 万文章、十轮 PageRank。30 台机器时，Hadoop、基本 Spark、控制分区的 Spark 分别约 171、72、23 秒；60 台时约 80、28、14 秒。

30 台的基本内存复用约带来 2.4 倍提升；再控制跨迭代 partitioning，约到 7.4 倍。图没有证明“无 shuffle”，它体现的是避免不必要的重新分区。Pregel-on-Spark 版本每轮多约 4 秒，用于额外结束投票操作。

## 8. 故障、内存不足与真实应用的测量边界

**§6.3–6.6，PDF 第 10–11 页；Figure 11–14。**

### 8.1 一台 worker 失效后，只补丢失的工作

Figure 11 的 k-means 实验为 75 个节点、100 GB 数据、每轮 400 个任务，在第六轮开始杀掉一台机器。此前约 58 秒/轮，故障轮升到约 80 秒，之后回落。**柱上标注 81 秒，正文写 80 秒**，保留这个近似差异，不强行写成更精确的统一数值。

丢失分区可在存活机器并行从输入重建，无需回滚此前全部迭代。论文说这些例子的 lineage 都不到 10 KB，而复制整个工作集需处理约 100 GB 数据。这只衡量所测例子的元数据与数据量，不说明任意用户闭包、任意迭代深度的 lineage 都小于 10 KB。

### 8.2 不能把“不全装入内存”说成程序必然失败

Figure 12 用 25 台机器处理 100 GB 逻辑回归，内存中保留比例从 0%、25%、50%、75% 到 100% 时，迭代时间约为 68.8、58.1、40.7、29.7、11.5 秒。此扫描负载逐渐退化，不是“数据超内存即不能运行”。它也没有覆盖所有 shuffle 溢写与偏斜场景。

### 8.3 三类用户应用说明复用可以跨不同查询

Conviva 的报表在相同筛选子集上按不同字段聚合。原来多个 Hive/MapReduce 作业反复处理同一数据；改成共享 RDD，200 GB 压缩数据的报表由约 20 小时缩短至 30 分钟，使用两台 Spark 机器、96 GB RAM。内存小于输入的原因是仅保存匹配行和列；不能据此推出完整解压后的 200 GB 数据“神奇装入 96 GB”。

交通建模用约一万条路段、60 万 GPS 行程样本，EM 迭代中有两组 map/reduceByKey；Figure 13(a) 在 20/40/80 台机器的每轮时间为 1521/820/422 秒，近线性扩展。

Twitter 垃圾链接分类使用 50 GB 子集、25 万 URL、$10^7$ 个特征维度，分布式求和梯度；Figure 13(b) 对应 70.6/38.6/27.6 秒，固定通信成本使扩展逊于线性。图中的误差线标为标准差，不是最坏延迟。

### 8.4 1 TB 的交互查询仍扫描全集

Figure 14 的硬件与默认实验不同：100 台 m2.4xlarge，每台 8 核、68 GB RAM。分析两年的 Wikipedia 浏览日志，分别求总浏览量、标题精确匹配和子串匹配后的浏览量。

100 GB 时三类查询约 1.7/2.0/2.8 秒，500 GB 时 3.2/4.5/4.7 秒，1 TB 时 5.5/7.0/6.6 秒（顺序按图例：精确匹配、子串匹配、全量计数）。这是每次扫描全体内存输入的查询延迟，不是单键 lookup 延迟；对照从磁盘查 1 TB 约 170 秒。柱间差异和误差线也提醒，不能给查询复杂度做逐点机械排序。

## 9. 表达能力、调试与相关工作的准确位置

**§7–9、致谢及文献表，PDF 第 12–14 页。**

§7.1 逐一说明可如何表达已有模型：MapReduce 用 flatMap 配合 groupByKey/reduceByKey；DryadLINQ 与 SQL 的集合操作对应 RDD 转换；Pregel 可把每轮顶点状态存成 RDD，flatMap 产生消息，再连接到下一轮顶点状态。不可变没有阻止逻辑状态变化，只要求把变化表示成新版本。

作者将 Pregel 与 HaLoop 各实现为约 200 行库，强调的不只是能算出同样结果，还能保留缓存、局部性和部分恢复优化。批量流式处理则可以将上一时间窗口状态放入 RDD，与新日志合并；这是本论文的模型讨论，不是现代 Structured Streaming 或 Ray 的实现介绍。

§7.2 提出利用 lineage 调试：重建某个历史 RDD，交互检查数据，或在单进程调试器里重跑一个任务。它不是任意分布式执行的完整 record/replay；用户函数若有非确定行为，lineage 不能复现其全部内部事件，最多可通过校验和发现结果不一致。该调试器当时也写作开发中。

§8 把贡献放在已有工作之间：集合式 API 本身不是 Spark 独创；区别在于把可共享、可重算的内存数据作为明确抽象。Nectar 的公共子表达式复用、文件系统缓存、DSM 的细粒度共享、数据库视图，都解决相邻但不同的问题。论文认可 lineage/provenance 长期存在，新增的是对分区化批量计算足够便宜的恢复方式。

结论强调以接口限制换取高效共享与恢复。致谢和 33 条文献条目已读，但不因此把参考文献中的 Pregel、HaLoop、Nectar、博士论文或后续系统正文算成已读。

## 10. 与 2021 讲义、FAQ 的衔接

讲义的分桶 shuffle 描述补充了课堂未逐步画完的执行细节：上游按下游分区组织桶，下游取回相应桶；这是一条概念数据路径，不给现代 shuffle 实现补上未经阅读的代码细节。其 spark-shell 操作与输出只作为书面教学例子，数值缩放差异见 §3.3。

FAQ 说明 Spark 对多轮复用很有优势，但单次扫描再聚合若主要受 I/O 限制，RDD 缓存没有天然收益；“更通用”不等于任意作业都必然更快。FAQ 还强调位置元数据、闭包捕获、不可变与确定性重算，不需要为每份中间 RDD运行 Raft。

FAQ 的能源问题主要讨论硬件、机房与冷却的影响，并给出 FAWN 链接；流式系统、DataFrame、Databricks 用户、Naiad、Piccolo 等外链没有在本任务展开。“RDD somewhat deprecated”是当时材料的描述，不作为当前 API 弃用状态。未来可与 Ray 比较任务/对象、数据依赖和恢复边界，但 **update-ray 仍是后续未完成主题**，本页没有代替其指定阅读。
