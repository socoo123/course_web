## 02:00–04:00　并发不是并行，屏幕共享短暂停顿

并发关心怎样组织程序，把独立执行的控制流组合起来，同时应对许多事情而不把代码弄成一团；并行关心实际执行时，多个计算是否同时运行。

并发自然可以支持并行，但今天主要目标是让代码更清楚。运行更快当然很好，却不是本讲的重点。

开始四种模式之前，先看一个简单问题：把状态放在数据里，还是放在控制流里？例如读取一个 C 风格的引号字符串。

## 04:00–08:00　从显式状态机变成顺序代码

字符串例子每次读取一个字符，并不需要并行。若不验证每种转义的具体含义，只想识别引号与反斜杠，可以写成一个很小的状态机。

最机械的写法是：用 `state` 变量保存当前位置；循环读取字符，再根据 `state` 和字符决定下一状态。工具生成的代码可能如此，但人很难直接看出它在做什么。

现在逐步改写。先把读取字符放进各个分支，再把“设置状态、回到 switch”改成跳到相应代码位置。随后去掉不必要的跳转，把只有一个入口的状态内联，合并共同的后继，最后把回跳改成普通循环。

结果可以直接读懂：先检查开引号；然后循环读取，直到闭引号；遇到反斜杠就额外跳过下一个字符。原来用数据表示的状态，现在由程序计数器处在哪段代码表示。

即使手写程序没有那么机械，也可能有多余的 `inEscape` 标志，可以作类似简化。提示不是“永远不要状态变量”，而是：**如果更清楚，就把数据状态变成代码状态。**

> **编者校注：** 2021 PDF 第 13–15 页的简化循环在外层声明 `c` 后，内层又写 `c := readChar()`，会遮蔽用于循环条件的变量。第 15 页已对照 PDF 页面确认；按讲解意图应更新外层变量，而非重新声明。这里解释设计意图，不将幻灯片当可直接运行的代码。

## 08:00–11:00　借另一个 goroutine 保存控制流

并非所有接口都允许函数主动调用 `readChar`。也可能调用方一次递交一个字符，要求 `ProcessChar(c)` 立刻返回当前状态。这时普通函数每次都要返回，无法用自己的执行位置保存“解析到了哪里”，只能显式存状态。

Go 还提供另一种选择：启动一个 goroutine，在它自己的栈上运行已经写好的顺序解析器。外层每次收到字符，就通过一个 channel 送进去；解析器通过另一个 channel 报告“需要更多输入”或结束状态。

这样不用重写一个可能已经调试好的复杂解析器，也能满足逐字符输入的外部接口。**额外的 goroutine 可以持有额外的代码状态。**

Frans 确认大家可以随时打断提问，Russ 表示欢迎。

## 11:00–13:00　不要忘记解析器何时结束

使用 goroutine 并非没有代价，必须保证它能退出。Russ 回看幻灯片，发现结束状态的发送没有完整画出来，现场说明应当有成功和输入错误的终点。

正常交互中，解析器需要字符时报告 `NeedMoreInput`；调用者继续供给，直到拿到终止状态，解析 goroutine 也应结束。如果调用者自己遇到 EOF 就直接离开，却不通知解析器，它可能永远等下一个字符。

因此，任何这样的改写都必须回答：每个 goroutine 为什么、何时退出？这里的幻灯片是模式示意，不是完整处理 EOF、取消和终止消息的库。

## 13:00–15:00　泄漏的 goroutine 会留在原地等你检查

这类错误有一个好处：阻塞的执行流通常会留在原处，便于观察。示例启动许多 goroutine，让它们在 `h` 中向无人接收的 channel 发送，再启动一个 HTTP 服务。

在 Unix 终端按 `Ctrl-\` 会发送 SIGQUIT，使程序打印 goroutine 栈并退出；可以看到 `h` 被 `g` 调用、`g` 被 `f` 调用，以及阻塞的 channel 发送位置。

如果 HTTP 服务导入 `net/http/pprof`，也可以访问 `/debug/pprof/goroutine` 查看仍在运行的程序。输出会把相同栈聚合，并按数量呈现；若某个位置泄漏了一百个执行流，它通常很显眼。

提示是：不要只等程序崩溃，主动查看有哪些 goroutine 长期停在同一个位置。

## 15:00–17:00　模式一：发布／订阅接口

发布／订阅把事件产生者与消费者解耦，中间的服务负责连接双方。现实系统还会按事件种类过滤；本例先假设过滤已经处理，只研究并发。

接口包含 Publish、Subscribe、Cancel。订阅者交出一个接收事件的 channel；之后发布的事件会按共同的次序送给各个订阅者。取消时仍使用同一个 channel，先前已发布但尚未送达的事件处理完之后，服务关闭输出，表示以后不会再有事件。

channel 上信息从发送者流向接收者，关闭也是这个方向的通知。接收者不能通过随意关闭 channel 告诉发送者“我不想收了”，那会把通信方向倒过来。需要双向沟通时，可以使用两个 channel，两个方向甚至可以有不同的消息类型。

## 17:00–20:00　最简单的 mutex 版本及慢订阅者

先用一个 map 保存订阅 channel，一把 mutex 保护它。Publish 遍历 map 发事件，Subscribe 增加条目，Cancel 删除条目并关闭 channel。多个调用者可能同时进入，所以这些方法都需要同步。

在 Lock 后立即写 `defer Unlock`，可以照顾多个返回分支，函数 panic 时也会执行 defer。若 panic 发生时共享状态已经损坏，问题另当别论；这里只考虑较简单的情况。

例子对重复订阅、取消不存在的订阅使用 panic，这是为了简化。它意味着把这种误用视为编程错误；更通用的 API 可能返回 error。

更重要的问题是慢消费者。Publish 持有锁依次发送，如果一个订阅者迟迟不收，其他订阅者和订阅管理也会被拖住。但若应用已经约定消费者及时接收，这个简单实现可能足够好：不要为了复杂而复杂。

## 20:00–24:00　慢消费者的三种代价

简单方案的一个特点是 Publish 返回时，事件已经交给各接收方；不代表对方处理完了，只代表完成交接。给订阅 channel 加少量缓冲，可以吸收短暂延迟，但不能解决任意慢的消费者。

一般只有几种选择：减慢事件产生速度，丢弃或合并事件，或者把所有未消费的事件排起来。

Profiler 是合并／记录丢失的一种例子：如果读取 profile 数据的一方落后，缓冲耗尽后不能无限等待，就累计丢失的采样，并让 profile 显示这些数据没有被记录。`os/signal` 则可能直接省略无法投递的信号通知；调用者需要准备有缓冲的 channel，重复信号还可能合并，这与 Unix 信号本身的某些语义相近。

如果真的不能丢事件，就必须保存积压。但是分布式系统总有慢机器和离线机器，**引入无界队列之前要仔细想清楚**。Go 没有直接提供无限缓冲 channel，并不是忘了做，而是这种选择通常需要额外设计。

## 24:00–28:00　把 mutex 改成状态所有者

为继续演示，先把服务变成一个专门运行 `loop` 的 goroutine，通过 publish、subscribe、cancel 三个 channel 接收工作。订阅 map 现在只是这个 loop 的局部变量，其他执行流不能直接访问它。

三个方法变成小封装：Publish 把事件交进去；Subscribe、Cancel 发送包含目标 channel 和回复 channel 的请求，等待 loop 告知结果。原来互斥锁的“现在是谁在修改状态”，变成了单一执行流天然串行的控制流。

这种转换让所有权清楚，但不是每次都更好。原来的数据结构更便于直接观察关键状态。Raft 就是一个很特别的例子：副本可能刚认为自己是 leader，下一刻就发现被替换；日志也可能因纠正而改变。因此显式状态加锁，往往比把状态藏在程序计数器里更适合 Raft。

接下来给每个订阅者增加一个 helper，由它独自处理积压，主循环只负责维护订阅关系。

## 28:00–31:00　队列 helper 的两个陷阱

helper 一边接收新事件加入队列，一边向订阅者发送队首。初稿中有两个问题。

第一，空队列时仍在 `select` 的发送表达式中访问 `q[0]`。进入 select 会求值这些表达式，并非选中后才求值，所以可能越界。修正办法是先决定当前是否有可发事件：没数据时让发送 channel 为 nil，有数据时再设置真实 channel 和队首值。

第二，输入关闭后不能立即抛弃队列。接收时检查 `ok`，发现输入关闭就把输入 channel 置 nil，停止从它接收；之后继续发送积压。输入已经结束且队列清空，才关闭输出、返回。

> **编者校注：** PDF 第 34 页把继续条件写为 `in != nil && len(q) > 0`，但空队列开始时这会立即结束，也不能在输入关闭后排空。按所讲协议应是两者的“或”。字幕在 29 分钟附近同样有连接词含混；这里明确按协议解释，并记录原稿问题，未静默当作正确代码。

服务的订阅 map 从“输出 channel → 是否订阅”变成“输出 channel → helper 输入”。订阅时创建 helper，取消时关闭 helper 输入，由 helper 负责送完积压再关闭最终输出。

这样，以后若要改成丢弃或合并事件，主要改变 helper；订阅关系管理基本不用动。让独立关注点由独立 goroutine 承担，可以让程序结构更清楚。

## 31:00–33:00　模式二：工作调度器的起点

第二种模式是工作调度器，类似大家在当年 MapReduce 实验中见过的部分。这里把 RPC 隐藏在 `call(server,task)` 中，先假设服务器列表固定。

需要记录哪些服务器空闲。一个带缓冲 channel 可以当作并发安全的阻塞队列：初始化时把所有服务器放进去；每个任务拿走一台服务器、执行、再放回去。

最初的循环为每个任务启动一个 goroutine。它表达了任务相互独立，但有两个问题：闭包使用循环变量，以及没有管理好等待和数量。先看循环变量的问题。

## 33:00–35:00　循环变量捕获与 race detector

按 2021 Go 的语义，闭包运行时，外层循环可能已经改了 `task`。race detector 能帮助定位这种问题。Google 甚至鼓励部分服务将极少量生产流量送到开启检测的实例，尽早发现竞争，而不是事后排查数据损坏。

一种修正是给匿名函数加参数，把 task 的值在启动时传进去。`go` 语句必须带一次函数调用，也让这种求值和复制自然发生。

如果参数起名 `task2`，却忘记修改函数体里的 `task`，错误仍然存在。使用同名参数遮蔽外层变量，可以避免不小心又读旧变量。

另一种写法是在循环体开头建立新变量 `task := task`，再让闭包捕获它。第一次看会觉得奇怪，但它表达的是为这一轮建立独立副本。

> **版本校注：** Go 1.22 对循环头用 `:=` 声明的变量改为逐迭代独立。此处解释历史课堂；对外层已有变量用 `=` 赋值，或捕获其他共享对象，仍需另行分析。

## 35:00–38:00　限制执行流数量，并等待真正结束

另一个问题是任务太多。如果一百万个任务对应五台服务器，创建一百万个 goroutine，只是让绝大多数阻塞着等待资源。

把“取得空闲服务器”放到启动 goroutine 之前，派发循环就会被资源数量限制：有空闲服务器才开工。这形成背压，活跃的任务执行流数量接近服务器数量。

所有任务派发完之后，还要把所有服务器从空闲队列中收回来；当固定数量的服务器全部归还，才能知道任务结束。这样的好处是，仍能用普通 for 循环表达控制流程。

还可以进一步改成“一台服务器一个 goroutine”，而不是“一个任务一个 goroutine”。channel 里现在放待执行任务，服务器循环取任务。主执行流发完任务后关闭 work，worker 的 range 循环结束，再报告自己已退出；主执行流按服务器数量收齐这些通知。

## 38:00–40:00　服务器动态加入后，完成通知引发死锁

如果服务器可以随时加入，就把服务器来源改成 channel，单独开一个执行流接收新服务器并启动对应 worker。

但现在不容易知道总共有多少服务器，所以改成数完成的任务：每个任务完成后发一次 done，最后收齐任务总数即可。

这个看似小的改动引入了死锁。主执行流忙着发送下一个任务，要等全部派完才接收 done；worker 做完一个任务，先发送 done，只有它被接收后才能继续取任务。于是主执行流等 worker 接任务，worker 等主执行流接结果。

运行时打印的栈会显示双方都在 channel 发送处阻塞。关键不是“哪个 channel 错了”，而是两个方向的通信被安排成了互相依赖。

## 40:00–43:00　解除循环等待，再处理重试和关闭

可以用 select 同时发送工作和接收完成，也可以把发送循环放进独立 goroutine，让主执行流专门计数。两种逻辑本来就不要求先后执行，分离后便能相互推进。

若任务数固定且可接受内存成本，最简单的方案还可以是让 work 的缓冲足够容纳全部任务。每个任务只占一个很小的队列项，通常比一个等待中的 goroutine 栈便宜得多；但这仍是需要评估的容量选择。

再考虑失败：令 `call` 返回是否成功。成功则发 done；失败则把任务放回 work，供后续尝试。因为 worker 也成为 work 的发送者，不能在初始派发结束就关闭 work；必须等全部逻辑任务成功，确认不会再有重试发送，才关闭。

为什么不直接杀掉所有 worker？执行流可能持有锁，或正处于另一段通信中，突然终止会破坏别人的假设。应通过明确的结束协议让它自行清理并返回。

最后还要停止那个等待新服务器的执行流：增加退出通知，让它在“收到新服务器”和“调度已经结束”之间选择。

> **编者校注：** 这是解释并发结构的调度模型，不涵盖真实 MapReduce 的输出提交、重复尝试和服务器故障协议。它不是本路线 2026 Lab 1 的完整答案。

## 43:00–45:00　模式三：访问复制服务的客户端

现在假设同一服务有多个副本，客户端可以向任意一个合适副本发请求。初始化时给客户端服务器列表和访问单台服务器的 `callOne`；对外的 Call 不要求应用决定具体用哪台服务器。

希望先尝试上次成功的服务器，若太慢再换一台。跨调用需要保存的共享状态很少，主要是“偏好的服务器编号”，因此用一把 mutex 保护它最直接。

尽管今天大量讨论 channel，**如果 mutex 是最清楚的写法，就用 mutex**。

## 45:00–47:00　超时后尝试另一台，接受最先到达的结果

示例的 `callOne` 总会在返回时给一个 Reply，没有额外的失败值，因此这里把“太久没回来”作为开始另一次尝试的信号。需要在后台 goroutine 中执行它，当前 Call 则等待结果或 timer。

若拿到结果就返回；若 timer 到期，就重设定时器，向下一台发起尝试。所有尝试共用一个结果 channel，因此即使已经尝试第三台，第一台终于回来，也可以接收第一台的结果。

全部服务器都尝试过后，就等待某个结果，不再有新的服务器可切换。

结果 channel 的缓冲要容纳这些尝试的结果。调用者只拿第一个就走了，剩余尝试仍可能完成；给它们足够位置发送，才能避免卡在无人接收的结果发送上。

## 47:00–49:00　问答：为什么还要 Stop timer

**问：程序不再引用 timer 时，为什么垃圾回收不能自动收走它？**

Russ 解释当时的实现：活跃 timer 仍被 runtime 的队列引用，垃圾回收无法区分这个内部引用与程序的引用，所以要 Stop，将不需要的 timer 从活跃队列移除。曾经考虑对 timer channel 作特殊处理，但当时尚未采用。

最后加入偏好编号：每次从上次成功的服务器开始绕一圈尝试，得到结果后，在锁保护下更新偏好，再返回。为了让几条成功路径共享收尾代码，示例使用 goto；若它让控制流更清楚，没有必要教条地禁止。

> **版本校注：** Go 1.23 的 timer channel 实现改变了未引用 timer 的回收行为，且默认是否启用取决于主模块的 `go` 版本等配置。这里保留 2021 问答，当前实验模块的边界见 [L10 笔记 §7](#/c/mit-6.824-2021/lec/lec10?v=notes)。缓冲只能帮助已经返回的 RPC 发送结果，不能终止永不返回的底层调用。

## 49:00–52:00　模式四：协议复用器

协议复用器是 RPC 系统的一个核心部件。底层服务能发消息、收消息，并能从消息中读出 tag；请求与它的回复使用相同 tag。复用器要让多个 goroutine 同时调用 Call，却各自收到正确回复。

先设一个发送循环，只由它调用底层 Send，避免要求底层自己处理并发发送；再设一个接收循环，只由它调用 Recv。发送和接收可以独立推进，但各自内部串行。

另外用 pending map 记录“tag 对应哪个等待 channel”，并用 mutex 保护。接收循环得到回复，读取 tag，在锁内取出对应 channel 并删除条目，再把回复交给等待者。

Call 的路径是：读出请求 tag，建立自己的完成 channel，在 map 中登记，检查没有冲突，然后交给发送循环，最后等待回复。

这种写法同时使用了 goroutine、channel 和 mutex，各自承担最清楚的职责。Russ 回忆自己以前用 C 写过许多这类代码，Go 的结构容易表达得多。

> **编者校注：** PDF 的复用器片段还有 `ReadTag`／`Tag` 名称、map channel 类型及 send channel 初始化等不完整之处。本页描述协议结构，不提供从幻灯片拼出的可编译实现，也不宣称已验证该示例。

## 52:00–56:00　预先收集的问答：Go 的开发与设计目标

四种模式讲完，Russ 展示提示清单，开始回答同学事先提交的问题。

**Go 做了多久，团队多大？** 讨论始于 2007 年 9 月，Russ 在 2008 年博士毕业后全职加入；2009 年开放源码；课堂先说到原定的 Go 1 时间，再纠正为 2012 年 3 月。最初约五人，后来 Google 内部直接从事 Go 的团队约五十人，还有大量外部贡献者，不能忽略他们的作用。

**最重要的设计目标是什么？** 最初是解决 Google 自己的分布式软件问题；后来云软件普及，更多人也遇到类似需求。另一个目标是让很多程序员能够合作维护代码。即使团队很小，也可能依赖许多开源作者的代码，因此这个问题普遍存在。

核心设计组通常要讨论到形成共识才加入新东西，所以有时很慢；但组合起来的特性因而相对稳定。泛型也是如此：相比早期提案，当时终于觉得新方案像 Go 的自然一部分。

## 56:00–59:00　defer、导出名与当时的泛型计划

有同学喜欢 defer，Russ 也喜欢，并提到其他语言对这一想法的吸收。

**为什么用首字母大小写决定导出？** 起初为了推进开发，暂时让一切公开；后来必须增加隐藏机制。C++ 的 public/private 区域需要向前找最近的标记，Java 则要在各声明处重复写关键字。团队也讨论了 Python 下划线等约定。

大小写方案刚提出时，Russ 觉得不美观，却找不到足够理由反对。后来发现它非常有用：不仅在声明处，在每次使用名字时都能直接看出它是不是对包外开放的能力。

关于泛型，当时仍是提案和实现中的功能，计划进入未来的 Go 1.18。Russ 期待能自然表达通用的 min/max，而不必为每种类型起不同名称。

> **历史边界：** 本段保留 2021 年的计划，不把预测的发布日期和库 API 当作现在的事实。

## 59:00–62:00　不完美的用途、简单性与暂缓泛型

**Go 会不会被用于不最合适的领域？** 会，所有语言都有这种情况。一个已有系统主要用 Go 写，即使某部分用其他语言更自然，跨语言集成的成本也可能更高。

Russ 举整数数列百科搜索后台的例子：查询未知数列时需要复杂数学与大数计算，但由于整体服务的结构，直接用 Go 做也有现实理由。

**简单是否意味着故意不给开发者需要的功能？** 不是。集合与 map 很接近，可以用布尔或空值 map 表达；泛型则是担心过早设计错误。Go 开始时，团队刚看过其他语言引入泛型的复杂经历，知道没有泛型也能先写许多有用程序，便留出时间积累经验、向专家学习。

Russ 认为更早拥有泛型当然方便，但当时未必能设计出后来令人满意的形式。

## 62:00–65:00　goroutine 与 Plan 9，调度实现在哪里

**goroutine 与 Plan 9 线程库的关系是什么？协作调度是否造成问题？**

早年的经验确实有影响。Alef 有 channel、select 和类似 task 的设施，但没有垃圾回收；一些 task 被绑定到同一线程，只在通信点切换。程序员可能凭记忆认为几个 task 不会同时运行，因此无锁共享数据。

小程序里这种推理还勉强可行，半年后或换人维护就很容易忘记分组。Go 从一开始就要求把 goroutine 当成独立、可能被抢占的执行流；需要共享就明确用锁或通信同步，而不是靠记住调度时机。

早期实现的抢占点有限，后来扩大到函数入口；紧循环仍可能延迟垃圾回收。再后来使用信号机制改善抢占。但语言层面的编程模型并不是“只在你知道的几点才会切换”。

**想读调度器代码从哪里开始？** 可以从 runtime 的 `proc.go` 入手。Russ 将 runtime 比作运行在操作系统之上的小操作系统，并建议学习操作系统课程来理解其中的调度与执行状态。

## 65:00–68:00　负下标与垃圾回收器的难点

**为何没有 Python 式负下标？** 从末尾取值很方便，但一个倒序循环的 off-by-one 可能因此悄悄读到数组另一头，反而隐藏 bug。团队倾向于让这种越界立即显现，而不是增加特殊语法。

**最难实现的部分是什么？** 很多调度和通信组件都有先前经验，垃圾回收更难。Go 允许程序员较直接地控制内存布局，例如结构体内嵌结构体，而不是每个组成部分都间接指向另一个对象；又允许取内部字段的地址，回收器因此要识别指向分配对象中部的指针。

网络服务还要求低停顿，不能为了回收暂停全部请求很久。多核提供了后台并发回收的机会，但真正做对仍需要专门知识和持续工作。

## 68:00–70:00　问答：为何允许紧凑内存布局

**问：为何把结构体嵌套表示成一整块内存？**

答：一方面减少对象分配数量，减轻回收器负担；另一方面提高缓存局部性。处理器按缓存行读取相邻数据，紧凑布局常比追逐分散的指针更有效。

Russ 举 Gerrit 和 SHA-1 值的表示成本为例：像二十字节这样小而固定的值，如果必须额外分配对象或引入间接层，成本会不断累积。让程序员有布局控制是有意选择。

**是否自动并行化循环？** 标准 Go 工具链没有把它作为主要方向。其他后端可能利用已有编译优化，但 Google 常见的需求更偏向服务与请求之间的并发，而不是自动拆分大型向量运算。

> **字幕校订：** 此处 ASR 的 `garrett`、`shot one` 分别按语境整理为 Gerrit、SHA-1；没有把对其他语言表示方式的口头比较扩展为全面性能结论。

## 70:00–73:00　锁保护不变量，为什么不做可重入锁

**问：如何决定锁的取得与释放位置？为何不支持可重入锁？**

我们口头说“mutex 保护 map”，实际意思是保护一组关于数据的不变量，以及那些依赖这些不变量、执行过程中又可能暂时破坏它们的操作。

取得锁表示：现在可以依赖这些不变量。释放锁表示：即使刚才暂时破坏过，现在也已经恢复，下一位拿锁者可以继续依赖它们。

在复用器里，一个 pending channel 应至多收到一次回复。因此读取条目和删除条目要在同一临界区。若中间解锁再重锁，取消操作就可能插入，双方对谁负责完成请求产生错误判断。

可重入锁让“取得锁后不变量成立”不再那么直观：也许同一调用栈上层已经拿着锁，并且正在临时修改状态。下层再次加锁，并没有真正经过另一个完整临界区的边界。

另一个问题是重构。原来依赖同一调用栈重入的函数，移到新 goroutine 后，会真正等待上层释放锁；上层若又等它完成，就死锁了。Russ 因而建议按不变量理解锁，不依赖可重入行为。

## 73:00–75:00　现场问答：map、filter 与循环

**问：从 Python 转来，习惯 map、filter、列表推导式，为什么 Go 常建议写循环？**

答：在当时的类型系统中，很难表达这些通用函数的类型；另外，一串 map/filter 可能产生多次遍历和中间分配，而单个循环能将工作合并，减少垃圾。

但这不是说函数式写法永远不好。泛型引入后，可以建立相应的通用库；Russ 预计会出现围绕 slices 的操作。若它们适合问题，就可以用。

> **编者校注：** 对未来库的举例属于课堂设想；没有据此登记当前标准库存在 `slices.Map` 或 `slices.Filter`。

## 75:00–78:00　现场问答：为什么多开一个执行流就有意义

**问：有些例子看起来直接调用函数也可以，为什么非要独立 goroutine？**

答：目标是让本来独立的职责能够独立推进。回到调度器：派发者要发送下一个任务，worker 要先报告前一个任务完成。若主执行流必须派完才收结果，两边就会互等。

把派发循环放到另一执行流后，它可以等 worker 接任务；主执行流则可以接收 done，让 worker 继续。不是“开线程”神奇地解决问题，而是去掉了一个不必要的先后约束。

随后有人问 race detector 怎样工作，Russ 开始介绍它与 LLVM ThreadSanitizer 的关系。

## 78:00–80:00　race detector 检查 happens-before

检测器为被访问的地址维护额外信息，例如最近由哪个执行流读或写；通信、锁等同步事件则建立执行流之间的 happens-before 关系。

如果某次读与写之间没有恰当的同步顺序，就可能报告竞争。即使两个访问在墙钟时间上恰好没有同时发生，也不能用这种偶然错开代替同步关系。

检测需要额外内存和时间，课堂给出的是数量级上的开销感受；在测试或少量流量上使用，仍通常比事后排查内存损坏值得。有人确认名称，Russ 回答是 LLVM 项目中的 ThreadSanitizer。

## 80:00–82:00　slice 为什么是数组的视图

**问：为什么 slice 被设计成底层数组的视图？**

答：为了高效表达常见的内存操作。排序时把数组分成两半递归处理，希望传递的是对原存储一段区间的描述，而不是复制整段数据。

C 中常用“首元素指针加元素数”描述一段数组；可增长数组还要记录已经分配的容量，避免每增加一个元素都重新分配。slice 把这些惯例放进一个较安全、较自然的语言结构中。

它与底层存储分开，使创建子视图方便，但也意味着多个 slice 可能共享数组，不能把 slice 值的复制理解成底层数据复制。

## 82:00–84:00　模块路径、命名空间与正式下课

**问：为什么从带域名的路径获取模块，而不是全靠中央短名称仓库？**

Russ 说，最初并不想运营一个中心服务，也不希望大家争夺 `db` 这样的短名称。域名提供了分散的命名空间，工具可以去对应的源码服务获取代码。

他还讨论了多仓库生态中名称归属不清所带来的混淆与风险，用以解释为什么觉得域名边界有价值。

> **编者校注：** 这是嘉宾对设计动机和其他生态的口头比较，不将其中关于外部包管理器的概括当作已独立核验的当前行为。

## 84:00–86:00　课后：什么时候值得创建一门语言

先有人提醒课表上的幻灯片与这次展示不完全相同；Russ 表示会提供新 PDF。

**问：什么时候重新设计语言才是解决问题的最好办法？**

答：几乎从来都不是轻松的最佳选择。当时 Google 有大量程序员共享大型代码库，编译慢；事件驱动回调结构难以维护，多核利用和线程设施也不理想，确实有许多问题值得尝试新办法。

但把 Go 做到今天花了大量工作，而且成功不只来自语言本体，还来自生态、工具、go 命令以及周边设施。只盯语法和类型系统，会低估这些部分。

## 86:00–88:00　成熟项目的兼容性与自举

**问：Go 成熟之后，与早期工作有何不同？**

早期很容易改，今天非常难。最初所有 Go 代码都在一个仓库里，修改语法后，团队甚至可以一起看着编辑器批量更新世界上全部 Go 文件。比如 channel、map 早期暴露过的指针写法，后来就这样调整。

如今用户规模很大，不能随意做破坏兼容的改变；即使增加特性，也要考虑许多用户已有的代码和反馈。

**问：Go 自己用什么实现？** 原来的编译器与 runtime 用 C；后来做了针对原有 C 代码的翻译工作，尽量保留累积的实现知识，转成 Go，另有少量汇编。这样 Go 用户更容易参与项目，而不必先成为熟练的 C 开发者。

## 88:00–91:00　特性优先级与 min/max

**问：怎样决定加入什么语言特性？**

长时间里语言几乎被冻结，近年才有一些很小的变化，为较大变化积累经验，例如数字中的下划线分隔。泛型显然是下一项重要工作，但仍要弄清怎样设计；新特性应避免与现有特性产生奇怪干扰，并真正帮助目标领域中的大量用户。

**问：为何一直没有通用 min/max？**

因为没有泛型时，很难用统一类型签名表达，需要按类型区分名称。Russ 当时也在考虑它们是否应成为内建功能；有人提醒 math 已有浮点版本，他承认这是继承 C 数学库背景的结果，最后如何安排还要决定。

本段是 2021 年尚未定稿的设计讨论，不是当前工具链的 API 说明。

## 91:00–93:00　从竞赛编程到系统工作

**问：从算法竞赛转到系统和语言实现，经历了怎样的变化？**

Russ 说自己从一开始就更喜欢系统，竞赛是有趣的旁支，不是主要活动；他参加时的竞赛环境也不同于如今。语言实现仍会遇到基本算法，比如标准排序、差分算法，所以那些知识有用，但日常编程的重心不同。

同学追问竞赛是否只是副业，他确认如此，也感叹现在的竞争和投入方式已经变化很大。

## 93:00–95:27　学术与工业，以及维护二十年的代码

**问：为什么从学术研究走向工业工作？**

Russ 讲到自己在新泽西、靠近 Bell Labs 长大，因而有机会在中学与大学时期接触 Plan 9。他曾计划读完研究生回到研究实验室，但环境发生了变化；后来 Google 有许多有趣的分布式系统工作，提供了另一条道路。他也考虑过其他工业研究机构。

工业界仍有带研究性质的工作，只是机会与环境会改变。与学术的一项差异是：工业工作特别关心系统真正可靠地运行，并支持十年甚至更久；论文完成后往往可以转向下一个问题，而产品需要持续维护。

Russ 最后感叹，Go 中有些代码来自更早的积累，如今仍在修改自己二十年前写下的文件，是一种很特别的体验。录像在这段感想附近结束，未保留进一步答复。
