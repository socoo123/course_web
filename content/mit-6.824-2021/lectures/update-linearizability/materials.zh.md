# 论文精读：并发对象的形式契约

## 1. 阅读地图与论文真正要解决的问题

论文不是在提出某个数据库产品，而是在问：**怎样把顺序对象的规格，推广到多个进程并发调用的场景？**

| 原文位置 | 核心问题 | 本页位置 |
|---|---|---|
| §1，pp.463–467 | 哪些并发行为应当被视为同一个对象的合理行为？ | §2 |
| §2.1，pp.467–468 | 如何精确记录调用、返回和未完成操作？ | §3 |
| §2.2–§2.3，pp.468–470 | 用什么条件把历史变成合法顺序？ | §4 |
| §3.1，pp.470–471 | 分别正确的对象能否组合成正确系统？ | §5 |

这里的对象不只包括网络 KV，也包括队列、寄存器等共享对象。类型给出合法值与允许的操作；客户端只能经操作接口观察和改变它。对象模型使我们能把实现内部的线程交错藏起来，只对外部可见行为作判断。

直观的调用区间、实时顺序与 KV 小例子见[课程笔记 §1–§4](#/c/mit-6.824-2021/lec/update-linearizability?v=notes)。本页进一步解释原文的形式构造与证明目的。

## 2. §1：必须连同对象语义一起判断

### 2.1 FIFO 队列的四种行为

原文图 1 使用入队 Enq 和出队 Deq；判断不仅取决于事件先后，还取决于 FIFO 规格。

- **H1 可以接受**：x、y 的入队重叠，之后先出 x、再出 y。可以把入队顺序解释为 x 在 y 前。两次入队谁先返回并不能单独否定这一解释。末尾还有尚未完成的 z 入队，表示观察到的可能只是长期执行的一个前缀。
- **H2 不可接受**：x 的入队已经完成，y 的入队才开始；在 x 尚未出队时，却先取出 y。实时先后和 FIFO 共同排除了这种结果。
- **H3 可以接受**：x 的入队还没返回，另一个进程已经取出了 x。操作可以先产生效果，再稍后返回；返回消息延迟不意味着效果必须延迟。
- **H4 不可接受**：y 只入队一次，却被两次出队取走。无论怎样安排重叠操作，都不能凭空多出一个 y。

这些结论若把对象改成栈，就要重新分析。线性一致性不是某种脱离数据类型的“排序术”，而是把并发行为与**给定顺序规格**联系起来。

### 2.2 寄存器里的读也会限制顺序

原文图 2 先写 0，然后 B 发起一个很长的写 1。A 在其间读到 1；A 的读结束后，C 写 0；最后 B 读取。

虽然 B 的写 1 与 C 的写 0 重叠，A 已读到 1 这个事实迫使写 1 排在 A 的读之前；A 的读又严格先于 C 的写 0。因此最后 B 应读到 0。若它读回 1，就不能用“两个写并发，所以顺序随便选”来开脱。

论文借此说明：必须把**整个历史**的读写结果一起考虑。读不是被动附属品，它能揭示某个写已经发生，从而限制未来可接受的行为。

## 3. §2.1：历史、投影与 pending

### 3.1 历史是事件序列

形式上，历史 H 是一个有限的调用事件与返回事件序列。调用带对象、操作、参数和进程标识；返回带终止条件、结果和进程标识。

在论文的模型中，每个进程是顺序的：一次调用后先等它返回，再发下一次。一个真实客户端若有多个并发调用，可以将这些独立执行流视作不同的模型进程，而不是强行把它们塞进一条顺序进程历史。

“well-formed” 表示按进程查看时，每条进程历史都符合这样的调用／返回规律。不代表所有进程之间已经顺序化。

### 3.2 两种投影，各回答一个问题

- $H|P$：只保留进程 P 的事件，用来描述这个调用者看到的事情。
- $H|x$：只保留对象 x 的事件，用来局部分析某个对象。

两个历史等价，是指对每个进程投影后相同。不是只要求最终内存相同；每个进程的调用、结果与自身顺序都必须保留。

例如队列多出一次重复出队，即使后续操作碰巧使最终队列看起来一样，也不能据此宣布等价。调用者已经观察到不合法结果。

### 3.3 没返回的调用不能一概当成没执行

pending invocation 是在当前历史前缀中找不到匹配返回的调用。`complete(H)` 则去掉这些不完整操作，只保留调用与返回配对的部分。

但定义不会直接要求 `complete(H)` 能解释全部现象，因为 pending 调用可能已经产生效果。例如 x 的 Enq 尚未返回，另一个进程的 Deq 却已经返回 x；若直接丢弃 Enq，就会误判为凭空出队。

因此，后面的定义允许**先给某些 pending 调用补上返回，再取 complete**。剩余未补全的调用可当作在当前解释中尚未生效。

### 3.4 顺序规格描述每一步

顺序历史中，一个操作的调用和返回挨在一起，不与别的操作交错。对象的顺序规格是一组合法的顺序历史，并对前缀封闭：若完整行为合法，它已经发生的前缀也应是可解释的。

对 FIFO，入队把元素加到队尾，非空队列出队取走队首。原文把空队列上的 Deq 留为未定义的部分操作；这与某些实际 API 返回“空”错误是不同规格，不能混用。

## 4. §2.2–§2.3：两个条件缺一不可

原文先定义实时偏序：

$$
e_0 <_H e_1
\quad\Longleftrightarrow\quad
\operatorname{res}(e_0)\text{ 在 H 中先于 }\operatorname{inv}(e_1).
$$

两个操作若在这个关系中不可比较，就称为并发。它只强制不重叠操作的先后，不是按所有调用的时间戳排序。

历史 H 可线性化，当且仅当可以在末尾追加零个或多个返回事件，得到 H′，使得存在一个合法的顺序历史 S，满足：

1. **L1：** `complete(H′)` 与 S 等价。
2. **L2：** $<_H\ \subseteq\ <_S$。

L1 保留进程可见的操作与结果，并要求符合顺序规格；L2 保留原来已经存在的实时先后。

若只保留 L1，可能为了让返回值“说得通”而把已经完成的写排到很晚，忽略实时顺序。若只保留 L2，却不检查合法性，则可能把重复出队等错误照样排成一个顺序。

H′ 允许补全，不允许任意创造新调用或修改已观察到的返回值。对 pending Enq(x) 与已完成 Deq→x，可以补一个成功入队返回，并将它线性化在出队之前；对已完成却错误的出队，不能通过删掉它来修复。

可能存在多种 H′，同一个 H′ 也可能有多种 S。证明可线性化只需展示一种；证明对象实现可线性化，则必须覆盖它可能产生的全部历史，而非只为一次测试找到顺序。

**Lab 2 的区别：** ErrMaybe 已经是实际返回值，并不是 pending。怎样在顺序规格中容纳它，见课程笔记 §6；不要把论文允许补全 pending 的规则当成“所有错误都能删掉”。

## 5. §3.1：局部性为什么重要

定理 1 说：

$$
H\text{ 可线性化}
\quad\Longleftrightarrow\quad
\forall x,\ H|x\text{ 可线性化}.
$$

从整体到局部容易理解：整体已有一个合法顺序，投影到某个对象，仍然合法。

反方向才是重要部分：每个对象各自找到合法顺序，这些顺序是否可能与跨对象实时关系冲突？论文证明可以把它们组合起来。

### 5.1 证明的骨架

1. 对每个对象选择一份局部线性化，以及为 pending 调用补出的返回。
2. 将这些补出的返回加入总历史。
3. 汇合所有对象内部选定的顺序，再加上原历史的实时先后关系，取传递闭包。
4. 证明这个关系没有环；如此即可扩展为全序 S。
5. S 在每个对象上的投影符合其规格，也保留实时关系，所以满足 L1、L2。

“没有环”不是想当然。论文用最短环反证：若环只含一个对象，就与该对象已经可线性化矛盾；若跨多个对象，跨对象边只能来自实时先后。利用返回先于调用及时间传递性，可以压缩出更短的环，仍然矛盾。

因此不需要为互不相关的对象引入一个全局调度器，才能获得线性一致性。这让对象实现、验证和执行具备模块化空间。

### 5.2 能组合对象，不等于组合出事务

假设每个键都是独立对象，只提供单键操作，可以分别检查它们的历史。这正是许多 KV 检查器按键切分问题的理论背景。

但如果应用想让“从 A 扣钱”和“给 B 加钱”成为不可分割的一次转账，这两个单键操作之间仍可能被其他操作插入。定理没有将它们变成一个新的原子操作。

若 API 包含跨键原子操作，就必须把这个操作的规格和对象边界建模进去，不能继续机械地拆成各键互不相关的历史。

## 6. 阅读后的检查题

### H′ 为什么只能补返回，不能补任意写入调用？

<details><summary>展开答案</summary>

它解释的是已经发生的调用可能已经生效，只是返回还没出现在观察前缀中。补一个根本没有被调用的写，会凭空改变程序行为，不再是对 H 的解释。

</details>

### 每个键都可线性化，是否意味着系统只允许一个全局锁？

<details><summary>展开答案</summary>

恰好相反，局部性允许不同对象独立实现。一个全局锁可以是简单实现，但不是定义或定理要求；每个对象仍须满足自身的合法顺序与实时约束。

</details>

### 论文提到 nonblocking，是否意味着你的服务无需等待网络？

<details><summary>展开答案</summary>

不能这样推论。这里本批精读到 §3.1 为止；摘要中的性质不是对任意实现进度的承诺。实现仍可能阻塞、死锁或受网络故障影响，不应把正确性条件等同于 lock-free、wait-free 或高可用实现。

</details>
