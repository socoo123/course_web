# Ray：让计算的调用者管理结果的命运

## 1. 从一个大数组为什么绕路开始

设程序要计算两个大数组，再把它们相加。普通按值 RPC 的直觉路径是：生产者把数组发回调用者，调用者又把两个数组发给加法任务。调用者其实只想表达“把这两个结果相加”，却被迫成为数据中转站。

分布式 future 把两个决定拆开：

1. **逻辑决定：** 哪个任务依赖哪个结果。
2. **物理决定：** 在哪执行、什么时候搬数据、哪些副本可复用。

future 是尚未得到的结果的引用；结果可以留在远端。调用者先得到句柄，继续提交其他工作；系统等输入就绪再执行消费者。如果消费者与一个输入恰好同机，就可省去该输入的跨机复制。

但省掉复制并非免费：当所有值都按值传走，生产者交付后即可忘记；当其他任务还持有指向它的引用，系统必须知道**谁还需要这个值、谁负责让这个值最终可用、何时可以回收**。本讲的中心就是这份控制状态怎样分布。

## 2. 先分清三种“拥有”

用下面的概念程序固定角色；这是解释用伪代码，不是要求安装运行的 Ray 示例：

```text
P 调用 A
A 调用 B，得到 future x
A 调用 C(x)，得到 future y
```

假设 A、B、C 分别在 W1、W2、W3 上执行：

| 身份 | x 的对应者 | 负责什么 |
|---|---|---|
| owner | 执行 A 的 W1 | 保存 x 的控制元数据，安排 B，追踪使用者，决定回收与恢复 |
| producer / executor | 执行 B 的 W2 | 实际算出 x 的值 |
| 数据所在节点 | 起初通常是 W2 所在节点的 object store | 保存大对象字节；以后可有其他副本 |
| consumer | 执行 C 的 W3 | 使用 x 的值 |

**调用 B 的一方拥有 B 返回的 future；不是执行 B 的一方拥有它。** 这里的 ownership 是运行时协调责任，不是对象字节必须在 owner 内存，更不是可写权限。

如果 C 只是接收普通 future 参数，系统会先解析成值再执行 C；如果 A 传的是论文 API 中的 `shared(x)`，C 收到可继续传递的 future，成为 borrower。后者允许 C 决定接下来调用谁，而不必先读入大数组。

同一个 W3 可以同时借用 x，又因为调用 D 而成为 D 的返回 future z 的 owner。“owner/borrower”是相对于具体对象的关系，不是机器终身固定的角色。

## 3. task 与 actor：能保留状态，便多了一笔恢复债务

普通任务接收参数并产生结果。actor 则是可被多次调用、在调用之间保留本地状态的计算实体：模型 actor 可让权重留在 GPU，路由 actor 可累积一批请求后再发送。actor 的结果仍可以是不可变对象；**actor 内部状态可变，不等于 object store 的对象可原地变更。**

actor 构造调用也有 owner；系统把 actor 固定到一个 worker，其租用资源保持到 actor 不再被引用。论文保证对**同一调用者**按提交顺序执行 actor 任务，不应扩写为多个调用者共享一条全局先来先服务顺序。

反例：Counter 每调用一次就加一。worker 崩溃后重新运行构造函数，只会创建初始 Counter，不会自动找回崩溃前的 100。要恢复这个 100，需要应用状态的持久化、检查点或专门重放机制。Ownership 提供定位、检测、重启的基础设施，论文没有给任意 actor 状态提供透明恢复。

## 4. 为什么按 caller 分片，而不直接 hash 对象 ID

中央表可记录每个 future 的任务、使用者、位置与值。它容易决定谁来恢复，却也让每次任务提交、引用登记、结果查询经过中央服务。对执行几毫秒的任务，一次额外往返已占相当比例。

按对象 ID 散列可分摊容量与吞吐，却未必减少关键路径：新任务仍要去远程 shard 登记。Ownership 则利用程序结构：caller 创建 future，又常常把它交给下一任务，因此把元数据放在 caller 能把最常见的同步写变成本地写。

这是**同步但本地**，不是“完全不用记录”。owner 仍保存足够状态；有借用、远端调度和数据搬运时仍有通信。

### 4.1 一个简单成本模型

设用户计算时间为 t，每任务额外控制成本为 h，忽略排队与重叠时，计算占比为

$$
\eta=\frac{t}{t+h}.
$$

当 t 很大，减少一点 h 意义有限；当 t 与 h 同量级，控制面设计直接决定有效利用率。这是编者模型，不是论文测量值。它解释的是为什么本论文关注细粒度任务，而不能据此预言任意程序的实际加速比。

### 4.2 分片能力仍受程序提交结构约束

若所有任务都由一个 driver 产生，该 driver 仍有提交吞吐上限。增加 worker 不会使单线程控制逻辑自动并行。程序可以把控制逻辑下放给多个嵌套任务，各自创建和管理一组 futures，才会自然形成多个 ownership 分片。

进一步，若多个子任务都借用同一大输入，不能让每个子任务再调用都回根 owner 增减一次全局计数；否则提交扩展了，计数仍集中。这正是分层引用计数需要和嵌套任务一起设计的原因。

## 5. 第一个不变量：发出任务以前，owner 必须知道它去哪里

future 可以先于结果甚至先于最终放置位置存在。消费者没拿到值时，无法自行判断“生产者慢”“还在排队”“生产者已经死亡”。因此需要一个明确的恢复协调者。

把安全要求写成概念上的先后关系：

$$
\text{记录下一调度位置}\ \prec\ \text{向该位置转交任务或请求}.
$$

owner 向 scheduler 请求资源；scheduler 可能授予 worker，也可能建议另一个节点。owner 先更新本地位置，再继续联系下一站或向 worker 派发。这样每一次转交都不会脱离 owner 的视野。

**反例：** 表里还写 A 节点，但任务已经被直接转发到 B；A 随后失效，owner 可能错误地把 B 上的运行任务当作失败。先派发、以后异步补位置，会把故障判定变成猜测。

不要把这个约束套到所有字段：大对象副本的位置可异步更新。读者找错位置时可以询问该节点并重新查找；而任务位置用于判断谁失败和谁应重跑，约束更强。论文所谓元数据一致性，首先指元数据与实际执行状态对应，并不是在这里提出新的副本读写一致性模型。

scheduler 的资源租约也不等于旧方案的“每任务存活租约”：前者使 owner 获得一段时间内直接向 worker 发任务的资格；后者用租约过期协调失败判断。论文用 Ownership 替换旧故障协调方式，仍然使用资源租约。

完整往返路径、复用限制与 actor 调度见[课程资料 §3](#/c/mit-6.824-2021/lec/update-ray?v=materials)。

## 6. 第二个不变量：本地不用了，不等于全局没人用了

设 A 创建 x，借给 C；C 又把 x 借给 D。现在 A 删掉自己的变量，C 返回，但 D 仍在执行。若只看 A 的本地引用数，x 会被过早释放。

需要追踪的不是一个进程里的变量数量，而是：

- 本地仍可访问的引用；
- 已提交、尚未完成的依赖任务；
- 继续持有引用的 borrowers；
- 包含该 future 的其他在作用域内的嵌套 futures。

可以把值回收的必要条件概括为：**没有任何活的使用路径再要求保留该值。** 这不是把“所有任务已返回”当作判据：actor 可能把借来的引用放进状态，子任务返回后也可能还有它提交的任务在运行。

分层方案让 borrower 在本地记录继续分发的关系。回收时，若 C 已无本地引用和待完成任务，它把仍需追踪的 borrower 集合交回 owner；owner 继续追踪 D。C 的完成消息不是“全世界不再使用 x”的证据。具体树的合并、死亡通知和消息搭载见[课程资料 §5](#/c/mit-6.824-2021/lec/update-ray?v=materials)。

### 6.1 值与配方有不同寿命

假设 y=C(x) 已算好，活跃代码只使用 y，不再使用 x。x 的大块内存可以释放；但若 y 的副本以后丢失，重算 y 还要重算 x。因此 x 的 lineage 可能仍需保留。

系统为此有两笔账：

1. **值使用关系：** 现在谁还需要物化数据。
2. **lineage 使用关系：** 将来谁的重建还需要这个配方。

后者在依赖任务的 **Task 记录被回收**时才减少，不是在依赖任务刚执行完成时就减少。若把两者合成一个计数，就会在“无限保留大数据”和“过早删掉恢复配方”之间犯错。

`Release` 也不等于立即擦除：它让大对象可被淘汰；空闲内存里的副本仍可能帮助后续恢复。

## 7. 第三个不变量：等待者必须有活着的恢复责任人

### 7.1 executor 或对象副本丢失，owner 仍活着

回到 W1=A、W2=B、W3=C 的例子。若 W2 所在节点失效，x 的 owner W1 仍知道 B 的调用描述：

1. 先找可用的 secondary copy，能提升为 primary 就复用。
2. 没有副本则重跑 B。
3. B 的输入也丢了，就沿 lineage 递归恢复所缺输入。

如果只是 W3 的 C 失败，y 的 owner W1 重提 C；不应因为“C 用过 x”就无条件重跑全部祖先。仍在的值和内联参数都是回溯的停止边界。

### 7.2 owner 丢失，存在副本也不够

若 W1 死了，C 手里的 x 句柄仍指向旧 owner。即使 W2 上还有数据，谁能保证以后数据丢失时还有人恢复？谁掌握完整使用者与任务状态？本方案不让任何 borrower 随意接任 owner。

它选择 **fate sharing（命运共享）**：与失败 owner 相关的对象、未完成任务及持有引用者一同失效，资源被回收。上层 P 的 owner 机制重新提交 A；新 A 再创建 B、C，从而建立指向新 owner 的新引用关系。

这里容错的意思不是“每个旧句柄永远能继续使用”，而是通过使失去恢复责任人的计算退出，再由仍活着的祖先重建，使应用继续前进。代价是故障影响范围可能比原先坏掉的进程更大。

### 7.3 反例：把 future 返回给祖先

A 把自己拥有的 future x 返回给 P，P 就成为 borrower。A 的 worker 失败时，P 也可能需要 fate-share；影响并不总局限于“向下杀一棵子树”。不能把调用树与对象共享关系视为完全相同的树。

重建最终依赖有存活祖先可重新发起工作。论文明确整个应用与 root driver 命运共享；它没有通过递归无限向上恢复来消除 driver 边界。

## 8. 与 Spark 对照：继承 lineage，改变控制结构

| 问题 | 2012 RDD / 已学 L16 | 本文 Ownership 方案 |
|---|---|---|
| 主要表达单位 | 分区集合上的粗粒度转换 | 动态任务、单个返回对象、actor |
| 何时创建后续计算 | driver 构造转换和触发 action | 执行中的任务也可继续调用子任务 |
| 数据依赖 | RDD/分区之间的转换关系 | future 参数与创建该对象的任务 |
| 可重算状态 | 缓存分区可由确定输入与 lineage 重建 | 对象可由保留的任务描述与依赖重建 |
| 控制面生存问题 | 论文实现尚不容忍 scheduler failure | owner 失败通过 fate sharing 和祖先重放处理，root driver 仍是边界 |
| 状态表达 | 新 RDD 版本，而不是任意原地修改 | 共享对象不可变；actor 可持本地可变状态，但状态恢复另议 |
| 内存责任 | 缓存、shuffle、checkpoint 各有角色 | primary pin、secondary cache、分布式值计数及 lineage 计数分别管理 |

不要把 Spark 的“窄/宽依赖”直接拿来分类 Ray 的每个函数；也不要把 Ray 能动态建任务图解释成“任何细粒度状态变化都能靠 lineage 还原”。两者都需要保存重算所必需的输入和配方，且都不自动把任意外部副作用变成 exactly-once。

更完整的 RDD 粒度与 checkpoint 讨论见 [L16 课程笔记 §3–7](#/c/mit-6.824-2021/lec/lec16?v=notes)、[课程资料 §4–6](#/c/mit-6.824-2021/lec/lec16?v=materials)。

## 9. 用三个反例检查恢复承诺

**反例一：任务向银行发出扣款，然后崩溃。** 重跑可能再次扣款。论文假设可安全重执行的幂等计算，不提供跨外部系统的去重或提交协议；需要应用自己的事务、日志或幂等设计。

**反例二：任务每次抓取一个正在变化的网页。** 保存 URL 不等于保存输入版本。即使没有重复扣款，也不保证重算结果与第一次相同；应用必须决定何种重放语义可以接受。

**反例三：actor 将借来的 x 放进长期状态，随后 x 的 owner 死亡。** 引用计数可以追踪这种保存，但论文透明 owner 恢复的论证要求 actor 不在本地状态中保存 borrowed DFuts。**能安全追踪与回收，不等于能自动重建任意状态依赖。**

因此读到“最终 get 会返回”时，要同时带上失败模型、任务重执行假设、存活恢复根以及所支持的共享模式。论文为需要的应用提供透明对象恢复选项，不是一项无条件适用于全部 Ray 程序的保证。

## 10. 自测

### 题 1：A 调用 B，B 在另一台机器创建大数组 x。谁是 x 的 owner？

<details><summary>答案</summary>

执行 A 的 worker。B 是生产者，B 所在节点的 object store 通常保存 primary；三种身份可以分离。

</details>

### 题 2：Router 只想选模型，为什么还要 SharedDFut？

<details><summary>答案</summary>

普通 future 参数会在执行 Router 任务前隐式解析成值；first-class future 允许 Router 接收并转发句柄，避免把大图像搬进 Router 再搬出。这里是论文抽象 API，不能直接当作现代 Python 方法名。

</details>

### 题 3：对象位置可以异步更新，为何任务位置不能一律如此？

<details><summary>答案</summary>

旧对象位置可在读取时查询和纠正；任务位置还用于失败判定。若任务已转到 B 而表里仍是 A，A 失败可导致错误重试。owner 在每次转交前本地同步记下下一位置。

</details>

### 题 4：C 借用 x 后再交给 D，C 返回就能回收 x 吗？

<details><summary>答案</summary>

不能。D 可能还在使用。需要保留/转交 borrower 跟踪；C 无本地引用并不说明整个借用树已经空了。

</details>

### 题 5：x 当前没人读取，但 y 的 lineage 依赖 x，应永远 pin x 吗？

<details><summary>答案</summary>

不用把值与配方混为一谈。x 的值可以释放，x 的任务描述则按 lineage 计数保留，直到依赖它且可能重跑的任务记录都被回收。

</details>

### 题 6：C 调用 D 得到 z，D 的 worker 失败，谁重提 D？

<details><summary>答案</summary>

执行 C 的 worker 是 z 的 owner；它仍活着时负责重提 D。不是最初创建 x 的 A，也不是任何等待 z 的进程抢着重跑。

</details>

### 题 7：B 的节点死亡，与 A 的 worker 死亡，处理一样吗？

<details><summary>答案</summary>

不一样。前者丢 executor/值，但 owner A 可协调复用副本或重算。后者丢失管理 x、y 的元数据，触发 fate sharing，由 A 的上级重建 A 及相关计算。

</details>

### 题 8：重启 actor 构造函数，就能还原计数器与待处理请求队列吗？

<details><summary>答案</summary>

不能。重启只恢复 actor 的存在与初始构造；可变业务状态需要额外恢复设计。论文视频应用的 Redis checkpoint 是应用层方案，不是给所有 actor 自动拍快照。

</details>

### 题 9：ownership 分散在 worker，就能让一个 driver 无限提交任务吗？

<details><summary>答案</summary>

不能。控制逻辑仍集中时会受 driver 吞吐限制。嵌套任务分散提交、first-class futures 分散借用，以及分层计数共同帮助扩展。

</details>

### 题 10：4400 多万状态的模型检查证明了今天 Ray 所有 actor 恢复吗？

<details><summary>答案</summary>

没有。附录 B 只报告有限深度与数量的抽象模型检查，且明确排除 first-class futures 和 actors；也不是对现代实现源码的端到端证明。

</details>
