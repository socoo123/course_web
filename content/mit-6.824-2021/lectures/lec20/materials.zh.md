# Blockstack 2016 论文精读：只把必须全局一致的状态放到链上

## 1. 论文的问题不是“用区块链替代所有存储”

**摘要、§1–2；PDF 第 2–4 页，印刷页 181–183。**

论文报告了两段工作：先在 Namecoin 上运营身份与公钥服务，再把经验转化为基于 Bitcoin 的 Blockstack 命名和存储系统。前一阶段处理了超过 33,000 个条目、200,000 次交易；摘要给出的新系统用户数是 55,000。这些是论文时点的部署规模，不是当前产品数据，也不是性能基准的并发用户数。

核心需求是：用户可以选择可读名字；名字绑定某个密钥拥有者；没有单一中心机构能随意改掉绑定。它面向名字到任意值的认证，而不只面向付款。

作者用一个重要区分描述区块链：**逻辑上集中，组织上去中心化**。所有节点应接受同一个操作顺序、同一个全局状态，但没有唯一管理员维护这份日志。不能把“去中心化”理解成每个用户可自行解释同一名字却仍称为全局唯一。

论文 §2 对 Zooko 三角采用“人类可读、强所有权、去中心化”的表述；2021 课堂更强调“全局唯一、可读、去中心化”。二者讨论相近目标，但不是同一份形式化不可能性定理。链上名称的所有权也不是对真实姓名、邮箱或组织身份的证明。

### 1.1 Namecoin 提供了什么

Namecoin 从 Bitcoin 分支发展出自己的链和命名操作，最初希望提供不依赖 DNS 根管理的名称—记录映射。它支持命名空间、登记、更新、转移以及到期重注册。

登记分为先 preorder 名称承诺、再揭示 name-value 对，以减少未确认登记被抢跑的风险。论文把它称为 two-phase commit method，但这里是**承诺—揭示式名称登记**，不是事务课程里协调多参与者原子提交的 2PC。

名称费付给不可取回资金的地址，以提高囤积大量名称的成本。Namecoin 当时统一规定定价和到期规则，名称 36,000 个区块后到期，约八个月。这个数属于 Namecoin 背景，不能直接套成 Blockstack 所有命名空间的固定期限。

### 1.2 实际服务并非每个用户亲自完成所有步骤

作者 2014 年 3 月上线的服务在 Namecoin 的 `u/` 空间登记身份资料。服务先代用户登记并支付费用，再把名称转到用户控制的加密货币地址；默认有 ECDSA 公钥绑定，部分用户另加 PGP 密钥。

这说明“最终所有权由用户密钥控制”可以与集中式注册入口并存。入口如何交付密钥、用户怎样确认名字，仍是实际信任路径的一部分，不能从底层链去中心化推导出应用入口从未受信任。

## 2. Namecoin 运营经验：安全不仅取决于算法名称

**§3.1–3.6；PDF 第 5–7 页，Figure 1–3。**

### 2.1 算力集中是观测，攻击能力是威胁，不等于所有攻击都发生过

作者发现单个矿池长期超过 Namecoin 一半算力，某段时间超过 60%，曾观察到某周约 75%。Figure 1 分别画周分布和日分布，纵轴是算力百分比，主要对比 Slush 与 F2Pool；其目的在于展示持续集中，不是某次瞬时随机出块领先。

多数算力可以威胁近期链历史，使审查、重组或双花更容易。它不能凭空得到用户私钥，也不能让未满足验证规则的任意签名成为有效。不能把“可控制排序”扩写成“可伪造所有用户授权”。

软件与网络同样影响安全。论文引用过可盗取名字的 Namecoin 漏洞，并比较了 2016 年 1 月约 170 个 Namecoin 节点与约 4,600 个 Bitcoin 节点。维护力度、漏洞修复与抗拒绝服务能力，都是当时迁移决策的依据。

“Bitcoin 是最安全的链”是作者结合 2016 年环境得出的判断，不是跨时代的定理。论文的普遍启发是：不要只复制一种共识算法，就假定新网络具有原网络相同的攻击成本和维护水平。

### 2.2 出块延迟与交易被收录是两种指标

Figure 2(a) 是 2014 年 3 月至 2015 年 4 月区块间隔的互补累积分布，纵轴为对数尺度的 $1-\mathrm{CDF}$。图中给出 50/90/99/99.9 分位为 7/22/46/78 分钟。它不是一次应用写等待多次确认后的完整延迟分布。

Figure 2(b) 按区块高度画相邻出块时间，在约 192000 高度出现显著尖峰。作者调查后归因于带大量数据字段的交易触发性能问题，导致 Namecoin daemon 崩溃，矿工不能稳定出块。区块链协议仍在，实际软件却让服务迟迟无法登记名字。

另一次事故更容易被误诊：Figure 3 上半图的出块确认时间相对正常，下半图中被接受的交易数却常接近零，远低于发送目标，偶尔集中进入一个块。作者尝试升级和重广播，问题仍持续一周以上。

所以监控“平均十分钟出一个块”不足以保证命名服务有可用吞吐。需要另外观察自己的交易是否持续被纳入链。

### 2.3 selfish-mining-like，不应改写成已证实恶意动机

作者观察到大矿池、长等待后快速连续出块、较多被拒块等现象，认为与 selfish mining 类似。但论文明确保留了矿工是否有意攻击的不确定性。

本节应读成：生产网络出现了与相关攻击机制相符的行为，值得设计者重视；不能据此认定某个矿池在已证明执行特定攻击。论文采用的算力阈值也是该段所引用模型的背景，不是所有自私挖矿策略通用的充要条件。

### 2.4 升级与合并挖矿的激励边界

改变定价等共识规则，需要节点升级。对把 Namecoin 当副业的矿工，维护另一份软件未必值得投入工程时间；作者观察到大升级后部分矿工退出，未再返回。建议把破坏共识的变更与普通升级分开，并考虑维护者的激励。

合并挖矿让部分 Bitcoin 矿工用已有计算成果参与 Namecoin，但并不意味着全部 Bitcoin 算力都在保护 Namecoin。论文给出 F2Pool 在 Bitcoin 占约 30%–35%，在 Namecoin 却超过 60% 的对比。

关键分母是**真正参与这条链的算力**，不是理论上可以参与的所有算力。只有足够多主链矿工实际支持相应软件，才可能改善副链的集中问题。作者关于当时无法支撑许多安全链的结论带有明确时代条件，不外推为 2026 年现状。

## 3. 四层架构：排序、解释、发现和存储分别负责什么

**§4.1–4.3；PDF 第 8–10 页，Figure 4。**

数据大小、确认延迟、区块吞吐、不断增长的历史，是四个约束。论文当时举 Bitcoin 约 69 GB、约 413,000 个块以及启动需数天等量级；这些数字只说明 2016 年设计压力。

| 层次 | 保存或处理的对象 | 安全职责与限制 |
|---|---|---|
| Blockchain | 包含 Blockstack 元数据的合法交易及顺序 | 为命名操作提供底层共识与历史；不解释所有应用含义 |
| Virtualchain | 从交易提取操作，判断有效性，构造名称状态与历史 | 实现名称状态机；规则必须一致，不需要矿工理解新语义 |
| Routing | zone file，含 URI、数据定位和验证信息 | 让客户端找到数据；内容通过链上承诺的哈希验证 |
| Storage | 实际文件、签名、可选加密内容 | 承载大体积数据与可用性；不能靠签名保证最新或永不丢失 |

前两层是控制平面，后两层是数据平面。Figure 4 用颜色区分 x、y、z 的名称及对应 zone file，画出普通 Bitcoin 交易与命名交易交错出现；virtualchain 只把相关有效操作纳入自身状态。图上数据库的 name history 表示更新历史，不能仅凭示意方格推断具体数据库 schema。

### 3.1 virtualchain 不是另一个独立挖矿网络

其创新在于：底层仅需接受带附加数据的合法交易，上层自己解释新的操作和状态机。新增命名语义不必要求所有 Bitcoin 矿工升级。

在选定链历史、选定高度和一致规则下，重放应得到相同状态。若上层版本对同一操作的有效性有不同看法，底层交易顺序一致也可能产生不同名称视图；FAQ 的 consistency hash 问题专门指出这一点。

“可支持任意状态机”是这层抽象的表达能力，不表示本论文实现了现代智能合约平台、Stacks 共识或另一种代币机制。论文当前实现只定义了命名和存储状态机。

### 3.2 2016 routing 是 DHT，不要改写成后来的组件说明

论文 §4.3.3 采用 Kademlia 式 DHT 保存 zone file，只接纳哈希已经在链上出现过的文件，相当于存储白名单。zone file 较小，约 4 KB，因此多数生产服务器还保留全部 zone file 的副本。

它们沿用 DNS zone file 的格式，不表示 DNS 根服务器为这些名字授权，也不表示任意 DNS 域名自动属于链上同名用户。

2021 讲义另用 Atlas 描述 zone-record 服务，并用 Gaia 描述统一用户存储接口；2016 PDF 没有这两个组件名称。本文按各自来源保留边界，不用现代文档把旧论文“修正”为新版设计。

### 3.3 可迁移的是分层，不是无条件继承同等安全

论文认为可以更换底层链，但其安全性和可靠性会随底层改变。当时由核心开发者决定某一软件版本支持哪些链，应用可选择继续运行旧版并留在旧链。

因此迁移涉及版本选择与群体协调，不能解释成一个无人决定、永不分歧的自动 failover 协议。分层减少接口耦合，却不会消除治理和迁移信任问题。

## 4. 名称状态与两种文件绑定

**§4.3.4–4.4.1；PDF 第 10–11 页，Figure 5。**

### 4.1 可变与不可变，区别不在“永远禁止写”

可变模式中，zone file 保留稳定 URI，文件含用户签名。写者签名、复制新内容；读者验证 zone file 哈希和文件签名。只要定位与验证信息不变，更新文件不需要链交易。

不可变模式另在 zone file 的 TXT 记录中保存 $H(data)$。读者除前述检查外，还验证内容哈希。若发布新内容，必须改 zone file，再上链更新其哈希。

所以“immutable”指一个内容哈希锁定特定字节串，不是禁止名称后来指向新版本。它把内容版本选择也纳入链上承诺，因此付出链确认延迟。

论文称不可变模式有助于验证最新版本，前提是读者已取得正确、足够新的命名状态。若攻击者连旧链状态与旧 zone file 一并回放，只验证自洽哈希并不足以知道自己落后。可变模式则明确把版本机制留给读写者；单个签名不提供全局新鲜度。

原文有“data values are signed by public keys”一类不精确表达；技术过程应是私钥生成签名、公钥验证。数据可公开验证不等于默认保密，加密是另一个操作。

### 4.2 Figure 5 的状态机比“最早名字 wins”更具体

状态包括 absent、preordered、registered、revoked：

- absent 经 PREORDER 到 preordered；有效 REGISTER 后进入 registered。
- preorder 过期可回 absent。成功注册后，其他先前 preorder 失效；单有最早 preorder 并不等于永远拥有该名。
- registered 中可 UPDATE、TRANSFER、RENEW。转移改变以后谁有权签署名称操作，不等于自动重加密并迁移所有旧文件。
- REVOKE 进入 revoked，期间拒绝继续操作；过期后才可能重新登记。registered 名称到期也会回 absent。

论文说“最先成功写入 preorder 和 register 两步的用户”获得名字。具体时限、承诺编码和授权检查必须由实现规则决定，不能由课堂的 `hash(name)` 简图猜造。

### 4.3 命名空间定价与矿工交易费不可混淆

命名空间类似顶级域的分组，用来定义名称价格与续期政策。Blockstack 允许不同命名空间采用不同函数，例如 `.id` 中短的纯字母名更贵，增加长度或非字母字符后价格下降：`john.id` 比 `johnadam.id` 贵，后者又比 `john0001.id` 贵。

也可以创建名称登记价格为零的空间；但这不推出底层链交易费用也为零。名称资源价格、链上交易费、存储服务费用分别有不同用途。

作者报告为创建 `.id` 支付了等值 10,000 美元的 Bitcoin，借此说明开发者也遵守协议规则。它是当时的一次费用，不是注册一个普通用户名称的单价。收费提高囤积成本，却不证明所有好名字都会落到“正确”的真实人物手中。

## 5. SNV：可信哈希让历史证明可以跳跃，但信任起点不能省略

**§4.5；PDF 第 11 页，Figure 6 与两个定义公式。**

小节标题写 **Simple Name Verification**，正文展开写 **Simplified Name Verification**；本文统一简称 SNV，保留原文这个措辞差异。

每个高度 $h$ 的 consensus hash 依赖该块的 virtualchain 操作序列 $V_h$，以及一组几何间距的历史哈希：

$$
CH(h)=\operatorname{hash}(V_h+P_h),
$$

$$
P_h=\{CH(h-2^i)\mid i\in\mathbb{N},\ h-2^i\ge h_0\}.
$$

这里 $h_0$ 是起始块高度，`+` 表示按协议编码组合输入，不是对哈希做数值加法。论文没有在此完整规定序列化细节，也未明确自然数记号是否从零起；理解“按二的幂次引用历史”足够，不据记号猜实现。

### 5.1 两个用途，不要合成“自动获得共识”

第一，比较同高度的 consensus hash，帮助节点发现名称历史是否分歧。底层顺序相同而解释规则不同，也可能分叉；hash 是承诺和检测手段，不是代替 Nakamoto 共识的新投票机制。

FAQ 使用 **Consistency Hashes** 的称呼，并描述分叉后节点只接受同一分支的后续操作；2016 论文这一节重点说明 **consensus hash** 的构造、验证和启动。应按来源区分，不能从简短 FAQ 拼出未提供的完整分叉恢复协议。

第二，一个**已经可信**的较新 $CH(h)$ 可以认证较旧操作。Figure 6 从较新块向较旧块跳跃：先验证某个历史哈希，再把它作为下一步的可信起点，逐步接近标作 T 的目标块。几何引用使验证历史目标所需查询为对数量级，而不必逐块走完所有 Bitcoin 交易。

### 5.2 薄客户端证明与完整节点启动不是同一复杂度命题

新节点可以取得不可信数据库快照与某高度的可信 consensus hash，重建相关 virtualchain 历史、重算哈希，确认与可信值一致后，再处理后续块。

这里节省的是取回和检查大量无关底层交易的成本；不能由“单次历史查询对数次”推断“构造所有名称状态也只需对数工作”。仍要检查需要的操作、状态与承诺。

作者报告使用 SNV 启动约 1–2 小时，而不用时约 2–4 天；前面的 §4.1 对通用 Bitcoin 启动另给 1–3 天。它们是相近历史量级、不同语境的描述，不应抹平成一个精确统一基准。

最关键的未展开处是：客户端凭什么信任初始 $CH(h)$？本节把它作为前提，没有给出普适的无信任发现协议。攻击者若同时提供虚假数据库和自造的“可信”哈希，自洽本身不能证明它是公认历史。

## 6. 读写测量：链下性能不能当作链上登记吞吐

**§4.6；PDF 第 11–12 页，Figure 7。**

实验以 Amazon S3 为后端，对 1、10、100 MB 文件分别进行 25 次试验。Blockstack 需要签名、校验、加解密和压缩；论文称压缩后额外文件空间约 5%，网络性能接近直接访问后端。

Figure 7 的单位是**毫秒**。读图上半部区分总开销（含/不含加密）、解密开销、签名验证与反序列化；正文明确说省略文件下载时间，以突出 CPU 开销。因此不能把图上的“read total”当作包含网络传输的端到端读取时延。

下半部写图还区分加密、签名及序列化、元数据上传、文件上传。100 MB 写图中总时间约 16.852 秒，不含加密的总时间约 9.033 秒，加密分量约 7.782 秒；读图同尺寸的含加密总开销约 12.886 秒。

**原文口径边界：** 正文同时说大文件 CPU-bound overhead 在约两秒量级，但图中 100 MB 的加密与读取总 CPU 分量明显不都只有两秒。本材料不把这句话概括成“100 MB 加解密总是只需两秒”，也不自行猜测作者想排除哪些分量。

这些测量支持“把普通文件更新移到链下后，性能主要跟随存储后端及密码学开销”的论点；不证明链上名称创建也有毫秒延迟，更不等于多个提供者之间具备线性一致或事务语义。

## 7. 迁移经验、带宽竞争与论文结尾

**§5–7、致谢与文献；PDF 第 12–15 页，Figure 8。**

2015 年 9 月，作者把 33,000 个用户从 Namecoin 的 `u/` 迁到 Bitcoin 上的 `.id`；实现报告约 40,344 行 Python。论文给出迁移结果和教训，没有完整公开一个可直接照抄的跨链原子迁移协议。

Figure 8 在同一横轴区块高度上比较全部 Bitcoin 交易、嵌入数据的交易、Blockstack 交易；纵轴交易数为对数尺度，范围约 375000–395000。迁移期间出现明显流量尖峰。论文称 Blockstack 当时占历史数据嵌入交易的 26.9%，不是占全部 Bitcoin 交易的 26.9%。

作者为了不超过区块约 20%–30% 的容量，主动节流，延长了注册总时间。当时 1 MB 区块只提供约每秒 3–7 笔交易，论文认为未来即使升至 8 MB，也不足以直接支撑百万级用户的所有注册需求，提出多链或把多操作装入单笔交易作为后续方向。

迁移还碰到 CoinWallet 压力测试。大量小额交易堆积，作者支付平时 2–3 倍的交易费才能争取收录。依赖一个更安全的公共链，并不意味着独享它的容量；其他使用者会影响自己的延迟和成本。

相关工作讨论 UIA、联盟认证、其他链上命名、Keybase/CONIKS、分布式存储与存储类代币系统。这里已阅读的是本文对它们的定位，以及全部 53 项文献条目；没有进一步阅读全文或核对这些系统的现状。

结论强调四个成果：借用成熟链的安全基础；通过 virtualchain 扩展功能；把普通数据写从慢链移出；利用认证历史缩短启动。所有成果仍受密钥安全、链的共识假设、可信启动点及链下存储可用性约束。

## 8. 2021 讲义与 FAQ 给论文补充了哪些问题

**讲义 330 行、FAQ 174 行均全文阅读；本节只展开课堂或论文未充分覆盖的边界。**

### 8.1 Certificate Transparency 能暴露冲突，不自行选出获胜登记

FAQ 问能否用便宜的 CT 日志替代 Bitcoin。课程回答是：多个日志可以各自记录名称申请，却可能给出不同的先后顺序；公开冲突与裁决谁拥有名字是两件事。若要利用“先到先得”，还必须说明哪个总序是权威的。

这不等于 CT 毫无价值，也不等于任何透明日志都不能再加共识；只是 CT 本身的透明性不能直接替代本设计所需的排序和冲突解决。FAQ 关于“没有加密货币的开放链可能无法做到足够强的分叉解决”明确标为作者猜测，不在这里提升为一般不可能性结论。

### 8.2 密钥恢复与现实身份仍在协议外留下难题

一个可信名字登记服务也未必能可靠判断，声称要恢复某邮箱账户的人是否确实是原主人。邮箱验证、真实身份验证、恢复流程和链上密钥所有权不是同一命题。

FAQ 对邮件 PKI 的困难措辞很强，应该理解为全局身份绑定与恢复的难题，而非断言任何邮箱控制权检查都不可能。它把 Kerberos 称为 PKI 也采用了宽泛用法；通常 Kerberos 的核心是 KDC/对称密钥认证。

2021 讲义描述主私钥只给 Blockstack Browser，每应用拿独立私钥，口令保护静态密钥、活跃使用时存在明文副本。这说明隔离意图，但本批没有读对应实现，不能声称已审计这些机制。每应用隔离也会使同一用户的跨应用共享更难。

### 8.3 用户拥有文件，不等于应用生态自动互通

FAQ 和讲义还提出几个重要问题：公共索引、点赞计数、首页排名等数据往往不属于某个用户；简单按用户分文件，不会自动产生可信的全局聚合。讲义问到删除/修改的存储授权，但未提供完整 Gaia 写认证协议，本材料不猜造。

跨应用共享需要双方理解相同数据格式，单纯使用同一存储 API 不够。群组加密还涉及成员管理、密钥分发和撤销；让离组者无法读未来数据，与让其忘记曾经取得的明文是不同目标。

用户仍需信任能看到明文的应用软件不泄露它；存储端还可能观察访问模式。用户选择应用是一种控制权，不是对应用无恶意的密码学证明。共享、撤销、查询、应用收入和用户存储付费也都影响这套架构能否被采用。
