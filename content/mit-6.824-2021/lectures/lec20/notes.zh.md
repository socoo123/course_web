# L20 课程笔记：把每一种信任要求放回正确的层

## 1. 先回答五个不同的问题

“数据是可信的”太笼统。以读取朋友的共享清单为例，至少要分开：

| 问题 | 需要什么证据 | 单靠什么不够 |
|---|---|---|
| 我找的是哪位现实中的人？ | 可信的名称交换或身份关联 | 字符串看起来像其姓名 |
| 这个名字当前由谁控制？ | 选定链历史上的有效名称状态 | 某台服务器声称的公钥 |
| 取回的文件有没有被冒充或改写？ | 经认证公钥验证签名，或可信内容哈希 | 存储商声称“这是原件” |
| 它是否最新？ | 新鲜的命名状态及相应版本/读取协议 | 一个有效的旧签名 |
| 我能否持续取回它？ | 真实副本、可访问存储与故障恢复安排 | 区块链上仍有文件哈希 |

Blockstack 的核心贡献集中在第二项，以及从第二项延伸出的认证链。其他问题有些得到帮助，有些仍由应用、用户或存储提供者承担。

课堂的待办清单贯穿例子见[中文译稿 14:00–16:00、62:00–67:00](#/c/mit-6.824-2021/lec/lec20?v=draft)。下面把它压缩成推理工具，而不再复述每一步课堂演示。

## 2. 用状态机理解命名，不用“区块链”代替证明

设 $S_h$ 为高度 $h$ 后的名称状态，$B_h$ 为所选链上该块的交易序列，$\delta$ 为同一版本的名称解释规则：

$$
S_h=\delta(S_{h-1},\operatorname{extract}(B_h)).
$$

这是编者对论文 virtualchain 的抽象。要让两个正确节点得到同一名称状态，至少需要：

1. 起始状态一致；
2. 接受的底层历史及顺序一致；
3. 提取、合法性检查和状态转移规则一致。

Bitcoin 主要帮助第二项；它不会自动保证第三项。两版本对某个名称操作的接受规则不同，即使都读取同一 Bitcoin 块，也可能得到不同数据库。consensus hash 可以暴露这种分歧，不能使两个不同程序自动变成同一个程序。

这与 [Raft](#/c/mit-6.824-2021/lec/lec05?v=notes) 的复制状态机思路相通：**共识日志只在状态机规则一致时才导出相同结果。** 不同的是，Raft 主要面对固定成员的崩溃故障；本讲借用开放参与的 Nakamoto 共识，具有不同攻击假设和概率性确认边界。

### 2.1 名称所有权的不变量

对尚未到期、未撤销的已登记名称，能改变其有效绑定的操作必须满足当前所有权及状态机规则。任何人都能向 Bitcoin 发交易，不等于任何人的名称 UPDATE 都会被 virtualchain 接受。

把攻击分开看：

- **伪造更新：** 没有当前授权密钥，合法性检查应拒绝。
- **抢跑登记：** 对尚未占有的名字，攻击者可能争抢日志顺序，需要承诺—揭示。
- **审查或重组：** 威胁底层排序、确认与可用性，不能靠文件签名解决。
- **规则分叉：** 节点运行不同解释逻辑，需要发现并处理版本分歧。

多数算力不等于能伪造签名；有效签名也不等于保证交易会被及时收录。

## 3. 认证链中，每一次间接引用都必须被前一层约束

可把常见读取压缩为：

`可信名称状态 → zone file 哈希 → zone file → URI / 验证公钥 → 数据`

假设从当前名称状态得到 $z=H(Z)$，从路由服务器拿到候选 $Z'$，只有

$$H(Z')=z$$

才能接受它为当前绑定的 zone file。随后按 $Z'$ 中可信的验证信息检查文件签名。这个链条的重要作用是：**攻击者不能同时换掉文件和“用来证明文件是真的”的公钥，除非还突破前一层绑定。**

### 3.1 反例：所有哈希都正确，仍可能在错误的世界里

一个新客户端接受陌生服务器提供的旧名称状态、旧 zone file、旧签名文件，所有局部检查都通过。它证明这些对象互相一致，却没有证明它们是公认的当前状态。

因此安全讨论必须标出信任根：底层链如何取得和验证、确认到什么高度、轻客户端的可信 consensus hash 从何而来。只在图上画出若干哈希箭头，不足以说明系统从零建立了信任。

SNV 的具体公式、几何历史引用和启动前提见[课程资料 §5](#/c/mit-6.824-2021/lec/lec20?v=materials)。它让已有信任可以高效延伸，不能凭空制造信任。

### 3.2 文件可以从敌手那里取，副本仍得有人保存

验哈希让内容提供者无需被信任为“说真话的人”。但提供者可以拒绝回复、删除文件或只提供旧文件；验证失败也不会把丢失字节变出来。

因此“无需信任存储层”准确说是**某些真实性判断不依赖它诚实**，不是存储层没有任何可用性、新鲜度或隐私影响。密文还能暴露请求时机、对象大小等访问模式，端到端加密也不使这些自动消失。

## 4. 把新鲜度移出链，性能提升从哪里来，代价又是什么

| 模式 | 被链间接承诺的对象 | 文件内容更新是否上链 | 能直接验证什么 |
|---|---|---|---|
| Mutable | 稳定路由及验证信息 | 通常不需要，除非更改 zone file | 文件由相应密钥签发 |
| Immutable | 另包含具体内容哈希 | 新内容需更新 zone file 及链绑定 | 内容等于该命名状态承诺的版本 |

二者都不是“任何时候读到的都绝对最新”。不可变模式也以读到足够新的命名状态为前提；可变模式更明确地把文件版本选择留在链外。

### 4.1 版本号只能在已知范围内阻止回退

编者反例：写者先签署版本 7，后签署版本 8。客户端 A 已见过 8，存储再给它 7，A 可拒绝。客户端 B 第一次上线，只见过 7，则不能仅凭 `version=7` 知道 8 已存在。

即使 A 永不接受低于自己的最大版本，仍可能一直停留在 8，而写者已发布 9。**防已知回退不等于证明最新。** 2016 论文只要求应用使用版本机制，未给出解决所有情形的协议；2021 讲师也明确承认不足。

### 4.2 链下可变文件没有自动继承链上的并发控制

若同一用户的两台设备同时读版本 7，分别编辑后发布自己签署的版本 8，两份内容都可能有合法签名。签名无法决定哪份胜出，也无法自动合并修改。

这是编者用来测试接口边界的反例，不是声称论文观察过该故障。应用仍需定义写者模型、冲突处理与存储语义，不能把名字的共识排序视为对所有文件写的事务排序。

与 [SUNDR](#/c/mit-6.824-2021/lec/lec18?v=notes) 的连接在这里：两者都面对不可信存储，但 fork consistency、名称链总序、应用数据最新性是不同契约。不能因为都使用签名或哈希，就说它们提供相同一致性。

## 5. 承诺—揭示防的是什么，不防什么

若申请直接公开名字，对手可以看到未确认交易后争先入链。承诺—揭示先固定申请意图，再公开名字，使“知道明文才开始抢跑”的人不能创造更早的有效承诺。

两个必要区分：

1. 承诺必须有隐藏性。对短、常见名称，裸 $H(name)$ 可被字典枚举。课堂推测有额外参数或 nonce，但未核验编码，本材料不补造协议字段。
2. 防看到申请后的抢跑，不等于防所有囤积或现实冒名。攻击者仍可能早就登记了某个热门名称；定价只是增加成本，不会证明其身份资格。

论文状态机还要求成功完成有效 preorder/register，考虑到期与冲突。不能把“最早广播一个哈希”说成永久拥有名称，也不能把这两步与分布式事务 2PC 混同。

## 6. 数据控制权、保密与易用性是三条不同轴

### 6.1 用户能换应用，不代表应用可以无需信任

把存储与应用分离，用户有机会换 UI、备份自己的文件、在多个应用之间使用数据。但应用运行时若取得明文或私钥，仍可能泄露它们。迁到本机并不自动使供应商代码可信。

每应用独立密钥可以缩小一处泄露的影响范围，却增加跨应用共享的密钥协调。更换应用也需要兼容数据格式，不是只要都支持 `Get` 就能读懂对方的内容。

### 6.2 保密不自动等于可撤回

用数据密钥加密大文件，再把小密钥分别封装给获准读者，可以降低重复加密成本。撤销未来访问时可换密钥、更新分发；已经获得的旧密钥或明文不能靠删除一条授权记录从对方记忆里消失。

课堂 lockbox 是一般设计例子，不是已经核验的 Blockstack 2016 访问控制接口。大群组、成员退出、密钥恢复都是额外协议工作。

### 6.3 去中心化不自动提供跨用户秘密计算

拍卖应用若在用户控制的机器上拿到其他人的秘密出价，仅靠 UI 不显示它们无法保密。这个反例说明“用户控制执行”与“让程序知道但用户不知道”发生冲突。

公共索引、排行榜、点赞总数又提出另一类问题：它们跨用户聚合，未必有一个自然的用户拥有者。链上名称不会自动提供可信查询引擎或全球 SQL。完整课堂争论见中文译稿 20:00–23:00、67:00–80:00；FAQ 补充见课程资料 §8。

## 8. 自测：指出缺失的前提

### 题 1：任意 Bitcoin 交易都能写附加数据，是否就能修改别人的名字？

<details><summary>答案</summary>

不能。链接受底层交易，与 virtualchain 接受名称操作是不同判断。名称状态机仍检查当前所有权、操作类型、状态和授权；无效名称操作不会改变有效名称数据库。

</details>

### 题 2：所有节点拥有相同 Bitcoin 链，名称数据库必然相同吗？

<details><summary>答案</summary>

还需相同起始状态与相同解释规则。软件版本对操作有效性的判断不同，可能形成上层分叉。consensus hash 有助于发现，而非自动消除规则差异。

</details>

### 题 3：攻击者用自己的公钥签好假数据，再把公钥放进假 zone file，能否通过？

<details><summary>答案</summary>

若读者已获得正确名称状态，假 zone file 的哈希不匹配，会被拒绝。若读者连名称状态也盲信攻击者，局部自洽并不足以保护它；关键是认证链的起点。

</details>

### 题 4：文件签名有效、版本号比上次大，是否证明最新？

<details><summary>答案</summary>

不能。仍可能存在更大的已发布版本。版本号能帮助拒绝已知回退，但不知道所有写的客户端不能单凭一个数字证明全局最新。

</details>

### 题 5：不可变存储既然不可变，为什么论文还讲更新？

<details><summary>答案</summary>

内容哈希绑定一份固定字节串；发布新内容可生成新哈希、更新 zone file 和链上绑定。不可变的是该内容地址所指对象，不是名称永不改变。新绑定需要等待链处理。

</details>

### 题 6：可信的较新 consensus hash 能证明旧操作，是否可以让陌生服务器同时给出哈希和数据？

<details><summary>答案</summary>

服务器可以提供数据，但初始哈希的可信性必须另有依据。两者都由攻击者随意选择，只能证明一套自洽历史，不能证明公认历史。SNV 的可信起点是前提。

</details>

### 题 7：名称登记费为零的命名空间，是否表示用户不需任何付款？

<details><summary>答案</summary>

不表示。名称定价、底层交易费与存储费用分属不同资源。论文允许零名称价格，但不承诺矿工免费处理交易或云商免费保存数据。

</details>

### 题 8：用 CT 日志公开每个名称申请，为何还不够？

<details><summary>答案</summary>

透明日志能暴露冲突，但多个日志可能给出不同先后。若协议按全局先到先得分配名称，仍需明确哪个总序生效、如何解决分歧。公开可查不等于已经达成共识。

</details>

### 题 9：链上的哈希永久存在，文件就永久存在吗？

<details><summary>答案</summary>

不是。哈希验证字节串，不保存或恢复字节串。所有链下副本都丢失时，链仍可保留一条指向不可取得内容的有效承诺。

</details>

### 题 10：51% 算力是否可以任意签署受害者的名称转移？

<details><summary>答案</summary>

不能由算力直接得到私钥。多数算力能严重威胁排序、审查、重组和双花，但正常验证规则仍要求有效签名；规则漏洞或密钥泄露是另外的攻击途径。

</details>
