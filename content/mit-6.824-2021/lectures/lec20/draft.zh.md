# L20 中文译稿：Blockstack 与用户控制数据的应用

## 00:00–03:00 最后一篇论文：从去中心化存储走向应用

讲师向不同时区的同学问好。这是学期最后一周：今天讨论 Blockstack，周四由项目组报告工作，所以本次是最后一次论文讨论。

这里所谓去中心化应用，是让用户保有对数据的控制，而不是把数据交给网站统一控制。最近三讲沿着这个方向逐步向上：先用签名日志理解不可信存储，再用 Bitcoin 理解不可信、可能拜占庭的参与者如何达成共识，今天看怎样构建完整应用。

这不是刚出现的想法。九十年代末、二十一世纪初已有 P2P 应用的探索；课堂提到 Napster、Keybase、Solid 等作为历史背景。Blockstack 既是应用架构的一次尝试，也是区块链在货币之外的用途。指定论文最着力解决的，是去中心化命名。

## 03:00–05:00 这次讨论没有预设唯一正确答案

命名系统并不陌生，DNS、各种身份与认证系统都要把名字和对象联系起来。Blockstack 的特殊之处在于，它希望不依赖某个中心管理者。

但今天不同于此前“提出一个技术难题，再给出解决算法”的课堂。去中心化应用是否就是合适方向、Blockstack 是否就是合适实现，都还值得讨论。讲师在 2021 年的判断是，它已有用户群，但尚不足以成为压倒性的成功证明。

因此，这是一篇引发思考的论文。讲师邀请同学随时提问、争论，不需要把所有观点收敛到一个标准答案。这里的产品评价属于当时课堂，不是对今天部署情况的调查。

## 05:00–08:00 传统网站把应用和数据放在同一个控制边界内

先回顾常见网站：浏览器联系网站的应用代码，应用读写数据库，再把结果呈现给用户。网站内部即使跨越多个数据中心，控制结构仍可以是中心化的。

数据可能是帖子、推文、照片、Piazza 讨论，甚至医疗记录。应用能把不同用户的数据组合起来，例如聚合时间线、排序帖子、计算赞与踩。这些功能依赖应用对多份数据的集中访问。

关键分界在用户与“应用加数据库”之间，用户通常接触的是 HTML 或 UI。即使部分 JavaScript 在浏览器中执行，网站仍决定这段应用如何工作、哪些数据能被访问；不能仅凭代码运行在客户端，就说数据控制权已经去中心化。

## 08:00–11:00 成功架构的代价：界面、访问规则和窥探

应用与数据紧密结合，使传统网站容易实现复杂功能，也非常成功。但用户往往不能自由替换应用：网站提供什么界面，就只能按它的方式使用数据。

讲师用本地编辑器作对照。同一个文本文件，可以用 Vim，也可以用 Emacs；用户可以争论哪一个好，并真正作选择。很多网站却不提供相同自由。讲师先举 Gmail，随即承认它不是最好的例子，因为可以经 IMAP 取邮件，换一个邮件客户端；Twitter 这样的封闭使用方式更接近这里要讨论的问题。

网站还能更改访问规则，决定谁能看到数据。它可能为广告分析用户内容，也可能有员工因私人原因窥探数据。用户把数据交出后，很难再控制这些行为。这些痛点推动了另一种架构的探索。

## 11:00–14:00 把分界移到应用与通用存储之间

新图景仍使用云服务，但云端主要充当存储提供者，而不是掌握所有应用逻辑。用户选择把自己的数据存在哪里，例如 S3 或类似云盘的服务，并可先加密再存储。

用户一和用户二可以选择不同应用，例如不同照片浏览器。若双方共享照片，各自的应用从相应存储服务取回被授权的数据，再在用户端组合和显示。

此时关键接口变成通用的存储 API。它不能只为某个网站服务，而要支持照片、待办事项、时间线等多种应用；还要允许用户间、应用间在权限允许的范围内共享数据。控制权变化来自“用户能选择应用和存储”，不是某台物理机器搬到了哪里。

## 14:00–16:00 两人共享待办清单的基本构想

设用户一与用户二共享待办事项。用户一得知用户二的清单名称，下载对应文件，用用户二的公钥检查签名，再把它与自己的待办事项合并显示。

这里没有一个专属于待办应用的中心数据库替所有人完成查询。每名用户控制自己的文件，应用读取和组合被共享的内容；存储服务与具体应用分离。

这样，数据不再只能经某个网站使用。用户可以换程序，决定哪些应用和哪些人有权访问。这解决了一类控制权问题，但还没有解决所有实现难题，下面转向代价。

## 16:00–20:00 通用存储、秘密计算和密钥管理的困难

商业上首先要问，收入从哪里来，谁付钱让开发者把应用做好，用户为什么愿意采用。讲师不打算深入商业模式，主要讨论技术挑战。

第一，通用文件或 KV 接口通常没有 SQL 那么强。数据分布在不同用户、不同提供者那里，不再能轻易对一个集中数据库运行任意查询。约 17 分钟发生屏幕共享调整；字幕在 17:19.839–17:41.120 间没有覆盖，随后继续讲存储接口与 SQL 的差别。

第二，某些功能需要处理用户不该直接看到的秘密。例如拍卖服务要比较出价，又不能把所有出价立即暴露给每个参与者。第三，密码学增加了密钥管理负担：私钥丢失可能意味着无法读回数据，私钥被盗则可能让别人取得访问权。

剩下一个贯穿全系统的问题是命名。本讲重点就在这里，但前面这些困难对各种去中心化应用架构都存在。

## 20:00–23:00 问答：拍卖为什么难，应用一定要在本机吗

**问：出价场景究竟难在哪里？** 假设我的应用既拿到我的出价，也拿到另一用户的出价，以便决定谁领先，但又不能让我看到对方的秘密。若应用在我控制的机器上，我可以修改它，让它显示自己已知的一切。需要另一个可信角色或专门协议来解决，不能仅靠隐藏 UI。

**问：图里的两个应用不同是什么意思？** 就像一人用 Vim，另一人用 Emacs，双方选择不同程序操作自己掌握的数据，而不是所有人必须使用网站指定的唯一应用。

**问：去中心化应用必须运行在客户端吗，能不能放在网上？** 讲师说位置不是根本限制。应用原则上可以运行在别处，关键是用户能决定用哪个应用访问哪些数据，应用也不被绑定到唯一存储提供者。这里区分执行位置与控制权。

## 23:00–26:00 名字连接用户、数据位置和公钥

共享清单之前，需要能指明“我想与谁共享”。读取时，需要知道这个用户的数据在哪里；取回文件后，又需要知道应该用哪个公钥验证它确实来自那名用户。

所以名字至少承担三种连接：名字到用户、名字到数据位置、名字到公钥。后者通常归入 PKI，即公钥基础设施。没有可信的公钥发现过程，拿到一个签名也不知道应该相信哪个验证密钥。

讲师列举 DNSSEC、Web 证书和 Kerberos 作为命名认证背景，随后强调 Blockstack 的目标是去中心化的名称—密钥体系。

> **术语校注：** 字幕与课堂把 Kerberos 宽泛归入 PKI；通常 Kerberos 是以可信 KDC 和对称密钥为核心的认证体系，不能据此说所有 Kerberos 部署都是公钥证书基础设施。本段保留的是课堂对身份基础设施的类比。

## 26:00–30:00 三个愿望：全局唯一、可读、去中心化

讲师提出三个性质：名字在不同人那里指向同一对象；人能阅读和记忆；分配不依赖中心控制者。课堂借用 Zooko's triangle，讨论为何两项容易，三项一起较难。

邮件地址可以全局区分，又容易读，但仍依赖域名和管理机构。随机公钥可由用户独立生成，以极高概率不冲突，却不便人记忆；讲师把随机性与当时实验中的 Clerk ID 类比。

反过来，手机联系人表既可读又由自己管理，但不同人保存的 “John” 可能是不同对象。学生先举 P2P 文件名，讲师用联系人表给出更简单的例子。

这里的“唯一”主要是全局解释一致，不是保证名字对应的真实人物没有冒名者。论文 §2 对三角性质采用“可读、强所有权、去中心化”的措辞，课堂的全局命名版本与之相关，但不是逐字相同的定义。

## 30:00–33:00 利用有序日志决定名称登记先后

基本办法沿用了 Namecoin 的方向：把名称登记作为特殊操作写进区块链。Blockstack 使用 Bitcoin 链，在合法交易的附加数据里放名称记录。课堂用字符串 `6824` 作示例，并提到记录还会指向 zone file 的哈希。

如果两个人都申请同一个名字，日志中先满足规则的有效登记胜出，后面的冲突申请被忽略。这里先用“第一个 wins”建立直觉，稍后再补 preorder 与 register 两步。

Bitcoin 给出操作顺序；节点从头扫描、挑出相关记录、执行有效操作，便可重建名称数据库。真正决定名称语义的是上层状态机，不是 Bitcoin 矿工理解了这个名字。

## 33:00–35:00 与复制状态机相似，但共识假设不同

有同学指出，这和实验里把操作放入日志、依序执行并构造 KV 状态很像。讲师同意：基本模式确实相同。

区别是日志由 Bitcoin/Nakamoto 共识提供，而不是 Raft。对同一条链、同一套解释规则，节点应得到相同的名称数据库。它不是把开放参与者直接放进 Raft，也不能把两种协议的信任与最终性保证视为相同。

回看三个性质：全局顺序让节点能一致选择获胜登记者；名字本身可由人选择为可读字符串；底层不由一个中心登记机关控制。Namecoin 是这个方向的先行者。

> **版本校注：** 这里提到的 2021 Lab 3 是当年复制 KV 主题，不是固定 2026 实验的同号接口。

## 35:00–38:00 可读名字并不自动解释真实身份

即使 `6824` 是全局唯一的可读字符串，你仍不知道它代表课程、零件编号还是别的东西。即使名字看起来像某人的姓名，也不能证明登记者就是你想找的那个人。

另一问题是发现：怎样知道某位熟人的 Blockstack 名称？如何把现实中的人和链上的名字可靠关联？系统给了一个可用起点，却没有一次解决所有身份问题。

**问：Namecoin 做的就是往交易里加记录吗？** 讲师说明，Namecoin 使用自己的链，另有名称价格和操作规则；它不只是 Bitcoin 上一个任意字段。Blockstack 借鉴其命名方式，但采用不同的底层组织。

## 38:00–42:00 为什么不能把整个待办清单放进区块链

Bitcoin 交易可承载的数据有限，写入也慢。若要等若干后续区块降低分叉风险，课堂用四、五、六个块、每块约十分钟说明可能接近一小时。这个量级不是固定最终性上限。

如果每次勾选待办事项都必须这样等待，交互体验显然不好。吞吐同样有限：底层每秒只处理少量交易，无法让所有文件更新都走链。需要把高频、大体积读写移出去。

还有不断增长的账本。新节点若从头读取所有 Bitcoin 交易，会花很长时间，其中绝大多数又与 Blockstack 无关。论文给出加速方案，讲师此时不深入，先集中讲怎样减少链上工作。

## 42:00–46:00 分层图：从 Bitcoin 交易到名称数据库

讲师调出论文架构图，从底层逐层解释。Bitcoin 链混有许多普通交易，只有一部分携带 Blockstack 操作。Blockstack 节点找到这些记录，解释操作，并建立名字到 zone file 哈希的数据库。

附加数据放在交易的 `OP_RETURN` 机制中。课堂把记录简写成“名字 x 加 zone file 哈希”；实际还需要操作类型与所有权等状态机信息。Bitcoin 处理合法交易，上层则判断这个名称操作是否有效。

同一用户可以多次更新 zone file 的绑定，所以数据库也保留相关历史。但每次改绑定都要上链、等待确认并付出费用，因此应尽量少改。virtualchain 这一层负责从公共交易流构造自己的命名状态，而不是另起一套矿工共识。

## 46:00–48:00 哈希验证 zone file，公钥验证应用数据

拿到 `H(zone file)` 后，应用可以从某处获取声称对应的文件，重新计算哈希。只要与可信名称状态中的哈希一致，就能验证内容没有被替换；文件从哪里来与它是否可信，是两件事。

zone file 继续指向应用数据。例如待办应用有一个约定条目 `todo`，其中含 URI 及验证数据所需的公钥信息。另一用户取回待办文件后，检查签名，再决定是否接受。

一个 zone file 可以有不同应用使用的条目。课堂用“待办”“时间线”解释分层；这些是概念例子，不是已经核验过源码的具体字段格式。字幕在 mutable/immutable 的首次介绍处把两者都识别成 immutable，后续问答与论文 §4.3.4 能明确区分两种模式。

## 48:00–50:00 问答：哈希还在，数据丢了怎么办

**问：把数据移出链后，如果文件被删除，岂不是只剩哈希，数据仍会丢？** 学生先确认自己担心的是 zone file。字幕在 48:48.880–49:00.960 有 12.080 秒间隙，恢复时已是讲师说文件约四 KB、可以广泛复制；缺失部分不补成课堂原话。

对于较大的待办数据，讲师举在 S3 与 Google Drive 等不同提供者存多份副本的办法。Blockstack 的存储抽象使这些提供者看起来相似，应用不必分别处理每一家接口。

这解决的是复制安排，不是哈希带来自动恢复能力。文件真实性可以验证，数据可用性仍需要实际保存副本。接着讲师介绍另一种模式：除了 URI 等信息，zone file 还可包含数据文件的哈希。

## 50:00–52:00 两种模式把“更新需要上链”放在不同位置

不可变模式把数据哈希写进 zone file，绑定到特定内容版本。若改文件内容，就必须改 zone file 的哈希，再更新链上绑定。这让读者能把文件与链上承诺的版本对齐，但写很慢。

可变模式只保留稳定的定位与验证信息。用户更新待办文件并重新签名，不必改变 zone file，因此不必每次发送 Bitcoin 交易。名字登记与高频数据写被分离，绕过了很多时延、带宽和记录大小限制。

不过可变模式的签名只说明数据曾由相应密钥持有者签发，不能直接证明这是最新版本。论文提到版本控制；讲师稍后明确承认这方面细节不足。

## 52:00–55:00 问答：只知道哈希如何找文件，改数据是否仍需等待

**问：只有 zone file 哈希，到哪里取文件？** routing layer 接受这个哈希并返回候选文件。可以不信任提供者所声称的内容，因为能够自行验哈希；但它仍需找到一份可用副本。

**问：修改文件改变哈希，不还是得等 Bitcoin 确认吗？** 讲师把两个对象分开：改 zone file 确实要上链；但可变模式下改待办文件，并不改变 zone file 里的 URI 或公钥，所以可以不上链。

**追问：zone file 不是还存着数据哈希吗？** 那是不可变模式。写频繁的文件采用可变模式，不把每一个内容版本的哈希固定到 zone file。

**追问：可变模式怎么知道数据正确？** 可以验证签名，知道数据来自 x；不一定知道是 x 的最新数据。这是认证与新鲜度的区别。

## 55:00–58:00 问答：版本号的局限与公钥替换攻击

论文建议给可变数据加版本号，以发现某些回退。讲师认为描述较模糊，仍不足以保证读到最新版本。他没有给出一个完整的新鲜度协议。

**问：可变文件实际在哪里修改、读取？** 写者修改并签名后放回对应 URI；读者先取 zone file，再按 URI 访问存储。字幕把签名说成“用公钥”，技术上应是私钥签名、公钥验证，本文据此校订。

**问：每个名字只有一个 URI 吗？** 讲师说没有查看实现源码，不能确定完整格式。

**问：如果公钥也在文件里，攻击者能否自造一对密钥，换上自己的公钥并冒充 x？** 不能只替换 zone file 的内容而不改变其哈希。读者先从命名状态取得所信任的哈希，再验证 zone file，攻击者的替代文件过不了这一步。

> **表述校注：** 讲师用“只有登记者能产生这个 zone file”解释绑定，严格含义是只有授权者能有效更新该名字认可的哈希；公开文件本身当然可被任何人复制和提供。验证前提也包括取得正确的命名链状态。

## 58:00–60:00 名称注册为何要先承诺、再公开

名称创建需要 Bitcoin 交易，用户必须有相应资金支付交易费用。流程包含两次操作：preorder 先放名称的承诺，register 再公开名称与相关绑定。

讲师先把 preorder 简化为 `hash(name)`，让学生思考为什么不直接登记明文名称。学生回答：其他人看到尚未确认的申请，可以抢先发交易，争夺同一个名字。

这是 front-running。提交到网络并不等于已经占据链上顺序；如果先把想要的名字公开，对手便可能利用确认窗口抢跑。

## 60:00–62:00 问答：矿工抢跑与字典攻击

课堂用 `google.com` 作示例：你把申请广播出去，矿工或其他观察者看见后抢先把自己的申请写入链，便可能在简单的“先到先得”规则下获胜。这里的字符串只是例子，不表示登记 Blockstack 名称会获得真实 DNS 域名。

先提交隐藏名称的承诺，等其足够稳定，再揭示名称，可以使后来看到明文的对手无法伪造更早的有效承诺。讲师口头举六个或十个区块作为等待示意，不是本文确认的协议常量。约 60:15.839–60:28.799 有字幕间隙。

**问：攻击者预先计算 `google.com` 的哈希，再扫描链，不就能识别了吗？** 讲师同意：真实承诺必须比裸 `hash(name)` 更复杂，应该还有其他参数，例如 nonce，否则可以建立字典。课堂未核验确切字段；不能把这个推测补成指定版本的 wire format。两阶段登记思路来自 Namecoin。

## 62:00–65:00 把名称、路由和签名串成共享应用

重新画两名用户的待办应用。首先，U1 和 U2 必须通过某种可靠方式得知彼此的名字；系统不能跳过“这个名字确实属于我想合作的人”这一环。

U1 查 U2 的名称，获得 zone file，从中找到待办条目的 URI 与公钥，然后经统一存储接口取回文件，检查签名，必要时检查版本信息，最后与自己的清单合并显示。U2 反向执行同一流程。

讲师提到每应用一对密钥的设计：不希望所有应用共享一个极其敏感的主私钥，避免单个应用泄露就影响一切。这里是课堂对应用架构的说明，2016 论文没有完整给出后来 Browser/Gaia 的密钥接口。

## 65:00–67:00 更新靠各自写文件，再由其他人重新读取

用户更新自己的清单文件后，另一用户的应用可以周期性重新取回它，查看变化。这样能构造协作应用，但相较中心数据库多出了名称查找、存储定位、签名验证等步骤。

在中心化版本中，应用只需对集中存放的两份清单作 SQL 查询，再合并显示；去中心化版本的程序员必须处理更多机制。怎样让这种应用同样容易编写，是一个重要障碍。

讲师明确说，这次不分 breakout rooms，而留时间作全班讨论。后续是录像中实际保留的公开问答，没有需要虚构或恢复的分组讨论。

## 67:00–69:00 开放讨论：能否提供全球关系数据库接口

**问：为什么不能直接提供关系数据库，而只提供文件接口？** 难点在于数据分散在世界各地不同提供者，用户各自控制权限，不能像单个数据库那样随意执行全局 SELECT，也不能把所有人的数据先下载到本机。

学生提到 linked-data 一类方案。讲师认为，这可以成为研究方向：若能让用户仍控制数据和位置，又提供可扩展的关系查询，会很有价值。但本论文的 Blockstack 没有直接提供这件事。

接着有人问，它与同样去中心化的 web-of-trust PKI 相比有什么好处，讨论转向命名与密钥发现。

## 69:00–71:00 开放讨论：信任网、群组和全局名称

讲师提到自己熟悉的 Keybase，尤其认为其群组、群组密钥及成员管理设计值得注意。这与先前 SUNDR 里讨论群组的困难有关。

对于 Blockstack 的差异，他强调全局名称：本地信任网中的 “John” 可以只是我联系表里的别名，不一定与你的 “John” 指同一对象。Blockstack 则希望相同字符串在全系统得到一致解释。

讲师还提到 Keybase 把名称 Merkle 树的哈希发布到区块链，便于检查服务行为。

> **讨论边界：** 课堂把 web of trust、本地联系人别名和 Keybase 混在一起举例，并称 Keybase 没有全局唯一名称。这里保留论证意图，但这不足以成为 Keybase 产品的准确命名规格；本文未读取其实现或协议，不把这段评价扩写成已核实事实。

## 71:00–73:30 开放讨论：怎样只让指定的人解密

**问：一直说用户能控制谁读数据，这在系统里怎样实现？** 一种办法是为每位获准用户分别加密，例如只给 U1、U2，就分别用他们的公钥保护数据。

**追问：每增加一个人，都得重新加密整个文件吗？** 可以更精细：用一个数据密钥加密大文件，再把这把密钥放进小的 lockbox，分别给获准用户加密小盒子。这样大数据只加密一遍，随用户数增长的是较小的密钥封装。也可以进一步引入群组密钥。

**问：这些内容放在 zone file 里吗？** 讲师说可能是 zone file 里放相关公钥或间接引用，但自己不确定 Blockstack 文件系统实际如何实现访问控制，甚至没有在此确认它提供了哪些机制。这是一般密码学设计示例，不是已核实的历史 API。

## 73:30–76:00 开放讨论：能否在性能与规模上竞争

**问：这样的系统能否与中心化架构竞争，怎样才有同样的性能和规模？** 讲师明确说不知道。中心化服务扩到数百万用户也不容易，这门课已经看过许多为此解决瓶颈的论文。

若共享范围很小，例如一份清单只与十人共享，问题可能没有那么严重。可以把数据自然按用户分开，计算又由不同用户的机器承担，不一定所有工作都需要经过一个大数据中心缓存层。

但 2021 年课堂能看到的大规模成功部署仍更多来自中心化设计，也受其采用更广的影响。讲师把去中心化方案称作有吸引力的方向，没有给出“必定更快”或“必定扩不了”的结论。

## 76:00–78:00 开放讨论：可变数据的冗余究竟由谁负责

学生重新提出担心：名称或 zone file 可以小而稳定，真正大量的可变数据如何保证冗余？

讲师认为，安排复制是数据拥有者的责任，可以由存储抽象帮助把文件放到多个提供者，例如 Google Drive 和 S3；S3 本身也可能已有内部复制。是否多存几家、购买多少空间，需要实际安排。

zone file 小，容易广泛复制；应用数据则不能仅靠名称链代为保存。课堂最后一句“不必信任存储提供者”应限于可验证的真实性，不能推成不需要它维持可用性或返回最新数据。77:31.840–77:54.080 有本视频最长字幕间隙 22.240 秒，随后进入费用讨论。

## 78:00–80:00 开放讨论：命名费用与更换底层链

**问：使用名字还得付钱，是否浪费，有没有更便宜的办法？** 讲师说，公共链中的货币与矿工激励关系紧密。也不能忘记普通 DNS 域名同样收费，不能仅凭“需要付款”就断言哪一种更昂贵；他没有完整核算经济性。

课堂也提到 Bitcoin 用电成本，并提出是否可用采用其他共识方式的链。字幕把术语识别成 “stake of work”，上下文应是在与工作量证明对照的权益类方案，但没有音轨核验，不补出具体协议。

**问：能直接替换最底层吗？** 讲师认为论文的分层设计正是朝这个方向：它已经从 Namecoin 转到 Bitcoin，原则上可迁往别的链。替换不代表安全假设不变，也不表示已完成任何现代 Stacks 协议升级。

## 80:00–82:00 图上 name history 的含义与正式结束

**问：名称数据库里画的 name history 是什么？** 学生指向架构图中同一名称旁的多个方格。讲师推测它们对应 zone file 不同更新版本，可能保留旧版本；他表示不是百分之百确定，没有把图扩写成完整数据库 schema。

80:49.440–80:59.600 间没有字幕覆盖。随后讲师结束正式讨论，让要离开的同学先走，并预告周四八个项目组展示。那些项目是当年选做项目的安排，不是本路线 2026 实验的变更。

本讲希望大家思考用户掌握数据的架构，同时理解 Blockstack 如何利用区块链实现全局、可读名称。仍有问题的同学可以留下继续问。

## 82:00–84:30 课后问答：项目展示与为何借用 Bitcoin

**问：项目报告应该演示还是准备幻灯片？** 讲师建议少量幻灯片解释做了什么、为什么有趣，再加一个短演示；时间有限，不需要为展示额外准备很多小时，重点是分享已有工作。

**问：为什么把命名交易和普通 Bitcoin 交易放在同一链，而不另建专用链？** Blockstack 最初基于 Namecoin，但观察到其矿工少、某些矿池能掌握超过一半算力，底层容易受攻击。所以希望依赖更广泛使用、较难被对手接管的链。

> **安全校注：** 课堂把多数算力描述为“能对账本做任何事情”，这是过宽的口语概括。多数算力可威胁近期顺序、造成审查或重组；并不因此获得用户私钥，不能任意伪造其签名。论文的具体历史证据见课程资料 §2。

## 84:30–86:30 课后问答：URI 抽象与三角问题是否值得解决

**问：URI 指向 Blockstack 存储抽象，而不是一定直接写成 S3 地址吗？** 讲师认为可以更一般，由文件系统抽象解释，再通过具体后端去 S3、Google Drive 等处取回文件。应用作者不必自己关心各家的接口差异。

**问：客户端把不可读标识符显示成人类可读别名，不就够了吗？为什么一定要追求三角中的三个性质？** 讲师回到联系人表例子：本地显示名确实有用，但不自动产生全局相同解释。

如果学生真正想问的是“全局可读名字究竟有没有必要”，那是完全合理的质疑。即使大家对 `6824` 的链上绑定达成一致，仍要另行知道它在现实中意味着什么。

## 86:30–89:43 课后问答：百年账本、checkpoint 与验证信任

**问：一百年后账本长到很多 TB，怎么办？** 讲师不愿精确预测那么远，但提出可以对由日志构造的状态做 checkpoint，把 checkpoint 哈希放进日志，广泛复制 checkpoint，再从那里继续执行；直觉上类似实验里的快照。

**追问：制作 checkpoint 的一方必须可信么？** 讲师说客户端必须接受相应状态与规则，这可能要求协议变更甚至分叉。他讨论的是一种可能方向，不是证明任何节点可无条件跳过历史验证。2016 论文已有带可信 consensus hash 的 SNV，具体前提另见课程资料 §5。

他也回忆 Bitcoin 论文的历史压缩思路，提到不必一直保存所有交易细节、可保留区块头。这里需区分裁剪、轻客户端验证和完整验证：**仅有区块头不能替代对所有交易有效性或当前名称状态的验证**，也不能把课堂“每个币只记最后交易”的口述当成完整 UTXO 实现规格。

学生将问题归结为新节点启动时的验证开销，讲师认可这个方向，随后互相致谢结束。末条字幕从 89:39.440 延续至 89:44.880，超出元数据片长 1.880 秒；标题按 89:43 收束，归档保留原始时间。
