# ZooKeeper 论文精读：用小内核组合协调协议

## 1. 论文要提供的是协调内核

### 1.1 为什么没有把所有协调需求做成服务器 API

应用需要配置管理、成员列表、角色竞争、锁、队列和屏障。一个选择是为每件事开发独立服务，另一个选择是服务器直接提供很多高层原语。论文选择第三条路：服务端只维护少量带顺序保证的对象，客户端组合出各种协议。

这让一种新协调方式不必以修改服务器为前提。它也避免在服务端把某个请求的完成直接绑定到另一个客户端释放锁上：慢客户端可以阻碍“等它释放锁的应用”，但不应卡住协调服务的基本请求处理路径。

这里的 **wait-free** 应按论文的对象接口语境理解。`create` 可以立即得到成功或节点已存在的结果；服务端没有一个必须等其他客户端释放后才返回成功的 `acquire` 调用。需要等待的逻辑交给客户端，并借助 watch 避免持续轮询。

这不意味着网络分区时每个请求都能完成，也不意味着用这些 API 写出的重试循环保证每个竞争者都在固定次数内成功。ZooKeeper 的写可用性仍依赖多数服务器正常通信。FAQ 给出了并发对象理论中 wait-free 的严格定义，但本页不把它扩写成一个已证明的、无故障假设的端到端进展定理。

论文也提到 universal object 与 Herlihy 层次，用于说明接口表达力。相关外部理论论文没有在本次通读范围内；这里保留其设计动机，不补造证明。

### 1.2 强的写，较弱的读，配上失效通知

论文 §2.3 的两个基本顺序条件是：状态更新线性一致；同一客户端全部请求遵守 FIFO。它将允许同一客户端同时有多个未完成请求的定义称为 A-linearizability，重点是**异步在途不取消客户端的提交顺序**。

普通读由本地副本处理，可以陈旧；会话读取的写前缀不能倒退。watch 再补上“先通知失效，再向该客户端展示失效事件之后的新状态”的约束。

这些条件如何支持 `ready` 发布协议，课堂已完整推演，见[中文译稿 50:00–63:00](#/c/mit-6.824-2021/lec/lec09?v=draft)。本页不再按论文原段落重译这个例子，而把重点放在课堂没展开的配方、实现与评估。

## 2. 数据模型与 API：容易混淆的细节

### 2.1 Figure 1：树组织的是应用元数据

PDF 第 3 页 Figure 1 的根下面有 `/app1`、`/app2`，`/app1` 下有三个进程节点。这幅图表达的是名字空间和应用组织方式，不是服务器复制拓扑。每台 ZooKeeper 副本持有整棵数据树，而不是图中每个子树各在一台机器上。

每个 znode 可以保存数据；除 ephemeral 节点外还可以有子节点。数据采用整块读取／写入，不是通用文件系统的任意字节 I/O。论文实现默认每个 znode 的数据上限为 1 MB，可配置；系统把树放在内存中，目标是协调与配置的小数据，而不是代替大对象存储。

| 概念 | 生命周期或用途 | 不应混同 |
| --- | --- | --- |
| regular | 主动创建，主动删除 | 不是没有复制保护的临时缓存 |
| ephemeral | 创建它的会话结束时自动删除，也能显式删除 | 不等于 TCP 短暂断开就立即删除 |
| sequential 标志 | 名称追加同父节点下的递增序号 | 不是与前两种互斥的第三种生命周期 |
| 数据版本 | 用于发现对同一节点的更新，支持条件写 | 不是名称末尾的排队序号，也不是全局 zxid |
| zxid | 标识有序事务及客户端观察进度 | 不是指定读取历史快照的 API |

### 2.2 比“支持 watch”更重要的接口区别

`exists(path,watch)` 可以对尚不存在的路径注册关注；`getData(path,watch)` 则要求节点存在，否则不会建立同样的 watch。这一区别直接影响锁配方中“先检查，再等待”的竞态处理。

`getData` 返回数据及版本等元信息；`setData`、`delete` 的版本参数表达预期条件。版本为 `-1` 时，论文接口不做版本匹配。需要原子读改写时，不能随手把这个条件关掉。

所有方法有同步、异步形式；异步形式允许调用者做别的工作，也允许同时有多个请求在途，回调遵守客户端操作顺序。没有文件式的 `open/close` 句柄，每次操作带完整路径，减少服务端额外状态。

论文 `sync(path)` 的路径参数当时被忽略。它是把读推进到相关先前更新之后的屏障，不是把树同步到客户端磁盘。

### 2.3 watch 是一次性失效信号

论文中的 watch 触发一次就被移除，会话结束也会清除它。回调告诉应用“你缓存的认识可能过时”，并不包含每次变化的全部内容。

因此一次通知后，即使节点又改变三次，应用也不能要求收到三个额外通知。正确动作通常是重新读取最新内容，同时再注册 watch。它适合维护缓存有效性，不适合当成完整的变更日志。

连接状态事件也会通过回调通知应用，提醒它普通变化通知可能延迟。断连期间不能把“暂时没收到事件”当成状态没变的证明。

## 3. 客户端配方：本片没有讲完的部分

### 3.1 配置、会合点与成员表

**配置管理。** 启动参数给出配置 znode 路径；读配置时注册 watch；通知到达后重新读取并重新注册。应用必须自行决定旧配置何时停用，服务没有替应用透明维护任意内存缓存。

**Rendezvous，会合点。** 调度器决定进程启动位置时，客户端可能事先不知道 master 的地址和端口。先创建一个约定路径，把路径交给 master 与 workers；master 启动后写入联络信息，workers 读或等待更新。这是在位置确定之前先确定一个共同名字。

**成员表。** 每个成员在父目录下建立自己的 ephemeral 子节点，必要时附带地址与状态。列出子节点就得到当下可观察的成员列表，watch 子节点变化后重新读取。没有唯一成员名时，可以用 sequential 分配名字。

成员表反映的是**会话状态**，不是完美故障探测器。进程可能仍活着，只是与服务隔离；恢复连接后的进程必须处理原会话已经失效的事实。

### 3.2 最简单的锁：排他创建与失联清理

指定一个锁路径，竞争者尝试创建 ephemeral 节点。成功者持锁；节点已存在时，失败者观察其存在性并注册 watch，删除后再次竞争。持有者主动删除，或会话过期使节点自动删除，都能让后继继续。

这里有一个重要竞态：首次创建失败后，锁可能恰在设置 watch 之前被删除。不能不看 `exists` 的返回值就睡眠。如果 `exists` 已返回不存在，应直接重试竞争；若返回存在并设置好了 watch，才等待变化。用一次操作同时取得状态和关注资格，才不会落入“变化已发生，通知没注册”的空档。

这个算法的缺点是 **herd effect（惊群）**：锁一释放，所有等待者同时醒来、发送竞争请求，但最终只有一个胜出。

### 3.3 无惊群锁：排队，每个人只观察前驱

PDF 第 6 页的配方把一次竞争表示成一个 `EPHEMERAL|SEQUENTIAL` 子节点。其逻辑可以独立理解为：

1. 为自己创建一个带顺序编号的请求节点。
2. 读取该锁目录里的请求集合。
3. 若自己的编号最小，取得锁。
4. 否则找当前紧邻自己的较小编号节点，原子地检查它是否存在并设置 watch。
5. 它仍存在时等待；它已不存在或收到事件后，回到第 2 步重新判断。

释放时只删除自己的请求节点。排队者长期失联、会话过期后，其节点也会自动移除。

为什么一次陈旧列表不会让两个客户端都错误地认为自己最小？读列表在创建自己节点之后，FIFO 要求它至少包含自己的创建。所有编号比自己小的创建都在更早的写前缀里，不能有一个更小编号的创建后来才插到前面。陈旧视图可能保留一个实际已删除的前驱，导致多等或多读，而不是凭空越过一个仍然有效的早到竞争者。

**watch 触发不等于取得锁。** 例如 10 持锁，11 排队，12 观察 11；若 11 的会话先过期，12 会醒来，但 10 仍在。它必须重新列目录，转而观察仍挡在自己前面的节点。

图式排队不需要大量新图：`10（持有） ← 11（观察10） ← 12（观察11）` 即可表达。它减少的是无谓唤醒，不是承诺失联不会发生或业务临界区自动回滚。

### 3.4 读写锁与论文伪代码疑点

写锁请求等待所有编号更小的请求完成；读锁请求只需要等待编号更小的**写**请求。多个读者可以一起进入，因此一个写节点删除后唤醒一组读者是正确行为，并非必须消除的惊群。

**原文疑点：** 第 6 页 Read Lock 第 6 行写 `goto 3`，这样会继续使用旧的子节点集合 `C`。2021 FAQ 明确认为这是 bug，并给出外部配方入口。按本页读取的原代码与条件，等待结束后应回到获取 `C` 的第 2 步，再检查此前是否还有写节点；否则可能对已经删除的旧前驱反复检查，却永远不刷新列表。

这里不静默修正论文截图，也不声称已核验 FAQ 外链的实现；正文明确区分原文与校注。

### 3.5 双屏障与锁的边界

双屏障协调一段计算的开始与结束。参与者在屏障路径下注册；达到预定人数后建立 `ready`，让大家开始；结束时各自删除注册节点，等所有参与者退出后才完成屏障。

进入可观察 `ready`，退出可观察某个尚未退出的成员，收到事件后重新检查完整退出条件。仅等一个成员消失还不等于所有成员都结束。这是论文 §2.4 与 FAQ 对退出阶段的共同要点；应用还需要自己决定失败成员是否意味着计算成功或整体重试。

**编者推论：锁不是业务事务。** 若持锁者写完 A、尚未写 B 就崩溃，ephemeral 节点消失可以让新持有者进入，却不会撤销已经写出的 A。若旧持有者只是暂停或网络隔离，它甚至可能在会话过期后继续操作外部资源。涉及外部写入时，还需要资源端识别旧角色／旧世代，或让接任者检查与修复中间状态；仅有 ZooKeeper 锁节点的唯一性不足以证明外部业务原子性。该边界在官方讲义中提示，但本片未展开。

## 5. 实现精读：从请求到可恢复状态

### 5.1 Figure 4：客户请求与复制事务是两层对象

PDF 第 8 页 Figure 4 显示两条路径：写请求经过 Request Processor，变成事务 `txn`，再经过 Atomic Broadcast，最终修改 Replicated Database；读直接访问本地数据库。

关键不是简单地把原始 API 调用原封不动广播。leader 要按已经排定的写顺序计算**未来状态**，其中包括尚未应用到本地数据库的在途事务，然后把一次成功的条件写转成明确的状态赋值：新数据、新版本、新时间戳等。

为什么要看未来状态？如果两个请求都要求版本 4，而前一个已经被受理但还没应用，只检查当前数据库可能错误地让后一个也通过。请求预处理必须考虑前面已安排的更新。

条件不满足或节点不存在时，可以产生 `errorTXN`。因此“写线性一致”不仅是给成功结果排序，还要使条件判断和失败结果也与所选顺序一致。

### 5.2 Zab 的交付顺序与稳定存储

论文把 Zab 的选主细节放在本文范围之外。本次没有读取单独的 Zab 论文，也不以 Raft 的选举细节补足它。

这里需要的性质是：同一 leader 发出的状态变化按发送顺序交付；新 leader 广播自己的变化以前，必须先接上前任已经确定的变化。事务所描述的新状态依赖之前的历史，不能随意跨 leader 重排。

客户端可连接任一服务器，写被转发到 leader。接收客户端请求的服务器，在交付相应状态变化后返回结果。服务器通过多数决定提议，`2f+1` 台容忍 `f` 台不可用是默认配置模型。

实现使用 TCP 帮助保持连接内消息顺序；不能因此取消崩溃恢复和跨连接的协议责任。提议日志与数据库恢复用的 write-ahead log 共用，避免同一消息为两个用途各落盘一次。事务确认涉及持久化，不能用“仅在内存收到了”替代。

Raft 的持久化、快照及客户请求协议继续见 [L5 共享课程资料](#/c/mit-6.824-2021/lec/lec05?v=materials)，这里只讨论 ZooKeeper 的不同表示。

### 5.3 Fuzzy snapshot：先允许快照混合，再用有序事务修复

精确快照对应同一个执行边界。ZooKeeper 则不锁住整棵树长时间等待复制完成，而是深度优先扫描，原子读取**每个节点**的数据和元数据。因此不同节点可能来自不同时间，快照整体未必对应历史上曾存在过的全局状态。

PDF 第 9 页的例子是：扫描开始时 `/foo=f1,version=1`，`/goo=g1,version=1`。随后依次提交：

1. `/foo ← f2, version=2`
2. `/goo ← g2, version=2`
3. `/foo ← f3, version=3`

扫描结果可能是 `/foo=f3`、`/goo=g1`。这个组合从未出现在真实有序执行中。它之所以仍可用，是恢复时保留并重放**从扫描开始起**的事务，而不是把混合快照直接作为完整服务状态开放。

事务记录的是“设置为确定的新值和新版本”，不是“再把当前数值加一”。按顺序重放上述事务，最终修复为 `/foo=f3`、`/goo=g2`。同一事务可能已体现在快照的一部分里，再执行仍能得到规定结果。

需要同时满足三个条件：事务是这种可重复应用的状态变化；重放保持原顺序；日志保留范围覆盖快照期间的变化。单说“我的操作幂等”，不足以证明任意混合快照都能恢复。恢复中间值也不应暴露给客户端。

这与“客户端重发请求要不要去重”不是同一问题：原始请求可能有非幂等语义，服务器编译出的事务才是这里讨论的幂等对象。FAQ 对客户请求编号、去重和流水线跨选主的具体实现使用了推测语气；本页不把这些推测升级成已读源码事实。

### 5.4 本地 watch、会话进度和 sync

服务处理一个写变化时，触发并清除相关 watch；论文描述这条执行路径不会与其他读写并发交错，从而维护通知次序。watch 由客户端所连接的服务器本地管理，不是每个 watch 都要广播给所有副本。

每次读响应附上服务器最后看到的事务 zxid，心跳也包含进度。客户端改连另一服务器时，新服务器检查自己的状态是否至少达到客户端已经观察到的位置；落后就不能立即恢复这个会话。这是“换副本也不能后退”的论文依据，比课堂逐读携带最后一次写编号的草图更具体。

如果 A 写完后，通过应用自己的消息通道告诉 B“配置好了”，这条外部消息不会自动提高 B 的 ZooKeeper 会话进度。B 要确保看见这次变化，需要额外同步；论文给出 `sync` 后读的办法。

论文 §4.4 说 `sync` 在 leader 的先前待处理写之后排序，再沿 leader 到服务副本的队列推进。在没有正常事务可证明 leader 仍有效时，概念上需要提交空事务来确认；论文又说明其当时实现使用超时配置，让 leader 在 follower 放弃它以前先意识到自己失效，从而省略该空事务。

**边界：** 这是这篇 2010 论文描述的实现和时间假设，不是对所有 ZooKeeper 版本的接口承诺，也不是纯异步模型下“随便问旧 leader 就安全”的证明。学习无时间假设的 Raft 读方案请见 L5 §8.3，不复制到这里。

会话超时由 leader 统一判断：在超时时间内若集群没有服务器收到该 session 的活动，便认为它失效。论文客户库在空闲达到 `s/3` 时发心跳，`2s/3` 没听到服务器时尝试切换。它们是论文实现参数，不是本路线实验需要照搬的常数。

## 6. 评估：吞吐、延迟与协调开销是不同指标

### 6.1 先固定实验条件

论文 §5 的机器是双核 Xeon 2.1 GHz、4 GB 内存、千兆网络、两块 SATA 硬盘；不是课堂粗算所假设的 SSD。日志与快照分别写到两块盘。

饱和测试用 35 台机器模拟 250 个客户端，每个客户端至少保持 100 个异步请求在途，每次读写 1 KB。服务端还限制总在处理请求数量，实验配置为 2,000，避免无限排队耗尽内存。客户端每 300 ms 提交完成计数，论文按 6 s 采样。

因此，这组结果是有大量并发工作的系统吞吐，不是单客户端同步调用的往返能力；也不是今天某个 ZooKeeper 发行版的复测。

### 6.2 Figure 5 与 Table 1：加副本不等于给所有工作加速

PDF 第 10 页 Table 1 的两个极端如下，单位为操作／秒：

| 服务器数 | 全读 | 全写 |
| --- | ---: | ---: |
| 3 | 87,000 | 21,000 |
| 5 | 165,000 | 18,000 |
| 7 | 257,000 | 14,000 |
| 9 | 296,000 | 12,000 |
| 13 | 460,000 | 8,000 |

Figure 5 画出中间读写比例，纵轴为便于阅读被限制到 90,000；不能拿超出图框的曲线端点估算纯读性能。大约 60% 读占比附近，三副本曲线开始被更大配置超过，说明要根据负载结构选择副本数。

全读收益来自本地并行执行；全写仍由同一个有序广播域约束，副本更多反而增加工作。写扩展可以考虑多个独立 ensemble 分担数据，但这不等于同一 ensemble 自动拥有跨分片事务。

### 6.3 Figure 6、7：为什么单独的广播测速不等于服务吞吐

**Figure 6，PDF 第 11 页。** 强制所有客户端连接 leader 后，读多时的吞吐明显降低。连写多时也变差，因为接待客户端占用了 leader 的 CPU 和网络资源，与广播协调争抢资源。

**Figure 7，同页。** 隔离原子广播组件、直接在 leader 生成事务，吞吐高于完整 ZooKeeper，且随 ensemble 变大而下降。图中的误差条是最小值到最大值，不是标准差。论文指出此时 CPU 成为瓶颈；完整服务还要做客户端通信、ACL 检查、请求到事务的转换、序列化与复制。

因此，“性能差距都是磁盘”并不符合这组实验。批量减少落盘成本后，别的资源会成为瓶颈。

### 6.4 Figure 8：故障恢复图不能证明从不停顿

同页 Figure 8 用五台服务器、30% 写负载，依次注入 follower 故障及恢复、leader 故障、两台 follower 故障及恢复、再次 leader 故障和恢复。

失去一个 follower 仍有多数，所以服务可以继续推进，但丢掉它承担的读容量；leader 故障会带来更明显的低谷。论文报告观察到的选举少于 200 ms，并提醒采样较粗，短暂停顿未必表现成一个“吞吐恰为零”的采样点。

实际图像在两次 leader 故障附近都有接近横轴的尖锐低谷。因此不能从作者“没有观察到零吞吐”的文字进一步推断“完全没有服务中断”。这是时间聚合图，不是每个请求的延迟追踪。

恢复后的吞吐不一定立刻回到原值：客户端只有连接断开才迁移，导致负载重新分布不均。新客户端加入、旧客户端离开会逐渐改变这种分布，不能假定恢复机器马上平均接到流量。

### 6.5 Table 2、3：等待与应用结构会限制可用吞吐

**Table 2，PDF 第 12 页。** 一个 worker 循环创建节点、等待完成、异步删除，再创建下一个节点；每个 worker 总计创建 50,000 个节点。三副本时，1／10／20 个 worker 分别约为 776／2,074／2,740 次 create 每秒。单 worker 的倒数可用来理解平均请求延迟，论文报告约 1.2 ms；九副本约 1.4 ms。

这些数值与饱和测试的 21,000 写／秒并不矛盾：客户端的等待模式不同，统计的还是 create，而不是所有基础操作之和。论文和 Chubby 已发表数据的比较也不是同硬件、同负载的严格对照，不能当作永久倍数结论。

**Table 3，同页。** 测试 50／100／200 个客户端，依次进入并退出 200／400／800／1,600 个双屏障。例子包括：50 客户端、200 屏障平均 9.4 s；100 客户端、800 屏障 55.9 s；200 客户端、1,600 屏障 234.4 s。每项是五轮的平均完成时间，单位为秒。

作者观察到时间随屏障数、客户端数大致增长。折算为基础 ZooKeeper 操作，约 10,700–17,000/s；读写比约 4:1，却没有达到相同比例下饱和图中的 40,000/s 以上。原因是屏障本来就要求客户端互相等待，服务有能力处理更多请求，不意味着应用此刻能提供更多并行工作。

## 7. 相关工作与结论的适用范围

论文 §6 不是给系统排名，而是在定位不同选择：

- **Chubby** 以锁和强同步为中心，缓存管理、客户端接入方式与 ZooKeeper 不同；这里比较的是论文所述年代的设计。
- **ISIS、Horus、Ensemble、Totem** 提供群组通信及容错背景；ZooKeeper 不向客户端暴露内部 ensemble 通信，并采用 TCP，避免依赖特定网络广播拓扑。
- **Paxos／状态机复制** 提供共识与复制基础；ZooKeeper 将共识日志和应用恢复日志的用途结合。
- **Boxwood、Sinfonia、Dynamo** 展示高层存储原语、mini-transactions、弱一致 KV 等其他选择。ZooKeeper 聚焦全复制的小型应用元数据，不承诺取代这些系统。
- **AFS** 的缓存回调提供 watch 的思想背景；**DepSpace** 和相关 BFT 工作提醒我们，崩溃容错与拜占庭容错的威胁模型不同。校验和与合理性检查不等于完整 BFT 协议。

§7 的核心结论是：较弱的普通读取语义，并不必然使协调 API 无用。只要写序、每客户端顺序、条件更新和通知顺序设计得当，客户端可以组合出有用的强原语，同时把大量读取留在本地。

成功的关键也构成适用边界：应用必须理解这些保证，不能把“协调服务可靠”直接推成“所有业务操作已经有原子性”；高吞吐建立在目标负载与并发方式上，不能脱离读写比例和客户端等待结构。
