# MapReduce 论文中文精读

## 1. 阅读地图与核心问题（§1，PDF 第 1 页）

很多大数据任务本身并不复杂：统计词频、提取链接、构建倒排索引。难点在于输入过大，必须把计算分配到许多机器；而分区、调度、数据移动和故障处理会淹没原本简单的应用逻辑。

论文的主要贡献是把两件事结合起来：**受限但有用的编程模型**，以及能在大量普通机器上运行的**自动并行与容错实现**。阅读时不要只记住 Map、Reduce 的函数名，还要看接口限制如何帮助运行时恢复故障。

## 2. 编程模型：把同键数据聚在一起（§2，PDF 第 2–3 页）

应用先提供 Map，把一条输入映射成零个或多个中间键值对。运行时将所有相同中间键对应的值归组，然后调用 Reduce，生成输出值。论文的抽象类型是：

$$
\operatorname{map}(k_1,v_1)\rightarrow\operatorname{list}(k_2,v_2),
\qquad
\operatorname{reduce}(k_2,\operatorname{list}(v_2))\rightarrow\operatorname{list}(v_2).
$$

论文允许一次 Reduce 产生零个或多个值，并通过迭代器读取输入值，以免要求所有值同时驻留内存。2026 Go 实验接口更简单：`reducef(key, values)` 返回一个字符串，`values` 是字符串切片。二者主题相同，API 不相同。

词频例子及应用函数的讲解见[中文译稿 50:41–55:40、57:57–60:15](#/c/mit-6.824-2021/lec/lec01?v=draft)。阅读论文时要抓住接口边界：应用的 Reduce 只看一个键的值，不负责去其他 worker 搜索遗漏数据；**把完整输入交给它，是运行时的责任**。

### 任务、分区与函数调用

设有 $M$ 个输入 split、$R$ 个 Reduce 分区：

- 一个 Map 任务处理一个 split，通常产生许多键值对。
- 每个中间键按分区函数送入一个 Reduce 分区；默认可用 `hash(key) mod R`。
- 一个 Reduce **任务**负责一个分区，它可能对许多不同键分别调用 Reduce **函数**。

不同键可以落到同一分区；相同键必须落到同一分区。分区解决“发给谁”，分区内排序/归组解决“哪些值属于同一个键”，两者不能互相替代。

### 模型能表达什么

§2.3 给出的例子包括：匹配行筛选、URL 访问计数、反向链接图、主机词向量、倒排索引和分布式排序。可以用“选什么作为中间键”来理解它们：倒排索引用词作键、文档 ID 作值；反向链接图用被链接页面作键、来源页面作值。

排序尤其容易误读。每个分区内部有序，不保证把各分区按编号拼接后全局有序。论文的全局排序使用按键范围划分的分区；哈希分区不能直接提供这个保证。

## 3. 一次作业的数据路径（§3.1–§3.2，Figure 1，PDF 第 3–4 页）

论文把管理者称为 master；2026 实验称为 coordinator。以下用“协调器”描述角色，但不把两套实现混为一谈。

Figure 1 的基本流程已在[中文译稿 60:15–67:17](#/c/mit-6.824-2021/lec/lec01?v=draft)中随课堂解释；这里补足论文中的精确定义：库将输入拆成 split，中间结果划分为 $R$ 个区域并报告位置与大小；Reduce 数据放不进内存时用外部排序。每个 Reduce 分区生成一个最终文件，作业完成后库调用返回。后续作业可直接使用这 $R$ 个文件，不必合并成单个大文件。

**协调器主要传元数据，不中转全部中间数据。** 若所有数据都先汇聚到协调器，它就会成为网络与内存瓶颈。

协调器为每个任务维护空闲、进行中、已完成的状态，以及非空闲任务的 worker 身份；对完成的 Map 还维护各 Reduce 分区的数据位置。由于 Map 与 Reduce 之间存在多对多关系，论文实现的中间位置状态规模为 $O(MR)$，调度决策数量为 $O(M+R)$。

Figure 1 展示逻辑数据流，而不是要求“所有 Map 完成后才开始任何网络读取”。§5.3 明确说明 shuffle 从首个 Map 完成后即可开始。2026 实验选择等 Map 阶段整体完成再发 Reduce，是适合练习的简化。

## 4. 故障恢复与它真正保证的语义（§3.3，PDF 第 4–5 页）

### 4.1 不同输出位置决定重做范围

协调器通过周期性探测发现 worker 不响应，然后重派任务。论文需要区分三种状态：

| 丢失的工作 | 恢复动作 | 原因 |
|---|---|---|
| 进行中的 Map 或 Reduce | 重新调度 | 没有可依赖的完整结果 |
| 失败机器上已经完成的 Map | 重新调度，并通知 Reduce 新位置 | 中间数据仅在该机器本地，变得不可访问 |
| 已完成的 Reduce | 不必因此重做 | 最终输出已保存到全局文件系统 |

正在 Reduce 的 worker 若还未取到某个 Map 的旧输出，改从重新执行后的 worker 获取。论文的关键不是“失败就清空一切”，而是根据仍可用的数据重建必要部分。

### 4.2 多次执行怎样只贡献一次结果

论文通过输出的原子提交约束实现结果语义：

- 每个执行尝试写私有临时文件。
- Map 完成后向协调器报告 $R$ 个临时文件名。若逻辑任务尚未完成，协调器记录这些名字；若已完成，则忽略后来的完成消息。
- Reduce 完成后，把临时输出原子重命名为最终文件。多个尝试可能都执行 rename，底层文件系统保证最终可见的是某一次完整执行的文件，而非交错写出的混合内容。

这里没有声称 CPU 只运行一次。**重做计算是故障恢复手段；选择和发布结果才决定外部看到什么。** 文件系统的原子操作是论证所依赖的基础，不能省略。

### 4.3 确定性与非确定性的区别

当 Map 和 Reduce 对输入是确定性函数时，论文保证分布式执行的输出与整个程序某次无故障顺序执行相同。重新执行某个 Map 时，即使不同 Reduce 读取了不同尝试的结果，只要这些结果相同，整体结果仍一致。

论文没有简单宣布“非确定函数完全不能运行”，而是给出较弱语义：单个 Reduce 任务的输出可对应某次顺序执行，但不同 Reduce 的输出未必共同对应同一次顺序执行。

举例：一个 Map 每次随机选择颜色，同时向两个不同分区输出这个颜色。一次执行全是红色，另一次全是蓝色；两个 Reduce 分别读取不同尝试后，组合输出可能一红一蓝。每个分区单独看都合理，整体却不对应任一次只执行该 Map 一遍的结果。这是编者用于解释 §3.3 的例子。

### 4.4 协调器失败

论文说可以给协调器状态做检查点，但当时实现遇到 master 失败会中止作业，由调用者决定重试。不能把一种可行改进写成论文已经具备的高可用能力。复制协调器属于后续课程的问题。

## 5. 为什么能扩展，又为什么仍有长尾（§3.4–§3.6，PDF 第 5–6 页）

### 局部性：移动计算比移动大输入便宜

输入放在 GFS，块通常有多份副本。协调器尽量让 Map 在拥有输入副本的机器上运行；不行时尽量靠近，例如同一交换机下。这样大量输入读走本地磁盘，而不是跨共享网络。

Map 中间数据直接写本地磁盘，再由 Reduce 拉取，避免把每份可重算的中间结果也交给 GFS 做复制。最终输出则使用全局文件系统以保留成果。其权衡是：减少网络和复制成本，接受机器失败后的重算成本。

### 粒度：更多任务让快机器多干一些

如果每台机器预先分到固定的一大块数据，最慢机器决定尾部时间。把工作切成比 worker 数更多的小任务，做完就继续领任务，可自动把更多工作交给快机器；失败机器的任务也能被其他机器分摊重做。

任务不是越小越好。更多任务意味着更多调度和元数据；$R$ 还决定最终文件数量。论文的典型配置提到 $M=200{,}000$、$R=5{,}000$、约 2,000 个 worker，这是当时的实践值，不是通用推荐常数。

### 备份任务：避免最后几项拖垮全局

接近作业结束时，系统可以为剩余慢任务启动备份执行，任一尝试完成就推进逻辑完成状态。慢机器可能来自磁盘错误重试、其他作业争用或机器配置异常，而不只是输入大。

备份执行以额外资源换更短尾部时间；它不是复制全部任务。2026 实验尤其要求避免无故障情况下无谓重派，超时阈值使用 10 秒。

## 6. 接口之外的重要细节（§4，PDF 第 6–8 页）

### 6.1 自定义分区与有序输出（§4.1–§4.2）

用户可以改变分区函数，例如按 URL 的主机名分组，让同一主机的记录进入同一个分区。分区内按中间键有序，但不同分区之间的顺序要由分区规则提供。

### 6.2 Combiner：减少发送，不改变含义（§4.3）

对词频来说，一个 Map 发出一千条 `(the,1)`，可在本地先合并成 `(the,1000)`。这能显著减少网络数据，但要求局部合并后的值仍能被后续归约正确处理。

论文讨论的是具有交换、结合性质的归约。编者提醒：平均值不能简单“先求各分片平均，再平均一次”，因为分片大小可能不同；传递 `(sum,count)` 才能继续组合。不能机械地把任意 Reduce 当成 Combiner，也不能假设每条数据一定经过固定次数的局部合并。Lab 1 不要求实现 Combiner。

### 6.3 输入输出扩展与副作用（§4.4–§4.5）

输入不仅能来自文本文件，也能通过 reader 接口来自数据库等结构。文本读取器要在记录边界划分，不能任意截断一行。

若用户函数额外写辅助文件，原子性与幂等性由应用负责。论文不提供一个任务多个输出文件的原子两阶段提交。向外部系统扣款、发送通知等效果，不能因为框架会重试就获得安全语义。

### 6.4 坏记录与本地调试（§4.6–§4.7）

某条输入若稳定触发应用崩溃，重试同一任务可能永远无法推进。论文提供可选的坏记录跳过模式，通过崩溃前上报的位置识别反复出错的记录。但跳过会改变计算内容，前提是业务允许；它不是默认正确性修复。

本地顺序执行模式让开发者先调试 Map/Reduce 的纯计算逻辑，再处理分布式运行。实验中的 `mrsequential.go` 也能充当输出对照。

### 6.5 进度与计数器（§4.8–§4.9）

协调器状态页展示任务进度、读写字节、速率和失败记录。计数器可以检查诸如输入条数与输出条数是否匹配。

重试同样影响可观测性：如果把每次尝试的计数都相加，成功逻辑任务会重复贡献。论文聚合成功任务的计数并消除重复执行影响。调试统计也必须有清楚的计数对象。

## 7. 怎样读性能实验（§5，Figure 2–3，PDF 第 8–10 页）

实验使用约 1,800 台机器：每台双 2GHz Xeon、4GB 内存、两块 160GB IDE 磁盘和千兆网络；根部聚合带宽约 100–200Gbps。测量期间大部分资源空闲。下面的数值描述这套环境，不是今日性能承诺。

### 7.1 Grep 与 Sort 刻意制造不同压力

- **Grep** 扫描约 1TB 输入，只输出很少的匹配记录。输入速率峰值超过 30GB/s，总耗时约 150 秒，其中启动开销约一分钟。
- **Sort** 同样处理约 1TB，但中间数据很大，需要 shuffle，最终输出还要写两份 GFS 副本。正常运行约 891 秒。

因此不能只按“输入都是 1TB”比较两项任务。中间与输出规模不同，瓶颈也不同。

Figure 2 的横轴是秒、纵轴是输入 MB/s；曲线先上升后下降，体现 worker 陆续启动与 Map 任务陆续结束。峰值吞吐不是全作业平均吞吐，不能用 1TB 除以峰值来代替实际完成时间。

### 7.2 对照实验说明了什么

| Sort 条件 | 完成时间 | 可得结论 |
|---|---:|---|
| 正常执行 | 891 秒 | 比较基线 |
| 禁用备份任务 | 1,283 秒 | 约慢 44%；最后少量任务形成长尾 |
| 杀死 1,746 个 worker 中的 200 个进程 | 933 秒 | 本次故障实验约慢 5%；重调度可恢复大部分进度 |

Figure 3 每列是一种条件，三行依次表示输入、shuffle 和输出速率。禁用备份任务那一列并不是始终很慢，而是多数工作结束后尾部拖长。故障列的输入进度出现负值，是因为已完成但变得不可用的 Map 工作被撤销记账，不是磁盘在“负速率读取”。

故障实验杀的是进程，底层集群调度器立即重启它们；它不能证明任意比例的机器永久失联也只增加 5% 时间。读系统论文时必须同时读故障注入方式和恢复条件。

## 8. 实际使用与设计位置（§6–§8、附录 A，PDF 第 10–13 页）

论文展示了 MapReduce 在索引、日志分析、机器学习与图计算中的应用。Figure 4 记录源码树中 MapReduce 程序数量的增长；Table 1 统计 2004 年 8 月的一组作业，例如 29,423 个作业、平均每作业 157 个 worker、平均 1.2 次 worker 死亡。这些说明了采用规模与容错需求，不是严格控制变量的性能实验。

索引系统把处理过程拆为五到十次 MapReduce 调用。某个阶段的应用代码从约 3,800 行 C++ 减到约 700 行。价值不只是“跑得快”，还包括把容错代码收进框架，允许业务逻辑保持简单、便于修改。

§7 将系统与并行编程、集群排序、数据流等工作比较。区别不在于 MapReduce 发明了所有调度思想，而在于它利用受限接口，把自动分发、重执行、局部性和负载平衡组合成可用的基础设施。

附录 A 展示一个完整 C++ 词频应用如何连接 Map、Reduce、可选 Combiner、输入输出配置与运行入口。阅读重点是应用与框架的职责边界；它不是 Go 实验答案，不必照抄 API。

最终结论可以压缩为：**以表达能力的限制，换取运行时更容易自动处理并行、数据移动和失败。** 判断这个权衡是否合适，要看你的任务是否适合批处理、是否能安全重算，以及中间数据物化的成本。

## 9. 从论文走向 2026 Lab 1

| 方面 | 论文系统 | 2026 实验 |
|---|---|---|
| 运行位置 | 多台集群机器 | 同一机器上的多个进程 |
| 调度通信 | 集群环境中的 RPC | 显式 socket 参数、Unix socket RPC |
| 中间结果 | Map 所在机器的本地磁盘 | worker 共享的当前目录 |
| 数据获取 | Reduce 通过网络读 Map 输出 | Reduce 读取共享中间文件 |
| 故障判断 | 周期探测 worker | 任务等待超过 10 秒后可重派 |
| 最终结果 | 全局文件系统中的分区文件 | `mr-out-X` |
| 协调器失败 | 当时实现中止作业 | 不要求协调器容错 |

这些差异决定哪些设计需要实现、哪些只需理解。具体硬性要求见[实验说明](#/c/mit-6.824-2021/lab/mr?v=zh)，阶段拆解见[实验指导](#/c/mit-6.824-2021/lab/mr?v=guide)。
