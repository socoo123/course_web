# L17 中文译稿：Memcached at Facebook

## 00:00–03:00 一篇以规模和工程经验为中心的论文

今天讨论 Facebook 在 2013 年发表的 Memcache 论文。Memcached 仍被广泛使用，很多大型网站也采用相近的架构。这是一篇经验论文：重点不是提出全新的分布式算法，而是说明怎样把真实系统扩展到每秒十亿乃至数十亿次请求。

可以从三个角度读它。第一，使用 MySQL、memcached 这样的现成软件，仍然能做出极高吞吐，成果非常可观。第二，设计一直在性能与一致性之间取舍，而且这里主要由性能需求推动。第三，如果一开始没有认真组织一致性，后来补上所需的保证会相当困难。

此前许多系统追求线性一致性或外部一致性；Facebook 的这类应用并不要求信息流里的每条新闻立刻反映最新写。落后几秒通常可以接受。因此不能拿“它不是线性一致的”就当作对论文的全部评价。但目标较弱，也不意味着完全不用处理一致性。

## 03:00–06:00 网站起步：一台机器就能装下所有东西

讲师先说明安排：先讲性能，因为它驱动了整个设计；再讲这些选择引出的几个一致性问题。理解背景可以从一个普通网站的演进开始。

刚起步时，租一台机器，上面运行 Apache 一类 Web 服务器、PHP 或 Python 应用，以及 MySQL 数据库，就足够了。浏览器请求进入应用，应用查询数据库，生成页面；数据库提供 SQL、事务、持久保存和故障恢复。所有长期状态集中在数据库，备份与恢复的对象也很明确。

随着用户增加，第一个瓶颈常常是应用计算。很多用户同时请求页面，执行应用代码消耗全部 CPU；即使数据库还能处理请求，单台前端机器也无法再扩展。

## 06:00–08:00 多台无状态前端为什么容易扩容

最直接的改造是保留一个数据库，把 Web 服务器与应用复制到许多前端机器上。更多用户来了，就增加前端；所有前端连接同一个数据库。

这种扩容相对简单，因为前端不保存必须一致的长期状态。数据集中在数据库，不需要再设计一套前端之间的复制协议。前端崩溃，只需让别的前端接管请求或补一台机器，不需要从那台前端恢复用户数据。

在这个简化模型里，所有前端的读写都通过数据库，所以一致性与并发控制仍交给数据库。课程里已经讨论过的许多复制难题，此时还没有出现在前端层。

## 08:00–11:00 第二个瓶颈：数据库分片带来新的协调成本

单个数据库的容量和吞吐也有上限。讲师用大约每秒十万次简单读查询、几千次写事务作为量级示意；超过后，就需要把数据库拆到多台机器。

例如按键范围分成几片：一片放较小的键，第二片放中间的键，第三片放更大的键。前端知道键在哪一片，访问键 32 时去第一片，访问键 50 时去第二片。若请求均匀地分散在不同分片，就能利用多台数据库并行处理。

这一步比复制无状态前端痛苦。事务若跨越分片，就不能只依赖一台数据库自己的事务机制；要么设计放置策略，让常用的一组键尽量共处一片，要么引入两阶段提交等跨机器协议。继续把分片切得更细，虽然增加并行度，也可能增加跨片事务的频率。

## 11:00–14:00 用旁路缓存承接大量读取

另一条扩展路径是：不让数据库承担所有读取。在应用旁边增加缓存层，如 memcached 或 Redis。前端先查缓存；命中就立即返回，未命中才访问持久存储，再把结果放入缓存。写则仍然直接进入数据库。

Facebook 的负载非常适合这个方向：用户大多数时候看别人的动态、图片和新闻，读远多于写。缓存服务器可以极其简单，核心就是一个内存哈希表，不必为每次查询承担完整 SQL 和数据库事务的开销。

术语上，一份 memcached 程序或正在运行的服务进程叫 memcached；把许多这样的服务器组织起来的整个系统，论文称为 memcache。不能因为两词很接近，就把单机软件自带的能力与 Facebook 额外构建的分布式机制混为一谈。

## 14:00–17:00 缓存不只是加速器，还是数据库的负载屏障

讲师把缓存 KV 与当时 Lab 3 中的 KV 部分作比较：数据结构本身很简单，可能为不同哈希桶加锁，以利用机器内部并发。真正的挑战是让数据库与缓存保持足够一致，以及防止数据库被击穿。

一旦前端依靠缓存扩展到每秒十亿次请求，数据库就已经不是按这个总请求量配置的。缓存故障后，如果这些请求全部绕过缓存去访问数据库，数据库会过载，进而导致整个服务失败。因此论文中很多技巧的目的，是尽量避免突然增加数据库的请求量。

**问：前面的设计为什么强调客户端无状态？** 这里的客户端是前端服务器。答：这样扩展前端不需要复制数据，也不需要协调前端状态；任何一台前端失败都可以替换，因为真正的数据在数据库中。

> **版本校注：** 课堂 2021 Lab 3 对应本路线复制 KV 的主题，不是固定 2026 实验的同号接口。这里也没有主张把缓存的弱一致语义用于实验 KV。

## 17:00–20:00 “最终一致”之外，最想保住的是读到自己的写

加入缓存之后，必须说明希望得到什么语义。讲师称其为 eventual consistency，同时指出这个词本身很模糊；更明确的是，他们没有追求线性一致性。

写仍交给数据库排序和执行，不能让权威数据因为并发写变成随意的状态。读取则允许落后：用户页面晚一两秒出现一条动态，甚至晚几百毫秒，往往看不出来。但落后几小时就不是同一个问题。

还有一个特别重要的要求：用户应尽量读到自己的写。例如刚更新一个键，随后再读它，最好能看见刚才的结果；否则不但界面古怪，应用代码也更难写。这与 ZooKeeper 中“普通读可以落后，但同一客户端有额外顺序约束”的思路有些相似，不过不是相同的形式化契约。

## 20:00–23:00 数据库日志驱动失效，应用负责重新填入

基本策略是缓存失效。前端修改数据库；数据库旁运行一个叫 mcsqueal 的进程，观察提交日志，发现某个修改影响键 k，就发送 `delete(k)`，把缓存中的旧结果删掉。

之后有读请求到来，缓存返回未命中，应用从数据库查询数据，再把查询结果放回缓存。为什么不让缓存自己查询数据库？因为应用存进缓存的未必是一条原始数据库记录。

应用可能把文本加工成 HTML，也可能查询多个记录、计算一个聚合结果，再缓存这个派生值。只有应用知道它想缓存什么。因此缓存放在访问路径的一侧，由应用管理，称作 look-aside cache；它不是透明地夹在应用与数据库之间、替应用完成所有事情的一层。

## 23:00–26:00 一次页面读取往往拆成许多键查询

讲师回到论文的读写示意图。前端为了生成一张网页，可能需要几十到几百个键。客户端一次发出多个请求，实际联系许多 memcached 服务器；返回后，可以继续处理已经命中的部分。

缺少的部分需要向数据库发 `SELECT`。数据库返回后，应用可做加工，然后把结果填入 memcache。这里最重要的角色关系是：**读取数据库和回填缓存都是前端发起的，memcached 本身不知道背后的 SQL。**

整个流程可以理解为“先查结果缓存，再做昂贵计算或查询，最后缓存结果”。这也解释了为什么仅靠数据库知道某行被修改，并不意味着数据库能直接构造所有受影响的缓存值。

## 26:00–29:00 为什么写者还要自己发送 delete

写路径先更新数据库，例如发表帖子或修改图片关联。这是普通数据库事务。事务完成后可以回复前端，而 mcsqueal 的失效传播是异步进行的；不能假定返回时所有缓存都已删干净。

因此写者还会立即删除自己所在 cluster 的缓存键。这样同一前端接着读取时会 miss，重新查询数据库，避免直接命中自己刚写之前的旧值。这一步主要服务于 read-your-writes；其他缓存副本的失效仍由日志驱动的管道负责。

**问：为什么写者不在删除之后直接 set 新值？** 讲师说，这是另一种更新式方案，原则上可以做，但需要更认真地协调数据库、缓存与客户端的顺序。接下来用两名写者说明为什么“直接更新”并不自动正确。

## 29:00–32:00 两个写者的缓存更新可以倒序到达

假设键初值为 0。C1 把数据库里的 k 写成 1；稍后 C2 把它写成 2，所以数据库当前是 2。但 C1 在回填缓存之前被延迟了，C2 却先执行缓存 `set(k,2)`。等 C1 恢复，它执行 `set(k,1)`，便把缓存中的新值覆盖成旧值。

之后的读取可能长期得到 1。这不只是一个请求在传播窗口内稍微落后，而是旧结果被重新固定在缓存里，直到再次修改、淘汰或其他修复发生。

一种改进是由数据库给更新附上顺序号或时间戳，让缓存拒绝倒序更新；但这需要数据库与缓存协作。讲师认为 Facebook 选择失效方案，一个重要原因就是更容易围绕现成组件实现：数据库旁边的进程读取日志，发已有的 delete 操作。

后面还会出现相似的旧值回填问题，但那时是读者与写者竞争，可以借助缓存自己的 lease 机制处理。

## 32:00–34:00 既然前端会删，为什么还保留 mcsqueal

**问：前端已经执行 delete，为什么需要额外进程再发失效？** 答：后面会看到，缓存不止一份。写者会删除本地使用的那份，但系统还需要把失效传播到其他缓存副本。

有人继续确认，是否要向每一份 memcache 副本发 delete。讲师暂时不展开消息细节，转到总体部署图：此前的无状态前端、分片数据库与旁路缓存都很常见，接下来才是 Facebook 为进一步扩展而采取的具体组织方式。

首先是把完整的数据中心部署到不同地域。课堂用美国西海岸与东海岸两个 region 作例子。

## 34:00–38:00 跨地域复制：读靠近用户，写集中到主地域

每个 region 都有很多前端、一个由许多 memcached 服务器组成的缓存层，以及分片后的数据库存储层。东海岸的数据库保存西海岸数据的副本，而不是只保存东海岸用户的一小部分键。

一个 region 是主地域，另一个是副本地域。所有数据库写都发到主地域，即使发起写的前端在东海岸也是如此。主数据库执行事务，再把更新日志异步传播到另一个 region；当地数据库应用更新后，失效消息进一步清理当地缓存。

这样做的收益是本地读。东海岸用户连接附近前端，从当地缓存获得数据，不必为每次读取横跨美国。代价是副本及缓存会落后一些，但这与应用接受短暂陈旧的目标相容。

> **角色校注：** 课堂将日志复制与 mcsqueal 画在一起解释。论文实际依靠 MySQL 复制更新数据库，mcsqueal 从提交内容提取缓存失效，二者不是同一个协议。

## 38:00–40:00 问答：客户端固定联系哪台缓存服务器

**问：副本 region 的前端写主数据库后，自己删除哪里的缓存？** 答：删除它在本地访问的缓存。另一地域的数据库和缓存会通过异步复制与失效管道跟上。

**问：一个客户端总是联系同一个 memcached 吗？** 不是。键分散在许多服务器上；生成一页通常要取多个键，因此前端会并行联系多个 memcached，短时间内可能接触整个缓存层。对于固定的键，在分配关系未变时会找到固定的服务器。

讲师提到一致性哈希：服务器失败或成员变化之后，键到服务器的映射可能改变。学生由此提出读到自己写入结果的保证在故障切换后是否还能成立，讲师让大家先保留这个问题，后面再讨论相应竞争与补救。

## 40:00–43:00 问答：同步完成写，不代表异步副本已经追上

学生确认读写顺序。讲师强调：先完成数据库写，再 delete 本地缓存；下一次 get 未命中后，才从存储获取结果。不是“先删，然后某个时间再真正写入”。

**问：前面说写是异步的，那怎么确保删完后能读到？** 答：对主数据库的事务写本身是同步等待完成的；异步的是数据库副本复制和缓存失效传播。

**追问：如果我在副本 region 写主数据库，然后删本地缓存，却从尚未更新的本地数据库重读，仍会得到旧值吧？** 讲师确认这正是一个真实问题，后面会说明 remote marker。接下来先继续性能主线，因为仅有跨地域复制还不够。

## 43:00–46:00 分片增加容量，复制解决热点

提升吞吐有两个基本方向。分片把不同键放在不同机器上，增加服务器就能增加可存储的数据量，并让不同键的访问并行进行。

但是，若一个极受欢迎的人发布动态，许多用户都访问同一个键，那么这个键所在服务器会成为瓶颈。给其他键增加服务器，并不会减少这台服务器上的热点请求。

复制则把同一个键放到多台机器，让客户端分散访问这些副本。它适合热点，但消耗额外内存，不会按副本数增加独立数据容量。西海岸和东海岸各有一份缓存就是一种复制：同一批内容可以并行服务两边用户，但不能把两份相同内容算作两倍独立容量。

## 46:00–49:00 一个 region 内再划出多个 cluster

如果只在单一缓存集群里不断增加 memcached，前端就会联系越来越多的服务器，连接数和网络压力持续增加；对于单键热点，分片仍不能解决问题。

Facebook 因而在同一 region 内复制整组“前端 + 缓存”，每组叫一个 frontend cluster。不同 cluster 共享 region 的数据库存储层，但各自拥有前端和缓存。用户请求分配到不同 cluster，热点键便可能在每个 cluster 中各缓存一份。

另一个收益是控制 incast：前端并行向许多缓存服务器取数据，回复可能在几乎同一时刻涌回，耗尽交换机或接收端队列，造成丢包。把交互范围控制在较小的 cluster，有助于限制这种汇聚压力。

## 49:00–52:00 网络边界与 regional pool

要让一个巨大的全互联缓存集群拥有足够横截面带宽很困难。多个较小 cluster 可以分别配置网络，不必让每个前端与 region 内所有缓存服务器都频繁通信。

但复制也有浪费：不热门的数据在多个 cluster 各存一份，占了内存，却没有带来相应的吞吐收益。于是增加 regional pool，让这些较少访问的对象由多个 cluster 共享，而不是每个 cluster 都保留副本。

**问：每个 cluster 都有自己的 memcache，所以才分散热点吗？** 是的，前端与缓存都按 cluster 分组，用户在这些组之间分配。

**问：复制仍然没有增加独立容量吧？** 单纯复制确实如此；regional pool 则能通过减少低热度对象的重复副本，腾出空间存其他键。它是利用率改进，不是复制凭空产生内存。

## 52:00–55:00 冷集群为何可能把数据库压垮

学生确认：控制 incast 的含义是限制单个 cluster 的规模，而不是无限扩大其中的分片数。讲师随后把性能问题重新归结为保护数据库。

假设现有一个热缓存集群，再增加一个完全空的新集群，把一半用户转过去。若简单地让新集群每次 miss 都查询数据库，那么近一半请求会直达数据库；此前数据库承受的可能只是一小部分 miss，负载会突然放大很多倍。

因此“把新机器开机，等自然流量填满缓存”并不总是可接受。系统越依赖高命中率生存，启动、维护与故障恢复就越必须控制缓存预热的流量来源。

## 55:00–57:00 从热集群预热，再看惊群问题

**问：新集群从哪里取数据？** 有人先提到 Gutter，讲师区分后请另一名学生回答：从已有的热集群读，然后填入冷集群。

这是懒惰复制：新 cluster miss 时先借用旧 cluster 的缓存，而不是直接访问数据库。旧缓存集群的负载会增加，但通常比让数据库承受大量 miss 更合算。这个捷径也会带来新的陈旧数据竞争，稍后讨论。

第二个问题是 thundering herd。学生举出读写频繁交错的情况；讲师把例子进一步简化：**只要一次写删除了一个非常热门的键，就足够了。** 紧随其后的大量读都会 miss，若它们都去查询数据库，就形成短时间的请求洪峰。

## 57:00–60:00 lease 的第一项职责：只让少数人负责回填

学生提出使用 lease，并把它理解成某种临时许可：一个人负责更新，其他人稍后再试。

讲师说明，get 未命中不再只有一种结果。第一个符合条件的客户端得到 lease，表示它负责从数据库取数据并回填；其他客户端得到“稍后重试”的提示，而不是都立即访问数据库。

通常回填只需要几毫秒。其他客户端稍后再 get，就有机会命中，不会一起制造数据库洪峰。讲师猜测重试间隔可能采用退避式安排，这不是此处已经核实的具体算法。

**问：lease 也用于避免 stale set 吧？** 是的，它有两个用途：这里讨论的是性能，后面还会用同一个机制处理回填旧值的竞争。学生所谓“像锁”是直觉类比，不代表持有 lease 的人阻止了数据库写者。

## 60:00–63:04 少数缓存机器失败时，先转向 Gutter

考虑一台或少数 memcached 失败，而不是整个数据中心失效。get 无法返回后，最简单的处理是查数据库，但这会把失败机器上的负载突然转移给数据库。

系统保留一个较小的 Gutter 池，在故障机器修复或替换之前承接请求。客户端访问原机器失败，就先去 Gutter；Gutter 也 miss 时才查数据库并缓存结果。后来的请求便可能从 Gutter 命中。等原服务恢复，流量回到正常缓存，Gutter 留作下次故障时使用。

讲师强调，这是分钟级故障处置窗口里的缓冲机制。随后引出当天阅读题：为什么不给 Gutter 发送普通 delete 和失效消息？约 62:56 宣布分组，邀请同学讨论这个问题或其他设计细节。

## 69:03–71:00 返回后的回答：Gutter 小，额外失效流量很贵

讲师询问大家的猜测，并说明论文没有精确回答他提出的这一动机问题。学生认为 Gutter 机器很少，如果每次写都额外给它发请求，会产生相当大的压力；删除过于频繁还会让下一次访问再次查询数据库。

讲师赞同，并补充：原缓存池需要收 delete，Gutter 又收一份，失效流量也会增加。Gutter 的定位是让系统渡过少数缓存服务器故障与替换的过渡阶段，因此这个取舍是合理的。

> **论文补充：** 论文 §3.3 明确说 Gutter 条目很快过期，以避免专门向 Gutter 发失效；课堂给出的“额外流量”是动机推测。省掉失效不是得到更强一致性，而是以暂时陈旧换后端保护。

## 71:00–74:00 第一种竞争：旧读的回填跑到 delete 后面

现在讨论三个竞争。第一个只需要一个 region、一个 cluster。C1 get(k) 未命中，取得 lease，从数据库读到旧值 v1，但迟迟没有回填。其间 C2 将数据库里的 k 改成 v2，并删除缓存键。之后 C1 才把 v1 放回缓存，旧值便可能长期留下。

课堂画这条时间线时，讲师一度把 C2 的缓存动作写成 put，随后在 73 分钟附近明确纠正：这里采用失效方案，C2 做的是 delete，不是把 v2 更新到缓存。

修复的关键不是只检查过了多少秒，而是让 delete 同时撤销这个键已有的 lease。C1 回填时必须提交最初 get 获得的 token；如果中间发生过 delete，这张许可已经无效，缓存拒绝它。

## 74:00–76:00 问答：这里的坏处究竟是“倒退”还是长期看不到新值

讲师把 lease 的两个用途连起来：最初限制谁去查数据库，避免惊群；现在再让失效操作撤销许可，阻止旧结果覆盖失效边界。

**问：如果不撤销 lease，读到的仍是过去的一个合法值，难道不满足弱一致吗？** 讲师回答，这不仅影响写者看到自己的写，还可能使所有后续读者长期看不到 v2。

学生指出，在具体画出的历史里，客户端未必已经读过新值，所以严格说不一定发生“先新后旧”的倒退。讲师接受这个修正：用词可以不叫倒退，真正的问题是 v2 可能很久都不可见。系统接受短暂传播延迟，不希望一次竞争把旧值重新固定下来。

## 76:00–79:00 第二种竞争：冷集群从热集群抄来旧数据

接着回到预热场景。k 原本是 v1。C1 在数据库中写成 v2，然后删除冷 cluster 的缓存键。C2 在冷 cluster get 未命中，按照预热规则去热 cluster 取值。

如果热 cluster 还没收到失效，它会返回 v1；C2 再把这个值填入冷 cluster。结果与第一种竞争相似：冷 cluster 的 delete 已经发生，但旧值仍在之后进入缓存，可能长期留下。

讲师询问解决办法。有学生问两个客户端是否在同一个冷 cluster，讨论随后指出关键不在这两个前端的名字，而在“借来的热缓存副本还没有被删”。这一段包含等待回答的空隙，没有额外算法内容可从字幕补出。

## 79:00–81:00 两秒 hold-off 是预热期的工程缓冲

学生想起论文里的两秒 hold-off。讲师解释：在冷 cluster 的预热阶段，delete 后短时间内拒绝把这个键重新放进去，给其他地方的失效传播留出时间。

冷集群可能预热几小时；只有这段特殊时期启用这个技巧，命中率恢复稳定后就关闭。选择两秒，是认为多数失效能在此窗口内传播到热 cluster，不是一个由异步网络模型证明的绝对上界。

> **接口与口述校注：** 课堂统称 set/put；论文 §4.3 具体使用带 hold-off 的 delete 和 `add`，add 失败后从数据库重新取。字幕尾部提到传播到“cold database”，这里真正需要等的是热缓存上的失效；同一 region 内多个前端 cluster 共享存储层。详见课程资料 §5。

## 81:00–84:00 第三种竞争：本地数据库还没收到自己的跨地域写

第三种竞争就是先前学生指出的情况。客户端在副本 region，把写发送到主地域数据库；写完成后删本地缓存，再 get 时 miss。但如果随后查询的是本地副本数据库，更新可能还在复制途中，它仍返回旧值。

解决思路叫 remote marker：让本地系统知道这个键暂时不能相信本地数据库。读发现 remote 标记，就去主地域数据库取值，而不是从尚未追上的副本重新填入旧值。

**问：何时可以移除标记？** 答：当数据库复制把相应更新带到本地，能够安全地从本地数据库读取时，便清理标记。

> **协议校注：** 课堂简化成“删除时把 k 标为 remote”。论文实际在写主数据库之前，先在 regional pool 设置独立键 rk，再让 SQL 携带 k、rk 的失效信息，最后删本地 k。并发写与 marker 被淘汰仍可能破坏这项保护，因此不是无条件 read-your-writes 保证，见课程资料 §6。

## 84:00–86:00 课堂总结：性能扩展改变了必须处理的竞争

总结三点。第一，缓存是维持巨大请求量的关键，不只是减少一两次延迟。第二，分片让不同数据并行处理，复制让热点数据由多台机器服务，系统需要两者结合。

第三，即使只追求相对弱的一致性，数据库与缓存之间仍会出现很棘手的竞争。旧值回填、跨 cluster 预热和跨 region 副本延迟，都需要各自的补救机制。

“不过是一个缓存，能有多难”这个直觉不可靠。讲师说仍有研究试图更好地整合数据库与缓存，同时维持这样的吞吐。正式讲授结束，需要离开的同学可以去下一场会议；讲师留下回答问题。

## 86:00–89:00 课后问答：为什么特别在意 remote marker

**问：怎么判断 remote marker 值得增加复杂度，而不是直接接受旧数据？** 答：用户刚向时间线加一项，再刷新却看不到，会直接觉得自己的操作丢了。虽然论文没有把要求写得非常形式化，但这种可见的不一致是他们特别希望避免的。

**问：客户端与 mcsqueal 的失效分工是什么？** 讲师回到图上确认，客户端处理自己所在的局部缓存，日志驱动的机制负责更广的传播。这里“本地”在具体实现里是写者的 frontend cluster，不代表前端自行向整个 region 广播。

**问：同一 region 中前端是分配给某个 cluster 的吧？** 是，每个 cluster 都是“前端加缓存”的一组部署，前端属于其中一组。课堂以此解释为什么普通请求不会在多个 cluster 的缓存之间任意跳转。

## 89:00–92:00 课后问答：论文中的 marcher，以及缓存失败后的读取

学生问论文第 2 页 generic cache 段落中的 “existing marcher infrastructure” 指什么。讲师明确表示不知道，不在课堂上猜出一个系统定义。实际 PDF 确有这个词，本文也不把它擅自改成已知组件。

另一名学生回到之前的故障问题：前端刚写完，缓存服务器却崩溃；如果马上转到其他缓存，如何读到之前的写？讲师认为普通的 fallback 是去 Gutter，第一次可能 miss，再从数据库取，而不是自动访问另一个 frontend cluster 的缓存。

至于新机器加入后如何重分配键，讲师说论文并未充分描述，他推测与一致性哈希有关。这里保留推测身份，不把它补成一个已经核实的故障重配置协议。

## 92:00–95:00 课后问答：Gutter 的并发回填边界没有得到完整答案

学生进一步追问：如果不同地方同时故障，都去 Gutter，两个查询结果的回填可能倒序，如何处理？讲师先区分数据库写与缓存 set：数据库写由主存储排序，缓存回填则是读取之后的另一个动作。

学生把反例说得更具体：第一个客户端读到旧值，随后发生写，第二个客户端读到新值，两个 set 在故障转移后以不同顺序落入缓存。讲师承认论文没有描述所有边界情况，猜测 lease 可能有帮助：例如新服务器不认识旧服务器发出的 token，应拒绝相应回填。

**追问：Gutter 究竟怎样管理 lease？** 讲师回答不知道，需要坐下来进一步分析。本文保留这个未解决问题；不能把前面的推测当成 Gutter 已证明具有严格一致性，尤其它本来就不接收普通失效消息。

## 95:00–96:00 课后问答：为什么混用 UDP 与 TCP

学生觉得 get 使用 UDP、其他操作使用 TCP 很有意思，问这是否常见。讲师说，大家通常偏爱 TCP，因为它提供可靠、有序传输；但连接很多时，状态、CPU 和内存开销也会成为问题，因此转向 UDP 并不新奇。

有人会在 UDP 上重新实现需要的传输功能，学生以 QUIC 类比。讲师提醒，序号之外，还要考虑拥塞窗口、伸缩性等 TCP 原本承担的工作。不能把论文这个很具体的缓存取舍理解成“UDP 天生全面优于 TCP”。

## 96:00–98:00 课后问答：cluster 间并没有一套共识复制

学生问多个 frontend cluster 之间是不是没有正式复制协议。讲师先确认大家说的是同一 region 内的 cluster，而不是跨 region 的数据库。

在这里，各 cluster 共享存储层，缓存彼此独立，用户请求分配在不同 cluster；它们并不互相运行共识协议，把所有缓存状态同步成相同日志。数据库接受写、确定权威数据，再通过失效管道删除各 cluster 的缓存值。

lease 负责本缓存实例中的回填竞争；它不是让 cluster 之间就某个新值达成共识。这里的“复制”主要说同一数据被多处需求驱动地缓存，不是复制状态机意义下每台副本执行相同命令。

## 98:00–100:00 课后问答：系统设计是不是不断添加一层

学生观察，系统似乎每遇到新负载就增加一个层次，复杂性也不断增长，问这是否是一般发展方式。

讲师认为这篇论文采取了很务实的做法：解决真实出现的瓶颈，用相对有限的额外机制把现成组件扩展到极高规模。这个结果值得肯定。

当然也有人会回头问，能否从整体上重新设计，获得更强一致性与更简单的缓存协作。但在当时，把相同规模的高性能、成本和一致性都做到，仍是研究问题。这个评价是 2021 课堂的历史语境，不是对 2026 所有产品与研究的最新调查。

## 100:00–102:00 课后问答：所有写集中到主地域之后怎么办

学生先确认，每个 region 内仍有多个 frontend cluster；随后问，如果写继续增长，不能再全发到一个主地域，下一步怎么设计。

讲师提到 Facebook 后续的 Wormhole 工作，讨论可扩展的更新传播；又推测可以把不同用户或分片分给不同主地域，而不是让所有数据共享一个地域主节点。他明确说这是自己的推测与设计方向，不是本论文已核实的部署事实。

学生问是否可在不同存储地域之间运行共识协议。讲师以 Spanner 为例，提醒跨广域网写事务的往返很昂贵，并口头回忆每秒十次或百次的数字。

> **量纲校注：** 这种量级至多可帮助理解单个串行请求流受到往返延迟限制，不能当成 Spanner 全系统的总吞吐。分片、客户端并发和批处理都会影响系统吞吐；前一讲资料已区分事务延迟与全局吞吐。

## 102:00–104:15 最后的澄清：stale set 把短暂陈旧变成长期残留

最后一名学生说自己仍没看懂第一种竞争里的 v2。讲师重新指出：数据库已经被第二名客户端更新成 v2；delete 的目的，是让下一次读者重新从数据库获得这个值。

但是，先前读到 v1 的客户端在 delete 之后回填，就把旧值重新放进缓存。接下来的人看到的是 1 而不是 2，连刚写入 2 的客户端也可能如此。所谓“永久”要加引号，因为未来的淘汰或新写仍可能移走它；关键是这次更新对应的失效已经结束，不会自动再清理这次迟到回填。

学生表示理解，并说开头的网站演进过程很有帮助。讲师回应致谢，录像结束。原始最后一条字幕起于 104:13.800、结束于 104:16.800，超过元数据片长；本段标题按 104:15 收束，归档保留原始时间。
