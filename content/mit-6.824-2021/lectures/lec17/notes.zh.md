# L17 课程笔记：让性能捷径保留必要的失效边界

## 1. 先问“谁是权威”，再问“这里的副本有什么保证”

Memcache 的权威数据在数据库，缓存保存可丢弃的结果。读 miss 后由应用回填，数据库写之后则删除受影响的缓存。这些操作穿过不同系统，**不是一笔跨数据库与缓存的原子事务**。

一个值可以是 SQL 结果或应用加工结果，不必是数据库某一行的原样副本。因此有两条数据路径：

- **取值路径：** 应用 → 缓存；miss 后应用 → 数据库 → 应用加工 → 缓存。
- **失效路径：** 数据库提交 → 日志 → mcsqueal → mcrouter → 缓存 delete；写者另删本地 cluster。

学习目标不是把“加缓存”记成代码模板，而是检查：**旧计算结果还能否越过某个已经生效的失效事件，重新成为后续读取的依据？**

课堂网站演进与全部反例见[中文译稿 03:00–17:00、29:00–32:00、71:00–84:00](#/c/mit-6.824-2021/lec/lec17?v=draft)。下面只提炼推理方法。

## 2. 为什么缓存故障会危及数据库

设总读到达率为 $Q$，缓存命中率为 $h$。暂时忽略一次 miss 触发多个 SQL 的情况，数据库读负载约为

$$
Q_{DB}=Q(1-h).
$$

若平时命中率 99%，数据库只承受 $0.01Q$。把一半流量转到一个完全空的 cluster 后，旧 cluster 那一半仍有 1% miss，新 cluster 那一半全部 miss：

$$
Q'_{DB}=0.5Q\times0.01+0.5Q=0.505Q,
\qquad \frac{Q'_{DB}}{Q_{DB}}=50.5.
$$

这是编者在讲义“约五十倍”基础上的明确算例。实际系统有时间变化、批量化和不同查询成本，不能把它当作精确容量规划，但它解释了为什么**一个可丢弃的数据层也能成为可用性的关键依赖**。

| 突发负载来自哪里 | 应对方法 | 增加的语义负担 |
|---|---|---|
| 热点键失效，大量读同时 miss | lease 发放限速，其他人稍后重试 | 回填资格与重新发放策略 |
| 冷 cluster 接管流量 | 从热 cluster 预热 | 热副本可能陈旧，需 hold-off/add |
| 少数缓存服务器失效 | Gutter 缓冲 | 快速过期但不常规失效，接受陈旧 |
| 同键请求超过单机能力 | 复制键或 cluster | 每份副本都需要失效 |
| 低热度对象被复制太多 | regional pool 共享 | 跨 cluster 网络与共享故障域 |

缓存数量越多，不只是失效消息更多，还会出现更多“可以读到旧值的来源”。每条捷径都应单独检查。

## 3. 最重要的不变量：delete 之后，旧许可不能复活

对一个缓存实例中的键 k，记 `grant(k,L)` 为发放许可，`delete(k)` 为收到失效，`fill(k,L,v)` 为提交回填。

核心条件是：

$$
grant(k,L)\prec delete(k)\prec fill(k,L,v)
\quad\Longrightarrow\quad fill\text{ 必须被拒绝。}
$$

这里的先后是缓存服务器处理这些事件的顺序。它并没有说“数据库一提交，所有缓存瞬间知道”；传播窗口仍然存在。它只保证一旦本实例已经知道失效，就不能再次接受此前发出的旧回填许可。

### 3.1 为什么缓存为空时的 delete 也不能略过

假设 C1 正在查数据库，缓存里还没有值。此时写者修改数据库，delete 到达空缓存。若实现仅做“找不到值，什么也不用做”，C1 就可能稍后把旧结果放回来。

所以缓存条目为空，不等于没有需要清理的协议状态。value 可以不存在，未完成刷新对应的 token 仍然需要撤销。

### 3.2 三种容易混为一谈的量

| 机制 | 回答的问题 | 不能推出什么 |
|---|---|---|
| 64 位 key-bound token | 这次回填是否仍获当前缓存许可 | 数据库被锁住、跨键事务隔离 |
| 每键默认十秒的 token 发放限速 | miss 洪峰中允许多少刷新者去后端 | token 恰好十秒有效、十秒内值不变 |
| delete 撤销已发 token | 已知失效后能否接受更早的读取结果 | 任意远端副本都已追上 |

论文只给出了这些职责与关键步骤，不足以推出一个完整的崩溃恢复状态机。尤其不能把 lease 理解成“第一位读者取得十秒排他锁”。写者不会等待这个读者释放锁，而是正常修改数据库，再使旧 token 作废。

## 4. 一个正确的失效不变量，为什么还覆盖不了另外两种竞争

### 4.1 冷集群：新许可也可能配上旧数据

考虑 delete 已在冷 cluster 完成，C2 **此后**才 miss，并取得新的回填许可。C2 从未收到失效的热 cluster 读到 v1，再填回来。

第 3 节的不变量没有被违反，因为 C2 的许可在 delete 之后才发放。问题在**值的来源**，不是 token 太老。预热期的 hold-off 为热 cluster 的失效传播留出窗口，使用 add，失败后重新查数据库。

但窗口只有两秒；若失效被延迟更久，仍可能出问题。精确步骤见[课程资料 §5.3](#/c/mit-6.824-2021/lec/lec17?v=materials)。这项修复降低错误概率，不是异步网络下永远正确的证明。

### 4.2 跨地域：本地数据库本身可能是旧来源

把热 cluster 换成本地数据库副本，同一个问题又出现：miss 不等于从权威最新值刷新。为了保护读己之写，remote marker 使特定 miss 转向主数据库。

正常日志失效路径所需的顺序是：

$$
apply_{replica}(W)\prec invalidate_{local}(W).
$$

这让失效触发的回源有机会读到已应用的 W。副本地域写者还需 **先设 marker，再写主库，最后删本地缓存**，以覆盖自己的立即重读；marker 通过复制到达后的失效清理。

marker 被淘汰或被另一并发写提前清理时，这项保护仍可能失效。因此上式是识别正常路径责任的规则，不是宣称系统所有读取都具备线性一致性。

### 4.3 两个检查缺一不可

一次缓存回填至少问两件事：

1. **资格检查：** 我拿到的许可有没有被后来的失效撤销？
2. **来源检查：** 我查询的数据源是否足够新，能够满足这次读的目标？

前者由本地 token 机制处理，后者涉及 warmup、数据库复制与 marker。把它们统称“加了 lease，就一致了”，会隐藏最关键的跨层问题。

## 5. 普通缓存值与协调元数据的可丢弃性不同

普通缓存值被淘汰：下一次 miss，重新算或查数据库；主要成本是延迟与后端负载。remote marker 被淘汰：下一次 miss 可能选择错误的数据源，读取尚未追上的副本。

所以“这是内存缓存，随时丢都没事”只适用于某些值，不自动适用于塞进同一缓存系统的协议元数据。数据结构名字相同，语义责任可以完全不同。

同样，Gutter 的定位是降低失败回源压力。短期过期意味着最终有机会刷新，但不等价于每次读都反映已完成写。不要因为主数据库有事务，就给旁边所有缓存路径都附加事务语义。

## 6. 与前几批课程的准确连接

### P3：复制正确，不等于任意本地读都新

[Raft 课程笔记](#/c/mit-6.824-2021/lec/lec05?v=notes)讨论如何让复制日志认同并提交命令。Memcache 没有让每个缓存读参与同一共识日志；数据库写可靠，也不能证明旁路缓存已收到失效。两者的共同方法是寻找完成点与可观察点之间缺失的前提，不是把缓存直接视为 Raft follower。

### P4：名字叫“通知”，并不表示能建立任意跨系统原子性

[ZooKeeper 笔记 §3–5](#/c/mit-6.824-2021/lec/lec09?v=notes)区分原子操作、通知和外部资源的安全性。这里 delete 也只在收到它的缓存实例上产生作用；前端先写数据库再删缓存，并不会自动变成一个不可分割操作。

ZooKeeper 的会话顺序契约与本讲“尽力读己之写”强度不同，不能因为两者都允许部分旧读就认为等价。缓存 lease 更不等于应用取得 ZooKeeper 锁后对外部资源的排他权。

### P5：服务权、事务锁、leader 租约与回填许可分别约束什么

| 机制 | 被约束的对象 |
|---|---|
| [事务两阶段锁](#/c/mit-6.824-2021/lec/lec13?v=notes) | 并发事务对记录的冲突访问 |
| [Spanner leader 租约](#/c/mit-6.824-2021/lec/lec14?v=materials) | 某段时间谁有领导权，如何证明租约不重叠 |
| [分片迁移的 Freeze/Install/Delete](#/c/mit-6.824-2021/lec/update-lab-bridge?v=notes) | 配置更换时哪一组有权服务该分片 |
| 本讲 cache lease | 某次数据库读取结果能否回填到指定缓存实例的键 |

可以迁移的思维方式是“旧权利在新边界之后还能否被使用”，不能直接迁移协议。Memcache 的 delete 只让缓存值失效；迁移里的 DeleteShard 是数据与服务权交接中的阶段，二者不是同一个接口。两秒 hold-off 也不能代替迁移的持久屏障。

固定 2026 实验继续使用既有版本化 Put、RSM、Freeze/Install/Delete；本讲不增加缓存、SQL、lease 或跨地域数据库事务的实验要求。

## 7. 自测：先找错的是资格、来源还是契约

### 题 1：缓存中没有 k，delete(k) 可以直接返回吗？

<details><summary>答案</summary>

如果还有 k 的回填 token，不能略过撤销。旧读者可能正在数据库查询途中，缓存为空只描述当前 value，不描述所有未完成刷新。

</details>

### 题 2：拿到 token 后不到十秒，为什么 set 仍可被拒绝？

<details><summary>答案</summary>

因为期间可能收到 delete，token 已撤销。十秒是论文中的默认发放限速参数，不是“这个客户端十秒内一定可以写”的承诺。

</details>

### 题 3：把所有 delete 都改成可靠 TCP，就能解决 stale set 吗？

<details><summary>答案</summary>

不能。即使 delete 可靠到达，早先数据库读的回填也可能在它之后到达。可靠传输不替代跨客户端、跨数据源的顺序判断；仍需 token 校验等机制。

</details>

### 题 4：冷 cluster 的新 token 完全有效，回填为何仍可能旧？

<details><summary>答案</summary>

因为它读的是尚未失效的热 cluster。资格有效不能证明数据来源新鲜。warmup 用 hold-off/add 缓冲传播，add 失败后回到数据库；两秒不是绝对传播上界。

</details>

### 题 5：副本数据库最终会更新，为什么不能提前删当地缓存？

<details><summary>答案</summary>

提前删会触发 miss；miss 若从旧副本回填，就把旧值重新保存。要使该更新对应的普通失效发生在本地数据库应用之后，写者的立即重读另由 marker 引导。仅说“最终数据库会一致”没有描述缓存里的旧结果如何清除。

</details>

### 题 6：两个并发写共用一个 remote marker 有什么风险？

<details><summary>答案</summary>

较早写的复制与失效可能清除 marker，而另一写仍在复制途中。此时 miss 误判本地副本可读。论文承认这个窗口，没有给 marker 计数或版本机制的完整修复，不能自行添加后再算作论文保证。

</details>

### 题 7：增加一倍分片，是否一定能把热门页面吞吐翻倍？

<details><summary>答案</summary>

不一定。单键热点仍落在一台服务器；若页面每次访问所有键，进一步分片还可能增加每请求扇出与包数。论文 §3.2.3 的 100 键算例说明，复制完整小数据集、把客户端分散到副本，反而可能更合适。

</details>

### 题 8：Figure 11 表明一秒内四个九，能称为“一秒有界陈旧”吗？

<details><summary>答案</summary>

不能。分位数或成功比例允许长尾，图里甚至有一天的尾部；监测对象还是抽样失效事件，而不是任意读取历史。一秒有界陈旧是不同强度的系统契约。

</details>

### 题 9：把缓存去掉，数据库继续运行，服务一定更安全吗？

<details><summary>答案</summary>

不一定。权威数据可能仍完整，但数据库可能被几十倍新增回源压垮。数据不丢失与服务有足够容量是两项独立要求。

</details>
