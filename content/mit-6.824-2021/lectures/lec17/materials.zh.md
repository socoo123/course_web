# Memcache 论文精读：缓存数据路径与失效路径怎样配合

## 1. 先画清系统边界

**论文 §1–2，PDF 第 1–2 页；Figure 1、2。**

论文讨论的系统处理每秒十亿级请求、保存万亿级条目，支撑当时十亿以上用户。这些是整个部署的量级，不是一个 memcached 进程的能力。目标负载读远多于写，数据既可能来自 MySQL，也可能来自 HDFS 或其他后端服务，因此缓存接口要比单一数据库页缓存更灵活。

| 名称 | 具体职责 | 不应附加的含义 |
|---|---|---|
| memcached | 单机内存 KV 程序，基本操作为 get、set、delete | 本身没有服务器间共识、持久化和容错复制 |
| memcache | Facebook 组织出的缓存系统，包含客户端、路由、配置和多个缓存池 | 不是一个统一线性一致 KV 状态机 |
| frontend cluster | 一组 Web 前端与相应 memcached 部署 | 不含一个独立的完整数据库权威副本 |
| storage cluster | region 中承载数据库的存储层 | 不是普通缓存池 |
| region | 多个 frontend cluster 加一个存储层 | 与“一个缓存分片”不是同一层次 |
| regional pool | 被同一 region 多个前端 cluster 共享的缓存池 | 不是跨 region 的数据库复制组 |

Figure 1 的两条路径很重要：读 miss 后是 **Web 前端**查询数据库并回填；写先进入数据库，前端再删除缓存。缓存不能被当作权威存储，普通值可以被淘汰。delete 的幂等性让重复失效更容易处理，但幂等并不能单独解决“旧读在 delete 后回填”的问题。

Figure 2 则把跨地域的数据库复制画在存储层之间。frontend cluster 中相同键的副本通常由用户需求自然产生，不是 memcached 之间互相同步每次 set。把这两种“复制”混为一谈，会误以为某一缓存 miss 可以随意找任何副本读而不改变一致性。

论文还把 memcache 用作通用结果缓存，例如机器学习预计算输出。第 2 页原文确实出现 “existing marcher infrastructure”；课堂也未能解释 marcher，此处只记录原文，不赋予它未经证实的组件含义。

## 2. 单个 cluster：减少往返，也限制并行洪峰

**论文 §3.1，PDF 第 3–4 页；Figure 3、4。**

### 2.1 一张页面不是一次 KV get

论文举的热门页面平均需要 521 个不同条目，95 分位达到 1740 个。应用把数据依赖组织成 DAG，把互不依赖的获取尽量并行批量发出；平均每批 24 个键，95 分位为 95 个。

这意味着两种简单做法都可能不好：逐键串行会累积网络往返；无限并行则让众多回复同时挤向一个接收端，形成 incast。客户端还承担序列化、压缩、路由、错误处理与批量化，并从辅助配置系统获得服务器映射。

### 2.2 UDP get 与 TCP 修改是按失败后果作取舍

get 可以由前端线程直接经 UDP 发往 memcached，绕过 mcrouter，省掉大量连接状态。客户端用序号识别丢包或乱序，把这些情况当错误，**这里的 UDP 实现并不负责重传恢复**。高峰时约 0.25% 的 get 被丢弃，其中约 80% 来自迟到或丢包，其余来自乱序。

get 错误可按 miss 访问后端，但此时不再回填缓存，以免给可能已经过载的网络或服务器增加压力。真正的缓存 miss 与网络错误都可能触发后端访问，却不一定具有相同的后续动作。

set、delete 要确认状态变化，因而经 TCP，通过与 Web 前端同机的 mcrouter。代理把大量线程的连接合并，减少缓存端的网络、CPU 与内存开销。Figure 3 的横轴是中位数的平均值与 95 分位的平均值，纵轴是微秒；比较的是直接 UDP 与“TCP 经 mcrouter”两条完整路径，不能把全部差异都归因于传输协议本身。论文报告约 20% 延迟改善。

### 2.3 客户端窗口控制所有目的地的并发

客户端有一个跨目的服务器的滑动窗口，限制尚未完成的缓存请求数。收到回复才允许继续发；成功时慢增，超时未响应时减小。它与 TCP 的区别是：TCP 窗口作用于单条流，这个窗口约束一批发往不同 memcached 的请求。

Figure 4 呈现“过小与过大都差”的趋势：小窗口把请求分成许多串行轮，延迟增加；大窗口产生 incast、丢包与回源，同样拉长时间。纵轴是 Web 请求处于 runnable、等待调度状态的时间，不是单次缓存服务器执行时间。

第 4 页给出 Little 定律：

$$
L=\lambda W.
$$

稳定条件下，平均系统内请求数等于到达率乘平均停留时间。在实验到达率保持相对固定时，延迟增加会让更多 Web 请求积压。作者用这个关系解释调度等待与系统负载的关联；不能由它直接推出任意一个窗口值都是全系统的最优值。

## 3. lease：三个概念，不能压成一句“十秒锁”

**论文 §3.2.1，PDF 第 4–5 页；FAQ 的 stale set 与 thundering herd 两组问答。**

课堂两条时间线见中文译稿 57:00–60:00、71:00–76:00；这里补精确语义。

### 3.1 回填资格：与键绑定的 64 位 token

客户端 miss 时，缓存可以发给它一枚与该键绑定的 64 位 token。客户端回填时必须提交 token，缓存据此判断此次 set 是否仍然有效。这是缓存实例对“谁可以把这次读取的结果放回来”的授权。

**token 不是数据库记录的锁，也不是数据库版本号。** 得到 token 的客户端不会因此锁住 MySQL 中的行，另一个客户端仍然可以更新数据库。token 本身也没有告诉缓存“数据库现在到底是哪一个版本”。

### 3.2 delete 撤销资格：阻止跨过失效边界的旧回填

收到 k 的 delete，缓存不仅删除已有值，也使先前给 k 的 lease token 失效。即使当时 k 根本不在缓存中，撤销 token 仍然有意义。

FAQ 比课堂更完整地列出两个读者：C1 用 L1 读到 1 后延迟；数据库更新到 2，delete 撤销 L1；C2 取得新许可 L2，回填 2；最后 C1 拿 L1 尝试回填 1，被拒绝。即使没有 C2，拒绝 C1 也能保留 miss 状态，让下一次合法回填重新查询数据库。

这个机制与 load-linked/store-conditional 有相似直觉：最初读到“不存在”不代表过一段时间仍有权写入，中间的失效事件会使条件写失败。它没有把数据库读与缓存 set 合成跨系统事务；delete 传播之前仍可能读取到旧缓存。

### 3.3 发放限速：减少惊群，不是精确租期规格

服务器还限制 token 发放频率。论文给出的默认配置是：**每个键每十秒至多发放一次 token**。这个窗口内的其他请求得到稍等再试的特殊通知；实际回填通常只要几毫秒，等待者随后重试就可能命中。

因此要分别记住：

1. token 校验决定回填资格；
2. delete 是撤销旧资格的事件；
3. 发放限速决定缺失期间允许多少刷新者进入后端。

论文没有据这段文字给出一个完整的 token 到期、客户端崩溃和重发状态机，不能把“十秒发放间隔”直接改写成“持锁十秒，十秒内数据保证不变”。FAQ 为突出正确性，把 L2 画在 delete 后，省略了发放节流的具体时机；它不是证明 delete 总能绕过限速立即发新 token。

测量针对一组容易惊群的键，持续一周：峰值数据库查询率从 17K/s 降到 1.3K/s。它说明回源抑制很有效，并不表示所有负载都能降低同一比例。

### 3.4 可以明确返回“陈旧值”，但不是悄悄冒充新值

某些应用可以接受旧结果。删除时，值可短暂移入最近删除的数据结构；get 返回带 stale 标记的旧数据，或返回 lease。能够用旧结果继续工作的应用不必等待刷新。

这进一步表明系统把短暂陈旧作为一种可调性能选择。这里的缓存 lease 与 [Spanner 的 leader 租约](#/c/mit-6.824-2021/lec/lec14?v=materials)职责不同：前者约束回填许可，后者要证明领导权时间区间不重叠，才能支撑特定读与时间戳规则。

## 4. pool、复制与 Gutter：三种不同的资源安排

**论文 §3.2.2–3.3，PDF 第 5–6 页；Figure 5。**

### 4.1 pool 首先是隔离工作负载

默认 pool 叫 wildcard。某些应用把键放进独立 pool，避免相互挤占：可以给“很常访问但 miss 成本低”的键较小空间，给“访问少但 miss 极贵”的键较大空间。只按访问频率分配内存，并不总能最小化后端成本。

Figure 5 比较 low-churn 与 high-churn 键族的日、周工作集，纵轴 TB，柱子分别是最小、平均和最大估计。高 churn 的一周工作集远大于一天；混在一个 LRU 中，仍有价值的低 churn 对象可能先于刚刚热过但已无人访问的对象被逐出。独立 pool 使不同淘汰特征可分别管理。

工作集估计是对百万分之一的条目采样，再依据条目尺寸放大；图不是逐字节盘点所有机器内存。

### 4.2 pool 内复制：批量请求数也可能是瓶颈

论文给了一个非常有用的算例：100 个键都能放入一台服务器，每个请求一次取这 100 个键，服务器每秒可处理 50 万个这种请求。目标增长到每秒 100 万请求。

若把键对半分到两台服务器，每个应用请求仍要同时联系两台，每台处理约 50 个键，但每台都接到每秒 100 万个请求。若主要成本是每请求开销，分片没有消除瓶颈。

若两台都保存全部 100 个键，每个客户端只选一台，就可以让每台各处理约 50 万请求。论文按客户端 IP 选择副本，失效必须送到所有副本。这里的复制与 region 内多个 cluster 复制是不同层次的同一种资源取舍。

### 4.3 Gutter 是失败缓冲，不是同步热备

少量服务器故障时，自动修复仍可能需要几分钟。约占 cluster 缓存机器 1% 的 Gutter 池承接失败请求：原服务器无响应，客户端先问 Gutter；仍 miss 才查询数据库并填入 Gutter。

Gutter 条目很快过期，从而不必加入常规失效广播。代价是可能暂时陈旧。它不是保存主缓存每次写的热备，也不承担“任何故障后仍严格读己之写”的证明。

为什么不直接把失败键重新哈希给其他正常缓存？一个键就可能占原服务器 20% 的请求，接收它的繁忙服务器可能再过载，形成级联失败。把负载送到留有余量的池，降低这种风险。

测量要看清分母：论文分别报告客户端可见失败减少 99%、每天有 10%–25% 的失败被转换为 Gutter 命中；整台服务器失效时，Gutter 命中率通常在四分钟内超过 35%，常接近 50%。这些不是同一个指标。若整个 frontend cluster 下线，则把用户请求转给其他 cluster，不能指望这个小池接住整个 cluster。

Gutter lease 的完整并发协议未在本论文说明，课后问答也未得到确定答案。本文不补造细节。

## 5. 同一 region：失效流水线、共享池与预热

**论文 §4.1–4.3，PDF 第 6–7 页；Figure 6、Table 1。**

### 5.1 应用必须告诉日志哪些缓存键受影响

数据库行与缓存值之间可能有复杂映射。论文不是让 mcsqueal 自动理解所有应用逻辑，而是在修改权威状态的 SQL 中附带提交后需要删除的缓存键。mcsqueal 检查提交内容，提取这些键，把 delete 发往本 region 的各 frontend cluster。

Figure 6 的顺序是数据库提交日志 → mcsqueal → cluster 内 mcrouter → 负责具体键的 memcached。mcsqueal 批量打包失效，各 cluster 的代理解包并路由；“每包包含的 delete 数”的中位数提高 18 倍，不能说成系统总吞吐提高 18 倍。

为什么不由每个写前端向所有 cluster 广播？一是小前端不容易高效合批，跨 cluster 包数很大；二是若配置错误导致 delete 错路由，前端没有可靠、可重放的全局历史。嵌入数据库日志后，mcsqueal 可以重放丢失或误路由的失效。论文说只有约 4% 的 delete 真正命中被缓存的数据，这也说明“把新值广播给所有可能缓存处”会浪费很多工作。

前端自己删本地 cluster 是额外的 read-after-write 优化，不替代这条全局失效管道。

### 5.2 regional pool 节省复制空间，也增加跨 cluster 成本

同一 region 的 cluster 若随机接收用户流量，会逐渐缓存相似内容；这样下线一个 cluster 时，其他 cluster 仍可能有较好的命中率。但大型冷对象重复存很多份不划算，regional pool 可以使它们在 region 内共享一份。

代价是跨 cluster 访问延迟更大；论文环境中跨 cluster 的平均可用带宽比 cluster 内少 40%。因此“对象大就应该放 regional pool”也不对，必须结合访问频率与用户共享程度。

Table 1 的两类对象说明这个判断：A 的 get 约 3.26M/s、值中位数 10.7 kB、用户数中位数 30；B 是 458K/s、4.34 kB、1。B 虽然比 A 小，仍会占每个 wildcard pool 约 25%，而且访问少，迁移到 regional pool 更划算。A 访问太频繁，区域共享可能压垮跨 cluster 网络。该表是两个键族的比较，不是两种产品的吞吐基准。

### 5.3 冷集群 warmup 的实际动作是 add，不是无条件 set

完整课堂反例见中文译稿 76:00–81:00。论文的补救步骤是：

1. 冷 cluster 的 delete 使用默认两秒 hold-off。
2. 冷 cluster miss 时，先从热 cluster 取值。
3. 尝试用 `add` 放入冷 cluster；hold-off 期间拒绝该操作。
4. 如果 add 失败，按论文流程从数据库重新获取，而不是把借来的旧值当作已安全缓存。
5. 冷 cluster 命中率稳定、继续借用收益减小时，关闭 warmup。

这与普通 lease 防 stale set 的差别在于：即使新读者在 delete **之后**才取得许可，它从热 cluster 读到的也可能是旧值；单纯撤销 delete **之前**的 token 无法证明这次借来的数据新鲜。

两秒窗口是概率性工程缓冲。失效若超过两秒才到热 cluster，仍有理论上的错误窗口；论文明确接受这种少见情况。这里不提供任意网络延迟下的正确性证明。预热把恢复满负载的时间从几天缩短到几小时，但它不是当前所有 memcached 版本都必须保留的通用 API 规格。

## 6. 跨 region：先有可读的新数据，再使旧缓存失效

**论文 §5，PDF 第 7–8 页。**

### 6.1 主地域写：不能让远端 delete 跑在数据库复制前面

主 region 持有可写数据库，其他 region 持有只读副本，由 MySQL 日志复制追赶。当地缓存 miss 可以读当地数据库，所以失效传播必须与副本数据到达的顺序配合。

若主地域前端在提交后立即向副本地域发 delete，而数据库更新尚未复制过去，副本地域下一次 miss 会读到旧数据库值，并再次填入缓存。后续即使数据库更新到达，如果没有适当的失效，旧缓存仍可能留下。

因此正常日志路径使副本数据库应用更新后，再由当地 mcsqueal 广播该更新对应的失效。删除流与复制流共享跨地域通信通道，也减少广域网络成本。下游无响应时，数据库与 mcrouter 缓冲 delete，恢复后重放；缓冲期间陈旧概率上升，系统选择不立即大面积清空缓存或下线 cluster。

### 6.2 副本地域写：remote marker 的三个动作有先后

副本 region 的前端必须去主地域写，但希望用户立即重读时能看到自己的操作。论文对键 k 引入独立标记 rk：

1. **先**在本 region 的 regional pool 设置 rk。
2. 向主数据库执行写，把 k 与 rk 的失效信息一并嵌入 SQL。
3. 主数据库写完成后，删除本地 frontend cluster 的 k。

后续 get(k) miss 时，检查 rk：存在就去主地域数据库，不存在才从本地副本查询。随着复制到达本地并应用，日志中的失效清理 k 与 rk，于是普通本地读路径可以恢复。

课堂把它概括成“delete 后将键标为 remote”，适合先建立直觉；实际顺序不能随意互换。如果等到写后很久才创建 marker，中间就有重新从滞后副本回填的窗口；如果一个迟到 marker 在相应删除之后才建立，也会偏离预期生命周期。

### 6.3 marker 不是普通缓存值，丢失会改变决策

论文明确承认两个限制：marker 可能被缓存淘汰；两个并发修改同一个键时，一次操作的失效可能清除另一次仍然需要的 marker。两者都可能让读误以为本地数据库已足够新。

所以整个系统提供的是 **best-effort eventual consistency，偏重性能与可用性**，并尽量减少读不到自己写入结果的情况。它没有为所有故障与并发历史给出严格 read-your-writes，更没有提供线性一致性或跨键快照。

普通缓存值丢失，通常只是多一次回源；marker 丢失却会改变“应该信任哪份数据库”的判断。这是把缓存当协调元数据时必须特别辨认的边界。

## 7. 单机优化：CPU、内存与升级同样影响后端生存

**论文 §6，PDF 第 9–10 页；Figure 7、8。**

### 7.1 并发与网络优化的实验条件

早期改进包括哈希表动态扩容，避免负载增长后查找退化；增加多线程；每线程独立 UDP 端口，分散回复竞争与中断处理。随后把全局锁细化。

论文测试用 Xeon X5650、2.67 GHz、12 核与 12 个超线程、千兆网络、12 GB 内存；15 个客户端对一个 24 线程服务器施压，客户端与服务器位于同一机架，每次持续两分钟。生产机器有更多内存。这些条件不能当作 2026 硬件上的性能承诺。

Figure 7 的纵轴是 **items/s**，测量在平均响应低于一毫秒时可维持的最大速率；不是完整网页请求/s。10-key multiget 命中时，细粒度锁把 0.6M 提高到 1.8M items/s；全部 miss 从 2.7M 到 4.5M。miss 更快，是因为整批都缺失时可返回一个静态 END，命中则要构造和传输实际数据。

Figure 8 比较单 get 与 10-key multiget、TCP 与 UDP。UDP 分别比其 TCP 实现高约 13% 与 8%；multiget 约四倍的 item 处理率反映批量减少包开销，不是“十个键免费等于一个键”。

### 7.2 slab 自适应分配近似全局 LRU

memcached 用 slab class 管理不同大小条目。条目连同键和元数据进入能够容纳它的最小类；这份实现从 64 字节起，按 1.07 因子增长到 1 MB，按 4 字节对齐。每类维持空闲列表与自身 LRU，内存按 1 MB slab 分配。

问题是工作负载改变后，有些类不断淘汰仍热门的数据，另一些类却保留很久不用的对象。自适应分配器比较各类最老条目的最近使用时间：正在淘汰且候选对象比其他类最老对象的平均情况新至少约 20% 的类，被视为需要更多空间；再从持有最老对象的 slab 腾出空间转给它。

作者强调是在平衡“最老对象年龄”，不是只平衡淘汰率。淘汰率本身也受访问模式影响，不能单靠它判断哪里更缺内存。

### 7.3 短命对象到期与释放物理内存是两件事

普通过期检测是惰性的：get 时或对象到 LRU 尾部才检查。因此一个短时间热过、随后再没人访问的对象，即使逻辑上过期，也可能继续占内存。

Transient Item Cache 用按秒索引的环形链表桶组织短命对象，每秒清理到期桶。某个短寿命键族占缓存池的比例从 6% 降到 0.3%，命中率不变。这里释放内存带来的收益，不等于修改了普通读写的一致性协议。

### 7.4 升级不能随意清空所有热数据

服务器重新填热可能要几个小时，大范围升级若触发回源峰值，就可能需要超过十二小时逐步进行。作者把缓存值和主要数据结构放进 System V 共享内存，使软件升级时能保留热状态。

这是一种运维优化，不是把易失缓存变成磁盘持久数据库。缓存层与持久层分离后，故障、维护、升级都必须把对后端流量的影响计算进去。

## 8. 如何正确阅读测量，而不夸大保证

**论文 §7，PDF 第 10–12 页；Figure 9–11、Table 2–3。**

### 8.1 不同页面的 fanout 差别很大

Figure 9 是访问不同 memcached 服务器数量的累积分布。总体约 56% 的页面请求联系少于 20 台服务器，但某个热门数据密集页面多数请求超过 100 台，访问几百台并不少见。总体中位数不足以描述重页面的网络压力。

Figure 10 是返回值大小的 CDF，正文给出中位数 135 字节、均值 954 字节，说明长尾明显。图只展示到数百字节附近，不能从截取的横轴读出完整长尾均值。正文“three distinct peaks at approximately 200 bytes and 600 bytes”只有两个近似位置，表述本身不充分；本文不据此猜出第三个峰。

七天测量中请求延迟中位数 333 μs，p75 为 475 μs，p95 为 1.135 ms；空闲 Web 前端测得的相应值为 178、219、374 μs。它们包含路由、网络、反序列化与解压，繁忙时还有线程调度影响，不是纯服务端哈希查找时间。

### 8.2 四种 pool 的请求率与对象尺寸不能互相替代

Table 2 中，wildcard、app、replicated、regional 的 miss rate 分别为 1.76%、7.85%、0.053%、6.35%；对应 get/s 为 262K、96.5K、710K、9.1K。这些是选定 pool 的单服务器统计，不是整个 Facebook 的总量。

replicated pool 以更少包服务更多键：710K get/s 对应 44.5K packets/s，反映复制与批量访问的结合。regional pool 的 get 少，但 delete 达 35.9K/s，不能用读请求少来推断整台机器完全空闲。

Table 3 的 replicated 对象非常小，均值 66 字节，p50 为 68；regional 对象均值约 31.8K 字节，p50 5.31K，p99 381K。工作负载不仅访问频率不同，尺寸长尾也不同，所以独立管理 pool 有意义。

**原文统计口径疑点：** §7.2 说每四分钟取平均，并报告一个月采集期内的最高平均值；Table 2 标题却写 averaged over 7 days。两处已在实际页面核对，不能把它们强行拼成一个毫无歧义的实验窗口。

### 8.3 Figure 11 证明的是长尾存在，不是两秒新鲜度上界

失效健康监测抽样百万分之一的 delete，记录发出时刻，随后定期检查各前端 cluster 是否仍缓存应该删除的值。

Figure 11 纵轴是仍未完成相应失效的比例，**对数尺度**；横轴从 1 秒到 1 天，分别画主 region 内失效与副本 region 间路径。正文报告：主 region 内约一秒达到四个九、一小时达到五个九；副本 region 间约一秒达到三个九、十分钟达到四个九。

因此“通常几秒内足够新”是工程目标或经验，绝不是“任何条目绝不会落后超过几秒”的协议保证。图里直到一天仍有很小的尾部。FAQ 也直接承认这种不一致会增加应用开发难度，系统愿意为规模与可用性承担少见的陈旧读取。

这组图不能被转换成“缓存系统线性一致概率为某个数”；它测量的是失效管道中特定抽样事件的延迟，不是所有并发历史的完整一致性判定。

## 9. 论文结束处的设计经验与历史边界

**论文 §8–9、致谢与文献表，PDF 第 11–14 页。**

相关工作把系统放在更大空间里：Dynamo 偏重写与高可用，memcache 的动机是读密集；RAMCloud 等主存系统讨论权威存储与持久性，本系统将持久责任交给外部存储；事务查询缓存与通用应用缓存也有不同接口需求。

论文简述 TAO：固定长度标识符的图数据模型，并把图到持久层的映射编码在系统里，承担持久化责任；两者又复用了客户端和路由组件。这只是本文已读段落的定位，不代表已经阅读 TAO 或 FAQ 链接的后续论文。

作者总结的经验可以概括为：分离缓存与持久存储，便于独立扩展；监控、调试与运维效率和峰值性能一样重要；尽量把复杂逻辑放在容易迭代的无状态客户端；新功能必须能逐步上线和回滚，允许暂时异构；保持组件简单。

这些选择不是对所有系统都成立的最优解。它们受在线业务、工程人力、已有软件与负载形态约束。尤其本文所有 `get/set/delete/add`、lease 和 marker 都是历史缓存系统描述，不是固定 2026 Lab 2 的版本化 Put、Lab 4 的 RSM 或 Lab 5 的迁移接口。

讲义中未在课堂完整展开的池内批量复制、网络合批、单机内存和运维细节已在 §2、§4、§7 补齐；讲义关于“为何不按用户分 region”“为何不由数据库主动发新值”的提示分别指向社交访问局部性、应用派生结果、按需缓存与读己之写延迟等取舍，不需要再生成一份重复课堂提纲的译文。
