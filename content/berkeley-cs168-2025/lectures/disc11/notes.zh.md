# 每一次优化，都要说清工作从谁移到了谁

主线：[L23 SDN 与主机网络](#/c/berkeley-cs168-2025/lec/lec23?v=notes)、[L22 网络虚拟化](#/c/berkeley-cs168-2025/lec/lec22?v=notes)、[L21 数据中心拥塞](#/c/berkeley-cs168-2025/lec/lec21?v=notes)。先区分控制器、软件交换机、内核、NIC 和应用五个角色，再用原题练习追踪状态。页码均为题卷／官方解答的 PDF 页码。

## 1. 性能选择题：不是所有“快”都来自同一层

### 1.1–1.2：为什么值得优化主机网络？

定位：题 p.1；解 p.1。

<details><summary>展开 1.1、1.2</summary>

- **1.1：a、c、d。** 数据中心应用可能有严格吞吐和尾延迟要求；云商节省的 CPU 周期可以用于可售计算；运营者能统一控制自己的网络、服务器和软件。b 把网络硬件成本说成高于计算硬件，不符合本题的成本模型；不能因链路很贵就忘掉海量服务器的支出。
- **1.2：a、b、c。** Kernel bypass 让用户态实现更灵活的数据路径，避免为每次实验修改内核，并可能减少系统调用、拷贝和调度开销。它不是自动节约硬件支出的保证，轮询还可能持续占用核心。绕过内核也不等于可以绕过访问控制、缓冲区隔离或资源管理。

</details>

### 1.3–1.5：无状态卸载与更新难度

定位：题 p.1；解 p.1。

<details><summary>展开 1.3、1.4、1.5</summary>

- **1.3：True。** 所需输入随当前包／工作描述符给齐，不必在 NIC 内维护跨包连接状态，因此状态一致性和失效恢复更简单。
- **1.4：False。** 已固化的硬件能力受芯片、固件、驱动接口限制，修改通常没有用户态代码灵活；“在 NIC 中”并不等于所有设备永不可编程。
- **1.5：True，按课程卸载分类。** 分段卸载从一份大缓冲区及提供的首部、MSS 等元数据生成分段，不必代替主机运行完整的跨包 TCP 控制状态机。内部暂存计数器不等于这里所说的有状态协议卸载。

</details>

### 1.6：拥塞信号的信息量

定位：题 p.2；解 pp.1–2。

<details><summary>展开选择与比较边界</summary>

官方选 **a、c**。ECN 能在缓冲溢出丢包前标记排队压力，标记比例可保留比“是否观察到丢包”更早的拥塞线索；微秒级时延测量则容易受时钟、主机处理和采样误差影响。

b 不成立：不能把 ECN 直接排在所有精确时延信息之上。d 也不应成立：观测接收速率受发送速率、应用空闲、竞争和路径瓶颈共同影响，低速不唯一意味着拥塞。这里的“更多信息”是课程对信号用途的比较，不是脱离编码、采样方法和噪声之后的严格信息论全序。

</details>

### 1.7：QoS 何时改变结果？

定位：题 p.2；解 p.2。

<details><summary>展开官方选项及严格表述</summary>

官方选 **a、c、d**：竞争时按业务类型区分优先级，可以用 weighted fair queueing 执行份额策略；一个 class 可汇聚多条流，因此 b 错。

**a 的“只有 100% 利用率才重要”过强。** 教学意图是“没有竞争且队列空闲时，工作保持型调度器无需做取舍”。但长期平均利用率小于 100% 的链路仍会有短时突发和排队，QoS 可影响这些包的尾延迟；整形／限速也可在未满载时生效。应保留官方答案同时记住这个反例，不能把平均利用率阈值当实施 QoS 的必要条件。

</details>

## 2. SDN：三种抽象，不是一个协议

定位：2.1–2.4 题 p.3；解 p.2。

### 2.1：传统控制平面缺少什么？

<details><summary>展开官方 “None” 的语境</summary>

传统 L2/L3 分布式协议把发现状态、分布式一致性、路径计算和策略揉在实现中。官方回答“None”，是说缺少 SDN 所强调的统一、可编程控制平面抽象，并非传统网络没有路由表、协议接口或任何抽象。工程问题在于运营者要通过很多局部协议参数间接表达全局目标。

</details>

### 2.2：三层职责分离

<details><summary>展开需要的抽象</summary>

1. **转发抽象：** 设备能匹配什么字段、执行什么动作，以统一接口表达；OpenFlow 是一种实例。
2. **分布式状态抽象：** Network Operating System 收集拓扑和状态，给控制程序一个全局视图，而非让每个应用重写状态分发。
3. **配置／意图抽象：** 在抽象网络上指定所需行为，再转换成实际转发规则。

逻辑集中不意味着系统必须只有一个进程或一台物理控制器；高可用部署仍可复制控制器。

</details>

### 2.3：链路失效的控制链条

<details><summary>展开检测、计算与安装</summary>

邻接交换机检测链路变化并上报；控制器更新全局视图、重新计算受影响路径，再下发新的转发表规则。检测到失效不代表所有设备已同步安装完成：过渡期间可能有丢包或不一致，系统要另外设计更新顺序／快速保护。题目没有给出这些机制，因此不能凭空承诺无损瞬时恢复。

</details>

### 2.4：OpenFlow 的位置

<details><summary>展开为何不等价</summary>

OpenFlow 主要提供控制器与转发设备之间的规则接口，只覆盖上面的转发抽象。SDN 还包括状态视图、控制程序和策略表达；也可用其他南向接口实现。因此“不使用 OpenFlow 就不是 SDN”和“装了 OpenFlow 就完成全部 SDN”都不成立。

</details>

## 3. 虚拟网络：同一个 IP 值为什么能有两个接收者？

定位：3.1–3.4 题 p.4；解 p.3。已目视拓扑和包布局：S1 上 VM1 属租户 A、VM2 属租户 B，两者都是 `10.0.0.1`；S2 上 VM3 为 A 的 `10.0.0.2`，VM4 为 B 的 `10.0.0.3`。物理路径 S1–R1–S2。包按“外 IP｜VNET ID｜内 IP｜Payload”排列。

### 3.1–3.2：隔离名字空间与实现位置

<details><summary>展开地址重叠的目的与部署选项</summary>

- **3.1：** 租户独立选择自己的地址范围，无需与其他客户协调；全平台规模不再受一套共享私网地址池限制。同一租户内部仍须避免不希望出现的重复地址。
- **3.2：** Hypervisor／软件交换机可以加删虚拟网络头并解复用；也能将这些操作卸载给 NIC。选择取决于 CPU 成本、灵活性和硬件能力，不是必须在物理中间路由器中修改所有功能。

</details>

### 3.3：S1 的接收侧 match-action

<details><summary>展开两条规则及适用范围</summary>

| 已送达 S1 的虚拟网络 ID | 本地交付动作 |
| --- | --- |
| A | 交 VM1 |
| B | 交 VM2 |

两台本地 VM 的目的 IP 都是 `10.0.0.1`，所以单看 IP 无法区分；VNET ID 恢复了租户上下文。

官方仅填写这两条接收侧规则。它们应理解为已完成外层路由、解封装并确定目的为本地 `10.0.0.1` 的包。若不加上下文而对所有包无条件匹配 A→VM1，就会把 VM1 发向 VM3 的出站包误交回 VM1。因此这张表不是整个双向网络的全部规则；一般还需要方向、内层目的、隧道端点映射和隔离检查。这里明确边界，不把官方两行表扩充成题目未提供的地址配置。

</details>

### 3.4：match-action 能承担什么？

<details><summary>展开 a、c、d 的依据</summary>

限速可配 meter，访问控制可匹配后丢弃／允许，计费统计可更新 counter，因此选 **a、c、d**。HTTP 缓存涉及对象语义、存储、有效期和通常的应用协议处理，不能靠本题简单的包首部 match-action 表自然完成；它不是与前三项同层级的一个转发动作。

</details>

## 4. RDMA Send：两个应用与两个 NIC 的账本

定位：4.1–4.6 题 p.5；解 p.4。本节限定 **Send/Receive 双边操作**，不是把单边 RDMA Write 的行为搬来。

### 4.1–4.2：收益和准备工作

<details><summary>展开收益与两侧注册</summary>

- **4.1：b、c。** 数据移动／协议处理更多交给 NIC，可降低 CPU 开销并改善性能；注册、队列、权限与内存生命周期管理不保证更简单，也不保证迭代更快。
- **4.2：两侧都要注册缓冲区。** 发送侧让 NIC 能访问源数据，接收侧提供可写的目标内存及权限。注册成功不等于已经提交一次发送或接收工作请求。

</details>

### 4.3–4.4：发起与接收准备

<details><summary>展开工作队列顺序</summary>

- **4.3：** 发送应用向 send queue 提交引用已注册源缓冲区的工作请求。官方简写“放指针”，实际是带地址、长度、内存访问键等信息的描述符，而不是让网卡无条件访问任意裸指针。
- **4.4：** 接收应用需要预先向 receive queue 提交可用接收缓冲区。Send 并不知道对方任意虚拟地址；由接收端排队的缓冲区承接。缺少 receive 不等于网卡会自动分配一个应用可用缓冲区。

</details>

### 4.5–4.6：完成通知的含义

<details><summary>展开 CQE 的产生与消费</summary>

- **4.5：** 每侧 NIC 在对应工作完成时生成 completion queue entry，软件不是靠猜测经过的时间来补写完成项。
- **4.6：** 应用检查 completion queue，并核对工作标识与成功／错误状态；只有相应完成语义允许时才能复用缓冲区。发送完成不是“远端应用已经消费并处理了数据”的证明，接收完成也不等于业务事务完成。实际可采用轮询或事件驱动，本题不要求执行任何 RDMA 程序。

</details>
