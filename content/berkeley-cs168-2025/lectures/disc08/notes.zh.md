# 并发能重叠等待，不能凭空增加总带宽

先修：[L16 DNS](#/c/berkeley-cs168-2025/lec/lec16?v=notes)、[L17 HTTP](#/c/berkeley-cs168-2025/lec/lec17?v=notes)、[L12 TCP](#/c/berkeley-cs168-2025/lec/lec12?v=notes)。本页按实际 PDF 的问题编号组织。W/S 一律为文件中的物理页码，而非印刷页脚；两者不同时特别标出。

## 1.1 HTTP 管线化与多路复用（W1；S1）

<details><summary>官方判断与协议层边界</summary>

官方判假，指 HTTP/1.1 pipelining 没有成为常见浏览器实践：响应顺序要求会使慢响应阻塞后续响应，历史兼容性问题也妨碍部署。HTTP/2 的多流帧机制不能直接等同于 HTTP/1.1 管线化。

官方称 HTTP/2 避开上述问题，应限定为 HTTP 层响应顺序的阻塞；HTTP/2 仍在单一 TCP 字节流上运行，丢包导致的 TCP 队头阻塞仍存在。不要得出“HTTP/2 没有任何队头阻塞”的结论。

</details>

## 1.2 谁执行迭代查询（W1；S1）

<details><summary>推导与答案</summary>

通常是本地递归解析器完成向根、TLD、权威服务器的迭代查询，终端 stub resolver 向它提出请求，因此按题意为假。这里“本地”指所使用的递归解析服务，不必物理位于同一台电脑或同一局域网。

</details>

## 1.3 区域的服务器冗余（W1；S1）

<details><summary>课程答案与“always”的边界</summary>

官方判真，意在强调区域权威服务的冗余配置。学习时应记住多个权威服务器避免单点失效，而不是将“任何区域永远至少两台”当成可从 DNS 报文格式推出的事实。错误配置、私有区域及服务故障都使字面上的全称说法过强；两个 NS 名称也不自动证明两个独立故障域。

</details>

## 1.4 根服务的 anycast（W1；S1）

<details><summary>路由选择与“最近”的含义</summary>

按服务部署语义，官方判假：同一个根服务地址可由多个站点通告，客户端到达其中一个实例，这是 anycast。实现仍使用普通 IP 转发和 BGP 路由机制，不是 BGP 查询出一个名字服务器后逐包复制。官方说“最近”应理解为路由策略选中的实例，不保证地理距离或 RTT 最小。

</details>

## 1.5 能否与根服务器建立 TCP（W1；S1）

<details><summary>官方答案有误：标准明确要求 TCP</summary>

官方给出“不能”，理由是 anycast 可能把不同报文送到不同实例。该风险不能推出 TCP 不可用：在连接期间路由稳定且流量落在同一实例时，TCP 能正常工作。

更直接的依据是 [RFC 7720 §2](https://www.rfc-editor.org/rfc/rfc7720.html#section-2)：根名字服务必须支持 UDP 和 TCP 查询与响应。[RFC 7766 §5](https://www.rfc-editor.org/rfc/rfc7766.html#section-5) 也要求通用 DNS 实现同时支持两种传输。因此本题若按实际 DNS 标准判断，应为真。路由变化可能中断某条连接，与协议禁止建立连接是两回事。本页明确保留官方判定作为勘误对象，不将其传播为事实。

</details>

## 1.6 不存在 TLD 的查询比例（W1；S1）

<details><summary>区分测量结论与协议规则</summary>

官方判真。无效后缀、配置错误和名称泄漏能使根收到大量最终返回否定结果的查询。但“多数”需要特定观测时期和采样范围；本题没有附数据集，不能把它当成所有年份、所有根实例必然超过 50% 的协议性质。本页不虚构最新比例。

</details>

## 2 重复 DNS 题的逐项复习

该组与讨论 7 第 4 组使用同一图和参数；完整事件推导见[讨论 7：DNS 缓存时钟](#/c/berkeley-cs168-2025/lec/disc07?v=notes)的 4.1–4.3。原图 a 为主机到解析器，b–e 为解析器到四级 DNS 服务，均为单向时延。这里保留本卷编号与短答案，避免把相同推导重复成两份。

### 2.1 无缓存（W2；S2）

<details><summary>短结论与复习点</summary>

统一单位后，令 H 为可用总时长、C=2(a+b+c+d+e+t)。最多完成 floor(H/C) 单。对应讨论 7 的 4.1：关键是四轮上游 DNS 查询串行，且每单都要重做。原总述 T 为分钟，而延迟若以秒给出，应先把 H 写为 60T 秒。

</details>

### 2.2 TTL 覆盖全部时间（W2；S2）

<details><summary>短结论与复习点</summary>

若 H<C，完成零单；否则完成 1+floor((H−C)/(2a+2t)) 单。对应讨论 7 的 4.2：缓存位于解析器而不是主机，所以后续仍需 2a。TTL 和 H 必须使用一致单位。

</details>

### 2.3 有限 TTL（W2；S3）

<details><summary>短结论与边界检查</summary>

答案为 120 单，采用完成时间不晚于 600 s 的口径。最终 DNS 记录在 9 s 缓存、39 s 过期；第八单从 36 s 开始，其 DNS 请求 37 s 已命中，故可以在 40 s 完成。此后每 40 s 重复八单。完整时间表见讨论 7 的 4.3；不要在订单完成时检查 TTL，也不要直接将 600/30 当成刷新次数。

</details>

## 3 HTTP 性能：先画依赖，再加时延

HTML 必须完整获得后才能发现两个媒体对象。原题 z 是单向小报文传播时间；P、M 与速率 T 应采用兼容的数据单位。并发两连接时每条只有 T/2，不是各自拥有 T。题设不等待连接拆除；不另加 DNS、TLS、慢启动或处理时间。

### 3.1 非持久、顺序请求（W3；S3、5）

<details><summary>每个对象单独付连接成本</summary>

获取大小 X 的对象需要：握手等待 2z，请求到达 z，响应传播 z，再加 X/T 的数据发送时间。所以三个对象顺序相加：

$$
D_1=12z+\frac{P+2M}{T}.
$$

原手绘 Q1（物理 S5）将握手最后 ACK 与 HTTP 请求一起画出；即便作为背靠背的独立小包发送，在本题忽略序列化间隔的模型下也无需额外等一轮 RTT。

</details>

### 3.2 非持久、媒体并发（W3；S3、6）

<details><summary>只重叠能独立进行的部分</summary>

HTML 仍先花 4z+P/T。之后两条媒体连接握手同时进行，共同等待 4z；每个媒体以 T/2 传输，完成用时 M/(T/2)=2M/T。因此：

$$
D_2=8z+\frac{P+2M}{T}.
$$

原手绘 Q2（S6）媒体阶段标的是 M/(T/2)，不能把分母误读为 T。并发省下传播等待，不会把这两个媒体的总数据发送量除以二。

</details>

### 3.3 持久连接、顺序请求（W3；S4、7）

<details><summary>复用连接并不复用响应等待</summary>

HTML 首次花 4z+P/T；随后每个媒体不再握手，但仍分别等待一轮请求/响应传播 2z，再发送 M/T。故：

$$
D_3=8z+\frac{P+2M}{T}.
$$

此模型下与 3.2 恰好相等，原因不同：一个重叠了两次握手，一个删除了后续握手。不要由数值相等推断两种机制相同。

</details>

### 3.4 持久连接、管线化（W3；S4、8）

<details><summary>最后一位到达决定完成时间</summary>

HTML 后把两个请求连续送出，传播等待只付一次 2z；服务器在同一连接依次发送两个 M 大小响应，总发送时间 2M/T。第二个响应可以在第一个响应最后一位发出后立刻开始，不必等待第一份抵达客户端：

$$
D_4=6z+\frac{P+2M}{T}.
$$

原手绘 Q4（S8）上半段为 HTML，下半段两个响应连续铺在线路上，并标了两个 M/T。媒体名字在图上写为 media2、media1，与正文顺序相反；二者大小相同，不影响总时长，也不应由此声称 HTTP/1.1 允许随意颠倒响应顺序。

</details>

### 3.5 小对象与大对象（W3；S4）

<details><summary>比较时间项而不是只比较文件数</summary>

若 M/T 远小于 z，传播和交互轮次支配总时间；复用、并发、管线化减少轮次的收益明显。若 M/T 远大于 z，数据序列化项占主导；给同一瓶颈增加连接不会增加题设总速率 T。这里对 T 的使用是题定有效发送速率模型，不把传播时间再次包含进 T 后重复计入。

</details>

## 4 两层 HTTP 代理：并行握手与两项缓存

W4 的页脚印为 5；S9–11 的页脚为 5–7，后附手绘 S12–14。原拓扑为 A—P1—Internet—B，以及 Internet—P2—C。每条画出的接入链路单向为 L，穿过 Internet 另计 I。由图得：P1→B 为 2L+I，P1→P2 为 2L+I，P1→C 为 3L+I。

每个代理只缓存最近两个 HTTP 请求的结果；各代理只能看见实际经过自己的请求。握手相互重叠，不是沿每一段把完整三次握手机械串联。题设虽提三报文拆除，但明确不必等拆除完成才能开始下一请求。

### 4.1 顺序请求与分层命中（W4〔印5〕；S9–10、12–14）

<details><summary>先算一类请求，再维护缓存状态</summary>

定义单向延迟 D=2L+I、E=3L+I。A 的 SYN 花 L 到 P1；P1 的上游握手等待 2D 时，A—P1 的握手和请求已在并行完成。因此到 P1 能向上游发 HTTP 请求的关键时刻为：

$$
S=L+2D=5L+2I.
$$

到 C 也采用这一关键等待：P2 与 C 的较短握手被跨 Internet 的等待遮蔽。ACK 不携带数据，但紧随其后的独立 HTTP 小包没有额外序列化成本；不应再加一整段等待。

用 c1、c2 表示题中两个到 C 的不同资源，b1、b2 表示两个到 B 的不同资源。请求顺序为 c1、c2、b1、b2、b1、c1。两种域名都是不同缓存键；不能因域名共享后缀而命中。

| 请求位置 | 缓存行为 | 用时 |
|---|---|---|
| 1、2 | P1、P2 都首次见相应 C 资源 | 各 S+2E+L |
| 3、4 | P1 首次见相应 B 资源 | 各 S+2D+L |
| 5 | b1 仍在 P1 最近两项中 | 4L |
| 6 | c1 已被 P1 淘汰，但仍在 P2 | S+2(E−L)+L |

第 5 个请求只需要 A—P1 的握手与请求响应往返，共 4L。P2 没看见发往 B 的请求，所以它的两项缓存仍是 c1、c2；第 6 个请求不必走 P2—C 的两次 L。

$$
\begin{aligned}
D_{\mathrm{seq}}
&=2(S+2E+L)\\
&\quad+2(S+2D+L)+4L\\
&\quad+[S+2(E-L)+L]\\
&=58L+20I.
\end{aligned}
$$

源解答的一个叙述错误是声称前两次“去不同服务器”：题面明确两次都到 Host C。正确的未命中理由是不同资源/主机名缓存键，不能擅自改拓扑。另一个符号问题在手绘 S12、S13：图中文字把 LC、LB 写成含系数 2 的往返量，而正文定义为单向量且外面再乘 2。本页统一用 D、E 为单向量，避免重复乘二；最终结果与官方正文一致。

</details>

### 4.2 无缓存、全部并发（W4〔印5〕；S11，示意见S12–13）

<details><summary>取关键路径最大值，不是求和</summary>

这里忽略报文大小与处理时间，也没有题 3 那种大文件共享带宽项。所有请求并发且题设排除缓存，完成时刻取各请求完成时间的最大值。C 比 B 多一段接入链路，故由到 C 的请求决定：

$$
D_{\mathrm{parallel}}=S+2E+L=12L+4I.
$$

不能再把六条请求相加，也不能让重复资源因“先完成的并发请求”而缓存命中——这已被本小题假设排除。现实连接数、代理 CPU 与带宽限制均不在本题模型内。

</details>
